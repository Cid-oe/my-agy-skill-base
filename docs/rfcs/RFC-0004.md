# AGY RFC-0004: Artifact System

Status: Draft
Subsystem: Kernel / Artifact System
Depends on: Skill Resolver (RFC-0001, stable), Skill Registry & Loader (RFC-0002, stable), Policy Engine (RFC-0003, stable)
Depended on by: Scheduler, Executor/Runtime, Event Bus, RuntimeState, Observation Engine, Resource Manager, Learning Engine — every subsystem that produces or consumes data inside AGY

---

## 0. Preface: Why This RFC Exists Now, Out of the Handoff's Stated Order

AGY_HANDOFF.md names RFC-0004 as "Execution Runtime." RFC-0003 itself recommends Scheduler as RFC-0004. This RFC supersedes both orderings, on accepted findings from the prior architecture review:

- Scheduler should not be designed until Artifact, Event Bus, and RuntimeState exist.
- Every subsystem already assumes an Artifact abstraction — Resolver produces plans, Executor produces outputs, Policy produces evidence, Learning consumes history, Observation consumes telemetry — but no such abstraction has ever been formally specified. RFC-0001 through RFC-0003 each independently invented ad hoc shapes for the data they pass around (`ExecutionPlan`, `PolicyDecision`, `LedgerSnapshot`) with no shared contract between them.
- RuntimeState is referenced by name in RFC-0001 (`RuntimeState.priorFailures`) and RFC-0003 (`context.priorFailures`, `context.ledger`) but has no owning specification anywhere.
- Event Bus is assumed live and available by RFC-0003 §4.6 ("every `evaluate()` call... results in exactly one lifecycle event emitted by the framework") but its delivery semantics, ordering guarantees, and failure behavior are undefined anywhere in the accepted architecture.

This RFC addresses the first and largest of those four gaps: the Artifact System. It does not design Event Bus or RuntimeState in full — both are named as the necessary next RFCs in §16 and §17 — but it defines the Artifact contract those two subsystems must be built against, since an Event Bus that routes artifact-lifecycle events and a RuntimeState that is itself expressible as artifacts cannot be soundly designed before the thing they route/represent has a schema.

## 1. Executive Overview

### 1.1 Purpose

Every subsystem in AGY currently exchanges data through subsystem-specific, independently-invented shapes. RFC-0001's `ExecutionPlan` and `PlanNode`, RFC-0002's manifest and capability index, RFC-0003's `PolicyDecision` and `PolicyContext` are each internally well-designed but structurally unrelated to one another. There is no shared identity scheme, no shared lineage model, no shared way to say "this thing came from that thing," and no shared persistence contract. Every new subsystem that gets designed either invents a fifth private format or awkwardly reaches into a neighboring RFC's internal types.

The Artifact System exists to close this gap once, centrally, rather than requiring every future RFC to reinvent identity, lineage, checksum, versioning, and storage semantics for whatever data it happens to produce. It is the single answer to the question "what does it mean for one part of AGY to hand something to another part of AGY."

### 1.2 Responsibilities

- Define the canonical `Artifact` envelope: the one shape every unit of cross-subsystem data is wrapped in, regardless of payload type.
- Own artifact identity (`ArtifactID`), lineage (`parentArtifacts`, derivation edges), and immutability guarantees.
- Own the Artifact Store: durable, addressable, content-integrity-checked persistence for artifact payloads and their envelopes.
- Own the Schema Registry: per-`ArtifactType` payload schemas, their versioning, and compatibility rules across schema evolution.
- Define, but not fully implement, the artifact-lifecycle event vocabulary that a future Event Bus RFC must route (§10) — this RFC specifies *which* events exist and *what* they carry; it does not specify delivery guarantees, which belongs to the Event Bus RFC.
- Provide the read/write/query API surface every other Kernel subsystem uses instead of ad hoc storage.
- Define the taxonomy of concrete artifact types AGY currently needs (§5), extensible without a Kernel change (§7).

### 1.3 Non-goals

- **The Artifact System does not decide policy.** Whether a given artifact is *allowed* to be produced, consumed, or referenced by a given subsystem is a Policy Engine question (RFC-0003), not an Artifact System question. The Artifact System enforces structural integrity (is this a well-formed, checksummed, correctly-versioned artifact) — never semantic permission (should this subsystem be allowed to read it). This mirrors the boundary RFC-0003 §1.3 already drew between itself and RFC-0002's sandbox: two adjacent but non-overlapping authorities, not one subsuming the other.
- **The Artifact System is not the Event Bus.** It emits a well-defined vocabulary of lifecycle events (§10) but does not implement pub/sub delivery, backpressure, ordering, or subscriber management. That is explicitly out of scope and named as the next required RFC (§16, §17).
- **The Artifact System is not RuntimeState.** RuntimeState (referenced by RFC-0001 and RFC-0003, never specified) is a *consumer* of this system in the design proposed here — a `RuntimeStateSnapshot` is one artifact type among many (§5.11) — but the live, mutable, in-memory RuntimeState object itself, and its update semantics, are out of this RFC's scope and are named as the second required next RFC.
- **The Artifact System does not execute anything.** It is a passive data-plane component: subsystems write artifacts to it and read artifacts from it. It has no scheduling authority, no opinion on execution order, and — consistent with the accepted finding that the Kernel should shrink to bootstrapping/lifecycle/DI/event-routing/shutdown only — the Artifact System is itself a Kernel-adjacent service the Kernel wires up, not Kernel logic itself.
- **The Artifact System does not solve distributed consensus.** Multi-instance AGY deployments sharing one Artifact Store is named explicitly as future work (§16), not designed here, for the same reason RFC-0002 and RFC-0003 deferred their own distributed variants: no current single-instance requirement justifies the added complexity now (Design Principle #3, restated as still governing in this RFC).

### 1.5 A Deliberate Boundary: Not Everything Becomes an Artifact

The design constraint states "everything exchanged inside AGY must eventually become an Artifact." This RFC interprets "exchanged" narrowly and states the interpretation explicitly rather than applying the constraint mechanically:

- **Cross-subsystem data that outlives a single call, or that another subsystem consumes later, becomes an Artifact.** `ExecutionPlan`, `PolicyDecision`, execution outputs, telemetry, evidence — all artifacts.
- **Configuration, manifests, and capability declarations (RFC-0002's skill manifests, RFC-0003's policy manifests) do not become artifacts.** They describe what a subsystem *is capable of*, evaluated at discovery/load time, not data one subsystem *hands to* another during execution. Manifests are inputs to the Registry's own trust/validation pipeline (RFC-0002 §3–§7), which this RFC does not re-scope. Forcing manifests into the Artifact model would conflate "static capability declaration, validated once at load" with "dynamic execution-time data, produced and consumed continuously" — two different lifecycles that RFC-0002's manifest lifecycle (`DISCOVERED -> VALIDATING -> REGISTERED -> ACTIVE`) and this RFC's artifact lifecycle (§3) are not interchangeable versions of.
- **In-process function call arguments/returns within a single subsystem's own internal logic do not become artifacts.** The Artifact System governs *cross-subsystem* exchange. A policy's internal helper function passing data to another internal helper function is not in scope — turning every internal call into an artifact write would be exactly the kind of unnecessary abstraction the design constraints ask this RFC to avoid.

This boundary is itself flagged as a judgment call, not a fact derived from the constraints — documented explicitly in §17.1 as a self-review item, since a different, stricter reading of "everything exchanged" is defensible and would produce a different scope.

## 2. Design Principles

### 2.1 Immutability

An artifact, once created, is never mutated. Every field described in §4 is write-once. Corrections, updates, and refinements are expressed by creating a **new** artifact whose `parentArtifacts` references the one it supersedes (§8.4), never by rewriting the original in place.

This is not a stylistic preference; it is what makes every other guarantee in this RFC possible:

- **Caching is only safe under immutability.** RFC-0003 §3.8's decision cache already depends on this principle implicitly (a cached `PolicyDecision` is only valid if the underlying data it was computed from cannot silently change). The Artifact System makes that assumption explicit and structural instead of a convention every subsystem must independently uphold.
- **Lineage graphs (§8) are only acyclic if artifacts cannot be edited after other artifacts reference them.** A mutable artifact would let a lineage edge point at something that no longer resembles what it pointed at when the edge was created — silently invalidating every consumer's audit trail.
- **Audit logs (a consumer of this system, e.g. RFC-0003 §12.7's policy decision log) require that "what was decided" cannot retroactively change.** Immutability at the storage layer is what makes an audit log more than a convention.

Immutability is enforced at the Artifact Store's write API (§9.3): there is no `update()` method. There is only `create()` and `supersede()`, and `supersede()` is implemented as `create()` with a lineage edge, never as an in-place mutation (§6.1, §8.4).

### 2.2 Traceability

Every artifact must be able to answer, without external context: *who produced me, from what, when, and why.* This is implemented structurally, not left to producer discipline:

- `producer` (§4) is a mandatory field — no artifact can be created without declaring which subsystem, and which specific execution context, produced it.
- `parentArtifacts` (§4, §8) is mandatory whenever an artifact was derived from prior data — an artifact with no parents is only valid for the small set of genuinely-root artifact types (e.g. `UserIntent`, §5.15 — the one type that legitimately originates outside AGY's own artifact graph).
- `lineage` is not a separate stored field but a *derived, queryable view* over the `parentArtifacts` graph (§8) — this avoids the redundancy and drift risk of storing a transitive-closure field that could fall out of sync with the edges it's supposed to summarize.

Traceability is the property that makes RFC-0003's core requirement — "every decision is auditable" — actually implementable rather than aspirational: a `PolicyDecision` artifact's `evidence` field (§5.4) references other artifacts, and each of those has its own producer and parents, recursively, all the way back to a root `UserIntent` or `ExecutionPlan`.

### 2.3 Determinism

The Artifact System's own machinery — ID generation, checksum computation, schema validation — must be deterministic: the same payload, produced under the same schema version, must always produce the same checksum and pass or fail validation identically regardless of when or on which host it's evaluated. This is the same discipline RFC-0001 §3 established for the Resolver ("same inputs, same plan") and RFC-0003 §4.4 established for policy `evaluate()` — applied here as the third instance of an AGY-wide invariant, not a subsystem-local choice.

Determinism does **not** extend to artifact *content* — an `ExecutionResult` artifact produced by a non-deterministic model call is not required to be reproducible in its payload. What must be deterministic is the Artifact System's *handling* of whatever payload it's given: the same bytes always hash the same way, the same schema always validates the same shape the same way.

### 2.4 Versioning

Every artifact declares two independent version concepts, and this RFC treats conflating them as a design error to avoid:

1. **`ArtifactType` schema version** (§4, §7) — which version of the payload schema for this artifact's *type* was in effect when it was created. Governs validation and migration.
2. **Artifact lineage version** — implicit in the `supersedes` relationship (§8.4): artifact B superseding artifact A is a version relationship between *instances*, not between *schemas*. These are orthogonal: a superseding artifact can use the same schema version as what it supersedes, or a newer one, independently.

Schema version compatibility rules are owned by the Schema Registry (§7), not by individual artifact instances — an instance only ever declares which version it was validated against.

### 2.5 Schema Evolution

Payload schemas must be able to change over AGY's lifetime without invalidating every artifact ever stored. This RFC adopts semantic versioning for artifact type schemas (`major.minor.patch`) with explicit compatibility rules (§7.3–7.4): additive, backward-compatible changes bump `minor`; breaking changes bump `major` and require a registered migration path (§7.4) before old artifacts of that type can be read by code expecting the new major version.

### 2.6 Auditability

Every mutating operation against the Artifact Store (`create`, `supersede`, `archive`, `delete` — §3, §9.3) is itself recorded, following the exact pattern RFC-0003 §12.6–12.7 already established for policy decisions: an append-only log of Artifact System operations, distinct from the artifacts themselves, sufficient to answer "what happened to this artifact over its lifetime" even after the artifact itself has been archived or (in the rare permitted case) deleted (§3.8).

## 3. Artifact Lifecycle

```
  DISCOVERED*  ->  CREATED  ->  VALIDATING  ->  VALIDATED  ->  STORED
                                     |
                                     v
                                 REJECTED (malformed payload, schema
                                            mismatch, checksum failure)

  STORED  ->  ACTIVE (available for consumption)
  ACTIVE  ->  REFERENCED (read by one or more consumers — not a state
                           transition in the strict sense, see §3.6)
  ACTIVE  ->  SUPERSEDED (a newer artifact points back via parentArtifacts
                           with relationship=supersedes, §8.4)
  ACTIVE / SUPERSEDED  ->  ARCHIVED (moved to cold storage per retention
                                      policy, §6.5, still readable)
  ARCHIVED  ->  DELETED (retention policy expiry or explicit operator
                          action — bounded, audited, see §3.8)

  * DISCOVERED only applies to artifacts recovered from storage at boot
    (e.g. after a crash) rather than freshly created in-process — see §3.1.
```

### 3.1 Discovery

"Discovery" for artifacts is not the same concept as RFC-0002's skill discovery (scanning disk for packages). An artifact is discovered only in the recovery sense: on Artifact Store startup, or when a subsystem queries for artifacts it didn't itself just create (e.g. the Scheduler querying for `ExecutionPlan` artifacts produced by a prior Resolver run after a process restart). Freshly created, in-process artifacts skip discovery entirely and enter the lifecycle at `CREATED`.

This distinction matters because RFC-0002's discovery involves untrusted bytes on disk needing structural validation before any code runs (RFC-0002 §7's checksum → signature pipeline, reused). Artifact discovery, by contrast, is reading data this same AGY instance already validated and stored — the trust boundary is different (§11.5), and re-running full validation on every read would be wasteful. Discovery here means locating and deserializing the envelope; checksum verification (§11.2) still happens on every read regardless, as a corruption check, not a trust check.

### 3.2 Creation

A producer calls `ArtifactStore.create()` (§9.3) with a payload and required envelope fields (§4). Creation is a single atomic operation: the envelope is assembled, the payload checksum is computed, the `ArtifactID` is generated (§4.1), and the combined envelope+payload is handed to Validation. An artifact does not exist — is not visible to any query, is not assigned a durable ID that any other artifact could reference — until it has passed Validation and reached `STORED`. This closes off a class of race condition where a producer hands out a reference to an artifact that later fails validation.

### 3.3 Validation

Validation is a two-stage gate, mirroring the structural pattern RFC-0002 §7 and RFC-0003 §3.4 both already use (schema → checksum → signature), applied here to artifact payloads instead of skill/policy packages:

1. **Envelope validation**: are all mandatory fields (§4) present and well-typed? Is `ArtifactType` a registered type (§7)? Is the declared schema version registered and not explicitly deprecated-for-writes (§7.5)?
2. **Payload validation**: does the payload conform to the JSON Schema (or equivalent) registered for this `ArtifactType`+version in the Schema Registry (§7)?

A failure at either stage transitions the artifact to `REJECTED` — it is never partially stored, and a `REJECTED` artifact does not receive a durable `ArtifactID` usable by other artifacts' `parentArtifacts` (an unvalidated thing cannot be a valid ancestor of anything). This is the same fail-closed posture RFC-0001 §9, RFC-0002 §14, and RFC-0003 §13.4 already established as an AGY-wide invariant — restated here as its fourth application, not a new policy.

### 3.4 Storage

Covered fully in §6.

### 3.5 Transport

"Transport" is the act of an artifact reference (its `ArtifactID`, not necessarily its full payload) crossing a subsystem boundary — e.g. the Scheduler receiving a reference to a `PolicyDecision` artifact from the Policy Engine. This RFC specifies that **references are the unit of transport, not payloads**, for the same reason RFC-0003's own audit log stores a context *hash* rather than the full context object (RFC-0003 §12.7): passing large payloads by value through every subsystem boundary would duplicate storage and make the "single source of truth" property of the Artifact Store meaningless. A consumer holding an `ArtifactID` fetches the payload from the Store only when it actually needs the content (§9.4's streaming interface exists specifically for this — large payloads are never forced into memory just to be passed along).

### 3.6 Consumption

Consumption — a subsystem reading an artifact's payload — is deliberately **not modeled as a lifecycle state transition** in §3's diagram, only noted there for completeness. An artifact does not change state by being read; `REFERENCED` in the diagram denotes that a consumption *event* is emitted (§10.6: `ArtifactReferenced`) and optionally recorded for audit/lineage purposes (a consumer can register itself as a formal `consumer` on the envelope, §4, if it wants that relationship to be durably queryable rather than only event-logged) — but reading an artifact never mutates it, consistent with §2.1. Read access is governed by Policy Engine decisions at the call site (§1.3), not by the Artifact System itself.

### 3.7 Archival

An artifact moves from `ACTIVE`/`SUPERSEDED` to `ARCHIVED` per its `retentionPolicy` (§4, §6.5) — typically time-based ("move to cold storage after 30 days of no reads") or event-based ("archive once superseded and no active consumer holds a reference"). Archival changes *where* the payload lives (hot store vs. cold store, §6.1) and may change access latency, but never changes the envelope, the checksum, or the artifact's validity — an archived artifact is still a complete, verifiable artifact, just one the Store deprioritizes for fast access.

### 3.8 Deletion

Deletion is the one lifecycle transition this RFC treats as exceptional rather than routine, consistent with the immutability principle (§2.1): an immutable, audit-critical system should default to *never* deleting, and deletion should require a deliberate, bounded, audited exception path, not a routine garbage-collection sweep indistinguishable from any other operation.

Deletion is permitted only for:
- **Explicit retention policy expiry** on artifact types whose `retentionPolicy` (§4) declares a hard expiry (e.g. high-volume `Telemetry` artifacts with a 90-day cap) — bounded, predictable, and disclosed at creation time via the artifact's own envelope, not decided later.
- **Explicit operator action** (e.g. legal/compliance deletion request) — always logged to the Artifact System's own audit trail (§2.6) with the operator identity and reason, and always leaves a **tombstone** artifact behind (§6.5) recording that a deletion occurred, its `ArtifactID`, timestamp, and reason — the payload is gone, but the *fact that something was here and was deleted* is never itself deleted. This is what keeps a deletion from creating an untraceable hole in the lineage graph (§8): a child artifact whose parent was deleted still resolves to a tombstone, not a dangling, silently-broken reference.

Deletion of an artifact that other artifacts' `parentArtifacts` reference does **not** cascade — children are never deleted because a parent was. They resolve their parent reference to the tombstone.

## 4. Canonical Artifact Model

### 4.1 The Envelope

Every artifact, regardless of `ArtifactType`, is wrapped in this envelope. The envelope is what the Artifact System itself understands and enforces; the `payload` field's internal shape is owned by the Schema Registry (§7) per-type and is opaque to the envelope-handling machinery.

```typescript
interface Artifact<TPayload = unknown> {
  // Identity
  readonly id: ArtifactID;                    // §4.2

  // Type & Schema
  readonly artifactType: string;               // registered type name, §5, §7
  readonly schemaVersion: string;               // strict semver, §2.5, §7

  // Provenance
  readonly producer: ArtifactProducer;           // §4.3
  readonly consumers: ArtifactConsumerRef[];      // append-only, populated over time, §4.4
  readonly createdAt: Timestamp;                 // ISO-8601, UTC, monotonic per producer

  // Lineage
  readonly parentArtifacts: ParentRef[];          // §4.5, §8
  // Note: transitive "lineage" is a derived query (§2.2, §8.2), not a stored field.

  // Trust & Provenance Signals
  readonly confidence: number | null;            // 0.0-1.0, producer-declared, §4.6
  readonly evidence: ArtifactID[];                // supporting artifacts, §4.7

  // Content
  readonly metadata: Record<string, JSONValue>;    // producer-defined, non-authoritative, §4.8
  readonly payload: TPayload;                     // type-specific, schema-validated, §5

  // Integrity
  readonly checksum: string;                     // sha256 over canonical payload bytes, §11.2
  readonly signature: string | null;              // present if producer is a sandboxed
                                                  // third-party plugin, §11.3

  // Governance
  readonly retentionPolicy: RetentionPolicy;      // §4.9, §6.5

  // Lifecycle (mutable metadata only — never the fields above)
  status: ArtifactStatus;                        // §3's states; the ONE field the Store
                                                  // itself is permitted to change post-creation,
                                                  // since lifecycle state is Store bookkeeping,
                                                  // not artifact content (§2.1 still holds:
                                                  // payload/envelope-proper are never mutated)
}
```

### 4.2 ArtifactID

```typescript
type ArtifactID = string;  // ULID: 26 chars, lexicographically sortable by creation time,
                            // no coordination required across producers (RFC-0004 §4.2
                            // deliberately reuses the same rationale as the ULID choice
                            // flagged in the prior architecture-review session: sortable,
                            // unique, no central allocator needed — important for a
                            // system where Resolver, Executor, and Policy Engine all
                            // produce artifacts concurrently with no shared sequence).
```

ULIDs were chosen over UUIDv4 specifically because lexicographic sortability by creation time is a load-bearing property for §6.2's indexing strategy and §8's lineage-graph traversal (children are, by construction, ID-sortable after their parents in the overwhelming majority of cases, which is a useful index locality property even though it is not relied upon as a correctness guarantee — the `parentArtifacts` graph, not ID ordering, is the authoritative lineage source).

### 4.3 ArtifactProducer

```typescript
interface ArtifactProducer {
  readonly subsystem: string;          // "resolver" | "executor" | "policy-engine" | ...
  readonly componentId: string | null;  // e.g. specific skill id (RFC-0002) or policy id
                                        // (RFC-0003) if the producer is a plugin, not the
                                        // framework itself
  readonly version: string;            // producer's own version, for reproducibility
  readonly executionContextId: string;  // correlates to the RuntimeState/session this
                                        // artifact was produced within (§17.2 — this field
                                        // is a forward reference to the not-yet-specified
                                        // RuntimeState RFC; defined here as an opaque string
                                        // now, to be given a formal type once that RFC lands)
}
```

### 4.4 ArtifactConsumerRef

```typescript
interface ArtifactConsumerRef {
  readonly subsystem: string;
  readonly componentId: string | null;
  readonly firstReadAt: Timestamp;
  readonly readCount: number;           // updated by the Store on each read — the one other
                                        // Store-owned mutable field alongside `status`
}
```

Populated lazily: an artifact with zero reads has an empty `consumers` array. This is metadata *about* consumption, not a mechanism *for* consumption — a subsystem does not need to be listed here to read an artifact (access control is Policy Engine's job, §1.3); this field exists purely for observability and lineage-graph completeness (§8.3's "consumes" edge type is derived from this field, not the other way around).

### 4.5 ParentRef

```typescript
interface ParentRef {
  readonly parentId: ArtifactID;
  readonly relationship: "derivedFrom" | "supersedes" | "references";  // §8
}
```

Three relationship types, not more — kept deliberately small (mirroring RFC-0003 §5.2's fixed-field-set philosophy for `PlanNodeModification`, applied here to keep the lineage graph's edge semantics enumerable and every consumer's graph-traversal logic exhaustive rather than needing to handle an open-ended edge vocabulary). `derivedFrom` is the general case (this artifact was computed from that one). `supersedes` is the special case underlying immutable-update (§2.1, §8.4). `references` is a weak edge — "this artifact points at that one for context, but is not derived from its content" (e.g. a `Decision` artifact referencing a `Documentation` artifact it cited, without the decision having been *computed from* the documentation in the same sense a `PolicyDecision` is computed from a `PolicyContext`).

### 4.6 Confidence

```typescript
confidence: number | null;   // 0.0–1.0, or null if the producer has no meaningful
                              // confidence signal for this artifact type (e.g. a
                              // RepositorySnapshot has no "confidence" — it either
                              // captured the repo state or it didn't)
```

Reuses the same 0.0–1.0 scale RFC-0003 §5.1's `PolicyDecision.confidence` and RFC-0001's `confidenceThreshold` mechanism already establish — deliberately not a new scale, so a `ConfidencePolicy`-style consumer (RFC-0003 §7.6) can reason about artifact confidence and policy-decision confidence with the same comparator logic.

### 4.7 Evidence

```typescript
evidence: ArtifactID[];   // artifacts this one's content is substantiated by
```

Distinct from `parentArtifacts`: an artifact can be *derived from* one set of artifacts (`parentArtifacts`, computational lineage) while being *substantiated by* a different, possibly overlapping set (`evidence`, epistemic support). A `Decision` artifact (§5.5) is `derivedFrom` the `ExecutionPlan` node it decided about, but its `evidence` might point at several `ExecutionResult` artifacts from earlier nodes that informed the decision without the decision being computed as a pure function of them the way `derivedFrom` implies. This mirrors RFC-0003 §5.1's own `PolicyDecision.evidence: EvidenceRef[]` field precisely — RFC-0003 already needed this exact concept; this RFC gives it a formal home instead of leaving it as a bespoke RFC-0003-local type.

### 4.8 Metadata

```typescript
metadata: Record<string, JSONValue>;   // producer-defined, non-authoritative
```

Explicitly non-authoritative: nothing in the Artifact System's own logic (validation, lineage traversal, retention) may key off `metadata` contents, only off typed envelope fields and the schema-validated `payload`. This prevents `metadata` from becoming an untyped escape hatch that slowly accretes load-bearing behavior outside the schema system — the same failure mode RFC-0002 §3.2's manifest design implicitly guards against by keeping declared fields typed and validated rather than free-form.

### 4.9 RetentionPolicy

```typescript
interface RetentionPolicy {
  readonly tier: "hot" | "warm" | "cold";               // §6.1
  readonly archiveAfter: DurationSpec | null;             // null = never auto-archive
  readonly deleteAfter: DurationSpec | null;               // null = never auto-delete (default)
  readonly deletionRequiresApproval: boolean;              // true for any artifactType touching
                                                           // Evidence, Decision, SecurityFinding —
                                                           // see §6.5's per-type defaults table
}
```

Declared per-`ArtifactType` as a default in the Schema Registry (§7.2), overridable per-instance only within bounds the type's registered policy permits (a producer cannot grant itself a shorter retention than its type's registered minimum for audit-critical types — this is a fail-closed constraint enforced at creation-time validation, §3.3).

### 4.10 Checksum & Signature

Covered fully in §11.2–11.3.

## 5. Artifact Taxonomy

Each type below is defined by: **purpose**, **payload schema shape** (illustrative, not exhaustive — full schemas live in the Schema Registry, §7), **typical producer/consumers**, and **relationship notes**. This taxonomy is the registered set at RFC-0004's ratification; §7 defines how new types are added without a Kernel change.

### 5.1 ExecutionPlan

**Purpose**: The artifact form of RFC-0001's Resolver output. **Producer**: Resolver. **Consumers**: Policy Engine (evaluates each `PlanNode`), Scheduler (future), Executor (future).

```typescript
interface ExecutionPlanPayload {
  planId: string;                 // RFC-0001-native plan identifier, distinct from ArtifactID —
                                  // the Resolver's own internal plan concept predates and is
                                  // wrapped by, not replaced by, the Artifact envelope
  nodes: PlanNode[];               // RFC-0001 §-defined shape, referenced not redefined here
  fallbackChains: Record<string, string[]>;  // RFC-0001 §10
  resolvedAt: Timestamp;
}
```

**Relationship notes**: An `ExecutionPlan` artifact is typically a root or near-root in the lineage graph — its `parentArtifacts` may point to a `UserIntent` artifact (§5.15) if one exists, or be empty if the plan originated from a non-artifact-tracked trigger (a gap flagged in §17.3).

### 5.2 ExecutionResult

**Purpose**: The output of a single executed `PlanNode`. **Producer**: Executor (not yet designed — this RFC specifies the artifact shape Executor must produce into, per the accepted finding that Artifact must precede Scheduler/Executor design). **Consumers**: Policy Engine (continuous evaluation, RFC-0003 §6.4), downstream `PlanNode`s consuming this as input, Observation Engine (future).

```typescript
interface ExecutionResultPayload {
  nodeId: string;                  // RFC-0001 PlanNode id
  status: "success" | "failure" | "partial";
  output: JSONValue | ArtifactID;   // small outputs inline; large outputs stored as a
                                    // separate artifact and referenced (§3.5, §12.4)
  observedConfidence: number | null;  // feeds RFC-0003 §7.6 ConfidencePolicy directly
  durationMs: number;
  resourceUsage: ArtifactID;         // reference to a ResourceUsage artifact (§5.18)
}
```

**Relationship notes**: `parentArtifacts` includes the `ExecutionPlan` artifact (`derivedFrom`) and any `ExecutionResult` artifacts from upstream nodes this node consumed (`derivedFrom`).

### 5.3 Evidence

**Purpose**: A standalone artifact substantiating a claim, decision, or downstream action — the artifact-system-native home for what RFC-0003 §7.5's `EvidencePolicy` checks for. **Producer**: any subsystem; commonly Executor (a skill's output that another node/policy will cite) or a human operator (manual evidence attachment). **Consumers**: `EvidencePolicy` (RFC-0003 §7.5), any `Decision` artifact's `evidence` field.

```typescript
interface EvidencePayload {
  claim: string;                    // what this evidence supports, human-readable
  evidenceStandard: string;          // matches RFC-0003 §7.5's configured evidence-standard vocabulary
  sourceType: "execution-output" | "external-fetch" | "human-attestation" | "derived-computation";
  content: JSONValue | ArtifactID;
}
```

### 5.4 Decision

**Purpose**: The artifact form of RFC-0003's `PolicyDecision`. **Producer**: Policy Engine. **Consumers**: Scheduler (future), audit tooling, `RetryPolicy`/`ConfidencePolicy` reading `priorDecisions` (RFC-0003 §9.1).

```typescript
interface DecisionPayload {
  policyId: string;
  outcome: "ALLOW" | "DENY" | "MODIFIED" | "ESCALATE" | "DEFER";  // RFC-0003 §5.1, unchanged
  rationale: string;
  modification: PlanNodeModification | null;   // RFC-0003 §5.2
  escalateTarget: EscalationTarget | null;
}
```

**Relationship notes**: This is the first concrete example of a naming collision worth flagging (§17.4): RFC-0003 already defines a type called `PolicyDecision` with near-identical shape. This RFC's `Decision` artifact **wraps** RFC-0003's `PolicyDecision` as its payload rather than replacing it — RFC-0003's internal type is unchanged; the Artifact System adds an envelope around it for cross-subsystem exchange and persistence. RFC-0003 itself is not modified by this RFC (per the instruction to document cross-RFC findings separately rather than silently changing accepted contracts — see §17.4).

### 5.5 Telemetry

**Purpose**: Low-level operational signal — timing, resource counters, health pings. **Producer**: any subsystem. **Consumers**: Observation Engine (future). High volume, short default retention (§6.5).

```typescript
interface TelemetryPayload {
  metric: string;
  value: number;
  unit: string;
  tags: Record<string, string>;
}
```

### 5.6 Metrics

**Purpose**: Aggregated/derived Telemetry over a time window — distinct from raw `Telemetry` in the same way RFC-0003 §7.3 distinguishes plan-time cost *estimate* from Ledger-tracked *actual* accrual: `Metrics` artifacts are computed summaries, `derivedFrom` a set of `Telemetry` artifacts, not raw signal.

```typescript
interface MetricsPayload {
  windowStart: Timestamp;
  windowEnd: Timestamp;
  aggregation: "sum" | "avg" | "p50" | "p95" | "p99" | "count";
  metric: string;
  value: number;
}
```

### 5.7 Prompt

**Purpose**: A model-directed input, captured as a first-class artifact so model interactions are auditable and re-derivable, not just logged as unstructured text. **Producer**: any skill invoking a model. **Consumers**: `Completion` artifacts (`derivedFrom`), Learning Engine (future).

```typescript
interface PromptPayload {
  role: "system" | "user" | "assistant";
  content: string;
  modelTarget: string;               // which model this was directed at
  templateId: string | null;          // if generated from a registered prompt template
}
```

### 5.8 Completion

**Purpose**: A model's response to a `Prompt` artifact. **Producer**: the skill/subsystem that invoked the model. **Relationship notes**: `parentArtifacts` always includes the `Prompt` (`derivedFrom`) — a `Completion` with no `Prompt` parent is a validation error (§3.3), since it represents an unexplainable model output with no recorded stimulus, directly undermining §2.2's traceability principle.

```typescript
interface CompletionPayload {
  content: string;
  modelUsed: string;                // actual model, may differ from Prompt.modelTarget
                                    // if routed (RFC-0001's Model Router)
  finishReason: string;
  tokenUsage: { input: number; output: number };
}
```

### 5.9 ModelOutput

**Purpose**: A broader category than `Completion` for structured (non-text) model outputs — embeddings, classifications, tool-call results — kept as a distinct type rather than overloading `Completion`, since a `Completion`'s payload is specifically prose/turn-based and `ModelOutput`'s is not. This separation avoids the temptation to make `Completion.content` a polymorphic `any`, which would weaken schema validation (§7) for the common text case.

```typescript
interface ModelOutputPayload {
  outputKind: "embedding" | "classification" | "tool-call" | "structured-extraction";
  data: JSONValue;
  modelUsed: string;
}
```

### 5.10 RepositorySnapshot

**Purpose**: Captures repository state consumed by RFC-0001's `repository-map` skill and RFC-0003's `repositoryMetadata` context field (RFC-0003 §9.1). **Producer**: the `repository-map` skill. **Consumers**: Resolver, Policy Engine.

```typescript
interface RepositorySnapshotPayload {
  rootPath: string;
  commitHash: string | null;
  fileCount: number;
  languageBreakdown: Record<string, number>;
  contentRef: ArtifactID;            // large file trees stored as a separate large-artifact
                                     // reference, §12.4, not inlined
}
```

### 5.11 RuntimeStateSnapshot

**Purpose**: A point-in-time capture of the not-yet-formally-specified RuntimeState, expressed as an artifact so it can be checkpointed, audited, and referenced by other artifacts (e.g. a `Decision`'s context hash, RFC-0003 §12.7). **Producer**: whatever subsystem owns RuntimeState (undetermined until the RuntimeState RFC — flagged as an open dependency, §16). This RFC defines the *artifact wrapper*; it explicitly does not define RuntimeState's live, mutable shape.

```typescript
interface RuntimeStateSnapshotPayload {
  sessionId: string;
  capturedAt: Timestamp;
  priorFailures: JSONValue;           // RFC-0001 §3 / RFC-0003 §9.1's ResolutionFailure[],
                                      // typed loosely here pending RuntimeState RFC
  ledgerSnapshot: ArtifactID;          // reference to a ResourceUsage-family artifact
  sessionGrants: JSONValue;            // RFC-0003 §9.1 Permission[]
}
```

### 5.12 Checkpoint

**Purpose**: An Executor-produced (future) snapshot enabling resumption/rollback of a partially-executed plan, per the handoff's stated RFC-0004 (now RFC-0005+) goal of "checkpoints, rollback." **Producer**: Executor. Distinct from `RuntimeStateSnapshot`: a `Checkpoint` is scoped to a specific plan's execution progress; `RuntimeStateSnapshot` is scoped to a session's broader state.

```typescript
interface CheckpointPayload {
  planArtifactId: ArtifactID;          // the ExecutionPlan this checkpoints
  completedNodeIds: string[];
  pendingNodeIds: string[];
  resumeToken: JSONValue;
}
```

### 5.13 Error

**Purpose**: A structured failure record — distinct from a `Decision` with outcome `DENY` (a Policy Engine judgment) and distinct from `ExecutionResult` with status `failure` (an execution outcome) — `Error` is the artifact for exceptional, unexpected conditions: a crash, a timeout, a malformed input. RFC-0003 §13.1–13.2's `PolicyFailed` events, once an Event Bus exists (§16), would naturally accompany an `Error` artifact.

```typescript
interface ErrorPayload {
  errorClass: string;
  message: string;
  stackRef: ArtifactID | null;         // large stack traces stored separately, §12.4
  recoverable: boolean;
}
```

### 5.14 Warning

**Purpose**: Sub-error-severity structured signal — degraded-but-continuing conditions (e.g. a policy timeout that fell back per RFC-0003 §13.4 but didn't halt the pipeline).

```typescript
interface WarningPayload {
  warningClass: string;
  message: string;
  severity: "low" | "medium" | "high";
}
```

### 5.15 SecurityFinding

**Purpose**: Output of `SecurityPolicy` (RFC-0003 §7.1, referenced but not detailed in the reviewed excerpt) or any security-scanning skill — a `critical`-priority-adjacent artifact type whose `retentionPolicy` defaults to `deletionRequiresApproval: true` regardless of instance-level override attempts (§4.9, §6.5).

```typescript
interface SecurityFindingPayload {
  category: string;
  severity: "info" | "low" | "medium" | "high" | "critical";
  description: string;
  affectedResource: string;
  remediation: string | null;
}
```

### 5.16 ArchitectureFinding

**Purpose**: The artifact type this very RFC's own prior-session architecture review would have produced, had the Artifact System existed at the time — self-referential but genuinely useful: a structured record of architecture-review output (inconsistency, gap, coupling, risk findings) with severity, so future reviews are queryable history rather than only prose in chat transcripts.

```typescript
interface ArchitectureFindingPayload {
  category: "inconsistency" | "gap" | "coupling" | "scalability" | "security" | "debt";
  severity: "critical" | "high" | "medium" | "low";
  description: string;
  affectedRFCs: string[];
  blocksFutureRFCs: boolean;
}
```

### 5.17 Documentation

**Purpose**: Generated or human-authored explanatory content tied to a specific artifact or subsystem — e.g. an `explain()` output (RFC-0003 §4.5) materialized as a durable artifact rather than only computed on demand.

```typescript
interface DocumentationPayload {
  subject: ArtifactID | string;        // the artifact or subsystem this documents
  content: string;
  format: "markdown" | "plain";
}
```

### 5.18 UserIntent

**Purpose**: The one artifact type permitted to have an empty `parentArtifacts` array as a matter of course (§4.1's traceability principle names this as the deliberate exception) — the artifact representing what a human asked AGY to do, at the root of most lineage graphs.

```typescript
interface UserIntentPayload {
  rawInput: string;
  interpretedGoal: string | null;
  sessionId: string;
}
```

### 5.19 ResourceUsage

**Purpose**: The artifact-system home for what RFC-0003 §9.2's `LedgerSnapshot` and `ResourceUsageSnapshot` context fields need — closing the "Execution Ledger has no owning subsystem" gap identified in the prior architecture review. This RFC does not claim to fully design the Ledger (that remains Resource Manager's eventual responsibility, per the existing roadmap), but it gives Ledger data a concrete, storable, queryable artifact shape now, unblocking `CostPolicy` and `RetryPolicy` from depending on an undefined type.

```typescript
interface ResourceUsagePayload {
  cost: { spent: number; currency: string };
  tokens: { input: number; output: number };
  wallClockMs: number;
  scope: "node" | "plan" | "session";
}
```

**Relationship notes**: This is the clearest example in this taxonomy of the Artifact System resolving a gap flagged in the prior review (the phantom Execution Ledger dependency) as a byproduct of defining the taxonomy, rather than requiring a separate fix — documented explicitly here rather than silently claimed as solving Resource Manager's whole scope, which it does not (§17.5).

## 6. Artifact Store

### 6.1 Architecture

Three-tier storage, aligned to `RetentionPolicy.tier` (§4.9):

```
   Producer                                    Consumer
      |                                            ^
      v  create()                        query()/  |
  +-----------------------------------------+  get()|
  |            Artifact Store API             |------+
  |     (envelope validation, checksum,        |
  |      ID generation — §3.2, §3.3, §9)        |
  +-------------------+-----------------------+
                       |
         +-------------+-------------+
         |             |             |
         v             v             v
    +--------+   +---------+   +---------+
    |  HOT    |   |  WARM   |   |  COLD   |
    | (in-mem |   | (local  |   | (object |
    |  + fast |   |  disk/  |   |  store,  |
    |  index) |   |  SSD)   |   |  §6.5)   |
    +--------+   +---------+   +---------+
```

- **Hot**: recently created, actively referenced artifacts. In-memory index + fast local store. Default tier at creation for all types unless the type's Schema Registry default (§7.2) specifies otherwise (e.g. `Telemetry` defaults to warm immediately, given its volume).
- **Warm**: local persistent storage, indexed, not memory-resident by default. Artifacts move here automatically once read frequency drops below a configurable threshold, or immediately for high-volume types.
- **Cold**: archival object storage (§3.7). Full envelope + payload preserved, index entry retained (so queries still find cold artifacts, at higher latency), retrieval requires an explicit fetch rather than being index-served.

Storage backend choice (which physical object store, which local disk format) is explicitly deferred to Resource Manager's eventual RFC (§1.3, §16) — this RFC specifies the tier *model* and the API contract (§9), not the physical implementation.

### 6.2 Indexing

Every artifact is indexed on: `id` (primary key), `artifactType` + `schemaVersion` (type-scoped queries), `producer.subsystem` + `producer.componentId`, `createdAt` (range queries, and the natural sort order given ULID's lexicographic property, §4.2), and `parentArtifacts[].parentId` (the reverse-lineage index enabling "find all children of X" queries, §8.2, without which lineage traversal would require a full scan).

`metadata` fields are **not** indexed by default (§4.8's non-authoritative status extends to indexing — indexing arbitrary producer-defined keys would be an open-ended performance and storage commitment). Types that need a specific metadata field queryable register it explicitly in the Schema Registry (§7.2) as a secondary index, an opt-in exception, not a default.

### 6.3 Caching

Two cache layers, deliberately modeled on RFC-0003 §3.8's two-cache-layer precedent rather than inventing a new caching taxonomy:

1. **Envelope cache**: recently-read artifact envelopes (metadata, not payload) held in memory, keyed by `ArtifactID`, invalidated only by TTL — envelopes are immutable (§2.1) except for `status`/`consumers` (§4.1, §4.4), so this cache never needs write-invalidation for those two mutable fields; a `status` or `consumers` change is tolerated to be briefly stale in cache, since neither field's staleness can cause an incorrect *content* read, only a momentarily-stale bookkeeping view.
2. **Payload cache**: for small payloads only (below a configurable size threshold, §12.1), cached alongside the envelope. Large payloads (§12.4) are never cached in this layer — they're streamed on demand from their storage tier.

### 6.4 Garbage Collection

Distinct from deletion (§3.8): GC here refers only to *tier migration* (hot→warm→cold) and *cache eviction*, never payload removal. Actual payload removal is exclusively the bounded, audited deletion path (§3.8) — this RFC deliberately does not provide an unbounded "garbage collect unused artifacts" sweep, since "unused" is not a safe automatic-deletion criterion for a system whose core promise is auditability (an artifact with zero current reads may still be load-bearing for a future audit query).

### 6.5 Retention (Per-Type Defaults)

| Artifact Type | Default `archiveAfter` | Default `deleteAfter` | `deletionRequiresApproval` |
|---|---|---|---|
| Telemetry | 1 day | 90 days | false |
| Metrics | 7 days | 1 year | false |
| ExecutionResult | 7 days | never (default) | false |
| Decision | 30 days | never | **true** |
| Evidence | 30 days | never | **true** |
| SecurityFinding | never (stays hot/warm) | never | **true** |
| Error / Warning | 3 days | 180 days | false |
| Checkpoint | 1 day after plan completion | 30 days after plan completion | false |
| UserIntent | 30 days | never | false |
| RuntimeStateSnapshot | 7 days | 90 days | false |

Governance-critical types (`Decision`, `Evidence`, `SecurityFinding`) default to never-delete with mandatory approval for any exception — mirroring RFC-0003 §12.6's own audit-log-permanence posture, applied consistently to the broader artifact set rather than left as a Policy-Engine-only guarantee.

### 6.6 Compression

Payloads above a configurable size threshold are compressed at rest (warm/cold tiers) transparently to the API — `get()` (§9.3) always returns decompressed content; compression is a storage-layer optimization invisible above the Store's own boundary, never something a consumer needs to be aware of.

### 6.7 Deduplication

Content-addressable deduplication at the **payload** level only, keyed by `checksum` (§4.10, §11.2): if two artifacts of the same type produce byte-identical payloads (e.g. two `Telemetry` artifacts with identical values in the same window — plausible for zero-delta metrics), the physical payload bytes are stored once, referenced by both envelopes. Envelopes are never deduplicated — two artifacts with identical payloads are still two distinct artifacts with distinct `id`, `producer`, `createdAt`, and lineage, because identity and provenance are envelope properties, not content properties (this is the artifact-system analog of RFC-0001/0002's general principle that structural sameness does not imply identity sameness).

## 7. Schema Registry

### 7.1 Purpose

Owns the payload schema for every registered `ArtifactType`, at every schema version that has ever existed, so that (a) creation-time validation (§3.3) has something concrete to validate against, and (b) an artifact created three schema-versions ago can still be correctly read today.

### 7.2 Registration

New `ArtifactType`s register via a manifest, deliberately reusing the exact three-tier pattern (RFC-0002 skill manifests, RFC-0003 policy manifests, this RFC's artifact type manifests) that has now proven itself twice:

```yaml
artifactType: string
schemaVersion: string          # strict semver
payloadSchema: JSONSchema      # the actual validation schema
defaultRetentionPolicy: RetentionPolicy   # §4.9, §6.5
secondaryIndexes: string[]     # opt-in metadata fields to index, §6.2
checksum: string
```

This means adding a new artifact type — the extensibility goal named directly in the design constraints — never requires a Kernel change, only a new registration, exactly matching RFC-0002 §7.9's precedent for custom policies ("architecturally indistinguishable from built-ins").

### 7.3 Version Compatibility

- **`patch`**: no schema change meaningful to validation (e.g. description-only metadata update to the schema definition itself). Fully compatible in both directions.
- **`minor`**: additive, backward-compatible field additions (new optional fields). An artifact validated against `1.0.0` remains valid reading code written against `1.1.0` (missing optional fields simply absent); code written against `1.0.0` reading a `1.1.0` artifact ignores the unknown additional fields (forward-compatible by construction, since `minor` bumps are additive-only by definition — enforced at registration time, not just by convention: the Schema Registry rejects a `minor` bump that removes or retypes an existing field).
- **`major`**: breaking change. Requires a registered migration (§7.4) before any code path can be guaranteed to read both old and new artifacts of this type correctly.

### 7.4 Migration

A `major` version bump must register a `migrate(oldPayload, fromVersion, toVersion) -> newPayload` function alongside the new schema. Migration is applied **lazily, at read time**, never eagerly rewriting stored artifacts — consistent with immutability (§2.1): the *stored* artifact is never touched; a `get()` call (§9.3) requesting the current schema version transparently runs the migration function on the stored payload before returning it, and the original stored bytes remain exactly as created, checksummed against their original schema version, forever. A caller that explicitly requests the artifact "as originally stored" (an audit use case) can bypass migration and get the raw original payload plus its original schema version tag.

### 7.5 Backward & Forward Compatibility

- **Backward compatibility** (new code reading old artifacts): guaranteed for `minor`/`patch` differences by construction (§7.3); guaranteed for `major` differences only if a migration path is registered — if none exists, `get()` returns a typed `SchemaMigrationUnavailable` error rather than a best-effort guess (fail-closed, consistent with §3.3, §13.3).
- **Forward compatibility** (old code reading new artifacts): guaranteed for `minor`/`patch` only. `major` changes are never forward-compatible by design — old code is not expected to understand a breaking schema change, and no migration is defined in that direction (migrating "down" to an older major version would require inventing data that didn't exist at write time, which this RFC does not attempt).

A type can be marked **deprecated-for-writes** once superseded by a new major version — existing artifacts of the old version remain fully readable (with migration) indefinitely; the Schema Registry simply refuses new `create()` calls declaring the deprecated version.

## 8. Artifact Relationships

### 8.1 Relationship Types (Restated From §4.5)

- **`derivedFrom`** (computational lineage — "I was computed from you")
- **`supersedes`** (versioning — "I am the corrected/updated version of you")
- **`references`** (weak/contextual — "I point at you for context, not derivation")

Two additional relationships are **derived**, not stored, and are worth naming explicitly since they appear in the requirements list:

- **`consumes`**: the inverse view of `ArtifactConsumerRef` (§4.4) — "which artifacts did subsystem X read." Derived from the `consumers` field across all artifacts, not a `ParentRef` relationship, since consumption is not a lineage edge (reading something doesn't make you derived from it).
- **`produces`**: the inverse view of `producer` (§4.3) — "which artifacts did subsystem X create." Derived from a query over `producer.subsystem`, not a stored edge.

**`Parent`/`Child`** are not separate relationship *types* — they are the two directions of traversal over the same `parentArtifacts` edges (`derivedFrom`/`supersedes`/`references`), named this way only in query results for readability (§9.5), not as a fourth and fifth stored relationship kind. Treating "parent/child" as its own relationship type alongside the three above would be redundant — every parent/child pair already has one of the three real relationship types on its edge.

### 8.2 Lineage Graph Construction

```
                    UserIntent (root, no parents)
                          |  derivedFrom
                          v
                    ExecutionPlan
                     /          \
          derivedFrom            derivedFrom
                /                      \
     ExecutionResult (node A)   ExecutionResult (node B)
        |            \                    |
   derivedFrom    evidence          derivedFrom
        |              \                  |
   Decision          Evidence      Decision
   (Policy Engine)                 (Policy Engine)
        |
   supersedes (if re-evaluated)
        v
   Decision (v2)
```

Lineage is not a stored field (§2.2) — it is computed by recursive traversal of `parentArtifacts` edges starting from any artifact, in either direction (ancestors via `parentArtifacts`, descendants via the reverse index, §6.2). The graph is a DAG by construction: `parentArtifacts` can only ever reference an already-`STORED` artifact (§3.2's atomicity guarantee — an artifact cannot exist as a valid parent reference before it itself has been validated and stored), so no artifact can transitively reference itself. This is the same "DAG by construction, not by runtime cycle detection" argument RFC-0003 §13.3 makes for its own composition rule, applied here to a different graph.

### 8.3 Query Patterns

- **Ancestors of X, N levels deep**: traverse `parentArtifacts` recursively from X.
- **Descendants of X**: traverse the reverse-lineage index (§6.2) from X.
- **Full audit trail for X**: ancestors + all `evidence` references transitively + all `Decision` artifacts anywhere in that ancestor set.
- **"What superseded this?"**: single-hop reverse lookup for `relationship=supersedes` edges pointing at X.

### 8.4 Supersession Mechanics

`supersede(oldId, newPayload, ...)` (§9.3) is syntactic sugar over `create()`: it constructs a new artifact of the same `artifactType`, sets `parentArtifacts: [{parentId: oldId, relationship: "supersedes"}]`, and — critically — updates the **old** artifact's `status` field (the one mutable field, §4.1) to `SUPERSEDED`. This is not a violation of immutability: `status` is Store bookkeeping about lifecycle position, not artifact content; the old artifact's `payload`, `checksum`, `producer`, and every other content field remain exactly as created, forever, fully readable, fully checksummable against their original bytes.

## 9. APIs

### 9.1 Design Note

All APIs below are Kernel-internal interfaces other subsystems call directly (in-process or via the Kernel's DI-provided handle, per the accepted finding that the Kernel's remaining job includes dependency injection) — there is no network boundary assumed for the current single-instance deployment model (§1.3, §16 defers distribution).

### 9.2 Public Interface

```typescript
interface IArtifactSystem {
  readonly store: IArtifactStore;         // §9.3
  readonly schemaRegistry: ISchemaRegistry;  // §9.3.5
  readonly query: IArtifactQuery;          // §9.5
  readonly stream: IArtifactStream;         // §9.4
}
```

### 9.3 Storage Interface

```typescript
interface IArtifactStore {
  create<T>(input: ArtifactCreateInput<T>): Promise<Artifact<T>>;
  // Atomic: envelope assembly -> checksum -> validation -> storage (§3.2-3.4).
  // Throws ArtifactValidationError (never returns a partially-stored artifact).

  supersede<T>(oldId: ArtifactID, input: ArtifactCreateInput<T>): Promise<Artifact<T>>;
  // §8.4. Fails if oldId does not exist or is already SUPERSEDED by a different artifact
  // (no diamond supersession — an artifact can only be superseded once, enforced at
  // this API boundary, to keep "what is the current version of X" a well-defined,
  // single-answer question rather than requiring a most-recent-by-timestamp tiebreak).

  get<T>(id: ArtifactID, options?: { asOfSchemaVersion?: string }): Promise<Artifact<T>>;
  // Applies migration (§7.4) unless asOfSchemaVersion requests the original.
  // Throws ArtifactNotFoundError, ArtifactCorruptedError (checksum mismatch, §11.2),
  // or SchemaMigrationUnavailableError.

  archive(id: ArtifactID): Promise<void>;   // §3.7 — idempotent, no-op if already archived
  delete(id: ArtifactID, reason: string, approvedBy: string | null): Promise<TombstoneRef>;
  // §3.8 — throws DeletionRequiresApprovalError if the type's policy demands it and
  // approvedBy is null.
}
```

### 9.3.5 Schema Registry Interface

```typescript
interface ISchemaRegistry {
  register(manifest: ArtifactTypeManifest): Promise<void>;   // §7.2
  getSchema(artifactType: string, version: string): JSONSchema;
  registerMigration(artifactType: string, from: string, to: string, fn: MigrationFn): void;
  deprecateForWrites(artifactType: string, version: string): Promise<void>;
}
```

### 9.4 Streaming Interface

```typescript
interface IArtifactStream {
  createStreaming<T>(input: ArtifactCreateInputMeta<T>): WritableStream;
  // For large payloads (§12.4) — envelope fields provided up front, payload bytes
  // streamed in; checksum computed incrementally; artifact only reaches STORED once
  // the stream closes cleanly (§3.2's atomicity still holds — a partial stream never
  // produces a partially-valid artifact).

  getStreaming(id: ArtifactID): ReadableStream;
  // Streams payload bytes without loading the full payload into memory —
  // the mechanism §3.5 relies on to justify "references are the unit of transport."
}
```

### 9.5 Search / Query Interface

```typescript
interface IArtifactQuery {
  byType(artifactType: string, options?: QueryOptions): AsyncIterable<Artifact>;
  byProducer(subsystem: string, componentId?: string): AsyncIterable<Artifact>;
  ancestorsOf(id: ArtifactID, maxDepth?: number): Promise<LineageGraph>;   // §8.2
  descendantsOf(id: ArtifactID, maxDepth?: number): Promise<LineageGraph>;
  currentVersionOf(id: ArtifactID): Promise<Artifact>;   // follows supersedes chain to tip
  auditTrail(id: ArtifactID): Promise<AuditTrail>;        // §8.3's "full audit trail" pattern
}
```

### 9.6 Internal Interfaces

Not exposed beyond the Artifact System's own boundary: tier-migration scheduler (§6.4), compression codec selection (§6.6), deduplication index (§6.7). These are implementation details of `IArtifactStore`, deliberately not part of the public contract, so the physical storage strategy can evolve (per §16's distributed-storage future work) without breaking any consumer.

## 10. Event Integration

This RFC defines the **vocabulary** of artifact-lifecycle events. It does not implement delivery — that is the Event Bus RFC's job (§16, §17.6). Every event below is emitted by the Artifact System's own internal machinery (never by a producer/consumer subsystem directly, mirroring RFC-0003 §4.6's identical rule for policy events and RFC-0003 §12.1's reasoning: the framework emits events about untrusted-adjacent operations, not the operation's own code).

| Event | Emitted When | Payload |
|---|---|---|
| `ArtifactCreated` | An artifact reaches `STORED` (§3.2) | `{ id, artifactType, producer }` |
| `ArtifactValidated` | Validation passes (§3.3), immediately before `ArtifactCreated` | `{ id, artifactType, schemaVersion }` |
| `ArtifactRejected` | Validation fails (§3.3) | `{ attemptedType, producer, reason }` — note: no `id`, since a rejected artifact never receives one (§3.3) |
| `ArtifactModified` | **Never fires** — kept in the vocabulary only to document why: immutability (§2.1) means this event has no valid trigger. Included here explicitly rather than silently omitted, since the requirements list names it and its absence should be a documented decision, not an oversight. |
| `ArtifactSuperseded` | `supersede()` completes (§8.4) | `{ oldId, newId }` |
| `ArtifactArchived` | Tier migration to cold (§3.7) | `{ id, fromTier, toTier }` |
| `ArtifactDeleted` | Deletion completes (§3.8) | `{ id, tombstoneId, reason, approvedBy }` |
| `ArtifactReferenced` | First read by a new consumer (§3.6, §4.4) | `{ id, consumer }` |
| `ArtifactFailed` | An internal Store operation errors (storage failure, §13.5) — distinct from `ArtifactRejected` (a validation-time outcome) | `{ id \| attemptedType, operation, error }` |

**Delivery semantics deferred**: ordering guarantees, at-least-once vs. exactly-once delivery, subscriber backpressure, and what happens if no Event Bus is currently available to receive these events (buffer? drop? block the Store?) are explicitly not decided here — this table is the contract the Event Bus RFC must satisfy, not a claim that these events are currently being reliably delivered anywhere. Until that RFC lands, this RFC recommends the Artifact Store durably log these events to its own audit trail (§2.6) regardless of Event Bus availability, so no lifecycle event is ever lost even if pub/sub delivery isn't live yet — but that's a bridging measure, not a substitute for the real design.

## 11. Security

### 11.1 Trust Boundaries

```
 Untrusted: payload bytes from a sandboxed skill/policy plugin (RFC-0002 §14.5 /
            RFC-0003 §12.4 sandbox boundary)
     |
     v  [Producer returns payload value across sandbox boundary — same mechanism
         RFC-0003 §12.1 already established: sandboxed code never gets a live
         handle to the Artifact Store, only returns a value the framework wraps]
     |
 Structurally trusted: payload handed to Artifact System's create() call
     |
     v  [Envelope + payload validation, §3.3; checksum computed, §11.2]
     |
 Trusted (stored): Artifact in the Store, checksummed, addressable
     |
     v  [get() call, checksum re-verified on read, §11.2]
     |
 Trusted (consumed): payload handed to a consumer subsystem
```

This mirrors RFC-0003 §12.5's trust-boundary diagram structurally — a fifth application of the same "untrusted bytes -> validated -> sandboxed-execution-produces-a-value-not-a-handle -> trusted" pattern already used by RFC-0002 (skills) and RFC-0003 (policies), now applied to artifact payloads.

### 11.2 Checksums

`checksum` is `sha256` over the **canonical serialization** of the payload — canonical meaning a deterministic byte representation (sorted object keys, fixed number formatting, no incidental whitespace) so that logically-identical payloads always checksum identically regardless of producer-side serialization quirks. This is what makes §6.7's deduplication correct (dedup keys off this checksum) and what makes corruption detection meaningful on every `get()` call (§9.3): a checksum mismatch on read means the stored bytes have been altered or corrupted since write, and `get()` throws `ArtifactCorruptedError` rather than silently returning tampered data — fail-closed, consistent with the AGY-wide invariant restated in §2.6.

### 11.3 Signatures

`signature` is populated only when the producer is a sandboxed third-party plugin (a skill or policy, per RFC-0002/0003's trust model) — not for Kernel-framework-produced artifacts, where the trust chain is already established by the framework's own process identity and a signature would add no information. When present, it is verified against the producing plugin's registered public key (RFC-0002 §7's signature verification, reused, not reimplemented) at validation time (§3.3) — an artifact claiming to be produced by plugin X whose signature doesn't verify against X's registered key is rejected, preventing a compromised or malicious plugin from forging another plugin's provenance.

### 11.4 Encryption

Payloads are encrypted at rest for `warm`/`cold` tiers by default (§6.1) using a Kernel-managed key, transparent to the API (`get()`/`create()` never expose ciphertext to callers). `hot`-tier (in-memory) artifacts are not separately encrypted beyond whatever process-level memory protection the host provides — this RFC does not specify in-memory encryption, judging it disproportionate for data that only exists transiently in a trusted process's own memory space, consistent with avoiding unnecessary abstraction (design constraints).

### 11.5 Access Control

Deliberately **not** implemented by the Artifact System itself (§1.3) — every `get()`/`query()` call is expected to have already passed through Policy Engine evaluation at the calling subsystem's boundary (RFC-0003's `PermissionPolicy`, §7.2, referenced but not detailed in the reviewed RFC-0003 excerpt, is the natural owner of "may subsystem X read artifacts of type Y"). The Artifact System's own API has no user/role concept; it answers "is this artifact well-formed and does it exist," never "should you be allowed to see it." This is a genuine, deliberate scope boundary, not an oversight — but it is flagged in §17.6 as worth revisiting once RFC-0003's `PermissionPolicy` integration point is concretely specified, since right now the *hook* for that integration doesn't exist in this RFC's API surface either (no `callerContext` parameter on `get()`), which is itself a gap.

### 11.6 Tamper Detection

Covered by §11.2 (checksum re-verification on every read) and §2.6 (append-only operation audit log, distinct from the artifacts themselves, so an attempt to retroactively alter Store metadata about an artifact's history is itself detectable against the operation log even if the artifact's own checksum weren't enough).

## 12. Performance

### 12.1 Complexity

`create()`: O(1) amortized (ID generation, checksum computation over payload size, single validation pass) — dominant cost is proportional to payload size for checksumming, not to Store size. `get()` by ID: O(1) via primary index (§6.2). `ancestorsOf`/`descendantsOf` (§8.2, §9.5): O(depth × branching factor) — bounded by `maxDepth`, since an unbounded traversal on a large lineage graph is a real risk this RFC flags rather than assumes away (§13.6).

### 12.2 Memory Usage

Hot-tier envelope cache (§6.3) is bounded by a configurable max-entry count with LRU eviction — never unbounded. Payload cache is similarly bounded and, per §6.3, only applies below a size threshold at all, keeping worst-case memory usage predictable regardless of how many large artifacts exist in the Store.

### 12.3 Caching

Covered in §6.3. The key performance property: envelope reads (the common case — most consumers want metadata/lineage more often than full payload, per §3.5's "references are the unit of transport" principle) are served from the fast in-memory cache far more often than payload reads, which correctly puts the cheap operation on the fast path and the expensive operation (large payload fetch) behind an explicit, deliberate call.

### 12.4 Large Artifact Handling

Any payload above a configurable threshold (default: 1MB) **must** be created via the streaming interface (§9.4), not the standard `create()` call — `create()` itself enforces this at validation time, rejecting an oversized inline payload with a `PayloadTooLargeError` directing the caller to `createStreaming()`. This keeps the common-path `create()`/`get()` calls' complexity bound (§12.1) honest — if large payloads could silently flow through the non-streaming path, the O(1)-amortized claim above would be false for any producer that happened to attach a large blob.

### 12.5 Streaming

Covered in §9.4. The design goal: a consumer that only needs to check `ExecutionResult.status` never pays the cost of loading a multi-megabyte `output` payload — it reads the envelope (cheap), and only calls `getStreaming()` on the referenced large-payload artifact (§5.2's `output: JSONValue | ArtifactID` union) if it actually needs the content.

### 12.6 Indexing Cost

Every `create()` call pays the cost of updating the indexes described in §6.2 — this is a real, non-zero write-amplification cost accepted deliberately, since the alternative (unindexed writes, full-scan reads) would make §8's lineage queries and §9.5's search interface unusably slow at any meaningful artifact volume. Flagged as a tradeoff, not a free property.

## 13. Failure Recovery

### 13.1 Corruption

Detected via checksum mismatch on read (§11.2, §11.6). Recovery: `get()` throws `ArtifactCorruptedError`; the Artifact System does not attempt automatic repair (there is no "correct" version to repair *to* — the checksum only proves *that* corruption occurred, not what the original bytes were). If a `supersede()`-chain predecessor or a replicated copy exists (deferred to distributed-storage future work, §16), manual/operator-driven recovery from that source is possible but out of this RFC's automated scope.

### 13.2 Missing Artifacts

`get()` on a nonexistent `ArtifactID` throws `ArtifactNotFoundError`. Distinguished from a *deleted* artifact (§3.8), which instead resolves to its tombstone (a `TombstoneRef`, not a full artifact, but a real, findable record) — "missing" specifically means an ID that was never valid, e.g. a typo or a reference from a corrupted/malicious source, not a legitimately deleted one. This distinction matters for §8.2's lineage traversal: a `parentArtifacts` entry resolving to a tombstone is a normal, expected traversal terminus (§3.8); one resolving to `ArtifactNotFoundError` indicates a genuine integrity problem worth surfacing loudly, not silently treating the two cases identically.

### 13.3 Schema Mismatch

Covered by §7.5's fail-closed `SchemaMigrationUnavailableError` — never a best-effort coercion attempt. A caller receiving this error has three options: request the artifact `asOfSchemaVersion` (raw, unmigrated) if it can handle the old shape itself; register the missing migration; or treat the artifact as currently unreadable by this code path without losing the underlying data (which remains safely stored either way).

### 13.4 Migration Failure

If a registered `migrate()` function itself throws during a `get()` call, this is treated identically to a corruption-class failure (§13.1) rather than silently falling back to the unmigrated payload — returning data silently in a shape the caller didn't ask for and isn't validated against would violate §3.3's validation guarantee. The original stored artifact remains completely unaffected (migration is read-time-only, §7.4) — only this specific `get()` call fails, not the artifact's existence or integrity.

### 13.5 Storage Failure

Backend-level failures (disk I/O error, object store unavailability) during `create()` are surfaced as `ArtifactStoreUnavailableError` **before** any partial state is visible — per §3.2's atomicity guarantee, a failed `create()` never leaves a half-written artifact discoverable by any query. During `get()`, a storage failure on a specific tier (e.g. cold-tier object store down) is distinguished from "artifact doesn't exist" — surfaced as a retryable `ArtifactTemporarilyUnavailableError`, since the artifact's existence and validity aren't in question, only current reachability.

### 13.6 Unbounded Traversal Risk (Self-Identified)

`ancestorsOf`/`descendantsOf` (§9.5) without a caller-supplied `maxDepth` on a deep, densely-connected lineage graph (plausible for a long-running session with many `supersede()` chains and wide `evidence` fan-out) is a genuine, currently-unbounded-by-default performance risk this RFC flags rather than silently ignores — the API requires `maxDepth` as an optional, not mandatory, parameter, which is arguably the wrong default (§17.7).

## 14. Testing Strategy

### 14.1 Unit Testing

Envelope assembly, checksum computation, ID generation determinism (§2.3), and per-relationship-type edge validation (§4.5) are unit-testable in isolation with no Store dependency — pure functions, consistent with §2.3's determinism requirement making them naturally unit-testable without mocking time or randomness beyond ID generation's monotonic-per-producer clock input.

### 14.2 Integration Testing

Full lifecycle round-trips (§3): create → validate → store → get → supersede → archive → delete, against a real (test-instance) Store, verifying every state transition in §3's diagram is reachable and every illegal transition (e.g. attempting to `supersede()` an already-superseded artifact, §9.3) is correctly rejected.

### 14.3 Property Testing

Strong candidates given this RFC's structural guarantees:
- **Immutability property**: for any artifact, every envelope field except `status`/`consumers` is bit-identical across repeated `get()` calls, regardless of intervening operations by other producers.
- **DAG property**: for any randomly generated set of `create()`/`supersede()` operations, the resulting `parentArtifacts` graph never contains a cycle (§8.2's construction argument, verified empirically against the implementation, not just argued structurally).
- **Checksum determinism property**: for any payload, canonical serialization (§11.2) produces the same checksum regardless of key insertion order in the source object.
- **Round-trip property**: for any registered schema, a payload that validates, when migrated through every registered migration path back to its original version, produces a payload validating against the original schema.

### 14.4 Fuzz Testing

Malformed envelope inputs (missing required fields, wrong types, oversized `metadata`), malformed payloads against every registered schema, and adversarial `parentArtifacts` references (pointing at nonexistent IDs, pointing at IDs still `VALIDATING`) — verifying every case is rejected at `create()` (§3.3) rather than accepted and causing a downstream failure.

### 14.5 Golden Artifacts

A fixed, version-controlled set of canonical example artifacts for every registered `ArtifactType` (§5) — checked into the schema registry's own test fixtures — used to catch unintended schema-validation regressions when the Schema Registry's implementation changes, independent of any specific migration test. Each golden artifact is re-validated against its declared schema version on every Schema Registry change as a smoke test.

## 15. Tradeoffs

| Approach | Why Not Chosen (or, for the winner, why chosen) |
|---|---|
| **Pure JSON** (no envelope, subsystems pass raw JSON blobs directly) | Rejected — this is the status quo the RFC exists to fix. No shared identity, no lineage, no checksum, no schema evolution story. Every consumer would need to defensively validate shape on every read, and provenance (§2.2) would be unrecoverable once a JSON blob crosses a subsystem boundary with no accompanying metadata. |
| **Database rows** (relational schema per artifact type, foreign keys for lineage) | Rejected as the *sole* model, though influential on §6's indexing design. A rigid relational schema fights §2.5's schema-evolution requirement — adding a field to a widely-used artifact type would mean an ALTER TABLE migration touching every historical row, in direct tension with §2.1's immutability principle (rows are naturally mutable in a relational model, requiring extra discipline to *not* update in place). The envelope+payload split (§4.1) gets relational-style structure for the envelope (which is genuinely fixed-shape and benefits from strong typing/indexing) while keeping `payload` schema-flexible per type — closer to a hybrid than a pure rejection. |
| **Event sourcing** (artifacts as a pure append-only event log, current state always derived by replay) | Partially adopted, not fully. This RFC's audit trail (§2.6) and immutable-artifact-plus-supersession model (§2.1, §8.4) are event-sourcing-adjacent — an artifact's lineage chain *is* a replayable history. Rejected as the *complete* model because full event sourcing would mean the Store never holds materialized current-state directly, requiring replay-to-current-state on every read — unacceptable for §12's performance requirements on hot-path reads like `ExecutionResult` lookups mid-execution. The chosen model gets event-sourcing's auditability without its read-amplification cost, by keeping `status` as a small, explicitly-scoped exception to full immutability (§8.4) rather than modeling every state change as a replayable event. |
| **Object store (e.g. S3-style, keyed blobs, no query layer)** | Rejected as the *sole* model — adopted as the physical substrate for the cold tier only (§6.1). An object store alone has no lineage graph, no schema registry, no typed query interface — it would push all of §7, §8, §9's responsibilities onto every consumer to reimplement independently, exactly the fragmentation problem this RFC exists to solve. |
| **Content-addressable storage (CAS)** (artifact ID *is* its content hash) | Rejected as the primary identity scheme, though adopted for deduplication (§6.7). Pure CAS identity would make `supersede()` (§8.4) impossible to express cleanly — a corrected artifact with even a one-byte payload difference would necessarily get a wholly unrelated ID under pure CAS, severing the "this is a new version of that" relationship that `ArtifactID` (ULID, time-ordered, producer-assigned) preserves naturally. CAS is the right model for *payload deduplication* (§6.7), wrong for *artifact identity*. |
| **Graph database** (artifacts and relationships modeled natively in a graph DB, e.g. for §8's lineage queries) | Rejected as the primary store, acknowledged as a plausible *specialized index* for lineage-heavy query workloads at scale. For the current single-instance deployment model, a dedicated graph database is disproportionate infrastructure for a lineage graph this RFC expects to be sparse relative to total artifact volume (most artifacts have 1-3 parents, not the dense many-to-many structure graph databases are optimized for) — the reverse-lineage index (§6.2) on top of the primary store is judged sufficient for current scale, with graph-database migration named as a legitimate future option if lineage query patterns prove this wrong (§16). |
| **Chosen: envelope+payload hybrid over a tiered store with a separate Schema Registry** | Matches the actual shape of the problem: fixed, strongly-typed, universally-needed metadata (envelope) plus evolvable, type-specific content (payload), with tiered storage matching real access-pattern variance (hot execution-time reads vs. cold audit-time reads) and a schema registry that makes extensibility (new artifact types, per the design constraints) a registration operation, not a Kernel change — directly satisfying "avoid unnecessary abstraction" (a single unified model, not five separate subsystems solving pieces of this) and "prefer explicit contracts over implicit behavior" (every relationship, every schema version, every retention rule is a declared, validated field, not inferred convention). |

## 16. Open Questions

1. **Storage backend selection** (physical object store, local disk format) — explicitly deferred to Resource Manager, per §6.1, §1.3.
2. **Distributed/multi-instance Artifact Store** — no current requirement justifies this now (§1.3); flagged for revisit if AGY moves to multi-instance deployment, at which point the reverse-lineage index (§6.2), the deduplication index (§6.7), and the append-only audit log (§2.6) all need a consistency model this RFC does not specify.
3. **Event Bus delivery semantics** — this RFC defines the vocabulary (§10); ordering guarantees, backpressure, and at-least-once vs. exactly-once delivery are the Event Bus RFC's job, named as the necessary next subsystem (§17.6).
4. **RuntimeState's live, mutable shape** — this RFC defines only the artifact-snapshot wrapper (§5.11); the actual live object, its update semantics, and which subsystem owns it are undesigned, named as the second necessary next subsystem (§17.2).
5. **Access control integration point** — flagged in §11.5 as a real gap: the API surface (§9) has no `callerContext` parameter for `PermissionPolicy` (RFC-0003) to hook into. Needs resolution before Scheduler/Executor can safely enforce read-time permissions through this API rather than around it.
6. **Default `maxDepth` for lineage traversal** — §13.6 flags the current optional-parameter default as possibly wrong; needs a decision (mandatory parameter? conservative default with override?) before this API ships.
7. **Whether Artifact-System-internal operations (tier migration, GC, deduplication) should themselves produce audit artifacts**, or remain confined to the separate operation log (§2.6) — currently the latter; revisit if audit requirements demand artifact-level (not just log-level) visibility into Store-internal operations.
8. **Graph-database migration trigger criteria** (§15) — no concrete threshold (artifact count, lineage density) is specified for when the reverse-index approach should be reconsidered; worth defining as a measurable trigger rather than a vague "if it becomes a problem."

## 17. Critical Self-Review

### 17.1 The "What Becomes an Artifact" Boundary Is a Judgment Call, Not a Derived Fact

§1.5 draws a line excluding manifests/configuration from the Artifact model. This is defensible but not the only reasonable reading of "everything exchanged inside AGY must eventually become an Artifact" — a stricter reading would argue that a skill manifest, once loaded and consulted by the Resolver, *is* being exchanged between RFC-0002 and RFC-0001 and should be artifact-wrapped too. This RFC chose the narrower reading because it keeps RFC-0002's existing, working manifest lifecycle untouched (per the constraint "preserve backward compatibility where practical" from the original project rules) — but a future reviewer applying the stricter reading would have grounds to push back, and this RFC does not claim to have proven the narrower reading correct, only chosen it and stated why.

### 17.2 RuntimeState Circularity Risk

§5.11 defines `RuntimeStateSnapshot` as an artifact type, which means this RFC has made a design decision *about* RuntimeState (that it is at least partially expressible as a snapshot artifact) before RuntimeState itself has been formally specified. If the eventual RuntimeState RFC concludes that RuntimeState is fundamentally not snapshot-able in this way (e.g. if it contains live references, open connections, or other non-serializable state), §5.11 would need revision. This is flagged explicitly as a forward-dependency risk this RFC accepted deliberately (to unblock RFC-0003's existing references to `RuntimeState.priorFailures`) rather than one it resolved.

### 17.3 ExecutionPlan's Root-Artifact Gap

§5.1 notes an `ExecutionPlan` "may be empty [parentArtifacts] if the plan originated from a non-artifact-tracked trigger." This is a real, currently-unresolved gap: if `UserIntent` artifacts (§5.18) aren't consistently created for every plan-triggering event (e.g. a scheduled/cron-triggered plan with no human intent behind it), the lineage graph's root nodes will be inconsistent — some plans traceable to a `UserIntent`, others not, with no artifact explaining *why* they exist. This RFC does not resolve what non-human-triggered plans should have as their root artifact (a `SystemTrigger` type? nothing?) — named here rather than papered over.

### 17.4 Naming Collision With RFC-0003's `PolicyDecision`

§5.4 flags this in-line, restated here for completeness: this RFC's `Decision` artifact wraps, rather than replaces, RFC-0003's `PolicyDecision` type. This is the correct choice per the instruction to document cross-RFC findings separately rather than silently modifying accepted contracts — but it does mean AGY's codebase will have two related, similarly-named types (`PolicyDecision` and `Decision`'s payload, which *is* a `PolicyDecision`) that a future engineer could easily confuse. Worth a documentation/naming-convention pass, not a structural fix.

### 17.5 ResourceUsage Does Not Solve the Execution Ledger Gap, Only Unblocks It

§5.19 gives `ResourceUsage` a concrete artifact shape, closing the immediate "undefined type referenced by RFC-0003" problem — but it does not design the Ledger's actual accounting logic (running totals, budget-ceiling enforcement mechanics, concurrent-write handling under multiple simultaneously-executing nodes). That remains genuinely Resource Manager's job. Overclaiming this RFC as "solving the Ledger gap" would be inaccurate; it is more precisely "giving the Ledger's data a storable shape so Resource Manager doesn't have to design that too."

### 17.6 This RFC Cannot Be Fully Validated Without Event Bus and RuntimeState

Consistent with the accepted finding that Scheduler shouldn't be designed until all three (Artifact, Event Bus, RuntimeState) exist: this RFC's own §10 (Event Integration) and §5.11/§17.2 (RuntimeState) sections are, by the same logic, only partially verifiable right now. The event vocabulary (§10) is a contract for a system that doesn't exist yet; there is no way to confirm it's the *right* vocabulary until Event Bus is actually built against it and friction (or lack of it) becomes visible. This is accepted as an inherent property of designing subsystems in dependency order rather than a flaw unique to this RFC — but it means this RFC should be revisited, not treated as permanently frozen, once Event Bus lands.

### 17.7 Unbounded-by-Default Traversal (Restated From §13.6)

The `maxDepth` parameter on `ancestorsOf`/`descendantsOf` (§9.5) being optional rather than mandatory is, on reflection, likely the wrong default for a fail-closed system — every other dangerous-by-default operation in this RFC (large payload handling, §12.4; deletion, §3.8) requires an explicit opt-in or approval step, while unbounded lineage traversal currently does not. This inconsistency with the RFC's own stated fail-closed posture (§2.6, restated throughout) is a genuine design flaw, not just an open question, and should be corrected before implementation: `maxDepth` should be mandatory, with no unbounded default.

### 17.8 Kernel-Adjacency Claim Is Asserted, Not Enforced By Anything in This RFC

§1.3 states the Artifact System is "a Kernel-adjacent service the Kernel wires up, not Kernel logic itself," consistent with the accepted finding that the Kernel should shrink to bootstrapping/DI/lifecycle/event-routing/shutdown only. But nothing in this RFC's own API design (§9) structurally *prevents* the Artifact System from accreting Kernel-like responsibilities over time the way RFC-0003's framework/policy split (§2.1 of that RFC) structurally prevents policy logic from leaking into the framework. This RFC states the right intention but, unlike RFC-0003's more mechanically-enforced boundary, does not yet have an equivalent structural guardrail — worth strengthening in a later revision.

## 18. Recommendation: Next Subsystem to Design

Per the accepted finding, **Scheduler should not be designed until Artifact, Event Bus, and RuntimeState exist.** This RFC completes the first of the three. Of the remaining two, this RFC recommends **RuntimeState next, not Event Bus**, for a reason not previously stated in the accepted findings and worth justifying explicitly:

Event Bus's design surface is now well-bounded by this RFC's §10 — the event vocabulary it needs to route is fully enumerated, and RFC-0003 §4.6/§12.1 already independently established the emission-pattern precedent (framework-emits, plugin-never-emits-directly) that Event Bus needs to be consistent with. Event Bus, in other words, now has two independent, converging specifications to design against.

RuntimeState, by contrast, is currently only referenced — never specified — by *three* separate RFCs (RFC-0001's `priorFailures`, RFC-0003's `context.ledger`/`context.sessionGrants`/`priorDecisions`, and this RFC's §5.11 `RuntimeStateSnapshot` wrapper) with no single document reconciling what these references actually assume RuntimeState's shape and update semantics to be. This RFC's own §17.2 flags a real circularity risk from having guessed at part of that shape. The longer RuntimeState remains unspecified while more RFCs silently accumulate assumptions about it, the more expensive it becomes to formally define without breaking something — the same "phantom dependency" problem this RFC identified and closed for the Execution Ledger (§5.19, §17.5) is currently *worse*, not better, for RuntimeState, because more RFCs depend on it and it's referenced with less consistency across them than the Ledger was.

**Recommended: RFC-0005, RuntimeState.** Event Bus should follow as RFC-0006, once RuntimeState's shape is fixed — since Event Bus will need to route `RuntimeStateSnapshot`-related events (session start/end, state transitions) that don't yet have a stable definition to route around.
