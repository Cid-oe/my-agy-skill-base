**Series:** AGY AI Operating System
**Status:** Review (Phase-0 reconciliation baseline)
**Editor:** AGY Architecture Working Group
**Last updated:** 2026-08-21 (Phase 0: Corpus Reconciliation)

> This document is the single entry point to the AGY specification. It
> defines the RFC process, records the status of every RFC, holds the

> and states the repository and naming conventions. Everything else in

## 1. Vision

AGY is an **AI Operating System**: a kernel that governs how an ecosystem of
skills, tools, models, and agents plan, execute, observe, and improve work —
deterministically where decisions are made, sandboxed where third-party
code runs, policy-governed at every boundary, and auditable end to end.

Design invariants (the corpus's load-bearing, cross-RFC rules):

1. **Determinism in the control plane** — same inputs, same decisions
   (Resolver plans, Policy decisions, Scheduling order, Executor bookkeeping).
2. **Fail-closed everywhere** — unknown predicates, sandbox defaults, policy
   outages, and validation failures deny, never permit.
3. **Separation of decide / enforce / execute** — Policy evaluates, sandbox
   enforces, Scheduler/Executor act; no component does another's job.
4. **References over payloads** — artifacts, events, and state carry IDs;
   bytes live in exactly one store.
5. **Amendments, not rewrites** — accepted contracts change only through
   recorded amendments (see §5).
6. **Evidence before adaptation** — the system may tune its own parameters
   only within bounds, with validation, rollback, and audit (RFC-0014).

## 2. Architecture at a glance

Kernel (control plane) → Platform (capability plane) → Cognition loop:

```
           ┌────────────────────────── Cognition loop ─────────────────────────┐
           │  RFC-0011 Planner → goals/task DAGs                                │
           │  RFC-0013 Reflection → lessons   RFC-0014 Learning → parameters    │
           │  RFC-0015 Observability → views/debug                              │
           └───────────────▲───────────────────────────────▲───────────────────┘
                           │ reads/writes                  │ signals
┌──────────────────── Kernel (execution path) ─────────────────────────────────┐
│ RFC-0002 Registry ─► RFC-0001 Resolver ─► RFC-0003 Policy ─► RFC-0007        │
│        (trust root)     (skill selection)   (decision        Scheduler        │
│                                            authority)        │ Orders         │
│                                                             ▼                │
│  RFC-0004 Artifacts ◄──► RFC-0005 Runtime State ◄──► RFC-0008 Executor       │
│         ▲                     ▲    (live state)        (runs the work)      │
│         │                     │                                           │
│  RFC-0006 Event Bus ◄─────────┴─────────────── observation & lifecycle       │
└──────────────────────────────────────────────────────────────────────────────┘
┌──────────────────── Platform ────────────────────────────────────────────────┐
│  RFC-0010 Memory (7 tiers)      RFC-0012 Tool Runtime (connector boundary)  │
└──────────────────────────────────────────────────────────────────────────────┘
```

Runtime pipeline order (who calls whom at steady state):
**Planner → Resolver → Policy → Scheduler → Executor → (skills → Tool
Runtime | Memory)**, with Reflection/Learning/Observability consuming the
artifacts and events everything else leaves behind.

**Rules established by this graph (Phase-0 decisions):**
- The former 0001↔0005 type cycle is legal because **type edges impose no
  load order**; only runtime edges do.
- RFC-0001's phantom dependencies on the *skills* "Repository Map" and
  "Context Manager" are removed — data arrives via RuntimeState.
- RFC-0007's dependency header now matches its text (per RFC-0007-A1 R1).
- Runtime pipeline order ≠ dependency layers: the Planner runs *first* in a
  pipeline but depends *last* in build order.

## 5. RFC process

### 5.1 Status lifecycle

```
Draft ──► Review ──► Accepted ──► Implemented
              │          │            │
              └──────────┴────┐       ▼
                              ▼   Archived (terminal, after Superseded/Deprecated)
                        Superseded (by named RFC)
                        Deprecated (still referenced; do not build to it)
```

| Status | Meaning | Entry criteria |
|---|---|---|
| **Draft** | Being designed; may change freely | First commit of the document |
| **Review** | Design stable; contradictions resolved; under ratification review | No unresolved cross-RFC contradiction; self-review complete; schema surfaces enumerated |
| **Accepted** | Binding contract; changes only via ratified amendment | Review complete; amendment pack (if any) ratified; schemas enumerated in `schemas/` |
| **Implemented** | Shipping code matches the contract | Conformance + determinism suites green in `kernel/` |
| **Superseded** | Replaced by a named RFC | Named successor Accepted |
| **Deprecated** | Still load-bearing for readers; do not build against it | Editor decision + pointer to successor |
| **Archived** | Removed from the active map; retained for history | No live references |

**Amendments** (`docs/amendments/RFC-00NN-Ax.md`) carry
Problem/Reason/Impact/Resolution/Compatibility/Migration, are ratified on
their own record, and are folded into the parent RFC at its next revision
(minor-version bump). Accepted RFCs are never edited in place.

### 5.2 Numbering rules

1. Numbers are **allocation-only; never reused**. A referenced-but-unissued
   number is retired by a record (see [RFC-0009](RFC-0009.md)), never
   reassigned.
2. Subsystem RFCs take the next free number from the registry (§8).
3. Amendments are `RFC-00NN-A<k>`; an A0 is a "bundle" of coupled
   amendments ratified together.
4. Suggested-but-unchartered RFCs live in the **unassigned pool** and get
   numbers only when chartered — suggestions in RFC prose are not
   reservations.

## 7. Repository structure & naming conventions

```
AGY/
├── RFC-0000 entry: docs/rfcs/RFC-0000.md        (this file)
├── docs/
│   ├── rfcs/            RFC-00NN.md subsystem specifications
│   ├── amendments/      RFC-00NN-Ax.md ratified-or-proposed amendments + index
│   ├── adr/             Architecture Decision Records (implementation-time, numbered AD-00NN)
│   ├── architecture/    Reviews & analyses (incl. the 2026-08-20 architecture review)
│   ├── phase-0/         Phase-0 reconciliation deliverables (01…10)
│   ├── diagrams/        Diagram sources & exports
│   └── glossary.md      Canonical terminology
├── schemas/             Machine-readable contracts (manifest/, artifacts/, events/,
│                        policy/, state/) — populated at Gate G1, authoritative once RFCs are Accepted
├── skills/agy-skills-v2/ The skill package (dirs = skill ids; manifest.json derived)
├── kernel/              Kernel implementation (Phase 1+; one package per L-layer)
├── tests/               Cross-kernel conformance, determinism & golden suites
└── examples/            Runnable end-to-end examples
```

**Naming conventions**
- RFC files: `RFC-00NN.md`; amendments `RFC-00NN-Ax.md`; ADRs `AD-00NN-title.md`.
- Event topics: `<domain>.<object>.<verb>[.<correlationId>]` (RFC-0006-A1 R2).
- Artifact types: UpperCamelCase names registered in RFC-0004's Schema
  Registry; event/skill ids: lower-kebab-case.
- Skill directories MUST equal the skill `id`; `manifest.json` is
  regenerated from frontmatter, never hand-edited for paths.
- Canonical status words are exactly those in §5.1.

## 9. Roadmap

- **Phase 0 (this document set):** reconcile the corpus; conformance-repair
  the skill pack; ratify the amendment pack (Gate G0).
- **Phase 1:** schemas (`schemas/`, Gate G1) → kernel implementation in
  layer order L0→L5 (Registry, Resolver, Policy, Artifacts, State, Bus,
  Scheduler, Executor), each gated by its RFC's test sections; skill pack
  serves as the Registry's conformance fixture. See
  `docs/phase-0/10-phase-1-build-plan.md`.
- **Phase 2:** platform subsystems (Memory Phase-1 tiers, Tool Runtime) and
  the RFC-0016/0017/0020 roots they require.
- **Phase 3:** cognition loop (Planner, Reflection, Learning,
  Observability) + RFC-0018/0019/0021.
- **Phase 4:** distribution, federation, marketplace (RFC-0023+).
