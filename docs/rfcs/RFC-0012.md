## 1. Executive Overview

RFC-0012 defines the **Tool Runtime** for the AGY AI Operating System. The Tool Runtime is the kernel subsystem responsible for everything that happens between a skill deciding to invoke an external capability and that invocation's result being available for the next step in an execution graph.

A tool, in AGY's model, is any external capability that the kernel can invoke on behalf of a skill: a REST endpoint, a command-line program, a browser session, a Python interpreter, an MCP server, a database query, a file system operation, a gRPC service, or any future connector not yet conceived. Tools are not skills. Skills are AGY's internal reasoning and coordination units, governed by the Skill Registry and resolved by the Skill Resolver. Tools are external. They exist outside the kernel. They have their own versioning, their own failure modes, their own protocols, their own latency characteristics, and their own security surfaces.

The Tool Runtime is the **kernel's boundary with the external world**. Everything inside the kernel is governed, typed, versioned, and auditable. Everything outside it is untrusted, potentially slow, potentially unavailable, and potentially malicious. The Tool Runtime is where trust is enforced, contracts are validated, results are normalized, and the chaos of the external world is translated into the orderly data structures that the rest of AGY expects.

The central design insight is this: **the connector is not the abstraction**. MCP, REST, CLI, Python, and Browser are protocols, not capabilities. The capability is what the tool does. The Tool Runtime separates capability description (what a tool can do, what it accepts, what it returns, what it costs, what permissions it requires) from connector implementation (how to talk to the tool over a specific protocol). This separation allows the same tool to be reached through different connectors over time, allows capabilities to be composed across tools, and allows the kernel to reason about tools at the capability level rather than at the protocol level.

The Tool Runtime is not a thin wrapper around HTTP clients and subprocess calls. It is a **structured execution environment** with its own lifecycle management, its own concurrency model, its own retry and idempotency semantics, its own sandboxing hooks, and its own result normalization pipeline. It is designed to be the substrate on which every current and future connector protocol is implemented.

## 2. Responsibilities

**Tool Discovery**
- Discovering tools registered statically at startup and dynamically at runtime.
- Querying remote tool catalogs (MCP servers, OpenAPI registries, internal catalogs) for available tools.
- Normalizing discovered tool descriptions into canonical Tool Capability Records.
- Detecting conflicts between tools offering the same capability name across different connectors.

**Tool Registration**
- Maintaining the Tool Registry: the authoritative catalog of known tools, their capabilities, their connectors, their versions, and their contracts.
- Supporting manual registration (operator-defined tools), auto-discovery registration, and programmatic registration by skills.
- Versioning tool registrations and tracking changes over time.
- Deregistering tools cleanly when they become unavailable.

**Tool Execution**
- Accepting tool invocation requests from skills (via the Public Interface).
- Routing invocations to the correct Connector based on tool registration.
- Managing the full execution lifecycle: pre-execution validation, connector dispatch, result receipt, post-execution normalization.
- Tracking execution state for every in-flight tool call.

**Timeouts**
- Enforcing per-tool, per-connector, and per-invocation timeout policies.
- Distinguishing connection timeouts, read timeouts, and total execution timeouts.
- Canceling in-flight executions cleanly when timeouts are reached.
- Reporting timeout events to the Event Bus and the calling skill.

**Permissions**
- Enforcing tool access control through the Policy Engine (RFC-0003).
- Ensuring that only authorized skills can invoke specific tools or tool capability classes.
- Enforcing rate limits and quota constraints per tool, per skill, and per tenant.

**Sandboxing Hooks**
- Providing a defined interface for sandboxing enforcement: process isolation, network isolation, filesystem isolation, and resource limits.
- Not implementing sandboxing directly — providing the hooks that platform-level sandboxing implementations plug into.
- Ensuring that all connector executions pass through sandboxing hooks; there is no bypass path.

**Result Normalization**
- Translating the raw output of every connector (HTTP response bodies, subprocess stdout, Python return values, browser DOM captures) into canonical `ToolResult` structures.
- Validating results against the tool's declared output schema.
- Handling partial results, truncated outputs, and encoding variations.
- Materializing large results as Artifacts (RFC-0004).

**Streaming**
- Supporting streaming tool outputs where the connector and tool support it.
- Providing a unified streaming interface regardless of the underlying streaming mechanism (SSE, chunked HTTP, subprocess pipe, websocket).
- Buffering, backpressure, and partial result delivery for streaming invocations.

**Retries**
- Implementing configurable retry policies per tool: max attempts, backoff strategy, retry-eligible error classes.
- Ensuring retries are safe: only retrying idempotent operations unless explicitly configured otherwise.
- Recording retry attempts in the invocation log.

**Idempotency**
- Assigning and tracking idempotency keys for all tool invocations.
- Detecting duplicate invocation requests and returning cached results for confirmed duplicates.
- Propagating idempotency keys to connectors that support them (e.g., REST APIs that accept `Idempotency-Key` headers).

**Versioning**
- Tracking tool versions and connector versions independently.
- Routing invocations to the correct tool version based on skill requirements or policy.
- Detecting and handling tool version changes that break the declared contract.

**Tool Contracts**
- Maintaining declared input schemas, output schemas, error schemas, and behavioral contracts for each tool.
- Validating invocation inputs against input schemas before dispatch.
- Validating results against output schemas after receipt.
- Flagging schema violations without silently swallowing them.

**Tool Capabilities**
- Modeling tools not just as callable endpoints but as capability bundles: what they can do, what they cost, what side effects they have, and what permissions they require.
- Supporting capability-based routing: a skill requests a capability (e.g., "web search"), and the Tool Runtime selects the best available tool that provides it.

## 3. Non-Goals

- **Implementing specific connectors.** This RFC defines the Connector Interface. MCP, REST, CLI, Python, and Browser connectors are separate implementations that implement that interface. They are not specified here.
- **Implementing sandboxing.** The Tool Runtime defines sandboxing hooks. Platform sandboxing (containers, seccomp, gVisor, WebAssembly runtimes) is an infrastructure concern.
- **Implementing tool logic.** The Tool Runtime invokes tools. It does not implement what tools do.
- **Managing model context.** The Tool Runtime returns normalized results. How those results are incorporated into a model's context is the skill's or execution layer's concern.
- **Implementing authentication for specific protocols.** The Tool Runtime defines a credential interface. Specific credential types (OAuth tokens, API keys, certificates) are managed by a Credential Store (a future RFC).
- **Providing a query language for tool discovery.** The Tool Registry supports structured queries. A query language is out of scope.
- **Implementing tool composition.** Chaining multiple tool invocations is the Planner's (RFC-0011) and Scheduler's (RFC-0007) concern. The Tool Runtime executes one tool invocation at a time.
- **Rate limiting at the network layer.** Network-layer rate limiting is infrastructure. The Tool Runtime enforces logical rate limits per policy.

## 4. Relationship to Previous RFCs

### RFC-0001: Skill Resolver

Skills invoke tools through the Tool Runtime's public interface. The Skill Resolver resolves which skill handles a given task. That skill, once executing, may call the Tool Runtime to invoke external capabilities. The Tool Runtime does not call the Skill Resolver. The relationship is one-directional: skills are callers, Tool Runtime is the execution substrate.

**Interaction:** The skill identity resolved by RFC-0001 is passed as `requester_identity` on every tool invocation. The Tool Runtime uses this identity for policy evaluation, audit logging, and quota enforcement. A skill cannot invoke a tool without providing its resolved identity.

### RFC-0002: Skill Registry & Loader

Skills may declare tool dependencies in their manifests: which tools they expect to use, which capability classes they require, and which tool versions they are compatible with. The Tool Runtime reads these declarations at skill load time to pre-validate that required tools are available. If a required tool is unavailable, the Tool Runtime can surface this before the skill is invoked rather than failing mid-execution.

**Interaction:** Tool Runtime reads skill manifests from RFC-0002 to resolve tool dependencies. This is a one-way, read-only dependency. RFC-0002 does not call the Tool Runtime.

**New field required:** Skill manifests should include a `tool_dependencies` block. If RFC-0002 does not currently support this field, an amendment is required. This is documented in Compatibility Notes.

### RFC-0003: Policy Engine

Every tool invocation is policy-gated. Before dispatching any tool call, the Tool Runtime evaluates the invocation against RFC-0003 with a `ToolInvocationPolicyRequest` containing: requester identity, tool ID, capability class, sensitivity classification, side-effect class, and resource cost estimate. Policy decisions are cached per `(identity, tool_id, capability_class)` with a configurable TTL.

**Interaction:** Bidirectional. Tool Runtime calls RFC-0003 for permission evaluation. RFC-0003 may emit policy change events via RFC-0006 that invalidate the Tool Runtime's policy decision cache.

**New attribute namespace required:** RFC-0003 must support `tool.*` policy attributes: `tool.id`, `tool.capability_class`, `tool.side_effect_class`, `tool.cost_tier`, `tool.connector_type`. These are defined in this RFC and must be registered in RFC-0003's attribute namespace.

### RFC-0004: Artifact System

Large tool results — file downloads, binary outputs, lengthy text responses, structured data exceeding the inline threshold — are materialized as Artifacts rather than returned inline. This keeps invocation results bounded in size and gives large results the full Artifact treatment: content addressing, deduplication, lineage, and lifecycle management.

**Interaction:** Tool Runtime writes result Artifacts to RFC-0004 when result size exceeds the configured inline threshold (default: 32KB). The `ToolResult` structure carries an `artifact_ref` rather than inline data for these cases. Tool inputs that are large (e.g., a file to be processed) are referenced as Artifact IDs and hydrated from RFC-0004 before dispatch.

**Bidirectional dependency:** Tool Runtime reads Artifacts as tool inputs and writes Artifacts as tool outputs. Artifact lifecycle changes (deletion, expiry) may invalidate cached tool results that reference those Artifacts. The Tool Runtime subscribes to `artifact.deleted` events from RFC-0006.

### RFC-0005: Runtime State

The Tool Runtime reads Runtime State to determine the execution context of each invocation: which execution, session, project, and user the invocation belongs to. This context is used for scope-aware audit logging, quota enforcement, and memory writes.

**Interaction:** Read-only. Tool Runtime reads RFC-0005 to bind invocations to their execution context. The Tool Runtime does not write to Runtime State, but it does contribute to it indirectly: invocation state (in-flight tool calls) is visible in the Runtime State as part of the execution's resource profile.

### RFC-0006: Event Bus

The Tool Runtime is both a publisher and subscriber.

**As publisher:**
- `tool.invocation.started`
- `tool.invocation.completed`
- `tool.invocation.failed`
- `tool.invocation.timeout`
- `tool.invocation.retrying`
- `tool.registered`
- `tool.deregistered`
- `tool.contract.violation`
- `tool.sandbox.violation`

**As subscriber:**
- `artifact.deleted` — to invalidate cached results referencing deleted Artifacts.
- `policy.updated` — to invalidate policy decision cache.
- `skill.registry.updated` — to refresh tool dependency pre-validation cache.
- `scheduler.task.cancelled` — to cancel in-flight tool invocations for cancelled tasks.

### RFC-0007: Scheduler

The Scheduler dispatches Tasks from the Execution Graph. When a Task's skill requires a tool invocation, the Scheduler does not call the Tool Runtime directly. The skill executes (under Scheduler dispatch) and the skill calls the Tool Runtime. The Scheduler is aware of tool-related resource constraints through the scheduling hints in the Execution Graph (RFC-0011): estimated tool call latency, cost tier, and exclusive resource requirements.

**Interaction:** Indirect. The Scheduler drives skill execution; skills drive tool invocations. The Scheduler responds to `tool.invocation.timeout` events to update Task state. The Scheduler may cancel in-flight tool invocations when a Task is cancelled.

### RFC-0010: Memory System

The Tool Runtime writes invocation records to Episodic Memory after each completed invocation. These records capture: tool ID, capability, input summary, outcome, latency, and error (if any). This data feeds the Reflection Memory pipeline that the Planner (RFC-0011) uses for cost and confidence estimation.

**Interaction:** Tool Runtime writes to RFC-0010 Episodic Memory after each invocation. This is a one-way write. The Tool Runtime does not read from Memory for invocation routing (routing decisions are based on the Tool Registry, not Memory).

**Write-on-completion only:** Memory writes are non-blocking and happen after the result is returned to the caller. A failed Memory write does not cause an invocation failure.

### RFC-0011: Planner

The Planner assigns `skill_type` to Tasks and optionally annotates Tasks with tool capability hints when the skill's `tool_dependencies` declaration is specific enough to predict which tool will be invoked. The Tool Runtime does not call the Planner. The Planner reads tool metadata from the Tool Registry (indirectly, through RFC-0002 skill manifests) when building cost and confidence estimates.

**Interaction:** One-way data dependency. Planner uses tool metadata for estimation. Tool Runtime executes without knowledge of the plan that generated the invocation.

## 5. Architecture

### 5.1 Architectural Philosophy

The Tool Runtime is structured as a **protocol-agnostic execution kernel** with a strict layered architecture. The key architectural invariant is:

> **No connector-specific logic may appear above the Connector Interface layer. No kernel logic may appear below the Connector Interface layer.**

This invariant is the primary mechanism for achieving the stated goal of becoming the abstraction underneath MCP, REST, CLI, Python, Browser, and future connectors. If connector-specific logic leaks upward, the abstraction fails and new connectors require changes to the kernel. If kernel logic leaks downward, connectors become tightly coupled to kernel internals and cannot be developed or deployed independently.

### 5.2 The Connector Interface

The Connector Interface is the most important boundary in this architecture. It is defined as a set of operations that every connector must implement, and a set of guarantees that the kernel makes to every connector. Nothing crosses this boundary except through the defined interface.

**Every connector must implement:**

```
CONNECTOR INTERFACE:

connect(config: ConnectorConfig) → ConnectionHandle | ConnectorError
disconnect(handle: ConnectionHandle) → void
invoke(handle: ConnectionHandle, request: NormalizedRequest)
  → RawResult | ConnectorError
stream(handle: ConnectionHandle, request: NormalizedRequest)
  → RawResultStream | ConnectorError
health_check(handle: ConnectionHandle) → ConnectorHealth
get_capabilities(handle: ConnectionHandle) → [RawCapabilityDescription]
cancel(handle: ConnectionHandle, invocation_id: UUID) → CancelResult
```

**The kernel guarantees to every connector:**

1. `invoke()` is called only after `connect()` has returned a valid `ConnectionHandle`.
2. `invoke()` is called with a `NormalizedRequest` that has already been validated against the tool's declared input schema.
3. `cancel()` will be called before `disconnect()` for any in-flight invocation.
4. No connector method is called concurrently on the same `ConnectionHandle` for the same invocation ID.
5. Credentials are delivered via the `ConnectorConfig`, never embedded in `NormalizedRequest`.

### 5.3 Capability-Based Tool Model

Tools are not modeled solely as callable endpoints. Each tool registers one or more **Tool Capabilities**: named, versioned, schema-bound operations that the tool can perform. A tool may offer multiple capabilities. Multiple tools may offer the same capability name (e.g., three different tools may each offer a `web.search` capability).

This capability model enables:
- **Capability-based routing:** A skill requests capability `web.search` and the Tool Runtime selects the best available tool offering that capability.
- **Capability-based policy:** Policy grants permission to use a capability class, not a specific tool, allowing tool substitution without policy changes.
- **Capability-based fallback:** If the preferred tool for a capability is unavailable, the Tool Runtime can automatically route to an alternative tool offering the same capability.

Capability routing is governed by a **Capability Selector** that applies: policy constraints, skill preferences, current tool health, cost tier, and latency estimates.

## 6. Internal Components

### 6.1 Tool Registry

The Tool Registry is the authoritative catalog of all tools known to the Tool Runtime. It is persistent (survives restarts), versioned, and indexed.

**Registry entry contents:**
- Tool identity: `tool_id`, `tool_name`, `vendor`, `version`.
- Capabilities: list of `ToolCapability` records (see Data Structures).
- Connectors: one or more registered `ConnectorBinding` records mapping the tool to a connector implementation with its configuration.
- Contract: declared input schemas, output schemas, error schemas.
- Behavioral metadata: side-effect class, idempotency classification, cost tier, latency profile.
- Lifecycle metadata: registered_at, last_seen, health status, version history.

**Registry indexes:**
- By `tool_id` (primary).
- By `capability_name` (for capability-based routing).
- By `connector_type` (for connector-specific queries).
- By `cost_tier` (for cost-aware routing).

**Registry consistency:** The Registry is the authority. In-memory caches of Registry data are derived. Cache invalidation is event-driven via RFC-0006.

### 6.2 Discovery Engine

The Discovery Engine populates the Tool Registry by finding available tools from multiple sources:

**Static discovery:** Tools declared in configuration files at startup. These are the most trusted tools: operator-defined, human-audited, policy-assigned.

**MCP server discovery:** The Discovery Engine connects to configured MCP servers and queries them for their available tools using the MCP protocol's tool listing mechanism. Each discovered tool is normalized into a `ToolCapability` record and registered.

**OpenAPI discovery:** The Discovery Engine fetches OpenAPI specifications from configured endpoints and synthesizes `ToolCapability` records from the operation definitions. This enables any REST API with an OpenAPI spec to be automatically registered as a set of tool capabilities.

**Programmatic discovery:** Skills may register tools at runtime via the `RegisterTool` interface. These registrations are scoped to the registering skill's identity and subject to policy.

**Conflict resolution:** When two sources register a tool with the same `capability_name`, the Conflict Resolver applies a priority ordering: static > MCP > OpenAPI > programmatic. Within the same source type, the most recently registered version takes precedence. Conflicts are logged and published as events.

**Discovery freshness:** The Discovery Engine re-queries dynamic sources (MCP servers, OpenAPI endpoints) on a configurable schedule (default: every 60 seconds) to detect new tools, updated tools, and tools that have disappeared. A disappeared tool is marked as `UNAVAILABLE` in the Registry rather than immediately deregistered, allowing in-flight invocations to complete.

### 6.3 Invocation Orchestrator

The Invocation Orchestrator is the central coordinator for a single tool invocation. Every invocation gets an `InvocationRecord` and passes through the following phases under the Orchestrator's control:

**Phase 1: Pre-invocation**
- Policy evaluation.
- Idempotency check.
- Quota and rate limit check.
- Input schema validation.
- Connector selection and routing.
- Sandboxing pre-execution hook.

**Phase 2: Execution**
- Connector dispatch.
- Timeout management (start timeout clock).
- In-flight tracking (update execution state).
- Streaming setup (if applicable).

**Phase 3: Post-invocation**
- Raw result receipt from connector.
- Sandboxing post-execution hook.
- Result normalization pipeline.
- Output schema validation.
- Artifact materialization (if result is large).
- Retry decision (if result indicates a retriable error).
- Memory write (Episodic Memory, non-blocking).
- Event publication.
- InvocationRecord finalization.

The Orchestrator is stateful for the duration of a single invocation. Its state is the `InvocationRecord`. The Orchestrator is not stateful across invocations; each invocation creates a new Orchestrator instance (or an equivalent stateless coordination chain).

### 6.4 Policy Gate

The Policy Gate wraps RFC-0003 calls with Tool Runtime-specific context. It evaluates:

- Can this `requester_identity` invoke this `tool_id`?
- Can this `requester_identity` use this `capability_class`?
- Can this invocation proceed given its declared `side_effect_class`?
- Does this invocation's `cost_tier` exceed the requester's allowed cost?

Policy decisions are cached per `(requester_identity, tool_id, capability_name)` with a TTL (default: 120 seconds). Cache invalidation on RFC-0006 `policy.updated` events.

**Fail-closed:** If RFC-0003 is unavailable, all tool invocations are denied. No cached decision overrides a live-unavailability for a new invocation. This is the same fail-closed principle applied throughout AGY.

### 6.5 Idempotency Manager

The Idempotency Manager prevents duplicate tool invocations from executing multiple times when the caller retries.

**Idempotency key assignment:** Every invocation receives an idempotency key. The caller may provide one explicitly; if absent, the Orchestrator generates one from: `hash(skill_id, tool_id, capability_name, serialized_input, execution_id, invocation_sequence_number)`. This ensures that the same logical invocation within the same execution always produces the same idempotency key.

**Idempotency store:** A short-lived store (default TTL: 24 hours) mapping `idempotency_key → InvocationRecord`. Before dispatching an invocation, the Idempotency Manager checks the store. If a record exists:
- Status `COMPLETED`: return the cached result immediately.
- Status `IN_FLIGHT`: return an `INVOCATION_IN_PROGRESS` response (caller may poll or wait).
- Status `FAILED`: proceed with the new invocation (failed invocations are not cached as idempotent results).

**Propagation to connectors:** Connectors that support idempotency headers (e.g., REST APIs accepting `Idempotency-Key`) receive the idempotency key as part of the `NormalizedRequest`. The connector is responsible for propagating it to the tool.

**Non-idempotent tool handling:** Tools with `idempotency_class: NON_IDEMPOTENT` declared in their registration are not subject to retry on failure (unless explicitly configured otherwise by the caller). The Idempotency Manager does not cache results for non-idempotent tools.

### 6.6 Quota and Rate Limit Enforcer

The Quota Enforcer maintains counters per `(tool_id, requester_identity, time_window)` and enforces:

- **Per-invocation rate limits:** Maximum invocations per second/minute/hour.
- **Cost-based quotas:** Accumulated cost units per time window (where cost is declared by the tool's `cost_tier`).
- **Concurrent invocation limits:** Maximum simultaneous in-flight invocations per tool per identity.

Counters are maintained in an in-memory structure with periodic persistence for crash recovery. In a distributed deployment, counters are maintained in a shared store (implementation-defined; the interface is defined here). Counter updates are optimistic: the counter is checked before invocation and decremented after. If the counter is at limit, the invocation is rejected with `QUOTA_EXCEEDED`.

**Quota source:** Quota limits are configured in RFC-0003 policy rules, not hardcoded in the Tool Runtime. The Quota Enforcer reads limits from the policy decision returned by the Policy Gate. This ensures quota policy changes take effect without Tool Runtime code changes.

### 6.7 Timeout Manager

The Timeout Manager enforces three distinct timeout types per invocation:

1. **Connection timeout:** Maximum time to establish the connection to the tool (via the connector). Default: 5 seconds. Configurable per tool registration.
2. **Read timeout:** Maximum time between data chunks during execution (prevents slow reads from hanging forever). Default: 30 seconds. Configurable per tool registration.
3. **Total timeout:** Maximum wall-clock time from invocation start to result receipt. Default: 60 seconds. Configurable per tool registration, per invocation, and per policy.

Timeout fires trigger:
- `cancel()` call to the connector.
- `InvocationRecord` status update to `TIMED_OUT`.
- `tool.invocation.timeout` event publication to RFC-0006.
- Return of `ToolError { error_class: TIMEOUT }` to the caller.

**Timeout hierarchy:** The more restrictive of (policy timeout, tool-registration timeout, invocation-specific timeout) applies. A policy may override tool registration defaults but cannot exceed a global system maximum.

### 6.8 Retry Engine

The Retry Engine decides whether and how to retry a failed invocation.

**Retry eligibility:**
- Only `RETRIABLE` error classes are retried automatically. Error classes are defined in Data Structures (Section 9.8).
- Only tools with `idempotency_class: IDEMPOTENT` or `AT_LEAST_ONCE` are automatically retried. `NON_IDEMPOTENT` tools require explicit `allow_retry_on_non_idempotent: true` in the invocation options.
- The caller may explicitly disable retries with `retry_policy: NONE`.

**Backoff strategies (configurable per tool registration):**
1. `IMMEDIATE`: Retry immediately. Only for transient network errors.
2. `LINEAR`: Wait `base_delay × attempt_number`.
3. `EXPONENTIAL`: Wait `base_delay × 2^attempt_number`.
4. `EXPONENTIAL_JITTER`: Exponential with random jitter. Default for most tools.

**Retry budget:** Maximum attempts is configurable per tool (default: 3). Total retry duration must not exceed the invocation's `total_timeout`. The Retry Engine checks the remaining timeout budget before each retry attempt.

**Retry logging:** Every retry attempt is logged in the `InvocationRecord` with the attempt number, delay, and error that triggered the retry.

### 6.9 Sandboxing Hook Layer

The Sandboxing Hook Layer provides a defined extension point for platform sandboxing enforcement. The Tool Runtime does not implement sandboxing. It calls sandbox hooks at specific points and enforces that hooks must succeed before execution proceeds.

**Hook interface:**

```
SANDBOXING HOOK INTERFACE:

pre_exec(context: SandboxContext) → SandboxDecision
  // Called before connector.invoke(). Returns PERMIT or DENY with reason.
  // On DENY: invocation is aborted; sandbox.violation event published.

post_exec(context: SandboxContext, raw_result: RawResult) → SandboxDecision
  // Called after connector.invoke() returns, before normalization.
  // May inspect result content for data exfiltration or policy violations.
  // On DENY: result is discarded; sandbox.violation event published.

on_stream_chunk(context: SandboxContext, chunk: RawChunk) → SandboxDecision
  // Called for each chunk in a streaming invocation.
  // On DENY: stream is terminated; sandbox.violation event published.
```

**SandboxContext contents:**
- `tool_id`, `capability_name`, `connector_type`
- `requester_identity`, `execution_id`, `session_id`
- `declared_permissions`: the permissions the tool claims to need.
- `network_destinations`: IP/hostname targets the connector will contact.
- `filesystem_paths`: paths the connector may read/write (for CLI connectors).
- `resource_limits`: CPU, memory, time limits declared for this connector type.

**Registered sandbox implementations:** At startup, sandboxing implementations register themselves with the Tool Runtime for specific connector types. CLI connectors may use a seccomp/cgroup sandbox. Python connectors may use a restricted interpreter sandbox. REST connectors may use a network egress firewall hook. If no sandbox is registered for a connector type and the tool is classified as requiring sandboxing, the invocation is denied.

**Null sandbox:** For development environments, a null sandbox (always returns PERMIT) may be registered. Production deployments must have non-null sandboxes for all connector types that access external network or filesystem resources.

### 6.10 Result Normalization Pipeline

The Result Normalization Pipeline transforms the raw output of every connector into a canonical `ToolResult` structure. Every connector speaks a different protocol and returns data in a different format. By the time the result reaches the calling skill, it is always a `ToolResult`.

**Pipeline stages:**

1. **Encoding Normalizer:** Converts bytes to text using the result's declared encoding (UTF-8 default). Handles encoding detection for connectors that do not declare encoding.

2. **Error Classifier:** Inspects the raw result for error signals (HTTP error codes, non-zero exit codes, exception types, error fields in JSON responses) and classifies them into canonical `ToolErrorClass` values.

3. **Schema Validator:** Validates the result content against the tool's declared output schema. Schema violations are captured as `ToolResult.schema_violations` rather than hard failures, unless the tool is configured with `strict_schema_validation: true`.

4. **Type Coercer:** Coerces result fields to their declared types where safe coercion is possible (e.g., numeric strings to numbers, ISO date strings to timestamp types). Unsafe coercions are reported as violations.

5. **Artifact Materializer:** If the result size (after normalization) exceeds the inline threshold (default: 32KB), writes the result content to RFC-0004 and replaces inline content with an `artifact_ref`.

6. **Truncation Handler:** If the result exceeds a maximum size limit (configurable; default: 10MB) after normalization, the result is truncated and annotated with `truncated: true`. Truncation is a last resort; the Artifact Materializer handles large results before truncation would occur.

**Pipeline failures:** A failure in any pipeline stage produces a `ToolResult` with `status: NORMALIZATION_FAILED` and a description of the failure. The raw result is preserved (or materialized as an Artifact) for debugging. The calling skill receives the normalization failure, not a raw result.

### 6.11 Streaming Manager

The Streaming Manager handles tool invocations that produce results as a stream of chunks rather than a single response.

**Unified stream abstraction:** Regardless of the underlying streaming mechanism (Server-Sent Events, chunked HTTP transfer, subprocess pipe, WebSocket frames), the Streaming Manager presents a unified `ToolResultStream` to the caller: an ordered sequence of `ToolResultChunk` values, each with a sequence number, a partial result payload, and a `stream_complete` flag on the final chunk.

**Backpressure:** The Streaming Manager applies backpressure if the caller is consuming chunks slower than the connector is producing them. Backpressure implementation is connector-specific (the connector must support it via the stream interface). If backpressure is not supported, the Streaming Manager buffers up to a configurable number of chunks before dropping the stream and reporting `STREAM_BUFFER_OVERFLOW`.

**Partial result delivery:** Each chunk is individually normalized (using the streaming variant of the Result Normalization Pipeline). Schema validation operates on the complete assembled stream, not on individual chunks, unless the tool's output schema specifies chunk-level schemas.

**Sandboxing for streams:** The `on_stream_chunk` sandbox hook is called for each chunk. This allows sandbox implementations to detect data exfiltration patterns that only become visible across multiple chunks (e.g., a tool that drip-feeds sensitive data across hundreds of small chunks).

## 9. Runtime Lifecycle

### 9.1 System Startup

```
1. Tool Runtime initializes configuration.
2. Tool Registry loads persisted registrations from durable store.
3. Connector implementations are loaded and health-checked.
4. Sandboxing Hook implementations register themselves per connector type.
5. Discovery Engine performs initial static discovery (configuration files).
6. Discovery Engine begins async dynamic discovery (MCP servers, OpenAPI endpoints).
   Discovery runs concurrently with steps 7-9; tools are registered as found.
7. Idempotency store is initialized (loaded from persisted state if available).
8. Quota Enforcer initializes counters (loaded from persisted state if available).
9. Tool Runtime subscribes to RFC-0006 event topics.
10. Tool Runtime registers background jobs with RFC-0007 Scheduler:
    - Discovery refresh job (configurable interval; default: 60 seconds).
    - Health check job (configurable interval; default: 30 seconds).
    - Idempotency store cleanup job (configurable interval; default: 1 hour).
    - Contract verification job (configurable interval; default: 6 hours).
11. tool.runtime.ready event published to RFC-0006.
```

### 9.2 Invocation Lifecycle (Non-Streaming)

```
1.  Invoke() received.
2.  InvocationRecord created, status = IN_FLIGHT.
3.  Policy Gate evaluated. On DENY: return POLICY_DENIED, record finalized.
4.  Quota and rate limit checked. On EXCEEDED: return QUOTA_EXCEEDED.
5.  Idempotency Manager checked.
    - CACHED result found: return cached result, record updated with CACHED status.
    - IN_FLIGHT: return INVOCATION_IN_PROGRESS.
    - No record: proceed.
6.  Input validated against ToolCapability input schema.
    On violation: return INPUT_SCHEMA_VIOLATION with violation details.
7.  Connector selected by Capability Selector (see Algorithm 11.2).
8.  Credentials resolved from CredentialReference (future RFC).
9.  NormalizedRequest constructed.
10. Sandboxing pre-exec hook called. On DENY: return SANDBOX_DENIED.
11. Connector.invoke() dispatched. Timeout clock started.
12. Raw result received (or timeout/error).
13. Sandboxing post-exec hook called. On DENY: result discarded, SANDBOX_DENIED.
14. Result Normalization Pipeline applied.
15. ToolResult constructed.
16. Retry decision made.
    - If retriable error and attempts < max_attempts: goto step 9 (with backoff).
    - Otherwise: finalize.
17. If result size > inline threshold: Artifact materialization (RFC-0004).
18. InvocationRecord finalized.
19. Idempotency store updated (result cached for IDEMPOTENT tools).
20. Episodic Memory write (RFC-0010, non-blocking fire-and-forget).
21. tool.invocation.completed (or .failed) event published (RFC-0006).
22. InvocationResult returned to caller.
```

### 9.3 Tool Registration Lifecycle

```
1. RegisterTool() received.
2. Policy Gate: can this identity register tools at this scope?
3. Contract validated (schema syntax, behavioral metadata completeness).
4. Connector reachability verified (connector.health_check() called).
   On failure: CONNECTOR_UNREACHABLE error. Registration rejected.
5. Conflict detection: does a tool with the same capability_name exist?
   - No conflict: proceed.
   - Conflict: apply Conflict Resolver. If unresolvable: CONFLICT_UNRESOLVABLE.
6. Tool assigned a tool_id (if new) or version incremented (if updating).
7. Tool Registry persisted.
8. Capability Index updated.
9. tool.registered event published (RFC-0006).
10. Return tool_id and assigned_capabilities.
```

### 9.4 Health Check Lifecycle

The Health Check background job runs on a configurable schedule (default: 30 seconds). For each registered tool:

```
1. connector.health_check() called for each ConnectorBinding.
2. ConnectorHealth received: HEALTHY | DEGRADED | UNAVAILABLE.
3. Tool Registry updated with health status.
4. If status transitions HEALTHY → UNAVAILABLE:
   - In-flight invocations are allowed to complete (no forced cancellation).
   - New invocations to this tool return TOOL_UNAVAILABLE.
   - tool.deregistered event not published (tool remains in registry as UNAVAILABLE).
5. If status transitions UNAVAILABLE → HEALTHY:
   - Tool marked HEALTHY.
   - New invocations resume routing to this tool.
6. If tool remains UNAVAILABLE for > configured grace period (default: 5 minutes):
   - Tool marked STALE_UNAVAILABLE.
   - Discovery Engine may attempt re-discovery.
```

### 9.5 Contract Verification Lifecycle

The Contract Verification job periodically validates that registered tools still conform to their declared contracts. It does this by:

1. Executing a set of synthetic, non-destructive test invocations against the tool using the tool's declared test fixtures (if provided in the `ToolContract`).
2. Comparing results against expected outputs defined in the test fixtures.
3. If results deviate: marking the contract as `VIOLATION_DETECTED` and publishing a `tool.contract.violation` event.
4. Contract violations do not automatically deregister the tool or block invocations. They surface as warnings in `GetToolContract` responses and as events for human review.

Contract verification using destructive tools (those with `side_effect_class: IRREVERSIBLE` or `DESTRUCTIVE`) is skipped unless the tool provides explicit read-only test fixtures.

## 11. Algorithms

### 11.1 Capability Selector Algorithm

Given a tool invocation request that specifies a `capability_name` (rather than an explicit `tool_id`), the Capability Selector finds the best available tool:

```
PROCEDURE select_tool(capability_name: string,
                      requester_identity: SkillIdentity,
                      options: InvocationOptions) → ConnectorBinding | ERROR:

  // Step 1: Find all tools offering this capability
  candidates = registry.query(capability_name=capability_name,
                               health_status=HEALTHY)
  IF candidates is empty:
    candidates = registry.query(capability_name=capability_name,
                                 health_status=DEGRADED)
    IF candidates is empty:
      RETURN CAPABILITY_NOT_FOUND

  // Step 2: Filter by policy
  permitted = [c FOR c IN candidates IF
               policy_gate.evaluate(requester_identity, c.tool_id,
                                    capability_name) == PERMIT]
  IF permitted is empty:
    RETURN POLICY_DENIED

  // Step 3: Filter by version constraint (if specified)
  IF options.version_constraint is set:
    permitted = [c FOR c IN permitted IF
                 satisfies(c.version, options.version_constraint)]
    IF permitted is empty:
      RETURN NO_COMPATIBLE_VERSION

  // Step 4: Filter by cost tier (if options specify a max cost tier)
  IF options.max_cost_tier is set:
    permitted = [c FOR c IN permitted IF
                 c.behavioral_metadata.cost_tier <= options.max_cost_tier]

  // Step 5: Score and rank remaining candidates
  FOR EACH candidate IN permitted:
    candidate.selection_score =
      (0.4 × health_score(candidate)) +         // HEALTHY=1.0, DEGRADED=0.3
      (0.3 × (1.0 / cost_score(candidate))) +   // lower cost = higher score
      (0.2 × (1.0 / latency_score(candidate))) + // lower latency = higher score
      (0.1 × priority_score(candidate))          // connector binding priority

  // Step 6: Select highest scoring candidate
  selected = max_by(permitted, key=selection_score)
  RETURN selected.get_connector_binding(connector_type=best_available)
```

**Tie-breaking:** On equal score, lower `connector_binding.priority` value wins (explicit operator preference). On equal priority, alphabetically first `tool_id` wins (deterministic but arbitrary).

### 11.2 Retry Backoff Algorithm

```
PROCEDURE compute_retry_delay(attempt: integer,
                               strategy: BackoffStrategy,
                               base_delay_ms: integer,
                               max_delay_ms: integer,
                               tool_retry_after_ms: integer) → integer:

  hint_delay = tool_retry_after_ms IF tool_retry_after_ms > 0 ELSE 0

  SWITCH strategy:
    IMMEDIATE:
      computed_delay = 0

    LINEAR:
      computed_delay = base_delay_ms × attempt

    EXPONENTIAL:
      computed_delay = base_delay_ms × (2 ^ (attempt - 1))

    EXPONENTIAL_JITTER:
      exp_delay = base_delay_ms × (2 ^ (attempt - 1))
      jitter = random_uniform(0, exp_delay × 0.3)
      computed_delay = exp_delay + jitter

  // Tool-provided hint takes precedence if larger than computed delay
  final_delay = max(computed_delay, hint_delay)

  // Cap at configured maximum
  final_delay = min(final_delay, max_delay_ms)

  // Verify this delay fits within remaining timeout budget
  remaining_budget = invocation.total_timeout_ms - invocation.elapsed_ms
  IF final_delay >= remaining_budget:
    RETURN RETRY_BUDGET_EXHAUSTED

  RETURN final_delay
```

### 11.3 Idempotency Key Generation

```
PROCEDURE generate_idempotency_key(skill_id: SkillID,
                                    tool_id: UUID,
                                    capability_name: string,
                                    input: map<string, TypedValue>,
                                    execution_id: UUID,
                                    sequence_number: integer) → string:

  canonical_input = canonicalize(input)
    // Canonicalize: sort keys lexicographically, normalize values,
    // remove ephemeral fields (timestamps, request IDs provided by caller).

  components = [
    skill_id,
    tool_id,
    capability_name,
    SHA256(canonical_input),
    execution_id,
    sequence_number
  ]

  RETURN BASE64URL(SHA256(JOIN(components, separator=":")))
```

**Why execution_id + sequence_number?** Two different invocations of the same tool with the same input within the same execution (e.g., retry loop) must have different idempotency keys — the sequence number differentiates them. Two invocations of the same tool with the same input in different executions (e.g., replanning) should also have different idempotency keys — the execution_id differentiates them. This prevents cross-execution idempotency collisions.

### 11.4 Contract Violation Detection

```
PROCEDURE validate_output(raw_result: RawResult,
                           tool_contract: ToolContract) → ValidationResult:

  normalized = normalize(raw_result)

  violations = []

  // Schema validation
  schema_result = validate_against_schema(normalized, tool_contract.output_schema)
  violations.extend(schema_result.violations)

  // Behavioral guarantee checks
  FOR EACH guarantee IN tool_contract.behavioral_guarantees:
    SWITCH guarantee.guarantee_type:
      IDEMPOTENT:
        // Check: repeated invocation with same key returns same result
        // (only verifiable if we have a previous result to compare)
        prior_result = idempotency_store.get(current_invocation.idempotency_key)
        IF prior_result exists AND prior_result != normalized:
          violations.append(Violation(IDEMPOTENCY_BROKEN,
            "Tool returned different result for same idempotency key"))

      SIDE_EFFECT_FREE:
        // Cannot verify at invocation time; recorded for audit.
        // Sandbox post-exec hook is the primary enforcement.
        PASS

  IF violations is empty:
    RETURN ValidationResult(VALID)
  ELSE:
    IF any violation has severity ERROR:
      RETURN ValidationResult(CONTRACT_VIOLATED, violations)
    ELSE:
      RETURN ValidationResult(SCHEMA_WARNING, violations)
```

### 11.5 Result Normalization Pipeline Execution

```
PROCEDURE normalize(raw_result: RawResult,
                     tool_contract: ToolContract) → ToolResult:

  // Stage 1: Encoding
  text_content = encoding_normalizer.decode(
    raw_result.content,
    declared_encoding = raw_result.encoding,
    fallback = "UTF-8"
  )

  // Stage 2: Error classification
  error_classification = error_classifier.classify(
    raw_result.status_indicator,
    raw_result.connector_type,
    text_content
  )
  IF error_classification.is_error:
    RETURN ToolResult(status=FAILED, error=error_classification.tool_error)

  // Stage 3: Content parsing
  parsed = parse_by_content_type(text_content, raw_result.content_type)
  IF parsing fails:
    RETURN ToolResult(status=NORMALIZATION_FAILED,
                      error=PARSE_FAILURE,
                      raw_artifact_ref=materialize(raw_result.content))

  // Stage 4: Schema validation
  violations = schema_validator.validate(parsed, tool_contract.output_schema)

  // Stage 5: Type coercion
  coerced = type_coercer.coerce(parsed, tool_contract.output_schema)
  violations.extend(type_coercer.coercion_violations)

  // Stage 6: Size check and artifact materialization
  size = estimate_size(coerced)
  IF size > INLINE_THRESHOLD:
    artifact_ref = artifact_system.write(coerced)
    output = ToolOutput(artifact_ref=artifact_ref)
  ELSE:
    output = ToolOutput(inline_data=coerced)

  // Stage 7: Truncation (last resort)
  IF size > MAX_RESULT_SIZE AND artifact_ref is null:
    output = truncate(output, MAX_RESULT_SIZE)
    truncated = true

  RETURN ToolResult(
    status = SUCCESS IF violations.all(severity=WARNING) ELSE SCHEMA_VIOLATION,
    output = output,
    schema_violations = violations,
    truncated = truncated,
    result_hash = SHA256(canonical_serialize(coerced))
  )
```

## 12. Failure Recovery

### 12.1 Failure Classification Matrix

| Failure | Detection | Immediate Response | Recovery |
|---|---|---|---|
| Connector connection failure | `ConnectorError` on `connect()` | Route to alternate connector if available | Retry with backoff; mark binding UNAVAILABLE |
| Connector read timeout | Timeout Manager fires | Cancel in-flight invocation | Retry if retriable |
| Tool returns error response | Error Classifier | Classify error class | Retry if RETRIABLE class |
| Schema contract violation | Schema Validator | Log violation; return partial result | Publish `tool.contract.violation` event |
| Sandbox hook DENY | SandboxingHookLayer | Abort invocation | Do not retry; return SANDBOX_DENIED |
| Policy Engine unavailable | Policy Gate | Fail-closed; deny invocation | Do not retry invocation; wait for PE recovery |
| Artifact System unavailable (result materialization) | RFC-0004 write failure | Return inline result if below threshold | Log; do not fail the invocation |
| Artifact System unavailable (input hydration) | RFC-0004 read failure | Fail invocation | Cannot proceed without input |
| Memory write failure (Episodic) | RFC-0010 write failure | Swallow error; log | Non-fatal; next invocation will write |
| Tool Registry corrupted | Registry integrity check at startup | Load from last valid snapshot | Alert; registry rebuilt from persisted state |
| Idempotency store unavailable | Store access failure | Continue without idempotency protection | Log IDEMPOTENCY_DEGRADED warning; proceed |

### 12.2 Connector Failover

When a tool has multiple `ConnectorBinding` entries (e.g., a primary MCP connector and a fallback REST connector), the Capability Selector normally routes to the highest-scored binding. If that binding's connector returns a `NETWORK_UNAVAILABLE` or `NETWORK_TIMEOUT` error, the Invocation Orchestrator may fail over to the next highest-scored binding for the same tool, without counting the failover as a retry attempt.

Failover eligibility: only for `NETWORK_UNAVAILABLE` and `NETWORK_TIMEOUT` error classes. Application-level errors (`AUTHORIZATION_DENIED`, `INPUT_INVALID`, `CONTRACT_VIOLATED`) do not trigger failover; they are returned to the caller immediately.

### 12.3 Graceful Degradation

When the Tool Runtime is under extreme load or partial failure:

1. **Discovery disabled:** If the Discovery Engine fails, the Tool Runtime serves the last known Registry state. New tools will not be discovered until discovery recovers, but existing tools remain available.
2. **Health checks disabled:** If health check jobs fail, tools remain in their last known health state. Invocations to tools in UNKNOWN health state are permitted with a `HEALTH_UNKNOWN` annotation on the InvocationRecord.
3. **Idempotency store degraded:** If the idempotency store is unavailable, the Tool Runtime continues without idempotency caching. Duplicate invocations may re-execute. This is logged as a degraded mode warning.
4. **Policy cache without invalidation:** If RFC-0006 event subscription fails, the policy cache TTL ensures stale decisions are eventually refreshed. The refresh cycle may be longer than normal during Event Bus outage.

### 12.4 In-Flight Invocation Handling on Shutdown

On graceful shutdown:

```
1. Stop accepting new Invoke() calls (return SERVICE_SHUTTING_DOWN).
2. Allow in-flight invocations to complete up to the configured
   shutdown grace period (default: 30 seconds).
3. After grace period: cancel all remaining in-flight invocations.
4. Finalize all InvocationRecords with appropriate terminal status.
5. Persist Idempotency store state.
6. Persist Quota Enforcer counter state.
7. Disconnect all active connector connections.
8. Publish tool.runtime.shutdown event.
```

## 13. Security Considerations

### 13.1 Threat Model

**Threats specific to the Tool Runtime:**

1. **Connector injection:** A skill registers a malicious connector implementation that steals credentials, exfiltrates data, or executes arbitrary code on the AGY host.
2. **SSRF via tool invocation:** A skill crafts tool inputs that cause a connector to make HTTP requests to internal network resources (e.g., `http://169.254.169.254/` on cloud infrastructure).
3. **Data exfiltration via tool outputs:** A tool returns a response that contains data from the AGY host filesystem or internal memory that it should not have access to.
4. **Credential theft:** A connector implementation reads credentials from the NormalizedRequest and transmits them to an attacker-controlled endpoint.
5. **Replay attacks:** An attacker replays a previously recorded valid tool invocation to cause unintended side effects.
6. **Resource exhaustion:** A skill invokes high-cost tools at high frequency to exhaust quota or degrade the system for other tenants.
7. **Contract poisoning:** A malicious skill registers a tool with a benign-looking contract but an implementation that violates declared behavioral guarantees.

### 13.2 Defense Mechanisms

**Connector injection:** Connector implementations are loaded at startup from a configured, operator-controlled path. Runtime registration of new connector implementations is not permitted through the public API. Only tool configurations (which connector to use, and how to configure it) can be registered at runtime, not new connector code.

**SSRF:** Network destination validation is the responsibility of the sandboxing hook implementation for REST and other network-accessing connectors. The `SandboxContext.network_destinations` field provides the declared destinations to the sandbox; the sandbox enforces allowlists. SSRF via dynamic URL construction (tool input contains a URL that the connector uses) is defended by requiring that all connector endpoints be declared in `ConnectorBinding.endpoint` at registration time — dynamic URL construction from tool inputs must be explicitly declared as a tool behavior and requires elevated policy.

**Data exfiltration:** The sandboxing post-exec hook inspects result content before it is returned. File system access by connectors (CLI, Python) is restricted to declared paths in `SandboxContext.filesystem_paths`. Results that contain content from undeclared paths are flagged as violations.

**Credential theft:** Credentials are resolved from `CredentialReference` immediately before connector dispatch and passed to the connector as an `OpaqueCredential`. The credential value is never logged, never included in InvocationRecord summaries, and never included in Artifact outputs. Connectors receive credentials only through the `NormalizedRequest.credential` field; accessing them in any other way is a sandbox violation.

**Replay attacks:** Idempotency keys prevent exact replay: the same invocation with the same idempotency key returns the cached result without re-executing. Tools with `side_effect_class: IRREVERSIBLE` or `DESTRUCTIVE` have their idempotency records retained for longer periods (configurable; default: 7 days).

**Resource exhaustion:** The Quota Enforcer enforces per-tool, per-identity, per-tenant rate limits. These limits are policy-driven and enforced before invocation. Sustained quota violation patterns are published as events for automated alerting.

**Contract poisoning:** Contract verification (see Section 9.5) uses synthetic test invocations to detect deviations from declared behavior. Tools with unverified contracts are flagged in `GetToolContract` responses. Policy may be configured to deny invocations of tools with `verification_status: VIOLATION_DETECTED`.

### 13.3 Input Sanitization Scope

The Tool Runtime validates inputs against the declared input schema. It does not perform protocol-specific sanitization (SQL injection, XSS, shell injection). That is the connector's responsibility. However:

- **CLI connectors** must sanitize all tool inputs before including them in shell commands. The CLI Connector specification (a separate implementation document) must mandate shell escaping.
- **REST connectors** must URL-encode path parameters and query strings.
- **Python connectors** must not use `eval()` or `exec()` on tool inputs.

These are **connector implementation requirements** enforced by the sandbox, not by the Tool Runtime kernel.

### 13.4 Audit Trail Integrity

Every `InvocationRecord` is written to an append-only audit log independent of the Tool Registry and the Episodic Memory write. Audit logs capture the full invocation lifecycle without including raw credentials, full input/output (privacy), or internal connector errors (security). The audit log is write-once. Modification of audit log entries by any identity, including administrative identities, requires a separate out-of-band process with multi-party approval — this is a deployment policy, not a kernel enforcement.

## 14. Performance Analysis

### 14.1 Invocation Latency Targets

| Invocation type | Target P50 | Target P99 |
|---|---|---|
| Policy cache hit, small inline result | < 5ms overhead | < 20ms overhead |
| Policy cache miss, small inline result | < 15ms overhead | < 50ms overhead |
| Large result (Artifact materialization) | < 50ms overhead | < 150ms overhead |
| Streaming (first chunk delivery) | < 20ms overhead | < 80ms overhead |

"Overhead" means the Tool Runtime's contribution to latency, excluding the tool's own execution time.

### 14.2 Critical Path Analysis

```
Policy Gate (cache hit):            < 2ms
Idempotency Manager check:          < 1ms
Quota Enforcer check:               < 1ms
Input Schema Validation:            < 3ms (cached schema)
Connector Selection:                < 1ms
Sandbox Pre-Exec Hook:              < 2ms
NormalizedRequest Construction:     < 1ms
Connector Dispatch:                 [tool execution time - not our latency]
Sandbox Post-Exec Hook:             < 2ms
Result Normalization (small):       < 5ms
Event Publication:                  < 1ms (async, non-blocking)
Memory Write (async, non-blocking): < 0ms (caller does not wait)
─────────────────────────────────────────
Total overhead P50:                 ≈ 19ms
```

### 14.3 Connection Pooling Impact

Connection establishment is the dominant latency contributor for network-based connectors. Connection pooling amortizes this cost across invocations. A pool of 10 connections to a REST tool, each with a 200ms establishment time, reduces effective establishment latency to < 1ms per invocation in steady state. The connection pool configuration in `ConnectorBinding` must be tuned per tool based on expected invocation frequency.

### 14.4 Schema Validation Cost

Validating tool inputs and outputs against JSON Schema (or equivalent) can be expensive for complex schemas. The Tool Runtime caches compiled schema validators per `(tool_id, capability_name, schema_version)`. Schema compilation occurs once at registration time and at schema version changes. In steady state, validation against a cached compiled schema is < 1ms for most inputs.

### 14.5 Throughput Targets

- 10,000 tool invocations per second across all tools (distributed).
- 1,000 concurrent in-flight invocations per Tool Runtime node.
- 100 concurrent streaming invocations per node.
- Tool Registry queries: 50,000 reads per second (heavily cached).

## 15. Scalability Analysis

### 15.1 Tool Registry Scale

The Tool Registry must support thousands of registered tools, each with multiple capabilities and connector bindings. At 10,000 tools with an average of 5 capabilities each, that is 50,000 capability entries. The Capability Index (keyed by `capability_name`) must support sub-millisecond lookups at this scale. A hash-indexed in-memory structure with a persistent backing store achieves this.

### 15.2 Concurrent Invocation Scale

At 1,000 concurrent in-flight invocations, the Invocation Orchestrator manages 1,000 active `InvocationRecord` instances. Each record is isolated; there is no shared mutable state across concurrent invocations (beyond the Quota Enforcer counters, which use atomic operations). This scales horizontally: each Tool Runtime node handles its own concurrent invocations independently.

### 15.3 Idempotency Store Scale

The Idempotency Store grows with invocation volume. At 10,000 invocations per second with a 24-hour TTL, the store contains up to 864,000,000 entries — clearly not manageable as a full in-memory store. Practical implementations should use a tiered approach: recent entries (< 1 hour) in memory, older entries in a persistent store (queried only when a key is not found in memory). Most idempotency key reuse occurs within seconds or minutes of the original invocation, so the memory tier handles the vast majority of lookups.

### 15.4 Scalability Risks

**Risk 1: Sandbox hook latency.** If sandbox implementations are slow (e.g., they make network calls to a policy enforcement point), they add to the critical path of every invocation. Sandbox implementations must be designed for sub-millisecond execution in the common case.

**Risk 2: Discovery storm.** If many Tool Runtime nodes restart simultaneously and all trigger dynamic discovery at the same time, they may overwhelm MCP servers or OpenAPI endpoints with concurrent requests. Discovery must include jitter and exponential backoff for dynamic sources.

**Risk 3: Result Normalization pipeline for large streaming results.** A streaming invocation producing 1GB of data through the normalization pipeline is a memory pressure risk. The Streaming Manager must process chunks incrementally and not buffer the full stream. Schema validation for streaming results must be designed to operate on chunks, not on the assembled full result.

**Risk 4: Contract verification at scale.** Running synthetic test invocations against every registered tool on a 6-hour cycle, at 10,000 tools, means approximately 28 test invocations per second. This must be rate-limited and scheduled with low priority to avoid impacting production traffic.

## 16. Concurrency Model

### 16.1 Invocation Isolation

Every tool invocation is isolated. There is no shared mutable state between concurrent invocations except:
- Quota Enforcer counters (atomic increment/decrement operations).
- Idempotency Store (concurrent read-before-write with optimistic locking).
- Tool Registry reads (read-only; no locking required).
- Connection Pool (pool-internal locking; connection checkout/checkin is atomic).

### 16.2 Connection Pool Concurrency

The Connection Pool for each `ConnectorBinding` uses internal locking to manage connection checkout and checkin. The pool is the concurrency boundary for connector connections. The Invocation Orchestrator checks out a connection at the start of execution and checks it in at the end (or on failure). Connections are never shared between concurrent invocations.

### 16.3 Streaming Concurrency

A streaming invocation holds a connector connection open for the duration of the stream. Concurrent streaming invocations require concurrent connections. The `max_concurrent_invocations` in `ToolCapabilityDeclaration` and the `max_connections` in `ConnectionPoolConfig` must be tuned together: if a tool supports maximum 10 concurrent streaming invocations and the pool allows 20 connections, the capability limit (10) is the binding constraint.

### 16.4 Registry Write Concurrency

Tool Registration and Deregistration are serialized through the Registry's write lock. Concurrent registrations are queued. This is acceptable because registration is an infrequent operation compared to invocation. Registry reads are concurrent and lock-free (read-copy-update semantics on the in-memory index).

### 16.5 Background Job Concurrency

Background jobs (Discovery, Health Check, Contract Verification) run under RFC-0007 Scheduler control. Each job type runs one instance at a time per Tool Runtime node (enforced by the Scheduler's exclusive lease mechanism described in RFC-0010). Health checks for individual tools run concurrently (up to a configurable maximum parallel health check degree, default: 50).

## 17. Testing Strategy

### 17.1 Connector Interface Compliance Tests

Every connector implementation must pass a standard compliance test suite that validates:
- `connect()` succeeds with valid config and fails gracefully with invalid config.
- `invoke()` returns a `RawResult` conforming to the expected structure.
- `cancel()` terminates in-flight invocations within the connector's declared cancel latency.
- `health_check()` returns a valid `ConnectorHealth` structure.
- `stream()` produces chunks in order with correct sequence numbers and a final `is_final` chunk.

These tests are connector-agnostic and defined by this RFC. New connector implementations must pass this suite before being accepted.

### 17.2 Unit Tests

- **Capability Selector:** All selection criteria combinations. Tie-breaking determinism. Empty candidate list. All candidates policy-denied.
- **Idempotency Manager:** Cache hit returns cached result. Cache miss proceeds. IN_FLIGHT response for concurrent duplicate. Non-idempotent tool bypasses cache.
- **Retry Engine:** Max attempts respected. Total timeout budget respected. Non-retriable error class not retried. EXPONENTIAL_JITTER produces different delays each attempt.
- **Timeout Manager:** Connection timeout fires correctly. Read timeout fires correctly. Total timeout fires correctly. Cancel is called on timeout.
- **Result Normalization Pipeline:** Each stage independently. Pipeline failure at each stage. Large result triggers Artifact materialization. Encoding detection for missing content-type.
- **Contract Violation Detection:** Correct detection of schema violations. Behavioral guarantee violations. Correct severity assignment.

### 17.3 Integration Tests

- **Policy integration:** Policy PERMIT allows invocation. Policy DENY blocks invocation. CONDITIONAL policy annotates InvocationRecord. Policy Engine unavailability triggers fail-closed.
- **Artifact integration:** Large result materializes correctly to RFC-0004. Artifact input hydrated correctly from RFC-0004. Artifact deletion event (RFC-0006) invalidates cached result reference.
- **Memory integration:** Episodic Memory write occurs after invocation. Memory write failure does not fail invocation. Record content is bounded (no raw credentials in memory).
- **Event Bus integration:** All defined events published at correct lifecycle points. Payload structure matches defined schemas.
- **Sandbox integration:** Pre-exec DENY aborts invocation. Post-exec DENY discards result. Stream chunk DENY terminates stream.

### 17.4 Scenario Tests

- **Full invocation lifecycle:** Register tool → Discover tool → Invoke tool → Verify InvocationRecord → Verify Episodic Memory entry → Verify Event Bus publications.
- **Retry scenario:** Tool returns RATE_LIMITED on first two attempts. Succeeds on third. Verify correct retry delay, attempt count in InvocationRecord.
- **Capability-based routing:** Three tools registered for same capability. Primary tool is UNAVAILABLE. Verify routing to next best tool.
- **Streaming scenario:** Stream 100 chunks. Cancel after chunk 50. Verify CANCELLED status. Verify no further chunks processed.
- **Idempotency scenario:** Invoke tool. Before completion, invoke again with same idempotency key. Verify second invocation returns INVOCATION_IN_PROGRESS. After completion, invoke again. Verify CACHED result returned.
- **Contract violation scenario:** Register tool with strict schema. Invoke tool. Return response that violates schema. Verify CONTRACT_VIOLATED result. Verify `tool.contract.violation` event published.
- **Graceful shutdown:** 10 concurrent in-flight invocations. Trigger shutdown. Verify all complete within grace period. Verify all InvocationRecords finalized.

### 17.5 Adversarial Tests

- **SSRF attempt:** Craft tool input containing internal IP address. Verify sandbox hook DENY fires. Verify SANDBOX_DENIED returned.
- **Quota exhaustion:** Invoke tool at 2× rate limit. Verify QUOTA_EXCEEDED returned for excess invocations.
- **Backtracking exhaustion (registration):** Attempt to register 1,000 tools with the same capability name simultaneously. Verify Conflict Resolver handles all without deadlock.
- **Malformed raw result:** Connector returns binary garbage. Verify normalization pipeline returns NORMALIZATION_FAILED without panicking.

## 18. Tradeoff Analysis

### 18.1 Capability-Based vs. Tool-Specific Invocation

**Decision:** Support both. Skills may invoke by `tool_id` (tool-specific) or by `capability_name` (capability-based).

**Rationale:** Pure capability-based routing is ideal for flexibility but loses the ability for a skill to require a specific tool when it genuinely matters (e.g., a skill that produces output specifically for a downstream system that only accepts input in a tool-specific format). Pure tool-specific invocation eliminates the routing flexibility that makes capability-based substitution possible.

**Weakness:** Skills that use tool-specific invocation are tightly coupled to a specific tool. When that tool is deprecated or unavailable, the skill breaks. Skills should be designed to use capability-based routing wherever possible. This is an engineering culture concern, not an enforcement concern.

### 18.2 Synchronous Result Normalization vs. Async

**Decision:** Synchronous Result Normalization Pipeline.

**Rejected alternative:** Async normalization where the raw result is buffered and normalization happens in a background job.

**Rationale:** Skills expect a normalized result before they can proceed. Async normalization would require skills to poll for results or use a callback mechanism, adding protocol complexity. The synchronous pipeline's overhead (< 10ms for most results) is acceptable on the critical path.

**Weakness:** The synchronous pipeline becomes a bottleneck for very large results. The Artifact Materializer stage mitigates this by offloading large content to RFC-0004, but the pipeline itself must process the full result before materializing. Streaming results partly mitigate this by processing chunk-by-chunk.

### 18.3 Sandboxing Hooks vs. Built-In Sandboxing

**Decision:** Pluggable sandboxing hooks.

**Rejected alternative:** Built-in sandboxing (e.g., running all connectors in gVisor containers).

**Rationale:** Sandboxing requirements vary dramatically by deployment environment. A cloud-native deployment may use container-level isolation. An on-premises deployment may use hypervisor-level isolation. A development environment may use no isolation. A single built-in sandboxing mechanism would be correct for one deployment model and incorrect or impossible for others. Pluggable hooks allow platform-appropriate sandboxing without changing the kernel.

**Weakness:** The effectiveness of sandboxing is entirely dependent on the quality of the plugged-in implementation. The Tool Runtime provides no fallback sandboxing if no implementation is registered. For connector types requiring sandboxing, absence of a registered sandbox implementation must deny invocations — this is the fail-closed behavior specified in Section 6.9.

### 18.4 InvocationRecord as Full Audit vs. Summary

**Decision:** InvocationRecord stores summaries of input and output, not full data. Full data is in the result Artifact (access-controlled).

**Rejected alternative:** Store full input and output in the InvocationRecord.

**Rationale:** Full input/output in the InvocationRecord creates privacy and security concerns: credentials embedded in inputs (even though the Tool Runtime tries to prevent this, defensive design matters), PII in outputs, or sensitive business data in both. Summaries provide enough for audit without storing full data in a lower-security context. Full data is in the result Artifact, which has RFC-0004's access control applied.

**Weakness:** Debugging production failures becomes harder when the InvocationRecord only has summaries. A separate "debug mode" flag (policy-gated) that stores full input/output for a configurable duration is a reasonable future extension.

### 18.5 Per-Node vs. Distributed Quota Enforcement

**Decision:** Per-node quota enforcement with optional distributed store.

**Rationale:** Strict distributed quota enforcement requires a distributed atomic counter with sub-millisecond latency — extremely difficult to achieve without a purpose-built distributed rate limiter (like a Redis-based token bucket). Per-node enforcement is immediately implementable and correct for single-node deployments. For distributed deployments, the "distributed store" option in the Quota Enforcer allows operators to plug in a shared counter implementation.

**Weakness:** Per-node enforcement permits quota overrun by a factor of N (where N is the number of Tool Runtime nodes). A skill on node 1 and the same skill on node 2 could each consume the full per-node quota. This is an accepted tradeoff for the deployment simplicity it provides. Tools with strict quota requirements should use the distributed store option.

### 18.6 Retry Before Failover vs. Failover Before Retry

**Decision:** Failover before retry for `NETWORK_*` errors. Retry with backoff for application-level retriable errors.

**Rationale:** For network errors, the current connector binding is likely unavailable, so retrying against the same binding is unlikely to succeed. Failover to an alternative binding has a higher chance of immediate success. For application-level retriable errors (rate limiting, transient server errors), all connector bindings are likely to exhibit the same behavior (since they reach the same backend tool), so failover adds no benefit; retry with backoff allows the tool to recover.

**Weakness:** The distinction between "network error" and "tool application error" is not always clear. An HTTP 503 from a REST connector could be a network layer error or an application layer error. The Error Classifier's classification may be wrong in edge cases, leading to failover when backoff would be correct, or vice versa. The Connector Compliance Tests should include edge case classification scenarios.

## 19. Compatibility Notes

### 19.1 RFC-0002: skill_manifests Require tool_dependencies Field

This RFC requires skills to declare their tool dependencies in their manifests (`tool_dependencies` block). RFC-0002 may not currently support this field. An RFC-0002 amendment is required.

**If RFC-0002 is not amended:** The Tool Runtime's pre-validation of tool availability at skill load time will be skipped. Tool availability will not be checked until the skill actually invokes a tool during execution, which surfaces the failure later and less gracefully. The system remains functional but loses the early warning capability.

### 19.2 RFC-0003: Tool-Specific Policy Attributes

This RFC introduces `tool.*` policy attributes. RFC-0003 must support these in its attribute namespace. Additionally, this RFC requires a distinction between plan-time policy evaluation (introduced in RFC-0011) and tool-invocation-time evaluation. RFC-0003's policy evaluation context must support a `TOOL_INVOCATION` context type.

**Required addition:** RFC-0003 attribute namespace must include `tool.id`, `tool.capability_class`, `tool.side_effect_class`, `tool.cost_tier`, `tool.connector_type`, `tool.idempotency_class`.

### 19.3 RFC-0004: Artifact Deletion Events

This RFC's Tool Runtime subscribes to `artifact.deleted` events to invalidate cached results referencing deleted Artifacts. This event dependency was also noted in RFC-0010. If RFC-0004 does not publish `artifact.deleted` events, both RFC-0010 and RFC-0012 have unresolved dangling reference risks. This strengthens the case for an RFC-0004 amendment to publish Artifact lifecycle events.

### 19.4 RFC-0006: Tool Event Namespace

This RFC introduces the `tool.*` event namespace. RFC-0006 should maintain a registry of namespaces. The `tool.*` namespace must be registered. Confirm no collision with existing event topics in RFC-0006.

### 19.5 RFC-0007: Invocation Cancellation Coordination

When the Scheduler cancels a Task (RFC-0007), it must also cancel in-flight tool invocations associated with that Task. The coordination mechanism is via RFC-0006: the Scheduler publishes `scheduler.task.cancelled`, which the Tool Runtime receives and uses to cancel associated invocations. The mapping from `task_id` to `invocation_id` is maintained in the Invocation Orchestrator's in-flight tracking table.

**Risk:** If the RFC-0007 `scheduler.task.cancelled` event does not include the `execution_id` and `task_id` in a structure the Tool Runtime can use to find associated invocations, the cancellation chain breaks. The event payload schema must be agreed upon between RFC-0007 and RFC-0012.

### 19.6 RFC-0010: Episodic Memory Entry Schema for Tool Invocations

This RFC writes Episodic Memory entries after each tool invocation. The schema of these entries must be compatible with what RFC-0011's Cost and Confidence Estimator expects to read. Specifically, the entry must include `tool_id`, `capability_name`, `outcome`, `total_duration_ms`, and `error_class` (if applicable). If RFC-0010 does not mandate a schema for Episodic Memory entries (it does not — entries are schema-free), this RFC must register a canonical schema for tool invocation records. That schema should be referenced in both RFC-0010 and RFC-0012 documentation.

### 19.7 RFC-0011: Tool Capability Cost Metadata for Planning

RFC-0011's Cost and Confidence Estimator uses tool capability metadata (latency profile, cost tier) to build estimates for plans that include tool-using skills. This metadata is now formally defined in `ToolCapabilityDeclaration.behavioral_metadata`. RFC-0011 should reference RFC-0012's `ToolCapabilityDeclaration` structure as the authoritative source for tool-level cost metadata.

## 20. Critical Self-Review

### 20.1 The Connector Interface Is Synchronous by Default

The Connector Interface defines `invoke()` as a synchronous operation: it dispatches and waits for a result. This is appropriate for most connectors, but it means that the Invocation Orchestrator's thread (or coroutine) is blocked for the duration of the connector call. At high concurrency (1,000 in-flight invocations), this requires 1,000 concurrent execution contexts.

**Honest assessment:** Most modern execution environments (async I/O runtimes, goroutines, fibers) handle this efficiently. But the RFC should explicitly state that connector implementations are expected to be non-blocking internally. A connector that blocks its execution context while waiting for a network response in a single-threaded environment would be catastrophic. This is an implementation guideline that must be enforced by the Connector Compliance Tests but is not currently stated explicitly in the Connector Interface definition. The definition should include: "Connectors must not block the calling execution context for longer than the declared `connection_timeout`. Long-running operations must use async I/O or equivalent non-blocking mechanisms."

### 20.2 Sandboxing Hooks Are Not Verified at Registration

When a tool is registered with a `sandbox_profile` referencing a named sandbox configuration, the Tool Runtime verifies that the named profile exists. It does not verify that the sandbox configuration correctly restricts the declared network destinations, filesystem paths, or resource limits. An operator could register a sandbox profile that declares tight restrictions but implements none of them (e.g., a null sandbox with a non-null name). The Tool Runtime would accept this without complaint.

**Honest assessment:** Sandbox configuration correctness cannot be verified by the kernel without executing the sandbox, which is circular. The correct solution is external attestation: sandbox implementations should provide a self-test that verifies their isolation properties, and the Tool Runtime should require passing this self-test at registration time. This RFC does not define such an attestation protocol. It is a gap that should be addressed in a security-focused amendment.

### 20.3 Contract Verification Is Shallow

The Contract Verification job uses synthetic test invocations to detect behavioral deviations. But contract verification using pre-defined test fixtures can only detect deviations that the test author anticipated. A tool that behaves correctly on test inputs but deviates on production inputs will pass contract verification and still cause runtime failures.

**Honest assessment:** This is an inherent limitation of blackbox contract testing. The correct long-term solution is continuous contract monitoring: sample a small percentage of production invocations, compare results against contract predictions, and flag deviations. This is significantly more complex than the synthetic testing approach defined here and belongs in a future RFC. The current contract verification mechanism is necessary but not sufficient.

### 20.4 The Capability Name Hierarchy Is Unenforceable by the Kernel

Capability names are defined as hierarchical dot-notation strings (e.g., `web.search`, `file.read`, `code.execute.python`). The hierarchy implies that policy governing `code.execute` should implicitly govern `code.execute.python`. The kernel does not enforce this implication. Policy must explicitly name each capability it governs. A policy that permits `code.execute` does not automatically permit `code.execute.python` unless the Policy Engine implements prefix matching.

**Honest assessment:** This is a significant usability gap. Without hierarchical policy matching, operators must enumerate every capability variant explicitly, which is error-prone at scale. RFC-0003 should be amended to support prefix-based policy matching for capability names. Until it does, the hierarchical naming convention is a documentation convention, not an enforced structure.

### 20.5 Idempotency Key Generation Uses SHA-256 of Input

The idempotency key generation algorithm hashes the canonical serialization of the input. This means that two invocations with semantically identical but syntactically different inputs (e.g., `{"query": "foo", "limit": 10}` vs. `{"limit": 10, "query": "foo"}`) will produce different idempotency keys if canonicalization does not normalize key ordering. The algorithm specifies "sort keys lexicographically" in the canonicalization step, which handles this case. But it does not handle semantic equivalence: `{"limit": 10}` and `{"limit": "10"}` (integer vs. string) may be semantically identical for a tool that accepts both, but will produce different idempotency keys.

**Honest assessment:** Perfect semantic idempotency key generation is not achievable without a tool-specific understanding of which input variations are semantically equivalent. The current algorithm is correct for syntactic equivalence. Semantic equivalence requires tool-specific normalization, which the Tool Runtime cannot provide generically. This is an accepted limitation that is documented in the InvocationRecord but not solvable at the kernel level.

### 20.6 No Circuit Breaker Pattern

The current failure handling retries up to `max_attempts` and then fails. There is no circuit breaker that detects a sustained pattern of failures for a specific tool and stops dispatching to it entirely for a cooldown period. Without a circuit breaker, a failing tool can absorb retry budget from all callers for its full retry count × max_attempts before the failure is surfaced. At high invocation volume, this translates to significant wasted latency and quota consumption.

**Honest assessment:** A circuit breaker pattern should be implemented in the Invocation Orchestrator. The circuit breaker state (CLOSED, OPEN, HALF_OPEN) per tool is managed based on recent failure rate. When the circuit is OPEN, invocations are immediately rejected with `CIRCUIT_OPEN` without attempting connector dispatch. This is a well-understood pattern that was not included in this RFC to avoid scope creep, but it is a production-critical feature that should be addressed in an amendment.

### 20.7 Credential Resolution Is Deferred to a Future RFC

This RFC references `CredentialReference` and `OpaqueCredential` as placeholders for a credential management system. Credentials are security-critical. The deferral to a future RFC means that the Tool Runtime cannot be fully implemented without a parallel Credential Store RFC. Implementations may use a temporary, simplified credential mechanism (e.g., environment variable lookup by credential type) but must be prepared to replace it when the Credential Store RFC is published.

## 21. Future RFC Dependencies

### RFC-0013 (Required): Credential Store

The Tool Runtime's `CredentialReference` mechanism requires a Credential Store that manages credential lifecycle, rotation, encryption, and access control. Without it, credentials must be embedded directly in `ConnectorBinding.endpoint.config`, which is a security anti-pattern. RFC-0013 should define: credential types, storage, rotation, access policy, and the resolution protocol used by the Tool Runtime.

### RFC-0014 (Suggested): Circuit Breaker and Reliability Patterns

As identified in the Critical Self-Review, the Tool Runtime needs circuit breaker implementation for production reliability. RFC-0014 should define: circuit breaker state machines, failure rate thresholds, cooldown periods, and integration with the Tool Runtime's Invocation Orchestrator and the Event Bus. This RFC may also cover bulkhead patterns for resource isolation between tool capability classes.

### RFC-0015 (Suggested): Tool Capability Marketplace

At organizational scale, teams will author and publish Tool Capability Declarations for shared use. RFC-0015 should define: a capability publishing protocol, capability discovery across organizational boundaries, capability versioning and deprecation workflows, and the trust model for externally-authored capabilities.

### RFC-0016 (Suggested): Connector SDK

This RFC defines the Connector Interface contract. RFC-0016 should define the Connector SDK: a set of libraries and scaffolding that makes it straightforward to implement a new connector correctly. The SDK would provide: the interface implementation skeleton, the Compliance Test Suite runner, sandbox hook integration utilities, result normalization utilities for common content types, and documentation generation from `ToolCapabilityDeclaration`.

### RFC-0017 (Suggested): Continuous Contract Monitoring

As identified in the Critical Self-Review, synthetic test-based contract verification is insufficient for production confidence. RFC-0017 should define continuous contract monitoring: production traffic sampling, result comparison against contract predictions, anomaly detection, and feedback into the Tool Registry's `verification_status`. This RFC would depend on RFC-0010 (Memory System, for storing monitoring observations) and RFC-0006 (Event Bus, for publishing violation events).

### RFC-0018 (Suggested): Tool Invocation Budget Management

Integration with RFC-0009 (Token Budgeting, assumed) for tool invocations that consume LLM tokens as part of their execution (e.g., a tool that internally calls an AI model). RFC-0018 should define how tool-side token consumption is tracked, budgeted, and reported back to the AGY kernel's token budget ledger.

### Dependency on RFC-0003 Amendment

RFC-0003 must be amended to:
1. Add the `tool.*` attribute namespace.
2. Add the `TOOL_INVOCATION` evaluation context.
3. Support prefix-based capability name matching.

This amendment should be coordinated with the RFC-0012 acceptance process.

### Dependency on RFC-0004 Amendment

RFC-0004 must be amended to publish `artifact.deleted` and `artifact.expired` lifecycle events to RFC-0006. This was also identified as a dependency in RFC-0010. The two RFCs should be cited jointly in the RFC-0004 amendment to ensure both consuming subsystems' requirements are addressed.
