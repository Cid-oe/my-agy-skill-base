# AGY RFC-0006: Event Bus

Status: Draft
Subsystem: Kernel / Event Bus
Depends on: Skill Resolver (RFC-0001, stable), Skill Registry & Loader (RFC-0002, stable), Policy Engine (RFC-0003, stable), Artifact System (RFC-0004, stable), RuntimeState (RFC-0005, stable)
Depended on by: Scheduler (RFC-0007), Execution Runtime/Executor (RFC-0008), Observation Engine (RFC-0009), Resource Manager (RFC-0010), Learning Engine (future)

---

## 0. Preface: Position in the Dependency Order

RFC-0005 §19 recommended Event Bus over Scheduler as the next subsystem, on the grounds that Scheduler's own responsibilities depend on reliably observing two things that already have defined *producer*-side vocabularies but no defined *delivery* mechanism: Artifact lifecycle events (RFC-0004 §10, which explicitly deferred delivery semantics to "the Event Bus RFC") and RuntimeState mutation events (RFC-0005 §7.4, §8, whose mutation model is described as "message-proposal-shaped" precisely because it anticipated event-driven consumption without specifying one). This RFC is that delivery mechanism.

This RFC treats RFC-0001 through RFC-0005 as accepted contracts and modifies none of them. Where this RFC's design surfaces an incompatibility with an existing RFC's assumption, it is documented as a finding (§14) rather than silently resolved by editing the earlier RFC.

## 1. Executive Overview

### 1.1 Purpose

Every subsystem specified so far is a *source of truth* for its own domain — RFC-0004 is authoritative for artifact lineage, RFC-0005 is authoritative for live execution status — but neither is responsible for telling anyone else, in a timely and reliable way, that something changed. RFC-0004 §10 defines what events exist (`ArtifactCreated`, `ArtifactSuperseded`, etc.) but not how a subscriber learns about them. RFC-0005's mutation surface (§12–13) is synchronous and request/response-shaped for the mutator, but nothing tells a non-mutating observer (Scheduler, Observation Engine) that a mutation happened, without that observer polling RuntimeState directly — which RFC-0005 §1.3 implicitly discourages by scoping RuntimeState as a data structure with a controlled mutation surface, not a pub/sub system.

Event Bus is AGY's answer to the same problem a hardware interrupt controller solves for a CPU, a Kubernetes Informer/Watch API solves for cluster state, and a message broker (Kafka, NATS) solves for microservices: a single, canonical channel through which "something changed" propagates from the component that knows it happened to every component that needs to react, without the producer needing to know who's listening and without listeners needing to poll.

### 1.2 Responsibilities

Event Bus owns:

- **Event ingestion**: accepting event publications from authorized producers (RFC-0004's Artifact System, RFC-0005's RuntimeState mutation surface, and — once specified — Scheduler, Executor, Policy Engine).
- **Delivery**: routing published events to subscribed consumers, with the ordering and durability guarantees defined in §4.
- **Topic/subject taxonomy** (§3): a structured namespace so subscribers can subscribe narrowly (e.g., "RuntimeState transitions for this one Execution Instance") rather than firehose-consuming everything.
- **Backpressure and flow control** (§7): preventing a slow consumer from either blocking producers or silently dropping events it couldn't keep up with.
- **Replay** (§9): allowing a consumer that was offline, crashed, or newly subscribed to catch up on events it missed, bounded by a defined retention window.

### 1.3 Non-Goals

- **Event Bus is not a source of truth.** It never originates a fact — every event it carries is a notification *about* a fact already recorded by its owning subsystem (an Artifact in RFC-0004's store, a RuntimeState mutation already committed per RFC-0005 §8.2's atomic-update guarantee). If an event and its source of truth ever disagree, the source of truth wins and the event is treated as a delivery bug, not a data conflict — this is what keeps Event Bus a strictly additive layer rather than a second, competing store of state.
- **Event Bus is not the Artifact Store or RuntimeState.** It carries references (`ArtifactID`, `runtimeId`+`revision`) exactly as RFC-0004 §3.5 and RFC-0005 §1.3 already establish as the transport principle one layer down — an event payload is small and pointer-shaped, never the artifact bytes or the full RuntimeState object.
- **Event Bus does not schedule, execute, or decide.** It has no opinion on what a subscriber does with an event. Scheduler (RFC-0007) deciding to dispatch a Node because a dependency's `ArtifactCreated` event arrived is Scheduler's decision, made using Event Bus as a transport, not Event Bus's decision.
- **Event Bus is not a general message queue for arbitrary application data.** It carries a closed, versioned set of event types (§3.2) tied to AGY's own subsystem lifecycles — it is not a place for a skill to pass ad hoc data between Nodes (that's `executionVariables`, RFC-0005 §6, or `currentArtifacts`, RFC-0005 §10).
- **Event Bus does not guarantee exactly-once delivery.** It guarantees at-least-once delivery with dedupable event IDs (§4.2) — exactly-once is explicitly rejected as a goal (§4.3) because achieving it across a distributed consumer set adds coordination cost this RFC's design constraints do not justify, and every consumer this RFC anticipates (Scheduler, Observation Engine) can be made idempotent to event ID far more cheaply than the bus can be made exactly-once.

### 1.4 Relationship to Previous RFCs

```

      |                            |
      | publishes                 | publishes
      | ArtifactCreated,          | StatusTransitioned,
      | ArtifactSuperseded,       | MutationApplied,
      | LineageRecorded           | CheckpointWritten
      |                            |
```

Event Bus does not change what RFC-0004 or RFC-0005 already record — it only adds a `publish()` call at the point each already commits a fact, and a subscription API for everyone downstream.

## 2. Event Model

### 2.1 Core Concepts

- **Event**: an immutable record that something happened. Once published, never mutated (mirrors RFC-0004 §2.1's immutability principle, applied to notifications instead of artifacts).
- **Topic**: a hierarchical string identifying an event's subject (§3.1) — the unit subscribers filter on.
- **Producer**: an authorized subsystem publishing events about facts it owns. Only RFC-0004 (Artifact System) and RFC-0005 (RuntimeState) are producers as of this RFC; Scheduler, Executor, Policy Engine become producers once their own RFCs define what they publish, using this RFC's API without needing to redesign it (§3.3 leaves room by namespace, not by mechanism).
- **Consumer / Subscriber**: any component that subscribes to one or more topics and receives events matching them.
- **Consumer Group**: a named set of subscriber instances that share delivery — each event is delivered to one member of the group, not all (used for horizontally-scaled consumers like a distributed Scheduler, RFC-0007 §14). A subscriber not in a named group receives every event on its subscribed topics independently (broadcast semantics), which is the default.
- **Offset / Cursor**: a per-subscription position marking how far a consumer has read, used for replay (§9) and at-least-once redelivery on reconnect.

### 2.2 Event Envelope

```typescript
interface Event {
  eventId: string;            // ULID, globally unique, generated at publish time
  topic: string;               // hierarchical topic string, §3.1
  eventType: EventType;        // closed enum, §3.2
  publishedAt: string;         // ISO-8601, set by Event Bus at ingestion, not by producer
                                 // (producer-supplied timestamps are untrusted for ordering, §4.1)
  producerId: string;          // which subsystem published this ("artifact-system", "runtime-state")
  sourceRevision?: number;     // for RuntimeState-sourced events: the revision (RFC-0005 §8.2)
                                 // this event corresponds to, enabling ordering validation
  correlationId: string;       // executionId (RFC-0005 §3.3) or equivalent — the thing this event
                                 // is "about," used for topic construction and replay scoping
  payload: EventPayload;       // closed, typed per eventType — pointer-shaped, never inline bytes
  schemaVersion: string;       // per RFC-0004 §3.1's precedent — events are versioned artifacts
                                 // of a kind, and consumers must tolerate unknown future versions
}
```

`publishedAt` being bus-assigned rather than producer-supplied is a deliberate correctness choice: it makes the bus's own delivery order the ordering authority for a topic, rather than trusting potentially-skewed producer clocks (§4.1).

### 2.2.1 [assumed] Payload shape

RFC-0004 and RFC-0005 do not currently define exact wire-format payloads for the events they're described as "publishing" in narrative form (RFC-0004 §10's event vocabulary is named but not schematized to field level; RFC-0005 does not schematize event payloads at all, since RFC-0005 predates this RFC). This RFC therefore treats every payload schema below (§3.2) as **[assumed: minimal pointer-shaped payload sufficient for a subscriber to look up the full fact via RFC-0004/0005's own APIs — if wrong: RFC-0004/0005 should be amended with a formal payload schema, and this RFC's §3.2 adjusted to match]**. This is the single largest unverified surface in this RFC and is restated in §14.1.

### 2.3 Ordering Guarantee

Events are strictly ordered **within a single topic**, using publish-time sequencing at the bus (not producer clock). Ordering is **not** guaranteed across different topics, even for causally related events (e.g., a `RuntimeState.StatusTransitioned` event and a same-instant `Artifact.ArtifactCreated` event for the Node that just completed are not guaranteed relative order unless a consumer subscribes to a topic granularity that puts them in the same stream — see §3.1's per-execution-instance topic, which is the recommended subscription for consumers that need this).

## 3. Topic Taxonomy and Event Types

### 3.1 Topic Structure

Hierarchical, dot-delimited, most-general-to-most-specific, mirroring RFC-0004 §4's namespacing precedent:

```
<domain>.<subject-type>.<event-verb>[.<correlationId>]

Examples:
  artifact.plan.created
  artifact.result.superseded
  runtimestate.status.transitioned.{executionId}
  runtimestate.mutation.applied.{executionId}
  runtimestate.checkpoint.written.{executionId}
```

Subscribers may subscribe at any prefix (`runtimestate.status.*` for all status transitions across every execution, or `runtimestate.status.transitioned.{executionId}` for exactly one execution's transitions) — prefix-based subscription is the mechanism that lets a Scheduler instance narrowly watch only the Execution Instances it currently owns, rather than every execution in the system, which matters directly for §7's backpressure design (a narrowly-scoped subscriber has a naturally bounded event rate).

### 3.2 Closed Event Type Enum

| `eventType` | Producer | Fired when | Payload fields |
|---|---|---|---|
| `ArtifactCreated` | Artifact System | A new artifact is committed (RFC-0004 §3) | `artifactId`, `artifactType`, `producedByExecutionId` [assumed shape, §2.2.1] |
| `ArtifactSuperseded` | Artifact System | `supersede()` called (RFC-0004 §9.3) | `oldArtifactId`, `newArtifactId` [assumed] |
| `LineageRecorded` | Artifact System | A lineage edge is added (RFC-0004's lineage graph) | `artifactId`, `parentArtifactIds[]` [assumed] |
| `StatusTransitioned` | RuntimeState | `currentStatus` changes (RFC-0005 §4) | `executionId`, `fromStatus`, `toStatus`, `revision` |
| `MutationApplied` | RuntimeState | Any mutation succeeds (RFC-0005 §5.2, §8.2) — fired in addition to, not instead of, the more specific `StatusTransitioned` when a mutation also crosses a status boundary | `executionId`, `revision`, `mutatedFields[]` |
| `CheckpointWritten` | RuntimeState | A checkpoint (RFC-0005 §9) is durably captured | `executionId`, `checkpointArtifactId`, `revision` |
| `NodeBlocked` | RuntimeState | `currentStatus` → `Blocked` specifically, split out from the generic `StatusTransitioned` because Scheduler (§7.4 of RFC-0007's brief) needs to react to this specific case with distinct, higher-priority logic | `executionId`, `blockedNodes[]`, `reason` |
| `EscalationTimedOut` | [reserved, unowned] | Would fire when `timeoutState` (RFC-0005 §3.7) expires — **not producible by any component today**, since RFC-0005 §18.2 and §18.7 leave escalation-timeout ownership unassigned. Listed here as a reserved event type so a future RFC can claim it without a topic-taxonomy redesign, per this finding restated in §14.2 | n/a — undefined until an owner exists |

This table is deliberately closed (RFC-0004 §3.1-style minimality applied to event types): a producer publishing an event type not in this table is a schema violation, rejected at ingestion (§5.1), not silently accepted. New event types require an RFC amendment, exactly as RFC-0004 treats new artifact types.

### 3.3 Namespace Reserved for Future Producers

Per §1.3's non-goal note, this RFC reserves `scheduler.*`, `executor.*`, and `policy.*` topic prefixes for RFC-0007, RFC-0008, and a future Policy Engine event-emission amendment respectively, without defining their event types here — this is the "leaves room by namespace, not by mechanism" property that lets those RFCs add producers without renegotiating Event Bus's core design.

## 4. Delivery Semantics

### 4.1 Ordering

As stated in §2.3: total order per-topic, at the bus, using arrival sequence. For RuntimeState-sourced topics specifically, `sourceRevision` (§2.2) lets a consumer detect a gap (received revision 5 after revision 3, meaning revision 4's event was lost or reordered) even under the at-least-once model's redelivery — this is the mechanism that makes "detect a missed event without waiting for replay" possible without full exactly-once guarantees.

### 4.2 At-Least-Once Delivery

Every event is delivered at least once to every subscriber of a matching topic. Redelivery happens on: consumer acknowledgment timeout, consumer reconnect after disconnect, or explicit replay request (§9). Consumers **must** be idempotent with respect to `eventId` — the bus provides `eventId` specifically so a consumer can maintain a dedup window and discard a redelivered event it already processed, rather than the bus attempting to guarantee it never redelivers (which §4.3 explains is out of scope).

### 4.3 Why Not Exactly-Once

Exactly-once delivery in a distributed system requires either a distributed transaction spanning producer-commit and bus-publish (adding write latency and a new failure mode to every producer, including the already-accepted RFC-0004 and RFC-0005 commit paths, which this RFC is not permitted to modify), or idempotent consumer-side processing (which is required anyway, for at-least-once, at much lower cost). Given that every named consumer in this RFC's dependency chain (Scheduler, Observation Engine, Resource Manager) can be made idempotent to `eventId` cheaply, at-least-once plus consumer idempotency dominates exactly-once on cost with no correctness loss — **[assumed: no future consumer will have a legitimate need for exactly-once side effects that can't be made idempotent — if wrong: a specific consumer would need its own outbox/dedup-transaction pattern layered on top, not a redesign of this RFC]**.

### 4.4 Delivery Timing

Best-effort low-latency (push-based delivery to connected subscribers), not a batch/polling design — this follows directly from Scheduler's stated need (RFC-0005 §19, restated in RFC-0007's brief §3 "Dispatcher") to react to dependency-satisfying events promptly. No specific latency SLA is set in this RFC; it is deferred to implementation and measured via Observation Engine (RFC-0009) once built, consistent with this RFC's general posture of specifying mechanism and contract, not implementation-specific performance numbers not yet measured.

## 5. Ingestion and Validation

### 5.1 Producer Authorization

Only components named as producers (§2.1) may publish. Authorization is enforced at ingestion: an unrecognized `producerId`, or a `producerId` publishing an `eventType` not in its allowed set (§3.2's table's Producer column), is rejected — this mirrors RFC-0004 §7's provenance/trust model applied to event publication rather than artifact creation, keeping the two subsystems' trust postures consistent rather than inventing a separate one.

### 5.2 Schema Validation

Every event is validated against its `eventType`'s closed payload schema (§3.2) before acceptance. A malformed event is rejected at the producer boundary with an error returned synchronously to the publish call — never silently dropped, and never allowed onto the bus in a form a subscriber could fail to parse. This is the event-bus-level restatement of RFC-0004 §7.2's validation-before-acceptance principle.

### 5.3 Idempotent Publication

Producers may retry a publish call safely: `eventId` is producer-generated (not bus-generated) specifically so that a producer's retry of a failed publish attempt reuses the same `eventId`, and the bus deduplicates on ingestion by `eventId` — this closes the producer-side half of the at-least-once story (§4.2 covers the consumer-side half), ensuring a producer's network retry never results in two logically-identical events with different IDs reaching consumers.

## 6. Subscription Model

### 6.1 Subscription Types

- **Broadcast subscription**: every matching event delivered to every subscribed instance independently. Default mode; used by Observation Engine (RFC-0009), which needs to see everything for its own purposes regardless of what any other consumer does with it.
- **Consumer-group subscription**: matching events are load-balanced across group members, each event delivered to exactly one member (at-least-once still applies per-group, not per-member). Used where a subsystem is horizontally scaled (a distributed Scheduler, RFC-0007 §14) and must not have two instances both react to the same event as if it were their own responsibility.

### 6.2 Subscription API (sketch)

```typescript
interface EventBusClient {
  subscribe(topicPattern: string, options?: {
    group?: string;                 // consumer-group name, omit for broadcast
    startFrom?: "now" | "earliest" | { offset: string };  // §9
  }): Subscription;

  publish(event: Omit<Event, "publishedAt">): Promise<PublishResult>;  // §5.3's eventId reuse on retry
}

interface Subscription {
  onEvent(handler: (event: Event) => Promise<AckResult>): void;
  // handler must ack or nack; unacked events are redelivered per §4.2's timeout
  close(): void;
}
```

### 6.3 Acknowledgment

A subscriber acknowledges an event only after it has durably recorded (in its own domain, per its own RFC's persistence model — e.g., Scheduler's queue state, RFC-0007) that it has processed the event, not merely received it. Failure to ack within a bounded window triggers redelivery (§4.2). This is deliberately the same "durable-before-acknowledged" discipline RFC-0005 §5.2 applies to its own mutations, kept consistent across the two RFCs.

## 7. Backpressure and Flow Control

### 7.1 The Problem

A producer (RuntimeState, under heavy concurrent Node execution) can generate events faster than a slow consumer (a struggling Scheduler instance, or Observation Engine under its own load) can process them. Two bad outcomes must both be avoided: blocking the producer's own commit path on a slow consumer (which would make Event Bus a correctness-critical bottleneck for RFC-0004/0005's already-accepted commit semantics — unacceptable, since this RFC may not add latency risk to those), and silently dropping events past a slow consumer (which breaks at-least-once, §4.2).

### 7.2 Design: Bounded Buffer Per Subscription, Never Per Producer

Each subscription has its own bounded, durable buffer (backed by the same retention store as §9's replay window — no separate mechanism). A producer's `publish()` call returns as soon as the event is durably ingested into the topic's shared log (§5), **never** waiting on any individual subscriber's buffer state — this decouples producer latency from consumer speed entirely, satisfying the first half of §7.1.

For the second half: a subscriber whose buffer fills (falls too far behind, exceeding a configured lag threshold) does not have events dropped from the shared log — the shared log is retained per §9's window regardless of consumer state. Instead, the *subscriber* is marked lagging and its `onEvent` delivery rate is unaffected (delivery continues from the durable log at whatever pace the consumer can sustain) — what changes is that a lagging subscriber crossing the full retention window without catching up transitions to a **gap state**, surfaced to it explicitly on next successful connection ("you have missed events older than X; replay is only available from X forward"), rather than being silently caught up on a truncated, incomplete history. This makes data loss for a badly-lagging consumer visible and explicit, never silent.

### 7.3 Producer-Side Rate Limiting

Not implemented at the Event Bus layer. If a producer (e.g., RuntimeState under a retry storm, RFC-0007 §13's concern) generates an unsustainable event rate, that is a producer-side or Resource-Manager-side (RFC-0010) concern to throttle at the source — Event Bus's job per §1.3 is transport, not admission control on its producers' own domains.

## 8. Failure Handling

| Failure | Detection | Recovery |
|---|---|---|
| **Bus process/node failure** | Producer publish call fails or times out | Producer retries per §5.3's idempotent-publish design; no event is lost if the durable log write hadn't been acknowledged, since an unacknowledged publish is defined as not-yet-committed |
| **Consumer crash mid-processing** | Ack timeout (§6.3) | Event redelivered per §4.2; consumer's own idempotency (keyed on `eventId`) handles the case where the crash happened after real side-effects but before ack |
| **Consumer permanently lost / decommissioned** | No ack activity past a long-idle threshold | Subscription marked stale and eventually reaped (mirrors RFC-0004 §3.8/RFC-0005 §5.9's bounded, audited deletion pattern — reused here for subscription cleanup, not reinvented) |
| **Malformed event from a producer bug** | Schema validation (§5.2) | Rejected at ingestion; never enters the durable log; producer receives a synchronous error, consistent with RFC-0004 §7.2 |
| **Topic-level log corruption** | Checksum mismatch on read (mirrors RFC-0004 §7.1's provenance/checksum precedent) | Log segment isolated and flagged; consumers of that segment fall into the gap-state path (§7.2) for the corrupted range; underlying storage-layer recovery is out of this RFC's scope (delegated to whatever durable store backs the log, same posture RFC-0005 §18.5's storage-backend delegation takes) |

## 9. Replay and Retention

### 9.1 Retention Window

Each topic's durable log is retained for a bounded window — **[assumed: default retention of 7 days or until the correlated Execution Instance reaches `Archived` (RFC-0005 §5.8) plus a fixed grace period, whichever is longer — if wrong: retention should be a configured value per topic prefix, following RFC-0003 §17's layered configuration precedent rather than a single global constant]**. This bound is what makes §2.1's "Offset/Cursor" meaningful and keeps the durable log's storage footprint bounded, mirroring RFC-0005 §14.1's hard sizing constraint applied to a log instead of a live object.

### 9.2 Replay API

```typescript
subscribe(topicPattern, { startFrom: "earliest" })       // full available history within retention
subscribe(topicPattern, { startFrom: { offset: cursor } }) // resume from a specific prior position
subscribe(topicPattern, { startFrom: "now" })              // default; only new events
```

A newly-registered consumer (e.g., a freshly-deployed Observation Engine instance) uses `"earliest"` to backfill its own state from the retained window before switching to live delivery — the mechanism that lets a consumer be stateless-on-deploy and rebuild its view entirely from Event Bus plus RFC-0004/0005's own APIs, rather than requiring a separate bootstrap data path.

---

## 10. Ordering Guarantees Under Consumer Groups

Within a consumer group (§6.1), per-topic total order is preserved **only within a single partition** of that topic — **[assumed: topics are partitioned by `correlationId` (executionId), so all events for one Execution Instance are strictly ordered and delivered to one consumer-group member, while different Execution Instances may be processed by different members in parallel — if wrong: a non-partitioned design would force single-consumer processing per topic prefix, defeating RFC-0007's horizontal-scaling requirement]**. This is the design that makes a distributed Scheduler (RFC-0007 §14) able to scale horizontally while still seeing a fully-ordered event stream for any single execution it's responsible for.

---

## 11. Security and Isolation

Event payloads carry references (`ArtifactID`, `executionId`), never inline sensitive data, consistent with RFC-0004's own posture that payload bytes live in the Artifact Store where RFC-0004's access-control model already applies (not duplicated here). Subscription-level authorization (which components may subscribe to which topic prefixes) is delegated to the Policy Engine (RFC-0003) exactly as RFC-0005 §3.8's `PermissionContext` model delegates permission evaluation rather than reimplementing it — Event Bus enforces the resulting ALLOW/DENY at the subscribe() call boundary but does not itself define the policy.

---

## 12. Performance Characteristics

- **Publish latency**: O(1) amortized per event — append to a per-topic-partition durable log, no cross-topic coordination.
- **Delivery latency**: bounded by consumer processing rate plus network; decoupled from publish latency per §7.2's design.
- **Storage**: O(retained events per topic-partition), bounded by §9.1's retention window — does not grow unboundedly with system uptime, mirroring RFC-0005 §14.1's boundedness discipline.
- **Subscription scaling**: O(number of active subscriptions) for fan-out delivery; a hot topic (e.g., `runtimestate.status.*` unscoped) with many broadcast subscribers is the worst case, mitigated by encouraging narrow topic subscription (§3.1) as the default usage pattern rather than a firehose default.

---

## 13. Alternatives Considered

- **Direct polling of RFC-0004/0005 APIs instead of an event bus**: rejected — this is exactly the status quo RFC-0005 §19 identified as forcing every consumer to invent its own polling cadence and miss the "reactive, low-latency" property Scheduler needs; it also doesn't solve the fan-out problem (multiple consumers each polling independently multiplies load on RFC-0004/0005's own APIs, which were not designed as high-QPS read paths).
- **Synchronous callback/webhook model** (producer directly invokes each subscriber): rejected — couples producer commit latency to the slowest subscriber, exactly the failure mode §7.1 rules out, and requires the producer to know its subscriber set, violating the decoupling this RFC exists to provide.
- **Exactly-once delivery via distributed transactions**: rejected per §4.3's cost/benefit analysis.
- **Unbounded retention** (never expire events): rejected — directly conflicts with RFC-0005 §14.1's precedent that live/near-live state must have a hard sizing discipline; unbounded retention here would just relocate the unbounded-growth problem RFC-0005 avoided for itself into this RFC instead.

## 14. Findings and Open Items

### 14.1 RFC-0004/0005 Do Not Yet Define Formal Event Payload Schemas

Restated from §2.2.1: this RFC's §3.2 payload column is this RFC's own [assumed] construction, not a ratified schema from RFC-0004 or RFC-0005. **Recommend a follow-up amendment to RFC-0004 §10 and a new subsection in RFC-0005 formally adopting this RFC's §3.2 payload shapes**, the same pattern RFC-0005 §18.6 used to formally close RFC-0004 §5.11's placeholder typing.

### 14.2 `EscalationTimedOut` Has No Producer

Restated from §3.2's table: this event type is reserved but unimplementable until RFC-0005 §18.2/§18.7's escalation-resolution-ownership gap is closed by some future RFC. Flagged here as confirmation that this RFC does not itself close that gap, consistent with the instruction to document rather than silently resolve cross-RFC issues.

### 14.3 Retention Window Value Is a Placeholder

Restated from §9.1: the specific default (7 days / archive-plus-grace) is asserted, not derived from any load or cost analysis, since no production data exists yet. Should be revisited once Observation Engine (RFC-0009) can supply real event-volume metrics to inform a cost-based retention policy.

## 15. Recommendation: Next Subsystem

Per this RFC's own dependency closure: Scheduler (RFC-0007) can now be fully specified, since it has both a defined RuntimeState to read/mutate (RFC-0005) and a defined, reliable channel to observe transitions and artifact events without inventing its own delivery mechanism (this RFC). **Recommended: RFC-0007, Scheduler**, exactly as RFC-0005 §19 anticipated.
