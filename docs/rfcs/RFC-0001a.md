# RFC-0001a: Version Conflict Resolution Policy

**Status:** Accepted (Amendment to RFC-0001)  
**Subsystem:** Skill Resolver  
**Author:** Lead Systems Engineer  

---

## 1. Problem Statement
RFC-0001 specifies that the Skill Resolver matches skills against version constraints (`requiresSkillVersion`). However, when two skills in the same execution plan transitively require conflicting versions of a third dependency skill (the "diamond dependency problem"), RFC-0001 did not specify the exact conflict resolution policy.

## 2. Policy Specification

1. **Resolution Semantics (Deterministic Highest Compatible):**
   - For any shared dependency `D` requested with constraints `C1, C2, ... Cn`, the Resolver attempts to find the highest installed semver version `V` such that `V satisfies C1 AND V satisfies C2 ... AND V satisfies Cn`.
   - If a compatible version exists, `D@V` is selected as a single shared singleton node in the DAG.

2. **Multi-Version Coexistence vs Conflict:**
   - If no single version satisfies all constraints:
     - If the dependency is **pure/stateless** (produces immutable artifacts only and does not hold kernel leases or runtime state), side-by-side versions (`D@1.0.0` and `D@2.0.0`) are permitted as distinct nodes in the DAG.
     - If the dependency is **stateful** (manages leases, writes to single-writer runtime state, or interfaces with external side effects), multi-version coexistence is rejected with a typed `ResolutionError("CONFLICTING_VERSION_CONSTRAINTS", { dependency, constraints })`.

3. **Invariants:**
   - Version resolution is 100% deterministic and pure given the same `(Goal, SkillRegistry, RuntimeState)`.
