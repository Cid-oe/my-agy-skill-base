# RFC-0001: Skill Resolver

Status: Draft
Subsystem: Kernel / Skill Resolver
Depends on: Skill Registry (skill manifests, v2 schema), Repository Map, Context Manager (read-only)
Blocks: Scheduler, Execution Graph (DAG) construction, Executor

---

## 0. Why This Subsystem, Why Now

AGY currently has a Kernel component list but no completed subsystem design.
Before picking one, it's worth ruling out the obvious alternatives, because
"start with the Scheduler" or "start with the Policy Engine" are both
plausible-sounding wrong answers.

**Rejected: Scheduler first.** A scheduler orders and time-slices work that
already exists as discrete, dependency-annotated units. AGY has no such
units yet — it has a flat skill catalog. Building a scheduler before the
resolver means scheduling nothing in particular.

**Rejected: Policy Engine first.** Policy is an enforcement layer that gates
*decisions* (which skill runs, with what budget, under what constraints).
Without a decision-making component, the Policy Engine has nothing to gate
and its interface would be speculative.

**Rejected: Execution Graph (DAG) first.** The DAG is a data structure, not
a subsystem with independent behavior. It's the *output* of resolution. It
belongs inside this subsystem's data model, not ahead of it.

**Chosen: Skill Resolver.** It is the first point where AGY makes an actual
decision — "given this goal, this set of skill manifests, and this runtime
state, which skills run, in what order, with what fallback." Every other
Kernel component (Scheduler, Executor, Policy Engine, Reflection Engine)
consumes its output or wraps around it. It is also the subsystem the
existing skill pack was explicitly built to feed: every SKILL.md already
carries `requires`, `optional`, `consumes`, `produces`, `triggerPredicates`,
`exclusiveWith`, `priority`, `estimatedCost`, and `confidenceThreshold` in
its frontmatter, and `manifest.json` exists as a flat index of exactly this
data. Nothing currently reads it. That's the gap this RFC closes.

---

## 1. Purpose

Given:
- a **goal** (a decomposed subtask, or a raw request if `task-decomposer`
  hasn't run yet),
- a **skill registry** (parsed manifests for all installed skills), and
- **runtime state** (conversation length, files touched, risk flags,
  previously-produced artifacts, prior resolution failures),

produce an **execution plan**: an ordered, dependency-correct, mutually-
non-conflicting subgraph of skills to invoke, each annotated with why it was
selected and what happens if it fails.

The resolver does **not** execute skills. It does not manage context
windows. It does not enforce policy (it may be *vetoed* by the Policy
Engine, but it does not implement the veto logic itself). Its only job is
selection and ordering.

### Non-goals
- Retrying failed skills (Executor's job).
- Deciding *how much* budget a skill gets (Resource Manager's job).
- Persisting run history (Execution Ledger's job).
- Learning better weights over time (Adaptive Learning's job, though it is
  this subsystem's primary consumer of feedback — see §14).

## 2. Architecture

```
                         +---------------------+
                         |   Skill Registry     |
                         |  (parsed manifests)   |
                         +----------+-----------+
                                    |
                                    v
 Goal --------------------> +-------------+     candidate pool     +-------------+
 (Subtask or                |  Matcher    | ----------------------> |   Ranker    |
  RawRequest)                +-------------+                        +------+------+
                                    ^                                       |
                                    | runtime state                        v
                             +------+------+                        +-------------+
                             | State Probe |                        | Constraint  |
                             +-------------+                        |   Solver    |
                                                                     +------+------+
                                                                            |
                                                                            v
                                                                     +-------------+
                                                                     |  Plan       |
                                                                     |  Builder    |
                                                                     +------+------+
                                                                            |
                                                                            v
                                                                   ExecutionPlan (DAG)
                                                                            |
                                                                            v
                                                                +----------------------+
                                                                | Policy Engine (veto)  |
                                                                +----------------------+
```

**Matcher** — evaluates every skill's `triggerPredicates` against current
runtime state and produces a *candidate pool*: skills that are plausibly
relevant, with no ordering or filtering yet.

**Ranker** — scores each candidate using `priority`, `estimatedCost`,
`estimatedLatency`, `confidenceThreshold`, and (if Adaptive Learning is
present) a historical success-rate prior. Produces a ranked list per
"resolution slot" (see §5).

**Constraint Solver** — applies `requires`, `optional`, `consumes`/
`produces` matching, and `exclusiveWith` to prune the ranked list down to a
*feasible* selection. This is the only component in the resolver with
combinatorial complexity; see §8 for the algorithm.

**Plan Builder** — assembles the feasible selection into a DAG: nodes are
skill invocations, edges are `produces → consumes` data dependencies, plus
ordering edges implied by `requires`.

**State Probe** — a narrow, read-only interface into Context Manager,
Repository Map, and Execution Ledger, used only to evaluate
`triggerPredicates`. The resolver never mutates state; it only reads it.

The resolver hands the finished `ExecutionPlan` to the Policy Engine, which
may veto individual nodes (not in this RFC's scope) before the Scheduler
takes it.

## 3. Public API

```
resolve(goal: Goal, registry: SkillRegistry, state: RuntimeState) -> ResolutionResult

interface Goal:
    id: string
    kind: "raw_request" | "subtask"
    description: string
    requiredArtifacts: ArtifactType[]      # what this goal needs produced
    riskHint: "low" | "high" | "unknown"   # optional caller-supplied hint

interface RuntimeState:
    conversationTokens: int
    filesTouched: int
    changedFiles: int
    availableArtifacts: Map<ArtifactType, ArtifactRef[]>   # already-produced
    priorFailures: ResolutionFailure[]     # this session, for backoff
    costSensitivity: "low" | "medium" | "high"

interface ResolutionResult:
    status: "resolved" | "partial" | "unresolvable"
    plan: ExecutionPlan | null
    unresolvedSlots: Slot[]                # what couldn't be satisfied
    diagnostics: Diagnostic[]              # human-readable trace of decisions

interface ExecutionPlan:
    nodes: PlanNode[]
    edges: PlanEdge[]                      # dependency + data-flow edges

interface PlanNode:
    skillName: string
    skillVersion: string
    selectionReason: string                # which predicate/priority won
    confidenceThreshold: float
    escalateTo: string | null
    fallbackChain: string[]                # ranked alternates, precomputed

interface PlanEdge:
    from: PlanNode
    to: PlanNode
    kind: "data" | "ordering" | "exclusion"
```

`resolve()` is synchronous from the caller's perspective and pure with
respect to the registry and state snapshots it's given — same inputs,
same plan. Non-determinism (e.g. model calls) lives downstream in the
Executor, not here. This determinism is deliberate: Design Principle #4.

### Secondary API

```
explainPlan(plan: ExecutionPlan) -> string          # human-readable rationale
reresolve(plan: ExecutionPlan, failedNode: PlanNode, state: RuntimeState) -> ResolutionResult
```

`reresolve` is how the Executor asks for a fallback after a node fails or
drops below its `confidenceThreshold` — it re-enters the resolver at the
failed node using its precomputed `fallbackChain`, without re-resolving the
whole plan.

## 4. Internal Components

| Component | Responsibility | State held |
|---|---|---|
| Matcher | Predicate evaluation | none (stateless function of registry + state) |
| Ranker | Scoring | Adaptive Learning prior cache (read-only, refreshed per session) |
| Constraint Solver | Feasibility pruning | none |
| Plan Builder | DAG assembly | none |
| State Probe | Bounded read access | none — proxies to other subsystems |

The resolver is intentionally stateless across calls. All state it needs is
passed in as `RuntimeState` or fetched live via State Probe. This makes it
trivially restartable and testable (§12), and keeps Checkpoint Manager out
of its critical path — a resolution can always be recomputed from scratch
if a checkpoint is stale, at the cost of a synchronous recompute, never at
the cost of correctness.

---

## 5. Resolution Slots

A **slot** is a single unit of resolution work: either the whole goal (if
it maps to one skill) or one node the Plan Builder needs filled. Slots
exist because a goal like "review this change" doesn't name a skill — it
names an *artifact need* (`ReviewVerdict`), and multiple skills can produce
that artifact (`caveman-review`, `ponytail-review`).

```
Slot:
    requestedArtifact: ArtifactType   # e.g. "ReviewVerdict"
    candidates: PlanNode[]            # ranked, post-constraint-solve
    filled: bool
```

Slots are how the resolver stays declarative: it never hardcodes "if risk
is low use caveman-review else ponytail-review." It asks "who produces
ReviewVerdict and satisfies my predicates," and the exclusivity constraint
(`caveman-review exclusiveWith ponytail-review`) does the rest.

---

## 6. State Machine

Per-slot resolution state:

```
        +-----------+  predicates match >=1 skill   +-----------+
 START ->|  MATCHING | -----------------------------> |  RANKED   |
        +-----------+                                +-----+-----+
              |  no predicates match                        |
              v                                              | constraint solve
        +-----------+                                        v
        | UNRESOLVED| <----------- all candidates ----+-----------+
        +-----------+              pruned by          |CONSTRAINED|
                                    exclusiveWith/       +-----+-----+
                                    unmet requires              |
                                                                 v
                                                          +-----------+
                                                          |  FILLED   |
                                                          +-----------+
```

Plan-level state (aggregate over all slots):

```
PLANNING -> [all slots FILLED] -> RESOLVED
PLANNING -> [some slots UNRESOLVED, goal still partially satisfiable] -> PARTIAL
PLANNING -> [a required slot UNRESOLVED] -> UNRESOLVABLE
```

`PARTIAL` is a legitimate terminal state, not an error — e.g. resolving
`self-review` while `documentation-sync`'s predicate
(`api_surface_changed == true`) doesn't fire yet is expected, not a
failure.

## 7. Data Structures

```
SkillManifest:                      # parsed from SKILL.md frontmatter
    name: string
    version: string
    priority: enum
    estimatedCost/Latency/Context: enum
    confidenceThreshold: float
    escalateTo: string | null
    consumes: ArtifactType[]
    produces: ArtifactType[]
    requires: string[]              # hard skill deps
    optional: string[]              # soft skill deps
    triggerPredicates: Predicate[]
    exclusiveWith: string[]
    requiresSkillVersion: SemverRange

Predicate:                          # e.g. "conversation_tokens > 80000"
    variable: string
    operator: "> < >= <= == !="
    value: string | number | bool

SkillRegistry:
    byName: Map<string, SkillManifest>
    byProduces: Map<ArtifactType, string[]>   # inverted index, built once
    byPredicateVariable: Map<string, string[]> # inverted index for eval speed
```

The two inverted indices (`byProduces`, `byPredicateVariable`) are what
keep matching sub-linear: the Matcher never iterates all skills for a
single artifact need, and predicate evaluation only touches skills whose
predicates reference a variable that's actually present in `RuntimeState`.

## 8. Algorithms

### 8.1 Matching

```
function match(goal, registry, state) -> Candidate[]:
    neededArtifacts = goal.requiredArtifacts
    pool = []
    for artifact in neededArtifacts:
        producers = registry.byProduces[artifact]
        for skillName in producers:
            skill = registry.byName[skillName]
            if evalPredicates(skill.triggerPredicates, state):
                pool.append(Candidate(skill, artifact))
    return pool
```

`evalPredicates` is a short-circuiting AND over the skill's predicate list
— a skill with zero predicates always matches when reached by artifact need
(it's opting in to "always relevant if requested," e.g. `bluf`,
`self-review`).

### 8.2 Ranking

```
function rank(candidates, state) -> Candidate[]:
    for c in candidates:
        c.score = weight(priority=c.skill.priority)
                 - costPenalty(c.skill.estimatedCost, state.costSensitivity)
                 - latencyPenalty(c.skill.estimatedLatency)
                 + historicalSuccessBonus(c.skill.name)   # 0 if no history
    return sortDescending(candidates, by=score)
```

Weights are configuration, not hardcoded constants — see §13 (Tradeoffs)
for why this matters.

### 8.3 Constraint Solving (feasibility pruning)

This is a constraint satisfaction problem over a small domain (candidates
per slot rarely exceed single digits), so exhaustive backtracking is
acceptable and preferable to an approximate solver — Design Principle #4,
determinism, rules out heuristic SAT solvers here.

```
function solve(slots) -> Assignment | UNRESOLVABLE:
    return backtrack(slots, assignment={})

function backtrack(slots, assignment):
    if all slots assigned: return assignment
    slot = nextUnassignedSlot(slots)          # most-constrained-first
    for candidate in slot.candidates:          # already rank-sorted
        if satisfiesRequires(candidate, assignment)
           and satisfiesExclusion(candidate, assignment)
           and satisfiesVersion(candidate):
            assignment[slot] = candidate
            result = backtrack(remainingSlots, assignment)
            if result != UNRESOLVABLE: return result
            unassign(assignment, slot)
    return UNRESOLVABLE
```

`satisfiesExclusion` checks the candidate's `exclusiveWith` list against
every skill already committed in `assignment` — this is where
`caveman`/`ponytail` mutual exclusion is enforced. `satisfiesRequires`
checks that every name in `requires` is either already assigned or
resolvable as its own slot (recursively triggering §8.1–8.3 for the
dependency — this is why `task-decomposer` gets pulled in automatically
when `cavecrew.requires = [task-decomposer]` and no `SubtaskList` exists
yet in `availableArtifacts`).

**Complexity:** worst case exponential in slot count, but bounded in
practice — most-constrained-first ordering plus the small per-slot
candidate count (rarely > 5, since `exclusiveWith` pairs are typically
2-wide) keeps real plans resolving in low-single-digit backtracks. If a
future skill catalog grows large enough to change this, §14 covers the
escape hatch (constraint propagation / arc consistency pre-pass) without
requiring a rewrite of this algorithm's contract.

### 8.4 Plan Building

```
function buildPlan(assignment) -> ExecutionPlan:
    nodes = [toPlanNode(c) for c in assignment.values()]
    edges = []
    for node in nodes:
        for dep in node.skill.requires:
            edges.append(PlanEdge(from=nodeFor(dep), to=node, kind="ordering"))
        for artifact in node.skill.consumes:
            producer = findProducerInPlan(artifact, nodes)
            if producer: edges.append(PlanEdge(from=producer, to=node, kind="data"))
    topologicalSortCheck(nodes, edges)   # must be a DAG — cycle is a build-time error
    return ExecutionPlan(nodes, edges)
```

A cycle here (e.g. two skills each requiring the other) is a **registry
validation error**, not a resolver runtime error — see §9.

## 9. Failure Cases

| Failure | Detected by | Behavior |
|---|---|---|
| No skill produces a required artifact | Matcher (empty candidate pool) | Slot → `UNRESOLVED`; plan → `PARTIAL` or `UNRESOLVABLE` depending on whether the artifact was itself required or optional |
| All candidates pruned by exclusion/requires | Constraint Solver | Backtrack; if backtracking exhausts all slots, `UNRESOLVABLE` with a diagnostic naming the conflicting skills |
| Two installed skills declare a cyclic `requires` | Plan Builder (topological sort) | Reject at **registry load time**, not resolution time — a cyclic manifest pair should never make it into `byName` in the first place; this is enforced by a load-time validator, with the DAG check in Plan Builder as defense in depth |
| `requiresSkillVersion` unsatisfied by an installed skill's actual version | Constraint Solver (`satisfiesVersion`) | Candidate excluded from that slot, same as any other unmet constraint — surfaced in diagnostics, not silently dropped |
| Predicate references a `RuntimeState` variable that doesn't exist | Matcher | Predicate evaluates to `false` (fail-closed, not fail-open) and a diagnostic warning is logged — a skill author's typo should never accidentally *broaden* matching |
| Resolution takes too long (pathological catalog growth) | Constraint Solver, wall-clock guard | Abort backtracking at a configurable node-visit ceiling; return best-known partial assignment as `PARTIAL` rather than hanging |

## 10. Recovery

- **`UNRESOLVABLE`**: surfaced to the caller (typically the Executor or a
  human-facing layer) with `diagnostics` naming exactly which slot failed
  and why — "no candidate for ReviewVerdict satisfies exclusiveWith after
  caveman-review was pruned by change_risk == high" — not a generic error.
- **`PARTIAL`**: is not a failure. The Scheduler executes the resolved
  subgraph and re-invokes `resolve()` for the remaining slots once more
  `RuntimeState` is available (e.g. after `task-decomposer` actually runs
  and produces the `SubtaskList` a later slot needed).
- **Node failure mid-execution**: the Executor calls `reresolve()`, which
  walks the failed node's precomputed `fallbackChain` before falling back
  to a full slot re-match — this is why `PlanNode.fallbackChain` is
  precomputed at plan-build time rather than derived lazily: recovery must
  not re-run the full constraint solve under failure pressure.
- **Registry corruption / bad manifest**: rejected at load time (see §9),
  never reaches the resolver. The resolver's contract assumes a validated
  registry; validating manifests is the Skill Registry loader's job, not
  this subsystem's.

## 11. Testing Strategy

1. **Manifest fixtures, not live skills.** Unit tests construct synthetic
   `SkillManifest` sets — including deliberately cyclic, deliberately
   conflicting, and deliberately version-incompatible ones — so resolver
   logic is tested independently of the real 25-skill catalog.
2. **Golden plans.** For the real registry, a fixed set of `(Goal,
   RuntimeState)` inputs have checked-in expected `ExecutionPlan` outputs.
   Any change to weighting or constraint logic that alters a golden plan
   must be an explicit, reviewed diff — this is the determinism guarantee
   (§3) made testable.
3. **Adversarial predicate fuzzing.** Random `RuntimeState` generation
   against the real registry, asserting only structural invariants (no
   `exclusiveWith` violation ever appears in an emitted plan; every edge's
   `from` node is topologically before its `to` node) rather than exact
   plan equality — catches constraint-solver bugs golden plans wouldn't.
4. **Backtracking bound test.** A synthetic worst-case manifest set (dense
   mutual exclusions) verifies the wall-clock guard in §9 actually trips
   before a real timeout would.
5. **Reresolve isolation.** Verify `reresolve()` never re-touches nodes
   outside the failed node's downstream closure — a regression here would
   silently turn cheap failure recovery into a full re-plan.

## 12. Performance Characteristics

| Operation | Complexity | Notes |
|---|---|---|
| `match()` | O(k) per artifact, k = producers of that artifact (via inverted index) | Not O(n) over full registry |
| `rank()` | O(c log c), c = candidates in a slot | c is small in practice (< 10) |
| `solve()` | Exponential worst case, low-single-digit-backtrack typical case | Bounded by wall-clock guard (§9) |
| `buildPlan()` | O(n + e), n = nodes, e = edges | Standard DAG construction + topo sort |
| `reresolve()` | O(fallbackChain length), amortized O(1) in the common case | Precomputed chain avoids re-solving |

Full resolution for a goal touching ~5–8 skills (typical AGY task) is
expected to be low-single-digit-millisecond work excluding any network
calls — the resolver does no I/O of its own beyond the State Probe reads,
which should be cache-backed by Context Manager rather than live-fetched
per predicate.

## 13. Security Considerations

- **Predicate injection**: `triggerPredicates` are data, not code — the
  Matcher must use a fixed, small predicate grammar (comparison operators
  over named `RuntimeState` fields only) and never `eval()` arbitrary
  expressions from a skill manifest. A malicious or buggy skill package
  should not be able to smuggle executable logic through this field.
- **Registry trust boundary**: manifests from unverified sources (e.g. a
  skill installed from an untrusted plugin) must be validated and
  sandboxed at *load time*, before they ever reach the resolver's
  `byName`/`byProduces` indices. The resolver trusts its registry
  completely — that trust must be earned upstream, not re-checked here on
  every call.
- **Exclusion bypass**: a bug that lets `satisfiesExclusion` silently pass
  is a security-relevant bug, not just a correctness one, if exclusivity
  was declared for a reason like "never run an untrusted execution skill
  alongside one that has filesystem write access." §11's structural-
  invariant fuzzing exists specifically to catch this class of regression.

## 14. Tradeoffs

| Decision | Alternative considered | Why this was chosen |
|---|---|---|
| Stateless resolver, state passed in | Resolver owns a state cache | Statelessness makes determinism (§3) and recovery (§10) trivial to reason about; the cost is that callers must assemble `RuntimeState`, which is acceptable since Context Manager already tracks most of it |
| Exhaustive backtracking over heuristic SAT | Off-the-shelf SAT/SMT solver | Catalog size makes exhaustive search cheap today; a solver dependency would be premature abstraction (Design Principle #2) for a problem this small — revisit if catalog size grows an order of magnitude |
| Fail-closed on unknown predicate variables | Fail-open (predicate ignored, skill still eligible) | Fail-open silently broadens matching in a way that's invisible to the skill author and the operator; fail-closed produces a loud diagnostic instead |
| Precomputed `fallbackChain` at plan-build time | Lazy re-match on failure | Slightly larger plan objects, but recovery latency and determinism both improve — failure recovery is exactly the moment you don't want a fresh combinatorial search |
| Configuration-driven ranking weights | Hardcoded scoring constants | Cost sensitivity (`RuntimeState.costSensitivity`) and org-specific priority tuning both need to change ranking behavior without a resolver code change |

---

## 15. Future Extensions

- **Constraint propagation pre-pass**: arc-consistency filtering before
  backtracking, if catalog growth ever makes naive backtracking's
  worst case matter in practice (currently speculative — no evidence
  requires it yet, per Design Principle #3).
- **Adaptive Learning integration**: `historicalSuccessBonus` in §8.2 is
  a stub hook today; once the Execution Ledger has enough resolved-plan
  outcomes, this becomes a real learned prior rather than a constant zero.
- **Multi-goal batch resolution**: resolving several independent goals in
  one call to share Matcher/Ranker work — not needed until Cavecrew-style
  parallel subtask execution is common enough to matter.
- **Plan diffing**: given two `ExecutionPlan`s for the same goal at
  different points in a session, compute a minimal diff — useful for
  `explainPlan()` output when a `reresolve()` changes the plan
  significantly.

## Open Questions for Next RFC

This subsystem assumes a validated, in-memory `SkillRegistry`. The next
subsystem to design should be either:

(a) **Skill Registry / Loader** — manifest parsing, validation, the
cyclic-`requires` rejection referenced in §9, and the trust boundary
referenced in §13, or

(b) **Execution Graph consumer (Scheduler)** — takes the `ExecutionPlan`
this RFC defines and actually runs it.

(a) is the harder dependency to leave undefined — this RFC's §9 and §13
both assume validation guarantees that don't exist yet. Recommend (a)
next.
