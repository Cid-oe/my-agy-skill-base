## Status of This Memo

This document specifies an Internet-style standard for the AGY project. It is a
design draft that has not yet been ratified. Distribution is unlimited. Comments
are requested and should be addressed to the Architecture Working Group.

## Abstract

The **Executor** is the component of AGY that turns Scheduler output into
finished work. It takes an immutable Execution Order from the Scheduler
(RFC-0007), resolves and loads a Skill (RFC-0001, RFC-0002), authorizes the
invocation through the Policy Engine (RFC-0003), runs the Skill, and produces a
durable, auditable outcome — a committed result set of Artifacts (RFC-0004), a
final state record in Runtime State (RFC-0005), and a complete, ordered,
replayable event history on the Event Bus (RFC-0006).

The Executor is **not** an agent, and it is not a scheduler. It contains no
planning logic, no goal-seeking, and no resource-allocation policy of its own.
It is a *deterministic control plane over non-deterministic work*. Every
decision the Executor makes — admission, retry, cancellation, rollback,
finalization — is a pure function of (input spec, durable state snapshot,
pinned policy snapshot, clock reading). The skills it runs are free to be
non-deterministic; the Executor's bookkeeping about them is not.

This document specifies the Executor's responsibilities, architecture,
components, interfaces, data structures, state machines, algorithms, failure
recovery, security posture, and its scaling and concurrency model. Resource
management (CPU, memory, IO, network quotas; worker-pool sizing; node
placement) is explicitly **out of scope** and is deferred to a later RFC. This
document only defines how the Executor *signals* resource pressure, never how
resources are allocated.

## Terminology

The following terms are used with precise meaning throughout this RFC. Readers
should not import looser colloquial meanings.

- **Execution** — the logical unit of one Skill invocation under one Execution
  Order. An Execution has an identity, a spec, a state machine, and a terminal
  outcome. One Execution may span several Attempts.
- **Attempt** — one physical run of the Skill (one loaded session, one process
  or sandbox or remote call). Attempts exist to support retries. Attempt `i+1`
  never observes the in-memory residue of attempt `i`.
- **Execution Order (Order)** — the immutable instruction emitted by the
  Scheduler (RFC-0007). The Executor consumes Orders and produces nothing that
  modifies an Order.
- **Plan** — the directed acyclic graph (DAG) of steps owned by the Scheduler.
  Each step maps to exactly one Execution in the Executor. The Executor executes
  steps; it never edits the DAG.
- **Causation ID** — the identity of the Execution that *requested* this work
  (a parent step, an external trigger, or `nil` for a root). Causation is a
  tree; it is not a call stack and it is not resource lineage.
- **Trigger** — why an Execution exists: `SCHEDULER`, `RETRY`, `ROLLBACK`,
  `MANUAL`, `EVENT`, `COMPENSATION`.
- **Failure Record** — a typed, structured, content-addressed description of a
  failure (kind, retryability, rollbackability, payload reference, causation).
- **Compensation** — a Skill or inverse step declared to semantically undo a
  completed mutation. Rollback executes compensations.
- **Cleanup** — release of Executor-held resources (locks, leases, streams,
  scratch state). Cleanup is not rollback and must never fail.
- **Stream / Frame / Segment** — a Skill's output is a Stream of ordered
  Frames; persisted Frames are grouped into immutable Segments (Artifacts).
- **Lease / Fence** — the mechanism granting exactly one Executor worker
  write-ownership of an Execution at a time.
- **PEP** — Policy Enforcement Point, a call site where the Executor queries the
  Policy Engine.
- **Determinism envelope** — the claim that, given identical (spec, state
  snapshot, policy snapshot, clock), the Executor's control-plane decisions are
  identical. Skill output is outside the envelope.

## 1. Executive Overview

AGY decomposes intelligence work into a pipeline of *authority* and *work*.
RFC-0007 (Scheduler) owns the question "what should run, in what order, with
what priority and deadline." This RFC owns the question "how is a single unit
of work actually run, safely, durably, and observably." The split is deliberate
and mirrors the control-plane / data-plane separation found in Kubernetes
(scheduler vs. kubelet) and in stream processors (coordinator vs. worker).

The Executor has three jobs, in decreasing order of glamour:

1. **Faithful execution.** Given a resolved, authorized, loaded Skill and an
   input snapshot, drive the Skill to a terminal state while honoring
   deadlines, cancellation, and policy obligations.
2. **Durable bookkeeping.** Make every meaningful fact about an Execution —
   state transitions, attempts, failures, stream checkpoints, artifact
   references — durable *before* it can be observed as "true." The Executor's
   output of record is a set of Artifacts plus a final Execution Record in
   Runtime State, and an ordered event log on the Event Bus.
3. **Graceful degradation.** Under failure, overload, or contradiction, degrade
   in a way that is *explainable and reversible*: retry transient failures,
   roll back partial success, shed load with a typed reason, and never leave an
   Execution in a state that cannot be audited from durable state.

Two properties are load-bearing throughout the design:

- **Deterministic control plane.** The Executor's own decisions are replayable.
  This is what makes crash recovery, auditing, and testing tractable at scale.
  It is *not* a claim that skills are deterministic.
- **Single-writer ownership.** At any instant, exactly one Executor worker is
  authorized to advance a given Execution. This collapses an enormous class of
  distributed-systems bugs (double-spend of attempts, duplicate side effects,
  torn state) into a single, well-understood lease-and-fence problem.

The Executor is designed to be horizontally scaled by sharding Executions across
many workers. There is no global "execution registry" hot spot: workers own
disjoint key ranges, and coordination happens only through Runtime State
(compare-and-swap) and the Event Bus (ordered logs). This is the same shape as
Kafka consumer groups and PostgreSQL's per-row MVCC, and it is the property that
lets the design reach thousands of skills, thousands of artifacts, and hundreds
of concurrent executions without a central bottleneck.

## 2. Responsibilities

The Executor **is responsible for**:

1. **Ingesting Execution Orders** from the Scheduler idempotently, validating
   them, and admitting or rejecting them (with a typed reason) under
   backpressure.
2. **Execution lifecycle management** — driving each Execution through
   ADMITTED → PREPARING → RUNNING → terminal, with defined transient states
   for retry wait, cancellation, and rollback (Section 10).
3. **Skill invocation** — resolving the Skill to a pinned, verified descriptor
   (RFC-0001/0002), loading it, and invoking it through a canonical, transport-
   agnostic Invocation Contract (Section 7.3).
4. **Parallel execution** — running ready steps of a Plan concurrently,
   subject only to DAG dependencies and policy-expressed safety caps; and
   running unrelated Executions concurrently (Sections 5, 11, 16).
5. **Cancellation** — cooperative, tree-scoped, graceful-then-forced, with
   idempotent command handling and cascade to descendants (Sections 10, 11.6).
6. **Retries** — policy-driven attempt scheduling with a typed error taxonomy,
   bounded attempts, deterministic backoff, and idempotency keys (Section 11.4).
7. **Rollback** — compensating completed mutations in reverse topological
   order, best-effort, bounded, and fully audited (Section 11.5).
8. **Streaming outputs** — managing ordered, framed, backpressured output
   streams, persisted as Artifacts, with checkpoints and partial-result
   semantics (Sections 6.6, 8, 11).
9. **Artifact creation** — producing the input snapshot, result set, stream
   segments, logs, failure records, and checkpoints as content-addressed
   Artifacts (RFC-0004), with an atomic finalize (Section 11.11).
10. **Telemetry** — emitting a complete, ordered, versioned event history for
    every Execution, with deterministic sampling for high-volume frames
    (Sections 6.7, 8, 14).
11. **Timeout management** — layered deadlines on a single monotonic clock,
    stall detection on streams, and typed timeout failures (Section 11.9).
12. **Backpressure** — admission shedding/re-queueing toward the Scheduler,
    credit-based stream flow control, and bounded internal queues with spill
    (Section 11.10).
13. **Execution isolation** — logical fault-domain and security isolation:
    per-Execution state/artifact/stream namespaces, scoped credentials, fault
    containment at the invocation boundary (Section 11, 13).
14. **Failure propagation** — typed, lossless propagation of failures to
    parents, to the Scheduler (for re-planning), and to subscribers
    (Section 12).
15. **Policy interaction** — calling the Policy Engine at every defined PEP,
    pinning a policy version per Execution, and enforcing obligations
    (Sections 6.5, 11.3).
16. **Crash recovery** — reconstructing its working set from Runtime State and
    the Event Bus, and reconciling orphaned/zombie Executions via leases and
    fencing (Sections 11.8, 12).

## 3. Non-goals

The Executor is **not responsible for**:

- **Resource management.** CPU, memory, IO, network quotas; worker-pool sizing;
  autoscaling; node selection; GPU/cache partitioning; fair-share scheduling of
  physical resources. The Executor *signals* pressure (backpressure events,
  `RESOURCE_STARVED` failure kinds) and *consumes* whatever capacity a future
  Resource Management RFC grants. All of that RFC's decisions are out of scope
  here.
- **Planning or prioritization.** The DAG, ordering, deadlines, and priorities
  belong to RFC-0007. The Executor executes one step at a time; it never
  reorders siblings, never promotes or demotes, never re-plans. If a failure
  requires re-planning, the Executor *returns the problem* to the Scheduler as
  a typed event; it does not solve it.
- **Skill resolution policy.** Version selection, dependency resolution, and
  integrity verification are RFC-0001/0002 territory. The Executor pins and
  caches what it is handed.
- **Policy *authoring*.** The Executor enforces policy; it never defines,
  stores, or mutates policy. The Policy Engine (RFC-0003) is the single source
  of truth for decisions.
- **Skill semantics.** The Executor cannot make a non-idempotent Skill
  idempotent, cannot invent compensations a Skill does not declare, and cannot
  guarantee perfect undo of arbitrary side effects (see Critical Self Review).
- **Distributed transactions.** There is no two-phase commit spanning Skills.
  Rollback is best-effort semantic undo, not atomicity.
- **User-facing product behavior.** No goal representation, no agent loop, no
  memory synthesis. Those are other RFCs.
- **Secrets *storage*.** The Executor injects credentials as short-lived scoped
  handles; the vault/identity system that issues them is a later RFC.

## 4. Relationship to Previous RFCs

This section states, for each prior RFC, the interaction contract the Executor
relies on. Contracts are treated as immutable. Where this RFC *adds* to a prior
RFC's surface, the addition is strictly additive (new namespaces, new event
types, new keys in Executor-owned scopes) and never redefines an existing
contract. Appendix A collects the assumed minimal contract of each RFC; any
delta between that assumption and the published text is a compatibility note
(Section 19).

### 4.1 RFC-0001 (Skill Resolver)

**Interaction.** During `prepare`, the Executor calls the Resolver to turn the
Order's skill reference into a *Resolved Skill* — a pinned, immutable
descriptor `{ skillId, version, manifestHash, entrypoints, capabilityClaims }`.
The Executor then **holds that descriptor for the lifetime of the Execution**:
resolution happens once, at admission, and is never re-run mid-Execution (this
is what makes the control plane deterministic — see `D-1`). If a skill is
updated or deprecated while an Execution is in flight, the in-flight Execution
is unaffected; it is pinned to the resolved version.

**Why this matters.** Re-resolving mid-flight would make two Executions with the
same Order behave differently depending on registry timing, breaking the
determinism envelope and making audits untraceable.

### 4.2 RFC-0002 (Skill Registry & Loader)

**Interaction.** Given a Resolved Skill, the Executor requests a *load* from the
Loader and receives a `LoadedSkill` handle with a verified content digest and
the Skill's *declared interface* — including, critically, its declared
**compensations** and its **idempotency/retryability declaration** (if the
manifest carries one). The Executor caches handles keyed by digest; it never
loads code itself and never bypasses integrity verification.

**Coupling.** Load latency sits on the cold path of `prepare`. The Executor
therefore treats a load as an async, cacheable operation and does not serialize
all Executions behind a single load lock. A failed load is a typed, permanent
failure (`SKILL_LOAD_FAILED`) — it is not retried as if it were transient
(Section 11.4).

### 4.3 RFC-0003 (Policy Engine)

**Interaction.** The Executor calls the Policy Engine at every Policy
Enforcement Point (Section 6.5). Each call passes a `DecisionRequest`
`{ action, principal, resource, context, policyVersion }` and receives a
`Decision` `{ effect ∈ {permit, deny, obligate}, obligations[], reason,
decisionId }`. Two rules govern this interaction:

1. **Policy version is pinned per Execution.** The Executor records the policy
   version active at admission and evaluates every subsequent decision against
   that snapshot. A policy change mid-Execution does **not** retroactively
   re-decide committed decisions. This is a hard determinism requirement, and it
   means the Executor and the Policy Engine must agree on a snapshot/version
   identifier (an extension the Policy Engine RFC may not yet define — flagged
   in Section 19).
2. **Decisions are cached** by `(policyVersion, decisionKey)` with an explicit
   invalidation on policy-change events. The Policy Engine sits on the hot path
   (every admission, every retry decision, every artifact commit); an
   uncached round-trip per decision would dominate Executor latency.

**Failure semantics.** A Policy Engine outage is a control-plane failure. The
default is **fail-closed** (deny) for *authorization* PEPs and
**fail-open-with-audit** for *obligation* PEPs whose obligations are purely
observational (e.g., "emit this event"). This asymmetry is configurable per
policy class and is documented in Section 13.

### 4.4 RFC-0004 (Artifact System)

**Interaction.** Everything the Executor produces that must outlive the process
is an Artifact: input snapshots, result payloads, stream segments, logs,
failure records, checkpoints, and a final **manifest** that binds the result set
into one content-addressed, atomically committed unit. The Executor uses the
Artifact System's `Create` (content-addressed, immutable) and `Commit`
(atomic manifest) primitives.

**Coupling.** Artifact write latency must not sit on the Skill's critical path.
The Executor spools streams in background writers (Section 6.6) and only
*references* Artifacts in its own records — it never copies payloads into
Runtime State. Per-Execution artifact namespaces (Section 11.2) prevent
cross-Execution collisions at thousands-of-artifacts scale.

### 4.5 RFC-0005 (Runtime State)

**Interaction.** Runtime State is the Executor's single source of truth for
*current* facts: the Execution Record, Attempt Records, the command journal,
leases, checkpoints. All Executor state transitions are committed via
compare-and-swap (CAS) with monotonic version numbers; a CAS failure means
"someone else (or a past self) already advanced this Execution" and triggers the
fencing/refresh path, not a retry of the side effect. Watches on state keys
drive cancellation and command delivery.

**Why state, not the bus.** The Event Bus is a log of what *happened*; Runtime
State is what *is*. Recovery (Section 11.8) rebuilds "what is" from "what
happened," but the hot path reads and writes "what is" because it is
point-lookup, not scan. Keeping telemetry out of Runtime State (it belongs on
the bus) is a deliberate write-amplification control.

### 4.6 RFC-0006 (Event Bus)

**Interaction.** The Executor publishes to Executor-owned streams: per-Execution
ordered logs, a global `executions` stream of coarse lifecycle events, command
streams for control, and telemetry/metrics streams. It consumes command streams
(cancellation, retry-now) and policy-change events. All consumers — including
the Executor's own recovery path — are required to be idempotent on event id,
because the bus is at-least-once.

**Coupling.** Recovery depends on bus *retention*. If an Execution's event
history has aged out of the bus before a worker recovers, recovery must fall
back to Runtime State + Artifacts. The Executor therefore treats the bus as a
*convenient ordered log*, and Runtime State as the *authoritative* log of
record; Section 19 records this as a latent assumption to verify against the
published RFC-0006.

### 4.7 RFC-0007 (Scheduler)

**Interaction.** The Scheduler emits Execution Orders; the Executor admits or
rejects them. The Executor reports terminal outcomes and `RESOURCE_STARVED` /
`REPLAN_REQUIRED` signals back to the Scheduler. The boundary is strict:
**the Scheduler decides *when and in what order*; the Executor decides *how and
whether at all* (admission).** The Executor never holds an unbounded queue of
its own (see `D-1`) — it either runs an Order now or tells the Scheduler to
hold it, so the Scheduler's queue remains the single authoritative queue in the
system.

## 5. Architecture

### 5.1 Control plane / data plane split

The Executor is two planes sharing one identity:

- **Control plane** (the "Executor proper"): admission, policy calls, state
  transitions, retry/rollback/cancellation logic, lease management, finalization.
  This plane is deterministic, stateless-reconstructible, and horizontally
  scalable by sharding.
- **Data plane** (the "invocation runtime"): the actual running of Skills —
  process/sandbox/remote-call hosting, stream plumbing, credential injection.
  This plane is where non-determinism lives, and where fault containment is
  enforced (a crashing Skill must not be able to corrupt the control plane).

The two planes communicate only through the Invocation Contract (Section 7.3)
and through durable state. There is no shared memory between them. This is the
single most important structural decision in this RFC, because it is what makes
crash recovery, replay, and testing tractable: the control plane can be replayed
and unit-tested without running a single Skill.

### 5.2 Ownership and sharding

Executions are the unit of sharding. Each Execution is owned by exactly one
Executor worker at a time (single-writer), enforced by lease + fence token
(`D-13`). Workers are assigned key ranges by consistent hashing of the
Execution ID; a shard's working set is a cache, not the truth — the truth lives
in Runtime State. This means a worker can crash and be replaced with zero data
migration: the new worker rebuilds the shard's working set from durable state.

There is no global coordination service invented by this RFC. Cross-Execution
coordination that is *not* per-Execution CAS (e.g., global policy-derived
safety caps) is expressed through policy and enforced cooperatively; anything
requiring hard global consensus is deferred to the Resource Management RFC.

### 5.3 The invariant list

The Executor's correctness reduces to a small set of invariants. Everything
else is derived.

1. **Order immutability.** An Execution Order is never mutated after admission.
2. **At-least-once attempts, exactly-once bookkeeping.** A Skill attempt may run
   more than once (retry, crash-redispatch); the Executor's *records* of
   attempts are written exactly once each, keyed by (Execution, Attempt), via
   CAS. Idempotency of the *Skill's* side effects is the Skill's responsibility,
   enabled by Executor-supplied idempotency keys (Section 11.4).
3. **Single-writer.** At most one worker holds a valid fence for an Execution.
4. **Durable-before-observable.** No state transition, artifact reference, or
   terminal outcome is reported until it is durable in Runtime State (and, for
   terminal outcomes, in the committed manifest).
5. **Lossless failure.** Every failure produces a Failure Record; no failure is
   swallowed; no terminal state is reached without a recorded cause chain.
6. **Determinism envelope.** Control-plane decisions are functions of
   (spec, state snapshot, policy snapshot, clock).
7. **Bounded everything.** No unbounded queues, buffers, or retries. Every
   queue has an explicit overflow policy (Section 11.10).

### 5.4 Top-level data flow

```
Scheduler ──Order──▶ [ Admission ] ──▶ [ Prepare ] ──▶ [ Run ] ──▶ [ Finalize ]
 (RFC-0007)           │ accept/reject    │ resolve/load     │ attempts   │ commit
                      │                  │ policy/context   │ streams    │ manifest
                      ▼                  ▼                  ▼            ▼
                 Backpressure       Policy Engine      Skill (Invocation   Artifact
                 signal ──────▶     (RFC-0003)         Contract)          System
                                                       │  │  │            (RFC-0004)
                                    Runtime State ◀────┴──┴──┘
                                    (RFC-0005)  ← lease, state, checkpoints
                                    Event Bus ◀── telemetry, commands
                                    (RFC-0006)
```

The diagram is deliberately linear at the top level; all the complexity is in
the Run box's state machine and in the failure paths that fan out from it.

## 6. Internal Components

The Executor is decomposed into nine components. Components communicate through
per-Execution message passing (Section 16); none of them may hold global
mutable state.

### 6.1 Admission Controller

First contact for Orders. Responsibilities: validate the Order (schema,
references, deadline sanity), assign the Execution ID (deterministically
derived from `(planId, stepId, orderId)` — never a central sequence), check
admission budget and backpressure state, and produce one of `ACCEPT`,
`REJECT(reason)`, or `HOLD(reason)` (Section 11.10). Admission is idempotent on
Order ID. The Admission Controller is the only component allowed to talk
backpressure to the Scheduler.

### 6.2 Preparer

Drives ADMITTED → PREPARING → RUNNING. Steps: pin policy version; resolve skill
(RFC-0001); request load (RFC-0002); evaluate admission PEPs (RFC-0003);
materialize the input snapshot as an Artifact; create the Execution's
namespaces (state scope, artifact scope, stream scope); write the initial
Execution Record and checkpoint. The Preparer is deliberately the only place
where resolution and loading happen, so that everything downstream sees a
pinned descriptor.

### 6.3 Invoker

Owns the Invocation Contract on the Executor side: hands the Skill its input
snapshot reference, output stream handles, cancellation token, credential
handles, checkpoint handle, and applicable policy obligations; then drives the
Skill until terminal. The Invoker enforces fault containment — any panic,
uncaught exit, or protocol violation at the boundary is converted into a typed
`SKILL_CRASH` / `PROTOCOL_VIOLATION` failure, never into Executor corruption
(Section 13). The Invoker is transport-agnostic: the same contract is
implementable over in-process calls, local IPC, remote RPC, or sandboxed
runtimes (Section 7.3).

### 6.4 Attempt Manager

Implements the retry loop (Section 11.4): classifies failures, consults retry
policy (possibly via a PEP), computes backoff with deterministic jitter, and
spawns the next Attempt. It owns the Attempt Records and the attempt-id
sequence. It guarantees that attempt `i+1` starts from a clean state (no
inherited memory, fresh context snapshot, same idempotency domain with a
distinct attempt id).

### 6.5 Policy Enforcement Points (PEPs)

A PEP is a named call site, not a component — but the Executor maintains a
single **PEP registry** so that policy interaction is auditable and uniform.
The PEPs are:

| PEP | When | Effect on deny | Effect on obligations |
|---|---|---|---|
| `admission` | Order accepted | `DENIED` (never ran) | e.g., "attach mandatory label", "force telemetry level" |
| `pre-invoke` | before each attempt | `FAILED` (ran zero times) | e.g., "redact secrets", "cap output rate" |
| `retry` | before scheduling a retry | no retry; terminal `FAILED` | e.g., "max attempts", "backoff floor/ceiling" |
| `stream-egress` | each output frame/batch | frame dropped or stream aborted | e.g., redaction, filtering, size caps |
| `artifact-commit` | before finalize | `FAILED` with cause | e.g., retention class, export review flag |
| `rollback` | before executing a compensation | compensation skipped (recorded) | e.g., "require human approval above cost X" |
| `teardown` | after terminal state | — | e.g., "delete scratch", "retain logs N days" |

Each PEP call is cached keyed by `(policyVersion, decisionKey)` (Section 4.3).
Obligations are returned to the component as constraints it must enforce for
the rest of the Execution (e.g., a rate cap obligation becomes a stream
throttle).

### 6.6 Stream Manager

Manages all output streams (a Skill may expose several named streams: primary
result, structured events, produced-artifact list, diagnostics). Per stream it
maintains: frame ordering, per-frame sequence numbers, checksums, a bounded
in-memory buffer with credit-based flow control toward the producer, background
spooling to Artifact segments, checkpoint tracking, and stall detection
(heartbeat). Consumers read either live (subscribing to the live tap) or
replayed (from persisted segments). Partial-result semantics live here: on
failure, the last committed checkpoint is published as a `PARTIAL` result
artifact (Section 11.11).

### 6.7 Telemetry Emitter

Produces the Execution's event history and metrics. All telemetry is expressed
as versioned, typed events on the bus (there is no separate side-channel
metrics pipeline that could drift from the log). Correlation uses
`{ executionId, attemptId, causationId, spanId }`. High-volume frame-level
events are subject to **deterministic sampling** — hash(executionId, seq) below
a threshold — so that sampling is reproducible across replay (Section 14).
Metrics (counters, gauges, histograms) are *derived* from the event log, which
guarantees the metric view and the audit view can never disagree.

### 6.8 Finalizer

Runs the terminal transition: gathers the result set, writes the manifest
Artifact, runs the `artifact-commit` PEP, commits the final Execution Record via
CAS, emits the terminal event, releases the lease, and runs `teardown`
obligations. The Finalizer is the only component allowed to write a terminal
state. Finalization is idempotent: re-running it after a crash must not
duplicate artifacts or events (Section 11.11).

### 6.9 Recovery Coordinator

Rebuilds the worker's working set after (re)start and reconciles orphans: for
each Execution in the shard's key range it loads the Execution Record, replays
events after the last durable checkpoint, and either resumes, fences, or
re-queues (Section 11.8). It also runs the lease-expiry sweeper that detects
zombie workers (Section 11.7).

## 7. Public Interfaces

Interfaces are specified by *shape and semantics*, not by transport or language.
Any conformant implementation may expose them over its own RPC/queue mechanism.

### 7.1 Dispatch

```
Dispatch(Order) → AdmissionResult
Order = {
  orderId, planId, stepId,              # immutable identity
  skillRef,                             # resolved by RFC-0001 at prepare
  inputs: ArtifactRef?,                 # or inline input snapshot spec
  context: { causationId, labels, parentPlanRef? },
  budget: { deadline, priority, costClass },
  policyAttrs: { policyVersionHint?, requiredLabels? },
}
AdmissionResult = Accepted(executionId)
                | Rejected(reason)      # schema, security, policy-invalid
                | Hold(reason)          # backpressure; Scheduler must hold
```

`Dispatch` is idempotent on `orderId`. The returned `executionId` is a
deterministic function of `(planId, stepId, orderId)` (Section 11.1), so
re-dispatch after a lost reply yields the same Execution, and the Executor
reports `AlreadyAdmitted` instead of duplicating.

### 7.2 Control commands

All control commands are idempotent and journaled (Section 11.6):

```
Cancel(executionId, reason, { gracePeriod? })   → CommandResult
RetryNow(executionId, { skipBackoff? })         → CommandResult
Query(executionId)                              → ExecutionRecord
```

Control commands may arrive by RPC or by Event Bus command topic; both paths
converge on the same per-Execution command journal in Runtime State. A command
is acknowledged when it is *durably journaled*, not when its effect completes
(completion is observable via events). Commands for unknown Executions are
`NACK`ed with a typed reason; commands for terminal Executions are `NACK`ed
unless they are idempotent no-ops (e.g., `Cancel` of an already-cancelled
Execution is `ACK`).

### 7.3 The Invocation Contract (Executor ↔ Skill)

This is the single most consequential interface in the RFC. It is deliberately
minimal and side-effect-enumerated:

```
Invoke(InvocationContext) → (OutputChannels, DoneSignal)
InvocationContext = {
  executionId, attemptId,                 # identity + idempotency domain
  input: ArtifactRef,                     # immutable input snapshot
  params,                                 # typed arguments
  credentials: CredentialHandle[],        # scoped, short-lived, revocable
  cancellation: CancellationToken,        # deadline + grace + escalation
  checkpoint: CheckpointHandle,           # cooperative yield/checkpoint
  telemetry: TelemetryHandle,             # structured emit, span attach
  obligations: Obligation[],              # policy constraints to enforce
  env: { stateScope, artifactScope },     # Executor-assigned namespaces
}
OutputChannels = { primary, events, producedArtifacts, diagnostics }
DoneSignal = { status, result?: ArtifactRef, failure?: FailureRecord }
```

Contract rules:

1. **Inputs are references, never copies.** The Skill receives an ArtifactRef
   to an immutable input snapshot; the Executor guarantees the snapshot is
   stable for the Execution's lifetime.
2. **Outputs are streams, not return values.** A Skill emits ordered frames to
   named channels; a "return value" is merely the terminal frame of `primary`
   plus a `DoneSignal` carrying a result ArtifactRef.
3. **Cooperative cancellation.** The Skill is expected to poll or await the
   cancellation token and to honor the deadline. The Executor escalates from
   signal → deadline → forced abort (Section 11.6). A Skill that ignores the
   token is eventually force-aborted; the contract documents that force-abort
   forfeits rollback guarantees (partial side effects possible).
4. **Failure is structured.** A Skill reports failure as a FailureRecord, not
   as an unstructured exit code. Exit codes / exceptions are mapped at the
   boundary into the taxonomy (Section 12) — the mapping table is part of the
   contract so behavior is uniform across skills.

### 7.4 Observability interface

```
Subscribe(executionId, { fromSequence? })  → EventStream
Tap(executionId, stream)                   → LiveStream   # live frames
ListExecutions(filter)                     → ExecutionRecord[]
```

`Subscribe` returns the ordered event log (replay-safe). `Tap` gives a live,
lossy-at-boundary view of an output stream for interactive consumers — lossy
because the authoritative copy is the persisted segment, never the live tap.

## 8. Data Structures

All structures are versioned. Field additions are backward-compatible; semantic
changes bump the structure version. Storage is via Runtime State (records) and
the Artifact System (payloads). Payloads are never duplicated into records —
records hold references.

### 8.1 ExecutionRecord

```
ExecutionRecord {
  executionId, orderRef, causationId, trigger,
  status,                                # see Section 10
  policyVersion,                         # pinned at admission
  skillRef,                              # pinned resolved descriptor
  attemptCounter, currentAttempt?,
  deadlineMonotonic,                     # monotonic-clock deadline
  timeouts: { perAttempt, stall, grace, rollbackBudget },
  lastCheckpoint: CheckpointRef,
  resultSet: ArtifactRef?,               # manifest, set at finalize
  failure?: FailureRecord,
  timestamps: { admittedAt, startedAt, endedAt },
  version,                               # CAS version
}
```

### 8.2 AttemptRecord

```
AttemptRecord {
  executionId, attemptId,                # (executionId, attemptId) is the key
  status,                                # see Section 10.2
  startedAt, endedAt,
  inputRef,                              # input snapshot (may differ across attempts if inputs are time-scoped)
  outcome: SUCCEEDED | FAILED | CANCELLED | TIMED_OUT,
  failure?: FailureRecord,
  idempotencyKeys: { skillKey, artifactKey },
  resourcesUsedHint?,                    # telemetry only; no enforcement
}
```

### 8.3 FailureRecord

```
FailureRecord {
  failureId,                             # content hash; dedupe/reference key
  kind,                                  # taxonomy: Section 12
  retryable: bool,
  rollbackable: bool,
  codeDomain, code,                      # e.g., ("skill","timeout"), ("executor","lease_lost")
  message,                               # human-readable, redaction-applied
  payload: ArtifactRef?,                 # stack/dump/diagnostic artifact
  causation: { executionId, attemptId, spanId },
  occurredAtMonotonic,
}
```

### 8.4 Stream frame and segment

```
Frame { stream, executionId, seq, checksum, mediaType, payload, tsMonotonic }
Segment { stream, executionId, seqRange, digest, size, artifactRef }
Checkpoint { executionId, stream, seq, durableAt }
```

Frames are the unit of ordering; segments are the unit of durability; a
checkpoint records that everything ≤ `seq` is durably spooled.

### 8.5 Command journal entry

```
CommandEntry { executionId, commandId, command, args, requestedAt,
               ackStatus: PENDING|ACK|NACK, ackReason?, version }
```

The command journal is a per-Execution ordered list in Runtime State. Command
IDs are caller-supplied idempotency keys; re-delivery of the same `commandId`
returns the recorded `ackStatus` without re-executing (Section 11.6).

### 8.6 Lease record

```
Lease { executionId, holder, fenceToken, expiresAtMonotonic, version }
```

The lease is a CAS-guarded record. `acquire` and `renew` are CAS operations;
`expire` is the sweeper's CAS. A stale holder's writes are rejected because its
`fenceToken` no longer matches (Section 11.7).

### 8.7 Telemetry event (skeleton)

Appendix C gives the full schema. Every event carries `{ schemaVersion,
executionId, attemptId?, causationId, seq, tsMonotonic, type, payload }`.
`seq` is per-Execution and monotonic; `tsMonotonic` is the Executor clock.

## 9. Runtime Lifecycle

The lifecycle is described from the perspective of a single Execution. The
phases map 1:1 onto the state machine (Section 10); this section explains
*what happens* in each phase and *why the ordering matters*.

1. **Admission.** Order arrives → validate → admit (durably write ExecutionRecord
   with status `ADMITTED`) → reply. Durable admission is what makes `Dispatch`
   idempotent. Admission does not yet touch the Skill.
2. **Prepare.** Pin policy version; resolve + load Skill; run `admission` PEP;
   create input snapshot; allocate namespaces; write initial checkpoint;
   transition to `RUNNING`. Prepare is fully cancelable (a cancel that arrives
   here prevents the first attempt entirely, yielding `CANCELLED` with zero
   side effects — the cheapest possible cancellation).
3. **Run.** The Attempt loop: start attempt → invoke → stream → terminal
   (Section 11.3). Retries, cancellations, and timeouts all play out inside
   this phase.
4. **Rollback.** If the Execution completed *some* steps and then failed or was
   cancelled, and compensations exist, run them (Section 11.5).
5. **Finalize.** Commit the result set (or failure record set) as an atomic
   manifest; run `artifact-commit` PEP; write terminal state; emit terminal
   event; release lease; run `teardown` obligations.

Ordering matters in three places: durable-admission-before-reply (idempotency),
checkpoint-before-observable-progress (resumability), and
manifest-commit-before-terminal-state (so a terminal Execution always has a
self-contained, addressable outcome). A consumer that sees `SUCCEEDED` can
dereference `resultSet` and find a committed manifest, always.

## 10. State Machines

State machines are the Executor's executable specification. They are finite,
explicit, and every transition is (a) triggered by a durable input (command,
event, timeout, attempt outcome) and (b) committed via CAS before its effects
are visible.

### 10.1 Execution state machine

Terminal states: `SUCCEEDED`, `FAILED`, `CANCELLED`, `DENIED`, `SKIPPED`,
`TIMED_OUT`. `TIMED_OUT` is a specialization of failure (it implies `FAILED` in
the failure taxonomy but is reported distinctly for operators).

```
                  ┌──────────┐
   Dispatch ─────▶│ ADMITTED │
                  └────┬─────┘
                       │ prepare
                       ▼
                  ┌───────────┐── deny ─────▶ DENIED
                  │ PREPARING │── skip ─────▶ SKIPPED
                  └─────┬─────┘
                        │ ready
                        ▼
                  ┌─────────┐
        ┌────────▶│ RUNNING │◀──────────────┐
        │         └──┬───┬──┘               │
        │ attempt    │   │ attempt          │
        │ failed     │   │ succeeded        │
        │            │   ▼                  │
        │            │ ┌────────────┐       │
        │            │ │ RETRY_WAIT │       │
        │            │ └─────┬──────┘       │
        │   retry (within budget)           │
        └──────────────────┘   no retries / budget exhausted
                                │
                                ▼
                         ┌──────────────┐
                         │ ROLLING_BACK │──▶ FAILED
                         └──────┬───────┘
                                │ (no compensations / rollback done)
                                ▼
                        ┌──────────────┐
                        │  FINALIZING  │──▶ SUCCEEDED | FAILED | TIMED_OUT
                        └──────────────┘

   Cancellation path (from any non-terminal state):
        state ──Cancel──▶ CANCEL_REQUESTED ──(grace)──▶ CANCELLING
              ──(cleanup + optional rollback)──▶ CANCELLED
```

Notes:

- `RETRY_WAIT` is entered only when a retry is permitted; it is a *waiting*
  state, not a running one. A cancel arriving in `RETRY_WAIT` is immediate.
- `ROLLING_BACK` is itself an Execution of trigger `ROLLBACK` (a rollback run
  has its own attempts, its own budget, its own failure record — see
  Section 11.5). The parent remains in `ROLLING_BACK` while compensations run.
- `DENIED` vs `SKIPPED`: `DENIED` means policy forbade the work; `SKIPPED`
  means the plan marked the step optional-and-skipped (e.g., a precondition
  false). They are distinct because their audit semantics differ.

### 10.2 Attempt state machine

```
PREPARING ──▶ RUNNING ──▶ SUCCEEDED
                 │   │
                 │   └──▶ FAILED
                 ├────────▶ TIMED_OUT
                 └────────▶ CANCELLED
```

An Attempt has no `RETRY_WAIT`: retry is a property of the Execution, not the
Attempt. An Attempt is terminal once; Attempt Records are immutable after
terminal.

### 10.3 Stream state machine (per named stream)

```
OPEN ──▶ CHECKPOINTING ──▶ OPEN (loop)
  │
  ├──▶ EOS (end-of-stream, success)
  ├──▶ ABORTED (failure/cancel; last checkpoint remains as PARTIAL)
  └──▶ STALLED ──(no heartbeat within stallTimeout)──▶ ABORTED(stall)
```

`STALLED` is a soft state: it emits a stall event and starts escalation; only
after the stall timeout with no heartbeat does the stream abort and the
Execution transition toward `TIMED_OUT` (Section 11.9).

## 11. Algorithms

Algorithms are specified in structured English, implementation-independent. All
state writes are CAS; all side effects are ordered after their durable record.

### 11.1 Admission and identity

**Execution ID derivation.** `executionId = H(planId ‖ stepId ‖ orderId)`
truncated to the shard key space. Deterministic derivation gives idempotent
dispatch without a central sequencer, and it makes the shard placement
computable by any party. *Weakness:* hash-derived IDs lose global temporal
ordering (you cannot tell which Execution is older from the ID). Ordering, when
needed, comes from `admittedAt` timestamps and the bus sequence — acceptable
because Execution IDs are keys, not clocks.

**Admission decision.** If a record with this `executionId` exists → reply with
its current state (`AlreadyAdmitted`). Else validate; then consult the
admission budget (Section 11.10): admit (write `ADMITTED`), reject, or hold.

### 11.2 Namespace allocation

At prepare, the Executor allocates three disjoint namespaces, all derived from
the Execution ID so they are collision-free and reconstructible after crash:

- **State scope** — a subtree in Runtime State for this Execution's records and
  command journal.
- **Artifact scope** — an Artifact System namespace for this Execution's
  artifacts.
- **Stream scope** — bus stream namespace for this Execution's output streams.

Derivation from the ID (not a registry) means a recovering worker can
reconstruct namespaces without consulting any index — no global namespace table
to contend on. *Scalability note:* the Artifact System must tolerate a very
large number of namespaces (one per Execution); if it cannot, the Executor must
bucketed-namespace (`scope = H(executionId) % B`), trading isolation strength
for namespace count. This is flagged to RFC-0004 in Section 19.

### 11.3 Prepare and invoke (the run loop)

```
prepare:
  pin policyVersion (record it)
  resolvedSkill = Resolve(order.skillRef)          # RFC-0001
  decision = PEP(admission, ...)                   # RFC-0003
  if deny: → DENIED; if skip: → SKIPPED
  loadedSkill = Load(resolvedSkill)                # RFC-0002 (async, cached)
  inputSnapshot = Artifact.Create(inputs)          # RFC-0004
  allocate namespaces; write initial checkpoint
  → RUNNING

run:
  for attempt in 1..maxAttempts:
    record = AttemptRecord{attempt, PREPARING, idempotencyKeys...}
    decision = PEP(pre-invoke, ...)
    ctx = InvocationContext{...}
    outcome = Invoke(ctx)                          # drives the Skill
    record terminal AttemptRecord (CAS)
    if outcome == SUCCEEDED: break → finalize
    else:
      classification = classify(outcome.failure)   # Section 12
      retryDecision = PEP(retry, classification)
      if retryable and budget remains:
        backoff = schedule(attempt, classification) # deterministic jitter
        → RETRY_WAIT (await backoff or Cancel)
      else: break → rollback → finalize(FAILED)
```

The loop is deliberately simple; the complexity lives in the helpers
(classify, schedule, Invoke's internal stream/cancel handling).

### 11.4 Retry algorithm

**Error classification** (Section 12) produces `{retryable, kind}`. The retry
decision is a pure function of `(classification, policySnapshot, attemptCount,
remainingBudget)` — not of wall-clock accident. Backoff is exponential with
**deterministic jitter**: `delay = min(ceil, base * 2^(attempt-1)) * j`,
where `j ∈ [0.8, 1.2]` is derived from `H(executionId ‖ attempt)` — the same
Execution on any worker computes the same schedule, which makes retry timing
replayable and testable.

**Idempotency keys.** The Executor supplies the Skill with stable keys:
`skillKey = H(executionId ‖ skillId ‖ "invoke")` and
`artifactKey = H(executionId ‖ attemptId ‖ stream ‖ seqRange)`. These let a
*cooperating* Skill deduplicate its own external side effects across retries.
The Executor itself guarantees at-least-once attempts and exactly-once
bookkeeping; it cannot make a non-cooperating Skill idempotent, and it does not
pretend otherwise (see Section 20).

**Why not "exactly-once execution"?** True exactly-once of arbitrary side
effects requires distributed transactions or the Skill's own idempotency;
both are out of the Executor's power. Claiming it would be a lie that hides a
correctness gap. The Executor's honest contract is *at-least-once attempts,
exactly-once records, idempotency-enabled-by-keys* — the same shape Kafka and
PostgreSQL adopt for the same reason.

### 11.5 Rollback algorithm

Rollback is **compensation-based**, not snapshot-based. Rationale in `D-7`.

```
rollback(execution):
  completed = steps that reached a "mutating" milestone   # from plan + records
  compensations = completed.flatMap(declaredInverse)      # from Skill manifests
  ordered = reverseTopological(compensations)             # inverse of completion order
  for c in ordered:
    if PEP(rollback, c) == deny: record skipped; continue
    run c as an Execution{trigger=ROLLBACK, budget=rollbackBudget,
                          attemptLimit=small, retryable=idempotent-only}
  record RollbackRecord{attempted, succeeded, skipped, failed, cost}
  release executor-held resources (locks, streams)         # cleanup, never fails
```

Key properties: compensations are themselves Executions (they get the full
lifecycle: attempts, timeouts, telemetry, artifacts); rollback is best-effort
(it records what it could not undo); a failed compensation is not retried
beyond its own small budget (a broken compensation that loops is worse than a
recorded gap); cleanup is unconditional and must not fail. *Weakness:* if a
Skill has external side effects it never declared an inverse for, the gap is
permanent and only visible in the RollbackRecord. The Executor cannot invent
undo logic — it can only make the gap first-class and auditable.

### 11.6 Cancellation and control-command handling

Cancellation is cooperative-first, escalating:

```
on Cancel(executionId, reason, grace):
  command = {commandId, CANCEL, reason, grace}
  CAS append to command journal (idempotent on commandId)
  state machine: any non-terminal → CANCEL_REQUESTED
  signal cancellation token to the running attempt (grace period starts)
  if attempt terminates within grace: → CANCELLING → (rollback if needed) → CANCELLED
  else at grace expiry: force-abort the attempt (boundary kill)
      → record forceAbort=true in AttemptRecord
      → CANCELLING → cleanup → CANCELLED
  cancellation cascades: for each descendant Execution (causation tree),
      emit Cancel(reason=cascade, grace=shared) — descendants cancel themselves
```

The **cascade is via events**, not via a synchronous fan-out that could deadlock
on a slow descendant. A cancelled parent's terminal state does not wait for
every descendant; descendants are independent Executions that will reach
terminal on their own, and the parent's record links to them by causation for
audit. *Weakness:* a slow-to-die descendant can outlive its parent's terminal
state, producing a window where the parent is `CANCELLED` but descendant work is
still running. This is acceptable (descendants are independently owned), but it
must be surfaced in telemetry as `cascadeIncomplete`, and a later "plan
teardown" RFC may tighten it.

**Force-abort semantics.** Force-abort is the last resort and is documented as
side-effect-unsafe: rollback guarantees are forfeited for anything the Skill
did not already checkpoint/compensate. The Executor never force-aborts before
grace expiry, and it records every force-abort with a human-visible reason.

### 11.7 Lease and fencing

```
acquire(executionId): CAS lease{holder=me, fence=random, expires=now+TTL}
renew:   CAS {version → version+1, expires=now+TTL}   # heartbeat, TTL≫heartbeat
expire:  sweeper CAS {holder=H, fence=F} → {holder=none} if now > expires
every write by holder H carries fence F; the state layer rejects writes
whose fence ≠ current fence.  # fencing: a zombie H is dead to the system
```

Takeover after expiry: the new owner acquires the lease (new fence), reloads
the Execution Record, and reconciles (Section 11.8). The old owner, if it
revives, finds its fence invalid and aborts its own writes — it can no longer
double-write. This is the standard lease-fence pattern (Kubernetes leases,
Postgres advisory locks); it is the only place in the Executor where a
distributed mutual-exclusion problem exists, and it is deliberately the only one.

### 11.8 Crash recovery and reconciliation

A worker restart performs, for each Execution in its shard range:

1. Load the ExecutionRecord. If terminal → nothing to do (but verify the
   manifest exists; if missing, the Finalizer re-runs — it is idempotent).
2. If a live lease exists with a *different* fence than mine → the Execution is
   owned elsewhere; skip (do not fence a healthy owner).
3. If the lease expired or is mine → acquire; replay events with
   `seq > lastCheckpoint.seq`; rebuild the in-memory working state.
4. If an Attempt was `RUNNING` at crash: the Skill session is gone. The Executor
   does **not** transparently resume mid-skill unless the Skill implemented the
   checkpoint contract (Section 7.3). Default: mark the attempt `FAILED(kind=
   EXECUTOR_RESTART)`, then run the normal retry decision — which, for a
   retryable classification, produces a fresh attempt. This gives correct
   semantics with a simple recovery path; transparent resume is an optional
   optimization for checkpoint-cooperating skills.

The recovery sweep is idempotent and re-runnable; it is safe to run it
concurrently with live traffic because every mutation is CAS-guarded.

### 11.9 Timeout management

A single monotonic clock drives layered timeouts; all wall-clock deadlines are
converted to monotonic at admission. Layers:

1. **Deadline** (from the Order's budget) — absolute end of the Execution.
2. **Per-attempt timeout** — default derived from budget, overridable by policy.
3. **Stall timeout** — on every output stream: no frame/heartbeat for `stall`
   → `STALLED` → abort → `TIMED_OUT`.
4. **Grace period** — cancellation window before force-abort.
5. **Rollback budget** — bound on total compensation time.
6. **Admission hold timeout** — a held Order is released (to the Scheduler)
   after this, so holds cannot silently starve work.

Every timeout produces a typed `TIMED_OUT`/`STALLED` event carrying *which*
layer fired, so operators can distinguish "skill is slow" from "consumer is
slow" from "we starved it." *Weakness:* monotonic clocks do not survive across
host reboots consistently, and a deadline computed from a wall-clock that jumps
(NTP) can misbehave. Mitigation: deadlines are computed once at admission and
stored as monotonic deltas; wall-clock is only used for *display*.

### 11.10 Backpressure

Three planes, all bounded (see `D-10`):

1. **Admission backpressure (Executor → Scheduler).** The Admission Controller
   maintains a per-shard admission budget (max concurrent Executions per shard,
   max outstanding attempts). When saturated it returns `Hold(reason)`, telling
   the Scheduler to keep the Order in *its* queue. This keeps the Scheduler's
   queue the single queue in the system and avoids double-buffering.
2. **Stream backpressure (Skill ↔ consumers).** Credit-based flow control: the
   Stream Manager grants the producer credits for buffered frames; a slow
   consumer stops receiving credits, the bounded buffer fills, and the producer
   is asked to slow or, if the producer cannot block, frames beyond the buffer
   are spilled to a segment Artifact and delivered later. No silent drop: spill
   is lossless, only deferred.
3. **Internal backpressure.** Telemetry emission is batched and sheds
   non-critical frames under pressure (critical frames: state transitions,
   failures — never shed). State writes are coalesced. The retry queue is
   bounded; if it fills, retries are *re-queued to the Scheduler* rather than
   grown unbounded in the Executor.

The Executor also emits `Backpressure` events so the future Resource Management
RFC can observe and act; the Executor itself never provisions resources.

### 11.11 Finalize and artifact commit

```
finalize:
  if outcome == SUCCEEDED:
    resultSet = { result, streamSegments, producedArtifacts, logs }
  else:
    resultSet = { failureRecord, partialCheckpoint (if any), logs }
  decision = PEP(artifact-commit, resultSet)
  manifest = Artifact.Commit(resultSet)      # atomic, content-addressed
  CAS ExecutionRecord{status=terminal, resultSet=manifest}
  emit terminal event; release lease
  PEP(teardown) obligations                     # retention, scratch cleanup
```

The manifest is the Executor's atomic commit point. Everything a terminal
Execution *is*, is reachable from one ArtifactRef. Partial results on failure
are published as `PARTIAL` — the last durable checkpoint of each stream —
marked in the manifest so consumers can distinguish "complete" from
"incomplete-but-usable."

## 12. Failure Recovery

### 12.1 Failure taxonomy

Every failure is classified once, at the boundary, into a typed record. The
taxonomy is two-dimensional — **kind** (what it is) and **disposition** (what
to do):

| Kind | Disposition | Retry | Rollback |
|---|---|---|---|
| `TRANSIENT` (timeout-stall, net hiccup, resource-unavailable) | retry | yes | n/a |
| `PERMANENT` (bad input, unsupported, type error) | fail | no | yes |
| `SKILL_CRASH` (panic, OOM-in-skill, segfault) | retry once, then fail | maybe | yes |
| `SKILL_LOAD_FAILED` | fail | no | no |
| `POLICY_DENIED` | denied | no | no |
| `EXECUTOR_RESTART` (attempt lost to restart) | retry (if retryable) | yes | yes |
| `LEASE_LOST` (fenced) | abort immediately | no | cleanup only |
| `CANCELLED` | terminal | no | optional |
| `RESOURCE_STARVED` (deferred to Resource RFC) | re-queue to Scheduler | n/a | no |
| `PROTOCOL_VIOLATION` (Skill broke the contract) | fail | no | cleanup only |
| `UNKNOWN` | fail-closed with diagnostics | no | yes |

`UNKNOWN` exists deliberately: the taxonomy must be closed (every path maps to
a kind), and "we could not classify" is itself a first-class, fail-closed kind
rather than an unhandled exception.

### 12.2 Propagation

Failures propagate in three directions:

- **Up (to parent):** the FailureRecord is attached to the Execution Record and
  the terminal event; the parent Execution sees its child's failure as an input
  to its *own* next decision (a step that fails FAIL_FAST, vs. a step that
  collects child failures).
- **Back (to Scheduler):** `REPLAN_REQUIRED`, `RESOURCE_STARVED`, and
  plan-level failure events. The Scheduler decides re-planning; the Executor
  only hands over the evidence.
- **Out (to subscribers):** the ordered event log carries the failure; no
  subscriber is ever expected to poll.

Propagation policy (FAIL_FAST / CONTINUE / SKIP_DOWNSTREAM / BEST_EFFORT) is a
*plan* attribute set by the Scheduler and overridable by policy. The Executor
enforces it mechanically: on a step failure it either stops scheduling sibling
steps (FAIL_FAST), marks downstream steps `SKIPPED` (SKIP_DOWNSTREAM), or lets
siblings proceed and collects failures (CONTINUE). No failure is ever silently
dropped: even under CONTINUE, every failure is recorded and surfaced.

### 12.3 Recovery paths (summary)

- **Worker crash** → Section 11.8 reconciliation.
- **Skill crash** → attempt `SKILL_CRASH`, retry per disposition, then rollback.
- **Policy outage** → fail-closed/fail-open per policy class (Section 13).
- **Artifact System outage** → the Executor cannot finalize; it holds the
  Execution in `RUNNING`/`FINALIZING` with a `BACKEND_UNAVAILABLE` state,
  spools uncommitted streams locally, and retries finalize with backoff. No
  terminal state is written until the manifest commits (invariant 4).
- **Event Bus outage** → telemetry is buffered (bounded) and sheds non-critical
  frames; control commands arriving over the bus are lost until redelivered —
  the command journal in Runtime State is the durable command path, so a bus
  outage degrades *observability* and *async commands*, never state integrity.

## 13. Security Considerations

1. **Least-privilege credentials.** Skills receive scoped, short-lived,
   revocable CredentialHandles, never raw secrets, and never more than the
   policy grants for this Execution's principal. A Skill cannot read another
   Execution's handles (handles are bound to the Execution's scope). The vault
   that mints handles is out of scope, but the Executor's contract *requires*
   it to be revocation-capable, because cancellation must be able to revoke a
   running Skill's authority even if the Skill ignores its token.
2. **Policy fail-closed.** Authorization PEPs deny on Policy Engine outage.
   Obligation-only PEPs may fail-open with audit, but only where the obligation
   is observational; any obligation that *constrains* (rate caps, redaction)
   is treated as fail-closed. This asymmetry must be configurable and audited,
   because a mis-set fail-open here is a real privilege-escalation vector.
3. **Redaction at the boundary.** The `stream-egress` PEP may impose redaction
   obligations; the Executor enforces them at the stream boundary so secrets
   never enter the persisted log or artifacts in the first place — post-hoc
   redaction of stored data is not a substitute (and is a known anti-pattern).
4. **Confused-deputy and cross-Execution isolation.** Namespaces (state,
   artifact, stream) are per-Execution and unforgeable because they derive from
   the Execution ID and are allocated by the Executor, not chosen by the Skill.
   A Skill's credential handles are authorized only within its scope.
5. **Injection via inputs.** Inputs are content-addressed snapshots; the
   Executor never *interprets* Skill inputs, so a malicious input cannot be
   executed as Executor logic. Skill-side injection is the Skill's problem,
   mitigated by the `pre-invoke` PEP.
6. **Command spoofing.** Control commands are authenticated (caller identity)
   and authorized by policy before journaling; the journal records the
   principal for audit. Cancel is the most sensitive command and requires
   authorization against the target's causation tree (you may cancel what you
   caused, or what policy grants you).
7. **Telemetry as a side channel.** Telemetry may contain sensitive data; the
   telemetry PEPs (admission obligations) control verbosity and redaction
   levels per Execution, and sampling is applied before persistence.
8. **Fence tokens are secrets.** A fence token must be unguessable (cryptographic
   randomness); a predictable fence would let a third party write as a live
   worker. Fence tokens are never logged.
9. **Denial of service.** Admission backpressure and bounded queues (Section
   11.10) prevent a Skill or subscriber from exhausting Executor memory.
   Force-abort after grace bounds a malicious Skill's hold on the system.

## 14. Performance Analysis

- **Hot path** (a successful short Execution): admission CAS + prepare (policy
  PEP + cached resolve/load) + one attempt + finalize (manifest commit + terminal
  CAS + event). The design keeps the number of *serial* durable operations
  small and makes policy the main potential serial bottleneck — mitigated by
  the decision cache (Section 4.3). Cached resolve/load keep cold-start skills
  off the hot path.
- **Streaming path:** frames are buffered and spooled in background; the Skill
  is never blocked on a slow Artifact write (bounded buffer + spill). Frame
  throughput is therefore bounded by spool throughput, not by Skill compute.
- **Telemetry:** batched emission; critical events are synchronous-durable
  (state transitions, failures), non-critical frames are asynchronous and
  sheddable. This keeps a 100k-frame Execution from costing 100k durable
  writes.
- **Determinism cost:** the decision cache and pinned policy version add a
  little memory and an invalidation protocol, but buy back replayability and
  testability that dominate in production debugging.
- **Achilles' heel:** per-Execution CAS serialization. All mutations to one
  Execution are CAS, i.e., serialized on that Execution's record. That is
  *correct* (single-writer) but means an Execution with a very hot state key
  (e.g., a fast counter) could contend. Mitigation: coalesce writes (Section
  11.10) and keep per-Execution write volume proportional to *meaningful
  transitions*, not to frames (frames go to the bus, not to state).

---

## 15. Scalability Analysis

Target: thousands of skills, thousands of artifacts, hundreds of concurrent
Executions. Analysis:

- **Thousands of skills:** resolution/loading are cached per digest; the
  Executor's per-skill state is O(1). No Executor data structure is O(#skills).
- **Thousands of artifacts:** per-Execution artifact namespaces prevent
  collision; artifact references in records are O(1) per Execution. The Artifact
  System itself must scale its namespace/index (its RFC's problem, flagged in
  Section 19). The Executor's manifest design means a terminal Execution is one
  ArtifactRef, so "thousands of artifacts" does not mean "thousands of
  references to chase."
- **Hundreds of concurrent Executions:** sharding by Execution ID gives
  per-shard isolation; a shard's working set is bounded by its in-flight
  Executions. Cross-Execution coordination is only (a) policy safety caps and
  (b) backpressure signals — both amortized, not per-Execution hot locks. The
  single shared system is the Event Bus (append-only, horizontally scalable by
  design) and Runtime State (key-partitioned by scope).
- **No global hot spots:** no central ID sequencer, no global registry, no
  global lock. The lease sweeper is the closest thing to a global actor and is
  trivially sharded (sweep disjoint key ranges).
- **Growth limits (honest):** per-Execution event volume scales with frames;
  the bus's per-Execution stream must be able to hold an Execution's full
  history or the Executor must bound and spill it (deterministic sampling +
  segment artifacts). Retention vs. recovery horizon is a real coupling
  (Sections 4.6, 19).

---

## 16. Concurrency Model

- **Actor-per-Execution.** Each in-flight Execution is driven by a single
  logical actor (state machine) within its owning worker. The actor owns its
  in-memory working state and is the *only* code path that mutates it. This
  eliminates locks within an Execution entirely.
- **Coordination only via CAS and the bus.** Actors never share memory and
  never call each other synchronously. Cross-Execution facts (child failure,
  cancellation cascade) travel as events; cross-worker facts (fencing) travel as
  lease CAS. This is the whole concurrency story: *actors + CAS + fences*.
- **Worker = thread pool + event loop.** Internally, a worker schedules actors
  over a bounded executor of tasks; blocking work (loading, spooling) is off the
  actor loop. The exact threading model is an implementation detail; the
  *specification* constraint is that no actor blocks another on shared memory.
- **Parallelism is structural, not ad hoc.** Parallelism arises from (a) many
  Executions owned across workers, (b) sibling steps of a Plan whose
  dependencies are satisfied, dispatched as independent Executions. The
  Executor never "discovers" parallelism inside a single Skill; a Skill that
  wants internal parallelism does it inside its own attempt.
- **Backpressure under concurrency:** admission budget per shard caps
  concurrent Executions; the stream credit system caps per-stream buffering.
  Neither requires a global lock (budgets are per-shard counters, eventually
  consistent under pressure).

## 17. Testing Strategy

The determinism envelope is the testing superpower; the test plan leans on it.

1. **State-machine conformance.** Exhaustive model tests: for every (state,
   event) pair, assert the transition (or that it is illegal). The state
   machines are small enough to enumerate. Property-based tests generate random
   event sequences and assert invariants 1–7 hold.
2. **Determinism replay.** Record a control-plane trace; re-execute the
   control plane against the replayed inputs (spec, state snapshots, policy
   snapshots, recorded clock) and assert bit-identical decisions. This is the
   single highest-value test: it proves the recovery and audit claims.
3. **Crash injection.** Kill workers at every durable-write point (between any
   two CAS/emit steps) and assert that recovery reaches a legal terminal state
   with no duplicated attempts and no lost records. Chaos-test the lease
   sweeper (split-brain attempt: two workers, one stale fence).
4. **Fault injection at boundaries.** Simulated Policy/Artifact/Bus outages
   (Section 12.3) assert fail-closed/fail-open behavior and that no terminal
   state is written before the manifest commits.
5. **Backpressure tests.** Saturated consumers, stalled skills, full admission
   budget: assert bounded memory, lossless spill, typed shed reasons, and that
   the Scheduler receives correct Hold signals.
6. **Cancellation/rollback matrix.** Every state × cancel; compensations that
   succeed, fail, loop, and are denied by policy. Assert RollbackRecord
   completeness and cleanup-always-runs.
7. **Scale tests.** Synthetic workload: thousands of skills, thousands of
   artifacts, hundreds of concurrent Executions across N shards; assert
   per-Execution latency distributions and that no component exhibits
   O(#skills) or O(#artifacts) behavior.
8. **Deterministic sampling test.** Assert sampling decisions are identical
   across replay and across workers (hash-derived).
9. **Compatibility conformance.** A suite that pins each RFC-0001…0007
   contract used here and fails loudly if a prior RFC changes semantics
   (guards against silent drift).

## 18. Tradeoff Analysis

The Executor's most consequential tradeoffs, collected:

1. **Determinism vs. flexibility.** Pinning policy versions and skill
   descriptors per Execution makes behavior replayable but means a running
   Execution cannot pick up a hotfix. *Chosen:* pin (auditability wins). A
   "rolling re-pin" would reintroduce non-determinism for marginal freshness.
2. **At-least-once attempts vs. exactly-once.** Claiming exactly-once would be
   dishonest without transactions; the Executor ships at-least-once +
   idempotency keys and says so. *Cost:* cooperating skills must dedupe.
   *Rejected:* best-effort exactly-once (worse than honest at-least-once).
3. **Compensation rollback vs. snapshot restore.** Snapshot restore (filesystem/
   state snapshot) is simpler for state but does not undo *external* side
   effects (an email sent, a charge made). Compensation undoes semantics but
   requires declared inverses. *Chosen:* compensation, with snapshot restore
   explicitly delegated to the Resource/Isolation RFCs where it belongs.
4. **Actor-per-Execution vs. shared worker pools.** Actors give correctness by
   construction but add scheduling overhead per Execution. *Chosen:* actors;
   the overhead is small and the correctness win (no shared-memory bugs) is
   large. *Weakness:* a single Execution's actor is single-threaded, so one
   pathological Execution cannot exploit many cores — acceptable, and internal
   Skill parallelism is the Skill's business.
5. **Single queue (Scheduler's) vs. Executor-side queueing.** A second queue
   in the Executor would duplicate prioritization logic and cause priority
   inversion between the two queues. *Chosen:* Executor holds (bounded) or runs;
   the Scheduler's queue is authoritative. *Cost:* the Executor depends on a
   responsive Scheduler for Hold/re-dispatch (coupling, Section 19).
6. **Event-driven cascade vs. synchronous cancellation.** Synchronous cascade
   is simpler to reason about but couples parent terminality to slow children.
   *Chosen:* event-driven cascade with `cascadeIncomplete` surfacing. *Cost:*
   the transient window where a parent is terminal but a descendant runs on.
7. **Bus as log vs. Runtime State as truth.** Two sources of truth is a
   classic bug farm. *Chosen:* Runtime State is authoritative "what is"; the bus
   is "what happened," and recovery reconciles the two with the bus strictly
   subordinate. *Cost:* recovery must handle bus/state divergence (Section
   11.8).

## 19. Compatibility Notes

These notes record where RFC-0008 depends on assumptions about, or discovers
latent issues in, prior RFCs. None of these change a prior RFC's contract; they
are requests for clarification or flagged extension points.

1. **Policy versioning (RFC-0003).** RFC-0008 requires a *versioned policy
   snapshot* identifier that can be pinned per Execution. If RFC-0003 does not
   define versioned snapshots, this is a required extension (additive, in a
   new field) — without it, determinism across policy changes is unattainable.
2. **Artifact namespace cardinality (RFC-0004).** One namespace per Execution
   implies the Artifact System must support a very large namespace count. If it
   does not, RFC-0008 falls back to bucketed namespaces (Section 11.2) at the
   cost of weaker isolation. Clarification requested.
3. **Bus retention vs. recovery horizon (RFC-0006).** Recovery prefers bus
   replay but *must* work from Runtime State + Artifacts when the bus has aged
   out an Execution's history. If RFC-0006 guarantees unbounded retention per
   Execution stream, recovery simplifies; otherwise recovery must not assume
   replay availability (this RFC already does not).
4. **Scheduler Hold semantics (RFC-0007).** `Hold(reason)` assumes the
   Scheduler can hold and later re-dispatch an Order without losing priority
   or violating its own ordering guarantees. If the Scheduler cannot hold,
   the Executor must instead buffer (bounded) and shed — a worse outcome that
   should be avoided by confirming the Scheduler's Hold contract.
5. **Skill manifest compensations (RFC-0002).** Rollback depends on declared
   inverses living in the Skill manifest. If RFC-0002's manifest does not have a
   slot for compensation declarations, that slot is a required additive
   extension (a new optional manifest section); skills without it are simply
   non-rollbackable.
6. **Per-Execution state subtree (RFC-0005).** RFC-0008 assumes Runtime State
   supports cheap per-key CAS and subtree namespacing. If CAS is only available
   at coarse granularity, per-Execution serialization will contend — an
   implementation must then use finer keys (per-record) which RFC-0008's data
   structures already anticipate.
7. **Non-change confirmation.** This RFC defines new event types, state keys,
   and artifact manifest media types in Executor-owned namespaces only. It does
   not redefine any event, key, or type owned by RFCs 0001–0007. Any
   unintentional overlap must be treated as a bug in this RFC.

## 20. Critical Self Review

Written adversarially, against this RFC.

1. **Compensation rollback is fundamentally leaky.** The Executor can only undo
   what skills declare. Real systems have side effects nobody declared an
   inverse for; the Executor will record the gap but cannot close it. A hostile
   reviewer will call rollback "audited best-effort, not rollback." That is
   *true*, and it is the honest limit of any non-transactional executor. The
   alternative — global transactions or mandatory snapshot isolation — is
   rejected because it would constrain skills so hard the system would be
   useless. This is a *documented* weakness, not a hidden one.
2. **The determinism envelope is narrower than it looks.** Wall-clock
   deadlines, NTP jumps, garbage-collection pauses, and the order in which the
   OS delivers signals are all outside the envelope. The envelope covers
   *control-plane decisions given recorded inputs*, which is the claim that
   matters for audit — but a reader expecting "the whole system is
   deterministic" will be disappointed. The RFC must keep repeating the scope
   of the claim.
3. **Actor-per-Execution caps single-Execution throughput.** One Execution's
   actor is single-threaded; a single enormous Skill cannot use many cores
   through the Executor. The design accepts this (internal parallelism is the
   Skill's concern), but it is a real scalability ceiling for "one giant
   execution," distinct from "many executions."
4. **Policy on the hot path is a latent availability risk.** Every attempt and
   retry decision consults policy. The cache mitigates but does not eliminate
   the coupling: a policy version flip during high traffic invalidates caches
   en masse and can produce a thundering herd against the Policy Engine. The
   RFC notes it but does not solve it; a future RFC (policy distribution) must.
5. **Event-driven cancellation has a correctness wrinkle.** A descendant can
   outlive its parent's terminal state (Section 11.6). The RFC surfaces
   `cascadeIncomplete` rather than fixing it, because fixing it (synchronous
   cascade) reintroduces deadlock risk. This is the right tradeoff but it is a
   real semantic gap for anyone assuming "cancelled parent ⇒ cancelled
   children."
6. **The lease sweeper is a disguised global actor.** Sharded, yes, but its
   correctness (fence monotonicity, clock skew) is the kind of distributed
   systems problem that generates subtle bugs for years. The RFC isolates it
   deliberately; that isolation is the only reason the rest of the design is
   simple.
7. **Backpressure is partially resource management in disguise.** The RFC draws
   the line at "signal, never allocate," but a hostile reviewer will note that
   admission budgets *are* resource decisions, just expressed as policy
   obligations. The RFC's defense is that the Executor never *allocates*
   physical resources — it only respects limits others set. The line will need
   revisiting when the Resource Management RFC lands.
8. **Failure classification is a policy decision dressed as an algorithm.** The
   taxonomy is fixed, but the *mapping* of real failures to kinds is
   judgment, and different operators will want different mappings. The RFC
   makes classification a pure function of inputs but does not make the
   mapping itself data-driven; that should become a policy hook (a future
   extension), or the taxonomy will ossify.
9. **This RFC is heavy.** The full lifecycle (journal, leases, PEPs,
   manifests, checkpoints) is a lot of machinery per Execution. For a
   one-shot, sub-millisecond skill, the control-plane overhead dominates. The
   design trades per-Execution cost for correctness and auditability at scale;
   a lightweight fast path (e.g., "fire-and-forget best-effort" executions
   that skip journals/leases) is an obvious future optimization that this RFC
   deliberately omits to keep one coherent contract.

Net: the design is correct-by-construction in the places that matter
(single-writer, durable-before-observable, typed failures) and honestly
documents the places it cannot be (undo, global determinism, physical
resources). That is the intended shape of a production control plane.

## 21. Future RFC Dependencies

RFCs that must exist for the Executor to reach its full intended posture, in
dependency order:

1. **Resource Management & Placement** — consumes the Executor's
   `Backpressure`/`RESOURCE_STARVED` signals; owns CPU/memory/IO quotas,
   worker pools, node placement, and physical isolation (cgroups/VM-class).
   Until it exists, the Executor's "isolation" is logical only, and its
   backpressure is signal-only.
2. **Secrets & Identity** — mints the short-lived, revocable CredentialHandles
   the Executor injects; revocation-on-cancel (Section 13.1) depends on it.
3. **Policy Distribution & Versioning** — the versioned policy snapshots and
   their efficient distribution/invalidation; relieves the thundering-herd risk
   (Section 20.4).
4. **Plan Teardown / Lifecycle Governance** — tightens the cancellation cascade
   guarantee (parent terminal ⇒ descendants terminal) that RFC-0008 only
   approximates.
5. **Checkpoint & Resume** — the optional transparent mid-skill resume that
   RFC-0008 explicitly deferred; depends on this RFC's checkpoint contract.
6. **Observability / Metrics** — the derived-metrics pipeline over this RFC's
   event log; the Executor emits, but does not aggregate, metrics.

## Appendix B — Design Decision Register

Each entry carries the five mandated analyses: alternatives, why rejected,
known weaknesses, hidden coupling, scalability risks. Decisions are the
*load-bearing* choices of this RFC; if one of them is reversed, the dependent
sections must be re-derived.

---

### D-1 — The Executor is a control plane that consumes immutable Orders and never re-schedules

**Decision.** The Scheduler owns the queue and the DAG; the Executor admits an
Order, runs it, or returns `Hold(reason)` so the Scheduler's queue remains the
single authoritative queue in the system. The Executor never reorders, never
re-plans, never promotes or demotes.

**Alternatives considered.** (a) The Executor keeps its own queue of Orders;
(b) the Executor may re-schedule work itself after failure; (c) merge Scheduler
and Executor into one component.

**Rejected because.** (a) A second queue duplicates prioritization logic and
creates priority inversion between two queues that disagree about ordering; (b)
re-scheduling in the Executor splits scheduling authority, so no single place
can reason about the global schedule; (c) merging couples planning latency to
execution's hot path and destroys the control-plane/data-plane separation this
RFC depends on.

**Known weaknesses.** The Executor is hostage to a responsive Scheduler for
`Hold` re-dispatch; if the Scheduler is slow, held Orders accumulate there. A
malformed-but-valid Order that the Scheduler keeps re-sending can bounce
between the two components; the admission hold timeout (Section 11.9) is the
only escape valve.

**Hidden coupling.** The `Hold`/re-dispatch protocol must preserve Scheduler
ordering and priority guarantees; if the Scheduler's re-dispatch drops priority
metadata, the Executor's shed decision silently demotes work. The backpressure
protocol is therefore an inter-RFC contract in all but name (Section 19.4).

**Scalability risks.** A single Scheduler becomes a fan-in point for all
`Hold`/`Reject` signals under load; signal volume is proportional to shed rate,
which can spike during a downstream outage. Mitigation: coalesce and batch
signals (Section 11.10), and never signal per-frame.

---

### D-2 — Durable-execution control plane; workers are reconstructible caches

**Decision.** Workers hold only a working-set cache of in-flight Executions. The
truth lives in Runtime State; a worker can crash and be replaced with no data
migration because a fresh worker rebuilds its shard from durable state.

**Alternatives considered.** (a) In-memory Executor with periodic snapshots;
(b) a per-Execution replicated consensus log (Raft/Paxos per Execution); (c)
pure event-sourcing with no materialized "current state."

**Rejected because.** (a) Loses in-flight work on crash and makes `Dispatch`
idempotency a client-side problem; (b) replicated consensus per Execution is
orders of magnitude too expensive — hundreds of Executions would each run a
quorum protocol, and the complexity budget explodes; (c) pure event-sourcing
forces a full replay to answer "what is the current state," which is
unacceptable on the hot path.

**Known weaknesses.** Every meaningful transition now costs at least one
durable CAS round-trip; there is a hard latency floor the Executor cannot
optimize below without violating invariant 4. The working-set cache can drift
from state if a watch is missed; reconciliation (Section 11.8) must be cheap
enough to run continuously.

**Hidden coupling.** The Executor's throughput ceiling is Runtime State's CAS
throughput and write latency. If RFC-0005's CAS is coarse-grained or slow, this
RFC's whole performance model degrades. This is a dependency the Executor
cannot paper over internally (Section 19.6).

**Scalability risks.** Write amplification: if implementers let telemetry or
stream frames leak into Runtime State, the state layer becomes the bottleneck.
The design's separation (frames → bus, facts → state) is load-bearing and must
be enforced by convention and review, since nothing in the data model
*prevents* a lazy implementation from storing everything in state.

---

### D-3 — Execution/Attempt split; at-least-once attempts, exactly-once bookkeeping

**Decision.** An Execution is the logical unit (1..N Attempts). Attempts are
physical runs. The Executor guarantees at-least-once attempt execution and
exactly-once bookkeeping, and supplies stable idempotency keys so cooperating
Skills can dedupe their own external side effects.

**Alternatives considered.** (a) Claim "exactly-once execution"; (b) no
Attempt concept — a retry is a brand-new Execution; (c) exactly-once via
distributed transactions.

**Rejected because.** (a)/(c) Exactly-once of arbitrary side effects requires
transactional coordination with every external system a Skill touches, which is
unachievable and would be a dishonest claim; (b) conflating the logical unit
with the physical run destroys the audit trail (which run actually happened?),
breaks idempotency-domain reasoning, and complicates rollback bookkeeping.

**Known weaknesses.** A non-cooperating Skill can double-apply side effects
across attempts and the Executor cannot detect it. The idempotency keys are an
*offer*, not a guarantee. Attempt Records grow with every retry and need a
retention story (teardown obligations, Section 11.11).

**Hidden coupling.** Exactly-once *bookkeeping* depends on Runtime State's CAS
being genuinely atomic per (Execution, Attempt) key. If RFC-0005's CAS has
eventual-consistency semantics anywhere, the exactly-once claim silently
degrades. The claim must be scoped to the state layer's actual guarantee.

**Scalability risks.** Retry storms multiply Attempt Records and bus events;
the bounded retry queue and shed policy (Section 11.10) are the only
containment. Idempotency-key derivation must be pure (hash of stable
identifiers) — any key that depends on wall-clock or random per-call state
breaks cross-attempt dedupe.

---

### D-4 — Parallelism comes from DAG dependencies and policy safety caps, never implicit resource limits

**Decision.** The Executor runs ready Plan steps concurrently and many
Executions concurrently, bounded only by (a) Plan dependencies and (b)
policy-expressed per-skill safety caps. It invents no parallelism and enforces
no physical resource limits.

**Alternatives considered.** (a) The Executor infers additional parallelism
(e.g., speculative fan-out); (b) the Executor enforces global concurrency
limits computed from available resources; (c) strict serial execution per Plan.

**Rejected because.** (a) Inferring parallelism is dangerous — Skill side
effects may have ordering constraints only the Plan (or the Skill author) knows,
so speculative fan-out risks correctness for throughput; (b) global
concurrency limits *are* resource management, explicitly deferred to a later
RFC — the Executor must not silently become the resource manager; (c) strict
serialism leaves throughput on the table and contradicts the "hundreds of
concurrent executions" target.

**Known weaknesses.** Nothing structurally prevents a single Plan from fanning
out to an unbounded number of concurrent Executions before policy caps converge.
Policy safety caps are eventually consistent (no global lock), so they can be
transiently oversubscribed.

**Hidden coupling.** The policy engine must be able to express concurrency caps
as obligations that multiple Executors enforce *cooperatively*. If policy caps
require strong global consistency, they pull a distributed-lock dependency back
into the Executor — exactly what D-13 was designed to avoid.

**Scalability risks.** Fan-out explosion (a Plan spawning thousands of steps)
is the canonical scalability failure; mitigation is the admission budget
(Section 11.10) applied at the Plan level, plus the Scheduler's own fan-out
controls (RFC-0007's responsibility, not the Executor's).

---

### D-5 — Cooperative, tree-scoped, escalating cancellation; forced abort is last-resort

**Decision.** Cancellation is cooperative-first: signal → grace period →
force-abort. It cascades down the causation tree via events. Force-abort is
recorded, human-visible, and forfeits rollback guarantees.

**Alternatives considered.** (a) Always preemptively kill; (b) cancellation is
just a flag with no escalation; (c) synchronous cascade (parent waits for every
descendant).

**Rejected because.** (a) Preemptive kill forfeits rollback in *every* case,
even when a Skill could have stopped cleanly; (b) flag-only cancellation can
hang forever on a Skill that never polls the flag — a known production
pathology; (c) synchronous cascade couples a parent's terminality to its slowest
descendant and reintroduces deadlock risk.

**Known weaknesses.** Force-abort forfeits rollback for anything the Skill did
not checkpoint — side effects can be left dangling, and the only record is the
`forceAbort` flag. The `cascadeIncomplete` window (parent terminal, descendant
still running) is a real semantic gap (Section 20.5).

**Hidden coupling.** Cancellation's *authority* (revoking a Skill's ability to
keep acting) depends on a credential system that can revoke handles
(Section 13.1) — a future RFC. Until then, a Skill holding credentials can keep
acting even after the Executor considers it cancelled; the Executor can stop
*asking*, but cannot stop *the Skill's already-granted* authority.

**Scalability risks.** Mass cancellation (plan teardown, root-cause cancel)
generates an event storm down the causation tree. The cascade must be
rate-limited and sharded, and descendants must be able to batch-acknowledge, or
a single root cancel becomes a bus DoS.

---

### D-6 — Policy-driven retries with a typed taxonomy and deterministic jitter

**Decision.** Retry decisions are a pure function of (failure classification,
policy snapshot, attempt count, remaining budget). Backoff is exponential with
jitter derived deterministically from (Execution ID, attempt).

**Alternatives considered.** (a) A fixed retry policy compiled into the
Executor; (b) Skill-declared retryability only; (c) exponential backoff with
random jitter.

**Rejected because.** (a) Fixed policy cannot adapt to different failure modes
or operators; (b) trusting Skills to declare retryability invites under-
declaration (and mis-declaration) of retryable failures; (c) random jitter
breaks the determinism envelope — retry timing becomes unreplayable and
untestable.

**Known weaknesses.** The taxonomy is fixed but the *mapping* from real
failures to kinds is judgment (Section 20.8); a wrong mapping retries a
permanent failure or fails fast on a transient one. Deterministic jitter
sacrifices the de-correlation property of random jitter across *different*
Executions that share an ID prefix (collisions are unlikely but not
impossible).

**Hidden coupling.** The retry path consults the Policy Engine (a PEP); its
availability and its notion of "retryable" must agree with the taxonomy, or the
Executor will retry what policy intended to block and vice versa. A version
flip mid-Execution is handled by pinning (D-12), but the retry PEP cache is
the hottest of the PEP caches.

**Scalability risks.** Retry storms (a shared backend flapping) can herd
thousands of Executions into synchronized retries; deterministic jitter
de-correlates within an Execution but not across Executions against a common
deadline. The bounded retry queue and shed-to-Scheduler path are the
containment.

---

### D-7 — Compensation-based rollback plus unconditional cleanup

**Decision.** Rollback executes declared inverses (compensations) in reverse
topological order, best-effort, bounded, and audited. Cleanup (locks, streams,
scratch) is unconditional and must not fail. There is no transaction, no
snapshot restore of external state.

**Alternatives considered.** (a) Snapshot restore; (b) no rollback at all —
failures are documented and left; (c) distributed transactions.

**Rejected because.** (a) Snapshot restore only rewinds *state the Executor
controls*; it does not undo an email sent or a charge made — the external side
effects are exactly the ones that matter; (b) no rollback is operationally
untenable at production scale (operators will hand-roll unsafe undos); (c)
transactions across arbitrary external systems are a non-starter and would
constrain every Skill to be transactional.

**Known weaknesses.** Undeclared inverses leave permanent gaps that only the
RollbackRecord reveals — the Executor cannot invent undo logic. A compensation
can itself fail or loop; it gets a tiny attempt budget precisely to avoid
loop-forever pathologies, which means some compensations simply won't complete.

**Hidden coupling.** Rollback depends on a compensation declaration slot in the
Skill manifest (RFC-0002); if that slot does not exist, it is a required
additive extension and Skills are non-rollbackable until adopted (Section 19.5).
Compensation Executions inherit the full lifecycle, so rollback transitively
depends on everything else in this RFC working.

**Scalability risks.** Cascading rollbacks (a Plan rollback fanning out
compensations) multiply Executions; the rollback budget bounds the fan-out but
must be enforced at the Plan level too, or one bad compensation chain consumes
the shard's admission budget.

---

### D-8 — Streams are first-class, persisted, check-pointed artifacts

**Decision.** A Skill's output is an ordered stream of framed, checksummed
records, persisted as segment Artifacts with checkpoints; consumers read live
or replayed; failure yields a `PARTIAL` result at the last checkpoint.

**Alternatives considered.** (a) Return-value-only invocation; (b) streaming
without persistence; (c) single-blob result assembled in memory.

**Rejected because.** (a) Return-value-only cannot represent long-running or
incremental output and forces buffering of unbounded results in memory; (b)
unpersisted streams are unreplayable and unauditable — a crash loses output
with no record; (c) single-blob results lose ordering, partial results, and
checkpoint semantics, and make large outputs a memory hazard.

**Known weaknesses.** Persisting every stream adds spooling overhead and
segment/checkpoint bookkeeping; a Skill that emits a firehose of trivial frames
pays a durability tax it may not need (mitigated by deterministic sampling and
coalescing). The stream state machine (Section 10.3) is the most intricate
sub-machine in the RFC.

**Hidden coupling.** Streaming depends on the Artifact System supporting
append/segment semantics and many namespaces (Section 19.2), and on the bus
supporting ordered per-Execution streams for live taps. If either primitive is
weak, the Executor must buffer more aggressively, weakening backpressure
guarantees.

**Scalability risks.** Frame volume is the dominant scaling term: a
100k-frame Execution should not cost 100k durable writes. Sampling, coalescing,
and background spooling (Section 14) are the controls; without them, stream
persistence becomes the system-wide bottleneck at hundreds of concurrent
Executions.

---

### D-9 — Layered timeouts on a single monotonic clock

**Decision.** Deadlines, per-attempt timeouts, stall timeouts, grace periods,
rollback budgets, and hold timeouts are all derived from one monotonic clock;
wall-clock is converted to monotonic at admission and used only for display.

**Alternatives considered.** (a) A single wall-clock deadline per Execution;
(b) per-attempt timeout only; (c) OS-level timers only.

**Rejected because.** (a) A single deadline cannot localize *where* time went
(slow Skill vs. stalled stream vs. starved Execution), and wall-clock jumps
(NTP) make deadlines unreliable; (b) per-attempt-only cannot catch a Skill
that runs forever without output (stall) — the classic silent hang; (c) OS
timers do not understand stream heartbeats or policy budgets.

**Known weaknesses.** Monotonic clocks do not survive host reboot consistently;
an Execution whose deadline was computed on a dead host must be recomputed
carefully on takeover (the lease fence handshake handles this, but it is a
subtle spot). Layer interactions (deadline shorter than a retry backoff) must
be resolved by a documented precedence order, or they produce confusing
`TIMED_OUT` causes.

**Hidden coupling.** Lease expiry and deadline expiry must share a clock basis
with Runtime State's lease primitive; if RFC-0005's leases use wall-clock while
the Executor uses monotonic, a clock jump can prematurely expire a live lease
or fail to expire a dead one.

**Scalability risks.** Per-stream stall timers × hundreds of Executions =
potentially hundreds of thousands of timers. Implementations must use
hierarchical/coalesced timer wheels; naive per-frame timer allocation is a
silent scalability failure.

---

### D-10 — Three-plane backpressure (admission, stream, internal)

**Decision.** Backpressure exists at three planes — admission (Hold/Reject to
the Scheduler), stream (credit-based flow control with lossless spill), and
internal (bounded queues with shed). No unbounded queue exists anywhere.

**Alternatives considered.** (a) Unbounded buffering; (b) blocking admission
(backpressure by blocking Scheduler calls); (c) a global token bucket.

**Rejected because.** (a) Unbounded buffering is how systems OOM under load; (b)
blocking admission couples Executor threads to Scheduler latency and can
deadlock the control loop; (c) a global token bucket is a central hot spot and
a single point of contention — it contradicts the sharding model.

**Known weaknesses.** Hold depends on Scheduler cooperation (D-1); spill adds
Artifact writes under load (more work exactly when the system is stressed);
shedding non-critical telemetry loses observability precisely during incidents
(critical frames are never shed, but "critical" is a judgment call).

**Hidden coupling.** The stream credit protocol is a cross-component contract
between the Executor, the Skill, and any subscriber; a consumer that never
returns credits stalls a stream, which is indistinguishable from a stalled
producer without careful instrumentation.

**Scalability risks.** Shed storms: under multi-shard overload, many shards
shed simultaneously, and the re-admission of shed work can oscillate with the
shedding (admission thrash). Hysteresis and exponential backoff on re-admission
are required; without them, overload produces oscillation rather than
degradation.

---

### D-11 — Logical isolation domains, fault containment, scoped credentials

**Decision.** Isolation is *logical*: per-Execution state/artifact/stream
namespaces, fault containment at the invocation boundary, scoped short-lived
credentials. Physical isolation (resource quotas, VM/cgroup class) is deferred.

**Alternatives considered.** (a) No isolation — shared everything; (b) full
physical isolation now (one sandbox per Execution).

**Rejected because.** (a) Shared everything gives one crashing or malicious
Skill the blast radius of the whole worker; (b) physical isolation is resource
management (the future RFC) and, done here, would have this RFC silently own
the resource budget it was told not to own.

**Known weaknesses.** Logical isolation cannot stop a noisy neighbor from
exhausting CPU/memory/IO — a runaway Skill degrades *all* co-located Executions
on a worker. This is the most visible cost of deferring resource management and
must be stated plainly rather than papered over.

**Hidden coupling.** Logical isolation's strength depends on namespaces being
*unforgeable* — derived from Execution IDs and allocated by the Executor, never
chosen by the Skill (Section 13.4). If any prior RFC lets clients pick their
own namespaces, the isolation is decorative.

**Scalability risks.** Namespace cardinality (one set per Execution) must be
cheap in Runtime State, the bus, and the Artifact System (Section 19.2).
Credential issuance per Execution must not require a synchronous vault
round-trip per attempt at scale; caching minted handles by scope is required.

---

### D-12 — Policy enforcement points with version-pinned, cached, deterministic decisions

**Decision.** The Executor consults the Policy Engine at seven named PEPs
(Section 6.5), pins a policy version per Execution at admission, caches
decisions by (policyVersion, decisionKey), and fails closed on authorization
PEPs.

**Alternatives considered.** (a) Consult policy live at every decision without
pinning; (b) consult policy only at admission; (c) bake policy checks into the
Executor's own code.

**Rejected because.** (a) Without pinning, a policy change mid-Execution makes
two identical Executions diverge — the determinism envelope collapses; (b)
admission-only cannot enforce mid-run obligations (redaction, rate caps) which
are a core security requirement; (c) baking policy into the Executor merges
mechanism and policy and guarantees they rot together.

**Known weaknesses.** A policy version flip invalidates caches mass-wide and
can produce a thundering herd against the Policy Engine (Section 20.4).
Fail-closed during a Policy outage denies legitimate work — an availability
risk that operators will pressure to weaken, and weakening it is how privilege
escalations happen.

**Hidden coupling.** The Executor assumes the Policy Engine exposes versioned
snapshots (Section 19.1). If policy changes are unversioned, the Executor can
only pin by copying the entire policy corpus per Execution — expensive and
possibly infeasible.

**Scalability risks.** Per-Execution decision caches consume memory
proportionally to in-flight Executions × decisions-per-Execution; cache
eviction must be deterministic (LRU on decisionKey) to preserve the determinism
envelope's *observable* behavior, and the cache stampede on invalidation is a
load spike the Policy Engine must survive.

---

### D-13 — Lease + fence single-writer ownership; command journal for idempotent control

**Decision.** Each Execution is owned by exactly one worker under a renewable
lease with an unguessable fence token; every write carries the fence and the
state layer rejects stale fences. Control commands are journaled per-Execution
and idempotent on command ID.

**Alternatives considered.** (a) Optimistic concurrency only, no leases; (b) a
central lock manager; (c) compare-and-swap without fencing.

**Rejected because.** (a) Optimistic concurrency detects lost updates but
cannot distinguish a *dead* owner from a *slow* owner, so a zombie worker can
write forever; (b) a central lock manager is a bottleneck and a single point of
failure, contradicting the sharding model; (c) CAS without fencing cannot
evict a stalled owner — you can CAS around it, but you cannot stop its future
writes, which is the split-brain.

**Known weaknesses.** Fence correctness depends on clock discipline and on the
state layer actually enforcing fences on *every* write (a single un-fenced
write path voids the guarantee). The lease sweeper is a disguised global actor
whose bugs (fence monotonicity, clock skew) will surface for years (Section
20.6).

**Hidden coupling.** The fence protocol assumes Runtime State can enforce
write-time fence checks; if it cannot, the Executor must emulate fencing by
checking leases on every read — a weaker, race-prone substitute. The command
journal assumes per-Execution ordered storage in Runtime State.

**Scalability risks.** Lease renewal is a per-Execution heartbeat write; at
hundreds of concurrent Executions, renewal volume must be batched per shard or
it consumes the state layer's write budget. Heartbeat period must be decoupled
from TTL (renew rarely, TTL long) to avoid renewal storms.

### D-14 — Telemetry as versioned, ordered, correlation-keyed events with deterministic sampling

**Decision.** All telemetry is a versioned event log on the bus with
(executionId, attemptId, causationId, spanId) correlation; metrics are derived
from the log; high-volume frames are sampled deterministically by hashing
(executionId, seq).

**Alternatives considered.** (a) A separate metrics pipeline (side-channel); (b)
unsampled full-frame logging; (c) opaque free-text logs.

**Rejected because.** (a) A side-channel metrics pipeline drifts from the audit
log — two views of the same Execution can disagree, which destroys forensic
trust; (b) unsampled frames are a cost explosion at scale (D-8's durability
tax multiplied by observability); (c) opaque logs are unreplayable and cannot
be reconstructed or correlated.

**Known weaknesses.** Sampling loses fidelity for rare-but-important frames
(the fix — critical frames are never sampled — is a judgment call about what
"critical" means). Derived metrics require replay computation, which is
eventually-consistent with the log and adds latency to dashboards.

**Hidden coupling.** Telemetry's value depends on bus retention (Section 19.3);
if the bus ages out an Execution's history, its metrics and audit trail are
gone unless segments are archived as Artifacts. Downstream consumers must be
idempotent on event id (bus is at-least-once).

**Scalability risks.** Event volume is the Executor's largest write term;
batching, sampling, and shedding non-critical frames are mandatory at hundreds
of concurrent Executions. The shed policy must never drop state-transition or
failure events, or invariant 5 (lossless failure) breaks silently.

---

### D-15 — Finalize = atomic result-set manifest commit, with partial results and teardown

**Decision.** Terminal state is written only after a manifest Artifact commits
the entire result set (result, stream segments, produced artifacts, logs,
failure record, partial checkpoint) into one content-addressed unit. Failure
yields `PARTIAL` results at the last durable checkpoint. Teardown obligations
run last.

**Alternatives considered.** (a) Finalize = set a status flag in Runtime State;
(b) commit each artifact independently, no manifest; (c) discard partial output
on failure.

**Rejected because.** (a) A bare flag leaves the outcome unaddressable — an
observer that sees `SUCCEEDED` cannot dereference a torn result set; (b)
per-artifact commits without a manifest let observers see a half-committed
Execution (some artifacts committed, some not) with no atomic point; (c)
discarding partials throws away usable, checkpointed work for no correctness
gain.

**Known weaknesses.** Finalize adds a hard dependency on the Artifact System at
the terminal transition; if it is down, the Execution stalls in `FINALIZING`
(Section 12.3) — correct, but operationally awkward. Large result sets make
large manifests; manifest commit time grows with result-set size.

**Hidden coupling.** The atomicity claim is exactly as strong as the Artifact
System's `Commit` primitive. If RFC-0004's commit is not truly atomic, the
Executor's "atomic finalize" claim silently degrades to best-effort, and
invariant 4 is weaker than advertised.

**Scalability risks.** Commit storms: a Plan completing fans out many
Executions finalizing simultaneously, each committing a manifest. The Artifact
System's commit throughput becomes the ceiling; the Executor can coalesce
small finalizes but cannot reduce the fundamental commit count.

## Appendix C — Telemetry Event Schema (skeleton)

Every event: `{ schemaVersion, executionId, attemptId?, causationId?, seq,
tsMonotonic, type, payload }`. Types: `execution.admitted`,
`execution.preparing`, `execution.running`, `attempt.started`,
`attempt.succeeded`, `attempt.failed`, `attempt.cancelled`,
`attempt.timed_out`, `execution.retry_scheduled`, `execution.rolling_back`,
`rollback.compensation_started|succeeded|failed|skipped`,
`execution.finalizing`, `execution.succeeded|failed|cancelled|denied|skipped|timed_out`,
`stream.frame` (sampled), `stream.checkpoint`, `stream.stalled`,
`stream.eos|aborted`, `command.ack|nack`, `lease.acquired|renewed|expired`,
`backpressure.hold|shed|credit`, `policy.denied|obligated`, `telemetry.shed`.

Metrics (derived): attempt counts, per-attempt latency, frames/bytes per stream,
stall frequency, rollback success rate, admission accept/hold/shed rates,
policy deny rate. Derived from the log; never stored separately.
