## 1. Executive Overview

RFC-0014 defines the **Learning Engine** for the AGY AI Operating System. The Learning Engine is the subsystem that translates accumulated observational evidence — produced by the Reflection Engine (RFC-0013), recorded in the Memory System (RFC-0010), and derived from execution metrics, policy outcomes, and decision journals — into durable improvements to how AGY plans, routes, selects skills, and invokes tools.

The Learning Engine sits at the terminus of AGY's feedback loop. Execution produces artifacts and metrics. The Reflection Engine analyzes them and produces structured observations, lessons, and calibration data. The Learning Engine consumes those outputs and produces **parameter updates** — precise, versioned, bounded mutations to the heuristic tables, routing weights, confidence calibration parameters, skill rankings, and planning strategies that govern AGY's future behavior. It is the mechanism by which the system gets better at its own job over time without human intervention for every improvement.

This is an extraordinarily dangerous responsibility. A learning system that updates its own governing parameters without safeguards is a system that can degrade itself systematically, converge on locally optimal but globally harmful strategies, and do so at machine speed. Every design decision in this RFC is shaped by this danger. The Learning Engine is therefore not just an optimizer — it is an **optimizer with a comprehensive governance framework** built into its architecture. Evidence thresholds before any update. Bounded magnitude of any single update. Mandatory validation before application. Human override at every level. Automatic rollback on degradation. Complete audit trails for every parameter change.

The Learning Engine does not modify accepted RFC contracts. It does not change the structure of Execution Graphs (RFC-0011). It does not change the Connector Interface (RFC-0012). It does not change the Policy Engine's evaluation model (RFC-0003). It does not change the Memory System's tier definitions (RFC-0010). What it changes are the **operational parameters** that exist within those contracts: the weights used to rank skills, the confidence coefficients used by the Planner's estimator, the routing preferences among equivalent tools, the heuristic scores attached to planning Methods, and the cache strategies applied to execution results. These parameters are first-class objects in the system — versioned, governance-controlled, and rollback-capable. Changing a parameter is not the same as changing a contract.

The architectural lineage here is deliberate. The Learning Engine is to AGY what the Linux kernel's scheduler tuning, TCP congestion control parameter adjustment, and JVM JIT profile-guided compilation are to their respective systems: a closed-loop adaptation mechanism that improves performance within a fixed, stable architectural contract. The architecture does not change. The parameters within it do.

## 2. Responsibilities

**Evidence Ingestion**
- Consuming Reflection Artifacts from RFC-0013 via the Event Bus (RFC-0006) and direct Artifact System reads (RFC-0004).
- Consuming execution metrics from the Scheduler (RFC-0007) execution records.
- Consuming policy outcome records from RFC-0003's decision log.
- Consuming Decision Journals: structured records of every decision made during planning and execution, with the alternatives considered and the outcomes observed.
- Consuming calibration observations written to RFC-0010 Reflection Memory by RFC-0013.
- Normalizing all inputs into a canonical Evidence Record format before analysis.

**Evidence Aggregation**
- Maintaining an Evidence Store: a durable, time-series-organized collection of normalized evidence records, indexed by evidence type, subject entity, and context tags.
- Aggregating evidence across multiple executions before making any update decision.
- Computing statistical summaries over evidence windows: means, variances, trends, outlier detection.
- Detecting when sufficient evidence has accumulated to warrant an update to a specific parameter.

**Parameter Update Generation**
- Computing proposed parameter updates based on aggregated evidence.
- Generating updates for seven parameter domains: heuristic tables, routing weights, planning improvements, skill rankings, cache strategies, model routing weights, and confidence calibration parameters.
- Bounding all proposed updates by maximum allowed magnitude per update cycle.
- Attaching evidence summaries and confidence scores to every proposed update.

**Validation**
- Validating every proposed parameter update against a defined Validation Suite before application.
- Running shadow mode evaluation: applying proposed parameters to historical execution records and computing predicted outcome improvements.
- Detecting proposed updates that would degrade performance rather than improve it.
- Requiring explicit approval for updates above a configurable magnitude threshold.

**Parameter Application**
- Applying validated parameter updates to the Parameter Store: the authoritative, versioned repository of all Learning Engine-managed parameters.
- Publishing parameter change events to the Event Bus (RFC-0006) so that consuming subsystems can reload their parameters.
- Maintaining a complete history of all parameter versions with evidence lineage.

**Rollback**
- Monitoring system performance metrics after each parameter update.
- Detecting post-update degradation through a defined degradation signal.
- Automatically rolling back parameter updates that produce detected degradation within a configurable monitoring window.
- Providing manual rollback for any parameter version.

**Audit and Governance**
- Maintaining a complete, immutable audit trail of every evidence record, every proposed update, every validation result, every application decision, and every rollback event.
- Producing governance reports that summarize learning activity for operator review.
- Supporting manual freeze: the ability to halt all learning activity for a specific parameter domain without affecting others.

## 3. Non-Goals

The following are explicitly outside the scope of RFC-0014:

- **Modifying accepted RFC contracts.** The Learning Engine updates parameters within existing contracts. It does not change interface definitions, data structure schemas, or behavioral contracts defined in any prior RFC.
- **Training machine learning models.** The Learning Engine updates structured parameters using statistical aggregation and rule-based update policies. It does not perform gradient descent, backpropagation, or any form of model weight training. Model training is a separate infrastructure concern.
- **Making real-time decisions.** The Learning Engine operates in the background. It reads evidence, proposes updates, validates them, and applies them on a schedule or event-driven trigger. It does not make decisions during execution.
- **Replacing human governance.** The Learning Engine automates parameter updates within defined bounds. Updates above defined magnitude thresholds require human approval. The Learning Engine provides recommendations, not mandates, for high-impact changes.
- **Implementing the Reflection Engine's analysis.** RFC-0013 produces the analysis. RFC-0014 acts on it. Analysis logic belongs in RFC-0013.
- **Managing model weights or fine-tuning.** Model adaptation (fine-tuning, RLHF, etc.) is a model infrastructure concern outside the kernel.
- **Handling cross-tenant learning.** Each tenant's parameters are learned independently. Cross-tenant learning (anonymized federation) is a future RFC concern.
- **Natural language interpretation of lessons.** Lessons from RFC-0013 are structured data. The Learning Engine processes them as such. NLP over lessons is not in scope.
- **Providing a user-facing learning dashboard.** Governance reports are structured data for operator tooling, not a UI specification.

## 4. Relationship to Previous RFCs

### RFC-0001: Skill Resolver

The Learning Engine does not call RFC-0001. However, it produces **Skill Ranking Updates** — versioned tables that score each `(skill_type, skill_version)` pair by observed reliability, latency, and goal-achievement quality. These tables are stored in the Parameter Store and read by RFC-0001 at skill resolution time. RFC-0001 must be amended to consult the Skill Ranking parameter table when multiple skill instances are eligible for a given task type.

**Interaction:** One-way. Learning Engine writes Skill Ranking parameters. RFC-0001 reads them. RFC-0001 does not call RFC-0014.

**Contract constraint:** RFC-0001's core resolution contract — resolve a `skill_type` to an available, policy-permitted skill instance — is unchanged. The Skill Ranking table provides a preference ordering among eligible candidates; it does not override eligibility or policy decisions. A skill with a low ranking that is the only available instance for a task type is still resolved and dispatched.

### RFC-0002: Skill Registry & Loader

The Learning Engine reads skill manifests from RFC-0002 to understand what declared behavior each skill claims. Declared behavior is the baseline against which observed behavior (from RFC-0013) is compared. The Learning Engine does not write to RFC-0002. It does not modify skill manifests, skill versions, or skill registrations.

**Interaction:** Read-only. The Learning Engine reads declared behavioral metadata (`expected_latency_range`, `expected_reliability`, `cost_tier`) from RFC-0002 manifests when computing expectation deltas and generating `SKILL_MANIFEST_INACCURACY` recommendations. RFC-0002 does not call RFC-0014.

### RFC-0003: Policy Engine

The Learning Engine is policy-gated for its own operations. Parameter updates are sensitive operations that require policy authorization. Additionally, the Learning Engine produces **Policy Outcome Observations**: structured analyses of how RFC-0003 policy decisions correlated with execution quality. These observations are written to RFC-0010 Reflection Memory for human review and potential policy amendment — the Learning Engine never directly modifies policy rules.

**Interaction:** The Learning Engine calls RFC-0003 for authorization of parameter update operations. It reads RFC-0003 decision logs (as evidence inputs). It writes policy observations to RFC-0010 for human consumption. It never writes to RFC-0003 directly.

**New policy attributes required:** RFC-0003 must support `learning.*` policy attributes: `learning.parameter_domain`, `learning.update_magnitude`, `learning.requires_approval`. These define which identities can apply which classes of parameter updates.

### RFC-0004: Artifact System

The Learning Engine reads Reflection Artifacts from RFC-0004 as its primary evidence source. It writes three categories of Artifacts:

1. **Evidence Aggregation Artifacts:** Snapshots of aggregated evidence for a parameter domain over a time window. Immutable once written. These are the input audit trail.
2. **Parameter Update Proposals:** Proposed parameter updates with evidence summaries, confidence scores, and validation results. Immutable once written.
3. **Parameter Snapshots:** Point-in-time captures of the full Parameter Store. Used for rollback and governance.

All Learning Engine Artifacts carry lineage linking them to the Reflection Artifacts and execution records they were derived from.

**Interaction:** Bidirectional. Learning Engine reads Reflection Artifacts. Learning Engine writes Evidence Aggregation Artifacts, Parameter Update Proposals, and Parameter Snapshots. It never modifies existing Artifacts.

### RFC-0005: Runtime State

The Learning Engine does not interact with live RFC-0005 state. It reads execution context information from execution records (finalized snapshots of Runtime State) that are persisted as part of the Scheduler's execution record Artifacts.

**Interaction:** Indirect. Evidence records derived from execution records include context fields (tenant_id, project_type, goal_type) that the Learning Engine uses for context-specific parameter segmentation.

### RFC-0006: Event Bus

The Learning Engine is both a subscriber and publisher.

**As subscriber:**
- `reflection.completed` — primary trigger for evidence ingestion.
- `reflection.lesson.extracted` — immediate evidence signal for high-confidence lessons.
- `reflection.confidence.recalibration.completed` — triggers calibration update processing.
- `scheduler.execution.completed` — ingests execution metrics directly.
- `policy.updated` — triggers re-evaluation of policy observations.
- `learning.parameter.manual_rollback_requested` — external rollback trigger.
- `learning.parameter.freeze_requested` — external freeze trigger.

**As publisher:**
- `learning.evidence.ingested`
- `learning.update.proposed`
- `learning.update.validated`
- `learning.update.applied`
- `learning.update.rejected`
- `learning.update.rolled_back`
- `learning.parameter.frozen`
- `learning.parameter.thawed`
- `learning.governance.report_generated`

### RFC-0007: Scheduler

The Scheduler drives Learning Engine background jobs and provides execution metrics as evidence inputs.

The Learning Engine registers background jobs with RFC-0007:
- **Evidence ingestion sweep:** Poll RFC-0004 for new Reflection Artifacts not yet processed (configurable; default: every 5 minutes). Belt-and-suspenders for missed Event Bus triggers.
- **Evidence aggregation job:** Aggregate accumulated evidence across all parameter domains (configurable; default: every hour).
- **Update generation job:** Generate proposed parameter updates from aggregated evidence (configurable; default: every 6 hours).
- **Validation and application job:** Validate and apply approved proposed updates (configurable; default: every 12 hours, or on explicit trigger).
- **Degradation monitoring job:** Monitor post-update metrics (configurable; default: every 15 minutes for 48 hours after each update).
- **Governance report job:** Generate periodic governance reports (configurable; default: weekly).

**Interaction:** Learning Engine reads Scheduler execution record Artifacts from RFC-0004. Learning Engine registers background jobs with RFC-0007. RFC-0007 does not call RFC-0014.

### RFC-0010: Memory System

RFC-0010 is the Learning Engine's primary read channel for lesson data and the secondary write channel for learning observations.

**Reading:**
- Reflection Memory tier: all lessons produced by RFC-0013, including skill reliability observations, tool performance observations, planning heuristic observations, estimation calibration observations, and failure pattern observations.
- Semantic Memory tier: domain knowledge that provides context for interpreting lessons.

**Writing:**
- Reflection Memory tier: learning parameter update observations — records of what was changed, why, and with what outcome. These feed future Reflection Engine analysis.
- Episodic Memory tier: brief summaries of each learning cycle for temporal querying.

**Interaction:** Bidirectional. Heavy reader of RFC-0010 Reflection Memory. Selective writer of learning cycle summaries and parameter update records.

### RFC-0011: Planner

The Planner is the primary consumer of Learning Engine outputs. The Learning Engine produces updates to:
- **Confidence calibration parameters:** The coefficients used by RFC-0011's Cost and Confidence Estimator to translate evidence into confidence scores.
- **Method priority scores:** The ranking weights applied by RFC-0011's Method Selector to determine which Method to try first for a given abstract task type.
- **Planning heuristic parameters:** Configurable thresholds in the Planner (e.g., `GROUPING_WINDOW`, `MIN_GROUP_SIZE`) that govern decomposition behavior.

All of these are parameters within RFC-0011's existing architecture. The Learning Engine changes their values; it does not change how the Planner uses them.

**Interaction:** Learning Engine writes to the Parameter Store. RFC-0011 reads from the Parameter Store at planning session initialization (parameter pinning). RFC-0011 does not call RFC-0014.

**Critical integration note:** RFC-0011 must implement parameter hot-reloading: when a `learning.update.applied` event is published for the `PLANNER` parameter domain, RFC-0011 must reload its parameters from the Parameter Store before the next planning session. If RFC-0011 pins parameters at planning session start (as specified in RFC-0011 Section 18.4), the new parameters take effect for all planning sessions started after the reload.

### RFC-0012: Tool Runtime

The Learning Engine produces updates to:
- **Tool routing weights:** The capability selector scores (RFC-0012 Section 11.1) that determine which tool is preferred for a given capability when multiple tools are available.
- **Retry policy parameters:** Configurable parameters governing retry behavior (backoff coefficients, retry eligibility thresholds) within RFC-0012's Retry Engine.
- **Connection pool sizing recommendations:** Non-binding recommendations for connection pool configuration per tool binding.

**Interaction:** Learning Engine writes Tool Routing Weight updates to the Parameter Store. RFC-0012's Capability Selector reads from the Parameter Store when computing tool selection scores. RFC-0012 does not call RFC-0014.

### RFC-0013: Reflection Engine

RFC-0013 is the Learning Engine's upstream data producer. Every Reflection Artifact, every lesson, and every calibration observation produced by RFC-0013 is a potential input to RFC-0014. The interface between them is the Reflection Artifact schema and the RFC-0010 Reflection Memory lesson schema, both defined in RFC-0013.

**Interaction:** RFC-0013 writes Reflection Artifacts to RFC-0004 and lessons to RFC-0010. RFC-0014 reads both. RFC-0013 does not call RFC-0014. RFC-0014 does not call RFC-0013.

**Schema coupling:** The Learning Engine's evidence normalization depends on the exact structure of RFC-0013's `ReflectionArtifact`, `Lesson`, and `CalibrationObservation` schemas. Any breaking change to these schemas in RFC-0013 requires a corresponding update to RFC-0014's evidence normalizer. This coupling must be managed through versioned schema references.

## 5. Architecture

### 5.1 Architectural Philosophy

The Learning Engine is built on one overriding principle: **no parameter changes without evidence, validation, and audit**. This principle manifests in three architectural invariants:

**Invariant 1: Separation of evidence accumulation from parameter application.** Evidence is collected continuously. Parameters are updated infrequently, on a schedule, after accumulation thresholds are met. These two activities happen in separate phases with a validation gate between them. A system that updates parameters in response to every new evidence record is a system that thrashes — oscillating between local optima and never converging. A system that updates parameters only after accumulation produces stable, evidence-grounded improvements.

**Invariant 2: All parameter changes are bounded, versioned, and reversible.** No single learning cycle can change any parameter by more than a configured maximum magnitude. Every parameter state is versioned. Every prior version is retained. Any version can be restored. This makes learning safe: the worst case is a bad update that gets rolled back, not a catastrophic drift into an unrecoverable state.

**Invariant 3: The Parameter Store is the single source of truth for all Learning Engine-managed parameters.** Consuming subsystems (RFC-0001, RFC-0011, RFC-0012) read their learning-influenced parameters from the Parameter Store, not from internal configuration files. The Parameter Store is the interface between the Learning Engine and the rest of the system. This boundary is what allows the Learning Engine to change parameters without modifying RFC contracts.

## 6. Internal Components

### 6.1 Evidence Ingestion Bus

The Evidence Ingestion Bus is the entry point for all external evidence. It is a multiplexed consumer that receives evidence from multiple sources, normalizes it into a canonical `EvidenceRecord` format, and writes it to the Evidence Store.

**Sources:**

1. **Reflection Artifacts (RFC-0013 → RFC-0004):** The primary source. Every Reflection Artifact contains lessons, quality scores, decision scores, calibration observations, and failure analyses. The Ingestion Bus reads new Reflection Artifacts by subscribing to `reflection.completed` events and fetching the artifact from RFC-0004.

2. **Execution Metrics (RFC-0007 → RFC-0004):** Scheduler execution records provide task-level timing, resource consumption, retry counts, and completion status. These feed the Heuristic Updater and Skill Ranking Updater directly without waiting for Reflection Artifact generation.

3. **Policy Outcomes (RFC-0003 decision log → RFC-0004):** Policy Engine decision records, aggregated and written periodically to RFC-0004, provide a time series of policy decisions and their contexts. These feed the Policy Outcome Analyzer.

4. **Decision Journals:** Structured records of every decision made during planning (RFC-0011) and tool routing (RFC-0012), with the alternatives considered and the actual outcomes. Decision Journals are produced by RFC-0011 and RFC-0012 as part of their Plan Artifacts and InvocationRecords respectively.

**Normalization:** Every evidence record is normalized to `EvidenceRecord` regardless of source. Normalization extracts: evidence type, subject entity (skill_id, tool_id, method_id, etc.), context tags, observed value, metric type, timestamp, source artifact reference, and confidence. Evidence records are immutable once written to the Evidence Store.

**Deduplication:** Evidence records carry a `source_artifact_ref` and a `source_position` (e.g., "lesson_3 in reflection R-abc123"). If the same position in the same artifact is ingested twice (e.g., due to duplicate Event Bus delivery), the duplicate is silently discarded. Deduplication is by `hash(source_artifact_ref, source_position)`.

### 6.2 Evidence Store

The Evidence Store is the Learning Engine's private, durable repository of normalized evidence. It is not shared with other subsystems. It is owned by and written exclusively by the Learning Engine.

**Structure:**
- **Raw Evidence Log:** Append-only, time-ordered log of all ingested `EvidenceRecord` entries. The log is the canonical source; all derived structures are computed from it.
- **Entity Index:** An index mapping `(entity_type, entity_id)` → `[EvidenceRecord IDs]`. Enables efficient retrieval of all evidence for a specific skill, tool, or method.
- **Type Index:** An index mapping `evidence_type` → `[EvidenceRecord IDs]`. Enables efficient retrieval of all evidence of a specific type.
- **Aggregation Windows:** Pre-computed statistical summaries over configurable time windows (default windows: 24 hours, 7 days, 30 days). Aggregation windows are recomputed by the Evidence Aggregation background job (RFC-0007, hourly).
- **Staleness Tracker:** Records the last evidence timestamp for each `(entity_type, entity_id)` pair. Entities with no recent evidence trigger staleness warnings, which may cause their parameters to revert toward defaults.

**Evidence retention:** Evidence records are retained for a configurable period (default: 90 days). After expiry, raw evidence records are archived to RFC-0004 (as compressed Evidence Archive Artifacts) and removed from the hot Evidence Store. Aggregation Window summaries are retained longer (default: 1 year) as they are much smaller than raw records.

**Evidence completeness:** The Evidence Store tracks, per `(entity_type, entity_id)`, how many executions have contributed evidence. An entity with 3 evidence records has very different statistical confidence than one with 300. Evidence completeness is a first-class attribute of every aggregation window.

### 6.3 Update Generation Layer

The Update Generation Layer contains seven specialized Updaters, one per parameter domain. Each Updater:
- Reads aggregated evidence from the Evidence Store for its domain.
- Applies domain-specific update algorithms to compute proposed parameter changes.
- Produces a `ParameterUpdateProposal` containing: the proposed new parameter values, the delta from current values, the evidence basis, the confidence score, and the expected impact estimate.
- Does not apply the proposal — proposals go to the Validation Engine.

**Common Updater contract:**

```
UPDATER CONTRACT:

read_evidence(domain: ParameterDomain, window: TimeWindow)
  → AggregatedEvidence

compute_proposal(evidence: AggregatedEvidence,
                 current_params: ParameterSet,
                 constraints: UpdateConstraints)
  → ParameterUpdateProposal | NO_UPDATE_NEEDED

required_evidence_threshold(domain: ParameterDomain) → EvidenceThreshold
  // Minimum evidence required before a proposal is generated.
  // Below threshold: no proposal is generated; evidence accumulates.
```

**Updater isolation:** Each Updater operates on its own parameter domain. An Updater for Routing Weights cannot read or write parameters in the Skill Rankings domain. Domain boundaries are enforced by the Parameter Store's access control, not by convention.

#### 6.3.1 Heuristic Table Updater

Manages the planning heuristic parameters used by RFC-0011: Method priority scores, task-type-specific decomposition preferences, and context-sensitive planning thresholds.

**Evidence consumed:**
- `PLANNING_HEURISTIC_OBSERVATION` lessons from RFC-0013 (which Method tends to produce better outcomes for which goal types).
- Plan quality dimension scores from RFC-0013 quality scorecards, specifically `plan_quality` and `execution_efficiency`.
- Architectural critique findings: false dependency rates, parallelism utilization rates, replanning event counts.

**Update logic:**
- If a Method M consistently produces better outcomes than Method M' for goal type G (based on accumulated `PLANNING_HEURISTIC_OBSERVATION` lessons), M's priority score for goal type G is increased and M's priority score is decreased. The magnitude of adjustment is proportional to the confidence and sample count of the observation.
- If the replanning event rate for a specific goal type exceeds a threshold, the planning heuristics for that goal type are flagged for structural review — but the Heuristic Updater does not automatically adjust them (replanning events suggest planning problems that require architectural diagnosis, not parameter tweaking).

#### 6.3.2 Routing Weight Updater

Manages the tool routing weights used by RFC-0012's Capability Selector. For each `(capability_name, context_tag_set)` pair where multiple tools are registered, the Routing Weight Updater maintains a preference weight for each tool.

**Evidence consumed:**
- `TOOL_PERFORMANCE_OBSERVATION` lessons from RFC-0013: success rate, latency, cost per tool per capability.
- InvocationRecord aggregates: actual error class distributions, retry rates, and throughput per tool.
- Contract violation events: tools with recent contract violations receive a reliability penalty.

**Update logic (see Algorithm 11.3):** The routing weight for a tool is a function of its observed success rate, its observed latency relative to the capability's latency distribution, its cost tier, and any recent contract violations. Weights are normalized across all tools for a capability so that they sum to 1.0 (they function as probability weights in the Capability Selector, though the Capability Selector uses them as scoring factors, not strict probabilities).

#### 6.3.3 Planning Parameter Updater

Manages configurable threshold parameters within RFC-0011's Planner: `max_backtrack_depth`, `MIN_SUMMARY_TOKENS` (used by RFC-0010's compression engine, but initialized from Planner configuration), `GROUPING_WINDOW` for consolidation, and `MIN_GROUP_SIZE`.

**Evidence consumed:**
- Backtrack count statistics from Plan Artifacts: if the mean backtrack count across executions exceeds a threshold, `max_backtrack_depth` may need adjustment.
- Consolidation effectiveness metrics from RFC-0010's Consolidator: if consolidation groups are systematically too small, `MIN_GROUP_SIZE` should be reduced.
- Estimation calibration observations: systematic bias in latency estimation feeds the `latency_bias_correction_factor` parameter.

**Update conservatism:** Planning Parameter updates have the tightest magnitude bounds of all domains (maximum 10% change per update cycle) because these parameters affect the Planner's structural behavior. A poorly-tuned `max_backtrack_depth` can cause either missed valid plans (too low) or exponential planning time (too high). Changes are graduated and closely monitored.

#### 6.3.4 Skill Ranking Updater

Manages the skill ranking tables read by RFC-0001's Skill Resolver. The ranking table maps `(skill_type, skill_version, context_tag_set)` → `RankingScore`.

**Evidence consumed:**
- `SKILL_RELIABILITY_OBSERVATION` lessons from RFC-0013: success rate, latency, quality score contributions per skill type and version.
- Goal achievement dimension scores from quality scorecards: broken down by skill type where attributable.
- Decision scores from RFC-0013: when Decision Scorer identifies `WRONG_ALTERNATIVE_SELECTED` for skill selection decisions, the alternative's ranking is increased relative to the chosen skill.

**Update logic:**
- `RankingScore = w_reliability × success_rate + w_latency × (1/normalized_latency) + w_quality × quality_contribution`
- Default weights: reliability=0.5, latency=0.3, quality=0.2.
- Ranking scores are bounded [0.1, 1.0]. No skill is ranked to zero (which would effectively remove it from consideration, a more drastic action requiring human authorization).

**Version-aware ranking:** Skill rankings are tracked per `skill_version`. When a new version of a skill is released, it inherits the prior version's ranking as a starting point, with a configurable "new version discount" (default: -0.1) until sufficient evidence for the new version accumulates.

#### 6.3.5 Cache Strategy Updater

Manages parameters governing the Memory System's (RFC-0010) caching behavior: TTL values for different memory tier entries, consolidation frequency thresholds, and access-frequency decay rates.

**Evidence consumed:**
- Memory access pattern records: which memory entries are frequently accessed, which are rarely accessed, what the hit rates are for different TTL values.
- Consolidation effectiveness metrics: are consolidated entries accessed more or less than their source entries? (If less, consolidation is discarding useful detail.)
- Token budget utilization: how often are memory queries hitting the token budget limit? (Suggests TTL or retrieval scope adjustments.)

**Update conservatism:** Cache Strategy updates are applied only after very long evidence windows (default: 30 days) because cache behavior depends on workload patterns that vary seasonally and cyclically. A 7-day spike in access patterns should not permanently change cache TTLs.

#### 6.3.6 Model Routing Weight Updater

Manages the model selection weights that govern which AI model is selected for a given task type, token budget, and latency requirement. These weights are consumed by RFC-0008 and/or RFC-0009 (the model routing subsystems, whose specific architecture is treated as accepted and immutable).

**Evidence consumed:**
- Model performance observations: per-model latency, error rate, output quality assessments (where available through RFC-0013's quality scoring).
- Token cost observations: actual token consumption per model per task type.
- Goal achievement correlations: do executions using model M for task type T achieve goals at a higher rate than executions using model M'?

**Update constraint:** Model routing weight updates have a special constraint: they may not result in any single model having a routing weight of 0.0 for any task type for which it is the only available model. This prevents the Learning Engine from effectively deregistering a model through weight decay.

#### 6.3.7 Confidence Calibration Updater

Manages the confidence calibration coefficients used by RFC-0011's Cost and Confidence Estimator. These coefficients are the most directly tied to RFC-0013's calibration observations.

**Evidence consumed:**
- `ESTIMATION_CALIBRATION_OBSERVATION` lessons from RFC-0013: per-skill-type, per-metric calibration errors.
- Calibration reports generated by RFC-0013's periodic calibration report job.
- Trend data from the Evidence Store: is calibration error increasing, decreasing, or stable?

**Update logic (see Algorithm 11.2):** For each `(skill_type, metric)` pair with sufficient calibration observations, compute a correction factor: `correction = -mean_calibration_error × learning_rate`. Apply the correction to the current coefficient, bounded by `max_coefficient_change_per_cycle`.

**Why calibration is the most frequent domain:** Calibration observations are generated per-execution by RFC-0013. Evidence accumulates rapidly. Calibration drift — where plan-time estimates systematically diverge from actual outcomes — compounds if not corrected frequently. The 6-hour update cycle for calibration reflects this urgency relative to other domains.

### 6.4 Validation Engine

The Validation Engine is the quality gate between proposed parameter updates and their application. Every `ParameterUpdateProposal` passes through the Validation Engine before reaching the Parameter Store. The Validation Engine can: approve a proposal unchanged, approve with modifications (reduced magnitude), conditionally approve (requiring human confirmation), or reject.

**Validation stages:**

**Stage 1: Schema Validation**
Verify that the proposed parameter values conform to the type schema for their domain. A routing weight that is negative, a ranking score above 1.0, or a calibration coefficient of NaN fails schema validation and is rejected immediately.

**Stage 2: Bound Checking**
Verify that the magnitude of the proposed change does not exceed the maximum allowed magnitude for this domain in this update cycle. Magnitude is measured as the L∞ norm of the change vector across all parameters in the domain.

```
magnitude = max(|proposed_value[i] - current_value[i]| / range[i]
               for all parameters i in domain)

IF magnitude > MAX_UPDATE_MAGNITUDE[domain]:
  IF magnitude <= MAX_UPDATE_MAGNITUDE[domain] × APPROVAL_MULTIPLIER:
    proposal.status = REQUIRES_APPROVAL
  ELSE:
    proposal.status = REJECTED (magnitude too large even with approval)
```

Default `MAX_UPDATE_MAGNITUDE` values by domain:
- Heuristics: 0.15 (15% of parameter range per cycle)
- Routing Weights: 0.20
- Planning Parameters: 0.10
- Skill Rankings: 0.15
- Cache Strategies: 0.10
- Model Routing: 0.15
- Confidence Calibration: 0.20

**Stage 3: Conflict Detection**
Check whether this proposal conflicts with another proposal applied in the past N hours (configurable; default: 24 hours). Conflicts occur when two proposals modify the same parameter in opposite directions. Conflicting proposals are flagged for human review rather than automatically resolved — automated conflict resolution risks oscillation.

**Stage 4: Shadow Evaluation**
Apply the proposed parameters to a shadow copy of the Parameter Store. Replay the last N execution records (configurable; default: 100) through the affected subsystem's logic using the proposed parameters. Compare predicted outcomes against actual outcomes using the baseline parameters.

```
shadow_quality_delta = mean(shadow_predicted_outcome - baseline_predicted_outcome)
  for all replayed executions

IF shadow_quality_delta < SHADOW_REGRESSION_THRESHOLD (default: -0.05):
  proposal.status = SHADOW_REGRESSION_DETECTED
  proposal.shadow_analysis = ShadowAnalysis(delta, regression_details)
  // Proposal is not automatically rejected; human review is triggered.
  // But automatic application is blocked.
```

Shadow evaluation is the most computationally expensive validation stage. It is performed asynchronously; proposals wait in a `PENDING_SHADOW_EVALUATION` state during this phase.

**Stage 5: Approval Gate**
Proposals with status `REQUIRES_APPROVAL` are queued in the Approval Queue. Human operators (or an authorized automation system) review and approve or reject them via the `ApplyUpdate` interface with explicit approval metadata. Proposals remain in the Approval Queue for a configurable period (default: 7 days) before auto-rejection.

**Validation outcome codes:**

```
ValidationOutcome {
  APPROVED              // Apply immediately.
  APPROVED_WITH_REDUCTION // Approved at reduced magnitude.
  REQUIRES_APPROVAL     // Human approval required.
  SHADOW_REGRESSION_DETECTED // Shadow evaluation found regression.
  CONFLICT_DETECTED     // Conflicts with recent update.
  SCHEMA_INVALID        // Parameter values fail schema.
  BOUND_EXCEEDED        // Magnitude exceeds absolute maximum.
  INSUFFICIENT_EVIDENCE // Evidence below threshold at validation time.
  DOMAIN_FROZEN         // Domain is currently frozen.
}
```

### 6.5 Parameter Store

The Parameter Store is the authoritative repository of all Learning Engine-managed parameters. It is the boundary between the Learning Engine and the rest of the system. Consuming subsystems read from the Parameter Store; they do not read from the Learning Engine directly.

**Structure:**

```
ParameterStore {
  // Current values for all parameter domains
  current_parameters: map<ParameterDomain, ParameterSet>

  // Complete version history
  parameter_versions: map<ParameterDomain, [ParameterVersion]>
    // Ordered newest-first.
    // ParameterVersion includes: version_id, applied_at, applied_by,
    //   proposal_id, parameter_snapshot, evidence_artifact_ref.

  // Change log (append-only)
  change_log: [ParameterChangeRecord]

  // Freeze state
  frozen_domains: set<ParameterDomain>
  freeze_records: [FreezeRecord]

  // Rollback state
  active_rollback_monitors: [RollbackMonitor]
}
```

**Parameter Store access control:**
- The Learning Engine's Validation Engine is the only writer to `current_parameters`.
- All other subsystems have read-only access to `current_parameters`.
- The version history and change log are append-only; no entry is ever deleted.
- Read access to the Parameter Store is policy-gated (RFC-0003): operators can read all domains; skills can read only the parameters relevant to their execution context.

**Parameter hot-reloading protocol:**
When the Learning Engine applies a parameter update, it:
1. Writes the new parameter values to `current_parameters`.
2. Appends to the change log.
3. Publishes a `learning.update.applied` event to RFC-0006 with the domain and a change summary.
4. Consuming subsystems receive the event and reload their domain-relevant parameters on their next natural reload boundary (planning session start, scheduling cycle start, etc.).

Consuming subsystems do not need to poll. The event-driven reload is sufficient for the Learning Engine's update frequency (hours between updates).

### 6.6 Degradation Monitor

The Degradation Monitor watches system performance metrics after each parameter update and automatically triggers rollback if degradation is detected.

**Monitoring period:** Configurable per domain (default: 48 hours after any update to that domain). During the monitoring period, the Degradation Monitor samples relevant metrics at the Scheduler's monitoring job interval (default: every 15 minutes).

**Degradation signals per domain:**

```
DegradationSignals {
  HEURISTICS:
    - Mean plan quality score decreases by > 10% compared to pre-update baseline.
    - Replanning event rate increases by > 20%.
    - Mean planning latency increases by > 30%.

  ROUTING_WEIGHTS:
    - Mean tool invocation success rate decreases by > 5%.
    - Mean tool invocation latency increases by > 25%.
    - TOOL_INTERNAL_ERROR rate increases by > 15%.

  PLANNING_PARAMETERS:
    - Backtrack limit exceeded rate increases by > 10%.
    - Planning failure rate increases by > 5%.

  SKILL_RANKINGS:
    - Mean goal achievement score decreases by > 10%.
    - Task execution failure rate increases by > 10%.

  CACHE_STRATEGIES:
    - Memory retrieval latency increases by > 50%.
    - Cache hit rate decreases by > 15%.

  MODEL_ROUTING:
    - Mean execution quality score decreases by > 8%.
    - Model error rate increases by > 10%.

  CONFIDENCE_CALIBRATION:
    - Mean absolute calibration error increases by > 0.05.
    - Planner overconfidence rate increases by > 20%.
}
```

**Degradation detection algorithm:**
```
FOR EACH monitoring_sample IN monitoring_period:
  compute current_metrics(domain)
  compare against pre_update_baseline(domain)
  FOR EACH signal IN DegradationSignals[domain]:
    IF signal.threshold_exceeded(current_metrics, pre_update_baseline):
      signal_count[signal]++

  IF any signal_count[signal] >= CONSECUTIVE_THRESHOLD (default: 3):
    // Signal has been exceeded in 3 consecutive samples.
    trigger_rollback(domain, signal)
```

**Automatic rollback:** On triggered rollback, the Degradation Monitor restores the prior version of the domain's parameters from the version history. It publishes `learning.update.rolled_back` with the rollback reason and evidence. The rolled-back proposal is marked `ROLLED_BACK` in the change log and is ineligible for re-application without human review.

### 6.7 Governance Controller

The Governance Controller manages the Learning Engine's operational policies: freeze/thaw, approval queue management, governance report generation, and audit log access.

**Freeze semantics:** When a domain is frozen:
- Evidence continues to be ingested and accumulated.
- Update proposals continue to be generated and stored.
- No proposals are applied to the Parameter Store.
- Shadow evaluation continues (proposals accumulate validation status).
- On thaw: all accumulated, approved proposals are reviewed in chronological order before application. The Governance Controller does not automatically apply all accumulated proposals; human review of the accumulated queue is required.

**Approval queue management:** The Governance Controller maintains the approval queue for `REQUIRES_APPROVAL` proposals. It provides the public `ApplyUpdate` interface that authorized identities use to approve or reject queued proposals. Approved proposals are forwarded to Stage 5+ of the Validation Engine.

**Governance reports:** Generated weekly (RFC-0007 scheduled job). Contents:
- Summary of evidence ingested per domain.
- Summary of proposals generated, approved, rejected, rolled back.
- Current parameter values with delta from 30-day-prior values.
- Domains with active rollback monitoring.
- Domains with pending proposals in the approval queue.
- Domains with active freezes.
- Evidence staleness warnings.

## 9. Runtime Lifecycle

### 9.1 System Startup

```
1. Learning Engine loads configuration.
2. Policy Gate initializes.
3. Parameter Store loads current parameters from durable storage.
   - If no persisted state: initialize all domains to default parameters.
   - Verify all domain schemas against current RFC definitions.
   - Flag any schema mismatches as PARAMETER_SCHEMA_MISMATCH warnings.
4. Evidence Store loads index structures (raw log is on disk; indexes are in memory).
5. Resumption of in-progress operations:
   - Resume pending shadow evaluations (idempotent: re-run from scratch).
   - Restore active RollbackMonitors from persisted state.
   - Load Approval Queue from persisted state.
6. Governance Controller initializes frozen domain state.
7. RFC-0006 Event Bus subscriptions registered.
8. Background jobs registered with RFC-0007 Scheduler.
9. Degradation Monitor resumes active monitoring periods.
10. learning.engine.ready event published.
```

### 9.2 Evidence Ingestion Lifecycle

```
[reflection.completed event received]
1. Extract reflection_artifact_ref from event payload.
2. Fetch Reflection Artifact from RFC-0004.
3. Extract all lessons from Reflection Artifact.
4. For each lesson:
   a. Normalize to EvidenceRecord.
   b. Compute dedup_key.
   c. Check dedup_key against Evidence Store.
   d. If duplicate: discard. If new: write to Evidence Store.
5. Extract execution metrics from linked Scheduler records.
6. Normalize execution metrics to EvidenceRecord entries.
7. Check entity evidence thresholds:
   FOR EACH entity updated in this ingestion:
     IF entity.evidence_count >= domain.update_threshold:
       Mark entity as THRESHOLD_MET in Evidence Store.
8. Publish learning.evidence.ingested event with summary.
```

### 9.3 Update Generation Lifecycle

```
[Update generation job triggered by RFC-0007 Scheduler]
1. For each non-frozen ParameterDomain:
   a. Read AggregatedEvidence for all entities in this domain
      (using 7-day aggregation window as primary; 30-day as secondary).
   b. Filter entities: only those with evidence_count >= domain.update_threshold.
   c. Call domain Updater.compute_proposal(evidence, current_params, constraints).
   d. If Updater returns NO_UPDATE_NEEDED: skip this domain.
   e. If Updater returns a ParameterUpdateProposal:
      i.  Persist proposal to Proposal Store.
      ii. Write proposal as Artifact to RFC-0004.
      iii. Submit to Validation Engine.
      iv. Publish learning.update.proposed event.
2. Log update generation cycle completion to RFC-0010 Episodic Memory.
```

### 9.4 Validation Lifecycle

```
[ParameterUpdateProposal submitted to Validation Engine]
1. Stage 1: Schema Validation (synchronous; < 100ms).
   - On INVALID: reject immediately.
2. Stage 2: Bound Checking (synchronous; < 10ms).
   - On EXCEEDED:
     - If magnitude <= MAX × APPROVAL_MULTIPLIER: mark REQUIRES_APPROVAL.
     - Else: reject.
3. Stage 3: Conflict Detection (synchronous; < 500ms).
   - On CONFLICT: mark CONFLICT_DETECTED; queue for human review.
4. Stage 4: Shadow Evaluation (asynchronous; minutes to hours depending on load).
   - On SHADOW_REGRESSION_DETECTED: mark accordingly; do not auto-apply.
   - On SHADOW_PASSED: mark APPROVED or REQUIRES_APPROVAL (per magnitude).
5. Stage 5: Approval Gate (if REQUIRES_APPROVAL).
   - Sits in Approval Queue until approved, rejected, or expired.
6. On APPROVED: submit to Parameter Store for application.
7. Publish learning.update.validated event with outcome.
```

### 9.5 Parameter Application Lifecycle

```
[APPROVED proposal submitted to Parameter Store]
1. Record pre-application baseline metrics for all DegradationSignals[domain].
2. Apply proposed parameters to current_parameters[domain].
3. Append ParameterVersion to version history.
4. Append ParameterChangeRecord to change log.
5. Create RollbackMonitor for this domain.
   - monitoring_start = now()
   - monitoring_end = now() + monitoring_duration[domain]
   - pre_update_baseline = recorded baseline metrics
6. Write ParameterSnapshot Artifact to RFC-0004.
7. Publish learning.update.applied event with:
   - domain
   - version_id
   - parameter_delta_summary
   - rollback_monitor_id
8. Consuming subsystems receive event and schedule parameter reload.
9. Write learning cycle record to RFC-0010 Reflection Memory.
```

### 9.6 Rollback Lifecycle

```
[Degradation signal triggered OR manual rollback requested]
1. Identify the domain and the version to restore (prior version by default).
2. Policy gate: is this identity authorized to rollback this domain?
   (For auto-rollback: Degradation Monitor operates with system identity
    which has rollback authorization for all domains.)
3. If emergency=false: validate that target version is schema-compatible.
4. Restore prior_version.parameter_snapshot to current_parameters[domain].
5. Append ROLLBACK ParameterVersion to history.
6. Append ROLLBACK ParameterChangeRecord to change log.
7. Mark rolled-back proposal as ROLLED_BACK.
8. Terminate active RollbackMonitor for this domain
   (replace with new monitor for the restored version).
9. Write ParameterSnapshot Artifact for restored state to RFC-0004.
10. Publish learning.update.rolled_back event with:
    - domain
    - rolled_back_version
    - restored_version
    - reason (signal type for auto-rollback; manual note for manual rollback)
11. Consuming subsystems receive event and reload parameters.
```

## 11. Algorithms

### 11.1 Evidence Threshold Algorithm

Before an Updater generates a proposal, it must verify that sufficient evidence has accumulated. Insufficient evidence produces unstable parameter updates that may degrade performance.

```
PROCEDURE check_evidence_threshold(domain: ParameterDomain,
                                    entity_id: string,
                                    evidence: AggregatedEvidence)
                                    → ThresholdResult:

  thresholds = EVIDENCE_THRESHOLDS[domain]

  // Minimum sample count
  IF evidence.sample_count < thresholds.min_samples:
    RETURN ThresholdResult(
      MET=false,
      reason="Insufficient samples",
      current=evidence.sample_count,
      required=thresholds.min_samples
    )

  // Minimum time coverage
  time_coverage = evidence.window.end - evidence.window.start
  IF time_coverage < thresholds.min_time_coverage:
    RETURN ThresholdResult(MET=false, reason="Insufficient time coverage")

  // Minimum evidence completeness
  IF evidence.evidence_completeness < thresholds.min_completeness:
    RETURN ThresholdResult(MET=false, reason="Incomplete evidence")

  // Minimum confidence in key metrics
  FOR EACH required_metric IN thresholds.required_metrics:
    IF required_metric NOT IN evidence.metrics:
      RETURN ThresholdResult(MET=false, reason=f"Missing metric: {required_metric}")
    IF evidence.metrics[required_metric].trend == INSUFFICIENT_DATA:
      RETURN ThresholdResult(MET=false, reason=f"Insufficient data for trend: {required_metric}")

  RETURN ThresholdResult(MET=true)

EVIDENCE_THRESHOLDS = {
  HEURISTICS:             { min_samples: 20, min_time_coverage: 48h, min_completeness: 0.7 }
  ROUTING_WEIGHTS:        { min_samples: 50, min_time_coverage: 24h, min_completeness: 0.8 }
  PLANNING_PARAMETERS:    { min_samples: 30, min_time_coverage: 72h, min_completeness: 0.75 }
  SKILL_RANKINGS:         { min_samples: 15, min_time_coverage: 24h, min_completeness: 0.7 }
  CACHE_STRATEGIES:       { min_samples: 100, min_time_coverage: 720h, min_completeness: 0.9 }
  MODEL_ROUTING:          { min_samples: 30, min_time_coverage: 48h, min_completeness: 0.75 }
  CONFIDENCE_CALIBRATION: { min_samples: 25, min_time_coverage: 24h, min_completeness: 0.8 }
}
```

### 11.2 Confidence Calibration Update Algorithm

This is the most precisely specified update algorithm because calibration correctness is measurable and directly feeds back into RFC-0011's planning quality.

```
PROCEDURE compute_calibration_update(
    aggregated_evidence: AggregatedEvidence,
    current_params: ConfidenceCalibrationParameters,
    constraints: UpdateConstraints) → ParameterUpdateProposal:

  proposed = deep_copy(current_params)
  deltas = {}

  FOR EACH skill_type IN aggregated_evidence.entities:
    FOR EACH metric IN [LATENCY, TOKEN_COST, CONFIDENCE, RESOURCE_USAGE]:

      obs_key = (skill_type, metric)
      IF obs_key NOT IN aggregated_evidence.metrics:
        CONTINUE

      agg = aggregated_evidence.metrics[obs_key]

      // Mean calibration error (positive = overconfident; negative = underconfident)
      mean_error = agg.mean  // mean of (planned - actual) across samples

      IF abs(mean_error) < CALIBRATION_CORRECTION_THRESHOLD (default: 0.05):
        CONTINUE  // Within acceptable tolerance; no update needed.

      // Compute correction
      learning_rate = CALIBRATION_LEARNING_RATE[metric]  // default: 0.3
      correction = -mean_error × learning_rate

      current_correction = current_params.skill_type_corrections
        .get(skill_type, {})
        .get(metric, 1.0)

      proposed_correction = current_correction + correction

      // Bound correction to reasonable range
      proposed_correction = clamp(proposed_correction,
                                   MIN_CORRECTION (default: 0.3),
                                   MAX_CORRECTION (default: 3.0))

      // Compute delta
      delta = proposed_correction - current_correction

      // Apply per-update magnitude bound
      IF abs(delta) > constraints.max_delta_per_cycle:
        delta = sign(delta) × constraints.max_delta_per_cycle
        proposed_correction = current_correction + delta

      proposed.skill_type_corrections[skill_type][metric] = proposed_correction
      deltas[obs_key] = ParameterDelta(
        current_value = current_correction,
        proposed_value = proposed_correction,
        delta = delta,
        reason = f"Mean calibration error: {mean_error:.3f} over {agg.sample_count} samples"
      )

  IF deltas is empty:
    RETURN NO_UPDATE_NEEDED

  RETURN ParameterUpdateProposal(
    domain = CONFIDENCE_CALIBRATION,
    proposed_parameters = proposed,
    parameter_deltas = deltas,
    proposal_confidence = compute_confidence(aggregated_evidence),
    expected_quality_delta = estimate_quality_delta(deltas, aggregated_evidence)
  )
```

### 11.3 Routing Weight Update Algorithm

```
PROCEDURE compute_routing_weight_update(
    aggregated_evidence: AggregatedEvidence,
    current_params: RoutingWeightParameters,
    constraints: UpdateConstraints) → ParameterUpdateProposal:

  proposed = deep_copy(current_params)
  deltas = {}

  FOR EACH capability_name IN aggregated_evidence.capabilities:
    tools = aggregated_evidence.tools_for_capability(capability_name)

    IF len(tools) < 2:
      CONTINUE  // Only one tool; no routing decision to optimize.

    tool_scores = {}

    FOR EACH tool_id IN tools:
      agg = aggregated_evidence.get_tool_evidence(tool_id, capability_name)

      IF agg.sample_count < EVIDENCE_THRESHOLDS.ROUTING_WEIGHTS.min_samples:
        tool_scores[tool_id] = current_params.tool_weights[capability_name][tool_id]
          // Insufficient evidence: retain current weight.
        CONTINUE

      success_rate = agg.metrics["success_rate"].mean
      latency_p50 = agg.metrics["latency_p50_ms"].mean
      cost_score = COST_TIER_SCORES[agg.metrics["cost_tier"].mode]

      // Has this tool had recent contract violations?
      violation_penalty = 0.0
      IF agg.metrics.get("recent_contract_violations", 0) > 0:
        violation_penalty = 0.2

      // Raw score (higher = better)
      raw_score = (
        0.5 × success_rate +
        0.3 × (1.0 / normalized_latency(latency_p50, capability_name)) +
        0.2 × cost_score
      ) - violation_penalty

      tool_scores[tool_id] = max(raw_score, current_params.weight_floor)

    // Normalize to sum 1.0
    total = sum(tool_scores.values())
    normalized_scores = {tid: s/total for tid, s in tool_scores.items()}

    // Compute incremental update (blend current weight with new score)
    BLEND_FACTOR = 0.3  // 30% toward new score per cycle; avoids sharp transitions
    FOR EACH tool_id IN tools:
      current_weight = current_params.tool_weights
        .get(capability_name, {}).get(tool_id, 1.0/len(tools))
      new_weight = (1.0 - BLEND_FACTOR) × current_weight +
                    BLEND_FACTOR × normalized_scores[tool_id]

      // Bound delta
      delta = new_weight - current_weight
      IF abs(delta) > constraints.max_delta_per_cycle:
        new_weight = current_weight + sign(delta) × constraints.max_delta_per_cycle

      proposed.tool_weights[capability_name][tool_id] = new_weight
      deltas[(capability_name, tool_id)] = ParameterDelta(
        current_value = current_weight,
        proposed_value = new_weight,
        delta = new_weight - current_weight,
        reason = f"Evidence: success_rate={success_rate:.3f}, "
                 f"latency={latency_p50:.0f}ms, violations={violation_penalty}"
      )

    // Re-normalize after bounding to ensure sum = 1.0
    normalize_in_place(proposed.tool_weights[capability_name])

  IF deltas is empty:
    RETURN NO_UPDATE_NEEDED

  RETURN ParameterUpdateProposal(domain=ROUTING_WEIGHTS, ...)
```

### 11.4 Skill Ranking Update Algorithm

```
PROCEDURE compute_skill_ranking_update(
    aggregated_evidence: AggregatedEvidence,
    current_params: SkillRankingParameters,
    constraints: UpdateConstraints) → ParameterUpdateProposal:

  proposed = deep_copy(current_params)
  deltas = {}
  weights = current_params.ranking_weights

  FOR EACH (skill_type, skill_version) IN aggregated_evidence.skills:
    agg = aggregated_evidence.get_skill_evidence(skill_type, skill_version)

    IF agg.sample_count < EVIDENCE_THRESHOLDS.SKILL_RANKINGS.min_samples:
      CONTINUE

    success_rate = agg.metrics["success_rate"].mean
    latency_p50 = agg.metrics["latency_p50_ms"].mean
    quality_contribution = agg.metrics.get("quality_contribution", {}).mean

    // Normalize latency to [0,1]: lower is better
    normalized_lat = 1.0 - clamp(
      latency_p50 / SKILL_LATENCY_REFERENCE[skill_type],
      0.0, 1.0
    )

    new_score = (
      weights.reliability_weight × success_rate +
      weights.latency_weight    × normalized_lat +
      weights.quality_weight    × quality_contribution
    )

    // Clamp to [0.1, 1.0]: never fully exclude a skill via ranking
    new_score = clamp(new_score, 0.1, 1.0)

    // Context-specific rankings
    FOR EACH context_tag IN agg.context_breakdown.keys():
      ctx_agg = agg.context_breakdown[context_tag]
      IF ctx_agg.sample_count >= MIN_CONTEXT_SAMPLES (default: 10):
        ctx_score = compute_context_score(ctx_agg, weights)
        proposed.rankings[skill_type][skill_version][context_tag] = ctx_score

    // Global ranking (no context)
    current_score = current_params.rankings
      .get(skill_type, {}).get(skill_version, {}).get("*", 0.5)

    // Incremental update
    BLEND_FACTOR = 0.25
    blended_score = (1.0 - BLEND_FACTOR) × current_score + BLEND_FACTOR × new_score
    blended_score = clamp(blended_score, 0.1, 1.0)

    proposed.rankings[skill_type][skill_version]["*"] = blended_score
    deltas[(skill_type, skill_version)] = ParameterDelta(
      current_value = current_score,
      proposed_value = blended_score,
      delta = blended_score - current_score,
      reason = f"success_rate={success_rate:.3f}, samples={agg.sample_count}"
    )

  IF deltas is empty:
    RETURN NO_UPDATE_NEEDED

  RETURN ParameterUpdateProposal(domain=SKILL_RANKINGS, ...)
```

### 11.5 Shadow Evaluation Algorithm

```
PROCEDURE shadow_evaluate(proposal: ParameterUpdateProposal,
                           historical_executions: [ExecutionRecord],
                           baseline_params: ParameterSet) → ShadowAnalysis:

  shadow_params = apply_proposal(baseline_params, proposal)
  baseline_outcomes = []
  shadow_outcomes = []

  FOR EACH execution IN historical_executions:
    // Compute predicted quality score under baseline parameters
    baseline_predicted = predict_quality(execution, baseline_params)
    // Compute predicted quality score under shadow parameters
    shadow_predicted = predict_quality(execution, shadow_params)

    baseline_outcomes.append(baseline_predicted)
    shadow_outcomes.append(shadow_predicted)

  mean_baseline = mean(baseline_outcomes)
  mean_shadow = mean(shadow_outcomes)
  delta = mean_shadow - mean_baseline

  // Distribution analysis
  improved_count = count(s > b for s, b in zip(shadow_outcomes, baseline_outcomes))
  degraded_count = count(s < b for s, b in zip(shadow_outcomes, baseline_outcomes))
  unchanged_count = len(historical_executions) - improved_count - degraded_count

  // Regression check
  worst_case_delta = min(s - b for s, b in zip(shadow_outcomes, baseline_outcomes))

  regression_detected = (
    delta < SHADOW_REGRESSION_THRESHOLD OR
    worst_case_delta < SHADOW_WORST_CASE_THRESHOLD
  )

  RETURN ShadowAnalysis(
    mean_quality_delta = delta,
    improved_count = improved_count,
    degraded_count = degraded_count,
    unchanged_count = unchanged_count,
    worst_case_delta = worst_case_delta,
    regression_detected = regression_detected,
    executions_evaluated = len(historical_executions)
  )

PROCEDURE predict_quality(execution: ExecutionRecord,
                           params: ParameterSet) → float:
  // Applies the parameters to the execution's decision points
  // and estimates the quality outcome.
  // For routing decisions: replace actual tool weights with proposal weights,
  //   estimate whether the selected tool would have been the same or different.
  // For calibration: re-estimate plan confidence with new coefficients,
  //   assess whether the replanning threshold would have changed.
  // This is a lightweight simulation, not a full re-execution.
  // Accuracy is bounded; this is an estimation of direction, not magnitude.
```

### 11.6 Staleness Reversion Algorithm

```
PROCEDURE handle_stale_entities(evidence_store: EvidenceStore,
                                  current_params: ParameterStore):

  staleness_period = STALENESS_PERIOD (default: 30 days)
  reversion_period = staleness_period × 2

  FOR EACH entity IN evidence_store.entities_by_last_seen:
    age = now() - entity.last_evidence_at

    IF age > reversion_period:
      // Entity has been absent for too long.
      // Its parameters may reflect conditions that no longer apply.
      // Revert to defaults gradually.

      current_score = current_params.get_entity_score(entity)
      default_score = DEFAULT_PARAMETERS.get_entity_score(entity)

      IF current_score == default_score:
        CONTINUE  // Already at default; nothing to do.

      // Compute reversion step: move 20% toward default per staleness cycle
      REVERSION_RATE = 0.20
      new_score = current_score + REVERSION_RATE × (default_score - current_score)

      // Generate a STALENESS_REVERSION proposal
      proposal = ParameterUpdateProposal(
        domain = entity.domain,
        proposed_parameters = update_entity_score(current_params, entity, new_score),
        proposal_type = AUTOMATED,
        reason = f"Stale entity reversion: no evidence for {age.days} days"
      )
      // Staleness reversion proposals skip shadow evaluation
      // (no evidence to shadow against) but still require bound checking.
      submit_for_validation(proposal, skip_shadow=true)

    ELIF age > staleness_period:
      // Warn but do not act yet.
      publish_staleness_warning(entity)
```

## 12. Failure Recovery

### 12.1 Failure Classification

| Failure | Impact | Recovery |
|---|---|---|
| Evidence ingestion failure (RFC-0004 unavailable) | Evidence gaps | Evidence ingestion sweep job retries; gap is logged and reported in governance report |
| Evidence Store write failure | Evidence lost | Write-ahead log ensures at-most-once loss; next ingestion resumes from WAL |
| Shadow evaluation timeout | Proposal stuck in PENDING_SHADOW_EVALUATION | After configurable timeout (default: 2 hours), proposal is marked SHADOW_TIMEOUT and requires manual review |
| Parameter Store write failure | Update not applied | Retry with exponential backoff; on persistent failure, alert operator; parameters remain at prior version |
| Parameter Store read failure (by consuming subsystem) | Consuming subsystem cannot load updated params | Consuming subsystem falls back to its prior cached parameters; alerts operator |
| RFC-0006 event delivery failure | Consuming subsystem not notified of parameter update | Evidence ingestion sweep provides eventual consistency; consuming subsystems should also poll Parameter Store periodically as belt-and-suspenders |
| Degradation Monitor failure | Degradation not detected | Alert operator; rollback monitoring is safety-critical; manual monitoring required until recovered |
| Policy Engine unavailable | Parameter updates cannot be authorized | Fail-closed: no updates applied; queue proposals for retry when PE recovers |
| RFC-0013 schema change | Evidence normalization fails | Evidence records that cannot be normalized are quarantined; Learning Engine continues with prior evidence; quarantined records trigger schema mismatch alert |

### 12.2 Recovery from Bad Parameter Update

The most important failure recovery scenario is when a parameter update degrades system performance and must be rolled back.

**Auto-rollback path (Degradation Monitor):** Described in Section 6.6 and Section 9.6. Automatic for clear, signal-exceeding degradation within the monitoring window.

**Manual rollback path (operator-initiated):**
```
1. Operator observes degradation (through external monitoring or governance report).
2. Operator calls Rollback(domain, target_version, reason).
3. Rollback immediately restores prior parameters.
4. Consuming subsystems reload via event.
5. ParameterChangeRecord type=ROLLBACK written.
6. Rolled-back proposal marked ROLLED_BACK in proposal history.
7. Evidence that drove the rolled-back proposal is not deleted —
   it remains in the Evidence Store but is flagged as contributing
   to a rolled-back proposal. Future update proposals for the same
   domain will weight this evidence more cautiously.
```

**Evidence quarantine after rollback:** If a proposal is rolled back, the Learning Engine quarantines the evidence that drove it for a configurable period (default: 72 hours). During quarantine, that evidence is excluded from new aggregation computations. This prevents the system from immediately re-generating the same bad proposal from the same evidence.

### 12.3 Bootstrap Recovery

If the Parameter Store is lost entirely (e.g., storage failure with no valid snapshot):

```
1. Initialize all domains to hardcoded DEFAULT_PARAMETERS.
2. Alert operator: "Parameter Store recovered from defaults."
3. Resume evidence ingestion normally.
4. Evidence accumulated before the loss is still in the Evidence Store
   (or in Evidence Archive Artifacts in RFC-0004).
5. Re-ingest available evidence from RFC-0004 Evidence Archive Artifacts.
6. Re-run update generation over re-ingested evidence.
7. Apply updates normally (with validation and approval gates).
```

This recovery path means that losing the Parameter Store loses accumulated parameter tuning but not the evidence that drove it. The evidence can be re-processed to recover the parameters, subject to the normal evidence threshold and validation requirements. This is a lossy recovery (recent context-specific tuning may not be recoverable) but a safe one.

## 13. Security Considerations

### 13.1 Threat Model

**Threats specific to the Learning Engine:**

1. **Parameter poisoning via evidence manipulation:** An attacker who can manipulate Reflection Artifact content or execution records can cause the Learning Engine to generate bad parameter proposals (e.g., routing all traffic to a malicious tool by manipulating its performance observations).

2. **Unauthorized parameter modification:** An attacker with access to the Parameter Store write path could bypass the Learning Engine's governance and apply arbitrary parameter values directly.

3. **Learning rate exploitation:** By carefully timing executions to flood the Evidence Store with specific evidence, an attacker could accelerate parameter updates beyond what the magnitude bounds would normally allow (by accumulating threshold-meeting evidence rapidly).

4. **Rollback manipulation:** An attacker who can trigger rollbacks could use the rollback mechanism to revert to known-vulnerable parameter states.

5. **Governance report manipulation:** Falsifying governance reports to hide evidence of learning anomalies from human operators.

6. **Shadow evaluation gaming:** Crafting historical execution records such that the shadow evaluation incorrectly approves a harmful proposal.

### 13.2 Defense Mechanisms

**Evidence provenance verification:** Every `EvidenceRecord` carries a `source_artifact_ref` pointing to the Reflection Artifact or execution record it was derived from. The Evidence Normalizer verifies that the source Artifact exists in RFC-0004 and that its content hash matches. Evidence records from source Artifacts with broken or tampered hashes are rejected.

**Magnitude bounds as absolute limits:** The magnitude bounds (Section 6.4 Stage 2) are enforced as hard limits that cannot be overridden by evidence volume. Even if an attacker floods the Evidence Store with millions of evidence records, the parameter update per cycle cannot exceed the configured maximum. Flooding wastes attacker effort but cannot bypass bounds.

**Time-windowed evidence:** Evidence aggregation uses fixed time windows (24h, 7d, 30d). Flooding the Evidence Store with evidence from a single short burst does not increase the weight of that burst beyond its proportional contribution to the time window. A burst that constitutes 80% of evidence in a 24h window contributes only 1/30 of the evidence in the 30d window.

**Parameter Store write isolation:** The Parameter Store's write path is accessible only to the Learning Engine's Validation Engine component. No external interface allows direct writes to `current_parameters`. This is enforced at the policy level (RFC-0003) and at the architectural level (no public `WriteParameters` interface exists).

**Rollback authorization:** Rollbacks require explicit policy authorization. Auto-rollback (by Degradation Monitor) is performed under a constrained system identity that can only restore to the immediately prior version of the triggering domain, not to arbitrary historical versions. Manual rollback to arbitrary historical versions requires elevated policy.

**Audit trail immutability:** The change log and version history are append-only. No Learning Engine operation deletes or modifies existing entries. Detecting evidence of tampering is possible by comparing the hash chain of the change log against independently stored checkpoint hashes.

### 13.3 Parameter Update Authorization Matrix

```
Operation                          | Automated (system) | Operator | Admin
───────────────────────────────────┼────────────────────┼──────────┼──────
Generate proposal                  | ✓                  | ✓        | ✓
Approve proposal (small magnitude) | ✓ (auto-approved)  | ✓        | ✓
Approve proposal (large magnitude) | ✗                  | ✗        | ✓
Apply approved proposal            | ✓                  | ✓        | ✓
Auto-rollback (degradation signal) | ✓                  | ✗        | ✗
Manual rollback (prior version)    | ✗                  | ✓        | ✓
Manual rollback (arbitrary version)| ✗                  | ✗        | ✓
Emergency rollback                 | ✗                  | ✗        | ✓
Freeze domain                      | ✗                  | ✓        | ✓
Thaw with auto-apply               | ✗                  | ✗        | ✓
Read Parameter Store               | ✓ (domain scoped)  | ✓        | ✓
Read change log                    | ✗                  | ✓        | ✓
```

## 14. Performance Analysis

### 14.1 Throughput Requirements

The Learning Engine is explicitly not on any execution critical path. Its performance requirements are about processing capacity relative to evidence volume, not latency:

- **Evidence ingestion rate:** Must process Reflection Artifacts at the rate they are produced. At 1,000 executions/hour, with 1 Reflection Artifact per execution averaging 50 `EvidenceRecord` entries, the Learning Engine must ingest 50,000 evidence records/hour = ~14 records/second. This is trivial.
- **Aggregation computation:** Aggregating 50,000 records across 7 parameter domains, grouped by entity, over 3 time windows takes O(records × windows) = O(1,050,000) operations per hourly cycle. At sub-microsecond per operation: < 2 seconds. Acceptable.
- **Shadow evaluation:** Evaluating 100 historical executions per proposal, with 7 domains generating proposals in a 6-hour cycle = 700 shadow evaluations total. At ~5 seconds per shadow evaluation: 3,500 seconds = ~1 hour of shadow evaluation work per 6-hour cycle. This requires parallelism (multiple shadow evaluations running concurrently) or a longer evaluation window. The default is 10 concurrent shadow evaluations.

### 14.2 Evidence Store Size

At 50,000 evidence records/hour and 90-day retention, the raw Evidence Store holds 108,000,000 records. At an average of 500 bytes per record: 54GB. This is large but manageable for a dedicated storage backend. Aggregation windows (summarized data) are much smaller: perhaps 500KB for all domains and time windows combined. The hot evidence store (last 7 days) is approximately 8.4GB.

**Mitigation:** Evidence records older than 7 days that have already been included in a successful update proposal are candidates for archival to RFC-0004 (as compressed Evidence Archive Artifacts). This reduces the hot store to the last 7 days of raw records plus any older records that have not yet been incorporated into a proposal.

### 14.3 Parameter Store Performance

The Parameter Store is read heavily by consuming subsystems (RFC-0001, RFC-0011, RFC-0012) but written infrequently (hours between writes). The read path must be extremely fast (sub-millisecond). The Parameter Store should be fully in-memory with durable backing storage. At the size of the parameter domains described (a few MB for all domains combined), this is trivially achievable.

## 15. Scalability Analysis

### 15.1 Multi-Tenant Scalability

Each tenant maintains an independent Parameter Store and independent Evidence Store. Evidence and parameters from tenant A never influence tenant B's system behavior. This is enforced at the evidence ingestion stage: `tenant_id` is a required field in every `EvidenceRecord`, and the Evidence Store is partitioned by tenant.

At 1,000 tenants, the total evidence volume is 1,000× the single-tenant volume. The Learning Engine must either:
- Scale horizontally: one Learning Engine instance per tenant (or per tenant group). This is the recommended deployment at scale.
- Share infrastructure: a single Learning Engine instance with strict tenant partitioning of the Evidence Store and Parameter Store. This reduces operational overhead at the cost of a larger blast radius if the Learning Engine fails.

### 15.2 Evidence Volume Scalability

For extremely high-throughput tenants (millions of executions per day), the Evidence Store raw record volume becomes impractical. Two mitigations:

1. **Evidence sampling:** Instead of ingesting every Reflection Artifact, ingest a statistically representative sample (e.g., 10%). The sample must be unbiased (random sampling, not cherry-picked). With 10% sampling, evidence quality is slightly reduced but remains statistically valid.

2. **Streaming aggregation:** Instead of storing raw evidence records and aggregating in batch, compute running aggregation statistics in a streaming fashion (using online algorithms for mean, variance, and percentiles). This reduces storage from O(records) to O(entities × metrics × windows).

### 15.3 Proposal Volume Scalability

At large scales, many parameter domains may generate proposals simultaneously. The Validation Engine's shadow evaluation is the throughput bottleneck. Shadow evaluation parallelism (Section 14.1) must scale with proposal volume. At 10 domains each generating 50 entity-level proposals per cycle, 500 shadow evaluations per cycle must complete within the 6-hour update window. At 5 seconds per evaluation and 10 concurrent: 250 seconds = 4 minutes. Acceptable.

At 1,000 entity-level proposals per cycle: 500 seconds concurrent. Still within the 6-hour window. At 10,000: would require 50 concurrent shadow evaluations, which is feasible but requires careful resource management.

## 16. Concurrency Model

### 16.1 Evidence Ingestion Concurrency

Multiple Reflection Artifacts may be received concurrently. The Evidence Ingestion Bus processes them concurrently (configurable parallelism; default: 10 concurrent ingestions). Each ingestion writes to the Evidence Store independently. Writes are conflict-free by construction: each evidence record has a unique `evidence_id` and deduplication is by `dedup_key`.

The Entity Index is updated atomically per entity. If two concurrent ingestions both produce evidence for the same entity (e.g., two executions of the same skill complete simultaneously), the index updates are serialized for that entity. This is the only serialization point in ingestion.

### 16.2 Update Generation Concurrency

Update generation runs once per domain per cycle. Domains are processed concurrently (7 domains, 7 concurrent updaters). Each updater reads from the Evidence Store (read-only) and produces a proposal. There are no shared writes between concurrent updaters.

### 16.3 Validation Engine Concurrency

Multiple proposals may be in validation concurrently across different domains. Shadow evaluations are the expensive stage and are processed with bounded concurrency (default: 10 concurrent). Each shadow evaluation is a read-only operation against a copy of the Parameter Store and historical execution records.

### 16.4 Parameter Store Concurrency

The Parameter Store uses a readers-writer lock. Many concurrent readers (consuming subsystems reading current parameters) do not block each other. A write (applying a validated proposal) acquires an exclusive write lock for the duration of the write operation (milliseconds). Read lock acquisition is sub-microsecond for non-contended readers.

### 16.5 Degradation Monitor Concurrency

One active `RollbackMonitor` per domain. Monitors run concurrently (up to 7 simultaneous monitors). Each monitor reads current metrics (read-only from the monitoring data source) and may write to the Parameter Store (for rollback). Rollback writes acquire the Parameter Store write lock.

## 17. Testing Strategy

### 17.1 Unit Tests

**Evidence Normalization:**
- Normalize a complete Reflection Artifact: verify all expected EvidenceRecord entries are produced.
- Duplicate Reflection Artifact ingestion: verify deduplication discards second ingestion.
- Malformed source artifact: verify quarantine and warning publication.

**Evidence Threshold Checking:**
- Entity with exactly min_samples-1 samples: verify THRESHOLD_NOT_MET.
- Entity with exactly min_samples samples: verify THRESHOLD_MET.
- Entity with all required metrics: verify THRESHOLD_MET.
- Entity missing one required metric: verify THRESHOLD_NOT_MET.

**Calibration Updater:**
- Zero mean error: verify NO_UPDATE_NEEDED.
- Mean error below threshold: verify NO_UPDATE_NEEDED.
- Mean error above threshold, underconfident: verify proposed correction > 1.0.
- Mean error above threshold, overconfident: verify proposed correction < 1.0.
- Proposed correction would exceed MAX_CORRECTION: verify clamping.

**Routing Weight Updater:**
- Two tools, one with 0.95 success rate and one with 0.60: verify higher-performing tool receives higher weight.
- Tool with recent contract violation: verify violation penalty applied.
- Single tool for capability: verify NO_UPDATE_NEEDED.
- Proposed weight below weight_floor: verify floor enforcement.
- Post-update weights sum to 1.0: verify normalization.

**Skill Ranking Updater:**
- New skill version inherits prior version's ranking minus discount.
- Skill with success_rate = 0.0: verify ranking clamped to 0.1 minimum.
- Context-specific ranking differs from global ranking for same skill.

**Validation Engine:**
- Proposal with negative routing weight: verify SCHEMA_INVALID rejection.
- Proposal with magnitude 0.25 when max is 0.20: verify REQUIRES_APPROVAL.
- Proposal with magnitude 0.50 when max is 0.20 and APPROVAL_MULTIPLIER=2: verify BOUND_EXCEEDED rejection.
- Two proposals modifying the same parameter in opposite directions within 24h: verify CONFLICT_DETECTED.
- Shadow evaluation returning delta < SHADOW_REGRESSION_THRESHOLD: verify SHADOW_REGRESSION_DETECTED.

**Degradation Monitor:**
- Single signal exceedance: verify no rollback triggered.
- Three consecutive signal exceedances: verify rollback triggered.
- Signal exceedance followed by recovery: verify signal count resets.

### 17.2 Integration Tests

**Full learning cycle:**
1. Ingest 30 Reflection Artifacts for the same skill type, all showing overconfidence.
2. Run update generation job.
3. Verify CONFIDENCE_CALIBRATION proposal generated with correction < 1.0.
4. Validate proposal: verify APPROVED.
5. Apply proposal.
6. Verify Parameter Store updated.
7. Verify `learning.update.applied` event published.
8. Verify RFC-0011 parameter reload would use new calibration coefficients.

**Rollback cycle:**
1. Apply a routing weight update.
2. Inject synthetic degradation metrics into the Degradation Monitor's metric source.
3. Verify rollback triggered after 3 consecutive degradation samples.
4. Verify Parameter Store restored to prior version.
5. Verify `learning.update.rolled_back` event published.
6. Verify evidence that drove the update is quarantined.

**Freeze/thaw cycle:**
1. Freeze SKILL_RANKINGS domain.
2. Run update generation job.
3. Verify no proposals applied.
4. Verify proposals accumulated in DOMAIN_FROZEN state.
5. Thaw domain with auto_apply_accumulated=false.
6. Verify accumulated proposals require individual review.

**Cross-tenant isolation:**
1. Ingest evidence for tenant A with high tool performance.
2. Ingest evidence for tenant B with low tool performance.
3. Run update generation for both tenants.
4. Verify tenant A's routing weights favor the high-performing tool.
5. Verify tenant B's routing weights penalize it.
6. Verify tenant A's parameters are not affected by tenant B's evidence.

### 17.3 Adversarial Tests

**Evidence flooding:**
1. Ingest 10,000 evidence records for a single skill in a single hour (simulating a burst).
2. Run update generation.
3. Verify magnitude bound prevents update magnitude > MAX_UPDATE_MAGNITUDE.
4. Verify the update is correct (not destabilized by volume).

**Contradictory evidence injection:**
1. Ingest 20 evidence records showing a tool as highly reliable.
2. Ingest 5 evidence records (from a potentially compromised reflection) showing the same tool as unreliable.
3. Verify that the 5 records have limited impact relative to the 20 consistent records.

**Schema tamper detection:**
1. Ingest a Reflection Artifact with a modified content hash.
2. Verify Evidence Normalizer detects hash mismatch and quarantines records.
3. Verify quarantine alert published.

### 17.4 Regression Tests

The Learning Engine's parameter update algorithms must produce deterministic results for identical inputs. Regression tests capture algorithm outputs for known input datasets and verify they do not change across software versions. Any intentional algorithm change must be accompanied by explicit regression test updates and a governance report entry documenting the change rationale.

## 18. Tradeoff Analysis

### 18.1 Automated Updates vs. Human-in-the-Loop for All Updates

**Decision:** Automated updates for small-magnitude, evidence-grounded, shadow-passing proposals. Human approval for large-magnitude proposals.

**Rejected alternative (full automation):** Automate all updates without human approval thresholds. Maximum velocity of improvement; no human bottleneck. Rejected because: large-magnitude automated updates carry proportionally larger risks. A 50% change to all routing weights is not safely automated even with shadow evaluation, because shadow evaluation is a simulation, not reality.

**Rejected alternative (full human approval):** Require human approval for every update. Maximum safety; minimum velocity. Rejected because: at scale (thousands of skills, thousands of tools, hourly calibration updates needed), human approval for every update is operationally impossible. The system would not improve between human review cycles.

**Weakness:** The magnitude threshold that determines "small" vs. "large" is a configuration value (default: 15% per cycle). Setting it too high enables risky automation; too low creates an approval backlog. The correct threshold is workload-specific and must be tuned per deployment. This RFC provides defaults but cannot provide universally correct values.

### 18.2 Evidence Time Windows vs. Infinite Accumulation

**Decision:** Fixed time windows (24h, 7d, 30d) with evidence expiry at 90 days.

**Rejected alternative:** Accumulate all evidence forever; more data = better parameters. Rejected because: workloads change over time. Evidence from 6 months ago about a tool's performance is less relevant than evidence from last week. Infinite accumulation would cause old patterns to resist correction by new evidence.

**Rejected alternative:** Only use evidence from the last 24 hours. Maximum responsiveness; minimum historical context. Rejected because: 24 hours of evidence is insufficient to detect gradual trends and may be dominated by atypical workloads (weekends, end-of-month batch jobs, etc.).

**Weakness:** The choice of 30-day maximum window is arbitrary. For slowly-changing systems, 30 days may not be enough to detect a meaningful trend. For rapidly-changing systems, 30 days may include too much stale data. Both the window duration and the staleness expiry should be tunable per domain.

### 18.3 Blended Updates vs. Hard Updates

**Decision:** All updates use a blending factor (30% toward new score per cycle) rather than fully replacing current parameters with the computed optimal value.

**Rejected alternative:** Hard updates: replace current parameters with the newly computed optimal values immediately.

**Rationale:** The computed "optimal" values are estimates from imperfect evidence with a limited time window. Jumping immediately to the computed optimal causes oscillation: each update cycle overshoots the true optimum in an alternating direction. Blended updates produce a stable convergence toward the true optimum, at the cost of slower adaptation.

**Weakness:** Blended updates are slow to respond to large, genuine behavioral changes (e.g., a tool's performance degrades suddenly by 50%). The blended update would take several cycles to fully reflect the change. For critical degradations, the Degradation Monitor's rollback mechanism and the existing magnitude bounds provide faster correction than the blending loop.

### 18.4 Domain-Separated Updaters vs. Joint Optimization

**Decision:** Each parameter domain has an independent Updater. Updates to different domains are computed and applied independently.

**Rejected alternative:** Joint optimization: a single optimizer that simultaneously computes updates across all domains, accounting for interactions between them.

**Rationale:** Joint optimization across 7 parameter domains is an extremely high-dimensional optimization problem. The interactions between domains are poorly understood at specification time (how does a routing weight change interact with a calibration change?). Domain-separated updates are tractable, testable, and independently rollback-capable. The cost is that inter-domain interactions may be missed.

**Weakness:** Domain interactions are real. Increasing a tool's routing weight while simultaneously reducing the confidence calibration factor for the skill that uses that tool may have counteracting effects that neither updater accounts for. The Shadow Evaluator partially mitigates this by evaluating proposals against actual execution records (which capture the combined effect of all parameters), but it evaluates one domain's proposal at a time. True joint optimization requires a future architectural evolution.

### 18.5 Read-Through Parameter Store vs. Event-Driven Reload

**Decision:** Consuming subsystems reload parameters on `learning.update.applied` events, not by querying the Parameter Store on every operation.

**Rejected alternative:** Read-through: consuming subsystems query the Parameter Store on every planning session or routing decision.

**Rationale:** The Parameter Store changes infrequently (hours between updates). Reading it on every operation adds sub-millisecond latency to every planning session but provides no value in the 99.9% of cases where parameters have not changed. Event-driven reload achieves the same consistency with much lower overhead.

**Weakness:** If the event delivery fails (RFC-0006 outage), consuming subsystems will not reload updated parameters. They continue using prior parameters indefinitely. This is safe (prior parameters are valid and working) but means the system does not benefit from the update until the Event Bus recovers and the consuming subsystem next restarts. Consuming subsystems should implement a periodic parameter reload (every few hours) as a belt-and-suspenders against missed events.

## 19. Compatibility Notes

### 19.1 RFC-0001: Skill Resolution Must Consult Skill Rankings

RFC-0001 (Skill Resolver) does not currently define a mechanism for consulting external ranking tables when resolving skill instances. RFC-0001 must be amended to:
1. Accept a `skill_ranking_parameter_set` at initialization (read from the Parameter Store).
2. When multiple eligible skill instances exist for a task type, sort them by `rankings[skill_type][skill_version]["*"]` (or context-specific ranking if available) before selecting the highest-ranked available instance.
3. Subscribe to `learning.update.applied` events for the `SKILL_RANKINGS` domain and reload rankings.

**If RFC-0001 is not amended:** The Skill Ranking Updater continues to compute and publish ranking updates, but they have no effect on actual skill resolution. The Learning Engine degrades gracefully: other domains (calibration, routing) continue functioning.

### 19.2 RFC-0011: Parameter Store Integration for Planning

RFC-0011's Planner must be amended to:
1. Read `HeuristicParameters` and `ConfidenceCalibrationParameters` from the Parameter Store at planning session initialization.
2. Subscribe to `learning.update.applied` events for `HEURISTICS`, `PLANNING_PARAMETERS`, and `CONFIDENCE_CALIBRATION` domains.
3. Apply confidence calibration corrections in the Cost and Confidence Estimator: `corrected_confidence_factor = raw_factor × calibration_params.skill_type_corrections[skill_type][metric]`.

**Schema dependency:** RFC-0011's `estimate_confidence` algorithm (Section 11.3 of RFC-0011) must be updated to accept and apply the calibration correction factors defined by RFC-0014's `ConfidenceCalibrationParameters`. This is a behavioral change to RFC-0011 that must be explicitly versioned and documented in an RFC-0011 amendment.

### 19.3 RFC-0012: Capability Selector Must Consult Routing Weights

RFC-0012's Capability Selector (Section 11.1 of RFC-0012) must be amended to:
1. Read `RoutingWeightParameters` from the Parameter Store.
2. Incorporate tool routing weights into the selection scoring formula: `selection_score[tool_id] += routing_weight_params.tool_weights[capability][tool_id] × ROUTING_WEIGHT_FACTOR`.
3. Subscribe to `learning.update.applied` events for the `ROUTING_WEIGHTS` domain.

**Contract preservation:** RFC-0012's Capability Selector contract — "select the best available, policy-permitted tool for the requested capability" — is unchanged. The routing weights are an additional scoring input, not a replacement for the existing scoring logic. The `weight_floor` parameter ensures no registered tool is completely excluded by routing weight decay.

### 19.4 RFC-0013: CalibrationObservation Schema Is a Joint Contract

RFC-0013 produces `CalibrationObservation` records. RFC-0014 consumes them. The schema of these records (specifically: `skill_type`, `metric`, `planned_value`, `actual_value`, `calibration_error`, `context_tags`, `confidence_factor_types`) is a joint contract between RFC-0013 and RFC-0014. Any change to this schema in RFC-0013 requires a coordinated update to RFC-0014's Evidence Normalizer.

**Versioning:** The `EvidenceRecord.ingestion_version` field allows the Evidence Normalizer to apply version-specific parsing logic when processing records from different versions of RFC-0013. However, this is a maintenance burden. The CalibrationObservation schema should be treated as stable and changes should be managed through RFC amendment, not version multiplexing in the normalizer.

### 19.5 RFC-0003: Learning-Specific Policy Attributes

RFC-0003 must support `learning.*` policy attributes. The specific attributes required:
- `learning.parameter_domain`: Which domain an update targets.
- `learning.update_magnitude`: The magnitude of a proposed update (for threshold-based approval requirements).
- `learning.requires_approval`: Whether this operation class requires elevated authorization.
- `learning.change_type`: AUTOMATED | MANUAL | ROLLBACK | EMERGENCY.

Without these attributes, RFC-0003 cannot implement the authorization matrix defined in Section 13.3. All learning operations would require the same policy evaluation, losing the graduated authorization model.

### 19.6 RFC-0010: Reflection Memory Must Support Learning Engine Reads

RFC-0010's Reflection Memory tier is extensively read by the Learning Engine during evidence ingestion. The query interface RFC-0010 exposes for Reflection Memory must support:
- Query by `lesson_type` (to retrieve all lessons of a specific type).
- Query by `(entity_type, entity_id)` (to retrieve all lessons about a specific skill or tool).
- Query by `context_tags` (to retrieve context-specific lessons).
- Query by `time_range` (to support evidence windowing).
- Query by `min_confidence` (to filter low-confidence lessons).
- Query by `status` (to retrieve only ACTIVE lessons, not ARCHIVED or SUPERSEDED).

If RFC-0010's Reflection Memory tier does not support all of these query patterns natively, the Learning Engine must perform client-side filtering after fetching broader result sets — which is inefficient at scale. RFC-0010 should be amended to confirm or extend its query interface for these patterns.

### 19.7 RFC-0004: Parameter Snapshot Artifact Type

The Learning Engine writes Parameter Snapshots to RFC-0004. These must be registered as a distinct Artifact type (`learning.parameter_snapshot.v1`) in RFC-0004's type registry. The type registration should include the schema reference and appropriate retention policy defaults (parameter snapshots should be retained for at least 90 days for rollback eligibility).

## 20. Critical Self-Review

### 20.1 The Shadow Evaluator Is a Simulation of Limited Fidelity

The Shadow Evaluator predicts the effect of a proposed parameter change by replaying historical execution records through a simplified model of the affected subsystem's logic. This simulation has fundamental limitations:

- It cannot simulate execution side effects (tool invocations that change external state).
- It cannot predict how human or environmental factors that changed between the historical execution and today would interact with the new parameters.
- For the Confidence Calibration domain, it simulates confidence score changes but cannot simulate how changed confidence scores would have changed the plan structure — only whether the confidence threshold would have changed the replanning decision.
- For the Routing Weight domain, it simulates which tool would be selected under new weights but cannot simulate whether that tool would actually have behaved differently.

**Honest assessment:** The Shadow Evaluator provides a useful sanity check but not a reliable prediction of real-world impact. A proposal that passes shadow evaluation may still degrade real-world performance. The Degradation Monitor's post-application monitoring is the real safety net; the Shadow Evaluator is a first-pass filter that catches obvious regressions. Operators should not treat shadow evaluation passing as proof of correctness.

### 20.2 Blend Factors and Learning Rates Are Arbitrary Constants

The calibration learning rate (0.3), the routing weight blend factor (0.3), and the skill ranking blend factor (0.25) are constants defined in this RFC without empirical derivation. They were chosen to be conservative (avoiding oscillation) but are not grounded in specific workload analysis.

**Honest assessment:** These constants will need to be tuned per deployment based on actual workload characteristics. A tenant with rapidly changing tool performance needs a higher blend factor to keep up; a tenant with stable, slow-changing performance needs a lower blend factor to avoid over-reacting to noise. Making these constants configurable (which this RFC does, as they are part of the parameter domains) is the right structural decision, but the defaults may be wrong for any specific deployment. The first year of production operation will generate the calibration data needed to tune them. This bootstrapping problem is inherent and cannot be eliminated by specification alone.

### 20.3 Cross-Domain Interactions Are Unhandled

As acknowledged in Tradeoff Analysis 18.4, the Learning Engine updates parameter domains independently. The interaction between routing weight changes and calibration changes, or between skill ranking changes and planning heuristic changes, is not modeled. In pathological cases, two independent updates that are each individually beneficial may be jointly harmful.

**Honest assessment:** This is a genuine architectural gap with no simple resolution. Modeling cross-domain interactions requires either a joint optimizer (complex, hard to test, potentially unstable) or a domain interaction model (requires extensive empirical characterization of parameter interactions). The current design accepts this gap and relies on the Degradation Monitor to catch joint-update degradation after the fact. A future RFC addressing parameter interaction modeling would materially improve the Learning Engine's safety properties.

### 20.4 The Learning Engine Cannot Learn What It Does Not Observe

The Learning Engine only improves parameters for which it has evidence. Evidence comes from executions that actually happen. This creates a systematic bias: parameters for rarely-used skill types, rarely-used tool capabilities, and rare goal types receive little or no evidence, and their parameters drift toward defaults through the staleness reversion mechanism. Rare but important capabilities are precisely the ones most likely to be poorly tuned.

**Honest assessment:** This is the cold-start problem in a different guise, and it applies continuously, not just at system startup. There is no satisfying technical resolution: learning requires observation, and rare events are rarely observed. The correct response is operational: monitor evidence coverage metrics from the Governance Report, identify domains and entities with sparse evidence, and either artificially increase exercise of those capabilities (through integration testing or synthetic workloads) or accept that their parameters will remain at defaults. This RFC provides the tools (evidence coverage reporting, staleness warnings) to detect this problem but cannot resolve it through architecture alone.

### 20.5 Rollback Is Not Always Safe

The automatic rollback mechanism assumes that restoring the prior parameter version is always an improvement over the current (presumably degraded) version. This assumption can fail:

- **Compound updates:** If two parameter updates were applied in sequence (A then B), and a degradation signal fires after B is applied, rolling back B restores the state after A. But if the degradation was actually caused by A (a slow-manifesting degradation), rolling back B does not help and may mask the true cause.
- **Environmental changes:** If the degradation signal was triggered by an environmental change (e.g., a tool became unreliable independently of the parameter update), rolling back the parameter update does not fix the underlying problem.
- **Monitoring lag:** The Degradation Monitor samples every 15 minutes. A degradation that appears 2 hours after an update may be unrelated to the update but will still trigger rollback.

**Honest assessment:** The rollback mechanism is a conservative safety mechanism, not a precise diagnostic tool. False-positive rollbacks (rolling back a correct update due to an unrelated degradation signal) will occur. The Governance Report must make false-positive rollback patterns visible so that operators can tune the degradation signal thresholds. Rollback is always safe in the sense that it restores a known-good prior state; it is not always necessary in the sense that the degradation may have a different cause.

### 20.6 The Learning Engine Learns Within Structural Constraints It Cannot Change

The Learning Engine can optimize routing weights, but it cannot add a new connector type. It can tune planning heuristics, but it cannot add a new planning algorithm. It can improve skill rankings, but it cannot create a new skill. Every parameter it manages exists within a structural constraint defined by the prior RFC architecture. If the optimal behavior for a given workload requires a structural change (a new algorithm, a new connector, a new memory tier), the Learning Engine cannot produce it. It can only optimize within the existing structure.

**Honest assessment:** This is the intended and correct behavior. The Learning Engine is an optimizer within a fixed architecture, not an architect. The separation is valuable: architectural changes require human judgment and RFC amendment processes. Parameter optimization within a fixed architecture can be automated. Conflating the two would make automated learning unsafe. The limitation is real, but it is a feature, not a bug.

## 21. Future RFC Dependencies

### RFC-0015 (Required): Cross-Tenant Learning Federation

The current design learns independently per tenant. In a multi-tenant deployment, tenants using the same tools and skills could benefit from shared learning: if tool T is unreliable for tenant A, tenants B and C should know immediately, not only after they accumulate their own evidence. RFC-0015 should define: an anonymization protocol for cross-tenant evidence sharing, consent mechanisms (tenants should opt in to federated learning), and the federated evidence ingestion interface for RFC-0014.

### RFC-0016 (Required): Learning Governance Audit Interface

The Governance Report (Section 7.9) provides a summary. For compliance and audit purposes, a more detailed, machine-verifiable audit interface is needed: a full, queryable log of every evidence record, every proposal, every validation step, every application, and every rollback, with cryptographic integrity verification. RFC-0016 should define this interface as a first-class, compliance-oriented subsystem.

### RFC-0017 (Suggested): Parameter Interaction Modeling

As identified in Critical Self-Review 20.3, cross-domain parameter interactions are unhandled. RFC-0017 should define: a parameter interaction model, a method for empirically characterizing parameter interactions from historical data, and a joint optimization mechanism that accounts for known interactions before applying updates.

### RFC-0018 (Suggested): Synthetic Workload Generation for Cold-Start

As identified in Critical Self-Review 20.4, rare capabilities receive insufficient evidence for learning. RFC-0018 should define: a synthetic workload generation protocol that exercises under-evidenced capabilities, criteria for determining which capabilities need synthetic exercise, and safeguards to ensure synthetic workloads do not pollute production evidence (they should be tagged and handled separately from production evidence).

### RFC-0019 (Suggested): Learning Engine Explainability Interface

Operators need to understand why specific parameter changes were made. The current design provides evidence summaries and delta summaries, but not a human-readable explanation of the causal chain from observation to parameter change. RFC-0019 should define an explainability interface that generates natural language (or structured logical) explanations of parameter changes, tracing from the specific evidence records through the aggregation logic to the proposed delta.

### Dependency on RFC-0001 Amendment

RFC-0001 must be amended to consume Skill Ranking parameters from the Parameter Store (Section 19.1). This amendment is required before the Skill Ranking domain provides any operational benefit.

### Dependency on RFC-0011 Amendment

RFC-0011 must be amended to consume `HeuristicParameters` and `ConfidenceCalibrationParameters` from the Parameter Store (Section 19.2). This amendment is required before the Heuristic and Calibration domains provide operational benefit.

### Dependency on RFC-0012 Amendment

RFC-0012 must be amended to incorporate routing weights from the Parameter Store into the Capability Selector (Section 19.3). This amendment is required before the Routing Weight domain provides operational benefit.

### Dependency on RFC-0003 Amendment

RFC-0003 must be amended to support `learning.*` policy attributes (Section 19.5). This amendment is required before the authorization matrix in Section 13.3 can be enforced by policy.
