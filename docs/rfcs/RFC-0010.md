## 1. Executive Overview

RFC-0010 defines the **Memory System** for the AGY AI Operating System. Memory in AGY is not a single database, a vector store, or a cache. It is a **multi-tier, policy-governed, event-driven subsystem** responsible for the storage, retrieval, consolidation, compression, versioning, and eventual expiration of all information that AGY needs to reason across time, across skills, and across execution contexts.

The Memory System is best understood as a **kernel memory manager analogous to a virtual memory subsystem**, but for cognitive state rather than binary data. Just as Linux separates physical pages from virtual addresses and manages promotion, demotion, and eviction between memory tiers, AGY's Memory System separates raw information from indexed representations and manages promotion, consolidation, and forgetting across memory tiers.

The fundamental insight is this: **no single retrieval mechanism, no single storage format, and no single retention policy is correct for all memory types.** Working memory must be cheap and volatile. Semantic memory must be searchable by meaning. Episodic memory must be searchable by time and context. Long-term memory must survive restarts. Reflection memory must influence future behavior. Project memory must be scoped to task lineage. User memory must be governed by identity policies.

The Memory System is **not** a feature layered on top of AGY. It is a kernel subsystem. It has its own lifecycle, its own concurrency model, its own policy integration, and its own failure recovery path. Skills do not access memory directly. They request memory operations through the kernel interface, and the kernel enforces policy, routing, compression, and indexing transparently.

This RFC specifies the architecture of that subsystem in a manner that is independent of implementation language, independent of storage backend, and independent of embedding or indexing technology. The Memory System defines **contracts and composition**, not implementations.

## 2. Responsibilities

The Memory System is responsible for the following:

**Storage Tier Management**
- Maintaining the logical separation of Working, Semantic, Episodic, Long-term, Reflection, Project, and User memory tiers.
- Routing write operations to the correct tier based on memory type, content metadata, and policy.
- Managing the lifecycle of memory entries within and across tiers.

**Retrieval**
- Providing a unified retrieval interface that abstracts over all memory tiers.
- Executing retrieval queries using pluggable retrieval strategies (keyword, structural, temporal, semantic similarity, hybrid).
- Ranking and filtering retrieved memories by relevance, recency, confidence, and policy.

**Context Compression**
- Compressing memory content before injecting it into execution context windows.
- Maintaining fidelity markers so compressed memories can be audited against their originals.
- Tracking compression ratios and enforcing context budget constraints.

**Consolidation**
- Promoting short-lived memories from Working and Episodic tiers to Semantic or Long-term tiers based on consolidation triggers.
- Detecting and merging duplicate or near-duplicate memory entries.
- Generating summary memories that represent collapsed episodic sequences.

**Forgetting and Expiry**
- Applying time-to-live, access-frequency, policy-driven, and recency-weighted decay to memory entries.
- Physically expiring or archiving expired entries based on policy.
- Providing controlled forgetting as a first-class operation, not a side effect of eviction.

**Indexing**
- Maintaining one or more pluggable indexes per memory tier.
- Ensuring indexes remain consistent with the canonical memory store.
- Supporting index rebuild without service interruption.

**Versioning, Snapshots, and Lineage**
- Versioning memory entries on every write mutation.
- Creating point-in-time snapshots of memory tiers for rollback and audit.
- Tracking memory lineage: which execution, which skill, which artifact produced or mutated which memory entry.

**Artifact Integration**
- Materializing memory entries as Artifacts (RFC-0004) when their content is large or must be shared across executions.
- Consuming Artifact references as inputs to memory write operations.
- Tracking bidirectional dependency between Artifacts and memory entries.

**Policy Enforcement**
- Delegating all access control, retention, sensitivity classification, and cross-tenant isolation to the Policy Engine (RFC-0003).
- Never bypassing policy for any internal memory operation.

**Event Publication**
- Publishing memory lifecycle events to the Event Bus (RFC-0006) for observability, audit, and reactive coordination.

## 3. Non-Goals

The following are explicitly outside the scope of RFC-0010:

- **Defining a specific storage backend.** This RFC does not mandate SQL, NoSQL, graph databases, vector databases, or file systems. The Memory System defines storage adapter contracts.
- **Defining a specific embedding model or vector representation.** The Memory System defines an indexing adapter interface. Whether the underlying index uses dense vectors, sparse vectors, BM25, or tree structures is an implementation decision.
- **Implementing reasoning over memory.** Reasoning is performed by skills. The Memory System provides retrieval. It does not interpret what it retrieves.
- **Replacing the Artifact System.** Memory entries and Artifacts serve different purposes. This RFC defines their interaction, not a replacement.
- **Implementing conversation management or session management.** Conversation state may write to Working Memory, but conversation lifecycle is managed by the runtime layer above this subsystem.
- **Providing a query language.** This RFC defines structured query objects. A query language, if needed, belongs in a future RFC.
- **Managing model context windows directly.** Context injection is the responsibility of the skill execution layer. The Memory System provides compressed, ranked memory payloads. Injection is external.
- **Providing user-facing memory browsing UI.** Out of scope.

## 4. Relationship to Previous RFCs

### RFC-0001: Skill Resolver

Skills resolved by the Skill Resolver may declare **memory requirements** as part of their capability manifest: which memory tiers they need to read, which tiers they will write to, and what memory scopes they operate within. The Memory System does not consult RFC-0001 directly, but uses the resolved skill metadata as the authorization identity for memory access policy evaluation.

**Interaction:** Skill identity (skill_id, version, namespace) is passed as the `requester_identity` in all memory requests. The Policy Engine uses this identity to evaluate memory access policy.

### RFC-0002: Skill Registry & Loader

Skill definitions registered in the Skill Registry may include a `memory_profile` block declaring their expected memory footprint, preferred retrieval strategies, and consolidation hints. The Memory System reads these profiles at skill load time and caches them to avoid repeated registry lookups during execution.

**Interaction:** Memory System reads `memory_profile` from skill manifests. This is a one-way dependency. The Skill Registry does not call the Memory System.

### RFC-0003: Policy Engine

Every memory operation — read, write, delete, compress, consolidate, export — is gated by a policy decision. The Policy Engine is the authority. The Memory System is a policy consumer. The Memory System must never perform a destructive or sensitive operation without a policy PERMIT decision.

**Interaction:** Memory System calls Policy Engine with `MemoryPolicyRequest` objects before executing any sensitive operation. Policy decisions are cached per-execution-context with a TTL to avoid per-entry overhead. Cache invalidation on policy change is driven by RFC-0006 events.

**Critical integration note:** The Policy Engine must support memory-specific policy attributes including: `memory_tier`, `memory_scope`, `sensitivity_class`, `retention_policy`, `cross_tenant_access`. These attribute names are defined by this RFC and must be registered in RFC-0003's attribute namespace.

### RFC-0004: Artifact System

This is the most complex integration. Memory entries whose content exceeds the inline size threshold are **materialized as Artifacts**. The memory entry stores an Artifact reference rather than inline content. This keeps the memory index lean and delegates large-object storage to the Artifact System, which already handles content addressing, deduplication, and lineage.

**Interaction (bidirectional):**
- Memory System writes to Artifact System when materializing large memory entries.
- Memory System reads from Artifact System when hydrating memory entries for retrieval.
- Artifact System notifies Memory System (via RFC-0006) when an Artifact is deleted or expired, so the referencing memory entry can be tombstoned.
- Memory lineage records reference Artifact IDs as provenance inputs.

**Critical integration note:** Artifact lifecycle and memory lifecycle are independent. An Artifact may outlive the memory entry that created it (e.g., it was promoted to long-term Artifact storage). A memory entry may outlive its Artifact reference (e.g., the Artifact was expired, but the memory entry's metadata is still valid for retrieval routing). The Memory System must handle dangling Artifact references gracefully.

### RFC-0005: Runtime State

The Runtime State holds the current execution context: skill chain, DAG position, active execution ID, session ID, and user identity. The Memory System uses Runtime State to determine **scope bindings** for memory operations: which execution, which session, and which user a memory entry belongs to.

**Interaction:** Memory System reads Runtime State to populate `scope` fields on memory entries at write time. Memory System does not write to Runtime State. Runtime State does not call the Memory System.

### RFC-0006: Event Bus

The Memory System is both a publisher and a subscriber on the Event Bus.

**As publisher:** Memory lifecycle events (entry created, updated, expired, consolidated, snapshot taken) are published to the Event Bus for observability and reactive coordination.

**As subscriber:** The Memory System subscribes to:
- Artifact expiry events (to handle dangling references).
- Policy change events (to invalidate policy decision caches).
- Execution completion events (to trigger Working Memory consolidation or expiry).
- Scheduler tick events (to drive background consolidation and forgetting passes).

**Interaction:** All Event Bus interactions use the standard envelope defined in RFC-0006. Memory events are published under the `memory.*` topic namespace.

### RFC-0007: Scheduler

The Memory System registers background jobs with the Scheduler for:
- Periodic consolidation passes.
- Periodic forgetting/decay passes.
- Periodic index consistency checks.
- Snapshot rotation.

**Interaction:** Memory System registers `ScheduledJob` entries with the Scheduler at startup. Jobs are defined with cron-style intervals, priority, and idempotency keys. The Scheduler invokes Memory System job handlers via a defined callback interface.

### RFC-0008 and RFC-0009

These RFCs are referenced as accepted and immutable per the master prompt. Their specific contents are not elaborated here, but the Memory System does not introduce any contract violations against them. If either RFC defines constructs that interact with memory (e.g., model routing context, token budgeting), those interactions will be addressed in a subsequent compatibility amendment.

## 5. Architecture

### 5.1 Architectural Philosophy

The Memory System is structured as a **layered kernel subsystem** with four horizontal layers and seven vertical memory tier implementations:

```
┌────────────────────────────────────────────────────────────────┐
│                    Public Memory Interface                      │
│          (Unified read/write/query/compress/snapshot)          │
├────────────────────────────────────────────────────────────────┤
│                    Memory Kernel Core                           │
│   Policy Gate │ Scope Resolver │ Router │ Compression Engine   │
├──────────┬────────────┬───────────────────────┬───────────────┤
│ Working  │  Episodic  │  Semantic │  Long-term │  Reflection   │
│ Memory   │  Memory    │  Memory   │  Memory    │  Memory       │
│ Manager  │  Manager   │  Manager  │  Manager   │  Manager      │
├──────────┴────────────┴──┬────────┴────────────┴───────────────┤
│  Project Memory Manager  │     User Memory Manager             │
├──────────────────────────┴────────────────────────────────────┤
│                    Storage Adapter Layer                        │
│     Index Adapter │ Store Adapter │ Artifact Bridge Adapter    │
├────────────────────────────────────────────────────────────────┤
│          Background Services (Consolidator, Forgetter,          │
│          Snapshot Manager, Index Rebuilder)                    │
└────────────────────────────────────────────────────────────────┘
```

### 5.2 Memory Tier Model

The Memory System defines seven distinct tiers, each with different volatility, retention semantics, scope boundaries, and retrieval characteristics.

| Tier | Volatility | Scope | Primary Retention Driver | Retrieval Priority |
|---|---|---|---|---|
| Working | High | Execution | TTL + execution end | 1st |
| Episodic | Medium | Session | Time + consolidation | 2nd |
| Semantic | Low | Global/Project | Relevance + access | 3rd |
| Long-term | Very Low | Global | Explicit write + policy | 4th |
| Reflection | Low | Global/Agent | Agent self-evaluation | 5th |
| Project | Medium | Project | Project lifecycle | 2nd (project scope) |
| User | Low | User identity | User consent + policy | 1st (user scope) |

**Retrieval Priority** describes the order in which tiers are searched during a unified retrieval unless the query specifies explicit tier targeting.

### 5.3 Cross-Cutting Concerns

Four concerns cut across all tiers and are implemented once in the Memory Kernel Core:

1. **Policy Gate:** Every operation passes through a policy check before execution.
2. **Scope Resolver:** Maps execution context (from RFC-0005) to memory scope identifiers.
3. **Router:** Determines which tier manager handles a given operation.
4. **Compression Engine:** Compresses memory content for context injection.

## 6. Internal Components

### 6.1 Memory Kernel Core

The Memory Kernel Core is the central dispatcher. It receives all external memory requests, enforces cross-cutting concerns, and delegates to tier managers.

**Responsibilities:**
- Validate request structure.
- Resolve scope from Runtime State (RFC-0005).
- Evaluate policy via Policy Engine (RFC-0003).
- Route to appropriate tier manager(s).
- Collect, rank, and merge results for multi-tier queries.
- Publish lifecycle events to Event Bus (RFC-0006).
- Return responses conforming to the Public Interface contract.

**The Core is the only component that directly calls the Policy Engine.** Tier managers do not make independent policy decisions. This centralizes policy enforcement and prevents bypass via direct tier access.

### 6.2 Working Memory Manager

Working memory holds the active state of the current execution: intermediate results, in-progress plans, tool outputs awaiting processing, and short-horizon facts. It is analogous to CPU registers and L1 cache — fast, small, and volatile.

**Characteristics:**
- Keyed by `(execution_id, key)`.
- Default TTL: duration of the enclosing execution context.
- Maximum entry size: configurable inline limit before Artifact materialization.
- No background consolidation trigger — consolidation is triggered by execution lifecycle events.
- Cleared on execution termination unless explicitly promoted.

**Internal structure:**
- In-memory hash map keyed by `(execution_id, key)` for O(1) access.
- Secondary ordered list by insertion time for eviction ordering.
- No persistent backing store by default; implementation may opt into persistence for crash recovery.

### 6.3 Episodic Memory Manager

Episodic memory records what happened: the sequence of events, decisions, and outcomes within a session or across a short time horizon. It is the system's autobiographical record.

**Characteristics:**
- Keyed by `(session_id, timestamp, event_type)`.
- Retention window: configurable per-policy (default 7 days raw, 30 days summarized).
- Supports temporal range queries.
- Consolidation path: episodic sequences → semantic summary memories or long-term memories.
- Entries are append-only (mutations create new versions, not overwrites).

**Internal structure:**
- Ordered log (append-only) per session.
- Secondary index on `(session_id, timestamp)` for range queries.
- Secondary index on `(event_type)` for event-class queries.
- Compaction: sequential episodes are summarized by the Consolidator and replaced with a summary entry plus a pointer to the raw log (which may be archived to Artifact System).

### 6.4 Semantic Memory Manager

Semantic memory stores facts, concepts, relationships, and generalizations that are not tied to a specific time or event. It is the system's knowledge base — structured, searchable by meaning, and durable.

**Characteristics:**
- Keyed by `(namespace, concept_id)` where `concept_id` is content-addressed.
- No natural expiry; entries survive until explicitly deleted or policy-expired.
- Supports similarity-based retrieval via pluggable Index Adapter.
- Entries carry confidence scores, provenance, and access frequency counters.
- Supports graph-style relationship links between entries.

**Internal structure:**
- Primary store: key-value by `concept_id`.
- Index Adapter: pluggable (semantic similarity, keyword, graph traversal).
- Relationship graph: adjacency structure linking concept IDs by named relationship type.
- Confidence decay: periodic decay of confidence scores based on recency of corroboration.

### 6.5 Long-term Memory Manager

Long-term memory is the most durable tier. Entries are written explicitly, persist across restarts, and require explicit policy justification to delete. This is analogous to disk storage in the memory hierarchy.

**Characteristics:**
- Keyed by `(scope, memory_id)` where scope is `global`, `tenant`, or `project`.
- No automatic expiry unless policy mandates it.
- All writes versioned; full version history retained by default.
- Snapshot-eligible: included in system snapshots.
- Immutable once written unless a mutation policy is explicitly granted.

**Internal structure:**
- Append-only log with periodic checkpointing.
- Secondary index for retrieval.
- Version chain: linked list of prior versions per entry.
- Snapshot pointers: references to snapshot boundaries in the log.

### 6.6 Reflection Memory Manager

Reflection memory stores the system's self-evaluative observations: what went wrong, what went well, which strategies succeeded, which failed, and generalized lessons extracted from post-execution reflection. It is the feedback channel from execution outcomes to future behavior.

**Characteristics:**
- Written by Reflection skills (a class of skills, not defined here) after execution completion.
- Entries contain structured observations: `{execution_id, outcome, observation_type, lesson, confidence, context_tags}`.
- Retrieved during planning and skill selection to bias future decisions.
- Contributes to Semantic Memory via consolidation (generalizations of repeated lessons).
- Subject to confidence decay: a lesson observed once should have lower confidence than one observed ten times.

**Internal structure:**
- Primary store: keyed by `(execution_id, observation_id)`.
- Secondary index by `(observation_type, context_tags)` for retrieval during planning.
- Confidence aggregation: when similar lessons are observed repeatedly, confidence is aggregated and the entry is promoted to Semantic Memory.

### 6.7 Project Memory Manager

Project memory is scoped to a project lineage — a set of related executions sharing a common goal, a common DAG ancestry, or an explicit project identifier. It bridges the short-horizon (working, episodic) and long-horizon (semantic, long-term) memories for project-specific knowledge.

**Characteristics:**
- Keyed by `(project_id, memory_id)`.
- Lifecycle tied to project lifecycle: created with project, archived on project completion.
- Contains: project goals, constraints, prior decisions, team context, accumulated results.
- Accessible to all executions within the project scope, subject to policy.
- Archived to Long-term Memory or Artifact System on project completion.

**Internal structure:**
- Key-value store scoped by `project_id`.
- Relationship links to Artifacts produced within the project.
- Decision log: append-only record of key decisions made during the project.
- Completion snapshot: point-in-time snapshot triggered on project closure event.

### 6.8 User Memory Manager

User memory stores information specific to a user identity: preferences, learned behaviors, consent records, interaction history summaries, and personalization signals. It is the most policy-sensitive tier.

**Characteristics:**
- Keyed by `(user_id, memory_key)`.
- Subject to the strictest retention and sensitivity policies.
- Requires explicit user consent policy (from RFC-0003) for any write.
- Deletable by user request (right-to-delete compliance).
- Not shared across user identities under any circumstances.
- Exported as a structured bundle on user data export request.

**Internal structure:**
- Isolated store per user identity (logical or physical isolation per policy).
- Consent ledger: append-only record of consent events.
- Access log: every read of user memory is logged for audit.
- Export formatter: produces a structured, human-readable export bundle.

### 6.9 Context Compression Engine

The Context Compression Engine reduces memory content to fit within context window budgets for skill execution. It is not a lossy compressor in the cryptographic sense — it is a **semantic summarizer** that preserves the most decision-relevant information while reducing token count.

**Responsibilities:**
- Accept a list of ranked memory entries and a target token budget.
- Produce a compressed context payload within budget.
- Attach a `compression_manifest` to the payload describing what was omitted and why.
- Record the compression operation in the memory lineage log.

**Compression Strategies (pluggable):**
1. **Truncation:** Simple character/token limit. Lowest fidelity. Used as fallback.
2. **Hierarchical summarization:** Summarize low-priority entries, keep high-priority entries verbatim.
3. **Schema-guided extraction:** Extract only fields relevant to the requesting skill's declared input schema.
4. **Deduplication:** Remove entries that are near-duplicates before applying other strategies.

**Compression is a non-destructive operation.** The original memory entries are never modified by compression. Compression produces a derived artifact for context injection.

### 6.10 Consolidator

The Consolidator is a background service that runs on a schedule (via RFC-0007) and promotes memories across tiers. It is the primary mechanism by which short-lived memory becomes durable knowledge.

**Consolidation triggers:**
- Execution completion event (RFC-0006): Consolidate Working Memory for that execution.
- Session end event: Consolidate Episodic Memory for that session.
- Scheduled pass (RFC-0007): Consolidate aged episodic entries, promote high-confidence reflection lessons.
- Explicit request: A skill may request immediate consolidation of a specific entry.

**Consolidation operations:**
1. **Promotion:** Move an entry from a lower-durability tier to a higher-durability tier unchanged.
2. **Summarization:** Replace a sequence of entries with a single summary entry, archiving originals.
3. **Generalization:** Extract a general principle from multiple specific episodic or reflection entries and write it to Semantic Memory.
4. **Deduplication:** Merge near-duplicate entries, retaining the highest-confidence version with a merged provenance record.

### 6.11 Forgetter

The Forgetter is a background service responsible for the controlled expiry and decay of memory entries. It is not an eviction mechanism — it is a **policy-driven lifecycle enforcer**.

**Forgetting mechanisms:**
1. **TTL expiry:** Entry age exceeds its configured TTL. Entry is tombstoned.
2. **Access-frequency decay:** Entries not accessed in a configurable window receive a reduced relevance score. Below a threshold, they are archived or deleted.
3. **Policy-mandated deletion:** RFC-0003 policy update requires deletion of entries matching a classification. Forgetter executes the deletion pass.
4. **Confidence decay:** Semantic and Reflection memory entries whose confidence falls below a minimum threshold are tombstoned or archived.
5. **Capacity-based eviction:** When a tier approaches capacity limits, the Forgetter evicts lowest-scored entries first (score = relevance × recency × access_frequency).

**Tombstoning vs. deletion:**
- Tombstoned entries retain their metadata and lineage but have their content nulled. This preserves audit trails while reclaiming storage.
- Hard-deleted entries are removed entirely. Only permitted by explicit policy.
- User memory deletion (right-to-delete) is always a hard delete.

### 6.12 Snapshot Manager

The Snapshot Manager creates and manages point-in-time snapshots of memory tiers. Snapshots are used for rollback, audit, disaster recovery, and execution reproducibility.

**Snapshot types:**
1. **Tier snapshot:** Point-in-time capture of a single memory tier's state.
2. **Full system snapshot:** Coordinated snapshot of all tiers simultaneously.
3. **Execution snapshot:** Snapshot of Working Memory and relevant Episodic/Project memory at execution start, for rollback.
4. **Project snapshot:** Snapshot of Project Memory at project completion.

**Snapshots are materialized as Artifacts (RFC-0004).** This gives them content addressing, deduplication, and lineage for free. A snapshot Artifact's lineage points to the snapshot source tier and the triggering event.

### 6.13 Index Manager

The Index Manager maintains one or more indexes per memory tier and abstracts index operations behind a uniform adapter interface. It is explicitly implementation-independent.

**Index Adapter Interface:**
- `index(entry_id, content, metadata)` — Add or update an index entry.
- `remove(entry_id)` — Remove an entry from the index.
- `query(MemoryQuery) → [ScoredEntryReference]` — Execute a query and return scored references.
- `rebuild(tier_id)` — Rebuild the index for a tier from the canonical store.
- `health_check() → IndexHealth` — Report index consistency status.

**The canonical store is always the authority.** Indexes are derived structures. If an index is inconsistent, the Consolidator or Index Manager can rebuild it from the canonical store without data loss.

## 7. Public Interfaces

All interfaces are defined as logical contracts. Language-specific signatures are not prescribed.

### 7.1 MemoryWrite

```
OPERATION: MemoryWrite
INPUT:
  requester_identity: SkillIdentity
  tier_hint: MemoryTier (optional; kernel may override based on policy)
  scope_hint: MemoryScope (optional; kernel resolves from Runtime State if absent)
  key: string (optional; kernel generates if absent)
  content: MemoryContent
  metadata: MemoryMetadata
  ttl: Duration (optional)
  consolidation_hint: ConsolidationHint (optional)
OUTPUT:
  memory_entry_id: UUID
  assigned_tier: MemoryTier
  assigned_scope: MemoryScope
  version: VersionID
  artifact_ref: ArtifactReference (if content was materialized)
ERRORS:
  POLICY_DENIED
  TIER_CAPACITY_EXCEEDED
  INVALID_CONTENT
  SCOPE_RESOLUTION_FAILURE
```

### 7.2 MemoryRead

```
OPERATION: MemoryRead
INPUT:
  requester_identity: SkillIdentity
  memory_entry_id: UUID
  version: VersionID (optional; defaults to latest)
  hydrate_artifact: boolean (default true)
OUTPUT:
  entry: MemoryEntry (or null if not found)
  from_cache: boolean
ERRORS:
  POLICY_DENIED
  NOT_FOUND
  ARTIFACT_UNAVAILABLE
```

### 7.3 MemoryQuery

```
OPERATION: MemoryQuery
INPUT:
  requester_identity: SkillIdentity
  query: MemoryQuerySpec
    tiers: [MemoryTier] (optional; defaults to all permitted tiers)
    scope: MemoryScope (optional)
    filters: [MemoryFilter]
    retrieval_strategy: RetrievalStrategy
    max_results: integer
    token_budget: integer (optional; triggers compression if set)
    recency_weight: float (0.0–1.0)
    relevance_weight: float (0.0–1.0)
    include_tombstoned: boolean (default false)
OUTPUT:
  results: [RankedMemoryEntry]
  compression_manifest: CompressionManifest (if token_budget was set)
  tiers_searched: [MemoryTier]
  total_candidates: integer
ERRORS:
  POLICY_DENIED
  INVALID_QUERY
  INDEX_UNAVAILABLE (degraded mode returns partial results)
```

### 7.4 MemoryDelete

```
OPERATION: MemoryDelete
INPUT:
  requester_identity: SkillIdentity
  memory_entry_id: UUID
  delete_mode: TOMBSTONE | HARD_DELETE
  reason: string
OUTPUT:
  success: boolean
  version_at_deletion: VersionID
ERRORS:
  POLICY_DENIED
  NOT_FOUND
  IMMUTABLE_ENTRY (long-term entries require explicit policy grant)
```

### 7.5 MemoryConsolidate (explicit request)

```
OPERATION: MemoryConsolidate
INPUT:
  requester_identity: SkillIdentity
  source_entry_ids: [UUID]
  target_tier: MemoryTier
  consolidation_strategy: ConsolidationStrategy
OUTPUT:
  consolidated_entry_id: UUID
  source_entries_disposition: [EntryDisposition]
ERRORS:
  POLICY_DENIED
  CONSOLIDATION_CONFLICT
```

### 7.6 MemorySnapshot

```
OPERATION: MemorySnapshot
INPUT:
  requester_identity: SkillIdentity
  snapshot_type: TIER | FULL | EXECUTION | PROJECT
  target_id: UUID (execution_id or project_id, if applicable)
  tiers: [MemoryTier] (for TIER snapshot)
OUTPUT:
  snapshot_id: UUID
  artifact_ref: ArtifactReference
  snapshot_timestamp: Timestamp
ERRORS:
  POLICY_DENIED
  SNAPSHOT_IN_PROGRESS
```

### 7.7 MemoryExport (User Data)

```
OPERATION: MemoryExport
INPUT:
  requester_identity: SkillIdentity
  user_id: UserID
  export_format: STRUCTURED_JSON | ARCHIVE
OUTPUT:
  artifact_ref: ArtifactReference
  entry_count: integer
  export_timestamp: Timestamp
ERRORS:
  POLICY_DENIED
  USER_NOT_FOUND
```

## 8. Data Structures

### 8.1 MemoryEntry

```
MemoryEntry {
  id: UUID
  version: VersionID
  previous_version: VersionID (null if initial)
  tier: MemoryTier
  scope: MemoryScope {
    execution_id: UUID (nullable)
    session_id: UUID (nullable)
    project_id: UUID (nullable)
    user_id: UserID (nullable)
    tenant_id: TenantID
    global: boolean
  }
  key: string
  content: MemoryContent {
    inline_data: bytes (nullable; null if artifact_ref is set)
    artifact_ref: ArtifactReference (nullable)
    content_type: ContentType (TEXT | STRUCTURED | BINARY | COMPRESSED)
    token_estimate: integer
  }
  metadata: MemoryMetadata {
    created_at: Timestamp
    updated_at: Timestamp
    accessed_at: Timestamp
    access_count: integer
    ttl: Duration (nullable)
    expires_at: Timestamp (nullable)
    sensitivity_class: SensitivityClass
    tags: [string]
    source_skill: SkillIdentity
    source_execution: UUID
```

## 9. Runtime Lifecycle

### 9.1 System Startup

1. Memory Kernel Core initializes and reads configuration.
2. Each Tier Manager initializes its backing store connection and verifies connectivity.
3. Index Manager initializes adapters for each tier and runs health checks.
4. If any index is inconsistent, Index Manager schedules an async rebuild and operates in degraded mode (full-scan fallback) until rebuild completes.
5. Snapshot Manager validates the latest snapshot manifest.
6. Consolidator and Forgetter register their scheduled jobs with RFC-0007 Scheduler.
7. Memory Kernel Core subscribes to relevant Event Bus topics (RFC-0006).
8. Memory System publishes `memory.system.ready` event.

### 9.2 Execution Start

1. Execution start event received from RFC-0006 Event Bus.
2. Scope Resolver extracts `(execution_id, session_id, project_id, user_id, tenant_id)` from Runtime State (RFC-0005).
3. If `project_id` is present, Project Memory Manager loads the project context summary into Working Memory for this execution.
4. If `user_id` is present, User Memory Manager retrieves the user's active preference summary (compressed, per token budget) and injects it into Working Memory.
5. Execution snapshot is taken of the current Working Memory state (empty at this point, but establishes the snapshot boundary).

### 9.3 During Execution

1. Skills call MemoryWrite/MemoryRead/MemoryQuery through the kernel interface.
2. Each operation is policy-gated, scope-resolved, and routed.
3. Working Memory grows as execution progresses.
4. Reads from other tiers are cached in a short-lived read cache within the execution context to avoid repeated retrieval overhead.

### 9.4 Execution Completion

1. Execution complete event received.
2. Working Memory for the execution is snapshot-captured (final state).
3. Consolidation is triggered: Working Memory entries with `consolidation_hint=PROMOTE` or meeting automatic promotion criteria are promoted to Episodic or Project Memory.
4. Remaining Working Memory entries are tombstoned or hard-deleted per policy.
5. Reflection skills (if present in the DAG) write Reflection Memory entries for this execution.
6. `memory.execution.closed` event published.

### 9.5 Background Operation

The Scheduler (RFC-0007) drives two recurrent background operations:

**Consolidation Pass (configurable interval, default: every 5 minutes):**
1. Query Episodic Memory for entries older than the consolidation threshold.
2. Group entries by session and topic clustering.
3. Apply configured consolidation strategy.
4. Write summary entries to Semantic or Long-term Memory.
5. Archive or tombstone source entries.

**Forgetting Pass (configurable interval, default: every 15 minutes):**
1. Query all tiers for entries with expired TTLs.
2. Apply confidence decay to Semantic and Reflection entries.
3. Apply access-frequency decay to all tiers.
4. Tombstone or hard-delete entries per policy.
5. Publish `memory.expired` events for each affected entry.

## 10. State Machines

### 10.1 Memory Entry State Machine

```
                    ┌──────────┐
              ┌────▶│  ACTIVE  │────────────────────────────┐
              │     └──────────┘                            │
              │          │                                  │
              │    [TTL expired | policy delete |           │
              │     forgetter pass]                         │
              │          │                                  │
              │          ▼                              [consolidate]
              │    ┌───────────┐                            │
              │    │TOMBSTONED │                            ▼
              │    └───────────┘                    ┌──────────────┐
              │          │                          │ CONSOLIDATED │
              │    [policy: hard delete]             └──────────────┘
              │          │                                  │
              │          ▼                          [source archived]
              │    ┌─────────┐                             │
              │    │ DELETED │◀────────────────────────────┘
              │    └─────────┘
              │
         [restore]
              │
         ┌──────────┐
         │ ARCHIVED │
         └──────────┘
              │
        [archive TTL expired]
              │
              ▼
         ┌─────────┐
         │ DELETED │
         └─────────┘
```

**States:**
- `ACTIVE`: Entry is live and retrievable.
- `TOMBSTONED`: Content is nulled; metadata retained for audit; not returned in normal queries.
- `ARCHIVED`: Content moved to Artifact System; retrievable but requires hydration; not in hot indexes.
- `CONSOLIDATED`: Entry has been subsumed by a consolidation operation; pointer to consolidation record retained.
- `DELETED`: Entry is hard-deleted; only audit log entry remains.

**Valid transitions:**
- ACTIVE → TOMBSTONED (TTL expiry, policy delete, forgetter)
- ACTIVE → ARCHIVED (capacity eviction, explicit archive, project completion)
- ACTIVE → CONSOLIDATED (consolidation operation)
- TOMBSTONED → DELETED (hard delete policy)
- TOMBSTONED → ACTIVE (restore operation, policy-gated)
- ARCHIVED → ACTIVE (restore from archive)
- ARCHIVED → DELETED (archive TTL expiry)
- CONSOLIDATED → ARCHIVED (source consolidated entry archival)

### 10.2 Consolidation Job State Machine

```
IDLE → TRIGGERED → SCANNING → GROUPING → EXECUTING → WRITING → COMPLETE
                                                          │
                                                     PARTIAL_FAILURE
                                                          │
                                                      (retry or FAILED)
```

### 10.3 Index State Machine

```
INITIALIZING → HEALTHY
HEALTHY → REBUILDING (on detected inconsistency)
REBUILDING → HEALTHY (rebuild complete)
REBUILDING → DEGRADED (rebuild failed)
DEGRADED → REBUILDING (retry)
HEALTHY → DEGRADED (backend failure)
DEGRADED → HEALTHY (backend recovered + consistency confirmed)
```

## 11. Algorithms

### 11.1 Retrieval Ranking Algorithm

When a MemoryQuery returns candidates from one or more tiers, they must be ranked before being returned to the caller. The ranking algorithm is a weighted linear combination:

```
score(entry) = 
  (relevance_weight × relevance(entry, query)) +
  (recency_weight   × recency_score(entry)) +
  (confidence_weight × entry.metadata.confidence) +
  (access_weight    × normalized_access_frequency(entry))
```

Where:
- `relevance(entry, query)` is provided by the Index Adapter (strategy-dependent, normalized 0.0–1.0).
- `recency_score(entry) = 1 / (1 + age_in_hours(entry))` — hyperbolic decay.
- `normalized_access_frequency(entry) = log(1 + entry.metadata.access_count) / log(1 + max_access_count_in_tier)` — log-normalized.
- Weights are provided by the query's `RankingSpec`, defaulting to equal weights if not specified.

**Tie-breaking:** On equal score, newer entries rank higher. On equal score and timestamp, lower tier volatility ranks higher (long-term > semantic > episodic > working).

**Why this algorithm?** It is explainable, tunable per query, and does not require a trained model. It is deterministic given the same inputs, which supports testing and audit. Alternatives considered: learned ranking models (rejected: introduces a training dependency and non-determinism), pure BM25 (rejected: ignores recency and confidence which are critical for memory), pure recency sort (rejected: ignores relevance entirely).

### 11.2 Context Compression Algorithm

Given a ranked list of memory entries and a token budget:

```
PROCEDURE compress(entries: [RankedMemoryEntry], budget: integer) → CompressedContext:

  1. Sort entries by rank descending.
  2. Initialize token_used = 0, included = [], omitted = [].
  3. For each entry in ranked order:
     a. If entry.content.token_estimate + token_used ≤ budget:
        - Include entry verbatim. Add to included. Increment token_used.
     b. Else if budget - token_used > MIN_SUMMARY_TOKENS:
        - Apply schema-guided extraction or truncation to entry.
        - If summarized version fits: include summarized. Add to included.
        - Else: add to omitted with reason=BUDGET_EXCEEDED.
     c. Else: add to omitted with reason=BUDGET_EXHAUSTED.
  4. Build CompressionManifest.
  5. Return CompressedContext { content: included, manifest }.
```

`MIN_SUMMARY_TOKENS` is configurable (default: 50). Entries below this threshold are omitted rather than truncated, as extremely short summaries lose all fidelity.

### 11.3 Consolidation Grouping Algorithm

When the Consolidator processes episodic entries for a session:

```
PROCEDURE group_for_consolidation(entries: [EpisodicEntry]) → [ConsolidationGroup]:

  1. Sort entries by timestamp ascending.
  2. Initialize groups = [].
  3. For each entry:
     a. Find existing group with compatible topic_tags and time_proximity (< GROUPING_WINDOW).
     b. If found: add entry to group.
     c. If not found: create new group with this entry as seed.
  4. For groups exceeding MIN_GROUP_SIZE: mark as CONSOLIDATION_CANDIDATE.
  5. Return CONSOLIDATION_CANDIDATE groups.
```

`GROUPING_WINDOW` (default: 30 minutes) and `MIN_GROUP_SIZE` (default: 3) are configurable per policy.

### 11.4 Confidence Decay Algorithm

Applied during Forgetting Pass to Semantic and Reflection memory entries:

```
new_confidence = old_confidence × decay_factor^(days_since_corroboration)
```

Where `decay_factor ∈ (0.0, 1.0)` is configurable per tier (default: 0.95 for Semantic, 0.90 for Reflection). If `new_confidence < MINIMUM_CONFIDENCE_THRESHOLD` (default: 0.1), the entry is tombstoned.

**Corroboration:** When a new memory entry with similar content is written, the existing entry's `corroborated_at` timestamp is updated, resetting the decay clock. This ensures actively-relevant memories do not decay.

### 11.5 Deduplication Algorithm

Before writing a new Semantic Memory entry:

```
PROCEDURE check_duplicate(new_entry) → DuplicateCheckResult:

  1. Query Index Adapter with new_entry content, strategy=SEMANTIC_SIMILARITY, max_results=5.
  2. For each candidate in results:
     a. Compute structural similarity(new_entry.content, candidate.content).
     b. If similarity > DUPLICATE_THRESHOLD (default: 0.92):
        - Return DUPLICATE_FOUND { candidate_id, similarity_score }.
  3. Return NO_DUPLICATE.

ON DUPLICATE_FOUND:
  - If new_entry.confidence > candidate.confidence: update candidate, merge provenance.
  - Else: increment candidate.access_count, update candidate.corroborated_at.
  - Do not write new entry.
```

## 12. Failure Recovery

### 12.1 Failure Classification

| Failure Type | Impact | Recovery Strategy |
|---|---|---|
| Tier store unavailable | Cannot write/read that tier | Serve other tiers; publish degraded event; queue writes |
| Index unavailable | Retrieval falls back to full scan | Index Manager enters DEGRADED state; full-scan fallback |
| Artifact bridge failure | Cannot hydrate large entries | Return entry with `hydration_failed` flag; log |
| Consolidation failure | Entries not promoted | Retry with exponential backoff; entries remain in source tier |
| Forgetter failure | Entries not expired on schedule | Next pass handles them; no data loss |
| Snapshot failure | Point-in-time capture incomplete | Invalidate partial snapshot; retry; alert |
| Policy Engine unavailable | Cannot evaluate policy | Fail-closed: deny all operations; queue and retry |

### 12.2 Write Failure Handling

Memory writes use a **write-ahead approach**: the operation is logged to a durable write-ahead log before being applied to the tier store. If the tier store write fails after the WAL entry is written, the operation can be replayed on recovery. WAL entries are pruned after successful confirmation from the tier store.

This is not a full distributed transaction protocol. It is a local idempotency guarantee. Cross-tier consistency is eventual, not strict.

### 12.3 Partial Index Inconsistency

If the Index Manager detects that an index entry references a non-existent store entry (orphan index entry), it removes the orphan silently and logs the event. If a store entry has no index entry (missing index entry), it is re-indexed on the next Index Manager consistency pass. These are non-critical inconsistencies that do not cause data loss.

### 12.4 Fail-Closed Policy Gate

If the Policy Engine is unavailable, the Memory Kernel Core rejects all memory operations with `POLICY_ENGINE_UNAVAILABLE`. This is the correct fail-closed behavior per the AGY security model. Operations are not queued (to prevent unbounded queue growth). Callers must handle the error and retry.

**Alternative considered:** Cache last-known policy decisions and allow operations against cached decisions. Rejected because: policy changes (e.g., sensitivity reclassification) would not be respected during the outage window. The security risk outweighs the availability benefit.

### 12.5 Artifact Reference Breakage

When the Memory System receives a `memory.artifact_ref_broken` event (i.e., an Artifact it references has been deleted from RFC-0004), it:
1. Marks the referencing memory entry with `content.artifact_ref.status = BROKEN`.
2. If the entry has `inline_data` as a backup (pre-artifact-materialization snapshot), promotes inline_data to primary.
3. If no backup exists, tombstones the entry and logs `CONTENT_UNRECOVERABLE`.
4. Publishes `memory.artifact_ref_broken` event.

## 13. Security Considerations

### 13.1 Threat Model

**Threats specific to the Memory System:**
1. **Tier escalation:** A skill writing to Working Memory attempts to promote content to Long-term Memory without authorization.
2. **Cross-user memory access:** A skill reading memories scoped to user A while operating in user B's context.
3. **Cross-tenant memory leakage:** Memories from one tenant being returned in queries for another tenant.
4. **Memory poisoning:** A skill writing false or malicious content to Semantic or Reflection Memory to influence future reasoning.
5. **Consolidation manipulation:** A skill triggering consolidation to promote its own entries and suppress others.
6. **Snapshot exfiltration:** Unauthorized access to memory snapshots (which may contain sensitive historical data).

### 13.2 Defense Mechanisms

**Tier escalation prevention:** The router checks policy before any tier transition. A skill may declare a `tier_hint` but cannot force tier assignment. The kernel assigns the tier based on policy and content analysis.

**Cross-user/cross-tenant isolation:** Every memory entry carries its `scope.user_id` and `scope.tenant_id`. The Policy Engine enforces that query scope must match the requester's identity scope. The Scope Resolver validates scope bindings against the Runtime State identity at every operation.

**Memory poisoning mitigation:** All writes to Semantic and Reflection Memory are annotated with `source_skill` and `source_execution`. Content integrity hashes are stored at write time. Anomaly detection (a future RFC concern) can flag unusual write patterns. High-sensitivity tiers require elevated policy grants for write operations.

**Consolidation authorization:** Explicit consolidation requests are policy-gated like any other operation. Automatic consolidation by the Consolidator operates under a system identity with a constrained policy that only permits consolidation operations within the system's own execution context, not cross-tenant.

**Snapshot authorization:** Snapshot creation and retrieval are both policy-gated. Snapshots are stored as Artifacts with the same access controls as any other Artifact.

### 13.3 Sensitivity Classification Propagation

When a memory entry is consolidated from multiple source entries, the resulting entry inherits the **highest sensitivity class** of its sources. Sensitivity can never be downgraded by consolidation. This ensures that merging a sensitive entry with a non-sensitive entry always produces a sensitive result.

### 13.4 Audit Logging

Every memory operation produces an audit log entry independent of the Event Bus. Audit logs are append-only, write-once, and stored in a dedicated audit log store (implementation-defined, but must not be the same store as the memory tiers). Audit logs record: operation type, actor identity, entry ID, tier, scope, policy decision, and timestamp.

## 14. Performance Analysis

### 14.1 Critical Path Analysis

The critical path for a memory read during skill execution is:

```
MemoryRead → Policy Gate → Scope Resolve → Tier Router → Tier Manager →
Index Adapter Query → Store Fetch → Artifact Hydration (conditional) → Return
```

**Target latency (P99):**
- Policy Gate: < 2ms (with policy decision cache hit)
- Scope Resolve: < 1ms (Runtime State lookup)
- Tier Router: < 0.1ms
- Index Adapter Query (Working/Episodic): < 5ms
- Store Fetch (Working, in-memory): < 1ms
- Store Fetch (Episodic/Semantic, persistent): < 20ms
- Artifact Hydration (when required): < 50ms (cold) / < 5ms (warm)
- **Total P99 target (no artifact): < 30ms**
- **Total P99 target (with artifact hydration): < 80ms**

These are targets, not guarantees. Implementations must measure against these targets and tune accordingly.

### 14.2 Throughput Targets

- Working Memory writes: 10,000 writes/second per execution node.
- Episodic Memory writes: 1,000 writes/second.
- Semantic/Long-term Memory writes: 100 writes/second (these are intentionally throttled; high-frequency Semantic writes suggest a design problem in the calling skill).
- Unified query throughput: 5,000 queries/second across all tiers (with index warm).

### 14.3 Policy Cache

Policy decisions are cached per `(requester_identity, operation_type, tier, scope)` with a configurable TTL (default: 60 seconds). Cache invalidation is event-driven: policy change events from RFC-0006 invalidate matching cache entries immediately.

Without this cache, a policy Engine round-trip on every memory operation would add 10–50ms latency per call, making the system unusable at high throughput. The cache introduces a short window of stale policy (up to 60 seconds), which is an accepted tradeoff given the event-driven invalidation mechanism.

### 14.4 Token Budget as First-Class Concern

The `token_budget` field in MemoryQuery is a performance-critical parameter. It prevents the Memory System from returning excessively large payloads to the skill execution layer. The Compression Engine applies budget constraints before the result is returned, ensuring that the calling skill receives a bounded payload regardless of how many matching entries exist.

**Risk:** If skills consistently set `token_budget` too low, they will receive heavily compressed or truncated memory payloads, degrading reasoning quality. Skills must be designed to request appropriate budgets based on their known context window sizes.

## 15. Scalability Analysis

### 15.1 Horizontal Scaling

The Memory System is designed to scale horizontally. Each tier manager is an independent service that can be replicated. The Memory Kernel Core is stateless (beyond the policy decision cache) and can be replicated freely.

**Sharding strategy:** Memory entries can be sharded by `scope.tenant_id` for multi-tenant deployments, and within a tenant by `scope.project_id` or `scope.session_id`. The router layer handles shard resolution.

**Index scaling:** Each Index Adapter implementation must support distributed index operation. The Memory System defines the interface; the implementation must handle distribution.

### 15.2 Scale Targets

- 10,000 concurrent skills accessing memory.
- 1 billion total memory entries per tenant across all tiers.
- 10,000 artifacts referenced by memory entries.
- 100 concurrent execution contexts with active Working Memory.
- 1,000 concurrent memory queries.

### 15.3 Scalability Risks

**Risk 1: Consolidation backlog.** If the Consolidation Pass falls behind (e.g., due to high episodic write volume), entries accumulate in the Episodic tier beyond their intended retention window. Mitigation: Consolidation pass concurrency is configurable. The Scheduler (RFC-0007) can be configured to increase consolidation frequency under high load.

**Risk 2: Index rebuild cost.** A full index rebuild for a billion-entry tier is expensive. Mitigation: Incremental rebuild — only re-index entries modified since the last successful checkpoint. The Index Manager maintains a rebuild checkpoint.

**Risk 3: User Memory isolation overhead.** Physical isolation per user (separate stores) is expensive at millions of users. Logical isolation (same store, tenant-scoped keys with policy enforcement) is a valid alternative but increases blast radius if policy is misconfigured. This is a deployment-time decision, not an architecture decision.

**Risk 4: Working Memory for many concurrent executions.** At 100 concurrent executions each holding 10,000 working memory entries, that is 1,000,000 in-memory entries. At an average of 1KB per entry, that is 1GB of in-memory working memory per node. This is manageable but must be monitored. Working Memory entries exceeding the inline size threshold must be materialized to Artifacts immediately.

## 16. Concurrency Model

### 16.1 Concurrency Guarantees per Tier

| Tier | Read Concurrency | Write Concurrency | Consistency Model |
|---|---|---|---|
| Working | Concurrent reads within execution | Exclusive write per key within execution | Sequential per key |
| Episodic | Concurrent reads | Concurrent appends (append-only) | Append-only log; read your writes |
| Semantic | Concurrent reads | Serialized writes (optimistic lock) | Last-writer-wins with version check |
| Long-term | Concurrent reads | Serialized writes (strong locking) | Linearizable per entry |
| Reflection | Concurrent reads | Concurrent appends | Append-only |
| Project | Concurrent reads within project | Serialized writes within project | Sequential per project |
| User | Single-tenant reads | Serialized writes per user | Sequential per user |

### 16.2 Optimistic Locking for Semantic Memory

Semantic Memory writes use optimistic concurrency control. The caller provides the expected `version` at write time. If the current version does not match, the write is rejected with `VERSION_CONFLICT`. The caller must re-read and retry. This avoids write locks at the cost of occasional retries. For low-contention semantic knowledge, this is the correct tradeoff.

### 16.3 Background Job Concurrency

The Consolidator and Forgetter are background jobs scheduled via RFC-0007. They use exclusive leases per tier to prevent concurrent runs on the same tier. Lease acquisition is attempted at job start; if the lease is held, the job exits immediately (the Scheduler will retry at the next interval). Lease duration equals the maximum expected job duration plus a buffer.

### 16.4 Snapshot Consistency

Full system snapshots require a coordinated snapshot across all tiers. This uses a **two-phase approach**:
1. Phase 1: Write-quiesce all tiers (pause writes for a short window — target < 100ms).
2. Phase 2: Capture snapshot pointers for all tiers simultaneously.
3. Resume writes.

This is not a distributed transaction. It is a best-effort consistent snapshot with a brief write pause. For production deployments where a 100ms write pause is unacceptable, tier-level snapshots (without the quiesce phase) should be used instead, accepting that the full snapshot is not strictly consistent across tiers.

## 17. Testing Strategy

### 17.1 Unit Tests

- Each tier manager is tested in isolation with a mock store adapter.
- The Compression Engine is tested against known input/output pairs with explicit budget constraints.
- The ranking algorithm is tested against known candidate sets with known expected orderings.
- The deduplication algorithm is tested with pairs of entries at varying similarity thresholds.
- The confidence decay algorithm is tested against known time progressions.

### 17.2 Integration Tests

- **Policy integration:** Every memory operation is tested with both PERMIT and DENY policy decisions. Every operation must correctly reject on DENY.
- **Artifact bridge:** Write a large memory entry that triggers Artifact materialization. Verify the Artifact is created. Delete the Artifact. Verify the memory entry transitions to BROKEN_REF state.
- **Event Bus integration:** Verify that every lifecycle event is published with the correct payload.
- **Scheduler integration:** Verify that Consolidator and Forgetter jobs are registered and executed on the expected schedule.

### 17.3 Consolidation Tests

- Write a sequence of episodic entries for a single session. Trigger consolidation. Verify a summary entry is written to Semantic Memory. Verify source entries are tombstoned.
- Write duplicate semantic entries. Verify deduplication merges them correctly with correct provenance.
- Write reflection entries for multiple executions with similar lessons. Verify promotion to Semantic Memory with aggregated confidence.

### 17.4 Failure Recovery Tests

- Kill the tier store mid-write. Verify WAL replay produces the correct final state.
- Kill the Policy Engine. Verify all memory operations return POLICY_ENGINE_UNAVAILABLE immediately without hanging.
- Mark an index as corrupted. Verify the system enters DEGRADED mode and returns results via full scan.

### 17.5 Concurrency Tests

- 1,000 concurrent writes to the same Semantic Memory key with optimistic locking. Verify the final state is consistent and all version conflicts are surfaced to callers.
- 100 concurrent executions each with isolated Working Memory. Verify no cross-execution leakage.

### 17.6 Scalability Tests

- Write 1 million entries to Episodic Memory. Run a consolidation pass. Measure duration and resource consumption.
- Query Semantic Memory with 10,000 concurrent readers. Measure P99 latency.
- Write 100,000 entries with varying sensitivity classes. Run a policy-mandated deletion pass for one class. Verify correct deletion and no cross-class impact.

## 18. Tradeoff Analysis

### 18.1 Seven Tiers vs. Fewer Tiers

**Decision:** Seven distinct memory tiers.

**Alternatives considered:**
- Three tiers (short, medium, long): Simpler. Rejected because the qualitative differences between Working (execution-scoped), Episodic (temporal-autobiographical), Semantic (concept-relational), Reflection (self-evaluative), User (identity-scoped), and Project (goal-scoped) are not reducible to duration alone. Collapsing them would force callers to embed tier logic in metadata, recreating the same complexity with worse ergonomics.
- One tier with full metadata classification: Maximum flexibility, maximum complexity. Rejected because it makes retrieval routing, policy enforcement, and retention policy management indistinguishable from one another. Operational clarity is lost entirely.

**Weakness:** Seven tiers mean seven store adapters, seven index adapters, and seven sets of operational concerns. This is significant operational overhead.

### 18.2 Pluggable Index Adapters vs. Mandated Vector Index

**Decision:** Pluggable Index Adapters.

**Alternatives considered:**
- Mandate a vector database (e.g., FAISS, Pinecone, Weaviate): Simpler integration story. Rejected because it violates the implementation-independence principle of this RFC series. It also couples the Memory System to embedding model availability — if no embedding model is loaded, retrieval collapses.
- Mandate BM25 / full-text search: Simpler, no embedding dependency. Rejected because semantic similarity retrieval is a genuine requirement for AGY, even if the implementation is delegated.

**Weakness:** Pluggable adapters mean that the retrieval quality is entirely determined by the adapter implementation. A poor adapter will silently produce poor results with no kernel-level warning.

### 18.3 Inline Content vs. Artifact Materialization Threshold

**Decision:** Configurable inline size threshold; above threshold, content is materialized as an Artifact.

**Alternatives considered:**
- Always store inline: Simple. Rejected because large in-memory or in-index entries degrade performance and consume index capacity for non-index data.
- Always materialize to Artifact: Every memory entry is an Artifact. Rejected because it creates enormous Artifact System overhead for the common case (small working memory entries).

**Weakness:** The threshold is a magic number. Too low: excessive Artifact System traffic. Too high: index bloat. Default (configurable) is 4KB.

### 18.4 Eventual Consistency for Consolidation vs. Strong Consistency

**Decision:** Eventual consistency for consolidation (and for index updates).

**Alternatives considered:**
- Synchronous consolidation on every write: Fully consistent. Rejected because consolidation is expensive (it may involve summarization via a skill) and would add unacceptable latency to the write path.
- Two-phase commit across tier stores: Strongly consistent consolidation. Rejected because it introduces distributed transaction complexity that is disproportionate to the benefit. Memory tiers are not financial records; temporary inconsistency during consolidation is acceptable.

**Weakness:** During the consolidation window, a query may return both the source episodic entries and the consolidation result, causing apparent duplication. The query interface should allow callers to filter by `consolidation_state` to avoid this.

### 18.5 Policy Cache vs. No Cache

**Decision:** Policy decisions are cached per-operation-type with a 60-second TTL.

**Weakness:** A policy change (e.g., a sensitivity reclassification) may take up to 60 seconds to propagate to all memory operations. For high-sensitivity tiers (User Memory), this window should be configurable to zero (no cache). This creates an uneven policy enforcement latency across tiers, which must be documented clearly.

## 19. Compatibility Notes

### 19.1 RFC-0004 (Artifact System): Artifact Lifecycle Independence

**Observation:** RFC-0004 defines Artifact lifecycle management independently of any system that references those Artifacts. There is no defined mechanism in RFC-0004 for an Artifact to notify its consumers upon deletion.

**Impact on Memory System:** Memory entries that reference Artifacts via `artifact_ref` may silently hold dangling references if the Artifact is deleted without notification.

**Resolution adopted by RFC-0010:** The Memory System subscribes to Artifact lifecycle events via the Event Bus (RFC-0006), assuming that RFC-0004 publishes `artifact.deleted` events. If RFC-0004 does not currently publish such events, this is a gap in RFC-0004 that must be addressed — either in an RFC-0004 amendment or by a registry mechanism that allows consumers to register deletion callbacks.

**This RFC does not modify RFC-0004.** It documents the assumption and requires RFC-0004 to provide an `artifact.deleted` event publication. If this is a gap in RFC-0004, it should be resolved by an RFC-0004 amendment.

### 19.2 RFC-0005 (Runtime State): Scope Fields

**Observation:** RFC-0005 defines Runtime State fields, but the exact structure of fields like `session_id`, `project_id`, and `user_id` are not explicitly verified against RFC-0005's published schema in this RFC.

**Impact on Memory System:** The Scope Resolver depends on these fields being present and well-formed in the Runtime State. If they are absent or differently named, scope resolution will fail.

**Resolution adopted by RFC-0010:** The Memory System treats missing scope fields as `null` and constructs the most specific scope possible from available fields. If `execution_id` is absent (which would be unusual), the Memory System logs a warning and uses a fallback scope of `{tenant_id: current_tenant}`. This is defensive but may produce wider-than-intended memory scopes. RFC-0005 should be reviewed to confirm the presence of these fields.

### 19.3 RFC-0006 (Event Bus): Topic Namespace Collision

**Observation:** RFC-0006 presumably defines a topic namespace convention, but this RFC introduces the `memory.*` topic namespace without confirming that it is not already reserved or in conflict with existing topics.

**Resolution adopted by RFC-0010:** The `memory.*` namespace is proposed by this RFC. RFC-0006 should maintain a registry of topic namespaces. If no such registry exists, one should be established to prevent future collisions across subsystems.

### 19.4 RFC-0007 (Scheduler): Job Priority and Resource Limits

**Observation:** RFC-0007 defines the Scheduler, but the priority model for background jobs may not have been designed with the expectation of memory system jobs that have variable and potentially long runtimes (e.g., full consolidation passes on large tiers).

**Impact on Memory System:** A long consolidation pass may consume Scheduler resources that starve other system jobs.

**Resolution adopted by RFC-0010:** All Memory System Scheduler jobs include a `max_duration_hint` to allow the Scheduler to enforce time limits and preempt runaway jobs. If RFC-0007 does not support `max_duration_hint`, this is a gap that should be addressed in an RFC-0007 amendment.

### 19.5 RFC-0003 (Policy Engine): Memory-Specific Attribute Namespace

**Observation:** RFC-0003 defines a Policy Engine, but the set of supported policy attributes may not include memory-specific attributes such as `memory_tier`, `memory_scope`, `sensitivity_class`, and `retention_policy`.

**Resolution adopted by RFC-0010:** This RFC defines these attribute names and requires them to be supported by the Policy Engine. If RFC-0003 uses a fixed attribute schema, this requires an RFC-0003 amendment. If RFC-0003 supports extensible attribute namespaces, these attributes should be registered in the `memory.*` attribute namespace.

## 20. Critical Self-Review

### 20.1 The Seven-Tier Model May Be Over-Engineered

The seven memory tiers are logically coherent and architecturally clean. In practice, the operational burden of seven separate tier managers, seven store adapters, and seven index adapters is significant. Early deployments of AGY may find that three or four tiers (Working, Episodic, Semantic, Long-term) are sufficient and that Project and User memory can be implemented as scoped views within the Semantic tier.

**Honest assessment:** This RFC designs for full capability. Implementations should start with the four core tiers and add Project and User tiers when genuine need arises. The architecture must support this phased approach — tier managers should be genuinely independent so that deploying only four of them is a valid configuration, not a half-broken one.

### 20.2 Consolidation Algorithm Is Under-Specified

The consolidation grouping algorithm uses "topic clustering" (step 2b) without defining what topic similarity means or how it is computed. This is intentional (implementation-independent), but it means that different implementations will produce different consolidation results, making the system's behavior non-deterministic across implementations.

**Honest assessment:** The consolidation algorithm section should either specify a deterministic grouping algorithm (e.g., group by shared tags, with no semantic clustering) or explicitly acknowledge that consolidation quality is implementation-dependent and will vary. Leaving this ambiguous is a specification weakness.

### 20.3 Context Compression Quality Is Not Verified

The Compression Engine produces a `CompressionManifest` that records the fidelity hash of omitted content, but there is no mechanism to verify that the compressed context actually preserves the decision-relevant information for a given skill. Compression quality is untestable without executing the skill against both the compressed and uncompressed context and comparing outcomes.

**Honest assessment:** The Compression Engine, as specified, can only guarantee token count compliance. It cannot guarantee reasoning quality preservation. This is a fundamental limitation. Future RFCs should address context quality verification, possibly through sampling and outcome comparison.

### 20.4 Forgetting Is Not Precisely Defined for All Cases

The Forgetter's five mechanisms (TTL, access-frequency decay, policy-mandated deletion, confidence decay, capacity-based eviction) interact in complex ways. An entry might be simultaneously: below its confidence threshold, above its access frequency threshold, and within its TTL. Which mechanism wins?

**Honest assessment:** This RFC does not define a total ordering over forgetting mechanisms. It should. The recommended ordering (highest priority to lowest): (1) hard delete policy mandates, (2) TTL expiry, (3) confidence threshold, (4) capacity eviction, (5) access-frequency decay. This ordering should be stated explicitly in the Forgetter's operation, not left to implementers.

### 20.5 User Memory Deletion Is Under-Specified for Distributed Systems

The `MemoryDelete` with `HARD_DELETE` on User Memory is described as removing all trace of the entry except the audit log. In a distributed system with replicated stores and derived indexes, a hard delete requires coordinated deletion across all replicas, all index shards, all caches, and all Artifact references. This is a complex distributed operation that this RFC treats as a single atomic call.

**Honest assessment:** Right-to-delete compliance is a legal requirement in many jurisdictions, and this RFC does not adequately specify the distributed delete propagation mechanism. A future RFC or amendment must address the "right-to-delete in distributed systems" problem explicitly, including replica propagation, cache invalidation, and index cleanup confirmation.

### 20.6 Snapshot Write Pause Is a Scalability Risk

The full system snapshot uses a brief write-quiesce (target < 100ms). At high write throughput, even a 100ms pause is disruptive. The alternative (tier-level snapshots without quiesce) produces an inconsistent full snapshot.

**Honest assessment:** This design accepts a difficult tradeoff with no good resolution. Production deployments at scale should prefer tier-level snapshots and accept cross-tier inconsistency in snapshots. Full system snapshots should be reserved for maintenance windows. This should be stated as a deployment recommendation, not hidden in the concurrency section.

### 20.7 The Artifact Bridge Is a Hidden Coupling Point

The Memory System depends on the Artifact System for large entry storage, snapshot storage, and export bundles. This means the Artifact System's availability directly impacts the Memory System's functionality. This is a stronger coupling than the architecture's modular design suggests.

**Honest assessment:** The Artifact bridge is correct in principle (large-object storage should not be reinvented in the Memory System), but it creates an operational dependency that must be acknowledged. Memory System deployment depends on Artifact System availability. Degraded-mode behavior (when the Artifact System is unavailable) must be explicitly defined: reject large writes with an explicit error, and continue serving small in-memory entries without Artifact hydration. This RFC touches on this in failure recovery but does not state it as clearly as it should.

## 21. Future RFC Dependencies

### RFC-0011 (Suggested): Memory Query Language

The current MemoryQuerySpec is a structured query object. A future RFC should define a formal query language (akin to SQL for relational, or GraphQL for graph structures) that allows callers to express complex retrieval requirements without constructing deeply nested query objects. This is not in scope for RFC-0010 but is a natural next step.

### RFC-0012 (Suggested): Reflection and Meta-Cognition Engine

The Reflection Memory tier is defined structurally in this RFC, but the process by which skills perform reflection (generating lessons from execution outcomes) is not defined. A future RFC should define the Reflection Engine: the skill class, the reflection protocol, the confidence aggregation mechanism, and the feedback loop from reflection to skill selection and planning.

### RFC-0013 (Suggested): Memory Anomaly Detection

At scale, the Memory System will accumulate entries from thousands of skills. Detecting anomalous write patterns (a skill writing to Semantic Memory at abnormally high frequency), memory poisoning attempts (entries with inconsistent provenance), and cross-tenant probe attempts (queries probing scope boundaries) requires an active monitoring subsystem. This RFC records events and enforces policy, but does not analyze patterns.

### RFC-0014 (Suggested): Right-to-Delete and Data Sovereignty

As identified in the Critical Self-Review, the distributed deletion problem for User Memory requires its own RFC. This RFC should define the delete propagation protocol, replica coordination, cache invalidation confirmation, index cleanup verification, and audit logging format for compliance purposes.

### RFC-0015 (Suggested): Memory Federation

At multi-tenant and multi-region scale, memory tiers may be distributed across administrative boundaries. A Memory Federation RFC should define how memory scopes are resolved and how retrieval spans federated memory stores, while maintaining strict tenant isolation.

### RFC-0016 (Suggested): Context Quality Verification

The Compression Engine's quality limitation (acknowledged in the Critical Self-Review) requires a future RFC that defines a mechanism for verifying that a compressed context preserves sufficient information for the requesting skill to produce an equivalent outcome. This likely involves statistical sampling, outcome comparison, and feedback to the compression strategy selector.

### Dependency on RFC-0008 and RFC-0009

If RFC-0008 defines model routing and RFC-0009 defines token budgeting (this is assumed, not confirmed), then:
- **Model routing (RFC-0008):** The Memory System's Compression Engine must be aware of the token limit of the target model. The model routing decision may be made before memory retrieval, in which case the `token_budget` in the memory query should be derived from the model's context limit. The exact integration point must be defined when RFC-0008's contract is available.
- **Token budgeting (RFC-0009):** If RFC-0009 defines a system-wide token budget ledger, the Memory System's context compression should consume tokens from that ledger rather than applying a locally-specified budget. Integration with RFC-0009 should be formalized once its contract is confirmed.
