## 1. Executive Overview

RFC-0013 defines the **Reflection Engine** for the AGY AI Operating System. The Reflection Engine is the subsystem responsible for systematic, structured post-execution analysis of everything AGY does: how it planned, how it executed, what failed, what succeeded, why decisions were made, whether those decisions were good, and what should be different next time.

The Reflection Engine does not act. It does not modify plans. It does not change policies. It does not update the Skill Registry. It does not retrain models. It observes, analyzes, scores, and writes. Its outputs are **Reflection Artifacts** — structured, versioned, policy-controlled documents that record what the engine observed and concluded. These Artifacts are consumed by downstream systems, the most significant of which is the Learning Engine (a future RFC), which translates Reflection outputs into durable behavioral changes. The separation between observation and action is the defining architectural constraint of this subsystem.

This separation is not arbitrary. It exists because reflection and action operate on different timescales, require different authorities, and carry different risks. Reflection must be fast, cheap, and safe — it can run after every execution without fear of causing harm, because it changes nothing. Action is slow, expensive, and dangerous — changing how a system behaves requires evidence accumulated across many reflections, careful review, and explicit authorization. By making the Reflection Engine a pure observer and producer, AGY gains the ability to reflect continuously without the risk of continuous self-modification.

The Reflection Engine is also not a simple logger. Logs record what happened. The Reflection Engine analyzes what happened in the context of what was intended, what was expected, what alternatives existed, and what the outcomes reveal about the system's understanding of the world. It performs execution review, failure analysis, architectural critique, quality scoring, decision scoring, lesson extraction, and recommendation generation. These are structured analytical processes with defined algorithms, defined outputs, and defined confidence scores — not ad-hoc commentary.

The broader systems context is important. AGY is a kernel that coordinates AI reasoning and execution at scale. As that scale grows — thousands of skills, hundreds of concurrent executions, millions of tool invocations — the gap between what was planned and what actually happened will accumulate faster than human operators can manually review. The Reflection Engine is the mechanism by which that accumulation is processed into structured, actionable intelligence rather than noise. It is the observability layer for the system's own cognition.

## 2. Responsibilities

**Execution Review**
- Consuming execution records (plans, task outcomes, tool results, timing data, resource usage) from the Event Bus and Artifact System after execution completes.
- Constructing a complete, unified view of an execution from its distributed traces: what was planned, what was attempted, what succeeded, what failed, in what order, at what cost.
- Detecting discrepancies between what was planned (RFC-0011 Execution Graph) and what actually executed (RFC-0007 runtime records).

**Failure Analysis**
- Classifying failures by type: planning failures, task execution failures, tool invocation failures, resource exhaustion failures, policy denials, timeout failures, and unexpected state failures.
- Attributing failures to root causes when attributable: skill defects, tool unreliability, plan construction errors, policy misconfiguration, resource contention, or environmental conditions.
- Computing failure cascades: identifying when a single failure propagated through the execution graph to cause multiple downstream failures.
- Distinguishing recoverable failures (handled by retries, replanning, or fallback) from unrecoverable failures (execution terminated without producing the goal result).

**Architectural Critique**
- Evaluating the quality of the plan that was executed: was it the optimal decomposition, were there unnecessary steps, were dependencies correctly identified, was parallelism properly exploited?
- Identifying structural inefficiencies: serialized task chains that could have been parallelized, over-specified plans that constrained execution unnecessarily, under-specified plans that required excessive replanning.
- Detecting recurring architectural patterns across multiple executions that suggest systemic planning or decomposition problems.

**Quality Scoring**
- Assigning a structured quality score to each completed execution along multiple dimensions: goal achievement, plan quality, execution efficiency, resource efficiency, reliability, and tool utilization quality.
- Producing per-dimension scores with supporting evidence, not just aggregate scores.
- Maintaining score distributions over time to detect quality degradation or improvement trends.

**Decision Scoring**
- Evaluating individual decisions made during execution: method selection decisions (RFC-0011), skill selection decisions (RFC-0001), tool routing decisions (RFC-0012), and policy evaluation decisions (RFC-0003).
- Scoring decisions against the alternatives that were considered and rejected at decision time.
- Identifying decisions that were locally optimal but globally suboptimal.

**Lesson Extraction**
- Deriving generalizable lessons from specific execution experiences.
- Classifying lessons by type: skill reliability observations, tool performance observations, planning heuristic observations, environmental constraint observations, policy effectiveness observations.
- Computing lesson confidence: a lesson observed once has low confidence; a lesson observed consistently across many executions accumulates high confidence.
- Writing lessons to Reflection Memory (RFC-0010) with appropriate confidence scores and provenance.

**Recommendation Generation**
- Generating structured, actionable recommendations based on extracted lessons.
- Classifying recommendations by target: skill improvement recommendations, tool substitution recommendations, plan strategy recommendations, policy adjustment recommendations, resource configuration recommendations.
- Ranking recommendations by expected impact and confidence.
- Attaching recommendations to Reflection Artifacts for downstream consumption.

**Reflection Artifacts**
- Producing a well-formed, versioned Reflection Artifact for every analyzed execution.
- Materializing Reflection Artifacts to RFC-0004 Artifact System with appropriate lineage, linking the Reflection Artifact to the Plan Artifact (RFC-0011) and the execution records it analyzed.
- Making Reflection Artifacts queryable by execution ID, skill type, tool ID, failure class, quality score range, and time range.

**Confidence Recalibration**
- Comparing plan-time confidence estimates (RFC-0011) against actual execution outcomes.
- Computing calibration error: how far off were the plan-time estimates?
- Writing calibration observations to Reflection Memory for use by RFC-0011's Cost and Confidence Estimator to improve future estimates.
- Detecting systematic bias: does the Planner consistently over-estimate or under-estimate confidence for specific skill types, tool types, or goal domains?

## 3. Non-Goals

The following are explicitly outside the scope of RFC-0013:

- **Modifying any runtime component directly.** The Reflection Engine has no write access to RFC-0001, RFC-0002, RFC-0003, RFC-0007, RFC-0011, or RFC-0012. It cannot change skill registrations, policy rules, scheduled jobs, or plan strategies.
- **Implementing the Learning Engine.** The Learning Engine (a future RFC) consumes Reflection Artifacts and translates them into behavioral changes. The Reflection Engine produces the input to this process; it does not execute the process.
- **Real-time monitoring or alerting.** The Reflection Engine analyzes completed executions. Real-time monitoring is the domain of observability infrastructure external to the kernel.
- **Human-readable report generation.** Reflection Artifacts are structured data for machine consumption. Formatting them for human readers is a presentation layer concern.
- **Performing reflection during execution.** Reflection is post-execution. In-execution decision revision belongs to the Replanning mechanism (RFC-0011).
- **Accessing raw model completions or token streams.** The Reflection Engine works with structured execution records, not with the raw outputs of LLM calls.
- **Making policy decisions.** The Reflection Engine may observe that a policy appears suboptimal and generate a recommendation, but it cannot evaluate or enforce policy.
- **Compensating actions.** If an execution caused a side effect that should be undone, triggering compensating actions is the runtime's concern, not reflection's.
- **Providing explanations directly to users.** User-facing explanations are a presentation concern. The Reflection Engine produces structured analysis; human-readable explanation generation is downstream.

## 4. Relationship to Previous RFCs

### RFC-0001: Skill Resolver

The Reflection Engine does not call the Skill Resolver. However, Reflection Artifacts contain `skill_reliability_observations` keyed by `skill_id` and `skill_version`. These observations are the primary input for future skill selection decisions. The Reflection Engine thus influences RFC-0001 indirectly through the Memory System and the Learning Engine — never directly.

**Interaction:** One-way data production. Reflection Engine writes skill observations to RFC-0010 Reflection Memory. RFC-0001 will consume these (via the Learning Engine or via Planner RFC-0011) to adjust skill selection confidence. RFC-0001 does not call RFC-0013.

### RFC-0002: Skill Registry & Loader

Skill manifests (RFC-0002) contain declared behavior: expected latency ranges, expected reliability, declared side effects, declared resource usage. The Reflection Engine reads these declarations to compute **expectation deltas**: the difference between what the skill declared it would do and what it actually did. A large expectation delta is itself a lesson: the skill's manifest is inaccurate.

**Interaction:** Reflection Engine reads skill manifests from RFC-0002 at analysis time. Read-only. RFC-0002 does not call RFC-0013.

**Cache behavior:** Skill manifests are read once per reflection session and cached for the session duration. If a skill manifest is updated between execution time and reflection time, the Reflection Engine uses the manifest version that was active at execution time (retrieved from the Plan Artifact, which pins the Method Library version). This ensures reflection compares against the expectations that were in force when the plan was made.

### RFC-0003: Policy Engine

The Reflection Engine's own operations are policy-gated: not every identity can trigger reflection on every execution, and access to Reflection Artifacts is controlled by policy. Additionally, the Reflection Engine may identify policy decisions that appear to have contributed to execution failures and include these as policy effectiveness observations in the Reflection Artifact.

**Interaction:** Reflection Engine calls RFC-0003 for its own access control. It also reads the policy decision records stored in Plan Artifacts and InvocationRecords (RFC-0012) to analyze policy effectiveness. It never modifies policy.

**New policy attribute namespace:** RFC-0003 must support `reflection.*` attributes: `reflection.execution_id`, `reflection.requester_identity`, `reflection.artifact_sensitivity`. These must be registered in RFC-0003's attribute namespace.

### RFC-0004: Artifact System

The Reflection Engine is a heavy consumer of RFC-0004 in two directions:

**Reading:** The Reflection Engine reads Plan Artifacts (RFC-0011), InvocationRecord Artifacts (RFC-0012), execution trace records, and any output Artifacts produced during the execution being analyzed. These are the raw inputs to the analysis process.

**Writing:** Every completed reflection produces a Reflection Artifact written to RFC-0004. The Reflection Artifact's lineage links it to all the source Artifacts it was derived from. This creates a traceable provenance chain: from execution outputs, through reflection, to learning inputs.

**Artifact lineage:** The Reflection Artifact's `lineage.derived_from` field lists: the Plan Artifact ID, all relevant InvocationRecord Artifact IDs, and any output Artifact IDs from the execution. This allows the lineage graph to be traversed from any point.

**Interaction:** Bidirectional. Reflection Engine reads source Artifacts from RFC-0004. Reflection Engine writes Reflection Artifacts to RFC-0004. The Reflection Engine does not modify existing Artifacts.

### RFC-0005: Runtime State

By definition, reflection occurs after execution completes. The Runtime State for the analyzed execution is no longer active. The Reflection Engine reads the **finalized** execution record from the execution trace — a structured snapshot of Runtime State at execution completion — not the live Runtime State.

**Interaction:** Indirect. The Reflection Engine reads execution trace data that was derived from RFC-0005 during execution. It does not interact with live RFC-0005 state.

### RFC-0006: Event Bus

The Reflection Engine subscribes to execution lifecycle events to know when to begin reflection. It also publishes reflection lifecycle events for observability.

**As subscriber:**
- `scheduler.execution.completed` — primary trigger for post-execution reflection.
- `scheduler.execution.failed` — trigger for failure-focused reflection.
- `scheduler.execution.cancelled` — trigger for cancellation analysis.
- `planner.plan.completed` — to retrieve plan details before execution records are cleaned up.
- `tool.contract.violation` — to prioritize tool reliability analysis in the next reflection.
- `tool.invocation.failed` — to pre-index tool failures for aggregation.

**As publisher:**
- `reflection.started`
- `reflection.completed`
- `reflection.failed`
- `reflection.lesson.extracted`
- `reflection.recommendation.generated`
- `reflection.confidence.recalibration.completed`

**Interaction:** The Reflection Engine is primarily event-driven. Executions trigger reflection; reflection produces events. The Event Bus is the coordination mechanism.

### RFC-0007: Scheduler

The Scheduler drives the execution of Tasks within a plan. The Scheduler's execution records — task dispatch times, completion times, retry events, resource allocations, and cancellation records — are essential inputs to the Reflection Engine's execution review and quality scoring processes.

The Reflection Engine also registers background jobs with the Scheduler for:
- **Batch reflection:** Analyzing batches of low-priority executions that do not warrant immediate reflection.
- **Trend analysis:** Periodic aggregation of reflection observations across multiple executions to detect trends.
- **Calibration update jobs:** Periodic computation of updated calibration parameters based on accumulated observations.

**Interaction:** Reflection Engine reads Scheduler execution records (via Artifact System). Reflection Engine registers background jobs with RFC-0007. RFC-0007 does not call the Reflection Engine directly.

### RFC-0010: Memory System

The Memory System is the Reflection Engine's primary output channel for lessons and calibration observations. The Reflection Engine writes to two memory tiers:

**Reflection Memory:** The designated tier for skill reliability observations, tool performance observations, planning heuristic observations, and confidence calibration data. Written after every reflection session that produces lessons with sufficient confidence.

**Episodic Memory:** A brief summary of each reflection session is written to Episodic Memory, enabling temporal queries across reflection history: "Show me all reflections in the past 7 days that identified tool reliability issues."

**Reading:** The Reflection Engine reads prior Reflection Memory entries during trend analysis: have similar lessons been observed before? If so, confidence accumulates and the lesson may be ready for promotion to Semantic Memory by the Memory System's Consolidator.

**Interaction:** Reflection Engine writes to RFC-0010 Reflection and Episodic Memory tiers. Reflection Engine reads prior Reflection Memory entries for trend analysis. Memory writes are performed after the Reflection Artifact has been finalized and written to RFC-0004 — the Artifact is the authority; Memory is a derived index.

### RFC-0011: Planner

The Planner produces Plan Artifacts that are the primary structural input to the Reflection Engine's architectural critique and decision scoring processes. The Reflection Engine evaluates the quality of every plan it analyzes.

Additionally, the Reflection Engine's confidence calibration observations are specifically designed to improve RFC-0011's Cost and Confidence Estimator. Every time the Planner's plan-time confidence estimate deviates significantly from the actual execution outcome, the Reflection Engine records this as a calibration observation.

**Interaction:** Reflection Engine reads Plan Artifacts produced by RFC-0011. Reflection Engine writes calibration observations to RFC-0010 Reflection Memory that RFC-0011 will later consume. RFC-0011 does not call RFC-0013.

**Hidden coupling:** The schema of calibration observations written by RFC-0013 must match what RFC-0011 expects to read. This schema must be jointly specified (see Compatibility Notes).

### RFC-0012: Tool Runtime

The Tool Runtime produces InvocationRecords for every tool call. These records are the primary input to the Reflection Engine's tool reliability analysis, tool cost analysis, and tool utilization quality scoring.

Additionally, RFC-0012's contract violation events (`tool.contract.violation`) are subscribed to by the Reflection Engine, which incorporates them into the next reflection that involves the violating tool.

**Interaction:** Reflection Engine reads InvocationRecord Artifacts from RFC-0012 (via RFC-0004). Reflection Engine subscribes to `tool.contract.violation` events. RFC-0012 does not call RFC-0013.

## 5. Architecture

### 5.1 Architectural Philosophy

The Reflection Engine is architected around three principles drawn from the broader systems tradition:

**Principle 1: Separation of observation from action.** The Reflection Engine is a read-heavy analytical subsystem. It reads widely (plans, execution records, tool records, memory) but writes narrowly (Reflection Artifacts, Memory entries). Every write produces a structured, versioned, immutable artifact. No write modifies existing system state.

**Principle 2: Analysis pipelines, not monolithic analyzers.** The analysis of a completed execution is decomposed into a sequence of independent analytical stages. Each stage reads the outputs of prior stages and produces its own structured output. This pipeline structure enables: partial analysis (some stages may fail without invalidating others), parallel execution of independent stages, and independent testing of each stage.

**Principle 3: Evidence-grounded conclusions.** Every score, every lesson, every recommendation is backed by specific evidence drawn from the execution record. The Reflection Artifact does not contain opinions; it contains scored conclusions with evidence citations. This makes the Reflection Artifact auditable: a human or another system can trace any conclusion back to the specific execution event that grounded it.

### 5.3 The Analysis Pipeline

The Analysis Pipeline is the core of the Reflection Engine. It is a directed, partially-ordered sequence of analytical stages. Each stage:
- Receives a `ReflectionContext` containing all loaded execution data and the outputs of all prior stages.
- Produces a typed `StageOutput` that is added to the `ReflectionContext` for subsequent stages.
- May be skipped if the data required for that stage is unavailable (graceful degradation).
- Records its own execution metadata: duration, data completeness, confidence in its outputs.

Stages that share no data dependencies may execute concurrently. The pipeline implementation manages this concurrency.

**Stage dependency ordering:**
```
ExecutionReviewer
    │
    ├── FailureAnalyzer (depends on: ExecutionReviewer)
    │
    ├── DecisionScorer (depends on: ExecutionReviewer)
    │
    └── ArchitecturalCritic (depends on: ExecutionReviewer, FailureAnalyzer)
              │
              └── QualityScorer (depends on: ExecutionReviewer, FailureAnalyzer,
                                             ArchitecturalCritic, DecisionScorer)
                        │
                        └── LessonExtractor (depends on: all prior stages)
                                  │
                                  └── RecommendationGenerator (depends on: all prior stages)
                                            │
                                            └── ConfidenceRecalibrator (depends on: all prior stages)
```

## 6. Internal Components

### 6.1 Trigger Manager

The Trigger Manager is the Reflection Engine's event consumer. It listens to RFC-0006 for execution lifecycle events and initiates reflection sessions.

**Trigger types:**

1. **Immediate trigger:** `scheduler.execution.completed` or `scheduler.execution.failed` events trigger immediate reflection for high-priority executions (those with `priority: HIGH` or `CRITICAL` in their plan).

2. **Deferred trigger:** Lower-priority executions are queued for batch reflection. The batch job runs on a Scheduler-driven schedule (RFC-0007, default: every 5 minutes), processing the queue in priority order.

3. **Explicit trigger:** The public `Reflect` interface allows authorized identities to request reflection on a specific execution immediately, overriding the normal trigger priority.

4. **Periodic aggregate trigger:** A Scheduler job (RFC-0007, default: daily) triggers trend analysis across all reflections in the past period.

**Trigger deduplication:** If a reflection session for a given `execution_id` is already in progress or completed, duplicate trigger events are silently discarded. An execution is reflected upon exactly once unless an explicit re-reflection is requested.

**Trigger delay:** For immediate triggers, a configurable delay (default: 2 seconds) is applied before reflection begins. This allows all execution completion events to propagate through the Event Bus and all execution records to be fully committed to RFC-0004 before the Reflection Engine attempts to read them. Without this delay, reflection may begin before all source records are available.

### 6.2 Execution Record Loader

The Execution Record Loader assembles the complete input dataset for the Analysis Pipeline. It collects:

1. **Plan Artifact** (RFC-0011): The planned Execution Graph, including decomposition tree, scheduling hints, confidence estimates, and policy annotations.

2. **Scheduler execution record**: Task dispatch events, completion events, retry events, resource allocations, and task durations. Retrieved from the Artifact System where the Scheduler persists execution records.

3. **InvocationRecords** (RFC-0012): All tool invocation records associated with this execution, retrieved from RFC-0004.

4. **Runtime State snapshot**: The finalized execution context — identity, session, project, timing — retrieved from the execution trace.

5. **Prior Reflection Memory**: Relevant prior reflection observations for the same skill types and tool types, loaded from RFC-0010 Reflection Memory. These provide baseline context: is this execution's behavior typical or unusual compared to prior observations?

**Completeness assessment:** The Loader records which sources were successfully loaded and which were unavailable (e.g., InvocationRecords for tools that did not write records due to failure). Incomplete data reduces the confidence of the analysis stages that depend on the missing data, but does not prevent reflection from proceeding.

**Data pinning:** All source data is pinned at load time. If a source Artifact is modified or deleted after loading (unusual but possible), the reflection uses the loaded version. Reflection is always against a consistent snapshot, not live data.

### 6.3 Execution Reviewer

The Execution Reviewer is the first pipeline stage. It constructs a unified, structured view of the execution by reconciling the planned Execution Graph against the actual execution record.

**Outputs:**

1. **Execution Timeline:** A chronologically ordered sequence of events: what happened, when, for how long, and with what result. Derived from Scheduler records and InvocationRecords.

2. **Plan vs. Actual Comparison:** For each Task in the Execution Graph:
   - Was the Task executed? (Yes / No / Partial)
   - Did it complete successfully? (Yes / No / Retried successfully / Retried unsuccessfully)
   - Planned duration vs. actual duration.
   - Planned token cost vs. actual token cost.
   - Planned tool vs. actual tool (if tool routing occurred via RFC-0012's capability selector).
   - Were all expected output Artifacts produced?

3. **Execution Coverage Ratio:** The fraction of planned Tasks that were executed and completed successfully. A ratio of 1.0 means all planned work was done. Lower ratios indicate partial execution (due to failures, cancellations, or early termination on success).

4. **Replanning Events:** Any replanning events (RFC-0011 Replan operations) that occurred during the execution, with their triggers and the structural changes they introduced.

5. **Concurrency Utilization:** Were parallel-eligible Tasks actually executed concurrently? If not, why? (Resource contention, Scheduler priority decisions, dependency evaluation errors.)

### 6.4 Failure Analyzer

The Failure Analyzer takes the Execution Reviewer's output and performs deep analysis of any failures that occurred.

**Failure classification taxonomy:**

```
FailureClass {
  PLANNING_FAILURE {
    sub_types: NO_METHOD_FOUND | DEPTH_LIMIT_EXCEEDED |
               CONFIDENCE_BELOW_THRESHOLD | POLICY_BLOCKED_AT_PLAN_TIME
  }
  TASK_EXECUTION_FAILURE {
    sub_types: SKILL_ERROR | SKILL_TIMEOUT | SKILL_UNAVAILABLE |
               OUTPUT_SCHEMA_VIOLATION | UNEXPECTED_STATE
  }
  TOOL_INVOCATION_FAILURE {
    sub_types: CONNECTOR_FAILURE | TOOL_TIMEOUT | TOOL_RATE_LIMITED |
               TOOL_AUTH_FAILURE | TOOL_CONTRACT_VIOLATION |
               SANDBOX_VIOLATION | QUOTA_EXCEEDED
  }
  RESOURCE_FAILURE {
    sub_types: MEMORY_EXHAUSTION | TOKEN_BUDGET_EXCEEDED |
               CONCURRENT_LIMIT_REACHED | STORAGE_FULL
  }
  POLICY_FAILURE {
    sub_types: RUNTIME_POLICY_DENIAL | CREDENTIAL_UNAVAILABLE |
               PERMISSION_ESCALATION_DENIED
  }
  ENVIRONMENTAL_FAILURE {
    sub_types: EXTERNAL_DEPENDENCY_UNAVAILABLE | NETWORK_PARTITION |
               INFRASTRUCTURE_FAILURE
  }
  GOAL_FAILURE {
    sub_types: GOAL_UNSATISFIABLE_AT_RUNTIME | GOAL_CONTRADICTED_BY_OUTPUT |
               GOAL_PARTIALLY_ACHIEVED
  }
}
```

**Cascade analysis:** The Failure Analyzer builds a failure cascade graph: a directed graph where edges indicate "failure A caused or contributed to failure B." A single tool timeout that caused a downstream skill to receive no input, which caused a downstream planning step to fail, is a cascade of depth 3 from a single root cause. Cascade graphs are included in the Reflection Artifact.

**Root cause attribution:** The Failure Analyzer assigns an `attribution_confidence` to each root cause identification:
- `HIGH`: The causal chain is direct and unambiguous (tool returned HTTP 500 → InvocationRecord shows TOOL_INTERNAL_ERROR → task failed).
- `MEDIUM`: The causal chain is plausible but involves inference (task took 10× planned time → timeout fired → downstream tasks starved for input).
- `LOW`: The failure is observed but the root cause is not determinable from available data (task returned an unexpected state with no error code or trace).

**Distinguishing fault from variance:** Not all deviations from the plan are failures. The Failure Analyzer distinguishes:
- **Hard failures:** The execution could not proceed without a replanning event or produced no result.
- **Soft failures:** The execution completed but with degraded quality (partial results, lower confidence output, slower than expected).
- **Expected variance:** Deviations within the tolerance bands declared in skill manifests and tool contracts.

### 6.5 Architectural Critic

The Architectural Critic evaluates the structural quality of the plan that was executed, independent of whether the plan succeeded or failed. A well-structured plan can still fail due to environmental conditions. A poorly-structured plan may accidentally succeed. The Architectural Critic evaluates structure, not outcome.

**Critique dimensions:**

1. **Decomposition appropriateness:** Was the chosen Method the most appropriate for the goal and context, given the alternatives available? The Critic retrieves all applicable Methods for each task type (from RFC-0002, via the Execution Record Loader) and evaluates whether the selected Method was appropriate given the actual execution context.

2. **Dependency accuracy:** Were all dependency edges in the Execution Graph correct? Were there any false dependencies (serialized tasks that could have safely run in parallel)? Were there any missing dependencies (parallel tasks that actually needed a specific ordering)?
   - False dependencies are detected by: tasks with a dependency edge between them where the downstream task's actual inputs did not include any outputs from the upstream task.
   - Missing dependencies are detected by: parallel tasks where the downstream task's actual inputs included data that was produced by the upstream task after the downstream task started (race condition).

3. **Parallelism exploitation:** What fraction of the theoretically parallel work was structured as parallel in the plan? A plan that serializes all work when 60% could be parallel is architecturally suboptimal regardless of whether it succeeds.

4. **Over-specification:** Did the plan include Tasks that were never needed? Tasks that were planned but not executed because an earlier Task's output already satisfied the goal are evidence of over-specification.

5. **Under-specification:** Did the execution require replanning to add Tasks that should have been predictable at plan time? These are evidence of under-specification.

6. **Estimation accuracy:** How close were the plan-time estimates to actuals? Systematic over- or under-estimation of specific task types suggests that the estimator's data for those types is stale or biased.

**Critique output:** A structured `ArchitecturalCritiqueReport` with a critique for each dimension, a score (0.0–1.0, where 1.0 is architecturally optimal), and specific evidence citations from the Execution Timeline.

### 6.6 Decision Scorer

The Decision Scorer evaluates individual decisions made during execution against the alternatives that were considered. It focuses on decisions where alternatives existed — where a decision was made between multiple plausible options.

**Decision types analyzed:**

1. **Method selection decisions (RFC-0011):** At each decomposition step, the Method Selector ranked applicable Methods and chose the highest-priority applicable one. The Decision Scorer evaluates: given the actual execution outcome, was the selected Method a good choice? If the second-ranked Method was available and the selected Method failed, this is a `WRONG_ALTERNATIVE_SELECTED` finding.

2. **Tool routing decisions (RFC-0012):** The Capability Selector chose a specific tool from multiple available options. The Decision Scorer evaluates: given the actual invocation outcome (latency, error rate, cost), was the selected tool the best available option?

3. **Skill selection decisions (RFC-0001):** When multiple skills could resolve a given task type, how was the specific instance chosen? Was the choice appropriate given the actual execution context?

4. **Replanning decisions:** If replanning occurred, was the chosen replan strategy (PATCH vs. FULL_REPLAN) appropriate? Did the PATCH leave residual structural problems that a FULL_REPLAN would have avoided?

**Scoring methodology:**

For each scored decision:
```
DecisionScore {
  decision_id: UUID
  decision_type: METHOD_SELECTION | TOOL_ROUTING | SKILL_SELECTION | REPLAN_STRATEGY
  chosen_option: OptionReference
  considered_alternatives: [OptionReference]
  outcome: CORRECT | SUBOPTIMAL | WRONG | INDETERMINATE
  counterfactual_analysis: CounterfactualAnalysis
  score: float (0.0–1.0)
  confidence: float (0.0–1.0)
  evidence: [EvidenceRecord]
}
```

**Counterfactual analysis:** For `WRONG` or `SUBOPTIMAL` decisions, the Decision Scorer performs a limited counterfactual: "If alternative X had been chosen instead, what outcome was likely?" Counterfactuals are bounded in scope — they do not simulate full alternative executions. They apply simple heuristics: "The second-ranked tool for this capability had a historical success rate of 0.95 versus 0.72 for the chosen tool for this error class."

**Counterfactual confidence:** Counterfactual confidence is always lower than the primary decision confidence. The Decision Scorer applies a fixed counterfactual confidence discount (default: 0.3 subtracted from the primary confidence). This prevents counterfactuals from being treated as certain conclusions.

### 6.7 Quality Scorer

The Quality Scorer produces the composite quality score for the execution. It aggregates the outputs of the Execution Reviewer, Failure Analyzer, Architectural Critic, and Decision Scorer into a multi-dimensional quality assessment.

**Quality dimensions:**

```
QualityScoreCard {
  execution_id: UUID

  goal_achievement: DimensionScore {
    // Did the execution produce the intended result?
    // 1.0 = goal fully achieved
    // 0.5 = goal partially achieved
    // 0.0 = goal not achieved
    score: float
    evidence: [EvidenceRecord]
  }

  plan_quality: DimensionScore {
    // How well-structured was the plan?
    // Derived from ArchitecturalCritiqueReport.
    score: float
    evidence: [EvidenceRecord]
  }

  execution_efficiency: DimensionScore {
    // Actual duration vs. theoretically minimum achievable duration.
    // Accounts for necessary serialization; penalizes unnecessary serialization.
    score: float
    evidence: [EvidenceRecord]
  }

  resource_efficiency: DimensionScore {
    // Actual resource consumption vs. planned.
    // Penalizes over-consumption; rewards under-consumption
    // (within quality bounds — under-consumption via shortcuts is penalized separately).
    score: float
    evidence: [EvidenceRecord]
  }

  reliability: DimensionScore {
    // What fraction of planned Tasks completed without failure?
    // What fraction of failures were handled gracefully (retry/replan) vs. fatal?
    score: float
    evidence: [EvidenceRecord]
  }

  decision_quality: DimensionScore {
    // Aggregate of DecisionScorer scores.
    score: float
    evidence: [EvidenceRecord]
  }

  tool_utilization_quality: DimensionScore {
    // Were tools used appropriately?
    // Were tool results used correctly?
    // Were tools invoked at appropriate frequency?
    score: float
    evidence: [EvidenceRecord]
  }

  aggregate_score: float
    // Weighted average of dimension scores.
    // Weights are configurable per deployment; defaults:
    // goal_achievement: 0.30
    // plan_quality: 0.15
    // execution_efficiency: 0.15
    // resource_efficiency: 0.10
    // reliability: 0.15
    // decision_quality: 0.10
    // tool_utilization_quality: 0.05

  score_confidence: float
    // Confidence in the quality scores themselves.
    // Reduced when source data is incomplete.

  scoring_version: string
    // Version of the quality scoring algorithm.
    // Required for comparing scores across algorithm versions.
}
```

**Score stability:** Quality scores are not absolute values. They are relative to the scoring algorithm version. The `scoring_version` field allows downstream consumers to normalize scores across algorithm updates. The Learning Engine must not compare scores from different `scoring_version` values without normalization.

### 6.8 Lesson Extractor

The Lesson Extractor derives generalizable lessons from the specific findings of the analysis pipeline. Lessons are the primary output consumed by the Learning Engine and stored in RFC-0010 Reflection Memory.

**Lesson taxonomy:**

```
LessonType {
  SKILL_RELIABILITY_OBSERVATION {
    // "Skill S with parameters P in context C has reliability R."
    skill_id: SkillID
    skill_version: string
    context_tags: [string]
    observed_success_rate: float
    observed_latency_p50_ms: integer
    observed_latency_p99_ms: integer
    sample_count: integer
  }

  TOOL_PERFORMANCE_OBSERVATION {
    // "Tool T for capability C has observed latency L, error rate E,
    //  and cost C in context X."
    tool_id: UUID
    capability_name: string
    context_tags: [string]
    observed_success_rate: float
    observed_latency_p50_ms: integer
    observed_latency_p99_ms: integer
    observed_cost_units: float
    error_class_distribution: map<ToolErrorClass, float>
    sample_count: integer
  }

  PLANNING_HEURISTIC_OBSERVATION {
    // "For goals of type G, Method M produces better outcomes than
    //  Method M' under conditions C."
    goal_type: string
    context_tags: [string]
    preferred_method_id: MethodID
    avoided_method_id: MethodID
    preference_confidence: float
    evidence_summary: string
  }

  ESTIMATION_CALIBRATION_OBSERVATION {
    // "Plan-time estimates for skill type S are systematically biased
    //  by factor F in the direction D."
    skill_type: string
    context_tags: [string]
    planned_value: float
    actual_value: float
    bias_direction: OVER_ESTIMATE | UNDER_ESTIMATE
    bias_magnitude: float
    metric: LATENCY | TOKEN_COST | CONFIDENCE | RESOURCE_USAGE
    sample_count: integer
  }

  ARCHITECTURAL_PATTERN_OBSERVATION {
    // "Execution graphs of type G have recurring structural inefficiency I."
    goal_type: string
    pattern_type: FALSE_DEPENDENCY | UNDER_PARALLELIZED |
                  OVER_SPECIFIED | UNDER_SPECIFIED
    occurrence_count: integer
    impact_estimate: string
  }

  FAILURE_PATTERN_OBSERVATION {
    // "Failure type F recurs in context C with frequency R."
    failure_class: FailureClass
    context_tags: [string]
    recurrence_rate: float
    common_root_causes: [string]
    sample_count: integer
  }

  POLICY_EFFECTIVENESS_OBSERVATION {
    // "Policy P caused N denials in context C; X% of those denials
    //  appear to have been correct; Y% appear to have been false positives."
    policy_id: string
    context_tags: [string]
    denial_count: integer
    apparent_false_positive_rate: float
    confidence: float
    note: "Policy correctness cannot be determined by the Reflection Engine alone.
           This observation is a signal, not a verdict."
  }
}
```

**Lesson confidence computation:**

```
lesson.confidence = base_confidence × data_quality_factor × recurrence_factor

base_confidence:
  Single observation: 0.3
  Consistent with prior observations: 0.6
  Contradicts prior observations: 0.2 (conflict must be resolved)

data_quality_factor:
  All source data complete: 1.0
  Minor gaps in source data: 0.85
  Significant gaps: 0.6
  Major gaps: 0.3

recurrence_factor:
  First observation: 1.0
  Confirmed by 2–4 prior observations: 1.2 (up to max of 1.0 total, capped)
  Confirmed by 5+ prior observations: 1.4 (capped)
  Contradicts prior observations: 0.5
```

**Lesson deduplication:** Before writing a new lesson to RFC-0010, the Lesson Extractor queries Reflection Memory for prior lessons of the same type and context. If a prior lesson exists, the new observation is merged (confidence updated, sample count incremented, last_seen_at updated) rather than creating a duplicate entry. This is the accumulation mechanism by which confidence builds over time.

### 6.9 Recommendation Generator

The Recommendation Generator translates extracted lessons into structured, actionable recommendations. Recommendations are targeted at specific downstream systems and specific operators. They are suggestions, not commands.

**Recommendation types:**

```

  SKILL_IMPROVEMENT {
    target: SkillID
    finding: string
    recommendation: string
    expected_impact: ImpactEstimate
    priority: RecommendationPriority
  }

  TOOL_SUBSTITUTION {
    current_tool_id: UUID
    current_capability: string

    finding: string
    recommendation: string
    expected_impact: ImpactEstimate
  }

  METHOD_STRATEGY {
    goal_type: string
    context_tags: [string]
    current_method_pattern: string
    recommended_method_pattern: string
    finding: string
    expected_impact: ImpactEstimate
  }

  RESOURCE_CONFIGURATION {
    resource_type: string
    finding: string
    recommendation: string
    expected_impact: ImpactEstimate
  }

  POLICY_REVIEW {
    policy_id: string
    finding: string
    recommendation: string

  }

    direction: INCREASE | DECREASE

    confidence: float
  }

```

**Recommendation ranking:**

```
recommendation.priority_score =
  (impact_weight × normalized_expected_impact) +
  (confidence_weight × recommendation.lesson.confidence) +
  (recurrence_weight × recurrence_score(recommendation))
```

Default weights: impact=0.5, confidence=0.3, recurrence=0.2.

**Recommendation lifecycle:** Recommendations are included in the Reflection Artifact. They are not automatically acted upon. The Learning Engine (future RFC) reads recommendations from Reflection Artifacts and decides which to act on, based on accumulated evidence and authorized change policies.

### 6.10 Confidence Recalibrator

The Confidence Recalibrator specifically addresses the gap between RFC-0011's plan-time confidence estimates and actual execution outcomes. This is a focused, quantitative analysis.

**Calibration process:**

For each Task in the Execution Graph:
```
planned_confidence = task.confidence (from Plan Artifact)
actual_outcome = SUCCESS | FAILURE | RETRY_SUCCESS | TIMEOUT
actual_outcome_binary = 1.0 if SUCCESS or RETRY_SUCCESS else 0.0

calibration_error = planned_confidence - actual_outcome_binary
  // Positive: overconfident (predicted success, got failure)
  // Negative: underconfident (predicted failure, got success)
  // Zero: perfectly calibrated

calibration_observation = {
  skill_type: task.skill_type,
  context_tags: extracted_context_tags(task),
  confidence_factor_types: [f.factor_type for f in task.confidence_factors],
  planned_confidence: planned_confidence,
  actual_outcome_binary: actual_outcome_binary,
  calibration_error: calibration_error,
  execution_id: current_execution_id,
  observed_at: now()
}
```

**Bias detection:** Across multiple calibration observations for the same skill type and context:
```
mean_calibration_error = mean([obs.calibration_error for obs in observations])

IF abs(mean_calibration_error) > BIAS_THRESHOLD (default: 0.15):
  bias_direction = OVERCONFIDENT if mean_calibration_error > 0 else UNDERCONFIDENT
  emit ESTIMATION_CALIBRATION_OBSERVATION lesson with bias_direction and magnitude
```

**Calibration observations are written to Reflection Memory.** They are later read by RFC-0011's Cost and Confidence Estimator to adjust its estimation parameters. The adjustment mechanism is defined in the Confidence Calibration RFC (future dependency of RFC-0011), but the Reflection Engine's role — generating the raw calibration observations — is defined here.

### 6.11 Reflection Artifact Composer

The Composer assembles the complete Reflection Artifact from the outputs of all pipeline stages and writes it to RFC-0004.

**Composition steps:**
1. Collect all stage outputs from the `ReflectionContext`.
2. Validate completeness: which stages completed, which were skipped, which failed.
3. Compute overall reflection confidence: the minimum confidence across all completed stages, weighted by stage importance.
4. Assemble the `ReflectionArtifact` structure (defined in Data Structures).
5. Write to RFC-0004 with lineage linking to all source Artifacts.
6. Write summary to RFC-0010 Episodic Memory.
7. Write lessons to RFC-0010 Reflection Memory.
8. Publish `reflection.completed` event to RFC-0006.

## 9. Runtime Lifecycle

### 9.1 System Startup

```
1. Reflection Engine loads configuration.
2. Policy Gate initializes (reads reflection-specific policy rules from RFC-0003).
3. Reflection Artifact index loaded (from RFC-0004 metadata index for
   reflection.* artifact type).
4. Lesson index loaded (from RFC-0010 Reflection Memory, bootstrapped
   from persisted state).
5. Pending reflection queue loaded (executions that were queued
   before the last restart and not yet processed).
6. RFC-0006 Event Bus subscriptions registered.
7. Background jobs registered with RFC-0007 Scheduler:
   - Deferred reflection batch job.
   - Trend analysis job.
   - Calibration report generation job.
   - Lesson expiry and pruning job.
8. reflection.engine.ready event published to RFC-0006.
```

### 9.2 Reflection Session Lifecycle

```
1. Trigger received (event or explicit Reflect() call).
2. Policy Gate evaluated: can this identity trigger reflection on this execution?
3. Duplicate check: is a reflection for this execution_id already in progress
   or completed? If completed and force_rereflection=false: return existing artifact.
4. Execution Record Loader assembles input dataset.
5. ReflectionContext initialized.
6. Analysis Pipeline begins:
   a. ExecutionReviewer executes.
   b. FailureAnalyzer and DecisionScorer execute concurrently
      (both depend only on ExecutionReviewer output).
   c. ArchitecturalCritic executes (depends on ExecutionReviewer + FailureAnalyzer).
   d. QualityScorer executes (depends on all prior stages).
   e. LessonExtractor executes (depends on all prior stages).
   f. RecommendationGenerator executes (depends on all prior stages).
   g. ConfidenceRecalibrator executes (depends on all prior stages).
7. Reflection Artifact Composer assembles the ReflectionArtifact.
8. ReflectionArtifact written to RFC-0004.
9. Lessons written to RFC-0010 Reflection Memory.
   (Existing lessons updated; new lessons created.)
10. Reflection session summary written to RFC-0010 Episodic Memory.
11. Calibration observations written to RFC-0010 Reflection Memory
    (as ESTIMATION_CALIBRATION_OBSERVATION lessons).
12. reflection.completed event published to RFC-0006 with:
    - reflection_id
    - execution_id
    - reflection_artifact_ref
    - aggregate_quality_score
    - lesson_count
    - recommendation_count
```

### 9.3 Trend Analysis Lifecycle

```
1. Trend analysis job triggered by RFC-0007 Scheduler (default: daily).
2. Query RFC-0010 Reflection Memory for lessons active in the past period.
3. Group lessons by:
   - skill_type (for skill reliability trends)
   - tool_id + capability_name (for tool performance trends)
   - goal_type (for planning heuristic trends)
   - failure_class (for failure pattern trends)
4. For each group:
   a. Compute trend direction (improving / degrading / stable).
   b. Compute trend confidence (based on sample count and variance).
   c. Identify outlier executions in the trend.
5. For degrading trends above threshold: generate TREND_DEGRADATION recommendation.
6. For improving trends: update lesson confidence upward.
7. Write trend analysis summary as Episodic Memory entry.
8. Publish reflection.trend_analysis.completed event.
```

### 9.4 Calibration Report Generation Lifecycle

```
1. Calibration report job triggered by RFC-0007 Scheduler (default: weekly).
2. Query RFC-0010 Reflection Memory for all ESTIMATION_CALIBRATION_OBSERVATION
   lessons with sample_count >= min_sample_count.
3. Group by skill_type + metric.
4. Compute mean_calibration_error, bias_direction, bias_magnitude,
   confidence_interval for each group.
5. Compute overall system calibration score.
6. Write CalibrationReport to RFC-0004 as a specialized Artifact.
7. Write calibration report summary to RFC-0010 Episodic Memory.
8. Publish reflection.calibration_report.generated event.
```

## 11. Algorithms

### 11.1 Failure Cascade Analysis Algorithm

```
PROCEDURE build_cascade_graph(failures: [FailureRecord],
                               execution_timeline: [TimelineEvent])
                               → CascadeGraph:

  graph = CascadeGraph(nodes=failures, edges=[])
  root_failures = []

  // Sort failures by occurrence time
  sorted_failures = sort_by(failures, key=occurred_at)

  FOR EACH failure IN sorted_failures:

    // Find potential causes: failures that occurred before this one
    // and whose failed entity is upstream of this failure's entity
    potential_causes = [
      f FOR f IN sorted_failures
      WHERE f.occurred_at < failure.occurred_at
      AND is_upstream(f.failed_entity_id, failure.failed_entity_id,
                      execution_timeline)
    ]

    IF potential_causes is empty:
      root_failures.append(failure.failure_id)
    ELSE:
      FOR EACH cause IN potential_causes:
        // Determine cascade type
        IF direct_dependency_exists(cause.failed_entity_id,
                                     failure.failed_entity_id):
          cascade_type = DIRECT
        ELIF temporal_proximity(cause.occurred_at,
                                 failure.occurred_at) < PROXIMITY_THRESHOLD:
          cascade_type = PROBABLE
        ELSE:
          cascade_type = POSSIBLE

        graph.edges.append(CascadeEdge(
          cause_failure_id = cause.failure_id,
          effect_failure_id = failure.failure_id,
          cascade_type = cascade_type
        ))

  graph.root_failures = root_failures
  graph.max_cascade_depth = compute_max_depth(graph)
  RETURN graph

PROCEDURE is_upstream(entity_a: string, entity_b: string,
                       timeline: [TimelineEvent]) → boolean:
```

### 11.2 Dependency Accuracy Analysis Algorithm

```
PROCEDURE analyze_dependency_accuracy(execution_graph: ExecutionGraph,
                                       invocation_records: [InvocationRecord],
                                       timeline: [TimelineEvent])
                                       → DependencyAccuracyReport:

  false_dependencies = []
  missing_dependencies = []

  FOR EACH edge IN execution_graph.edges WHERE edge.dependency_type == DATA:

    source_task = execution_graph.nodes[edge.source_node_id]
    target_task = execution_graph.nodes[edge.target_node_id]

    // Check for false dependency:
    // Did the target task actually use an artifact from the source task?
    source_artifacts = artifacts_produced_by(source_task, invocation_records)
    target_inputs = artifacts_consumed_by(target_task, invocation_records)

    IF intersection(source_artifacts, target_inputs) is empty:
      false_dependencies.append(FalseDependency(
        edge_id = edge.edge_id,
        source_task = source_task.node_id,
        target_task = target_task.node_id,
        impact = UNNECESSARY_SERIALIZATION
      ))

  // Check for missing dependencies (race conditions):
  FOR EACH pair (task_a, task_b) IN parallel_eligible_task_pairs(execution_graph):
    a_artifacts = artifacts_produced_by(task_a, invocation_records)
    b_inputs = artifacts_consumed_by(task_b, invocation_records)
    b_completion = completion_time(task_b, timeline)
    a_completion = completion_time(task_a, timeline)

    IF intersection(a_artifacts, b_inputs) is not empty:
      IF a_completion > start_time(task_b, timeline):
        // task_b started before task_a completed, but consumed task_a's output.
        // This is a race condition: task_b should depend on task_a.
        missing_dependencies.append(MissingDependency(
          producer_task = task_a.node_id,
          consumer_task = task_b.node_id,
          shared_artifact_type = intersection(a_artifacts, b_inputs)
        ))

  RETURN DependencyAccuracyReport(
    false_dependencies = false_dependencies,
    missing_dependencies = missing_dependencies,
    accuracy_score = 1.0 - (len(false_dependencies) + len(missing_dependencies) * 2)
                          / len(execution_graph.edges)
      // Missing dependencies weighted 2× because they are safety issues,
      // not just efficiency issues.
  )
```

### 11.3 Lesson Confidence Update Algorithm

```
PROCEDURE update_lesson_confidence(existing_lesson: Lesson,
                                    new_observation: LessonObservation)
                                    → Lesson:

  // Check for contradiction
  IF contradicts(new_observation, existing_lesson):
    // Contradiction: weight by sample counts
    existing_weight = existing_lesson.sample_count
    new_weight = 1  // New observation counts as 1 sample

    IF new_weight / (existing_weight + new_weight) > CONTRADICTION_THRESHOLD:
      // New observation is strong enough to mark lesson as CONTRADICTED
      existing_lesson.status = CONTRADICTED
      RETURN existing_lesson
    ELSE:
      // New observation is not strong enough; reduce confidence
      existing_lesson.confidence = existing_lesson.confidence × 0.85
      RETURN existing_lesson

  // Confirmation: accumulate
  existing_lesson.sample_count += 1
  existing_lesson.last_observed_at = now()

  // Bayesian-inspired confidence update
  prior = existing_lesson.confidence
  likelihood = new_observation.evidence_strength  // 0.0–1.0
  normalizer = prior × likelihood + (1 - prior) × (1 - likelihood)
  posterior = (prior × likelihood) / normalizer

  existing_lesson.confidence = min(posterior, MAX_LESSON_CONFIDENCE)
    // MAX_LESSON_CONFIDENCE = 0.95
    // No lesson ever reaches 1.0; always some epistemic uncertainty.

  // Update lesson content (merge new observation data)
  existing_lesson = merge_observation(existing_lesson, new_observation)

  RETURN existing_lesson
```

### 11.4 Quality Score Aggregation Algorithm

```
PROCEDURE compute_quality_score(scorecard: QualityScoreCard,
                                 weights: DimensionWeights) → float:

  weighted_sum = 0.0
  total_weight = 0.0

  FOR EACH dimension IN scorecard.dimensions:
    IF dimension.score is not null AND dimension.evidence is not empty:
      weighted_sum += weights[dimension.name] × dimension.score
      total_weight += weights[dimension.name]
    ELSE:
      // Dimension is unavailable due to missing data.
      // Do not include in weighted average; do not penalize.
      // But record the gap in scorecard metadata.

  IF total_weight == 0.0:
    RETURN null  // No scoreable dimensions; do not produce aggregate.

  raw_aggregate = weighted_sum / total_weight

  // Confidence adjustment:
  // Aggregate score confidence is reduced when fewer dimensions are scored.
  dimension_coverage = total_weight / sum(weights.values())
  scorecard.score_confidence = scorecard.score_confidence × dimension_coverage

  RETURN raw_aggregate
```

### 11.5 Counterfactual Analysis Algorithm

```
PROCEDURE analyze_counterfactual(decision: DecisionScore,
                                  reflection_context: ReflectionContext)
                                  → CounterfactualAnalysis:

  chosen_option = decision.chosen_option
  alternatives = decision.considered_alternatives

  IF alternatives is empty:
    RETURN CounterfactualAnalysis(
      applicable = false,
      reason = "No alternatives were considered at decision time"
    )

  counterfactuals = []

  FOR EACH alternative IN alternatives:
    // Retrieve historical performance data for this alternative
    historical = reflection_context.prior_reflection_memory
      .filter(skill_type=alternative.skill_type OR tool_id=alternative.tool_id)
      .filter(context_tags ⊇ reflection_context.execution_context_tags)

    IF historical is empty:
      estimated_outcome = UNKNOWN
      counterfactual_confidence = 0.1  // Very low; no data.
    ELSE:
      estimated_success_rate = mean([h.observed_success_rate for h in historical])
      estimated_latency = mean([h.observed_latency_p50_ms for h in historical])

      estimated_outcome = SUCCESS if estimated_success_rate > 0.7 else UNCERTAIN

      counterfactual_confidence = min(
        len(historical) / MIN_SAMPLE_FOR_CONFIDENT_COUNTERFACTUAL,
        1.0
      ) × 0.7  // Cap at 0.7: counterfactuals are inherently uncertain.

    counterfactuals.append(CounterfactualOutcome(
      alternative = alternative,
      estimated_outcome = estimated_outcome,
      estimated_success_rate = estimated_success_rate,
      estimated_latency_ms = estimated_latency,
      counterfactual_confidence = counterfactual_confidence,
      data_source = historical.source_description()
    ))

  // Rank alternatives by estimated outcome quality
  ranked = sort_by(counterfactuals, key=estimated_success_rate, descending=true)

  best_alternative = ranked[0] if ranked else null

  was_chosen_optimal = (
    best_alternative is null OR
    chosen_option.historical_success_rate >= best_alternative.estimated_success_rate
  )

  RETURN CounterfactualAnalysis(
    applicable = true,
    best_alternative = best_alternative,
    all_alternatives = ranked,
    was_chosen_optimal = was_chosen_optimal,
    counterfactual_confidence = mean([c.counterfactual_confidence for c in counterfactuals])
  )
```

## 12. Failure Recovery

### 12.1 Reflection Engine's Own Failure Modes

The Reflection Engine must be resilient to failures in its own operation. Critically: **a failure of the Reflection Engine must never impact the execution path**. Reflection is always post-execution. Its failure degrades observability and learning, not operational capability.

| Failure | Impact | Recovery |
|---|---|---|
| Source Artifact unavailable | Incomplete analysis | Proceed with available data; reduce confidence scores; record data gap |
| RFC-0010 Memory write failure | Lessons not persisted | Retry with exponential backoff; lessons remain in Reflection Artifact as fallback |
| RFC-0004 Artifact write failure | No persistent Reflection Artifact | Retry; if persistent failure, publish `reflection.artifact_write_failed` event with in-memory result summary |
| Analysis stage timeout | Stage output unavailable | Mark stage as TIMED_OUT in pipeline metadata; continue pipeline with missing stage output |
| Policy Engine unavailable | Cannot evaluate reflection policy | Fail-closed: deny reflection request; queue for retry when PE recovers |
| Event Bus unavailable | Reflection triggered manually; events not published | Continue reflection; attempt event publication when EB recovers; buffer events in memory |
| Lesson deduplication failure | Duplicate lessons written | Periodic cleanup job removes duplicates; eventual consistency |
| Calibration write failure | Calibration data not persisted | Included in Reflection Artifact; Learning Engine can re-extract from Artifact |

### 12.2 Analysis Stage Failure Handling

Each analysis stage is wrapped in an error boundary. If a stage throws an unhandled error or exceeds its timeout:

```
1. Stage status recorded as FAILED or TIMED_OUT.
2. Stage error recorded in ReflectionContext.stage_statuses.
3. Dependent stages that cannot proceed without this stage's output are marked SKIPPED.
4. Independent stages continue unaffected.
5. Final Reflection Artifact is composed with whatever stages completed.
6. reflection_confidence is reduced by the confidence_weight of each failed stage.
7. ReflectionArtifact.status = PARTIAL if any stages failed; COMPLETED otherwise.
```

**Stage timeouts (configurable; defaults):**
- ExecutionReviewer: 10 seconds
- FailureAnalyzer: 15 seconds
- ArchitecturalCritic: 20 seconds
- DecisionScorer: 15 seconds
- QualityScorer: 10 seconds
- LessonExtractor: 30 seconds
- RecommendationGenerator: 20 seconds
- ConfidenceRecalibrator: 10 seconds
- **Total reflection session timeout: 120 seconds**

### 12.3 Replay and Re-reflection

If a reflection session fails completely (LOAD_FAILED or TIMED_OUT), the execution is re-queued for reflection with a backoff delay. If the failure persists across 3 attempts, the execution is marked `REFLECTION_FAILED` and a `reflection.persistent_failure` event is published. The execution record is not discarded — it remains available for manual reflection via the explicit `Reflect()` interface.

Re-reflection (when `force_rereflection=true`) creates a new ReflectionArtifact with an incremented version and a `parent_reflection_id` pointing to the prior reflection. Both versions are retained in RFC-0004.

### 12.4 Startup Recovery

On restart, the Reflection Engine:
1. Loads all reflection sessions that were IN_PROGRESS at the time of the previous shutdown (identified by sessions present in the pending queue with ANALYZING or WRITING status).
2. For each recovered session: begins fresh (does not attempt to resume a partial pipeline). The Analysis Pipeline is idempotent: running it twice on the same source data produces the same result.
3. Lesson deduplication prevents duplicate lesson creation from repeated reflections.

## 13. Security Considerations

### 13.1 Threat Model

**Threats specific to the Reflection Engine:**

1. **Reflection data access:** Reflection Artifacts contain detailed execution records including failure information, decision alternatives, and tool invocation patterns. An attacker with access to Reflection Artifacts could use this information to identify exploitable patterns in AGY's decision-making.

2. **Lesson poisoning:** An attacker who can influence execution outcomes (e.g., by controlling a tool's responses) could cause the Reflection Engine to extract false lessons. If those lessons influence future planning (via RFC-0011) or skill selection (via the Learning Engine), the attacker has influenced AGY's behavior indirectly.

3. **Recommendation injection:** If the Recommendation interface can be accessed by unauthorized identities, false recommendations could be injected into the recommendation queue, potentially causing the Learning Engine to make harmful changes.

4. **Calibration manipulation:** Systematic manipulation of execution outcomes to produce biased calibration observations, causing the Planner to systematically under- or over-estimate confidence for specific skill types.

5. **Cross-execution information leakage:** If reflection of execution A includes context from execution B (e.g., prior reflection context), and execution B belongs to a different tenant, sensitive information from B may be included in A's Reflection Artifact.

### 13.2 Defense Mechanisms

**Reflection data access:** Reflection Artifacts are stored in RFC-0004 with access control enforced by RFC-0003. Reflection Artifacts inherit the highest sensitivity class of any source Artifact they were derived from. By default, Reflection Artifacts are accessible only to the identity that triggered the execution and to administrative identities with explicit reflection-read policy grants.

**Lesson poisoning:** Lessons require accumulation across multiple executions before reaching high confidence. A single manipulated execution produces a lesson with confidence 0.3 — too low to significantly influence planning decisions. To reach high confidence, manipulation would need to be sustained across many executions, which increases the chance of detection through other monitoring channels. Additionally, lessons are attributed to their source executions; an unusual concentration of lesson updates from a single tool or skill is a detectable anomaly.

**Recommendation injection:** The `AcknowledgeRecommendation` interface is policy-gated. Recommendations can only be acknowledged by identities with `reflection.recommendation.acknowledge` policy. Recommendation creation is internal to the Reflection Engine; external callers cannot inject recommendations.

**Calibration manipulation:** Calibration observations carry source attribution (execution_id, skill_type, context_tags). Systematic bias in calibration data for a specific tool or skill (e.g., all executions involving tool T report identical anomalous latency) is detectable in the trend analysis pass. The trend analysis publishes a `CALIBRATION_ANOMALY` event when it detects suspiciously consistent outliers.

**Cross-execution leakage:** Prior reflection context is only loaded for executions within the same `scope.tenant_id`. Cross-tenant reflection context is explicitly prohibited. The Execution Record Loader validates that all loaded records share the same `tenant_id` as the current execution before including them in the `ReflectionContext`.

### 13.3 Sensitivity of Reflection Outputs

Reflection Artifacts are not just audit logs. They contain analytical conclusions about system behavior, failure patterns, and architectural weaknesses. This information is sensitive because:

- Failure patterns reveal which parts of the system are weak.
- Tool reliability observations reveal tool performance that vendors may consider proprietary.
- Policy effectiveness observations contain information about policy gaps.
- Decision scoring reveals the alternatives considered and rejected at execution time.

All of this information must be treated as at least as sensitive as the most sensitive execution that contributed to it. Sensitivity classification must propagate through the lineage chain.

### 13.4 The Reflection Engine Cannot Modify Runtime

The most important security property of the Reflection Engine is what it **cannot** do. It has no write access to any component that affects runtime behavior. It cannot modify skill registrations (RFC-0002), policy rules (RFC-0003), execution graphs (RFC-0011), or tool registrations (RFC-0012). Its only outputs are Reflection Artifacts (RFC-0004), Memory entries (RFC-0010), and Event Bus publications (RFC-0006, read-only from RFC-0006's perspective). This write-narrowness is enforced at the kernel level: the Reflection Engine's service identity has no policy grants for write operations on runtime-affecting components.

## 14. Performance Analysis

### 14.1 Reflection Latency Targets

Reflection is not on the execution critical path. Its latency targets are generous compared to execution-time subsystems:

| Trigger type | Target P50 | Target P99 |
|---|---|---|
| Immediate (high-priority execution) | < 5 seconds | < 30 seconds |
| Deferred (batch processing) | < 5 minutes | < 30 minutes |
| Trend analysis (daily batch) | < 10 minutes | < 60 minutes |
| Calibration report (weekly) | < 30 minutes | < 2 hours |

### 14.2 Pipeline Stage Latency Breakdown (typical medium execution)

```
Execution Record Loading:       1,000ms (Artifact reads from RFC-0004)
ExecutionReviewer:              500ms
FailureAnalyzer + DecisionScorer (concurrent): 1,000ms
ArchitecturalCritic:            1,500ms (most computationally intensive)
QualityScorer:                  300ms
LessonExtractor:                800ms (includes RFC-0010 read for deduplication)
RecommendationGenerator:        500ms
ConfidenceRecalibrator:         200ms
Artifact Composition:           300ms
RFC-0004 write:                 500ms
RFC-0010 writes:                400ms
Event publication:              100ms (async)
─────────────────────────────────────────
Total wall-clock (P50 estimate): ≈ 7,100ms (with FailureAnalyzer/DecisionScorer concurrent)
```

This is well within the 30-second P99 target for immediate reflection.

### 14.3 Data Loading Optimization

Loading InvocationRecord Artifacts for a complex execution (e.g., 50 tool invocations) requires 50 separate Artifact reads. At 20ms per read, this is 1,000ms sequentially. The Execution Record Loader performs Artifact reads concurrently (up to a configurable max concurrency, default: 20), reducing practical loading time to approximately `ceil(50/20) × 20ms = 60ms`. Artifact read caching (within the loading session) prevents duplicate reads when the same Artifact is referenced multiple times.

### 14.4 Memory Query Cost

The Lesson Extractor queries RFC-0010 Reflection Memory for prior lessons matching the skill types and tool IDs observed in the current execution. For an execution involving 10 skill types and 5 tools, this may require 15 separate Memory queries. These are performed concurrently and use the RFC-0010 index for sub-10ms per query. Total Memory query time: approximately 50ms (bounded by index performance).

## 15. Scalability Analysis

### 15.1 Scale Targets

- 1,000 reflection sessions per hour (matching 1,000 executions/hour).
- 10,000 active lessons in Reflection Memory.
- 100,000 Reflection Artifacts in RFC-0004.
- 1,000,000 CalibrationObservations across all lessons.
- Trend analysis across 10,000 reflections in the past 30 days.

### 15.2 Reflection Queue Scalability

The deferred reflection queue must handle bursts: if 1,000 executions complete simultaneously (e.g., after a scheduled batch job), 1,000 reflection triggers arrive within seconds. The queue must not drop triggers. The queue is persisted (survives restarts). The batch reflection job processes queue items concurrently (configurable; default: 10 concurrent reflection sessions). At 10 concurrent sessions and 7 seconds per session, throughput is approximately 86 reflections/minute — sufficient for most steady-state workloads. For burst scenarios, the queue depth grows; the backlog clears at the steady-state throughput rate.

**Burst mitigation:** For very high-volume deployments, the Reflection Engine should support horizontal scaling (multiple instances each processing a partition of the reflection queue). Queue partitioning is by `execution_id` hash, ensuring that the same execution is always processed by the same instance (idempotency).

### 15.3 Lesson Store Scalability

At 10,000 active lessons with an average of 1KB each, the lesson store is approximately 10MB — trivially small. The lesson store grows slowly: lessons accumulate confidence rather than creating new entries for every observation. The Lesson Extractor's deduplication algorithm ensures that 1,000 observations of the same skill behavior create one lesson with sample_count=1000, not 1,000 separate lessons.

**Long-term growth:** Lessons for deprecated skill types, removed tools, or superseded methods accumulate over time. The lesson expiry job (RFC-0007 scheduled, default: weekly) archives lessons whose source entities no longer exist, keeping the active lesson store bounded.

### 15.4 Scalability Risks

**Risk 1: Reflection Artifact accumulation.** At 1,000 reflections/hour, 24 hours/day, the system produces 24,000 Reflection Artifacts per day. At an average of 50KB per Artifact, that is 1.2GB per day. Over a year: 438GB. RFC-0004 must support Artifact TTL policies for Reflection Artifacts; older Reflection Artifacts may be archived or deleted per policy, retaining only the lessons they produced (which are much smaller).

**Risk 2: ArchitecturalCritic computational cost.** The Architectural Critic's dependency accuracy analysis is O(E × T) where E is the number of edges in the Execution Graph and T is the number of timeline events. For very large executions (500 tasks, 5,000 events), this is 2,500,000 comparisons. The stage timeout (20 seconds default) bounds the worst case, but very large executions may produce partial architectural critiques. The algorithm should be optimized with early termination when the analysis score is already at a threshold.

**Risk 3: Trend analysis at scale.** A daily trend analysis across 10,000 reflections, each with 10–20 lessons, requires processing 100,000–200,000 lesson observations. This is a significant batch operation. It must be scheduled during low-traffic periods and must not compete with immediate reflection sessions for resources.

## 16. Concurrency Model

### 16.1 Reflection Session Concurrency

Multiple reflection sessions execute concurrently (up to the configured maximum). Sessions are fully isolated: each session has its own `ReflectionContext` with its own loaded data. There is no shared mutable state between concurrent reflection sessions.

**Shared resources:**
- RFC-0004 (Artifact reads and writes): concurrent access handled by RFC-0004's internal concurrency model.
- RFC-0010 (Memory reads and writes): lesson deduplication requires optimistic locking on lesson entries.
- RFC-0006 (Event publication): concurrent event publications are handled by RFC-0006's internal concurrency model.

### 16.2 Pipeline Stage Concurrency

Within a single reflection session, pipeline stages execute with the dependency ordering described in Section 5.3. Specifically:
- `FailureAnalyzer` and `DecisionScorer` execute concurrently (both depend only on `ExecutionReviewer`).
- All other stages execute sequentially due to data dependencies.

The concurrent stages share read-only access to the `ReflectionContext`. Neither stage writes to the `ReflectionContext` during concurrent execution. Their outputs are collected after both complete, then merged into the context for the next stage.

### 16.3 Lesson Write Concurrency

Multiple concurrent reflection sessions may attempt to update the same lesson simultaneously (e.g., two executions involving the same skill type complete simultaneously, triggering two concurrent reflections that both extract lessons about that skill). Lesson writes use optimistic locking:

```
1. Session A reads lesson L, version=5.
2. Session B reads lesson L, version=5.
3. Session A writes updated lesson, expected_version=5. Succeeds: version=6.
4. Session B writes updated lesson, expected_version=5. Fails: VERSION_CONFLICT.
5. Session B re-reads lesson L, version=6.
6. Session B recomputes update based on version=6 and writes. Succeeds: version=7.
```

The merged result correctly reflects both sessions' observations.

## 17. Testing Strategy

### 17.1 Unit Tests

**ExecutionReviewer:**
- Execution where all tasks completed as planned: verify coverage ratio = 1.0, no replanning events, concurrency utilization ratio matches planned parallelism.
- Execution with mid-plan failure and successful replan: verify replanning event captured, coverage ratio reflects pre-failure incomplete work.
- Execution with all tasks failed: verify coverage ratio = 0.0, execution timeline reflects failures in order.

**FailureAnalyzer:**
- Single isolated failure: verify root cause attribution, cascade graph has one node, cascade depth = 1.
- Cascade failure (tool failure → task failure → downstream task failure): verify cascade graph has three nodes, root failure is the tool failure, cascade depth = 3, attribution confidence appropriate.
- Recovered failure (retry succeeded): verify failure classified as RECOVERED, recovery_mechanism=RETRY.

**ArchitecturalCritic:**
- Execution with documented false dependency (two tasks serialized unnecessarily): verify false dependency detected, efficiency score penalized.
- Execution with missing dependency (race condition): verify missing dependency detected, score penalized more heavily than false dependency.
- Optimal plan: verify all critique dimensions score at or near 1.0.

**LessonExtractor:**
- First observation of a skill type: verify new lesson created with confidence=0.3.
- Repeated observation consistent with prior: verify existing lesson updated, confidence increased, sample_count incremented.
- Contradicting observation: verify lesson confidence reduced, contradiction flag set.

**ConfidenceRecalibrator:**
- Task planned at confidence 0.9, succeeded: calibration_error = -0.1 (underconfident; planned success, got success, but calibration_error = planned - actual = 0.9 - 1.0 = -0.1).
- Task planned at confidence 0.9, failed: calibration_error = 0.9 (overconfident).
- 10 observations of same skill type all overconfident by similar margin: verify BIAS_DETECTED, ESTIMATION_CALIBRATION_OBSERVATION lesson generated.

### 17.2 Integration Tests

**End-to-end reflection:** Run a complete execution through RFC-0007 (simulated). Trigger reflection. Verify Reflection Artifact is written to RFC-0004. Verify lessons are written to RFC-0010. Verify events published to RFC-0006.

**Policy integration:** Verify that reflection on an execution by an unauthorized identity is denied. Verify that Reflection Artifact access is denied to non-owning identities.

**Re-reflection:** Reflect on an execution. Call Reflect() again with force_rereflection=true. Verify new Reflection Artifact created with incremented version and parent_reflection_id pointing to prior.

**Lesson accumulation:** Run 10 executions with the same skill type and consistent failure pattern. Verify lesson confidence increases monotonically. Verify lesson promoted from OBSERVED to ACCUMULATING.

### 17.3 Adversarial Tests

**Lesson poisoning attempt:** Run 5 manipulated executions that produce false performance data for a specific tool. Verify lesson confidence for that tool remains below the HIGH_CONFIDENCE_THRESHOLD. Verify the calibration anomaly detection triggers when the manipulated data is inconsistent with broader patterns.

**Cross-tenant leakage:** Execute two executions from different tenants. Trigger reflection on execution A. Verify that execution B's records are not included in execution A's ReflectionContext.

**Stage timeout:** Inject a slow implementation of ArchitecturalCritic (sleeps beyond timeout). Verify pipeline continues with TIMED_OUT status for that stage. Verify other stages complete. Verify Reflection Artifact is composed with PARTIAL status.

### 17.4 Regression Tests

Reflection output should be deterministic for the same input data. Regression tests capture Reflection Artifact outputs for known input datasets and verify that algorithm changes do not silently change outputs. Changes to scoring weights, lesson confidence formulas, or cascade analysis logic must be accompanied by deliberate regression test updates.

## 18. Tradeoff Analysis

### 18.1 Post-Execution Only vs. In-Execution Reflection

**Decision:** Reflection is strictly post-execution.

**Rejected alternative:** In-execution reflection (reflecting on partial execution state to influence ongoing decisions).

**Rationale:** In-execution reflection blurs the boundary between reflection and planning/execution. If reflection can influence an ongoing execution, the Reflection Engine becomes a runtime decision-maker, not an observer. This violates the core architectural constraint. Additionally, in-execution reflection introduces latency into the critical execution path.

**Weakness:** Some failures that could be averted with in-execution reflection will complete without correction. A plan that is clearly going wrong halfway through could theoretically be corrected by real-time reflection. This capability is not in scope for this RFC and is not lost — it is delegated to the Replanning mechanism (RFC-0011) and a future Execution Monitor RFC.

### 18.2 Immediate vs. Deferred Reflection

**Decision:** Tiered: immediate for high-priority executions, deferred for lower-priority.

**Rejected alternatives:**
- Always immediate: consumes resources even when not urgent; may impact execution throughput by competing for I/O with active executions.
- Always deferred: delays lesson extraction and calibration updates; high-priority failures go unanalyzed for minutes.

**Weakness:** The prioritization of immediate vs. deferred is based on execution priority, not on the severity of what happened. A low-priority execution that encountered a critical failure (e.g., a data corruption event) would be deferred rather than immediately reflected upon. A future enhancement should allow the Trigger Manager to escalate deferred reflections to immediate when the Failure Analyzer detects severe failure classes — but this requires the Failure Analyzer to run before the trigger decision, which is a pipeline ordering problem. This is an acknowledged gap.

### 18.3 Evidence-Grounded Scoring vs. Holistic AI-Generated Scoring

**Decision:** Structured, evidence-grounded, algorithmic scoring.

**Rejected alternative:** Use a language model to produce holistic quality assessments and lesson extractions.

**Rationale:** LLM-generated assessments would be non-deterministic, difficult to test, opaque in their reasoning, and subject to the model's own biases. A Reflection Engine that uses an LLM to reflect on AI execution is vulnerable to the LLM's failure modes: hallucination, inconsistency, and context window limitations. The structured algorithmic approach is deterministic, testable, and auditable. Every score is traceable to specific evidence.

**Weakness:** Structured algorithms cannot detect the quality of the *content* of execution — whether the goal was actually satisfied, whether an intermediate result was factually correct, whether a generated plan was semantically sound. Quality scoring in this RFC is structural: efficiency, reliability, dependency accuracy. Semantic quality — was the output actually good? — requires some form of evaluation that cannot be fully reduced to structural metrics. This gap is acknowledged and requires a future RFC addressing semantic evaluation.

### 18.4 Single Reflection Artifact per Execution vs. Multiple Specialized Artifacts

**Decision:** One Reflection Artifact per execution (containing all analytical outputs).

**Rejected alternative:** Separate Artifacts for failure analysis, quality scores, lessons, and recommendations.

**Rationale:** A single Artifact simplifies lineage: one Artifact derived from one execution. Querying, access control, and versioning are all simpler on a single Artifact. The individual sections of the Artifact are individually addressable via the structured schema.

**Weakness:** For large executions with many tasks and tool invocations, the Reflection Artifact may be large (hundreds of KB to several MB). RFC-0004's Artifact size limits and performance characteristics must accommodate this. The Reflection Artifact may need to be split into a header (small; indexable) and a body (large; stored as a referenced sub-Artifact) for performance.

### 18.5 Lesson Confidence as a Single Float vs. Multi-Dimensional Confidence

**Decision:** Single `confidence: float` per lesson.

**Rejected alternative:** Multi-dimensional confidence: separate confidence values for different aspects of the lesson (evidence quality, recurrence strength, context coverage).

**Rationale:** Multi-dimensional confidence is more precise but harder to use downstream. The Learning Engine needs to make binary decisions about whether to act on a lesson; a single confidence threshold is simpler to reason about than a multi-dimensional threshold.

**Weakness:** Collapsing multi-dimensional confidence into a single value discards information. A lesson observed 50 times in a single context has high recurrence confidence but low context coverage. A lesson observed 5 times across diverse contexts has low recurrence confidence but high context coverage. Both might have the same aggregate confidence score but warrant different downstream treatment. This is an accepted simplification for the first version.

## 19. Compatibility Notes

### 19.1 RFC-0011 (Planner): Calibration Observation Schema

The Confidence Recalibrator produces `CalibrationObservation` records that RFC-0011's Cost and Confidence Estimator is expected to consume (via RFC-0010 Reflection Memory). The schema of these observations — specifically the field names and types for `skill_type`, `metric`, `planned_value`, `actual_value`, `calibration_error`, and `context_tags` — must be agreed upon between RFC-0011 and RFC-0013.

**Required action:** RFC-0011 should be amended to formally reference RFC-0013's `CalibrationObservation` schema as the authoritative format for calibration data. Until this amendment is in place, RFC-0011's estimator may be unable to parse calibration observations written by RFC-0013.

### 19.2 RFC-0012 (Tool Runtime): InvocationRecord Episodic Memory Schema

RFC-0012 writes InvocationRecord summaries to RFC-0010 Episodic Memory in a schema that RFC-0013's FailureAnalyzer and Lesson Extractor depend on. This schema dependency was noted in RFC-0012's Compatibility Notes (Section 19.6). RFC-0013 formalizes the requirement: the Episodic Memory schema for tool invocation records must include at minimum: `tool_id`, `capability_name`, `invocation_id`, `outcome`, `error_class`, `total_duration_ms`, `retry_count`, `connector_type`. If RFC-0012's schema omits any of these fields, the corresponding Reflection Engine analyses will produce incomplete outputs.

### 19.3 RFC-0010 (Memory System): Reflection Memory Tier Assumptions

RFC-0013 extensively uses RFC-0010's Reflection Memory tier. RFC-0010's Reflection Memory is defined to store "self-evaluative observations" with a schema including `observation_type`, `lesson`, `confidence`, and `context_tags`. RFC-0013's Lesson structure is more detailed than RFC-0010's general schema implies.

**Resolution:** RFC-0010's Reflection Memory tier must support the full `Lesson` structure defined in RFC-0013 Section 8.4. RFC-0010 should be amended to include RFC-0013's `Lesson` structure as the canonical schema for Reflection Memory entries of type `SKILL_RELIABILITY_OBSERVATION`, `TOOL_PERFORMANCE_OBSERVATION`, etc.

### 19.4 RFC-0004 (Artifact System): Reflection Artifact Type Registration

Reflection Artifacts must be registered as a named Artifact type in RFC-0004's type registry (if such a registry exists). The type name `reflection.v1` should be registered with the schema reference pointing to RFC-0013's `ReflectionArtifact` data structure. This enables RFC-0004 to index, query, and manage Reflection Artifacts as a distinct class.

### 19.5 RFC-0007 (Scheduler): Execution Record Availability Timing

The Reflection Engine depends on Scheduler execution records being available in RFC-0004 by the time the Reflection Engine's Execution Record Loader runs. The Trigger Manager applies a 2-second delay before loading (Section 6.1). If RFC-0007 does not persist execution records synchronously before publishing the `scheduler.execution.completed` event — for example, if it persists records asynchronously after event publication — the 2-second delay may be insufficient, and the Execution Record Loader may find records incomplete or absent.

**Required action:** RFC-0007 must guarantee that all execution records are fully persisted to RFC-0004 before publishing `scheduler.execution.completed`. If this guarantee cannot be made, RFC-0007 should include the execution record Artifact reference in the `scheduler.execution.completed` event payload, allowing the Reflection Engine to verify availability before beginning.

### 19.6 RFC-0003 (Policy Engine): Reflection Sensitivity Attribute

Reflection Artifacts inherit sensitivity from source Artifacts. For this inheritance to work correctly, RFC-0003's policy must support `reflection.sensitivity_inherited_from: [artifact_id]` as a policy attribute for reflection access control decisions. RFC-0003 must be amended to support derived sensitivity classification.

## 20. Critical Self-Review

### 20.1 The Reflection Engine Cannot Evaluate Semantic Quality

The most significant limitation of this RFC is that the quality scoring and lesson extraction are purely structural and statistical. The Reflection Engine can determine that a plan was inefficient, that tasks failed, that tool utilization was poor, and that estimates were wrong. It cannot determine whether the goal was actually achieved in any meaningful sense, whether the outputs were factually correct, whether a decision was wise rather than merely successful, or whether the lessons extracted are actually true rather than spuriously correlated with outcomes.

**Honest assessment:** This is not a design flaw — it is an inherent constraint of systems-level analysis. The Reflection Engine operates on execution metadata, not on the content of what was executed. Semantic evaluation would require a domain-specific evaluator for every possible goal type, which is not feasible in a general-purpose kernel. The correct long-term response is to define a `GoalEvaluator` interface that skills or operators can implement for specific goal types, and to incorporate evaluator outputs into the quality scoring process. This RFC does not define that interface; it is a genuine gap.

### 20.2 Lesson Confidence Accumulation Is Slow and May Be Gamed

The lesson confidence accumulation algorithm requires multiple observations to reach high confidence. For rare skill types or rare goal domains, lessons may never accumulate enough observations to reach high confidence, leaving the system perpetually underconfident about those domains. Conversely, for common skill types, the system accumulates confidence rapidly — but if the early observations were atypical (e.g., during a system migration or a load test), the accumulated confidence reflects atypical conditions.

**Honest assessment:** The accumulation approach is correct in principle — trust should be earned through repeated observation, not granted immediately. The weakness is the cold-start problem: new skill types, new tools, and new goal domains start with confidence 0.3 regardless of how well they are designed. In practice, this means the system will be conservative (low planning confidence for new capabilities) for some period after any new capability is added. This is acceptable and is arguably correct behavior — new capabilities should be treated with caution until their behavior is observed. The cold-start problem should be documented as expected behavior, not treated as a failure.

### 20.3 The Counterfactual Analysis Is Speculative and May Be Misleading

The Decision Scorer's counterfactual analysis attempts to determine whether a different decision would have produced a better outcome. This is inherently speculative: the counterfactual was not executed, so its estimated outcome is based on historical data, not on actual execution in the specific context of the analyzed execution.

**Honest assessment:** Counterfactual analysis is the weakest component of the Decision Scorer. The confidence cap (0.7 maximum, typically lower) reflects this weakness. But even capped, a counterfactual conclusion of "alternative X would have been 30% more likely to succeed" carries significant weight when accumulated across many reflections and used to influence Method selection or tool routing. If the counterfactual reasoning is systematically biased (e.g., because the historical data for the alternative option is from different contexts), it could produce consistently wrong recommendations. The Recommendation Generator must apply additional skepticism to recommendations derived primarily from counterfactual analysis. This is stated in the recommendation generation algorithm but not enforced as a hard constraint. A `requires_empirical_validation` flag on counterfactual-derived recommendations would be a useful addition.

### 20.4 The Analysis Pipeline Has No Feedback Within a Session

The Analysis Pipeline is strictly sequential with defined data dependencies. Once a stage produces its output, subsequent stages consume it but cannot request additional analysis from prior stages. If the LessonExtractor discovers that the FailureAnalyzer misclassified a failure (e.g., it attributed a failure to a tool when the actual cause was an incorrect input schema in the skill), the LessonExtractor cannot trigger a re-run of the FailureAnalyzer. It can only note the apparent misclassification in its own output.

**Honest assessment:** This is a deliberate design choice (pipelines are simpler than iterative systems) but it means that analysis errors in early stages can propagate undetected. The alternative — an iterative, feedback-enabled analysis loop — would be more accurate but significantly more complex, harder to test, and potentially non-terminating. The current design is a pragmatic compromise. The `reflection_confidence` score and the explicit stage status tracking (FAILED, PARTIAL, COMPLETED) provide transparency about the analysis quality, allowing downstream consumers to treat low-confidence reflections with appropriate skepticism.

### 20.5 Recommendation Acknowledgement Has No Enforcement

The `AcknowledgeRecommendation` interface allows identities to mark recommendations as `ACTED_UPON`, `DISMISSED`, or `DEFERRED`. There is no mechanism to verify that an identity that marks a recommendation as `ACTED_UPON` actually implemented the recommended change. The Learning Engine will act on certain recommendations autonomously, but others (SKILL_IMPROVEMENT, POLICY_REVIEW, RESOURCE_CONFIGURATION) require human action. The Reflection Engine has no way to verify that the human action was taken.

**Honest assessment:** This is a human-process gap that the Reflection Engine cannot close technically. The correct solution is an operational process: recommendations must be tracked in an external work management system with verification criteria. The `AcknowledgeRecommendation` interface provides the hook for integrating with such a system, but the system itself is out of scope. The gap is real and must be documented to operators.

### 20.6 Trend Analysis Is a Batch Process with Latency

The trend analysis job runs daily. A degrading quality trend that began yesterday may not be detected until tomorrow. For fast-degrading systems (e.g., a tool that begins failing at high rates), this 24-hour detection latency could allow significant damage before reflection raises an alert.

**Honest assessment:** The trend analysis batch cadence is configurable. Operators should reduce the trend analysis interval for high-throughput or high-sensitivity deployments. Additionally, individual reflection sessions already generate lessons and recommendations after every execution — the trend analysis is not the only signal. A single reflection session that detects a `TOOL_PERFORMANCE_OBSERVATION` with very low success rate generates a recommendation immediately, without waiting for trend analysis. Trend analysis is for detecting gradual degradation that is not visible in any single reflection. For acute failures, the per-session signals are sufficient.

## 21. Future RFC Dependencies

### RFC-0014 (Required): Learning Engine

The Learning Engine is the primary consumer of Reflection Artifacts and recommendations. RFC-0013 produces structured input; RFC-0014 defines how that input is translated into behavioral changes: skill selection weight adjustments, Method priority changes, tool routing preference updates, and estimation parameter updates. Without RFC-0014, Reflection Artifacts accumulate but produce no behavioral improvement. The Reflection Engine and Learning Engine must be designed jointly to ensure their interfaces are compatible; RFC-0013 has been designed with this future RFC in mind, but RFC-0014 must formalize the consumption contract.

### RFC-0015 (Suggested): Semantic Goal Evaluation

As identified in the Critical Self-Review, RFC-0013 cannot evaluate the semantic quality of execution outputs. RFC-0015 should define a `GoalEvaluator` interface and a registration mechanism for goal-type-specific evaluators. The Reflection Engine would call registered evaluators during quality scoring. This would enable goal_achievement scoring to move from structural inference to actual evaluation.

### RFC-0016 (Suggested): Execution Monitor

The Reflection Engine operates post-execution. An Execution Monitor (RFC-0016) would operate in real-time during execution, detecting failure patterns before they cascade and triggering replanning or escalation. The Execution Monitor would consume the same execution records as the Reflection Engine but in streaming form rather than batch form. RFC-0016 and RFC-0013 would share the failure classification taxonomy defined here.

### RFC-0017 (Suggested): Calibration Governance

RFC-0013 produces calibration observations. RFC-0011 is expected to consume them. The process of actually updating RFC-0011's estimation parameters based on calibration observations — deciding when to update, by how much, with what constraints, and with what rollback mechanism — is not fully specified in either RFC. RFC-0017 should define the calibration governance process: who authorizes estimation parameter updates, how changes are versioned, how the impact of parameter changes is monitored, and how changes are rolled back if they degrade planning quality.

### RFC-0018 (Suggested): Reflection Federation

In multi-tenant deployments, Reflection Artifacts are tenant-scoped. But some lessons are tenant-agnostic: a tool that is unreliable for one tenant is likely unreliable for all tenants. RFC-0018 should define federated lesson sharing: a mechanism by which anonymized, sensitivity-stripped lessons can be shared across tenant boundaries to accelerate knowledge accumulation without violating tenant isolation. This requires careful design to ensure that tenant-specific information cannot be inferred from shared lessons.

### Dependency on RFC-0011 Amendment

RFC-0011 must be amended to formally specify that it will consume `ESTIMATION_CALIBRATION_OBSERVATION` lessons from RFC-0010 Reflection Memory in the format defined by RFC-0013. The amendment must define: which lessons trigger parameter updates, how the update magnitude is computed from the calibration error, and how updated parameters are validated before being applied to future planning sessions.

### Dependency on RFC-0010 Amendment

RFC-0010 must be amended to formally register RFC-0013's `Lesson` structure as the canonical schema for Reflection Memory entries. The amendment must also define the lesson lifecycle operations (deduplication, confidence update, status transitions) that RFC-0013 depends on being atomic at the Memory System level.
