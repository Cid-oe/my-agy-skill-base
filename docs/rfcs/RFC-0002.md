# AGY RFC-0002: Skill Registry & Loader

Status: Draft
Subsystem: Kernel / Skill Registry & Loader
Depends on: none (this is the trust root all downstream subsystems rely on)
Depended on by: Skill Resolver (RFC-0001), Scheduler, Policy Engine, Executor,
Reflection Engine, Adaptive Learning

---

## 1. Executive Overview

### 1.1 Purpose

The Skill Registry & Loader is the subsystem responsible for the entire
lifecycle of a skill *before* the Skill Resolver is permitted to reason
about it: discovery on disk, manifest parsing, validation, dependency and
version resolution, indexing for query, loading into an executable state,
caching, hot reload, and eventual unload.

RFC-0001 (Skill Resolver) explicitly assumes a validated, in-memory
`SkillRegistry` with two invariants it does not itself enforce:

1. No manifest reachable through `registry.byName` has an unresolved cycle
   in `requires`.
2. Every manifest reachable through the registry has passed integrity and
   permission checks — the resolver "trusts its registry completely."

This RFC is where those two invariants are earned. Everything here exists
to make RFC-0001's §9 and §13 true by construction, not by convention.

### 1.2 Responsibilities

- Discover skill packages across multiple scan roots (global, project,
  user, plugin) with a defined precedence order.
- Parse and validate manifests against the canonical schema (§3).
- Verify integrity (checksum) and, where present, authenticity (signature).
- Resolve inter-skill dependencies and detect cycles, missing skills, and
  version conflicts *before* anything is loaded.
- Build and maintain a capability index for query-by-capability lookup.
- Load skill code/entry points into an executable, reference-counted
  runtime state; unload them when no longer referenced.
- Support hot reload of a skill without restarting the AGY runtime.
- Cache parsed manifests and loaded skill instances with bounded memory.
- Emit lifecycle events on a shared Event Bus.
- Recover gracefully from any corrupted, malicious, or malformed skill
  package without taking down the registry as a whole.

### 1.3 Non-goals

- **Skill selection.** The Registry never decides *which* skill should run
  for a goal — that is the Resolver's job (RFC-0001). The Registry answers
  "what exists and is it safe to use," not "what should I use."
- **Execution.** The Loader instantiates a skill into a runnable state; it
  does not invoke it. That is the Executor's job.
- **Policy decisions.** The Registry enforces *structural* and
  *cryptographic* validity. It does not decide whether a validly-signed
  skill with `permissions: [filesystem:write]` is allowed to run in this
  session — that is the Policy Engine's job. The Registry exposes
  `permissions` as data; it does not interpret it as a decision.
- **Marketplace / distribution.** Publishing, discovery-across-the-network,
  and package management are out of scope for this RFC (see §20).

### 1.4 Relationship With Other Subsystems

```
        +----------------+       +------------------+
        |   Filesystem /  |       |  Remote Sources   |
        |   Plugin Hosts   | ----> |  (future, §20)     |
        +--------+---------+       +---------+----------+
                 |                            |
                 v                            v
        +---------------------------------------------+
        |         Skill Registry & Loader (this RFC)    |
        |  Discovery -> Validation -> Index -> Load       |
        +-----------------------+-----------------------+
                                 |
              read-only query API (ISkillRegistry)
                                 |
        +------------------------+------------------------+
        |                        |                          |
        v                        v                          v
+---------------+      +------------------+      +--------------------+
| Skill Resolver |      |  Policy Engine    |      | Reflection Engine   |
| (RFC-0001)      |      | (permission gate)  |      | (skill health data)  |
+---------------+      +------------------+      +--------------------+
```

The Registry is upstream of everything. It has no upstream dependency of
its own within AGY (it reads the filesystem and, in future, network
sources — see §20). This makes it, along with the Kernel bootstrap
sequence, one of the two subsystems that must be correct with the least
possible dependency surface: a bug here is load-bearing for the entire
system's trust model (§14).

## 2. Runtime Architecture

### 2.1 Pipeline

```
 Filesystem / Plugin Roots
        |
        v
 +----------------+
 |   Discovery     |  walks scan roots, finds candidate skill dirs
 +--------+--------+
          |  candidate paths
          v
 +----------------+
 | Manifest Parser |  reads SKILL.md frontmatter -> raw manifest object
 +--------+--------+
          |  raw manifest
          v
 +----------------+
 |   Validation    |  schema, checksum, signature, permissions (§7)
 +--------+--------+
          |  validated manifest              rejected -> Quarantine (§7.7)
          v
 +----------------+
 |    Registry     |  stores validated manifest, builds indices (§4)
 +--------+--------+
          |
          v
 +----------------+
 | Capability      |  inverted indices for query-by-capability (§8)
 |   Index         |
 +--------+--------+
          |
          v
 +----------------+
 |     Loader      |  lazy-instantiates executable skill on first use (§5)
 +--------+--------+
          |
          v
 +----------------+
 |  Runtime Cache  |  holds loaded instances, ref-counted (§11)
 +--------+--------+
          |
          v
 +----------------+
 | Skill Resolver  |  (RFC-0001) — the only consumer of loaded skills
 +----------------+
```

### 2.2 Two-Phase Design: Manifest-Time vs. Load-Time

A critical architectural decision, stated up front because it shapes every
section below: **manifest discovery/validation/indexing is decoupled from
skill loading.** The Registry can be fully populated — every manifest
parsed, validated, indexed, dependency-resolved — with zero skill code
actually loaded into memory. Loading is deferred until the Resolver or an
explicit warm-up request asks for a specific skill by name.

This split exists because:

- The Resolver (RFC-0001) needs manifest data (`requires`, `produces`,
  `triggerPredicates`, etc.) for *every* installed skill to do matching and
  constraint solving — but it only ever needs to *execute* a handful of
  skills per resolution.
- Thousands of skills (a stated goal, §0) means eagerly loading all
  entry points at boot is both slow and wasteful of memory for skills that
  may never be invoked in a given session.
- It cleanly separates two different trust operations: manifest validation
  is cheap and can run on every candidate; code loading is comparatively
  expensive and should only happen for skills the Resolver actually
  selected.

### 2.3 Boot Sequence

```
1. Registry.bootstrap(scanRoots, config)
2. Discovery.scanAll(scanRoots) -> CandidatePath[]
3. for each candidate (parallelizable, §15):
     manifest = ManifestParser.parse(candidate)
     result = Validator.validate(manifest)
     if result.ok: Registry.register(manifest)
     else: Quarantine.record(candidate, result.errors)
4. DependencyResolver.resolveAll(Registry) -> conflicts[]
   (missing skills, cycles, version conflicts — logged, not fatal at boot;
   see §9 for why partial-boot is preferred over all-or-nothing)
5. CapabilityIndex.build(Registry)
6. Registry.status = READY
7. emit RegistryReady { skillCount, quarantineCount, conflictCount }
```

Boot does **not** load any skill code. Step 4's conflicts are recorded but
do not block `READY` — an individual broken skill should not prevent AGY
from starting with the N-1 skills that are fine (Design Principle: no
single skill package should be a single point of failure for the whole
runtime).

## 3. Skill Manifest Specification

### 3.1 Canonical Schema

The manifest is the YAML frontmatter of a skill's `SKILL.md`, extended from
RFC-0001's fields with the registry/loader-specific fields this RFC
introduces (`id`, `author`, `license`, `permissions`, `capabilities`,
`entryPoint`, `hooks`, `checksum`, `signature`).

```yaml
# --- identity (required) ---
id: string                     # globally unique, immutable across versions
name: string                   # human-readable, may change across versions
version: string                # strict semver: MAJOR.MINOR.PATCH
description: string
author: string
license: string                # SPDX identifier

# --- resolver-facing (required, consumed by RFC-0001) ---
priority: critical | high | medium | low
requires: string[]             # skill ids, hard dependency
optional: string[]             # skill ids, soft dependency
consumes: string[]             # ArtifactType names
produces: string[]             # ArtifactType names
exclusiveWith: string[]        # skill ids
estimatedCost: low | medium | high
estimatedLatency: fast | medium | slow
estimatedContext: low | medium | high
confidenceThreshold: float     # 0.0-1.0
escalateTo: string | null      # skill id
triggerPredicates: Predicate[] # see RFC-0001 §7

# --- registry/loader-facing (required) ---
permissions: Permission[]      # capability grants this skill requests
capabilities: string[]         # capability tags for the index (§8)
entryPoint: string             # relative path to executable entry
hooks:                         # optional lifecycle hooks
  onLoad: string | null
  onUnload: string | null
  onValidate: string | null

# --- versioning (optional, defaulted) ---
requiresSkillVersion: string   # semver range this skill needs from deps
minAgyVersion: string          # minimum AGY kernel version, default "0.0.0"
deprecated: boolean            # default false
deprecatedReason: string | null
supersededBy: string | null    # skill id

# --- integrity (required for non-local trust levels, see §14) ---
checksum: string               # sha256 of the skill package contents
signature: string | null       # detached signature, required at trustLevel >= verified
```

### 3.2 Field Rules

| Field | Required | Default | Validation |
|---|---|---|---|
| `id` | yes | — | `^[a-z0-9][a-z0-9-]{1,63}$`, globally unique across all trust levels |
| `name` | yes | — | non-empty string, ≤128 chars |
| `version` | yes | — | strict semver (no `v` prefix, no ranges) |
| `description` | yes | — | non-empty, ≤2048 chars (this is what the Resolver's Matcher and any human-facing skill picker reads) |
| `author` | no | `"unknown"` | free text |
| `license` | no | `"UNSPECIFIED"` | SPDX identifier or `"UNSPECIFIED"` |
| `priority` | yes | — | enum, no default — forces every skill author to make this decision explicitly |
| `requires` | no | `[]` | each entry must resolve to a known `id` at dependency-resolution time (§9); unresolved entries are a *validation-time warning*, not a parse error, because a dependency may simply not be installed yet |
| `optional` | no | `[]` | same shape as `requires`, no error if unresolved |
| `consumes`/`produces` | no | `[]` | free-form strings, but the Registry maintains a soft "known artifact types" set and warns (does not reject) on unrecognized types — this keeps the artifact vocabulary decentralized without becoming silently inconsistent |
| `exclusiveWith` | no | `[]` | must be symmetric — see §3.3 |
| `estimatedCost`/`Latency`/`Context` | no | `medium` | enum |
| `confidenceThreshold` | no | `0.75` | float in `[0.0, 1.0]` |
| `escalateTo` | no | `null` | if set, must resolve to a known `id` (warning if not) |
| `triggerPredicates` | no | `[]` | each predicate's `variable` must be in the Registry's known `RuntimeState` field set (warning if not — matches RFC-0001 §9's fail-closed behavior) |
| `permissions` | no | `[]` | each entry validated against the fixed permission vocabulary (§14.2); unknown permission strings are a **hard validation error**, not a warning — an unrecognized permission is exactly the ambiguity a sandbox cannot safely default on |
| `capabilities` | no | `[]` | free-form tags, lowercase, used only for index queries (§8) — no uniqueness constraint |
| `entryPoint` | yes | — | relative path, must exist within the skill package, must not escape the package root (path traversal check, §14.4) |
| `hooks.*` | no | `null` | if set, must resolve to a callable within `entryPoint`'s module |
| `requiresSkillVersion` | no | `"*"` | semver range |
| `minAgyVersion` | no | `"0.0.0"` | semver |
| `deprecated` | no | `false` | boolean |
| `checksum` | yes at trust level ≥ `local-verified` | — | sha256 hex, computed over the package tarball excluding the manifest's own `checksum`/`signature` fields |
| `signature` | required at trust level `verified` | `null` | see §14.3 |

### 3.3 Symmetry and Consistency Rules (Cross-Manifest)

Some validation cannot happen per-manifest; it requires comparing manifests
across the registry. These run in the Validation Pipeline's cross-manifest
pass (§7.5), after all individual manifests have passed per-manifest
validation:

- **`exclusiveWith` symmetry.** If skill A declares `exclusiveWith: [B]`,
  B must declare `exclusiveWith: [A]` (or the Registry auto-symmetrizes it
  with a warning — see §7.5 for the chosen behavior). An asymmetric
  exclusion is a silent correctness bug in RFC-0001's constraint solver:
  it would let B be selected alongside A when only A "knew" to refuse.
- **`supersededBy` chains.** Must not cycle, and the target must actually
  declare a `version` greater than the superseded skill's.
- **`id` uniqueness across trust levels.** Two packages from different
  scan roots (§6) must not declare the same `id` at the same `version` —
  this is a discovery-time duplicate, handled in §6.5, not a validation
  error.

## 4. Registry Specification

### 4.1 Responsibilities

The Registry is the in-memory (and optionally persisted, §4.6) source of
truth for all validated manifests. It does not itself discover, parse, or
validate — those are the Discovery, Manifest Parser, and Validation
Pipeline's jobs respectively (§2.1). The Registry's job is storage, index
maintenance, and query.

### 4.2 Internal Storage

```
Registry:
    byId: Map<SkillId, Map<SemverString, ManifestEntry>>   # id -> version -> entry
    activeVersion: Map<SkillId, SemverString>                # currently selected version per id
    byProduces: Map<ArtifactType, SkillId[]>                 # inverted index (RFC-0001 §7)
    byPredicateVariable: Map<string, SkillId[]>              # inverted index (RFC-0001 §7)
    byCapability: Map<CapabilityTag, SkillId[]>              # inverted index (§8)
    dependents: Map<SkillId, SkillId[]>                      # reverse of `requires`/`optional`
    quarantine: Map<CandidatePath, QuarantineEntry>          # failed validation (§7.7)
    status: BOOTING | READY | DEGRADED | RELOADING

ManifestEntry:
    manifest: SkillManifest
    trustLevel: local | local-verified | verified            # (§14.1)
    sourceRoot: ScanRoot                                       # which scan root it came from (§6)
    packagePath: string
    registeredAt: timestamp
    loadState: UNLOADED | LOADING | LOADED | FAILED           # (§5.2)
```

Multiple versions of the same `id` may coexist in `byId` (needed for
side-by-side version resolution during upgrade/rollback, §10), but only
one is `activeVersion` at a time — the one the Resolver's `byName`-style
lookups actually see. This is the mechanism §10's rollback uses: rollback
is an `activeVersion` pointer change, not a re-install.

### 4.3 Indexes

| Index | Key | Value | Used by |
|---|---|---|---|
| `byId` | skill id + version | full manifest entry | version resolution, direct lookup |
| `byProduces` | artifact type | skill ids | Resolver Matcher (RFC-0001 §8.1) |
| `byPredicateVariable` | predicate variable name | skill ids | Resolver Matcher, and Registry's own "which skills would this RuntimeState change affect" queries |
| `byCapability` | capability tag | skill ids | capability-based discovery (§8), human-facing skill browsing |
| `dependents` | skill id | skill ids that `requires`/`optional` it | impact analysis for hot reload (§5.5) and deprecation (§10.6) |

All indices are rebuilt incrementally on register/unregister (§4.5), never
by full rebuild on the hot path — full rebuild is reserved for explicit
`Registry.rebuildIndices()` (used after bulk operations like a plugin
directory rescan).

### 4.4 Lookup API

```
interface ISkillRegistry:
    getManifest(id: SkillId, version?: SemverString) -> ManifestEntry | null
    getActiveVersion(id: SkillId) -> ManifestEntry | null
    findByProduces(artifact: ArtifactType) -> ManifestEntry[]
    findByCapability(tag: CapabilityTag) -> ManifestEntry[]
    findByPredicateVariable(variable: string) -> ManifestEntry[]
    listAll(filter?: RegistryFilter) -> ManifestEntry[]
    getDependents(id: SkillId) -> SkillId[]
    getQuarantined() -> QuarantineEntry[]
    status() -> RegistryStatus
```

This is the interface RFC-0001's `SkillRegistry` type is implemented
against — `registry.byName`/`byProduces` in RFC-0001 §7 map directly to
`getActiveVersion`/`findByProduces` here.

### 4.5 Concurrency

The Registry supports concurrent readers and serialized writers via a
readers-writer lock at the registry-instance granularity, not per-index:

- **Reads** (`getManifest`, `findByProduces`, etc.) never block each other.
- **Writes** (`register`, `unregister`, `setActiveVersion`) are serialized
  and each write atomically updates the manifest store and all five
  indices together — a reader must never observe a manifest present in
  `byId` but absent from `byProduces`.
- Hot reload (§5.5) and dependency re-resolution (§9) both go through this
  same write path, so there is exactly one place index consistency can be
  violated, and exactly one place to test it (§17).

This is a deliberate simplification versus per-index locking: skill
registration is not a hot-path, high-frequency operation (it happens at
boot and on hot reload, not per-resolution), so coarse-grained locking
trades a small amount of write throughput for a much smaller concurrency
bug surface — consistent with Design Principle #2 (simplicity before
abstraction).

### 4.6 Persistence

The Registry itself is rebuildable from disk on every boot (Discovery +
Validation is idempotent), so persistence is an optimization, not a
correctness requirement:

- A **manifest cache** (§11.1) persists parsed-and-validated manifests
  keyed by `(packagePath, checksum)` so unchanged skills skip re-parsing
  and re-validation on subsequent boots.
- The **quarantine log** persists across boots so a skill that failed
  validation doesn't silently retry every boot without operator visibility
  — it must be explicitly cleared or the underlying package must change
  (checksum changes) before it's re-attempted.
- No other Registry state is persisted. `activeVersion` selection,
  built indices, and load state are all rebuilt at boot — this keeps the
  "restart AGY" recovery path in §16 simple: delete the cache, get a
  correct-by-construction registry from a full rescan.

### 4.7 Garbage Collection

Two independent GC concerns:

1. **Manifest GC**: when a skill package is removed from disk (detected by
   a Discovery rescan, §6.4), its `ManifestEntry` is removed from `byId`
   and all indices, provided `dependents(id)` is empty. If it has
   dependents, it is marked `DEPRECATED_MISSING` rather than removed —
   removing it outright would silently break the `requires` invariant for
   every dependent, and RFC-0001's constraint solver would then fail
   confusingly deep in resolution instead of at the registry layer where
   the actual cause is visible.
2. **Loaded-instance GC**: covered under Runtime Cache (§11.2) — this is
   about executable instances, not manifest data, and follows a separate
   reference-counting lifecycle (§5.4).

## 5. Loader Specification

### 5.1 Design

The Loader turns a validated `ManifestEntry` into a **loaded skill
instance**: the `entryPoint` module imported/executed in an isolated
context, `hooks.onLoad` invoked if present, and the result placed in the
Runtime Cache. It is the only component in this RFC that executes
third-party code, which is why §14's sandboxing requirements apply
specifically to the Loader's `load()` operation.

### 5.2 Skill Lifecycle States

```
 UNLOADED --load()--> LOADING --success--> LOADED
     ^                    |
     |                 failure
     |                    v
     +---------------- FAILED
     
 LOADED --unload()--> UNLOADING --success--> UNLOADED
 LOADED --reload()--> RELOADING --success--> LOADED
                            |
                         failure
                            v
                     LOADED (previous instance retained, §5.5)
                     or FAILED (if no previous instance existed)
```

`FAILED` is not terminal — a `load()` retry (typically triggered by the
Resolver's `reresolve()` in RFC-0001 §10, or by an explicit operator
action) may transition `FAILED -> LOADING` again. The Loader does not
auto-retry on a timer; unprompted retries of a failing skill are a policy
decision (backoff, circuit-breaking), not a Loader responsibility — the
Loader exposes state, the caller decides whether to retry.

### 5.3 Load Operation

```
function load(id: SkillId, version?: SemverString) -> LoadResult:
    entry = registry.getManifest(id, version) or registry.getActiveVersion(id)
    if entry is null: return LoadResult.NOT_FOUND

    if entry.loadState == LOADED:
        cache.incrementRefCount(id)
        return LoadResult.CACHED(cache.get(id))

    entry.loadState = LOADING
    emit SkillLoading { id, version: entry.manifest.version }

    try:
        sandbox = Sandbox.create(entry.manifest.permissions)   # §14.5
        module = sandbox.import(entry.packagePath, entry.manifest.entryPoint)
        if entry.manifest.hooks.onLoad:
            module[entry.manifest.hooks.onLoad]()
        instance = LoadedSkill(manifest=entry.manifest, module=module, sandbox=sandbox)
        cache.put(id, instance)                               # refCount = 1
        entry.loadState = LOADED
        emit SkillLoaded { id, version: entry.manifest.version }
        return LoadResult.OK(instance)
    catch e:
        entry.loadState = FAILED
        emit SkillFailed { id, reason: e.message }
        return LoadResult.ERROR(e)
```

### 5.4 Reference Counting and Unload

```
function unload(id: SkillId) -> UnloadResult:
    if cache.decrementRefCount(id) > 0:
        return UnloadResult.STILL_REFERENCED

    instance = cache.get(id)
    if instance.manifest.hooks.onUnload:
        instance.module[instance.manifest.hooks.onUnload]()
    instance.sandbox.dispose()
    cache.evict(id)
    registry.getManifest(id).loadState = UNLOADED
    emit SkillUnloaded { id }
    return UnloadResult.OK
```

Reference counting is incremented by the Executor when it begins invoking
a skill and decremented when the invocation completes — a skill in active
use is never unloaded out from under a running execution, including under
memory pressure (§11.2's eviction policy must respect `refCount > 0` as a
hard floor, not a soft preference).

### 5.5 Hot Reload

Hot reload replaces a `LOADED` skill's instance with a freshly-loaded one
from an updated package, without requiring the Executor or Resolver to
restart:

```
function reload(id: SkillId) -> ReloadResult:
    oldInstance = cache.get(id)
    entry.loadState = RELOADING
    emit SkillReloading { id }

    newManifest = ManifestParser.parse(entry.packagePath)
    validation = Validator.validate(newManifest)
    if not validation.ok:
        entry.loadState = LOADED   # keep serving the old instance
        emit SkillFailed { id, reason: "reload validation failed", errors: validation.errors }
        return ReloadResult.VALIDATION_FAILED(validation.errors)

    try:
        newInstance = load_internal(newManifest)   # same as §5.3, new sandbox
    catch e:
        entry.loadState = LOADED   # old instance still valid, serve it
        emit SkillFailed { id, reason: "reload load failed" }
        return ReloadResult.LOAD_FAILED(e)

    # both instances briefly coexist; in-flight executions on oldInstance
    # are allowed to complete against it (refCount-gated), new invocations
    # get newInstance
    cache.replace(id, newInstance, drainOld=oldInstance)
    registry.register(newManifest)   # updates indices if manifest fields changed
    entry.loadState = LOADED
    emit SkillReloaded { id, oldVersion, newVersion }
    return ReloadResult.OK
```

The "old instance drains, new instance serves new calls" behavior is the
key hot-reload guarantee: reload never interrupts an in-flight execution.
`cache.replace` is the one place `refCount` semantics get subtle — see
§11.2.

### 5.6 Lazy Load

Lazy load is the default (§2.2): `Registry.register()` never calls
`Loader.load()`. The Resolver's `PlanBuilder` (RFC-0001 §8.4) triggers
`load()` only for skills that made it into a finalized `ExecutionPlan`,
immediately before the Executor needs them (or slightly ahead, as a
prefetch optimization — see §15.4).

### 5.7 Failure Recovery

| Failure | Behavior |
|---|---|
| `load()` throws during import | `FAILED` state, event emitted, old cached instance (if any, i.e. this was a reload) untouched |
| `hooks.onLoad` throws | Same as above — a throwing load hook is treated identically to an import failure, no special-casing |
| Sandbox creation fails (permission grant impossible, §14.5) | `FAILED` immediately, `Sandbox.create` never partially succeeds |
| `unload()` called on a skill with `refCount > 0` | No-op, returns `STILL_REFERENCED`, not an error — caller (typically GC pressure handling, §11.2) should retry later or force-drain |
| `reload()` fails validation or load | Old instance keeps serving (§5.5) — reload failure is never allowed to leave the registry with zero working instance of a previously-working skill |

## 6. Discovery Algorithm

### 6.1 Scan Roots

```
ScanRoot:
    path: string
    kind: global | project | user | plugin
    precedence: int        # lower number = higher precedence
```

Default precedence order (lower wins on duplicate `id`, §6.5):

1. `project` — skills committed to the current repository (`.agy/skills/`)
2. `user` — skills installed for the current user (`~/.agy/skills/`)
3. `global` — skills installed system-wide
4. `plugin` — skills contributed by installed plugins (lowest precedence,
   isolated by default, §14.5)

This order encodes a deliberate policy: project-local intent overrides
user preference, which overrides system defaults, which overrides
plugin-contributed extensions. A plugin should never be able to silently
shadow a project's own skill of the same `id`.

### 6.2 Repository Scan

```
function scanRoot(root: ScanRoot) -> CandidatePath[]:
    candidates = []
    for dir in walk(root.path, maxDepth=4):     # bounded depth, not unbounded recursion
        if exists(dir / "SKILL.md"):
            candidates.append(CandidatePath(dir, root))
    return candidates
```

`maxDepth=4` matches the observed category/skill nesting
(`<category>/<skill-name>/SKILL.md`) with headroom for one extra level of
grouping, and exists specifically to bound discovery cost — an unbounded
walk over a large monorepo with an `.agy` root misconfigured to point too
high would otherwise make boot time proportional to total repository size
instead of skill count.

### 6.3 Plugin Scan

Plugin-contributed skills are discovered through a registered plugin host
interface rather than a raw filesystem walk — a plugin declares its skill
directory via its own plugin manifest, and Discovery only walks paths a
plugin has explicitly declared. This is a trust-boundary decision (§14):
Discovery never walks arbitrary plugin-installation directories looking
for stray `SKILL.md` files, because that would let a compromised plugin
smuggle in a skill under a path Discovery wasn't told to trust.

### 6.4 Workspace Rescan

A rescan (triggered manually, on a filesystem-watch event, or on a fixed
interval — configurable, default: filesystem-watch where available,
falling back to a 60s poll) re-runs `scanRoot` for all roots and diffs
the result against the current Registry contents:

```
function rescan(roots) -> RescanResult:
    current = union(scanRoot(r) for r in roots)
    previous = registry.listAll().map(e -> e.packagePath)
    added = current - previous
    removed = previous - current
    unchanged = current ∩ previous

    for path in added: pipeline.processCandidate(path)          # §2.1 steps 3
    for path in removed: registry.markMissing(path)              # §4.7 GC
    for path in unchanged:
        if checksumChanged(path): pipeline.processCandidate(path, isReload=true)
    return RescanResult(added.size, removed.size, changed.size)
```

### 6.5 Duplicate Handling

Two candidates declaring the same `id` (regardless of `version`) is
resolved by scan-root precedence (§6.1), not by version — a `project`-root
skill always wins over a `global`-root skill of the same `id`, even if the
global one is a newer semver. This is intentional: precedence encodes
*trust and intent*, not recency. If two candidates with the same `id` come
from the *same* precedence tier (e.g. two plugins both declaring
`id: security-audit`), this is a hard validation error — Discovery cannot
silently pick a winner within a single trust tier, and both candidates are
quarantined with a `DuplicateId` reason until the conflict is resolved by
an operator (typically: rename one).

## 7. Validation Pipeline

### 7.1 Stages

```
Manifest Validation -> Dependency Validation -> Version Validation
    -> Capability Validation -> Permission Validation
    -> Checksum Verification -> Signature Verification (if required)
```

Each stage can independently fail; a failure at any stage short-circuits
the remaining stages and routes the candidate to Quarantine (§7.7) with
the specific stage and reason recorded. This ordering is deliberate: cheap
structural checks (schema shape) run before expensive cryptographic ones
(signature verification), so a malformed manifest fails fast without
paying for a signature check that was never going to matter.

### 7.2 Manifest Validation

Applies the field rules in §3.2. Produces either `ValidationOK` or a list
of `(field, rule, message)` errors. This stage is pure — no filesystem or
network access beyond the already-parsed manifest object.

### 7.3 Dependency Validation

Checks that every `requires` and `optional` entry is a syntactically valid
skill id (not yet checked for *existence* — that's cross-registry and
happens in §9, since a dependency's package may simply not have been
discovered yet in a partial scan). This stage only rejects malformed
references (e.g. an id violating the `^[a-z0-9][a-z0-9-]{1,63}$` pattern).

### 7.4 Version Validation

Confirms `version` is strict semver, `requiresSkillVersion` (if present)
is a valid semver range, and `minAgyVersion` is satisfied by the running
Kernel version — the last of these is a hard rejection at this stage
(§7.7), since a skill declaring a minimum AGY version the current runtime
doesn't meet cannot be safely loaded regardless of everything else about
it.

### 7.5 Capability & Cross-Manifest Validation

Runs the symmetry/consistency checks from §3.3, deferred to a pass that
runs after per-manifest validation for *all* candidates in the current
scan batch, since these checks are inherently comparative:

```
function crossValidate(batch: ManifestEntry[]) -> CrossValidationResult:
    warnings = []
    for entry in batch:
        for other in entry.manifest.exclusiveWith:
            otherEntry = findInBatchOrRegistry(other)
            if otherEntry and entry.manifest.id not in otherEntry.manifest.exclusiveWith:
                warnings.append(AsymmetricExclusion(entry.id, other))
                autoSymmetrize(otherEntry, entry.manifest.id)   # chosen behavior, see below
    return CrossValidationResult(warnings)
```

**Chosen behavior for asymmetric exclusion: auto-symmetrize with a
warning, not a hard rejection.** Rejecting outright would mean a single
skill author's oversight (forgetting to declare the reverse exclusion)
breaks *two* skills instead of the one that has the bug, including a skill
the author of the fix may not control (e.g. it's a third-party plugin
skill). Auto-symmetrizing preserves RFC-0001's correctness guarantee (the
constraint solver always sees a symmetric relation) while surfacing the
underlying authoring bug for a human to fix at the source.

### 7.6 Checksum and Signature Verification

```
function verifyIntegrity(entry, requiredTrustLevel) -> IntegrityResult:
    computed = sha256(packageContents(entry.packagePath, excludeFields=["checksum","signature"]))
    if computed != entry.manifest.checksum:
        return IntegrityResult.CHECKSUM_MISMATCH

    if requiredTrustLevel == "verified":
        if entry.manifest.signature is null:
            return IntegrityResult.SIGNATURE_MISSING
        if not verifySignature(entry.manifest.signature, computed, trustedKeys):
            return IntegrityResult.SIGNATURE_INVALID

    return IntegrityResult.OK
```

`requiredTrustLevel` is a Registry-level configuration, not per-skill — an
operator sets a minimum trust level for the whole runtime (or per scan
root, e.g. `plugin` roots default to requiring `verified` while `project`
roots default to `local`, matching the idea that code you wrote yourself
doesn't need a third party's signature). See §14.1 for the full trust
level model.

### 7.7 Quarantine

Any candidate failing any stage above is recorded, never silently dropped:

```
QuarantineEntry:
    candidatePath: string
    failedStage: string
    errors: ValidationError[]
    firstSeen: timestamp
    lastAttempt: timestamp
    checksumAtFailure: string
```

A quarantined candidate is **not** retried automatically on every rescan —
only when its on-disk checksum changes (§6.4's `checksumChanged` check
applies to quarantined candidates too). This prevents a permanently broken
skill package from generating repeated validation work and repeated
`SkillFailed`/`ManifestInvalid` event noise on every rescan interval.

### 7.8 Corrupted Skill Recovery

If a package's checksum cannot even be computed (missing files, unreadable
package), it is quarantined with `failedStage: "checksum"` and a specific
`errors: [PackageUnreadable]` — this is distinguished from a checksum
*mismatch* because the recovery path differs: a mismatch suggests tampering
or corruption of a previously-valid package (potentially security-relevant,
§14), while unreadability more often indicates a filesystem or packaging
problem (operationally relevant, not necessarily a threat).

## 8. Capability Index

### 8.1 Purpose

The `capabilities` manifest field (§3.1) is free-form tags — e.g.
`planning`, `security`, `repository-analysis`, `testing`, `documentation`,
`performance` — distinct from `produces` (typed artifacts consumed by
RFC-0001's Matcher). Capabilities exist for *category-level* discovery:
"what skills exist that do security work," independent of whether they
produce a specific artifact type the Resolver currently knows to ask for.
This is the query surface a human operator, `skill-creator`, or
`caveman-help`/`ponytail-help`-style index skills use.

### 8.2 Data Structure

```
byCapability: Map<CapabilityTag, Set<SkillId>>
```

A flat inverted index, not a hierarchy — tags are deliberately non-
hierarchical strings rather than a taxonomy tree, because a fixed taxonomy
would require centralized governance to extend (violates the same
decentralization principle as `consumes`/`produces`'s soft-known-set
approach in §3.2) while a flat tag set lets `skill-creator` add a new
capability tag the moment a new domain of skill appears, at the cost of
potential tag sprawl — mitigated by a "known tags" soft registry
(analogous to §3.2's known-artifact-types set) that warns, not rejects, on
novel tags.

### 8.3 Queries

```
interface ICapabilityIndex:
    query(tag: CapabilityTag) -> SkillId[]
    queryAll(tags: CapabilityTag[], mode: "any" | "all") -> SkillId[]
    tagsFor(id: SkillId) -> CapabilityTag[]
    knownTags() -> CapabilityTag[]          # for autocomplete / novel-tag warnings
```

`queryAll(..., mode="all")` is implemented as a set intersection across
`byCapability[tag]` for each requested tag — O(min tag-set size) using the
smallest candidate set as the intersection driver, not O(all skills).

### 8.4 Complexity

| Operation | Complexity |
|---|---|
| `query(tag)` | O(1) average (hash lookup) + O(k) to materialize k results |
| `queryAll(tags, "any")` | O(Σ k_i) — union of per-tag result sets |
| `queryAll(tags, "all")` | O(k_min × t) — intersection driven by smallest set, t = number of tags |
| Index update on register/unregister | O(tags per skill), typically ≤ 5 |

## 9. Dependency Resolution

### 9.1 What This Layer Detects

This is distinct from RFC-0001's Constraint Solver (which resolves
*which* skills fill *which slots* for a specific goal at resolution time).
This layer resolves **registry-wide structural validity**: whether the
installed skill set, taken as a whole, is internally consistent — before
any goal exists at all. RFC-0001 depends on this having already run.

### 9.2 Missing Skills

```
function findMissingDependencies(registry) -> MissingDependency[]:
    missing = []
    for entry in registry.listAll():
        for dep in entry.manifest.requires:
            if registry.getActiveVersion(dep) is null:
                missing.append(MissingDependency(entry.id, dep, hard=true))
        for dep in entry.manifest.optional:
            if registry.getActiveVersion(dep) is null:
                missing.append(MissingDependency(entry.id, dep, hard=false))
    return missing
```

A **hard** missing dependency (`requires`) does not remove the dependent
skill from the registry — it marks it `loadState: FAILED` preemptively
with reason `MissingHardDependency`, so a `load()` attempt fails fast at
the Loader (§5.7) rather than partially succeeding and failing later mid-
execution. A **soft** missing dependency (`optional`) is logged only.

### 9.3 Cycle Detection

```
function detectCycles(registry) -> Cycle[]:
    graph = buildRequiresGraph(registry)   # nodes = skill ids, edges = `requires`
    return findStronglyConnectedComponents(graph)   # Tarjan's algorithm
        .filter(scc -> scc.size > 1 or hasSelfLoop(scc))
```

Tarjan's algorithm is chosen over repeated DFS cycle checks because the
Registry needs the *full set* of cyclic components (to quarantine or flag
every skill involved, not just report "a cycle exists somewhere") in a
single O(V + E) pass rather than O(V × (V+E)) repeated single-source
checks.

Every skill id participating in a detected cycle is marked
`loadState: FAILED` with reason `CyclicDependency`, listing the full cycle
in the event payload (§13) — this is the enforcement point for RFC-0001
§9's stated invariant ("cyclic manifest pairs should never make it into
`byName`" — more precisely, they remain in `byId` for visibility/debugging
but are excluded from `getActiveVersion`'s successful-lookup path, so the
Resolver never sees them as viable).

### 9.4 Version Conflicts

Two dependents requiring incompatible version ranges of the same
dependency:

```
function findVersionConflicts(registry) -> VersionConflict[]:
    conflicts = []
    for depId in allDependencyIds(registry):
        constraints = collectRequiresSkillVersionConstraints(registry, depId)
        if not satisfiableIntersection(constraints):
            conflicts.append(VersionConflict(depId, constraints))
    return conflicts
```

AGY's Registry supports **side-by-side versions** (§4.2: `byId` maps to
multiple versions), so a version conflict is not automatically fatal the
way it would be in a single-version-per-package system — see §10.2 for how
`activeVersion` selection interacts with per-dependent version needs.

### 9.5 Exclusive Skill Conflicts

Not a registry-time error — `exclusiveWith` is a resolution-time
constraint (RFC-0001 §8.3), not a structural validity issue. Two mutually
exclusive skills coexisting in the registry is completely normal (that's
the whole point of `caveman`/`ponytail`). This layer's only role is the
symmetry check already covered in §7.5; true exclusivity enforcement
belongs entirely to the Resolver.

## 10. Versioning

### 10.1 Semantic Versioning

Strict semver (`MAJOR.MINOR.PATCH`) is enforced at manifest validation
(§7.4). Convention (not mechanically enforced, since intent can't be
validated, only documented):

- **MAJOR**: breaking change to `produces`/`consumes` artifact shape,
  `entryPoint` contract, or `permissions` requirements.
- **MINOR**: new capability, new optional field, backward-compatible
  behavior addition.
- **PATCH**: bug fix, no interface change.

### 10.2 Compatibility

`requiresSkillVersion` (a dependent's declared range for a dependency) is
checked against the dependency's `activeVersion` at dependency-resolution
time (§9.4) using standard semver range semantics
(`^1.2.0`, `~1.2.0`, `>=1.0.0 <2.0.0`, etc.). If the active version doesn't
satisfy a dependent's range but a *different installed version* of the
dependency does, the Registry does **not** automatically multi-version
the resolution per-dependent (that would mean two skills in the same
execution plan running against different versions of a shared dependency,
which breaks RFC-0001's single-`ExecutionPlan` determinism guarantee) —
instead this is logged as a version conflict (§9.4) requiring an explicit
`activeVersion` decision.

### 10.3 Upgrade

```
function upgrade(id: SkillId, toVersion: SemverString) -> UpgradeResult:
    newEntry = registry.getManifest(id, toVersion)
    if newEntry is null: return UpgradeResult.VERSION_NOT_FOUND

    impactedDependents = registry.getDependents(id)
        .filter(dep -> not satisfiesRange(dep.requiresSkillVersion, toVersion))
    if impactedDependents.nonEmpty and not force:
        return UpgradeResult.BLOCKED(impactedDependents)

    previousVersion = registry.getActiveVersion(id).manifest.version
    registry.setActiveVersion(id, toVersion)
    if loader.isLoaded(id):
        loader.reload(id)    # §5.5 — old instance drains, new one serves
    emit SkillUpgraded { id, from: previousVersion, to: toVersion }
    return UpgradeResult.OK(previousVersion)
```

Upgrade defaults to **blocking** on incompatible dependents rather than
proceeding — an operator must pass `force` explicitly, at which point the
blocked dependents transition to `FAILED` with reason
`IncompatibleDependencyVersion` (visible, not silent).

### 10.4 Downgrade / Rollback

Symmetric to upgrade — because both old and new versions coexist in `byId`
(§4.2), rollback is `setActiveVersion` pointed backward, using the exact
same code path as §10.3. No separate rollback mechanism is needed; this is
a direct consequence of the side-by-side versioning design decision.

### 10.5 Migration

For a MAJOR version bump where `produces`/`consumes` shape changes, the
manifest may declare a `migrationHook` (extending §3.1's `hooks`) —
`hooks.onMigrate: string | null` — invoked once during upgrade if present,
before the new version's `onLoad`. This is scoped narrowly: it exists to
let a skill migrate its own persisted state (if any — most skills are
stateless per RFC-0001 §4, but Registry-adjacent skills like
`ponytail-debt`, which maintains a ledger, are the intended use case), not
to migrate registry or resolver state, which is not skill-owned.

### 10.6 Deprecation

`deprecated: true` + `deprecatedReason` + `supersededBy` (§3.1) is a
manifest-declared state, not a Registry-computed one. The Registry's role
is purely to surface it: `findByCapability`/`listAll` results include the
deprecation flag, and `SkillLoaded` events for a deprecated skill carry a
`deprecationWarning` payload field so the Reflection Engine (out of scope,
future RFC) can aggregate "how often is this deprecated skill still being
selected" — informing whether `supersededBy` migration is actually
happening in practice.

## 11. Runtime Cache

### 11.1 What Is Cached

Two distinct caches, deliberately not unified, because they have different
lifetimes and different cost profiles:

1. **Manifest cache** (cheap, long-lived): parsed-and-validated manifest
   objects, keyed by `(packagePath, checksum)`. Surviving across boots
   (§4.6) is safe because validation is a pure function of package
   contents — an unchanged checksum guarantees an unchanged validation
   result, so re-validating is provably redundant work.
2. **Loaded-instance cache** (expensive, session-scoped): the actual
   executable `LoadedSkill` objects from §5.3, holding sandbox state and
   imported modules. Never persisted across restarts — a loaded instance
   is inherently tied to the current process's memory and sandbox.

### 11.2 Eviction

Only the loaded-instance cache is subject to eviction (the manifest cache
is small — metadata only — and evicting it would only force cheap re-
parses, so it is bounded by a generous size cap with LRU eviction and
otherwise ignored as a memory concern).

```
function evictIfNeeded(cache, memoryLimit):
    while cache.currentMemory() > memoryLimit:
        candidate = cache.leastRecentlyUsed(filter = refCount == 0)
        if candidate is null:
            break   # everything in cache is actively referenced — cannot evict, log pressure warning
        loader.unload(candidate.id)
```

The `refCount == 0` filter is the hard floor referenced in §5.4: eviction
never unloads a skill mid-execution, even under severe memory pressure. If
eviction cannot free enough memory because everything cached is actively
referenced, the Registry emits a `MemoryPressureUnrelieved` event for the
Resource Manager (a separate Kernel subsystem, out of scope) to act on —
this Registry does not implement backpressure or throttling itself.

### 11.3 TTL

Loaded instances additionally carry an idle TTL (default: 30 minutes,
configurable) — a skill with `refCount == 0` and no invocation in the TTL
window is proactively unloaded even without memory pressure, keeping
steady-state memory proportional to recently-used skills rather than every
skill ever loaded in a long-running session.

### 11.4 Invalidation

Cache invalidation is checksum-driven, not time-driven, for correctness
(TTL above is a memory-management concern, separate from correctness):
`rescan()` (§6.4) detecting a checksum change on a cached manifest
immediately invalidates both the manifest cache entry and triggers
`loader.reload()` if a loaded instance exists — there is no scenario where
a stale manifest or stale loaded instance is knowingly kept.

### 11.5 Checkpoint Interaction

Per RFC-0001 §4, the Resolver is stateless and Checkpoint Manager is kept
out of its critical path. The same applies here: the Runtime Cache is
never checkpointed. A checkpoint resume (Checkpoint Manager restoring a
task's state) never assumes a specific set of skills is pre-loaded — it
re-triggers lazy load (§5.6) for whatever the resumed `ExecutionPlan`
needs, exactly as if this were a fresh resolution. This avoids a whole
class of bugs where a checkpoint captured 20 minutes ago references a
skill instance that has since been evicted, reloaded, or upgraded.

## 13. Event Bus Integration

### 13.1 Emitted Events

| Event | Emitted when | Payload |
|---|---|---|
| `SkillDiscovered` | Discovery finds a new candidate | `{ candidatePath, sourceRoot }` |
| `SkillValidated` | A candidate passes the full validation pipeline | `{ id, version, trustLevel }` |
| `ManifestInvalid` | A candidate fails any validation stage | `{ candidatePath, failedStage, errors }` |
| `SkillLoaded` | Loader successfully loads a skill | `{ id, version }` |
| `SkillActivated` | (reserved for Executor/Resolver layer — a loaded skill begins actual execution; emitted by this RFC's Loader only in the sense of exposing the hook, actual emission point is downstream) | `{ id, version, planNodeId }` |
| `SkillDeactivated` | Corresponding end of an activation | `{ id, version, planNodeId, durationMs }` |
| `SkillUnloaded` | Loader unloads a skill | `{ id, version, reason: "refcount" \| "ttl" \| "evicted" \| "explicit" }` |
| `SkillFailed` | Load, reload, or validation-triggered load failure | `{ id, version, reason, error }` |
| `DependencyResolved` | Dependency resolution pass completes | `{ resolved: number, missing: number, cycles: number }` |
| `VersionConflict` | A version conflict is detected (§9.4) | `{ dependencyId, constraints }` |
| `SkillLoading` | Load begins | `{ id, version }` |
| `SkillReloading` / `SkillReloaded` | Hot reload begins/completes | `{ id, oldVersion, newVersion? }` |
| `SkillUpgraded` | `activeVersion` changes via upgrade/rollback | `{ id, from, to }` |
| `RegistryReady` | Boot sequence completes | `{ skillCount, quarantineCount, conflictCount }` |
| `MemoryPressureUnrelieved` | Eviction cannot free requested memory (§11.2) | `{ requestedBytes, freedBytes, cacheSize }` |

### 13.2 Delivery Semantics

Events are delivered **at-least-once, best-effort ordering within a single
skill id** (events about the same `id` are delivered in emission order;
no cross-id ordering guarantee). Consumers (Reflection Engine, Adaptive
Learning, operator dashboards) must be idempotent to duplicate delivery —
this is a deliberate simplification versus exactly-once delivery, which
would require a persistent event log with consumer offset tracking that
no current AGY subsystem's requirements justify (Design Principle #2).

## 14. Security

### 14.1 Trust Levels

```
TrustLevel:
    local            — no checksum/signature required; project/user roots by default
    local-verified   — checksum required, signature optional
    verified         — checksum + valid signature from a trusted key required
```

Trust level is configured per scan root (§6.1), not globally — this lets
an operator run entirely self-authored project skills at `local` while
requiring `verified` for anything from a `plugin` root, matching the
principle that trust should track provenance.

### 14.2 Threat Model

| Threat | Mitigation |
|---|---|
| **Malicious manifest** (a manifest declaring `permissions` it doesn't need, to gain access) | Policy Engine (downstream) grants permissions at execution time based on declared `permissions`; the Registry's role is only to ensure the declaration is well-formed and complete — it does not itself grant anything |
| **Fake metadata** (misleading `description`/`capabilities` to get selected by the Resolver for something it shouldn't do) | Not fully preventable by the Registry alone — mitigated by `confidenceThreshold`/`triggerPredicates` design (RFC-0001) plus signature verification (a signed skill's metadata is at least attributable to a known author) |
| **Permission escalation** (a skill's `entryPoint` code attempting operations beyond its declared `permissions`) | Enforced by the sandbox (§14.5) at load/execution time, not by the Registry's validation pass — validation only checks the *declaration* is well-formed |
| **Path traversal** (`entryPoint` or package contents referencing paths outside the package root) | Hard validation error at manifest validation (§7.2) — any resolved `entryPoint` path containing `..` segments that escape `packagePath` after normalization is rejected before Loader ever sees it |
| **Remote loading** (fetching skill code from a network location at load time) | Out of scope for this RFC — the Loader only ever loads from `packagePath` on local disk; remote sources are a §20 future extension requiring a separate trust model |
| **Supply chain attacks** (a dependency of a skill's own code, not the skill itself, being compromised) | Outside the Registry's boundary — this concerns the skill's own code dependencies (npm/pip packages etc.), which is the sandbox's and the skill author's responsibility, not something manifest-level validation can see into |
| **Sandbox escape** | Sandbox implementation detail (§14.5) — the Registry's contract is that it never loads a skill without going through `Sandbox.create()`, but sandbox robustness itself is that component's own security surface |

### 14.3 Signature Verification

```
function verifySignature(signature, computedChecksum, trustedKeys) -> bool:
    for key in trustedKeys:
        if cryptoVerify(signature, computedChecksum, key.publicKey):
            return true
    return false
```

`trustedKeys` is Registry-level configuration (an explicit allowlist), not
auto-discovered — there is no implicit trust-on-first-use in this design;
a key must be explicitly added to the trusted set before any skill signed
with it can pass `verified`-level validation.

### 14.4 Path Traversal Check

```
function validateEntryPoint(packagePath, entryPoint) -> bool:
    resolved = normalize(join(packagePath, entryPoint))
    return resolved.startsWith(normalize(packagePath) + separator)
```

Applied not just to `entryPoint` but to every path referenced by `hooks.*`
and to package contents enumerated during checksum computation (§7.6) —
any file within the declared package that resolves outside the package
root is itself a validation failure, independent of whether it's ever
referenced by `entryPoint`.

### 14.5 Sandbox Interaction

The Loader never imports skill code directly into the host process's
global scope. `Sandbox.create(permissions)` constructs an isolated
execution context (the specific isolation mechanism — process-level,
VM-level, or language-runtime-level — is an implementation choice outside
this RFC's scope, but the *contract* is fixed): the sandbox is granted
exactly the capabilities listed in `permissions`, nothing implicit, and
denies everything else by default (fail-closed, consistent with RFC-0001
§9's predicate philosophy). A skill's `entryPoint` code runs entirely
within this boundary; the Loader holds a handle to the sandbox, not a
direct reference to the skill's internal state.

### 14.6 Trust Boundaries Summary

```
 Untrusted:  raw filesystem bytes, plugin-declared paths, remote sources (future)
     |
     v  [Discovery — path validation, scan-root trust config]
     |
 Semi-trusted: parsed manifest object
     |
     v  [Validation Pipeline — schema, checksum, signature, permission vocabulary]
     |
 Trusted (structurally): ManifestEntry in Registry
     |
     v  [Loader — sandbox creation scoped to declared permissions]
     |
 Trusted (executing, contained): LoadedSkill inside Sandbox
     |
     v  [Policy Engine — out of this RFC's scope — runtime permission gating]
     |
 Trusted (executing, policy-approved): available to Executor
```

## 15. Performance

### 15.1 Complexity Summary

| Operation | Complexity | Notes |
|---|---|---|
| Discovery (full scan, n roots, m files) | O(m) bounded by `maxDepth` (§6.2) | Parallelizable per scan root |
| Manifest parse (single) | O(manifest size), effectively O(1) per skill | YAML frontmatter is small |
| Validation (single manifest) | O(1) per stage, O(stages) total | Schema + checksum dominate cost; signature verification is the most expensive single stage |
| Cross-manifest validation (batch of n) | O(n × e), e = avg `exclusiveWith` size | e is small (typically ≤ 3) |
| Cycle detection | O(V + E) via Tarjan's, V = skill count, E = total `requires` edges | Single pass for the whole registry |
| Registry lookup (`getManifest`, `findByProduces`, etc.) | O(1) average + O(k) materialization | Hash-indexed (§4.3) |
| Loader `load()` (cold) | Dominated by sandbox creation + module import cost — not bounded by this RFC, sandbox-implementation-dependent | |
| Loader `load()` (cached) | O(1) | Ref-count increment only |

### 15.2 Cold Start

Cold start (fresh boot, empty caches) is dominated by:

1. Discovery walk — parallelized across scan roots, target: sub-second for
   thousands of skills on local disk.
2. Validation of every discovered candidate — parallelizable per-candidate
   since validation is a pure function with no shared mutable state until
   the final `Registry.register()` write (§4.5's serialized write path).
3. Signature verification, if `verified` trust level is required — the
   single most expensive per-skill operation; batched/parallelized like
   validation generally.

No skill code is loaded during cold start (§2.2), so cold start scales
with skill *count*, not skill *complexity* — this is the direct payoff of
the manifest/load split.

### 15.3 Warm Start

With a populated manifest cache (§11.1) and unchanged checksums, warm
start skips parsing and validation entirely for every unchanged skill —
only the `rescan()` diff (§6.4) runs, which is proportional to filesystem
metadata (mtimes/checksums) rather than full re-validation.

### 15.4 Benchmark Targets

| Metric | Target | Rationale |
|---|---|---|
| Cold boot, 1,000 skills, `local` trust | < 1s to `READY` | No signature verification in the hot path at this trust level |
| Cold boot, 1,000 skills, `verified` trust | < 5s to `READY` | Signature verification is the dominant cost; parallelized across cores |
| Warm boot (unchanged skill set) | < 200ms to `READY` | Cache-hit path only |
| Single skill `load()` (cold, excluding sandbox/import cost) | < 5ms registry-side overhead | Everything before `Sandbox.create()` should be near-free |
| `findByProduces` / `findByCapability` query | < 1ms | Index-backed, should never scale with total skill count |
| Rescan diff (10,000 skill set, 5 changed files) | < 500ms | Bounded by filesystem stat calls, not full re-validation |

These are targets to validate against in §17's performance test suite, not
guarantees derived from a reference implementation — they exist to give
implementers a concrete bar rather than "should be fast."

## 16. Failure Recovery

| Failure | Detection | Recovery |
|---|---|---|
| **Corrupt manifest** (unparseable YAML, missing required fields) | Manifest Parser / §7.2 | Quarantine (§7.7); does not affect any other skill |
| **Broken dependency** (missing hard `requires`) | §9.2 | Dependent marked `FAILED` preemptively; does not affect skills that don't depend on it |
| **Cyclic dependency** | §9.3 (Tarjan's) | All skills in the cycle marked `FAILED`, full cycle logged for operator diagnosis |
| **Invalid permissions** (unrecognized permission string) | §7.2 (hard validation error) | Quarantine — never reaches Registry at all |
| **Missing entry point** (declared `entryPoint` doesn't exist in package) | §7.2 | Quarantine |
| **Registry corruption** (in-memory index inconsistency — a bug, not an external input problem) | Internal consistency assertions, checked in the same write-path lock (§4.5) that would have caused it | Not recoverable at runtime by design — this indicates a Registry implementation bug; the correct recovery is process restart with a full rescan (§4.6: Registry state is always rebuildable from disk), not an attempted in-place repair, since an inconsistent index is exactly the situation where "repair" logic is itself unverifiable at the moment it's needed |
| **Checksum mismatch on a previously-valid, currently-loaded skill** (tampering or corruption between rescans) | §6.4's `checksumChanged` on rescan | New checksum re-validated fresh (not assumed malicious by default, but if signature verification is required and now fails, the *previously loaded instance* is unloaded — an integrity failure on a currently-active skill is treated as security-relevant, not just a data-freshness event, and generates a `SkillFailed` with elevated severity for the Policy Engine / operator to see |
| **Sandbox creation failure** | §5.7 | `FAILED` immediately, no retry loop internal to the Loader (§5.2) |
| **Cascading reload failure** (a hot reload's new version fails, but old version's dependents expect the new `produces` shape) | Not detected by this RFC's reload path directly — `reload()` (§5.5) validates the *new* manifest but does not re-run §9's dependency resolution against dependents; this is a known gap, addressed in §21 | Interim mitigation: `reload()` failing validation/load leaves the *old* manifest and instance serving, so dependents see no change until a reload actually succeeds |

The unifying recovery principle throughout this table: **a single broken
skill package degrades to "that skill is unavailable," never to "the
Registry is down."** `DEGRADED` (§4.2) is a legitimate steady state — it
means "some quarantined/failed skills exist," not "the Registry cannot be
used."

## 17. Testing

### 17.1 Unit Tests

- Manifest schema validation: every field rule in §3.2, both valid and
  invalid cases, including boundary values (e.g. `confidenceThreshold` at
  exactly `0.0`, `1.0`, and just outside the range).
- Path traversal rejection (§14.4): a battery of `entryPoint` values
  including `../`, absolute paths, symlink-based escapes, and encoded
  traversal sequences.
- Reference counting correctness (§5.4): concurrent increment/decrement
  sequences never leave `refCount < 0` or unload a referenced instance.

### 17.2 Integration Tests

- Full pipeline: a fixture directory of skill packages (mix of valid,
  invalid, cyclic, version-conflicting, path-traversal-attempting) run
  through Discovery → Validation → Registry → Index → Loader end to end,
  asserting final Registry state matches expectations exactly (which
  skills are `READY`, which are quarantined, with what reasons).
- Hot reload: load a skill, mutate its package on disk, trigger reload,
  assert in-flight executions against the old instance complete
  successfully while new invocations see the new instance (§5.5).
- Upgrade/rollback round trip: install v1, upgrade to v2, verify dependent
  behavior, rollback to v1, verify state matches pre-upgrade (§10.3/10.4).

### 17.3 Stress Tests

- Discovery + validation at target scale (10,000+ synthetic skill
  packages) against the benchmark targets in §15.4.
- Concurrent read/write load on the Registry's readers-writer lock (§4.5):
  many concurrent `findByProduces` calls during an active `rescan()`.
- Memory pressure: loaded-instance cache eviction under a constrained
  memory limit with a mix of referenced and unreferenced skills, verifying
  the `refCount == 0` floor is never violated (§11.2).

### 17.4 Fuzzing

- Manifest fuzzing: randomized YAML mutations of valid manifests (field
  type confusion, unexpected nesting, oversized strings) targeting the
  Manifest Parser and Validator for crashes or, more importantly,
  *silent acceptance* of malformed input — a fuzzer that finds a crash is
  useful, but one that finds an invalid manifest slipping through
  validation is finding a security bug (§14).
- Path fuzzing specifically for `entryPoint` and package content paths,
  since this is the single highest-value target for path traversal bugs.

### 17.5 Mutation Testing

Applied specifically to §7 (Validation Pipeline) and §9 (Dependency
Resolution) — these are the two components whose entire job is *rejecting*
bad input, so a mutation testing pass that flips a validation condition
(e.g. `!=` to `==`) and confirms the test suite catches it is a more
meaningful correctness signal here than raw coverage percentage.

### 17.6 Performance Testing

Automated benchmark suite asserting the §15.4 targets on every release
candidate, run against both synthetic fixture sets (controlled skill
count/shape) and a snapshot of the real installed skill catalog, to catch
performance regressions introduced by real-world manifest complexity that
synthetic fixtures might not represent.

### 17.7 Golden Registry Tests

Analogous to RFC-0001 §11's golden plans: a fixed, checked-in skill
package fixture set has an expected final `Registry` state (exact
`byId`, `byProduces`, `byCapability` index contents, exact quarantine
list) checked into the test suite. Any change to Discovery, Validation, or
indexing logic that alters this golden output must be an explicit,
reviewed diff — the same determinism-as-testability discipline RFC-0001
established for the Resolver applies here to the Registry.

## 18. State Machines

### 18.1 Registry Lifecycle

```
        boot()
BOOTING -------> READY
   |                |
   |          quarantine/failure
   |          events during operation
   |                v
   |            DEGRADED  (some skills quarantined/failed; Registry itself fully usable)
   |                |
   |          rescan() triggers reload of subset
   v                v
 (fatal boot     RELOADING --------> READY or DEGRADED (depending on outcome)
  error, e.g.
  config invalid)
   |
   v
 BOOT_FAILED   (terminal — no partial Registry is exposed; this is the
                one case where "no single skill can bring down the
                Registry" does not apply, because this failure is about
                Registry configuration itself, not any skill)
```

Legal transitions only: `BOOTING -> READY`, `BOOTING -> BOOT_FAILED`,
`READY <-> DEGRADED`, `READY|DEGRADED -> RELOADING -> READY|DEGRADED`.
There is no transition back to `BOOTING` — a full restart is a new process
lifetime, not a Registry-internal transition.

### 18.2 Loader Lifecycle (Skill Instance)

Already presented in §5.2; repeated here for completeness as the state
machine table format used elsewhere in this RFC:

| From | Event | To |
|---|---|---|
| `UNLOADED` | `load()` called | `LOADING` |
| `LOADING` | import + hooks succeed | `LOADED` |
| `LOADING` | import or hooks throw | `FAILED` |
| `LOADED` | `unload()`, refCount reaches 0 | `UNLOADING` |
| `UNLOADING` | unload hook + sandbox dispose succeed | `UNLOADED` |
| `LOADED` | `reload()` called | `RELOADING` |
| `RELOADING` | new manifest validates + loads | `LOADED` (new instance) |
| `RELOADING` | validation or load fails | `LOADED` (old instance retained) or `FAILED` (no prior instance) |
| `FAILED` | `load()` retried | `LOADING` |

### 18.3 Skill (Registry-Entry) Lifecycle

Distinct from the Loader lifecycle above — this tracks the manifest
entry's registry-level status, independent of whether it's currently
loaded into memory:

```
DISCOVERED -> VALIDATING -> [VALID -> REGISTERED] or [INVALID -> QUARANTINED]
REGISTERED -> [dependency resolution] -> ACTIVE or FAILED (cycle/missing-hard-dep)
ACTIVE -> DEPRECATED (manifest declares deprecated: true)
ACTIVE -> DEPRECATED_MISSING (package removed from disk, has dependents, §4.7)
ACTIVE|DEPRECATED -> REMOVED (package removed from disk, no dependents)
QUARANTINED -> VALIDATING (checksum changed on rescan, §7.7)
FAILED -> ACTIVE (missing dependency subsequently discovered, §9.2 re-run)
```

## 19. File Layout

```
<scan-root>/
  skills/
    foundation/
      <skill-id>/
        SKILL.md              # manifest frontmatter + human-readable body
        entry.<ext>            # entryPoint target
        README.md
        evals/
          evals.json
          description_evals.json
    planning/
      <skill-id>/...
    quality/
      <skill-id>/...
    execution/
      <skill-id>/...
    utilities/
      <skill-id>/...

<agy-runtime-root>/
  registry/
    manifest-cache/            # §11.1 persisted parsed-manifest cache
      <packagePath-hash>.json
    quarantine.log             # §7.7 persisted quarantine entries
    trusted-keys/               # §14.3 signature verification allowlist
      <key-id>.pub
  cache/
    loaded-instances/            # transient; not persisted across restarts,
                                  # directory exists only for any on-disk
                                  # sandbox artifacts a given sandbox impl needs
  plugins/
    <plugin-id>/
      plugin.manifest.json       # declares its own skill directory (§6.3)
      skills/
        <skill-id>/...
```

Category directories (`foundation/`, `planning/`, `quality/`, `execution/`,
`utilities/`) are a discovery-time convenience and human-organization aid,
not a registry-semantic concept — `category` is read from within
`SKILL.md`'s own metadata during earlier RFC iterations of this skill
pack, not inferred from directory name, since inferring identity from
filesystem position would make the Registry's correctness depend on
directory discipline that a plugin-contributed skill (§6.3, arriving
through a declared path, not a fixed category tree) cannot be relied on to
follow.

## 20. Future Extensions

- **Marketplace / remote registry**: a network-addressable registry
  mirroring this RFC's query API (`ISkillRegistry`), requiring a
  substantially expanded §14 threat model (remote code execution risk,
  network-level trust, registry-of-registries federation) — deliberately
  deferred rather than speculatively designed now, per Design Principle #3
  (evidence before assumptions): there is no current evidence AGY needs
  multi-tenant remote skill distribution yet.
- **Signed packages as a hard requirement** (not just `verified` trust
  level as an option): a stricter default posture once a real key
  management and distribution story exists.
- **Package manager**: dependency resolution across *packages* (bundles of
  skills, akin to npm packages) rather than individual skill ids — would
  sit above this RFC's per-skill dependency resolution (§9), not replace
  it.
- **Automatic updates**: policy-gated auto-upgrade (§10.3) triggered by
  new version availability from a registry source, with rollback-on-
  failure using the existing side-by-side version mechanism (§10.4) as the
  safety net.
- **Distributed registries**: multiple AGY runtime instances sharing a
  consistent view of a skill registry — would require resolving this
  RFC's single-process concurrency model (§4.5) into a distributed
  consensus or eventually-consistent model, a substantially different
  problem than anything addressed here.

None of these are designed further in this RFC because none has a current
concrete requirement driving its shape — speculative design here would
violate Design Principle #2 (simplicity before abstraction) for
capabilities AGY does not yet need.

## 21. Critical Review

### 21.1 Weaknesses in This Design

1. **Cascading reload gap (noted in §16).** `reload()` validates the
   reloading skill's own manifest but does not re-check whether its
   `produces` shape change breaks currently-registered dependents. A
   dependent could keep running against a stale assumption about artifact
   shape until it fails at execution time, not at reload time. This should
   be closed by extending `reload()` to re-run a scoped version of §9's
   dependency resolution against just the reloading skill's `dependents`
   set before committing the swap — deferred here because it adds
   meaningful complexity to the reload path and no current skill in the
   installed catalog has dependents whose contracts are version-sensitive
   enough to have surfaced this in practice yet. Flagged as a known gap
   rather than silently left undesigned.

2. **Coarse-grained registry lock (§4.5).** A single readers-writer lock
   at instance granularity is simple but means a large rescan's write
   phase blocks all registry reads for its duration, however brief. At
   the stated scale target (thousands of skills, §15.4's targets), this
   should stay under the sub-second range even for a full rescan, but it
   is a design choice that trades write-path simplicity for a potential
   read-latency spike during rescans on a much larger catalog than
   currently anticipated. The alternative (per-index locking or a
   copy-on-write registry snapshot swapped atomically) was rejected as
   premature complexity (§21.2) but should be revisited if real rescan
   latency data contradicts the sub-second assumption.

3. **Free-form `capabilities` and soft-known `consumes`/`produces` sets
   (§3.2, §8.2)** trade centralized consistency for decentralized
   extensibility. This is a deliberate tradeoff, but it means the
   Registry cannot guarantee, for example, that "security" and
   "security-audit" aren't both in use as separate tags for the same
   underlying concept. The mitigation (warn-on-novel-tag, not reject) is
   weak — it surfaces the problem to whoever is watching warnings, not to
   whoever is about to introduce it. A stronger mitigation (suggesting
   the nearest existing tag via string similarity at manifest-authoring
   time, likely inside `skill-creator` rather than this Registry) is
   plausible future work, not designed here.

4. **Auto-symmetrization of `exclusiveWith` (§7.5)** silently repairs a
   manifest authoring bug rather than rejecting it. This favors system
   availability over strict correctness-by-construction. It is the right
   choice given this RFC's stated goal ("no single skill package should
   be a single point of failure"), but it is worth stating explicitly:
   this is a place where the design chose graceful degradation over
   fail-loud, and that choice should be revisited if silent auto-repair
   of manifest bugs ever causes a harder-to-diagnose problem than the
   rejection it avoided.

### 21.2 Alternatives Considered and Rejected

| Alternative | Rejected because |
|---|---|
| Eager loading of all discovered skills at boot | Contradicts the stated goal of supporting thousands of skills — memory and boot-time cost would scale with total catalog size instead of active-session usage (§2.2, §2.3) |
| Single global version per skill id (no side-by-side versions) | Would make upgrade/rollback (§10) require re-install rather than a pointer flip, and would force all dependents onto the same version simultaneously — incompatible with the stated goal of supporting gradual migration |
| Per-index fine-grained locking instead of instance-level lock (§4.5) | Rejected as premature complexity given current scale targets; noted as a real tradeoff in §21.1, not dismissed outright |
| Reject asymmetric `exclusiveWith` outright instead of auto-symmetrizing (§7.5) | Would let a single-skill authoring bug take down a second, unrelated skill — contradicts the failure-isolation principle running through §7.7, §9.2, §16 |
| Hierarchical capability taxonomy instead of flat tags (§8.2) | Requires centralized governance to extend, at odds with a plugin-extensible skill catalog; flat tags plus soft known-set warnings chosen instead, with the known weakness noted in §21.1 |
| Exactly-once event delivery with a persistent event log (§13.2) | No current AGY subsystem requires it; at-least-once with idempotent consumers is simpler and sufficient for every currently-specified consumer (Reflection Engine, Adaptive Learning) |
| Registry self-repair on detected internal inconsistency (§16) | An inconsistent index is precisely the condition under which repair logic's own correctness cannot be trusted; process restart with full rescan is simpler and more trustworthy, at the cost of availability during the restart — judged the better tradeoff for a subsystem this security-critical |

### 21.3 What Would Change This Design

- Evidence that real rescan latency at production catalog scale exceeds
  the §15.4 targets would justify revisiting the locking model (§21.1,
  item 2) ahead of schedule.
- A concrete cross-version compatibility failure in practice (not just
  the theoretical gap noted in §21.1, item 1) would justify prioritizing
  the cascading-reload fix over other Kernel work.
- Adoption of AGY skills from genuinely untrusted third parties (not just
  "installed plugins from a curated source") would justify accelerating
  the remote-registry / marketplace work in §20 ahead of its current
  deferred status.

## Open Questions for Next RFC

This RFC assumes a Policy Engine exists downstream to interpret
`permissions` as runtime grants (§1.3, §14.2) and assumes a Sandbox
implementation with a fixed contract (§14.5) without designing it. Of the
two, the **Policy Engine** is the harder gap to leave undefined — this
RFC's entire permission model (§3.1's `permissions` field, §14.2's threat
mitigations) is inert data without it, whereas a sandbox implementation
detail is swappable later without changing this RFC's contract. Recommend
**Policy Engine** as RFC-0003.
