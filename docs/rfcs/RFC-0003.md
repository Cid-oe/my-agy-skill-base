# AGY RFC-0003: Policy Engine

Status: Draft
Subsystem: Kernel / Policy Engine
Depends on: Skill Resolver (RFC-0001, stable), Skill Registry & Loader
(RFC-0002, stable)
Depended on by: Scheduler, Executor, Resource Manager, all downstream
Kernel components that make a decision affecting cost, safety, or
correctness

---

## 1. Executive Overview

### 1.1 Purpose

RFC-0001 produces an `ExecutionPlan`. RFC-0002 makes skills loadable and
exposes their declared `permissions`. Neither RFC decides whether a given
plan node is *allowed to run*, under what constraints, or what happens
when a runtime signal (cost, confidence, evidence, prior failures)
contradicts the plan as resolved. That decision authority does not exist
yet in AGY. This RFC creates it.

The Policy Engine is the Kernel's decision authority: the single place
every governance question — security, permissions, cost, context budget,
confidence, evidence sufficiency, retry/escalation, user override — is
evaluated, in a uniform way, producing an auditable, deterministic
decision.

### 1.2 Responsibilities

- Evaluate every `PlanNode` (RFC-0001) against the installed policy set
  before the Scheduler is permitted to execute it.
- Evaluate ongoing execution against policy continuously where relevant
  (e.g. cost accrual, context growth), not only at plan-approval time.
- Aggregate multiple policies' opinions on the same decision into one
  final `PolicyDecision` via a defined, deterministic conflict-resolution
  procedure (§8).
- Interpret RFC-0002's declared `permissions` as actual runtime grants or
  denials — closing the gap RFC-0002 §14.2 explicitly left open ("the
  Registry's role is only to ensure the declaration is well-formed... it
  does not itself grant anything").
- Provide a stable, versioned plugin interface (`IPolicy`) so new
  governance concerns can be added without Kernel changes.
- Make every decision explainable and auditable after the fact.

### 1.3 Non-goals

- **The Policy Engine does not execute work.** It evaluates a proposed
  action and returns a decision; the Executor carries out whatever the
  decision permits. This separation is stated as a Core Principle in the
  source spec and is treated here as a hard architectural boundary, not a
  preference — no `IPolicy` implementation may have a code path that
  performs the action it's evaluating.
- **The Policy Engine does not decide skill *selection*.** RFC-0001 already
  selects which skill fills which slot. The Policy Engine only answers
  "is this specific, already-selected node allowed to proceed" — it can
  say no (forcing RFC-0001's `reresolve()`, RFC-0001 §3, §10), but it does
  not pick an alternative itself.
- **The Policy Engine is not a sandbox.** RFC-0002 §14.5's sandbox enforces
  permission boundaries at the code-execution level (a skill physically
  cannot call a filesystem API it wasn't granted). The Policy Engine
  decides *whether to grant* that capability for this specific plan node
  in the first place — an upstream, higher-level gate, not a runtime
  enforcement mechanism. If the sandbox and Policy Engine disagree, the
  sandbox's denial is what actually stops the code; the Policy Engine's
  denial is what stops the Executor from ever asking the sandbox to try.

### 1.4 Relationship With Other Subsystems

```
                    +--------------------+
                    |   Skill Resolver    |
                    |    (RFC-0001)         |
                    +----------+----------+
                               | ExecutionPlan
                               v
                    +--------------------+       reads permissions,
                    |   Policy Engine     | <---- trust level, manifest
                    |    (this RFC)        |       data (RFC-0002)
                    +----------+----------+
                               | PolicyDecision (per node, or plan-level)
                               v
                    +--------------------+
                    |     Scheduler       |  only ever schedules
                    +----------+----------+  ALLOW / MODIFIED nodes
                               v
                    +--------------------+
                    |     Executor        | ----+
                    +--------------------+       | runtime signals
                               ^                  | (cost accrued,
                               |                  |  confidence observed,
                               +------------------+  evidence produced)
                          continuous re-evaluation (§6.4)
```

The Policy Engine sits **between** the Resolver's output and the
Scheduler's input, and additionally has a feedback edge from the Executor
for continuous (not just plan-time) evaluation. It reads from RFC-0002's
Registry (permissions, trust level, deprecation status) and from RFC-0001
concepts (`PlanNode`, `confidenceThreshold`, `escalateTo`) but writes to
neither — it is a pure evaluator sitting in the data path, not a mutator
of either subsystem's state.

## 2. Runtime Architecture

```
        Kernel
          |
          v
  +------------------+
  |  Policy Engine     |   <-- framework: lifecycle, registry, caching,
  |  (Framework)        |       ordering, conflict resolution (§3, §8)
  +--------+---------+
           |  dispatches PolicyContext (§9) to every applicable policy
           v
  +------------------+
  |  Policy Pipeline   |   <-- ordered/parallel evaluation (§6)
  +--------+---------+
           |  N x PolicyDecision
           v
  +------------------+
  |  Aggregator        |   <-- conflict resolution -> single Decision (§8)
  +--------+---------+
           |  final PolicyDecision (ALLOW | DENY | MODIFIED | ESCALATE | DEFER)
           v
  +------------------+
  |    Scheduler        |
  +------------------+
```

### 2.1 Framework vs. Policies

Per the Core Principle stated in the source spec, this is the central
architectural split and it is enforced, not just described:

- **Framework** (this RFC's Kernel-visible surface): `IPolicyEngine`,
  `IPolicyRegistry`, evaluation pipeline, caching, conflict resolution,
  event emission. The Kernel imports and depends on the framework only.
- **Policies** (`IPolicy` implementations): `SecurityPolicy`,
  `PermissionPolicy`, `CostPolicy`, `ContextPolicy`, `EvidencePolicy`,
  `ConfidencePolicy`, `ExecutionPolicy`, `RetryPolicy`, and any custom
  policy. These are plugins in the same structural sense RFC-0002 skills
  are plugins: discovered, validated, loaded, and unloadable independent
  of the framework's own lifecycle.

This split is what makes "policies are replaceable" (source spec) true in
practice: replacing `CostPolicy` with an org-specific variant never
touches the framework, exactly as swapping a skill never touches
RFC-0001's Resolver.

## 3. Policy Framework

### 3.1 Responsibilities

The framework owns everything a policy author should never have to think
about: how policies are found, loaded, ordered, cached, and reconciled
when they disagree. A policy author only implements `IPolicy` (§4).

### 3.2 Policy Lifecycle

```
DISCOVERED -> VALIDATING -> REGISTERED -> ACTIVE
                  |
                  v
              REJECTED (malformed IPolicy implementation, §12)

ACTIVE -> SUSPENDED (operator/config disables it without unregistering)
ACTIVE -> UNREGISTERED (removed entirely)
SUSPENDED -> ACTIVE
```

This deliberately mirrors RFC-0002's manifest lifecycle (RFC-0002 §18.3)
rather than inventing a new shape — policies are governed artifacts with
the same discover/validate/register discipline as skills, because the
same reasoning applies: a single malformed policy must never be able to
take down policy evaluation for every other policy (§13).

### 3.3 Registration

Policies register via `IPolicyRegistry.register(policy: IPolicy)`, either
at boot (from a configured policy directory, mirroring RFC-0002 §6's scan
roots — `global`, `project`, `user`, `plugin`, same precedence semantics)
or dynamically at runtime (an operator or the Adaptive Learning subsystem
installing a new policy mid-session). Dynamic registration goes through
the identical `VALIDATING` gate as boot-time registration — there is no
"trusted" fast path for runtime-added policies, since a policy added at
runtime is, if anything, a higher-risk artifact than one present at boot
and reviewed as part of deployment.

### 3.4 Discovery

Structurally identical to RFC-0002 §6: scan configured policy roots for
policy package manifests (a policy manifest is a narrower schema than a
skill manifest — see §4.3 for its shape), each validated independently
before registration. Discovery does not execute policy code — validation
only inspects the declared interface surface and metadata, the same
manifest/load split RFC-0002 §2.2 established for skills.

### 3.5 Ordering

Policies are ordered for evaluation by `priority` (declared on `IPolicy`,
§4) and, within equal priority, by a stable secondary key (registration
order) — never by registration *time* alone, which would make evaluation
order depend on incidental boot sequencing. This ordering matters for two
things: short-circuit evaluation (§6.2) and tie-breaking in conflict
resolution (§8) when scores are equal.

### 3.6 Composition

Policies compose by each answering a narrow question independently — a
policy never calls another policy directly, and never sees another
policy's decision during its own `evaluate()` call. This is the framework
enforcing statelessness-with-respect-to-siblings: `SecurityPolicy` cannot
condition its answer on what `CostPolicy` said, because if it could, the
evaluation order would silently become semantically significant beyond
the documented conflict-resolution procedure (§8), reintroducing exactly
the kind of hidden coupling Design Principle #5 (explicit interfaces over
hidden behavior) rules out. Composition happens only at the Aggregator
(§6.3, §8), which does see every decision.

### 3.7 Evaluation

Covered fully in §6 (Policy Pipeline).

### 3.8 Caching

Two cache layers:

1. **Applicability cache**: `appliesTo()` (§4) results are cached per
   `(policyId, planNodeShape)` — a coarse key derived from the node's
   skill id, not its full runtime context — since applicability is
   typically a structural question ("does this policy care about
   filesystem-writing skills") independent of the specific values in a
   given `PolicyContext`.
2. **Decision cache**: `evaluate()` results are cached per
   `(policyId, contextHash)` with a short TTL (default 5s, configurable),
   where `contextHash` is a hash over exactly the `PolicyContext` fields
   that policy declared it reads (§9.4) — not the whole context. This
   bounds cache key churn to what a given policy actually depends on, so
   an unrelated context field changing (e.g. a different node's confidence
   score) doesn't invalidate a policy's cached decision about this node.

Both caches are invalidated on any `PolicyRegistered`/`PolicySuspended`/
`PolicyUnregistered` event — a changed policy set is never served from a
stale cache, full stop.

### 3.9 Persistence

The framework itself holds no durable state beyond what's needed to
reconstruct its runtime shape (registered policies, their configuration)
from the same policy directories RFC-0002-style discovery reads — exactly
RFC-0002 §4.6's reasoning applied here: the Policy Engine is fully
rebuildable from disk on restart, so persistence is an optimization
(caching, §3.8), not a correctness requirement. The one thing that *is*
durably persisted is the **decision audit log** (§12.7) — every
`PolicyDecision` ever rendered, for auditability, which is a compliance/
security requirement, not a bootstrap requirement.

## 4. Policy Interface

### 4.1 Canonical Interface

```typescript
interface IPolicy {
  readonly id: string;
  readonly version: string;
  readonly priority: "critical" | "high" | "medium" | "low";
  readonly appliesToKinds: PolicyTargetKind[];   // declared statically, §4.2

  appliesTo(context: IPolicyContext): boolean;
  evaluate(context: IPolicyContext): PolicyDecision;
  explain(decision: PolicyDecision, context: IPolicyContext): string;
}
```

### 4.2 Target Kinds

A policy declares, statically, what *kinds* of thing it evaluates —
`plan-node` (a single `PlanNode` before execution), `execution-step` (an
in-flight execution, for continuous evaluation, §6.4), or `plan` (the
whole `ExecutionPlan` as a unit, e.g. an aggregate cost ceiling). This
static declaration is what lets the framework route context to the right
policies without every policy's `appliesTo()` having to reject every
irrelevant call — `appliesToKinds` is a coarse, cheap pre-filter;
`appliesTo()` is the fine-grained, context-dependent filter run only
within that coarse set.

### 4.3 Policy Manifest (Discovery-Time Metadata)

Mirroring RFC-0002 §3.1's skill manifest, but narrower:

```yaml
id: string
version: string                # strict semver
priority: critical | high | medium | low
appliesToKinds: PolicyTargetKind[]
readsContextFields: string[]   # declared subset of PolicyContext (§3.8, §9.4)
entryPoint: string
checksum: string
signature: string | null
```

Validated through the same pipeline structure as RFC-0002 §7 (schema →
checksum → signature), reusing that RFC's `ISkillValidator`-shaped
approach generalized to a shared `IManifestValidator<T>` rather than a
second, divergent validation implementation — the framework depends on
RFC-0002's validation primitives, not a reimplementation of them.

### 4.4 `evaluate()` Contract

**Inputs**: a single `IPolicyContext` (§9). **Outputs**: a single
`PolicyDecision` (§5). **Errors**: `evaluate()` must not throw for any
well-formed `PolicyContext` — a policy that cannot reach a confident
decision returns `DEFER` (§5), not an exception. An actual exception
(a genuine implementation bug) is caught by the framework and treated as
`PolicyFailed` (§10, §13), never propagated to the Aggregator as if it
were a legitimate decision.

**Purity requirement**: `evaluate()` must be a pure function of its
`IPolicyContext` argument — no I/O, no mutation of shared state, no
side effects. This is what makes decision caching (§3.8) and the
determinism testing in §15 possible, and it is the same discipline
RFC-0001 §3 established for the Resolver itself ("same inputs, same
plan"). A policy that needs live external data (e.g. a current spend
figure from a billing system) must have that data fetched *into* the
`PolicyContext` by the framework before evaluation, not fetched by the
policy mid-`evaluate()`.

### 4.5 `explain()` Contract

Given a decision this policy already rendered and the context it was
rendered against, produce a human-readable rationale string. Separated
from `evaluate()` deliberately: `evaluate()`'s hot path should not pay the
cost of string formatting for a decision that's cached or never inspected
by a human; `explain()` is called lazily, only when an audit view or a
`DENY`/`ESCALATE` surfaces to an operator.

### 4.6 Events

Every `evaluate()` call, regardless of outcome, results in exactly one
lifecycle event emitted by the framework (not by the policy itself — see
§12.1 for why policies never emit events directly): `PolicyStarted` before
the call, then exactly one of `PolicyPassed` / `PolicyDenied` /
`PolicyModified` / `PolicyEscalated` / `PolicyFailed` after (§10).

## 5. Decision Model

### 5.1 The Five Outcomes

```typescript
type PolicyOutcome = "ALLOW" | "DENY" | "MODIFIED" | "ESCALATE" | "DEFER";

interface PolicyDecision {
  policyId: string;
  outcome: PolicyOutcome;
  rationale: string;
  confidence: number;              // 0.0-1.0, the policy's own confidence in this decision
  evidence: EvidenceRef[];         // what this decision was based on
  suggestedRemediation: string | null;
  modification: PlanNodeModification | null;   // only present if outcome == MODIFIED
  escalateTarget: EscalationTarget | null;      // only present if outcome == ESCALATE
}
```

| Outcome | Meaning | Who acts on it |
|---|---|---|
| `ALLOW` | Proceed exactly as planned | Scheduler proceeds unchanged |
| `DENY` | Do not proceed | Scheduler must not execute this node; triggers RFC-0001 `reresolve()` (§8.4) or plan-level failure |
| `MODIFIED` | Proceed, but with the plan node altered (e.g. reduced budget, narrowed permission grant, forced fallback skill) | Scheduler executes the **modified** node, not the original |
| `ESCALATE` | Cannot be decided at this level; requires human or higher-authority input | Execution pauses on this node pending resolution (§5.3) |
| `DEFER` | This policy has no opinion / insufficient information to decide | Excluded entirely from aggregation (§8) — not counted as an implicit `ALLOW` |

`DEFER` is distinct from `ALLOW` by design: a policy that doesn't apply or
can't reach a confident conclusion must say so explicitly rather than
defaulting to permissive, because a silent default-to-allow is exactly the
fail-open failure mode RFC-0001 §9 and RFC-0002 §14 both explicitly reject
elsewhere in this system. Consistency of that fail-closed posture across
every RFC is treated as load-bearing, not incidental.

### 5.2 `MODIFIED` Semantics

A `MODIFIED` decision's `PlanNodeModification` is restricted to a fixed,
declared set of modifiable fields — budget ceilings, permission subset
grants, forced `escalateTo` override, timeout — never an arbitrary mutation
of the node. This keeps `MODIFIED` auditable and keeps the Policy Engine
from silently becoming a second resolver: it can *narrow* what RFC-0001
selected, it cannot *replace* the selection (that's still only
`reresolve()`'s job, triggered via `DENY`).

```typescript
interface PlanNodeModification {
  budgetCeiling: { cost?: number; tokens?: number; timeoutMs?: number } | null;
  permissionSubset: Permission[] | null;   // must be a subset of the node's declared permissions
  forcedEscalateTo: string | null;
}
```

### 5.3 `ESCALATE` Semantics

`ESCALATE` names a target (`EscalationTarget`: `human-operator` |
`policy-authority` | a specific escalation-handling skill id, potentially
RFC-0001's `escalateTo` chain reused at the policy layer) and suspends the
node pending that target's response. This is distinct from RFC-0001's own
`escalateTo` (a resolution-time fallback to a *different skill* on low
confidence) — here, `ESCALATE` means "a different *authority* must weigh
in on this exact decision," not "try a different skill." A single
resolved plan node can, in the worst case, hit both: the Resolver's
`escalateTo` if a skill under-performs post-execution (RFC-0001 §10), and
the Policy Engine's `ESCALATE` if a policy can't clear it pre-execution —
these are independent mechanisms addressing different questions and are
not conflated in this design.

### 5.4 Confidence and Evidence

Every `PolicyDecision` carries the *policy's own* confidence in its
decision (not to be confused with `ConfidencePolicy`, §7, which evaluates
the *execution's* confidence as its subject matter) and a list of
`EvidenceRef`s — pointers into the `PolicyContext` (specific ledger
entries, cost figures, prior decisions) that the rationale is traceable
to. This is what makes `explain()` (§4.5) non-fabricated: an explanation
string is generated from real evidence references, not synthesized
independently of them.

## 6. Policy Pipeline

### 6.1 Stages

```
IPolicyContext assembled
        |
        v
Coarse filter: appliesToKinds match?  ---no---> excluded, no evaluate() call
        |
       yes
        v
Fine filter: appliesTo(context)? -------no----> excluded, no evaluate() call
        |
       yes
        v
Cache check (§3.8) -------hit--------> cached PolicyDecision
        |
       miss
        v
evaluate(context)  --throws--> PolicyFailed (§13), treated as DENY (fail-closed, §13.4)
        |
    PolicyDecision
        |
        v
   Aggregator (§8)
        |
        v
   Final PolicyDecision
```

### 6.2 Ordering and Short-Circuit

Policies within the applicable set are evaluated in `priority` order
(`critical` first). A **short-circuit rule** applies only to `DENY`s from
`critical`-priority policies: a `critical` policy returning `DENY`
terminates the pipeline immediately for that node — no lower-priority
policy's `evaluate()` is called, since no outcome from a lower-priority
policy can override a critical denial (§8.1's ordering-first conflict
resolution makes this consistent, not a special case). `high`/`medium`/
`low` priority policies do **not** short-circuit each other on `DENY` —
their results all still feed the Aggregator, because a `medium`-priority
`DENY` might legitimately be outweighed by other `medium`/`low` signals
in a way a `critical` denial never can be (§8.2).

### 6.3 Parallel Evaluation

Because `evaluate()` is required to be pure (§4.4) and policies never see
each other's decisions during evaluation (§3.6), every applicable
policy's `evaluate()` call is independent and safely parallelizable —
the pipeline dispatches all non-short-circuited policies concurrently and
waits for the full set before the Aggregator runs. Purity is what makes
this safe without additional synchronization; this is the direct payoff
of the statelessness constraint stated in §3.6 and §4.4, not an
independent optimization decision layered on afterward.

### 6.4 Continuous (Post-Plan) Evaluation

Plan-time evaluation is a one-shot gate before execution starts.
Continuous evaluation re-runs a scoped subset of policies — specifically
those declaring `appliesToKinds: ["execution-step"]` — against updated
`PolicyContext` snapshots as execution proceeds (e.g. after each
Executor-reported cost increment or confidence observation). This is how
`CostPolicy` catches a plan that looked fine at resolution time but
accrues cost beyond a ceiling mid-execution — the Policy Engine is not
only a pre-flight gate, it is a running governor. A continuous-evaluation
`DENY` mid-execution triggers the Executor to halt the in-flight node
(coordinated through the Executor's own cancellation contract, out of
this RFC's scope) rather than merely blocking a not-yet-started one.

### 6.5 Aggregation

Once all applicable policies have rendered a decision (or the pipeline
short-circuited on a `critical DENY`), the Aggregator applies the
conflict-resolution procedure in §8 to produce the single
`PolicyDecision` the Scheduler sees. Aggregation itself is also required
to be deterministic and pure — given the same set of individual
`PolicyDecision`s, the aggregate is always the same, independent of the
order those decisions happened to arrive in from parallel evaluation
(§6.3) — sorted deterministically by `(priority, policyId)` before
aggregation runs, precisely so parallel dispatch never introduces
nondeterminism into the one place where it would be most dangerous.

## 7. Built-in Policies

Each specified with: responsibility, inputs (subset of `PolicyContext`
it reads), outputs, and interactions with other policies.

### 7.1 SecurityPolicy

**Responsibility**: rejects plan nodes whose skill's declared
`permissions` (RFC-0002 §3.1) exceed what the current execution mode /
trust level allows, independent of cost or confidence considerations.
**Reads**: `node.skill.permissions`, `node.skill.trustLevel` (RFC-0002
§14.1), `context.executionMode`, `context.userConfiguration.trustPolicy`.
**Outputs**: `DENY` if any requested permission exceeds the allowed set
for the current trust level; `MODIFIED` (narrowing `permissionSubset`) if
a partial grant is configurable and sufficient for the skill's stated
`triggerPredicates` context; otherwise `ALLOW`. **Priority**: `critical`
— this is the canonical case for §6.2's short-circuit rule; a security
denial is never outvoted. **Interactions**: feeds `PermissionPolicy`
nothing directly (they're independent, per §3.6), but both read
overlapping `PolicyContext` fields — kept as two policies rather than one
because they answer genuinely different questions (SecurityPolicy: "is
this ever allowed"; PermissionPolicy: "is this allowed *right now*, given
session-specific grants," §7.2) and merging them would violate the
narrow-question-per-policy composition principle (§3.6).

### 7.2 PermissionPolicy

**Responsibility**: session- and user-scoped permission grants, distinct
from SecurityPolicy's static trust-level gating — e.g. a user who has
explicitly authorized filesystem writes for *this session* even though
the skill's declared permission would otherwise require an escalation.
**Reads**: `node.skill.permissions`, `context.sessionGrants`,
`context.userOverrides`. **Outputs**: `ALLOW`/`DENY`/`MODIFIED` based on
matching declared permissions against active grants. **Priority**:
`critical`. **Interactions**: evaluated independently of, and with equal
short-circuit weight to, `SecurityPolicy` — both being `critical` means
either one's `DENY` alone halts the pipeline; this is intentional
redundancy, not duplication, since they gate different axes (systemic
trust vs. session grant) that both must independently clear.

### 7.3 CostPolicy

**Responsibility**: monetary and resource-cost governance — per-node cost
ceiling, per-plan aggregate ceiling, per-session budget. **Reads**:
`node.skill.estimatedCost` (RFC-0002), `context.ledger.spentSoFar`
(§9.2), `context.userConfiguration.budgetLimits`. **Outputs**: `ALLOW` if
within budget; `MODIFIED` (budget ceiling reduction, forcing a
cheaper-routed alternative via RFC-0001's Model Router if the node
supports it) if partial budget remains; `DENY` if no budget remains;
`ESCALATE` to `human-operator` if the ceiling is a soft (warn-then-ask)
rather than hard limit. **Priority**: `high`. **Interactions**: this is
the primary policy exercising continuous evaluation (§6.4) — plan-time
cost is an *estimate* (RFC-0002's `estimatedCost` enum), but actual
accrued cost is tracked in the Execution Ledger (Kernel component, out of
this RFC's scope, referenced via `PolicyContext.ledger`) and re-evaluated
as it changes.

### 7.4 ContextPolicy

**Responsibility**: context-window budget governance, directly consuming
RFC-0001's `token-budget`/`context-manager` skill outputs as
`PolicyContext` inputs rather than duplicating their logic. **Reads**:
`context.conversationTokens`, `node.skill.estimatedContext`. **Outputs**:
`MODIFIED` (forcing a compression step, e.g. inserting a
`caveman-compress` dependency ahead of this node — implemented as a
`forcedEscalateTo`-style mechanism, §5.2) when approaching budget;
`DENY` if a node's `estimatedContext: high` would exceed remaining budget
outright with no compression path available. **Priority**: `medium`.
**Interactions**: this policy is explicitly *not* a reimplementation of
`token-budget`/`context-manager` (those remain RFC-0001 skills, doing the
actual estimation and compression work) — `ContextPolicy` only gates
*whether* a node proceeds given their output, keeping the "policies
evaluate, skills execute" boundary (§1.3) intact even for a concern that
already has a skill-level analog.

### 7.5 EvidencePolicy

**Responsibility**: enforces that decisions with real-world consequence
(e.g. a `ponytail-gain`-style debt-ledger closure, or any node whose
output feeds an irreversible action) have sufficient supporting evidence
before proceeding — a governance analog to RFC-0001's `self-review` and
`ponytail-review` skills, but enforced structurally rather than left to
skill discipline. **Reads**: `node.producedArtifacts` (from prior nodes
in the plan), `node.skill.produces`, a policy-configured
`evidenceRequirements` map from artifact type to minimum evidence
standard. **Outputs**: `DENY` or `ESCALATE` if a node's inputs lack the
configured evidence standard for its artifact type; otherwise `ALLOW`.
**Priority**: `high`.

### 7.6 ConfidencePolicy

**Responsibility**: enforces `confidenceThreshold` (RFC-0002 manifest
field, RFC-0001 §5.4/§10 mechanism) as an actual gate rather than a
value the Resolver and Executor merely consult informally. **Reads**:
`node.skill.confidenceThreshold`, `context.observedConfidence` (set by
the Executor post-execution, for continuous re-evaluation, §6.4).
**Outputs**: at plan time, effectively always `ALLOW` (there is nothing
to measure yet); at continuous-evaluation time, `DENY` if
`observedConfidence < confidenceThreshold`, which is the trigger that
turns RFC-0001's `escalateTo` mechanism from documentation into an
enforced behavior — this policy is what makes escalation *happen*, not
just be *declared*. **Priority**: `high`.

### 7.7 ExecutionPolicy

**Responsibility**: governs execution-mode-level constraints not owned by
any other single policy — e.g. "no `ponytail`-family skill may run in
`fast-mode` sessions," or "exclusiveWith pairs must additionally respect
a configured preferred-family setting" (a *preference*, layered on top
of, not replacing, RFC-0001's hard `exclusiveWith` constraint solving).
**Reads**: `context.executionMode`, `node.skill.category`,
`context.userConfiguration.familyPreference`. **Outputs**: `MODIFIED`
(forcing `escalateTo` toward the preferred family) or `ALLOW`.
**Priority**: `medium`.

### 7.8 RetryPolicy

**Responsibility**: governs whether a failed node (RFC-0002 §5.7 load
failure, or an Executor-reported execution failure) may be retried, how
many times, and with what backoff — distinct from RFC-0001's
`reresolve()` (which picks a *different* skill) in that `RetryPolicy`
governs re-attempting the *same* skill. **Reads**: `context.priorFailures`
(RFC-0001 §3's `RuntimeState.priorFailures`), a configured max-retry
count and backoff curve. **Outputs**: `ALLOW` (retry permitted) up to the
configured ceiling, `DENY` (exhausted, must go to `reresolve()` or fail
the plan) beyond it. **Priority**: `medium`.

### 7.9 Custom Policies

Org- or project-specific policies register through the identical
`IPolicy` interface and discovery pipeline (§3.3–3.4) as built-ins — there
is no privileged built-in-only extension point. A custom
`ComplianceDataResidencyPolicy`, for instance, is architecturally
indistinguishable from `SecurityPolicy` to the framework; only its
`priority` and the questions it chooses to answer differ.

## 8. Conflict Resolution

### 8.1 Procedure

Deterministic, ordered, in this exact sequence — not a weighted vote,
justified in §8.2 and revisited critically in §18:

```
1. If any applicable `critical`-priority policy returned DENY:
       final = DENY (rationale = union of all critical DENY rationales)
       [pipeline already short-circuited here per §6.2 — no lower
        priority decisions even exist to consider]

2. Else, if any applicable policy (any priority) returned ESCALATE:
       final = ESCALATE (target = highest-priority ESCALATE's target;
                          ties broken by policyId lexicographic order)

3. Else, if any applicable `critical` or `high` priority policy returned DENY:
       final = DENY (rationale = union of DENY rationales at the
                      highest priority level with a DENY present)

4. Else, if one or more policies returned MODIFIED:
       final = MODIFIED (modifications merged per §8.3;
                          conflicting modifications resolved by
                          priority, then policyId)

5. Else:
       final = ALLOW
```

`DEFER` decisions are excluded from every step above (§5.1) — a
unanimous-`DEFER` applicable set, which can legitimately happen for a
node no built-in policy has an opinion on, resolves to `ALLOW` at step 5
by virtue of having nothing to deny, escalate, or modify, not by any
`DEFER`-counts-as-`ALLOW` special case.

### 8.2 Why Priority-Ordering, Not Voting or Weighted Scoring

**Rejected: weighted scoring** (sum of confidence-weighted votes across
policies, threshold-gated). Rejected because it makes the final decision
a function of numeric tuning (weights) that must be centrally maintained
and re-balanced every time a new policy is added — directly contradicts
"policies are composable" and "policies are replaceable" (source spec's
Core Principle): adding one new policy to a scoring system can silently
shift the outcome of every other decision that policy happens to
co-apply with, without any of those other policies' logic changing.
Priority-ordered short-circuit means adding a new `medium`-priority
policy can never change what a `critical` policy already decided, full
stop — composability is structural, not emergent from weight tuning.

**Rejected: majority voting.** Rejected for the same core reason plus a
sharper one: a security concern is not democratically overridable by
volume of unrelated `ALLOW`s from cost/context/style-level policies. Vote
counting treats all policies as commensurable, which they explicitly are
not (source spec lists them as a strict hierarchy of concern: safety
governs cost, not the reverse).

**Chosen: strict priority ordering with deterministic tie-breaks.**
Justified by: (a) it is trivially explainable — `explain()` output for an
aggregate decision is always traceable to "the highest-priority
non-ALLOW decision," a one-sentence rationale a human can audit without
statistics; (b) it composes correctly under policy addition/removal,
satisfying the Core Principle directly; (c) it matches the same
determinism discipline RFC-0001 §3 and RFC-0002 throughout this system
have already established as a hard requirement, not a nice-to-have.

### 8.3 Merging `MODIFIED` Decisions

When multiple policies return `MODIFIED` for the same node (e.g.
`CostPolicy` reduces the budget ceiling and `ContextPolicy` forces a
compression dependency), modifications are merged field-by-field — each
`PlanNodeModification` field is independent (§5.2's fixed field set
exists specifically to make this tractable), so non-overlapping
modifications simply combine. An overlapping modification to the *same*
field (two policies both trying to set `budgetCeiling.cost` to different
values) is resolved by taking the more restrictive value, not by
priority — restrictiveness, not policy rank, is the correct tie-break
for a resource ceiling, since the whole point of multiple policies
agreeing to modify the same field is that both constraints must hold
simultaneously.

### 8.4 Interaction With RFC-0001's `reresolve()`

A final `DENY` at the node level does not, by itself, fail the whole
plan. It is handed back to the Resolver via the exact `reresolve()`
mechanism RFC-0001 §3/§10 already defined for execution failures — from
the Resolver's point of view, a Policy Engine `DENY` and an Executor
failure are both just "this node didn't work, find a fallback," reusing
the precomputed `fallbackChain` (RFC-0001 §10) rather than requiring the
Policy Engine to understand resolution internals. If `reresolve()` itself
returns `UNRESOLVABLE`, that propagates up as a plan-level failure exactly
as RFC-0001 §9/§10 already specify — this RFC introduces no new
plan-failure pathway, it only adds a new *trigger* for the existing one.

### 9.1 Definition

```typescript
interface IPolicyContext {
  readonly targetKind: PolicyTargetKind;         // "plan-node" | "execution-step" | "plan"
  readonly node: PlanNode | null;                // RFC-0001, present for node/step-scoped evaluation
  readonly plan: ExecutionPlan;                   // RFC-0001, always present
  readonly ledger: LedgerSnapshot;                 // §9.2
  readonly resourceUsage: ResourceUsageSnapshot;    // §9.3
  readonly userConfiguration: UserPolicyConfig;      // §17
  readonly executionMode: "fast" | "careful" | "custom";
  readonly repositoryMetadata: RepositoryMetadata | null;  // from RFC-0001's repository-map skill output, if available
  readonly observedConfidence: number | null;         // set only for execution-step evaluation, §7.6
  readonly sessionGrants: Permission[];                // §7.2
  readonly priorDecisions: PolicyDecision[];           // §9.5
  readonly priorFailures: ResolutionFailure[];          // RFC-0001 §3
}
```

### 9.2 Ledger Snapshot

```typescript
interface LedgerSnapshot {
  spentSoFar: { cost: number; tokens: number };
  budgetLimits: { cost: number | null; tokens: number | null };
  entriesSince(timestamp: Timestamp): LedgerEntry[];
}
```

A read-only, point-in-time view supplied by the (out-of-this-RFC-scope)
Execution Ledger Kernel component — the Policy Engine never writes to the
ledger, only reads a snapshot, preserving the same "evaluate, don't
execute" boundary (§1.3) at the data layer, not just the control layer.

### 9.3 Resource Usage Snapshot

Analogous structure for context-window usage, wall-clock time elapsed,
and any Resource-Manager-tracked quantities — assembled by the framework
immediately before each evaluation batch, not cached across the whole
pipeline run, since resource usage is exactly the kind of thing continuous
evaluation (§6.4) exists to track as it changes mid-execution.

### 9.4 Declared Field Reading (`readsContextFields`)

Every policy manifest (§4.3) declares which `IPolicyContext` fields it
actually reads. This declaration is used for: (a) the decision cache key
scoping (§3.8), and (b) a validation-time check that a policy's
`evaluate()` implementation, if introspectable, doesn't access fields
outside its declared set — enforced on a best-effort static-analysis
basis where the policy runtime environment supports it, and otherwise
treated as a documented contract a policy author is expected to honor,
consistent with the same trust model RFC-0002 applies to skill
`entryPoint` code within its sandbox (RFC-0002 §14.5): declared intent,
enforced where mechanically possible, audited where not.

### 9.5 `priorDecisions`

The context includes prior `PolicyDecision`s made *earlier in this same
plan's evaluation* (not this node's own history) — this exists so a
policy like `ExecutionPolicy` can make a decision that's consistent with
an earlier plan-level decision (e.g. once one node in a plan was
`MODIFIED` to a fast-mode fallback, a later node's `ExecutionPolicy`
evaluation can see that and stay consistent) without violating §3.6's
no-policy-calls-another-policy rule — this is the framework supplying
already-finalized history, not live cross-policy communication.

## 10. Events

| Event | Emitted when | Payload |
|---|---|---|
| `PolicyStarted` | Immediately before a policy's `evaluate()` is invoked | `{ policyId, nodeId, targetKind }` |
| `PolicyPassed` | `evaluate()` returns `ALLOW` | `{ policyId, nodeId, confidence }` |
| `PolicyDenied` | `evaluate()` returns `DENY` | `{ policyId, nodeId, rationale, evidence }` |
| `PolicyModified` | `evaluate()` returns `MODIFIED` | `{ policyId, nodeId, modification }` |
| `PolicyEscalated` | `evaluate()` returns `ESCALATE` | `{ policyId, nodeId, escalateTarget, rationale }` |
| `PolicyFailed` | `evaluate()` throws, or a `critical` timeout occurs | `{ policyId, nodeId, error, fallbackOutcome }` |
| `PolicyDecisionAggregated` | Aggregator produces the final decision for a node | `{ nodeId, finalOutcome, contributingPolicyIds }` |
| `PolicyRegistered` / `PolicySuspended` / `PolicyUnregistered` | Framework lifecycle changes (§3.2) | `{ policyId, version }` |

**Ordering guarantee**: `PolicyStarted` for a given `(policyId, nodeId)`
pair always precedes its corresponding terminal event
(`Passed`/`Denied`/`Modified`/`Escalated`/`Failed`) in emission order —
this is a per-pair guarantee, not a global one, matching RFC-0002 §13.2's
delivery semantics exactly (at-least-once, ordered within a key, no
cross-key ordering guarantee) for consistency across the two event-
emitting Kernel subsystems.

## 11. Performance

### 11.1 Expected Latency

| Operation | Target | Notes |
|---|---|---|
| Single policy `evaluate()` (cache miss) | < 2ms | Pure function over an already-assembled context; no I/O inside `evaluate()` itself (§4.4) |
| Single policy `evaluate()` (cache hit) | < 0.1ms | Hash lookup |
| Full plan-time pipeline (typical plan, 5-8 nodes, 8 built-in policies) | < 20ms | Parallelized across applicable policies (§6.3) |
| Continuous re-evaluation per Executor signal | < 5ms | Only `execution-step`-scoped policies re-run, a small subset of the full set |
| Aggregation (per node) | < 1ms | Deterministic sort + fixed procedure (§8.1), no search |

### 11.2 Caching Impact

The two-tier cache (§3.8) is expected to dominate steady-state
performance for continuous evaluation specifically: most Executor signals
change only one or two `PolicyContext` fields (e.g. `spentSoFar.cost`
incrementing), so only policies whose declared `readsContextFields`
(§9.4) intersect the changed fields need to re-evaluate — everything else
serves from cache, unaffected.

### 11.3 Incremental Evaluation

Continuous evaluation (§6.4) is not "re-run every policy on every
signal" — the framework computes a `changedFields` diff between
successive `PolicyContext` snapshots and only invokes `evaluate()` for
policies whose `readsContextFields` intersects `changedFields`. This is
the mechanism that keeps §11.1's continuous-evaluation target achievable
regardless of total policy count.

### 11.4 Complexity

| Operation | Complexity |
|---|---|
| Coarse filter (`appliesToKinds`) | O(1) per policy, index-backed by target kind |
| Fine filter (`appliesTo()`) | O(p), p = policies surviving coarse filter |
| Parallel `evaluate()` batch | O(1) wall-clock beyond the slowest single policy (bounded parallelism) |
| Aggregation | O(p log p) for the deterministic sort, p typically single-digit |
| Incremental re-evaluation | O(c), c = policies whose declared fields intersect the change set, not O(p) |

### 11.5 Memory Footprint

Dominated by the decision audit log (§12.7) far more than by runtime
evaluation state, since evaluation itself holds no state beyond a single
pipeline pass. Audit log retention/rotation is a configuration concern
(§17), not something this RFC bounds by default — see §19 for a noted gap
around long-term audit storage.

## 12. Security

### 12.1 Policy Isolation

Policies execute within the same sandbox model RFC-0002 §14.5 defines for
skills — a policy's `entryPoint` code never runs in the host process's
global scope. This is why policies never emit events directly (§4.6): the
sandboxed policy code returns a `PolicyDecision` value across the sandbox
boundary, and the *framework*, running outside the sandbox, is what emits
the corresponding event — an untrusted policy implementation is never
given a live handle to the event bus, only a pure function contract.

### 12.2 Malicious Policies

A policy that always returns `ALLOW` regardless of input (attempting to
neuter governance) is not detectable by the framework at evaluation time
in the general case — a permissive policy is not distinguishable from a
correct one by its type signature alone. Mitigations: (a) `critical`-
priority built-in policies (`SecurityPolicy`, `PermissionPolicy`) are
Kernel-shipped and not replaceable by an arbitrary third-party plugin
without an explicit, audited operator override (§17's configuration
layer distinguishes "add a new policy" from "replace a critical built-in,"
the latter requiring a higher-friction configuration path); (b) the audit
log (§12.7) makes a policy's historical decision pattern inspectable —
a policy that has returned `ALLOW` for 100% of high-risk contexts is a
visible, auditable anomaly, not a silent one.

### 12.3 Privilege Escalation

A policy's own `evaluate()` execution is itself scoped to whatever
permissions the *Policy Engine framework* — not the policy — has been
granted, and the framework's own permission set is minimal: read access
to `PolicyContext` sources, no write access to Registry, Resolver, or
Executor state (§1.4). A malicious policy cannot escalate its own
privilege by virtue of running inside the Policy Engine, because the
Policy Engine itself has no privileged capability to inherit — it is
architected to be *less* powerful than the subsystems it governs, which
is a deliberate inversion of the usual "governance component needs
elevated access" assumption, chosen specifically to shrink this
component's own attack surface.

### 12.4 Sandbox Interaction

Identical mechanism to RFC-0002 §14.5, reused rather than reimplemented —
`Sandbox.create(policyPermissions)` where `policyPermissions` for any
policy is, by construction, a small fixed set (read `PolicyContext`,
return a `PolicyDecision`) far narrower than any skill's permission
surface, since a policy has no legitimate reason to need filesystem,
network, or execution capabilities at all.

### 12.5 Trust Boundaries

```
 Untrusted: policy package bytes on disk
     |
     v  [Discovery + Manifest Validation, §3.4, reusing RFC-0002 §7's pipeline shape]
     |
 Structurally trusted: registered IPolicy manifest
     |
     v  [Sandbox creation scoped to the fixed policy-permission set, §12.4]
     |
 Trusted (executing, contained): IPolicy.evaluate() inside sandbox
     |
     v  [Framework receives PolicyDecision value only, never a live handle]
     |
 Trusted (governing): PolicyDecision available to Aggregator, Scheduler, audit log
```

### 12.6 Tamper Resistance

The audit log (§12.7) is append-only from the framework's perspective —
no `IPolicy` or external caller has a mutation API into it, only the
framework's own internal write path following every `PolicyDecisionAggregated`
event. Tamper resistance beyond "no legitimate write path exists" (e.g.
cryptographic append-only log guarantees, external write-once storage) is
noted as a configuration/deployment concern, not something this RFC's
in-process data structure alone guarantees — flagged explicitly in §18/§19
rather than overclaimed here.

### 12.7 Auditability

Every `PolicyDecision`, at every level (individual policy and aggregated
final), is persisted to the audit log with: full `PolicyContext` hash
(not the full context object, to bound storage — but a hash sufficient to
detect context tampering after the fact), the decision, the rationale,
and the evidence references. `explain()` (§4.5) for any historical
decision can be regenerated from this log without needing the original
live `PolicyContext` object still in memory.

## 13. Failure Recovery

### 13.1 Policy Crashes

Covered in §4.4/§6.1: any exception from `evaluate()` is caught by the
framework at the pipeline stage boundary and converted to a `PolicyFailed`
event, never propagated as a `PolicyDecision`.

### 13.2 Timeouts

Every `evaluate()` call is wall-clock bounded (default 500ms, configurable
per policy via manifest, §4.3). A timeout is treated identically to a
crash: `PolicyFailed`, fail-closed outcome per §13.4. `critical`-priority
policy timeouts additionally halt the pipeline (consistent with §6.2's
short-circuit treatment of a genuine `critical DENY` — a `critical` policy
that cannot be evaluated at all is treated at least as conservatively as
one that actively denies).

### 13.3 Infinite Recursion / Circular Dependencies

Structurally prevented, not merely detected, by §3.6's composition rule:
because a policy's `evaluate()` never invokes another policy or the
Policy Engine itself, there is no call graph within policy evaluation
capable of recursing. The only place a cycle *could* theoretically arise
is `readsContextFields` declarations referencing `priorDecisions` (§9.5)
in a way that created a circular data dependency between two policies —
prevented by construction, since `priorDecisions` only ever contains
*already-finalized* decisions from strictly earlier in a single
evaluation pass (never the current pass's own in-flight decisions), making
the dependency graph a DAG by definition rather than something requiring
runtime cycle detection.

### 13.4 Fallback Behavior

The unifying fail-closed principle, stated once here as the governing
rule for every ambiguous failure case in this section: **any policy
evaluation the framework cannot complete with confidence (crash, timeout,
malformed decision) is treated as though that policy had returned `DENY`
at its declared priority, never as `ALLOW` or silently excluded.** This is
consistent with RFC-0001 §9's fail-closed predicate handling and RFC-0002
§14's fail-closed sandbox defaults — the third and final application of
the same posture across all three RFCs, treated as an AGY-wide invariant,
not a per-subsystem coincidence.

The one deliberate exception: a `DEFER`-eligible policy (§5.1) that fails
does *not* escalate to `DENY` at `critical` weight if its own declared
priority is `low`/`medium` and no `critical`/`high` policy in the same
batch failed — a failed low-priority style-preference-tier policy
degrading the whole pipeline to `DENY` would be a disproportionate
availability cost for a low-stakes concern. The fail-closed default is
scoped to the failing policy's own declared priority, not escalated
system-wide by a single low-priority failure.

## 15. Testing

### 15.1 Unit Tests

Every built-in policy (§7) tested against fixture `PolicyContext`s
covering: the outcome boundary conditions (exactly at a budget ceiling,
exactly at `confidenceThreshold`), each of the five outcomes individually,
and `explain()` output correctness against known evidence.

### 15.2 Integration Tests

Full pipeline: a fixture `ExecutionPlan` (from a stubbed RFC-0001 output)
run through the full policy set, asserting the aggregated decision matches
expectations for scenarios spanning every conflict-resolution branch in
§8.1 (a `critical DENY` short-circuit case, an `ESCALATE`-present case, a
`MODIFIED`-merge case, an all-`DEFER`-resolves-to-`ALLOW` case).

### 15.3 Property-Based Testing

Generated `PolicyDecision` sets (random combinations of outcomes across
random priority levels) fed directly into the Aggregator (bypassing
individual policy `evaluate()` calls) with invariant assertions: a
`critical DENY` in the input set always produces a `DENY` output; the
aggregation result is invariant under reordering the input set (§8.1's
determinism-under-parallel-arrival guarantee, tested directly rather than
only via the ordering discipline that's supposed to guarantee it).

### 15.4 Fuzzing

`IPolicyContext` field fuzzing targeting policy `evaluate()`
implementations for crashes (feeding §13.1's crash-handling path) and,
per the same reasoning as RFC-0002 §17.4, more importantly for *silent
acceptance of malformed context* — a fuzzer finding a policy that returns
a superficially valid but evidence-free `ALLOW` for a context that should
have denied is a governance-integrity bug, the policy-layer analog of a
security bug.

### 15.5 Determinism Tests

Direct tests that identical `(node, context)` pairs, evaluated multiple
times (including under artificially randomized parallel dispatch
ordering, §6.3), always produce byte-identical `PolicyDecision` output —
this is the Policy Engine's version of RFC-0001 §11's golden-plan
determinism discipline, applied to decisions instead of plans.

### 15.6 Policy Conflict Tests

A dedicated fixture suite specifically constructing policy sets designed
to disagree (one `ALLOW`, one `DENY`, one `MODIFIED`, at varying
priorities) and asserting the §8.1 procedure's exact output for every
combination — this is the highest-value test suite in this RFC, since
§8.2 argues the entire conflict-resolution design's correctness rests on
this exact procedure being followed precisely, not approximately.

### 15.7 Regression Suite

Every production incident where a policy decision was later judged wrong
(by an operator override or a post-hoc audit finding) becomes a permanent
fixture in this suite — mirroring RFC-0002 §17.7's golden-registry
discipline, applied to decisions.

## 16. State Machines

### 16.1 Engine Lifecycle

```
BOOTING -> READY (all critical built-in policies registered and validated)
BOOTING -> BOOT_FAILED (a critical built-in policy fails validation --
           terminal, unlike RFC-0002's DEGRADED-tolerant boot, because
           SecurityPolicy/PermissionPolicy absence means the Kernel has
           no governance authority at all, which this design treats as
           categorically worse than a missing skill)
READY -> DEGRADED (a non-critical policy fails/is suspended; engine
          remains fully usable, decisions still governed by whatever
          critical policies remain active)
READY|DEGRADED -> RELOADING (policy set changes, mirrors RFC-0002 §18.1)
RELOADING -> READY|DEGRADED
```

The `BOOTING -> BOOT_FAILED` terminal path for missing `critical`
built-ins is a deliberate asymmetry versus RFC-0002's registry boot
(which tolerates individual skill failures gracefully): a Registry
missing one skill degrades gracefully because most skills are
individually replaceable capability, but a Kernel with no active security
governance is not a "degraded" AGY, it is an ungoverned one — this RFC
treats that distinction as categorical, not a matter of degree.

### 16.2 Policy Lifecycle

Given in full in §3.2.

### 16.3 Decision Lifecycle

```
CONTEXT_ASSEMBLED -> FILTERING (§6.1 coarse/fine filter)
FILTERING -> CACHED (cache hit) -> DECIDED
FILTERING -> EVALUATING (cache miss)
EVALUATING -> DECIDED (evaluate() returns)
EVALUATING -> FAILED (crash/timeout, §13) -> DECIDED (fail-closed substitute per §13.4)
DECIDED -> AGGREGATING (once all applicable policies in DECIDED state)
AGGREGATING -> FINALIZED (§8.1 procedure applied)
FINALIZED -> AUDITED (persisted, §12.7)
```

## 17. Configuration

### 17.1 Layering

Mirrors RFC-0002 §6.1's scan-root precedence model directly, applied to
policy configuration rather than skill discovery:

```
project  (highest precedence — .agy/policies.yaml in the repo)
user     (~/.agy/policies.yaml)
global   (system default policy configuration)
```

### 17.2 What Is Configurable

- **Adding** a custom policy: any precedence layer, standard registration
  (§3.3), no special privilege required.
- **Suspending** a non-critical built-in or custom policy: any layer.
- **Replacing/overriding a `critical` built-in** (e.g. substituting an
  org-specific `SecurityPolicy`): requires an explicit, distinctly-named
  configuration key (`overrideCriticalPolicy: SecurityPolicy -> orgId/customSecurityPolicy`)
  that cannot be set by a `plugin`-precedence source — only `project` or
  `user` layers may override a `critical` built-in, closing the
  §12.2-noted risk of a plugin silently neutering governance through
  ordinary configuration.
- **Budget/threshold values** consumed by built-in policies (`CostPolicy`
  ceilings, `ConfidencePolicy` default thresholds when a skill manifest
  doesn't set its own): any layer, standard precedence.

### 17.3 User Overrides

A `userOverrides` field on `IPolicyContext` (§9.1) exists specifically for
explicit, session-scoped human overrides distinct from persistent
configuration — e.g. "I acknowledge the cost warning, proceed anyway for
this one plan" — consumed by `PermissionPolicy`/`CostPolicy` as
first-class input, not as a bypass of the framework (an override is still
evaluated, it just changes what a policy's `evaluate()` concludes; it
never skips evaluation entirely, preserving the audit trail).

### 17.4 Environment Overrides

Environment-variable-driven configuration (e.g. CI environments running
with a stricter or looser policy set than interactive sessions) is
treated as a variant of the `global` precedence layer — lowest precedence,
easily overridden by `project`/`user` configuration, ensuring environment
defaults are exactly that: defaults, never a silent floor a project
cannot tighten or loosen as needed.

### 17.5 Inheritance

Configuration values not explicitly set at a higher-precedence layer
inherit from the next layer down, field-by-field — not whole-file
replacement. A `project`-layer config that sets only `CostPolicy.ceiling`
inherits every other policy's configuration from `user`/`global`
unchanged, matching RFC-0002's manifest-field-default philosophy (§3.2)
rather than requiring a full re-declaration for a single overridden value.

## 18. Critical Review

### 18.1 Rule Engine vs. Decision Tree vs. Rete vs. Constraint Engine

| Approach | Why not chosen |
|---|---|
| **Decision tree** (single hierarchical tree of conditions producing one outcome) | Cannot cleanly express independently-authored, independently-replaceable policies (Core Principle) — a decision tree's branches are inherently coupled to each other's structure, the opposite of the plugin composability this RFC requires. Would need to be regenerated/restructured every time a policy is added, violating "policies are composable" and "policies are replaceable." |
| **Rete algorithm** (classic production-rule matching, optimized for many rules over frequently-changing facts) | Rete's strength — efficient incremental re-matching when a small number of facts change against a *large* rule set — is a real match for §11.3's incremental continuous-evaluation problem in principle. Rejected for now because: (a) it optimizes for rule-count scale (thousands of fine-grained rules) this RFC does not currently have (single-digit-to-low-double-digit policies, §7's built-in set plus modest custom additions) — building Rete's alpha/beta network machinery for a rule count this small is premature abstraction (Design Principle #2); (b) Rete's matching semantics are opaque compared to this RFC's explicit priority-ordered procedure (§8.1), working against the explainability requirement (§4.5, source spec's "policies are observable"). The declared-field-based incremental re-evaluation in §11.3 captures Rete's core performance insight (only re-evaluate what could have changed) at a fraction of the implementation complexity, appropriate to current scale. **Revisit if the policy count grows an order of magnitude** — flagged explicitly, not dismissed permanently. |
| **Constraint satisfaction engine** (treat policy evaluation as CSP, same family as RFC-0001 §8.3's constraint solver) | A CSP framing fits *selection* problems (RFC-0001's "which skill fills which slot," where multiple simultaneous constraints jointly determine one assignment). Policy evaluation is not a selection problem — each policy independently answers a yes/no/modify/escalate/defer question about an *already-selected* node; there is no joint assignment to search over. Forcing this into CSP framing would be solving a harder-shaped problem than the one that exists. |
| **Chosen: priority-ordered pipeline with declarative conflict resolution** | Matches the actual shape of the problem (independent evaluators, deterministic reconciliation), is fully explainable by construction (§8.2), and reuses patterns (manifest/discovery/validation, sandboxing, fail-closed defaults) already established and load-bearing in RFC-0001 and RFC-0002 rather than introducing a structurally novel evaluation paradigm for this one subsystem. |

### 18.2 Weaknesses in This Design

1. **`readsContextFields` self-declaration is trust-based, not
   mechanically enforced in general** (§9.4). A policy that under-declares
   its field reads gets an incorrectly-scoped cache key (§3.8), which
   could serve a stale cached decision for a context change the policy
   actually cared about but didn't declare. The mitigation (best-effort
   static analysis where the runtime supports it) is explicitly
   incomplete. This is analogous to, and exactly as unresolved as,
   RFC-0002 §21.1 item 3's soft-known-set weakness — flagged rather than
   silently accepted.

2. **Audit log tamper resistance (§12.6) is asserted at the
   application-write-path level only**, not backed by a cryptographic or
   infrastructure guarantee in this RFC's scope. A compromised host
   process could, in principle, corrupt the in-process audit log before
   it reaches durable storage. Full tamper-evidence (hash chaining,
   external write-once storage) is noted as necessary for a genuinely
   high-assurance deployment and is scoped to §19 rather than designed
   here, to avoid this RFC over-claiming a guarantee its current
   mechanism doesn't fully provide.

3. **`ESCALATE`'s human-in-the-loop path has no timeout/expiry
   behavior specified.** A node parked in `ESCALATE` awaiting
   `human-operator` response with no operator available indefinitely
   blocks that execution path. This RFC does not specify escalation
   timeout/auto-resolution behavior — a real gap, deferred because it
   depends on Scheduler-level session-lifecycle concerns (what happens to
   a session with a permanently-pending escalation) that are out of this
   RFC's boundary but should be resolved before Scheduler implementation
   proceeds.

### 18.3 Why the Chosen Architecture Is Appropriate

The problem this RFC solves — many independently-authored evaluators over
a shared context, needing a deterministic, explainable, replaceable
reconciliation procedure — is well-matched by priority-ordered pipeline
evaluation specifically because that shape mirrors every other
determinism-first, fail-closed, plugin-composable design decision already
made and validated (by the review discipline in RFC-0001 §21 and RFC-0002
§21) elsewhere in AGY. Choosing a structurally different paradigm here
would introduce a second set of idioms for engineers and policy authors
to learn, for a problem that does not require one.

## 19. Future Work

- **Adaptive policies**: policies whose thresholds (e.g. `CostPolicy`
  ceilings) adjust based on Execution Ledger history rather than static
  configuration — a natural consumer of the same Adaptive Learning
  Kernel component RFC-0001 §15's `historicalSuccessBonus` stub is
  designed to eventually feed from. Deferred pending that subsystem's
  own RFC.
- **Learning-based policies**: `IPolicy` implementations backed by a
  learned model rather than deterministic logic — would require relaxing
  §4.4's purity/determinism requirement (or, more likely, wrapping model
  inference in a deterministic decision layer that only *consumes* a
  model's output as one more `PolicyContext`-like input, preserving
  determinism at the `evaluate()` boundary even if the upstream signal
  isn't itself deterministic). Not designed further here — no current
  requirement justifies it (Design Principle #3).
- **Distributed policy evaluation**: policy evaluation across multiple
  AGY runtime instances sharing a consistent decision authority — same
  class of problem as RFC-0002 §20's distributed registries, deferred for
  the same reason (no current multi-instance requirement).
- **Remote policy providers**: policies fetched/evaluated against a
  network-hosted authority (e.g. a centralized org compliance service)
  rather than locally loaded — would require extending §12.5's trust
  boundary model with a network trust tier, analogous to RFC-0002 §14.1's
  future remote-source extension.
- **Marketplace**: discoverable, shared third-party policies — same
  deferred status and reasoning as RFC-0002 §20's skill marketplace.
- **Escalation timeout/expiry** (§18.2 item 3): should be prioritized
  ahead of the other future-work items above, since it is a gap in
  *current*-scope behavior rather than a genuinely deferred capability —
  called out here explicitly so it isn't lost among longer-term items.

## Open Questions for Next RFC

This RFC assumes a Scheduler exists downstream capable of consuming
`PolicyDecision`s (`ALLOW`/`MODIFIED` proceed, `DENY` triggers
`reresolve()`, `ESCALATE` suspends) and an Executor capable of emitting
the continuous-evaluation signals §6.4 depends on. Of the two, the
**Scheduler** is the harder gap to leave undefined: this RFC's entire
decision output (§5, §8) is inert unless something consumes it
correctly, whereas the Executor's continuous-signal contract (§6.4,
§7.3, §7.6) is a narrower, addable-later surface that doesn't block the
Scheduler's basic plan-time consumption of policy decisions. Recommend
**Scheduler** as RFC-0004.
