# RFC-0002a: Skill Unload & Drain Protocol

**Status:** Accepted (Amendment to RFC-0002)  
**Subsystem:** Skill Registry & Loader  
**Author:** Lead Systems Engineer  

---

## 1. Problem Statement
RFC-0002 specifies that skills can be hot-reloaded and unloaded via reference counting (`refCount`). However, the exact draining sequence when in-flight executions exist on an old version during a reload or shutdown was not fully formalized.

## 2. Protocol Specification

1. **Lifecycle States:**
   `UNLOADED -> LOADING -> LOADED -> DRAINING -> UNLOADED`

2. **Draining Sequence:**
   - When a skill `S` is unregistered or reloaded, its `loadState` immediately transitions to `DRAINING`.
   - `DRAINING` state guarantees:
     1. The Registry stops routing any *new* resolution requests or task dispatches to the draining version instance.
     2. In-flight tasks executing on the draining instance are granted a bounded drain period (default: `30,000ms` or task `Lease.expiresAt`).
     3. As each active task finishes, it decrements `refCount`.
     4. When `refCount === 0`, `hooks.onUnload` is invoked, sandboxes are cleanly disposed, and resources are reclaimed.
   - If the timeout expires while `refCount > 0`, the runtime forcefully cancels remaining tasks via their `CancellationToken`, waits for cancellation acknowledgment, and forces eviction.

3. **Hot-Reload Dual-Hosting:**
   - During hot reload, `S@v1` enters `DRAINING` while `S@v2` is loaded into `LOADED` and begins serving all new task invocations.
