# AGY RFC-0005: Runtime State

Status: Draft
Subsystem: Kernel / Runtime State
Depends on: Skill Resolver (RFC-0001, stable), Skill Registry & Loader (RFC-0002, stable), Policy Engine (RFC-0003, stable), Artifact System (RFC-0004, stable)
Depended on by: Event Bus, Scheduler, Executor/Runtime, Resource Manager, Observation Engine, Learning Engine — every subsystem that needs to know "what is this execution doing right now"

---

## 0. Preface: Position in the Dependency Order

RFC-0004 recommended RuntimeState as the next subsystem over Event Bus, on the grounds that RuntimeState is referenced inconsistently by three prior RFCs (RFC-0001's `RuntimeState.priorFailures`, RFC-0003's `context.ledger`/`context.sessionGrants`/`priorDecisions`, RFC-0004's own `RuntimeStateSnapshot` wrapper, §5.11) with no reconciling specification, and that the cost of leaving it unspecified grows with each additional RFC that silently assumes a shape for it. This RFC is that reconciling specification.

This RFC treats RFC-0001 through RFC-0004 as accepted contracts and does not modify any of them. Where this RFC's design reveals that an existing RFC's assumption about RuntimeState's shape was incompatible with the design settled on here, that is documented as a separate finding (§18) rather than silently resolved by editing the earlier RFC.

## 1. Executive Overview

### 1.1 Purpose

Every subsystem designed so far describes *what should happen* (RFC-0001's plan), *whether it's allowed to happen* (RFC-0003's decisions), and *what was produced* (RFC-0004's artifacts) — but nothing in the accepted architecture answers *what is happening right now, for this specific running workflow*. RFC-0001's Resolver reads `RuntimeState.priorFailures` to decide whether to `reresolve()`. RFC-0003's Policy Engine reads `context.ledger`, `context.sessionGrants`, `context.priorFailures`, `context.observedConfidence` — five distinct live-state reads — to make a `PolicyDecision`. Both RFCs assume a live, mutable, queryable object exists that holds this information *during* execution, distinct from the durable, immutable artifacts RFC-0004 defines for data that has already been produced.

RuntimeState is that object. It is AGY's answer to the same problem `task_struct` solves for a Linux process, PEB solves for a Windows process, and Pod Status solves for a Kubernetes pod: a single, canonical, in-progress representation of one running thing, that every other component of the system reads to know its status and that only a small, designated set of components may mutate.

### 1.2 Responsibilities

RuntimeState owns, for a single execution:

- **Execution status and progress**: current lifecycle state (§4), which nodes are active/completed/failed/blocked.
- **Live counters and references needed for policy and resolution decisions**: retry counts, cancellation/timeout state, resource-usage references, permission grants, model assignments — the exact fields RFC-0001 and RFC-0003 already assume exist.
- **Execution variables** (§6): the live working data a workflow accumulates as it runs, distinct from the durable artifacts that data eventually becomes.
- **Checkpoint metadata** (§9): enough to resume or roll back an interrupted execution.

RuntimeState does **not** own — and instead holds only a *reference* into — anything durable, structural, or already owned by an existing subsystem: artifact payloads (RFC-0004 owns those), policy definitions (RFC-0003), scheduler queues (future Scheduler RFC), registry data or skill manifests (RFC-0002), repository data (an artifact type, RFC-0004 §5.10), telemetry history (an artifact type, RFC-0004 §5.5), learning history (future Learning Engine), configuration, or plugin metadata (RFC-0002/0003). This ownership boundary is treated as a hard constraint throughout this RFC, not a preference (§2.2, §7.4).

### 1.3 Non-goals

- **RuntimeState is not an execution engine.** It has no scheduling authority, no ability to decide what runs next, and no code path that invokes a skill, a policy, or a model. It is a data structure with a controlled mutation surface (§4, §12–13), read by the components that do the deciding.
- **RuntimeState is not the Artifact Store.** It never holds payload bytes. Every reference to produced data is an `ArtifactID` (RFC-0004 §4.2), resolved through RFC-0004's API when the payload is actually needed. This mirrors RFC-0004 §3.5's own principle — "references are the unit of transport" — applied one layer up: RuntimeState doesn't even hold artifact *references inline as owned data* where an artifact reference itself would suffice, it holds *pointers to where the current reference can be found*, distinguished carefully in §10.
- **RuntimeState is not configuration.** Configuration (RFC-0003 §17's layered `global`/`project`/`user`/`plugin` precedence model) is read at policy-evaluation and resolution time from its own subsystem; RuntimeState may hold a *reference* to which configuration snapshot was in effect for this execution (for reproducibility, §2.3), but never the configuration values themselves.
- **RuntimeState is not telemetry.** Telemetry (RFC-0004 §5.5) is a high-volume, append-only observational record with its own artifact type and retention policy. RuntimeState holds only the small set of live counters (§3) that decision-making logic needs *right now* — it is not a metrics store and must not accumulate unbounded history (§14.1 makes this a hard sizing constraint, not a suggestion).
- **RuntimeState is not a general-purpose key-value store.** Execution variables (§6) are scoped and typed, not an arbitrary bag a skill can stuff anything into — the same anti-goal RFC-0004 §4.8 already established for `metadata` (non-authoritative, non-indexed) applies here with even more force, since RuntimeState fields *are* authoritative and load-bearing for policy/resolution decisions.

## 2. Runtime Model

### 2.1 Core Concepts, Defined

- **Runtime**: the umbrella term for "the live execution machinery of AGY as a whole" — not a single object, but the collective set of currently-active `ExecutionInstance`s and the infrastructure (this RFC's RuntimeState objects, the future Scheduler, future Executor) that manages them. Used only informally in this RFC; every concrete concept below has a formal type.
- **Workflow**: the *definition* — an `ExecutionPlan` artifact (RFC-0004 §5.1), itself the output of RFC-0001's Resolver. A Workflow is data, not a running thing; it has no RuntimeState of its own.
- **Node**: a single `PlanNode` (RFC-0001) within a Workflow — the unit of execution RuntimeState tracks progress against (`currentNode`, `completedNodes`, etc., §3).
- **Execution**: the act of running a Workflow. One Workflow (one `ExecutionPlan` artifact) may be executed more than once (e.g. retried from scratch, or re-run with different inputs) — each such attempt is a distinct **Execution Instance**.
- **Execution Instance**: the concrete, running (or previously-run, now-terminal) attempt to carry out a Workflow. **This is the thing RuntimeState represents, one-to-one.** Every RuntimeState object has exactly one Execution Instance; every Execution Instance has exactly one RuntimeState object, for its entire lifetime including after it reaches a terminal status (§4).
- **Session**: a broader grouping than Execution Instance — a Session may contain multiple Execution Instances (e.g. a user's interactive session in which they trigger three separate Workflow executions in sequence, asking follow-up questions between them). Session is a grouping/correlation concept; it is not itself a RuntimeState-tracked entity in this RFC's scope (§18.3 flags this as a deliberate scoping decision worth revisiting).
- **Checkpoint**: a durable, resumable capture of an Execution Instance's RuntimeState at a point in time — the live object serialized and written as a `RuntimeStateSnapshot` artifact (RFC-0004 §5.11) via this RFC's checkpoint mechanism (§9).
- **Context (ExecutionContext)**: the bundle of live handles a currently-executing Node's code actually receives — RuntimeState plus several other references (§7). Distinct from RuntimeState itself: ExecutionContext is a per-Node-invocation *view*, constructed fresh for each Node execution; RuntimeState is the single persistent object underneath that view.

### 2.2 Relationship Between Concepts

```
   Workflow (ExecutionPlan artifact, RFC-0004 §5.1)
        |
        |  execute (possibly more than once)
        v
   Execution Instance  <---------->  RuntimeState (1:1, this RFC)
        |                                    |
        | contains many                       | checkpointed into
        v                                    v
     Node executions            RuntimeStateSnapshot artifacts (RFC-0004 §5.11)
        |
        | each invocation constructs
        v
   ExecutionContext (§7, per-Node-invocation view over RuntimeState + other handles)
```

### 2.3 Lifecycle Narrative

An Execution Instance is created when the (future) Scheduler accepts an `ExecutionPlan` artifact for execution. Creation allocates exactly one RuntimeState object (§4.1's `Created` status). As Nodes execute, the Executor (future) and Policy Engine (RFC-0003, via the mutation surface defined in §12–13) advance RuntimeState through its state machine (§4). At any point, a checkpoint may be taken (§9), durably capturing the current RuntimeState as an artifact. If execution is interrupted — crash, cancellation, timeout — a fresh Execution Instance can be created that *resumes from* the last checkpoint, inheriting its RuntimeState fields as a starting point rather than starting fresh (§5.4). When execution reaches a terminal status (§4.3), RuntimeState itself does not disappear — it transitions to `Archived` (§5.8) and remains queryable for audit purposes, consistent with RFC-0004's own auditability-over-deletion posture (RFC-0004 §2.1, §3.8), applied here to live-state history rather than artifacts.

## 3. RuntimeState Object

### 3.1 Design Note on "Minimal"

The design principles require RuntimeState to be minimal. This RFC interprets "minimal" as: **every field must be either (a) something a currently-accepted RFC already reads or writes by name** (RFC-0001's `priorFailures`, RFC-0003's `ledger`/`sessionGrants`/`priorDecisions`/`observedConfidence`), **or (b) structurally required to make the state machine (§4) and checkpoint/resume mechanism (§9) well-defined.** Fields that would be merely convenient, or that duplicate data another subsystem already owns, are deliberately excluded — several candidate fields considered and rejected are listed in §3.4 precisely so the exclusion is a documented decision, not a silent gap.

### 3.2 Canonical Schema

```typescript
interface RuntimeState {
  // --- Identity ---
  readonly runtimeId: RuntimeID;                 // §3.3, unique per RuntimeState object
  readonly executionId: ExecutionID;               // §3.3, 1:1 with runtimeId; kept as a
                                                   // separate field because "execution
                                                   // instance identity" and "runtime state
                                                   // object identity" are conceptually
                                                   // distinct even though currently 1:1 —
                                                   // see §18.4 for why this separation
                                                   // is kept despite the current redundancy
  readonly parentExecution: ExecutionID | null;     // §3.5 — non-null for resumed/retried
                                                   // instances, §5.4

  // --- Status ---
  currentStatus: RuntimeStatus;                    // §4, the ONE field mutated most often
  readonly executionMode: "fast" | "careful" | "custom";  // matches RFC-0003 §9.1's
                                                          // identical field verbatim —
                                                          // RuntimeState is this field's
                                                          // owning source, RFC-0003's
                                                          // PolicyContext reads it from here
  readonly startTime: Timestamp;
  endTime: Timestamp | null;                       // set once, on reaching a terminal status

  // --- Progress ---
  currentNode: string | null;                      // PlanNode id, null if not currently
                                                    // executing a specific node (e.g. during
                                                    // Planning or between nodes)
  completedNodes: string[];                        // append-only
  failedNodes: NodeFailureRecord[];                 // §3.6, append-only
  blockedNodes: string[];                           // nodes awaiting ESCALATE resolution
                                                    // (RFC-0003 §5.1) or unmet dependencies

  // --- Retry / Failure ---
  retryCount: Record<string, number>;                // per-node retry count, read by
                                                      // RFC-0003 §7.8 RetryPolicy
  priorFailures: ResolutionFailure[];                // RFC-0001 §3's exact referenced type —
                                                      // this field is that type's canonical
                                                      // home, closing the "RuntimeState
                                                      // referenced but never specified" gap
                                                      // for this specific field

  // --- Cancellation / Timeout ---
  cancellationState: CancellationState;              // §3.7
  timeoutState: TimeoutState;                        // §3.7

  // --- Artifacts (references only, §10) ---
  currentArtifacts: ArtifactID[];                    // artifacts produced so far in this
                                                      // execution, most-recent-relevant subset
                                                      // (§10.2 — NOT the full lineage, which
                                                      // is queryable from RFC-0004 directly)

  // --- Permissions ---
  permissionContext: PermissionContext;              // §3.8, backs RFC-0003 §9.1's
                                                      // context.sessionGrants

  // --- Resources ---
  resourceUsageReference: ArtifactID | null;          // points at the current ResourceUsage
                                                      // artifact (RFC-0004 §5.19) —
                                                      // NEVER a duplicated counter, per the
                                                      // ownership boundary (§1.2, §7.4)

  // --- Model Routing ---
  modelAssignments: Record<string, string>;           // nodeId -> model identifier, RFC-0001's
                                                      // Model Router decisions, recorded here
                                                      // so a resumed execution reuses the same
                                                      // assignments rather than re-routing
                                                      // (determinism, §2.3 of this RFC's
                                                      // principles, and RFC-0001 §3's "same
                                                      // inputs, same plan" extended to resume)

  // --- Checkpointing ---
  checkpointReference: ArtifactID | null;             // most recent RuntimeStateSnapshot
                                                      // artifact (RFC-0004 §5.11), §9

  // --- Execution Variables ---
  executionVariables: ExecutionVariableStore;          // §6

  // --- Metadata ---
  metadata: Record<string, JSONValue>;                // producer-defined, non-authoritative,
                                                      // same exclusion-from-decision-logic rule
                                                      // as RFC-0004 §4.8

  // --- Versioning ---
  readonly schemaVersion: string;                    // strict semver, §3.9
  revision: number;                                  // monotonically incrementing per mutation,
                                                      // §8.2's optimistic-locking mechanism
}
```

### 3.3 RuntimeID and ExecutionID

```typescript
type RuntimeID = string;    // ULID — same rationale as RFC-0004 §4.2: sortable by
                             // creation time, no coordination required
type ExecutionID = string;  // ULID, independently generated
```

Both use ULIDs for the same reasons RFC-0004 §4.2 adopted them for `ArtifactID` — this RFC deliberately reuses that identity scheme rather than inventing a third one, consistent with the finding (RFC-0004 §17.8, restated as a positive example here rather than a gap) that AGY benefits from one consistent identity pattern across subsystems.

### 3.4 Fields Considered and Rejected

Documented explicitly per §3.1's minimality discipline:

- **`costSpentSoFar: number`** — rejected. This is exactly the kind of duplicated counter the ownership boundary (§1.2) forbids: `resourceUsageReference` (an `ArtifactID` pointing at RFC-0004's `ResourceUsage` artifact, §5.19) is the single source of truth. A live numeric field here would drift from the Ledger's own accounting the moment either was updated without the other.
- **`policyDecisionHistory: PolicyDecision[]`** — rejected as an inline field. RFC-0003's `priorDecisions` (RFC-0003 §9.1) is populated from `Decision` artifacts (RFC-0004 §5.4) queryable via RFC-0004's lineage API (RFC-0004 §9.5, `ancestorsOf`) filtered by type — RuntimeState holds no separate copy. (RuntimeState does hold `currentArtifacts`, §3.2, §10.2, which is sufficient for a consumer to find the relevant `Decision` artifacts without RuntimeState duplicating their content.)
- **`skillManifestCache: Record<string, Manifest>`** — rejected outright. This belongs to RFC-0002's Registry; RuntimeState has no legitimate reason to cache it, and doing so would violate the explicit "MUST NOT own... Skill manifests" requirement.
- **`fullExecutionLog: LogEntry[]`** — rejected. This is Telemetry's job (RFC-0004 §5.5) or a future Observation Engine's job — an unbounded-growth field is exactly what §14.1's sizing constraint exists to prevent.

### 3.5 `parentExecution`

Non-null only when this Execution Instance was created by resuming or retrying a prior one (§5.4) — the mechanism that lets a crashed or cancelled execution's replacement instance trace back to what it's continuing. This is a `derivedFrom`-relationship-shaped concept (RFC-0004 §4.5) at the Execution Instance level, deliberately kept as a typed field here rather than requiring a RuntimeState consumer to reach into the Artifact System's lineage graph just to answer "was this execution resumed from something" — a sufficiently common and cheap question that it earns a direct field, unlike the rejected fields in §3.4 which would have required no artifact-system round-trip savings to justify duplicating already-owned data.

### 3.6 NodeFailureRecord

```typescript
interface NodeFailureRecord {
  nodeId: string;
  failedAt: Timestamp;
  reason: "execution-error" | "policy-denied" | "timeout" | "cancelled";
  errorArtifactRef: ArtifactID | null;   // points at an Error artifact, RFC-0004 §5.13,
                                        // if one was produced — never inlines the error
                                        // detail itself
}
```

Distinguishing `reason` values matters because RFC-0001's `reresolve()` and RFC-0003's `RetryPolicy` (RFC-0003 §7.8) need to know *why* a node failed to decide whether retry or reresolve is the correct response — a `policy-denied` failure should never be blindly retried with the same skill (RFC-0003 §8.4 already routes `DENY` to `reresolve()`, not retry); only `execution-error`/`timeout` failures are `RetryPolicy`'s concern.

### 3.7 CancellationState and TimeoutState

```typescript
interface CancellationState {
  requested: boolean;
  requestedAt: Timestamp | null;
  requestedBy: string | null;         // subsystem or operator identity
  acknowledged: boolean;              // set true once the Executor observes the request
                                      // and stops — distinct from `requested`, since
                                      // cancellation is cooperative, not preemptive
                                      // (§8.4 explains why this must be cooperative)
}

interface TimeoutState {
  deadline: Timestamp | null;          // null = no timeout configured for this execution
  extendedCount: number;               // how many times the deadline was pushed
                                       // (e.g. by an operator, during an ESCALATE pause)
}
```

Both are held as explicit state rather than computed ad hoc because RFC-0003 §18.2 item 3 (self-identified gap: "`ESCALATE`'s human-in-the-loop path has no timeout/expiry behavior specified") names exactly this as a needed mechanism — `timeoutState` is this RFC's contribution toward closing that RFC-0003-flagged gap, though the actual escalation-timeout *policy* (what happens when the deadline passes) remains RFC-0003/Scheduler's decision, not something this RFC resolves (§18.2 revisits this boundary).

### 3.8 PermissionContext

```typescript
interface PermissionContext {
  sessionGrants: Permission[];          // RFC-0003 §9.1's exact referenced type — this
                                        // field is its canonical home
  grantedAt: Timestamp;
  grantedBy: "user-override" | "policy-decision" | "default";
}
```

### 3.9 Schema Versioning

RuntimeState's own schema evolves under the identical semver + migration discipline RFC-0004 §7 established for artifact payload schemas — reused rather than reinvented, since RuntimeState objects are themselves checkpointed as `RuntimeStateSnapshot` artifacts (§9.2) and therefore already subject to RFC-0004's schema registry mechanics for that serialized form. The live, in-memory `RuntimeState` object's own version is kept in lockstep with its snapshot artifact's `schemaVersion` — there is deliberately only one version number, not two independently-evolving ones, to avoid the exact kind of confusion RFC-0004 §2.4 warned against when distinguishing schema version from lineage version (a distinction that does not apply here, since a live RuntimeState object has no lineage-version concept of its own — only its snapshots do, via RFC-0004's artifact lineage).

## 4. State Machine

### 4.1 States

```
Created -> Initialized -> Planning -> Waiting -> Running
                                          ^          |
                                          |          v
                                          +----- Blocked
                                                     |
                                          Running <--+ (unblocked)
                                             |
                    +------------------------+------------------------+
                    v                        v                        v
                Retrying                  Paused                 Cancelled
                    |                        |                        |
                    v                        v                        |
                Running                   Running                     |
                (via unpause)          (via resume, §5.4)              |
                                                                       |
                    +----------------------------------------------+
                    v                        v                        v
                Completed                 Failed                  (Cancelled,
                                                                    terminal)
                    |                        |                        |
                    +------------------------+------------------------+
                                             v
                                         Archived
```

### 4.2 Definitions

| State | Meaning |
|---|---|
| `Created` | RuntimeState object exists; Execution Instance accepted but not yet begun. |
| `Initialized` | Initial `ExecutionVariables` (§6) and `PermissionContext` (§3.8) populated; `currentNode` still null. |
| `Planning` | Resolver-side re-planning in progress (e.g. after a `reresolve()` trigger) — distinct from `Waiting`, which is not resolver activity. |
| `Waiting` | Ready to execute the next node but not yet scheduled (Scheduler's queue, not RuntimeState's concern — this status only reflects "not blocked, not yet dispatched"). |
| `Running` | A node is actively executing (`currentNode` non-null). |
| `Blocked` | Progress halted on an unmet dependency or an `ESCALATE` decision (RFC-0003 §5.1) pending resolution — `blockedNodes` non-empty. |
| `Retrying` | A failed node is being re-attempted per `RetryPolicy` (RFC-0003 §7.8) — distinct from re-entering `Running` directly, so retry-specific invariants (§4.4) can be enforced only in this state. |
| `Paused` | Explicitly suspended (operator action or a checkpoint-then-pause request) — distinguished from `Blocked` in that `Paused` is a deliberate external stop, not a data/decision dependency. |
| `Cancelled` | Terminal. `cancellationState.requested = true` and execution stopped (cooperatively, §3.7, §8.4). |
| `Completed` | Terminal. All nodes reached a success/accepted-partial status. |
| `Failed` | Terminal. Unrecoverable failure — `reresolve()` returned `UNRESOLVABLE` (RFC-0003 §8.4) or a `critical`-priority `DENY` with no fallback. |
| `Archived` | Post-terminal. Consistent with RFC-0004 §3.7's artifact archival concept, applied here: the RuntimeState object is no longer active but remains queryable, typically after its final state is checkpointed (§9) and it moves to colder storage. |

### 4.3 Terminal States

`Cancelled`, `Completed`, `Failed` are terminal — no outbound transition except to `Archived`. This is enforced at the mutation API boundary (§12.1): any mutation attempt against a RuntimeState object already in a terminal status is rejected, not silently ignored, mirroring RFC-0004 §9.3's `supersede()` rule against re-superseding an already-superseded artifact ("no diamond supersession... to keep 'what is the current version' a well-defined, single-answer question") — applied here to keep "is this execution still capable of progressing" similarly unambiguous.

### 4.4 Illegal Transitions

Explicitly disallowed, and why:

- **`Created` -> `Running`** (skipping `Initialized`/`Planning`/`Waiting`): disallowed because `Running` implies `currentNode` is set and `ExecutionVariables`/`PermissionContext` are populated — jumping straight there would leave those fields in an undefined state, violating §3.1's minimality-plus-completeness discipline (every field either has a defined value or is explicitly nullable with defined null-semantics; there is no "not yet meaningful" third state for non-nullable fields).
- **Any terminal state -> any non-`Archived` state**: disallowed per §4.3 — a `Completed` execution cannot become `Running` again. A logically similar operation (re-running the same Workflow) must create a **new** Execution Instance (a new `RuntimeID`/`ExecutionID` pair) with `parentExecution` pointing at the old one if it's a genuine resume (§5.4), never a mutation of the terminal object. This is the RuntimeState-level restatement of RFC-0004 §2.1's immutability principle: terminal states behave as effectively-immutable, exactly as artifacts do, for the same reason — auditability requires that "what happened" cannot retroactively change.
- **`Blocked` -> `Completed`/`Failed` directly**: disallowed — a blocked execution must first resolve back through `Running` (unblocked) before reaching a terminal state, so that the eventual terminal state's `completedNodes`/`failedNodes` accounting is always reachable through a `Running` state that actually updated it, never inferred implicitly from the blocking condition alone.
- **`Retrying` -> `Retrying`** (self-loop as a distinct transition, rather than incrementing `retryCount` within a single `Retrying` sojourn): disallowed as a *named transition* — multiple retry attempts increment `retryCount` (§3.2) while remaining in one continuous `Retrying`-then-`Running`-then-possibly-`Retrying`-again cycle; there is no scenario where re-entering `Retrying` from `Retrying` without passing through `Running` in between is meaningful, since a retry attempt that hasn't yet run cannot yet have failed again.

## 5. Lifecycle

### 5.1 Creation

The (future) Scheduler, on accepting an `ExecutionPlan` artifact, calls `RuntimeStateManager.create()` (§12.1), which allocates a new `runtimeId`/`executionId` pair, sets `currentStatus: Created`, `parentExecution: null` (unless this is a resume, §5.4), and populates only the fields that are meaningful at creation time (`startTime`, `executionMode`, `schemaVersion`, `revision: 0`) — every other field takes its explicitly-defined default (empty arrays for node-tracking fields, `null` for not-yet-relevant references).

### 5.2 Mutation

Covered fully in §8 (Concurrency) and §12–13 (who may mutate what). The load-bearing rule stated once here: **every mutation increments `revision`** (§3.2, §8.2) and is itself capable of being checkpointed — mutation is never "invisible" to the checkpoint mechanism, since checkpointing (§9) always captures the current, fully-consistent state as of the moment it's called, not a cached or lagging view.

### 5.3 Checkpoint

Covered fully in §9.

### 5.4 Resume

Resuming from a checkpoint creates a **new** Execution Instance (new `runtimeId`/`executionId`), never reactivates the old one (§4.4's terminal-state immutability applies even to non-terminal-but-interrupted states, e.g. a crash mid-`Running` — the crashed instance's RuntimeState, once recovered, is treated as if it had reached an implicit terminal "interrupted" condition and is archived, not resurrected in place). The new instance's initial field values are copied from the checkpoint's `RuntimeStateSnapshot` artifact (RFC-0004 §5.11) — `completedNodes`, `retryCount`, `modelAssignments`, `executionVariables`, and `permissionContext` are inherited; `currentStatus` resets to `Initialized` (not `Running`, since re-entering `Running` requires the same validated path any fresh execution takes, per §4.4); `parentExecution` is set to the interrupted instance's `executionId`.

### 5.5 Rollback

Distinct from Resume: Rollback discards progress made *since* a specific earlier checkpoint, rather than continuing from the most recent one — used when a completed-but-incorrect set of nodes needs to be re-attempted (e.g. a `Decision` artifact was later found to be wrong and its downstream nodes' results are no longer trusted). Mechanically, Rollback is Resume (§5.4) targeting an older checkpoint than the most recent one, with an additional requirement: any `ArtifactID`s in `currentArtifacts` (§3.2, §10.2) produced by nodes *after* the rollback target are dropped from the new instance's `currentArtifacts`, though — critically, per RFC-0004 §2.1's immutability and §3.8's no-cascading-deletion rule — those artifacts are **never deleted**. They remain in the Artifact Store, simply no longer referenced by the new Execution Instance's live state. This is what makes rollback safe: the old branch of execution is fully preserved for audit (RFC-0004's lineage graph still shows it happened), only the *live* instance stops treating it as current.

### 5.6 Termination

Reaching a terminal status (§4.2, §4.3) via a valid transition. `endTime` is set exactly once, atomically with the terminal-status transition (§8.2's atomic-update guarantee applies here specifically to prevent a race where `endTime` is set but `currentStatus` isn't yet terminal, or vice versa — both fields transition together or the mutation fails entirely).

### 5.7 Garbage Collection

Mirrors RFC-0004 §6.4's distinction precisely: GC for RuntimeState means *tier migration* (moving an `Archived` RuntimeState object's storage location, if it's kept in a separate hot store during active execution, to a colder store once archived) — never deletion of the object itself as a routine sweep. Actual deletion, if ever needed, follows §5.9's bounded path.

### 5.8 Archival

Automatic transition from any terminal status to `Archived` (§4.1) once the final checkpoint (§9) has been durably written — this ordering is a hard invariant: a RuntimeState object never moves to `Archived` before its terminal-state checkpoint exists, since `Archived` is meant to signal "the durable record is safe, the live object is no longer needed for active decision-making," and that signal would be false if no durable record existed yet.

### 5.9 Deletion

Deletion of a RuntimeState object (as opposed to its checkpoint artifacts, governed by RFC-0004 §6.5's `RuntimeStateSnapshot` retention defaults) follows the identical bounded, audited, tombstone-leaving pattern RFC-0004 §3.8 defines for artifacts — reused, not reinvented, since RuntimeState's own audit requirements (§15.7, this RFC's principles list "auditable" explicitly) are no weaker than an artifact's.

## 6. Execution Variables

### 6.1 Taxonomy

```typescript
interface ExecutionVariableStore {
  temporary: Record<string, VariableEntry>;    // §6.2
  persistent: Record<string, VariableEntry>;    // §6.3
  derived: Record<string, VariableEntry>;       // §6.4
  system: Record<string, VariableEntry>;        // §6.5
  user: Record<string, VariableEntry>;          // §6.6
}

interface VariableEntry {
  value: JSONValue;
  scope: "node" | "plan" | "session";           // §6.7
  setBy: string;                                // producing node/subsystem id
  setAt: Timestamp;
}
```

### 6.2 Temporary Variables

Scoped to a single Node's execution (`scope: "node"` only) — cleared once that Node completes, regardless of the Node's outcome. Exists for intra-node working state that has no reason to outlive the node (e.g. a loop counter within a single skill's multi-step internal logic) but that still needs to be visible through `ExecutionContext` (§7) rather than being purely local to the skill's own closure — useful for observability/debugging without granting it any durability.

### 6.3 Persistent Variables

Survive across Nodes and across checkpoint/resume (§5.4) — the working data a Workflow actually accumulates as it progresses (e.g. "the user's stated budget constraint, extracted in node 1, needed by node 5"). These are the only variable category that is unconditionally included in checkpoint payloads (§9.2); the others are checkpoint-included only if their `scope` warrants it (§6.7).

### 6.4 Derived Variables

Computed from other variables or artifacts, never set directly by a producer — a `VariableEntry` in this category carries an additional `derivedFrom: string[]` (referencing other variable keys) so a consumer can tell "this value was computed, not asserted" without needing to inspect `setBy`. Exists to avoid the trap of treating a cached computation as equally authoritative as a directly-observed fact — mirroring RFC-0004 §4.7's distinction between `parentArtifacts` (computational lineage) and raw producer assertion, applied at the variable level.

### 6.5 System Variables

Set only by RuntimeState's own designated mutators (§12–13), never by skill/policy code — reserved namespace for values like `_executionStartedBy` or `_lastCheckpointAt` that are structurally part of RuntimeState's own bookkeeping but expressed through the variable store's uniform interface rather than as yet more top-level schema fields, keeping §3's canonical schema from growing unboundedly every time a small piece of bookkeeping metadata is needed (a scoped escape valve, deliberately narrower than `metadata`, §3.2, since system variables *are* authoritative for internal RuntimeState bookkeeping even though `metadata` is not).

### 6.6 User Variables

Explicitly set by a human operator (e.g. via `userOverrides`, the RFC-0003 §17.3 concept — a user variable set here is what `PermissionPolicy`/`CostPolicy` would read as that override) — kept in a distinct namespace from `persistent` so a consumer can distinguish "the workflow computed this" from "a human explicitly told the workflow this," which matters for both audit (§15.7) and for policy evaluation's purity requirement (RFC-0003 §4.4): a policy reading `context.userConfiguration.userOverrides` should be reading from this namespace specifically, not from `persistent` where a computed value could be mistaken for an explicit human instruction.

### 6.7 Scope, Visibility, Lifetime

| Scope | Visible to | Survives checkpoint/resume? | Cleared when |
|---|---|---|---|
| `node` | Only the producing Node's `ExecutionContext` (§7) | No (excluded from §9.2 checkpoint payload) | Node completes |
| `plan` | Any Node within the same Execution Instance | Yes | Execution Instance terminates |
| `session` | Any Execution Instance within the same Session (§2.1) | Yes, and additionally carried forward into a *new* Execution Instance within the same session (not just a resumed one) | Session ends — **but Session lifecycle is out of this RFC's scope (§18.3)**, so `session`-scoped variable expiry currently has no owning mechanism; flagged as an open question (§18.9) rather than resolved here.

## 7. Context Model

### 7.1 ExecutionContext Definition

```typescript
interface ExecutionContext {
  readonly runtimeState: ReadonlyRuntimeStateView;   // §7.2 — NOT the mutable object itself
  readonly artifacts: IArtifactQuery;                 // RFC-0004 §9.5, scoped read access
  readonly permissionGrant: Permission[];              // a snapshot slice of
                                                       // runtimeState.permissionContext,
                                                       // §3.8, at context-construction time
  readonly cancellationToken: ReadonlyCancellationView;  // read-only view over
                                                          // runtimeState.cancellationState
  readonly logger: ILogger;                            // writes Telemetry/Error/Warning
                                                        // artifacts (RFC-0004 §5.5, §5.13,
                                                        // §5.14) — never writes to
                                                        // RuntimeState directly
  readonly tracer: ITracer;                            // correlates emitted artifacts/events
                                                        // to this executionId
  readonly temporaryWorkspace: ITemporaryWorkspace;      // §7.3 — scratch space, explicitly
                                                        // NOT part of RuntimeState or the
                                                        // Artifact System
  readonly configuration: ReadonlyConfigView;            // RFC-0003 §17's layered config,
                                                        // resolved snapshot for this context
  readonly executionVariables: IVariableAccessor;         // scoped read/propose-write
                                                        // access to §6's store — "propose,"
                                                        // not "write," per §7.4
  readonly modelHandle: IModelHandle | null;             // the specific model assignment
                                                        // for the current node, resolved
                                                        // from runtimeState.modelAssignments
}
```

### 7.2 ReadonlyRuntimeStateView — Why Not the Object Itself

`ExecutionContext.runtimeState` is explicitly a read-only *view*, not the mutable `RuntimeState` object defined in §3. This is the single most important boundary in this RFC's Context Model: skill/policy code executing within a Node invocation must be able to *read* the full current RuntimeState (to make informed decisions, format explanations, etc.) but must never be able to *mutate* it directly, bypassing the designated-mutator model (§12–13). Handing out the live mutable object — even to trusted framework code, let alone sandboxed skill code (RFC-0002 §14.5) — would reintroduce exactly the hidden-coupling risk RFC-0003 §3.6 already ruled out for policies calling each other directly, applied here to code calling into shared mutable state directly.

### 7.3 TemporaryWorkspace

A per-Node-invocation scratch filesystem/memory area for skill code that needs working space beyond `temporary`-scoped variables (§6.2) — e.g. a skill that needs to write intermediate files before producing a final artifact. Deliberately **not** part of RuntimeState (it holds no state that survives past the Node invocation, has no schema, and is never checkpointed) and **not** part of the Artifact System (its contents are not addressable, versioned, or lineage-tracked — anything in it that should be durable and traceable must be explicitly written out as an artifact via RFC-0004's `create()`, at which point it stops being "temporary workspace content" and becomes a real artifact). This exclusion is deliberate scope discipline: without it, "temporary workspace" would become a second, informal artifact system with none of RFC-0004's guarantees.

### 7.4 Ownership and the "Propose, Not Write" Rule

`ExecutionContext.executionVariables` exposes a *propose*-write interface, not a direct write interface: a Node's code calls `proposeSet(key, value, scope)`, which does not immediately mutate RuntimeState — it queues the proposed change, applied atomically by the framework (never by the Node's own code) at the Node's completion boundary, alongside that Node's `ExecutionResult` artifact creation (RFC-0004 §5.2) and `completedNodes` update (§3.2). This mirrors RFC-0003 §4.6's identical rule for policy events ("framework emits, plugin never emits directly") and RFC-0004 §10's identical rule for artifact lifecycle events — the third application of "untrusted-adjacent code proposes, trusted framework code commits" in AGY's accepted architecture, now extended to RuntimeState mutation specifically.

### 7.5 What Is Intentionally Excluded From ExecutionContext

- **No direct handle to the Artifact Store's write API** (`IArtifactStore.create()`, RFC-0004 §9.3) — a Node's produced output becomes an artifact through the framework's own post-execution artifact-creation step (mirroring §7.4's propose-not-write pattern), not through the Node's code calling `create()` itself. This keeps artifact provenance (`producer`, RFC-0004 §4.3) trustworthy — a value the framework asserts about what a Node produced, not a claim the Node's own code makes about itself.
- **No direct handle to the Policy Engine.** A Node's code cannot query "would I be allowed to do X" mid-execution — policy evaluation happens at the framework level, before and around Node execution (RFC-0003 §1.4's diagram), never as a capability a Node calls into.
- **No handle to other Execution Instances' RuntimeState**, even within the same Session (§2.1) — cross-instance visibility, if ever needed, is a Session-level concept out of this RFC's scope (§18.3, §18.9), not something ExecutionContext grants by default.

## 8. Concurrency

### 8.1 Thread Safety

A single RuntimeState object may be read concurrently by multiple observers (e.g. the Policy Engine's continuous evaluation, RFC-0003 §6.4, reading `observedConfidence`/`ledger` while the Executor concurrently updates them) but is mutated only through the single designated-mutator API (§12.1), which internally serializes writes — RuntimeState itself does not expose a raw mutable reference that could be concurrently written by two callers without coordination.

### 8.2 Atomic Updates and Optimistic Locking

Every mutation is a compare-and-swap against `revision` (§3.2): a mutator reads the current `revision`, computes its intended change, and submits `(expectedRevision, mutation)`. If the object's `revision` has advanced since the read (another mutator won the race), the submission is rejected with a `RuntimeStateConflictError`, and the caller must re-read and retry — never silently overwritten, never blocked indefinitely. This is optimistic, not pessimistic, locking: for the expected access pattern (one Executor actively driving one Execution Instance forward, occasionally observed/lightly-annotated by Policy Engine's continuous evaluation) lock contention is expected to be low, and optimistic locking avoids paying pessimistic-lock overhead on every read, consistent with avoiding unnecessary abstraction/overhead where the access pattern doesn't demand it.

### 8.3 Conflict Resolution

A `RuntimeStateConflictError` is never automatically retried by the framework on the caller's behalf with a naive "just reapply the same mutation" strategy — because the *meaning* of a mutation can depend on what changed underneath it (e.g. two concurrent attempts to append to `completedNodes` need to merge as a set union, not silently take one and discard the other; two concurrent attempts to set the *same* `executionVariables` key are a genuine conflict requiring the same "more restrictive wins" or explicit precedence logic RFC-0003 §8.3 uses for merging `MODIFIED` decisions, depending on the field). This RFC specifies per-field conflict-resolution strategy, not a single blanket rule:

| Field category | Conflict strategy |
|---|---|
| Append-only arrays (`completedNodes`, `failedNodes`, `priorFailures`) | Set union — concurrent appends of different elements both succeed |
| Counters (`retryCount[nodeId]`) | Last-committed-wins is wrong (would lose a concurrent increment) — resolved as increment-and-retry: the mutator re-reads and re-applies its own logical increment against the new revision, not a raw overwrite |
| `currentStatus` | No merge — a genuine conflict (two mutators trying to set different terminal statuses concurrently) is treated as a `RuntimeStateConflictError` requiring the losing caller to re-evaluate against the new state, since blindly picking one status could violate §4.4's illegal-transition rules |
| `executionVariables` (same key, concurrent writes) | Rejected outright as a conflict — per §7.4, all variable writes are proposed and committed by the framework at Node-completion boundaries, which are already serialized per Node, making same-key concurrent writes structurally rare; the rare cross-Node case (two Nodes proposing the same `plan`-scoped key) is resolved by the framework applying commits in the order Node completions are received, last-committed-wins, since there is no principled way to merge two Nodes' independent opinions about the same named variable without domain-specific logic this RFC does not have visibility into |

### 8.4 Parallel Execution

RuntimeState's design assumes multiple Nodes may be `Running` concurrently within one Execution Instance (RFC-0001's plan structure permits parallel, non-dependent Nodes) — `currentNode: string | null` in §3.2 is, on reflection, insufficiently expressive for genuine parallelism (a single field cannot represent "nodes A and B are both currently running"). This is flagged here as a real design tension rather than silently resolved: §18.5 documents this as a self-identified correctness gap requiring `currentNode` to become `currentNodes: string[]` before this RFC can be considered complete for parallel-execution support, which the design constraints explicitly require ("must support parallel execution... without requiring redesign"). Cancellation is cooperative, not preemptive (§3.7), specifically because RuntimeState has no mechanism to forcibly halt a Node's in-flight execution — it can only set `cancellationState.requested` and wait for the Executor (future) to observe and honor it, which is why `acknowledged` is tracked as a separate signal from `requested`.

### 8.5 State Consistency

Every mutation is all-or-nothing (§8.2's CAS mechanism) and every read returns a fully-consistent snapshot as of some specific `revision` — there is no way to observe a RuntimeState object mid-mutation (e.g. `currentStatus` updated but `endTime` not yet, per §5.6's atomicity requirement). This consistency guarantee is what makes checkpointing (§9) safe to call at any time without needing to coordinate with in-flight mutations beyond the same CAS mechanism every other reader/writer already uses.

## 9. Checkpointing

### 9.1 Checkpoint Format

A checkpoint is a `RuntimeStateSnapshot` artifact (RFC-0004 §5.11), created via RFC-0004's standard `create()` API (RFC-0004 §9.3) — this RFC does not invent a separate checkpoint storage mechanism; checkpoints are ordinary artifacts, gaining all of RFC-0004's guarantees (checksumming, RFC-0004 §11.2; retention policy, RFC-0004 §6.5's `RuntimeStateSnapshot` defaults; lineage, RFC-0004 §8) for free.

### 9.2 Serialization

The full `RuntimeState` object (§3.2) serializes into `RuntimeStateSnapshotPayload` (RFC-0004 §5.11) directly — this RFC confirms and slightly extends RFC-0004's originally-provisional payload shape:

```typescript
interface RuntimeStateSnapshotPayload {
  sessionId: string;                    // unchanged from RFC-0004 §5.11
  capturedAt: Timestamp;                // unchanged
  priorFailures: ResolutionFailure[];    // now concretely typed (was JSONValue in
                                        // RFC-0004 §5.11's provisional definition,
                                        // pending this RFC — see §18.6)
  ledgerSnapshot: ArtifactID;            // unchanged — maps to this RFC's
                                        // resourceUsageReference (§3.2)
  sessionGrants: Permission[];           // now concretely typed (was JSONValue) — maps
                                        // to this RFC's permissionContext.sessionGrants
  // --- fields added by this RFC, extending RFC-0004 §5.11's provisional shape ---
  runtimeId: RuntimeID;
  executionId: ExecutionID;
  parentExecution: ExecutionID | null;
  currentStatus: RuntimeStatus;
  completedNodes: string[];
  failedNodes: NodeFailureRecord[];
  retryCount: Record<string, number>;
  modelAssignments: Record<string, string>;
  persistentVariables: Record<string, VariableEntry>;   // §6.3 only — node-scoped
                                                        // variables are never checkpointed,
                                                        // per §6.7's table
  revision: number;
  schemaVersion: string;
}
```

Excluded from the checkpoint payload, deliberately: `node`-scoped `executionVariables` (§6.7 — cleared at Node completion regardless, so never meaningfully "current" at checkpoint time in a way worth persisting), `temporaryWorkspace` contents (§7.3 — explicitly non-durable), and the live `ExecutionContext` object (§7 — a per-invocation view, not state).

### 9.3 Incremental Checkpoints

A full-payload checkpoint (§9.2) is not required on every state change — this RFC recommends, without mandating a specific cadence, that checkpoints be taken at Node-completion boundaries (natural, already-serialized commit points per §7.4/§8.3) rather than on every individual field mutation, to bound checkpoint-write volume. An **incremental checkpoint** is expressible as a `RuntimeStateSnapshot` artifact whose `parentArtifacts` (RFC-0004 §4.5) includes a `derivedFrom` edge to the prior checkpoint, with only changed fields populated and the rest implicitly inherited via lineage traversal (RFC-0004 §8.2) at read time. This RFC specifies the mechanism (reuse RFC-0004's lineage graph to represent incremental deltas) without mandating that every implementation must use incremental checkpoints — full-payload checkpointing at every Node boundary is a valid, simpler implementation choice for early AGY deployments, with incremental checkpointing available as an optimization once checkpoint volume/size becomes a measured problem (§14.3).

### 9.4 Recovery

On Scheduler (future) startup or explicit resume request, recovery means: query the Artifact System (RFC-0004 §9.5) for the most recent `RuntimeStateSnapshot` artifact whose `executionId` matches the target, resolve any incremental-checkpoint chain (§9.3) via lineage traversal to reconstruct the full payload, and use that reconstructed payload as the initial field values for a new Execution Instance per §5.4's Resume procedure.

### 9.5 Rollback

Covered in §5.5 — mechanically, targeting an older checkpoint artifact than the most recent one during Recovery (§9.4).

### 9.6 Crash Recovery

Distinguished from a normal Resume (§5.4) only in *how* the interruption is detected, not in the recovery mechanism itself: a crash means the Execution Instance never reached a terminal status or an explicit `Paused` state — its RuntimeState object's last known `currentStatus` was `Running`/`Retrying`/`Blocked` with no subsequent checkpoint reflecting a clean stop. Recovery in this case must additionally reconcile: any Node marked `currentNode` (or, post-§8.4's fix, in `currentNodes`) at the last checkpoint is treated as `failed` with `reason: "crashed"` in the new instance's `NodeFailureRecord` (§3.6) — extending §3.6's enum to include this reason — rather than assumed complete, since there is no reliable signal that a Node in-flight at crash time actually finished. This is a fail-closed choice (consistent with the AGY-wide invariant restated across RFC-0001 §9, RFC-0002 §14, RFC-0003 §13.4, RFC-0004 §3.3 and others): assuming an interrupted Node succeeded, with no evidence either way, would be the unsafe default.

## 10. Artifact Integration

### 10.1 The Reference-Not-Duplicate Rule

Restated as the governing rule for this section: RuntimeState never stores artifact *payloads*, only `ArtifactID`s (RFC-0004 §4.2). Every field in §3.2 that touches artifact data — `currentArtifacts`, `resourceUsageReference`, `checkpointReference`, `NodeFailureRecord.errorArtifactRef` — is typed as `ArtifactID` or `ArtifactID[]`, never as an inline payload type.

### 10.2 `currentArtifacts` — Scope

`currentArtifacts` is explicitly **not** the full lineage of everything this Execution Instance has ever produced (that is a query against RFC-0004's `descendantsOf`/`ancestorsOf` API, RFC-0004 §9.5, using the Execution Instance's root `ExecutionPlan` or `UserIntent` artifact as the starting point — always available, never duplicated here). It is a small, bounded, "currently relevant" working set — e.g. the most recent `ExecutionResult` per active/recently-completed Node, sized to support fast in-flight decision-making (a Policy Engine continuous-evaluation read, RFC-0003 §6.4, needing "what did the last few nodes produce" without a full lineage traversal) without RuntimeState itself becoming an unbounded, ever-growing artifact index — which would violate both §1.2's exclusion of "artifact payloads" from RuntimeState's ownership and this RFC's minimality principle (§3.1) if taken to its unbounded extreme.

### 10.3 Lineage Relationships

Every artifact created as a byproduct of this Execution Instance (via the framework-mediated creation path, §7.5) has its `parentArtifacts` (RFC-0004 §4.5) set by the framework to correctly reflect computational lineage — an `ExecutionResult` artifact is `derivedFrom` the `ExecutionPlan` and any upstream `ExecutionResult`s it consumed, exactly as RFC-0004 §5.2 already specifies. RuntimeState's role here is purely to supply the framework with the correct `executionId`/`currentNode` context needed to construct those `parentArtifacts` edges correctly — RuntimeState does not itself store or manage the lineage graph; RFC-0004 owns that entirely.

### 10.4 Checkpoint Artifacts as a Special Case

`checkpointReference` (§3.2) is the one field that points at an artifact *representing RuntimeState itself* (a `RuntimeStateSnapshot`, §9) rather than at output produced by execution — worth naming explicitly as a distinct category from `currentArtifacts`, since a consumer querying "what has this execution produced" should not need to filter out its own checkpoint history from that answer; keeping `checkpointReference` as a separate, singular field (most recent checkpoint only — older checkpoints are reachable via that artifact's own `parentArtifacts` chain, RFC-0004 §8.2) rather than folding it into `currentArtifacts` keeps that distinction structurally clear rather than requiring every consumer to know to filter by `artifactType`.

## 11. Policy Integration

### 11.1 What RuntimeState Exposes to Policy Engine

RFC-0003's `IPolicyContext` (RFC-0003 §9.1) reads several fields this RFC now gives a canonical home:

| `IPolicyContext` field (RFC-0003) | RuntimeState source (this RFC) |
|---|---|
| `context.ledger` | Resolved by fetching the `ResourceUsage` artifact at `resourceUsageReference` (§3.2, §10.1) |
| `context.sessionGrants` | `permissionContext.sessionGrants` (§3.8) |
| `context.priorDecisions` | Queried from the Artifact System (`Decision` artifacts, RFC-0004 §5.4) filtered by this execution's artifacts (§10.2's working set, or a full lineage query for completeness) — not stored redundantly in RuntimeState |
| `context.priorFailures` | `priorFailures` (§3.2) directly |
| `context.observedConfidence` | Read from the relevant `ExecutionResult` artifact's `observedConfidence` field (RFC-0004 §5.2), located via `currentArtifacts` (§10.2) |
| `context.executionMode` | `executionMode` (§3.2) directly |
| `context.repositoryMetadata` | Not a RuntimeState field — resolved via `currentArtifacts` to the relevant `RepositorySnapshot` artifact (RFC-0004 §5.10), if present |

This table is this RFC's confirmation that every RFC-0003 `IPolicyContext` field referencing live state now has an unambiguous, non-duplicated source — closing the exact gap this RFC exists to close.

### 11.2 Confidence and Evidence References

RuntimeState itself never computes or stores a policy `confidence` value — `observedConfidence` (read via §11.1's table) originates from the Executor's own reporting into an `ExecutionResult` artifact (RFC-0004 §5.2), not from RuntimeState synthesizing it. `evidence` (RFC-0003 §5.1's `PolicyDecision.evidence`) similarly stays as `ArtifactID[]` references on the `Decision` artifact itself (RFC-0004 §5.4) — RuntimeState is a pass-through/locator for these, never a second copy.

### 11.3 What RuntimeState Must Never Embed

Per the design constraints' explicit prohibition ("RuntimeState MUST NOT own... Policy definitions"): no `IPolicy` logic, no conflict-resolution logic (RFC-0003 §8), no policy manifest data (RFC-0003 §4.3) appears anywhere in RuntimeState's schema (§3) or mutation logic (§12–13). RuntimeState's only relationship to policy is as a *data source* `PolicyContext` construction reads from (§11.1) and as a *target* `PolicyDecision`-driven mutations act upon (§13.2) — never as a place where policy reasoning itself occurs.

## 12. Future Scheduler Integration

### 12.1 What Scheduler May Read

The entire `RuntimeState` object, via `ReadonlyRuntimeStateView` (§7.2) or an equivalent full-object read API (`RuntimeStateManager.get(executionId)`) — Scheduler needs the complete picture (`currentStatus`, `blockedNodes`, `retryCount`, etc.) to make scheduling decisions, and no field in §3.2 is scoped away from it.

### 12.2 What Scheduler May Mutate

Scheduler is a **designated mutator** (§8.1) for exactly these transitions and fields, and no others:

- `currentStatus` transitions: `Created -> Initialized`, `Initialized -> Planning`, `Planning -> Waiting`, `Waiting -> Running` (dispatching a Node), `Running -> Blocked` (detecting an unmet dependency Scheduler itself identifies, distinct from an `ESCALATE`-driven block, §12.3), `Blocked -> Running` (dependency resolved), any status `-> Paused` (explicit pause request), `Paused -> Waiting`/`Running` (resume).
- `currentNode` (§8.4's caveat noted — pending the `currentNodes` fix): setting which Node(s) are dispatched.
- `checkpointReference`: updating after Scheduler triggers a checkpoint (§9).

### 12.3 What Scheduler Is Forbidden From Changing

- **`currentStatus -> Blocked` triggered by an `ESCALATE` decision, and `Blocked -> Running`/terminal resulting from that escalation's resolution**: these transitions belong to whatever component consumes `Decision` artifacts with `outcome: ESCALATE` (RFC-0003 §5.1) — Scheduler may *observe* this happened (reading `blockedNodes` and the relevant `Decision` artifact) but does not itself decide to unblock; that requires the escalation's actual resolution (human input or higher-authority override), a mutation this RFC assigns to whatever future component formally owns escalation resolution (flagged as undecided in §18.7, since no accepted RFC currently names that owner).
- **`completedNodes`, `failedNodes`, `retryCount`, `currentArtifacts`, `modelAssignments`, `resourceUsageReference`**: these reflect what actually happened during execution — only the Executor (§13) may write them, since Scheduler does not itself run Nodes and has no first-hand knowledge to assert these fields correctly. Scheduler mutating them would violate §7.4/§7.5's "framework asserts what actually happened, not an upstream orchestrator's belief about it" principle.
- **`permissionContext`, `executionVariables` (`user`/`persistent` namespaces)**: these originate from Policy Engine decisions and explicit human input respectively (§6.6, §11.1) — Scheduler has no legitimate basis to set either.
- **Terminal-state transitions** (`-> Completed`, `-> Failed`, `-> Cancelled`) driven by execution outcome (as opposed to an explicit operator cancellation request, which Scheduler *may* relay): these require the Executor's confirmation that all Nodes reached a final outcome — Scheduler alone, without that confirmation, cannot correctly assert completion.

### 12.4 Rationale

This split mirrors RFC-0003 §1.3's own boundary discipline (Policy Engine decides, Scheduler executes, neither does the other's job) extended one level: Scheduler *orchestrates* (decides what runs when, per RFC-0003's decisions) but does not *assert outcomes* — that is exclusively the Executor's epistemic authority, since only the Executor has direct knowledge of what actually happened during a Node's execution.

## 13. Future Executor Integration

### 13.1 What Executor May Read

Same as Scheduler (§12.1) — full read access via `ReadonlyRuntimeStateView`, plus the constructed `ExecutionContext` (§7) for the specific Node it is currently running, which is Executor's actual working interface, not the raw RuntimeState read API.

### 13.2 What Executor May Mutate

The Executor is the designated mutator for outcome-reflecting fields:

- `currentStatus -> Running` (beginning a dispatched Node), `Running -> Retrying` (on failure, if `RetryPolicy` permits, RFC-0003 §7.8), `Retrying -> Running` (re-attempt), `Running -> Completed`/`Failed` (final Node outcome causing the whole Execution Instance to reach a terminal state, subject to §4.4's transition rules).
- `completedNodes`, `failedNodes` (via `NodeFailureRecord`, §3.6), `retryCount`.
- `currentArtifacts` (appending references to newly-created `ExecutionResult`/other artifacts, per the framework-mediated creation path, §7.5).
- `resourceUsageReference` (updating to point at the latest `ResourceUsage` artifact snapshot as costs accrue — the mechanism that makes RFC-0003 §7.3 `CostPolicy`'s continuous evaluation, RFC-0003 §6.4, actually see fresh data).
- `modelAssignments` (recording which model actually served a given Node, per §3.2's determinism-for-resume rationale).
- `executionVariables` — via the propose/commit mechanism (§7.4), not direct write, even for the Executor itself: this RFC does not grant the Executor an exception to §7.4's rule, since the propose/commit boundary exists to keep variable-write provenance trustworthy regardless of which subsystem is proposing.

### 13.3 What Executor Is Forbidden From Changing

- **`currentStatus -> Blocked`/`Waiting` transitions and any Scheduler-owned dispatch decision** (§12.2) — Executor runs what it's told to run; it does not decide what runs next or when, mirroring RFC-0003 §1.3's "Policy Engine does not select" boundary applied to Scheduler/Executor.
- **`permissionContext`** — Executor consumes permission grants (via `ExecutionContext.permissionGrant`, §7.1) but never sets them; that is exclusively Policy-Engine-driven (§11.1).
- **`cancellationState.requested`** — Executor may set `acknowledged` (§3.7, confirming it observed and honored a cancellation request) but never `requested` itself; requesting cancellation is an external (operator or Scheduler-relayed) action, not something Executor initiates about itself.
- **`checkpointReference`** — checkpoint-triggering is a Scheduler-level orchestration decision (§12.2), even though the checkpoint's *content* (§9.2) is drawn from fields Executor populated; Executor supplies the data, Scheduler decides when to durably capture it.

### 13.4 Rationale

The Scheduler/Executor split (§12 vs. §13) is deliberately drawn along the same "orchestration authority vs. outcome authority" line established in §12.4 — Executor is the only component with first-hand knowledge of what a Node actually did, so it alone may assert outcome-reflecting fields; everything about *when* and *whether* to run is Scheduler's (or Policy Engine's, for gating) authority, never Executor's to decide unilaterally.

## 14. Performance

### 14.1 Memory Model

RuntimeState objects for actively-`Running`/`Blocked`/`Retrying`/`Paused`/`Waiting` Execution Instances are held fully in memory (hot, mirroring RFC-0004 §6.1's tier model) — this is a hard sizing constraint, not an aspiration: §3.1's minimality discipline and §10's reference-not-duplicate rule exist specifically to keep a single RuntimeState object's in-memory footprint small and roughly constant regardless of how much data an Execution Instance has produced (bounded `currentArtifacts` working set, §10.2; no inline payloads, §10.1; no unbounded history, §6.5's rejection of `fullExecutionLog`). Terminal, `Archived` instances are evicted from the hot set entirely — their data lives only in their checkpoint artifacts (RFC-0004's tiered storage, §6.1), not in a resident RuntimeState object.

### 14.2 Copy-on-Write

`ReadonlyRuntimeStateView` (§7.2) is implemented as a copy-on-write snapshot at view-construction time — a Node's `ExecutionContext` (§7) sees a consistent view of RuntimeState as of the moment its Context was constructed, even if the underlying object mutates (via a different Node's concurrent completion, §8.4) during this Node's execution. This avoids requiring in-flight Node code to handle a torn/inconsistent read, without requiring a full lock during the Node's (potentially long) execution — the CoW snapshot is taken once, cheaply, and the live object remains free to accept new mutations from other concurrent Nodes immediately.

### 14.3 Snapshots

Distinguished from checkpoints (§9): a "snapshot" in this section's performance sense is the in-memory CoW view (§14.2), ephemeral and never durably written. A "checkpoint" (§9) is the durable, artifact-backed capture. Conflating these two concepts would be a real terminology hazard this RFC flags explicitly to avoid — the words are similar enough that implementation discussions should be precise about which one is meant.

### 14.4 Compression

Not applied to the in-memory hot object (§14.1's small-footprint design makes this unnecessary) — applies only to checkpoint artifacts once written, and is entirely RFC-0004 §6.6's concern at that point, not something this RFC needs its own mechanism for.

### 14.5 Caching

`ReadonlyRuntimeStateView` instances (§14.2) are themselves a form of cache — constructed once per Node invocation, not re-fetched on every field access within that invocation. No additional cross-invocation caching layer is specified in this RFC; given §14.1's already-small memory footprint, an additional cache would add complexity without a demonstrated performance problem to solve, consistent with avoiding speculative abstraction.

### 14.6 Scalability

The primary scalability question this RFC's design must answer is: does per-Execution-Instance RuntimeState size grow unboundedly with a long-running or heavily-retried Workflow? §3.1/§6.5/§10.2's bounding decisions are aimed directly at preventing this — but this RFC does not claim to have empirically validated the bound; §18.8 flags this as an open, testable question (what is the actual worst-case size of `completedNodes`/`failedNodes`/`retryCount` for a pathologically long-running Workflow, and is a bounded-size guarantee needed there too, e.g. capping `retryCount` history detail beyond a configurable Workflow-size ceiling).

## 15. Failure Recovery

### 15.1 Partial Execution

A RuntimeState object mid-`Running` at the moment of interruption represents partial execution by definition — §9.6 (Crash Recovery) is this RFC's answer: reconcile in-flight Nodes as `crashed` failures, never assumed-complete, then proceed via the ordinary Resume path (§5.4) from the last valid checkpoint.

### 15.2 Crash Recovery

Covered fully in §9.6.

### 15.3 Resume

Covered fully in §5.4.

### 15.4 Retry

Covered via `retryCount`/`RetryPolicy` integration (§3.2, §11.1) and the `Retrying` state (§4.1–4.2) — retry is a *normal*, expected-path lifecycle transition, not a failure-recovery-exceptional one, distinguishing it structurally from crash recovery (§9.6), which handles the *unexpected* interruption case.

### 15.5 Rollback

Covered fully in §5.5.

### 15.6 Corruption

A `RuntimeStateSnapshot` artifact failing checksum verification on read (RFC-0004 §11.2, §13.1) is handled identically to any other corrupted artifact — RFC-0004's `ArtifactCorruptedError` propagates up through this RFC's Recovery procedure (§9.4), which must then fall back to the next-most-recent valid checkpoint in the artifact's `parentArtifacts` chain (§9.3's incremental-checkpoint lineage) rather than failing recovery outright, provided an earlier valid checkpoint exists — a graceful degradation this RFC specifies explicitly rather than leaving to be discovered as a gap: **Recovery must walk backward through the checkpoint lineage until it finds a checksum-valid snapshot, not assume the most recent one is always usable.**

### 15.7 Consistency Guarantees

Restated as this RFC's summary consistency claim: any successfully-committed RuntimeState mutation (§8.2's CAS success) is immediately visible to all subsequent reads at or above its `revision`; any checkpoint (§9) captures a fully self-consistent state as of a specific `revision`, never a torn intermediate state (§8.5); and Recovery (§9.4, §15.6) always reconstructs a state that is *some* valid, previously-committed `revision`'s worth of data — never a synthesized or interpolated state that never actually existed during live execution. This last property — recovery only ever returns to a real, previously-true state — is the RuntimeState-level expression of the same determinism principle (§2.3 of this RFC's design principles, reusing RFC-0001 §3's "same inputs, same plan" lineage) applied to the recovery path specifically.

## 16. Testing Strategy

### 16.1 Unit Tests

State-machine transition validity (§4.4's illegal-transition table) is exhaustively unit-testable as a pure function of `(currentStatus, attemptedStatus) -> allowed | rejected`, independent of any live object or storage backend — every cell of the transition table should have a corresponding test.

### 16.2 Property Testing

- **Revision monotonicity**: for any sequence of successful mutations, `revision` strictly increases, never repeats, never decreases.
- **Terminal immutability**: once `currentStatus` reaches a terminal value (§4.3), no subsequent mutation attempt succeeds except the single `-> Archived` transition.
- **Checkpoint round-trip**: for any RuntimeState object, checkpointing (§9.2) then recovering (§9.4) produces a new Execution Instance whose inherited fields exactly match the checkpointed values (modulo the fields §5.4 deliberately resets, like `currentStatus -> Initialized`).
- **Reference-only property**: no field in a serialized RuntimeState object ever contains an artifact payload — a structural test asserting every artifact-touching field's runtime type is `ArtifactID`/`ArtifactID[]`, never an inline payload shape, enforcing §10.1 mechanically rather than only by code review.

### 16.3 Fuzz Testing

Malformed/adversarial mutation proposals (§7.4's propose/commit boundary) — out-of-range `revision` values, conflicting concurrent proposals for the same field (§8.3's table), malformed `ArtifactID` references — verified to be rejected at the mutation API boundary (§12–13) rather than silently accepted and corrupting state.

### 16.4 Concurrency Testing

Simulated concurrent mutators (multiple Nodes completing near-simultaneously, Scheduler and Executor racing on adjacent transitions) verified against §8.2's CAS guarantee and §8.3's per-field conflict-resolution table — specifically testing that the *documented* strategy per field is what actually happens under contention, not just that contention doesn't crash the system.

### 16.5 Recovery Testing

Simulated crash-at-every-possible-point testing: for a representative Workflow, force interruption at every Node boundary and every intra-Node point recoverable checkpoint granularity supports (§9.3), then verify Resume (§5.4) and Crash Recovery's reconciliation (§9.6) both produce a valid, `NodeFailureRecord`-correct new Execution Instance in every case.

### 16.6 Invariant Testing

A standing suite asserting, against any RuntimeState object at any point in its lifecycle: `endTime` is null iff `currentStatus` is non-terminal (§5.6); `currentArtifacts` never exceeds its bounded working-set size (§10.2, §14.1); every `ArtifactID`-typed field either resolves via RFC-0004's `get()` or resolves to a tombstone (RFC-0004 §3.8) — never to an `ArtifactNotFoundError`, since a RuntimeState-held reference should never point at something that was never validly created (§3.2's referenced artifacts are only ever set by the framework after RFC-0004's `create()` succeeds, §7.5).

## 17. Tradeoffs

| Approach | Why Not Chosen (or, for the winner, why chosen) |
|---|---|
| **Mutable runtime object** (the naive default — a plain mutable struct, no revisioning, no CAS) | Rejected as insufficient on its own — this RFC's design *is* fundamentally a mutable object (§2's design principles list "immutable-by-default" but the requirement is for the *object's field values* to change via controlled mutation, not for the object to be replaced wholesale on every change), but a naive mutable struct with no `revision`/CAS mechanism (§8.2) would fail the "thread-safe" and "auditable" principles outright — two concurrent writers could silently clobber each other with no detection. The chosen design keeps mutability (for the reasons below) but adds the CAS discipline a naive mutable object lacks. |
| **Immutable snapshots** (every mutation produces an entirely new RuntimeState object, no in-place field updates at all — the RFC-0004 artifact model applied directly to live state) | Considered seriously, rejected as the *primary* live-object model, adopted for checkpointing (§9) specifically. Full immutable-snapshot-per-mutation would mean every single field change (e.g. one Node's `completedNodes` append) allocates an entirely new object — for a Workflow with many Nodes, this is significant allocation/GC pressure for what is conceptually a small, incremental update, working against §14's performance goals. RFC-0004's artifacts are immutable because they represent *durable, already-finished* facts; RuntimeState represents an *actively changing* live process — the same reasoning that led RFC-0004 §15 to reject "event sourcing" as the *complete* artifact model (read-amplification cost) applies with even more force here, since RuntimeState mutations are far more frequent than artifact creation. |
| **Event sourcing** (RuntimeState's current value is always derived by replaying a full mutation-event log, never stored as materialized current state) | Rejected for the same read-amplification reason RFC-0004 §15 rejected it for artifacts, sharper here: a Policy Engine continuous-evaluation read (RFC-0003 §6.4) needs `context.observedConfidence` with low latency, on a hot path — requiring a replay-to-current-state on every such read would be a severe performance regression versus a materialized object with `revision`-tracked incremental updates. The checkpoint mechanism (§9) and `NodeFailureRecord`/`completedNodes` append-only fields are event-sourcing-*adjacent* (an append is a lightweight event), but the *current* state is always materialized, never derived by full replay at read time — the same "get the auditability benefit without the read-amplification cost" tradeoff RFC-0004 struck for artifacts, struck again here for live state. |
| **Database-backed runtime** (RuntimeState lives exclusively as rows in a relational or document database, no distinguished in-memory hot representation) | Rejected as the sole model for the same reason RFC-0004 §15 rejected "database rows" as artifacts' sole model — but with a sharper performance argument here: RuntimeState is read and mutated far more frequently, per unit time, than a typical artifact (every Node completion, every continuous-evaluation policy read, §11.1's table) — routing every one of those through a database round-trip would make RuntimeState the dominant latency cost of the entire execution path. The chosen design keeps RuntimeState's canonical live representation in-memory (hot, §14.1) with database/object storage reserved for checkpoint artifacts (§9.1, delegated entirely to RFC-0004's own storage tiers) — a hybrid, not a rejection of durable storage altogether. |
| **Actor model** (RuntimeState as an actor with a private mailbox, all reads and writes as async messages, no shared mutable state at all) | Rejected as the primary concurrency model, though the propose/commit pattern (§7.4) and CAS-based mutation API (§8.2) are actor-model-adjacent in spirit (a mutation "proposal" is message-passing-shaped). Full actor-model adoption would mean even *reads* of RuntimeState (Policy Engine's continuous evaluation, Executor's `ExecutionContext` construction) become asynchronous message round-trips rather than direct reads of an in-memory object — a heavier concurrency-control cost than the optimistic-CAS model (§8.2) for a workload this RFC expects to have low write contention (one Executor driving forward, occasional concurrent Node completions under parallelism, §8.4) rather than the high-fan-in message-contention pattern actor systems are optimized for. |
| **Chosen: mutable, revisioned, in-memory-canonical object with CAS-based controlled mutation and artifact-backed checkpointing** | Matches the actual access pattern (frequent, low-latency reads and writes to a single small object per Execution Instance, occasional durable capture) better than any single alternative above taken as the *whole* model — while deliberately borrowing the specific property from each alternative that *does* fit: immutability for terminal states and checkpoints (from immutable snapshots/artifacts), append-only event-shaped fields for lineage-relevant history (from event sourcing), durable tiered storage for checkpoints specifically (from database-backed/object-store models), and message-shaped proposal semantics for the controlled-mutation boundary (from the actor model) — without adopting any of those models' full overhead where the access pattern doesn't justify it. |

## 18. Critical Self-Review

### 18.1 `currentNode` Does Not Support Parallel Execution As Specified — A Real Gap, Not Just a Note

Flagged inline at §8.4 and restated here as the most significant unresolved issue in this RFC: the design constraints require support for parallel execution "without requiring redesign," but §3.2's schema defines `currentNode: string | null` — a single value, incapable of representing multiple concurrently-`Running` Nodes. This is a genuine correctness gap in the schema as specified, not merely a documented limitation. **This RFC should not be considered final until `currentNode` is corrected to `currentNodes: string[]`** (with corresponding updates to §4's state-machine description, which currently reasons about "a Node" in the singular in places, and to §14.2's CoW-snapshot reasoning, which is unaffected by the change but should be re-verified against it). This is called out as a required follow-up correction rather than silently fixed in this draft, per the instruction to document discovered issues rather than quietly resolve them — except that in this case the issue is internal to this RFC itself, not a conflict with a prior accepted RFC, so it is flagged as a required revision to this RFC before ratification, not a separate cross-RFC finding.

### 18.2 Escalation Timeout Ownership Remains Unresolved

§3.7 gives `timeoutState` a field but §12.3 explicitly declines to assign ownership of *acting* on an expired escalation timeout to Scheduler, and no accepted RFC (including this one) names the component that does. This RFC closes RFC-0003 §18.2 item 3's data-representation gap (there is now somewhere to record a deadline) without closing the *behavioral* gap (nothing yet decides what happens when the deadline passes). Genuinely unresolved, not merely deferred — worth explicit priority in whatever RFC ends up owning escalation resolution (§18.7).

### 18.3 Session Is Named But Not Designed

§2.1 defines Session as a concept RuntimeState's `parentExecution` field gestures toward but does not fully model — cross-Execution-Instance grouping, `session`-scoped variable lifetime (§6.7), and session-level permission/context inheritance are all named as real requirements implied by the design constraints ("user variables," "session" scope) without a Session object or lifecycle ever being specified. This is a deliberate scoping decision (Session was not named as this RFC's subject) but leaves a real gap: `session`-scoped `executionVariables` (§6.7's table) currently have no defined expiry mechanism, an issue directly restated in §18.9.

### 18.4 RuntimeID vs. ExecutionID Redundancy

§3.3 keeps these as two separately-generated ULIDs despite being 1:1 for every case this RFC currently defines. The stated justification (conceptual distinctness, future-proofing against a scenario where they diverge) is a real but speculative argument — this is flagged honestly as a case where §3.1's minimality principle arguably should have won and collapsed these into one field, and the current two-field design is a judgment call this RFC is not fully confident in, rather than a settled decision.

### 18.5 (Cross-reference to 18.1) Parallel Execution's Full Impact Was Not Traced Through Every Section

Beyond `currentNode` itself, §7.1's `ExecutionContext` (constructed per-Node-invocation) and §8.2's CAS mutation model were reasoned about with an implicit single-Node-at-a-time framing in places, even though §8.4 explicitly acknowledges concurrent Nodes as expected. A full revision pass re-checking every section against genuinely concurrent multi-Node execution (not just acknowledging it's possible in §8) has not been completed in this draft — named as required follow-up work, not resolved here.

### 18.6 RFC-0004's Provisional `RuntimeStateSnapshotPayload` Typing Is Now Superseded — Documented Separately

RFC-0004 §5.11 explicitly left `priorFailures: JSONValue` and `sessionGrants: JSONValue` as loosely-typed placeholders "pending the RuntimeState RFC." This RFC (§9.2) now provides concrete types (`ResolutionFailure[]`, `Permission[]`). Per the instruction to document such findings separately rather than silently editing an earlier accepted RFC: **RFC-0004 §5.11's `RuntimeStateSnapshotPayload` schema should be formally amended, in a follow-up patch to RFC-0004 or in this RFC's ratification notes, to adopt this RFC's §9.2 typed schema** — RFC-0004's own text anticipated this exact resolution ("typed loosely here pending RuntimeState RFC"), so this is confirmation of an already-anticipated update, not a surprise conflict, but it should still be tracked as a formal amendment rather than assumed to happen automatically.

### 18.7 No Component Owns Escalation Resolution

Restated from §12.3 and §18.2 as its own item because it is significant enough to warrant separate tracking: RFC-0003 defines `ESCALATE` as an outcome, this RFC defines `Blocked` as the resulting RuntimeState status and `blockedNodes`/`timeoutState` as where the relevant data lives, but **no accepted RFC names the component responsible for actually resolving an escalation** (presenting it to a human operator, receiving their response, and driving the corresponding RuntimeState mutation). This is a real, load-bearing gap in the accepted architecture as a whole, not specific to this RFC — flagged here because this RFC is the first one forced to confront it concretely (§12.3's mutation-ownership table has nowhere to put this responsibility).

### 18.8 Unbounded Growth Under Pathological Retry/Long-Running Workflows Not Empirically Validated

Restated from §14.6: this RFC's minimality/boundedness design (§3.1, §6.5, §10.2) is argued for structurally but not validated against a concrete worst-case scenario (e.g. a Workflow with thousands of Nodes, or a single Node retried hundreds of times). Whether `retryCount`, `completedNodes`, and `failedNodes` need their own bounding/summarization strategy at extreme scale is an open, testable question this RFC does not resolve.

### 18.9 `session`-Scoped Variable Lifetime Has No Owning Mechanism

Restated from §6.7 and §18.3: the table in §6.7 names `session` scope and describes when such variables should be cleared, but since Session itself is undesigned (§18.3), there is currently no mechanism that actually performs that clearing. This field/scope exists in the schema (§6.1) ahead of the infrastructure needed to fully honor its stated lifetime semantics — an honest gap between what §6's schema promises and what this RFC's scope can currently deliver.

### 18.10 Possible Simplification Not Taken: Collapsing `CancellationState`/`TimeoutState` Into `executionVariables.system`

§6.5 creates a `system` variable namespace explicitly to avoid growing §3.2's top-level schema for every piece of internal bookkeeping — yet `cancellationState` and `timeoutState` were kept as dedicated top-level fields rather than folded into that same namespace. The justification (§3.7: needing typed, structured access rather than the loosely-typed `VariableEntry.value: JSONValue` shape) is defensible, but this RFC acknowledges the line between "deserves a top-level field" and "belongs in `system` variables" was not applied with fully consistent criteria across §3.2 and §6.5 — worth a dedicated design-consistency pass rather than treated as fully settled.

## 19. Recommendation: Next Subsystem to Design

Per the accepted finding, Scheduler should not be designed until Artifact (RFC-0004), Event Bus, and RuntimeState (this RFC) all exist. This RFC completes the third. **This RFC recommends Event Bus as the next subsystem (RFC-0006), not Scheduler yet** — a departure from treating "the third box is checked, go straight to Scheduler" as sufficient, for a reason grounded in dependency analysis rather than convenience:

Scheduler's own responsibilities, as this RFC has now made concrete (§12), depend on being able to *observe* RuntimeState transitions and Artifact lifecycle events reliably — Scheduler needs to know when a Node's `ExecutionResult` artifact was created (RFC-0004 §10's event vocabulary) and when a RuntimeState mutation it didn't itself perform has occurred (e.g. a Policy-Engine-driven `Blocked` transition, §12.3), in order to react. RFC-0004 §10 already defined the *artifact*-side event vocabulary and explicitly deferred delivery semantics to "the Event Bus RFC." This RFC's own mutation model (§7.4, §8) is message-proposal-shaped precisely because it anticipates event-driven consumption, but — like RFC-0004 before it — this RFC does not itself specify delivery guarantees, ordering, or subscriber semantics for RuntimeState-mutation-triggered events; it only confirms (§18, throughout) that such events will need to exist.

Designing Scheduler next, with Event Bus still unspecified, would force Scheduler's RFC to either (a) invent its own bespoke event-delivery mechanism — precisely the "no subsystem may invent private exchange formats" problem RFC-0004's founding motivation exists to prevent, now recurring one layer up at the event-delivery layer — or (b) hand-wave delivery semantics and hope Event Bus's eventual design happens to be compatible, risking the same kind of retroactive rework RFC-0004 §17.6 already flagged as a general risk of building in dependency order. Event Bus is now the more tightly-scoped of the two remaining gaps: its job is fully bounded by the event vocabularies RFC-0004 §10 and this RFC's mutation/status-transition model already define — it has two independent, converging specifications to build against, the same argument RFC-0004 §18 used to justify recommending RuntimeState over Event Bus at that point in the sequence, now inverted now that RuntimeState is done.

**Recommended: RFC-0006, Event Bus.** Scheduler should follow as RFC-0007, once it has a defined, reliable way to observe both Artifact and RuntimeState events rather than needing to invent one as a side effect of its own design.
