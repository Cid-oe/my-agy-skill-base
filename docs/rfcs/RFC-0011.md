## 1. Executive Overview

RFC-0011 defines the **Planner** for the AGY AI Operating System. The Planner is the subsystem that transforms a **Goal** — an intention expressed at varying levels of abstraction — into an **Execution Graph** that the Scheduler (RFC-0007) can consume, sequence, and dispatch.

The Planner sits between intent and execution. It receives a Goal that may be vague, ambiguous, or incomplete. It must decompose that Goal into concrete, executable units. It must determine which units depend on which others. It must identify which units can run in parallel. It must estimate the confidence that the plan will succeed, the cost of executing it, and the risk of each decision along the decomposition path. When it is done, it emits an Execution Graph — a directed acyclic graph of Tasks, with edges encoding dependencies, metadata encoding estimates, and annotations encoding the reasoning behind every structural decision.

The Planner is **not** a reasoning engine. It does not invent new capabilities. It does not execute Tasks. It does not make runtime decisions about how Tasks are performed. Its only job is to produce a well-formed, policy-compliant, resource-aware plan that the Scheduler can execute and that a human or an audit system can inspect and understand.

The architectural choices in this RFC are motivated by one overriding principle drawn from the systems engineering tradition: **a plan is a contract**. It is a contract between the Planner and the Scheduler (about what will be executed), between the Planner and the Policy Engine (about what is permitted), between the Planner and the operator (about what was decided and why), and between the current execution and future executions (through Memory). A plan that cannot be audited, cannot be explained, and cannot be reproduced is not a plan. It is a guess.

This RFC selects **Hierarchical Task Networks (HTN)** as the planning model, extended with DAG dependency analysis, cost and confidence estimation, and policy-gated decomposition. The rationale for this choice — and the honest reasons why alternatives were rejected — occupies a full section of this document.

## 2. Responsibilities

The Planner is responsible for the following:

**Goal Ingestion and Normalization**
- Accepting Goals from the kernel's public interface.
- Normalizing Goals into a canonical internal representation regardless of how they were expressed.
- Detecting Goals that are malformed, ambiguous beyond resolution, or policy-prohibited before planning begins.

**Hierarchical Decomposition**
- Decomposing abstract Tasks into progressively more concrete subtasks using an ordered set of Methods retrieved from the Skill Registry (RFC-0002).
- Halting decomposition when all leaf nodes are primitive Tasks that can be directly executed by a skill.
- Recording the decomposition tree as a first-class artifact of the planning process.

**Dependency Detection**
- Analyzing decomposed Tasks for data dependencies (Task A produces an output that Task B requires).
- Analyzing Tasks for resource dependencies (Task A and Task B both require exclusive access to the same resource).
- Analyzing Tasks for ordering constraints declared by Methods.
- Encoding all dependencies as directed edges in the Execution Graph.

**Parallel Work Identification**
- Identifying Tasks with no dependency relationship (neither direct nor transitive) and marking them as eligible for concurrent execution.
- Computing the critical path through the dependency graph.
- Annotating the Execution Graph with parallelism degree at each level.

**Cost and Confidence Estimation**
- Estimating the token cost, latency, and compute resource cost of each Task.
- Estimating the confidence that each Task will succeed given the current context.
- Computing an aggregate plan confidence score and aggregate plan cost estimate.
- Sourcing estimation data from Reflection Memory (RFC-0010) and skill manifests (RFC-0002).

**Prioritization**
- Ordering Tasks on the critical path by priority when resources are constrained.
- Propagating Goal-level priority to Task-level scheduling hints.
- Detecting and resolving priority inversions within the plan.

**Policy Compliance**
- Gating every decomposition step through the Policy Engine (RFC-0003).
- Refusing to include Tasks in the plan that are policy-prohibited for the requesting identity.
- Annotating policy decisions on each Task node for audit.

**Execution Graph Emission**
- Producing a well-formed Execution Graph (defined in this RFC) that conforms to the contract expected by the Scheduler (RFC-0007).
- Attaching the Decomposition Tree, estimation metadata, and policy annotations to the Execution Graph as a planning Artifact (RFC-0004).
- Publishing planning lifecycle events to the Event Bus (RFC-0006).

**Replanning**
- Accepting replanning requests triggered by runtime failures, resource unavailability, or dynamic Goal changes.
- Producing a revised Execution Graph for the unexecuted portion of the original plan.
- Preserving the lineage relationship between the original plan and the revised plan.

## 3. Non-Goals

The following are explicitly outside the scope of RFC-0011:

- **Executing Tasks.** Execution is the Scheduler's responsibility (RFC-0007).
- **Resolving which specific skill instance handles a Task.** Skill resolution is RFC-0001's responsibility. The Planner assigns Task types; the Scheduler invokes the Resolver.
- **Reasoning about the content of Task outputs.** The Planner knows that Task A produces an Artifact that Task B consumes. It does not inspect the content of that Artifact.
- **Managing runtime state during execution.** Runtime State is RFC-0005's domain.
- **Learning new decomposition Methods.** The Planner uses Methods from the Skill Registry. It does not write new Methods.
- **Natural language understanding of Goals.** If Goals arrive as natural language, a Goal Parsing skill runs before the Planner receives the normalized Goal. The Planner operates on structured Goals.
- **Real-time plan monitoring or adaptation.** The Planner produces a plan and may replan on request. It does not monitor running executions.
- **Defining skill capability schemas.** These are defined in RFC-0002.

## 4. Relationship to Previous RFCs

### RFC-0001: Skill Resolver

The Planner does not invoke the Skill Resolver directly. However, the Planner assigns `skill_type` annotations to every leaf Task node in the Execution Graph. When the Scheduler dispatches a Task, it invokes RFC-0001 to resolve the specific skill instance for that `skill_type`. The Planner must only assign `skill_type` values that are registered in the Skill Registry (RFC-0002) and permitted by the Policy Engine (RFC-0003) for the requesting identity.

**Interaction:** One-way dependency. Planner reads skill manifests from RFC-0002 to determine what skill types are available. RFC-0001 is invoked by the Scheduler, not the Planner.

### RFC-0002: Skill Registry & Loader

The Planner's decomposition engine depends critically on RFC-0002. Methods — the decomposition rules that transform abstract Tasks into subtask sets — are stored in the Skill Registry as part of skill manifests. The Planner queries the Registry to find applicable Methods for each abstract Task during decomposition.

**Interaction:** The Planner queries RFC-0002 for:
- Methods applicable to a given abstract Task type.
- The input/output schema of each skill type (for dependency detection).
- The resource requirements of each skill type (for cost estimation and parallelism constraints).
- The `memory_profile` of each skill type (for memory-aware planning).

The Planner caches Method lookups per planning session to avoid repeated Registry calls. Cache invalidation is event-driven via RFC-0006 (skill registered/updated events).

**Hidden coupling risk:** If RFC-0002 allows Methods to be updated while a plan is being constructed, the Planner may decompose the first half of a plan using Method version 1 and the second half using Method version 2. The Planner pins the Method version at the start of each planning session and rejects Method updates mid-session.

### RFC-0003: Policy Engine

Every decomposition step is policy-gated. Before the Planner applies a Method to decompose a Task, it asks the Policy Engine whether the requesting identity is permitted to execute the resulting subtask types. If any subtask is denied, the Method is rejected and the next applicable Method is tried. If all Methods for a Task are denied, planning fails with a `POLICY_BLOCKED_DECOMPOSITION` error.

**Interaction:** The Planner calls RFC-0003 with `PlannerPolicyRequest` objects containing:
- `requester_identity` (from RFC-0005 Runtime State).
- `task_type` being evaluated.
- `method_id` being applied.
- `context_tags` from the Goal.

Policy decisions are cached per `(requester_identity, task_type, method_id)` for the duration of the planning session. Cross-session caching is permitted with a TTL but must be invalidated on policy change events.

**Critical integration note:** RFC-0003 must support a `PLAN_TIME` evaluation context, distinct from `RUNTIME` evaluation. Plan-time policy decisions are speculative (the Task has not yet executed) and may be more permissive than runtime decisions. The Policy Engine must not conflate plan-time and runtime contexts. This distinction must be registered in RFC-0003's policy attribute namespace.

### RFC-0004: Artifact System

The Planner produces two types of Artifacts:

1. **Plan Artifact:** The complete planning record — Decomposition Tree, Execution Graph, estimation data, policy annotations, and planning metadata — is materialized as an Artifact. This gives it content addressing, versioning, and lineage for free. The Plan Artifact's ID is attached to the Execution Graph as its canonical reference.

2. **Data dependency edges:** When the Planner detects that Task A will produce an Artifact consumed by Task B, it encodes this as a typed dependency edge in the Execution Graph. The Artifact is not yet created (it will be created during execution), but its expected type and schema are encoded at plan time.

**Interaction:** Planner writes Plan Artifacts to RFC-0004 at plan completion. Planner reads Artifact schemas from RFC-0004 (or from RFC-0002 skill manifests that reference RFC-0004 types) to validate data dependency compatibility.

### RFC-0005: Runtime State

The Planner reads Runtime State to determine the execution context in which planning is occurring: the requesting identity, the current session, the current project, and any active resource reservations that constrain the plan.

**Interaction:** Read-only access to RFC-0005. The Planner does not write to Runtime State. Runtime State does not call the Planner.

### RFC-0006: Event Bus

The Planner publishes events to the Event Bus at key planning lifecycle points and subscribes to events that may trigger replanning.

**As publisher:**
- `planner.goal.received`
- `planner.plan.started`
- `planner.plan.completed`
- `planner.plan.failed`
- `planner.replanning.triggered`
- `planner.replanning.completed`

**As subscriber:**
- `scheduler.task.failed` — may trigger replanning.
- `scheduler.resource.unavailable` — may trigger replanning.
- `skill.registry.updated` — invalidates Method cache.
- `policy.updated` — invalidates policy decision cache.
- `memory.consolidated` — may improve estimation quality for in-progress plans (non-blocking; informational only).

### RFC-0007: Scheduler

The Scheduler is the Planner's primary consumer. The Execution Graph produced by the Planner is the input contract for the Scheduler. These two subsystems are tightly coupled through the Execution Graph schema, which must be agreed upon by both.

**Interaction:** The Planner emits an Execution Graph conforming to the schema defined in this RFC. The Scheduler consumes it. Neither subsystem may unilaterally change the Execution Graph schema without a joint RFC amendment. This is the most critical interface in the AGY kernel.

**Scheduling hints produced by the Planner and consumed by the Scheduler:**
- Task priority scores.
- Critical path flags.
- Parallelism degree annotations.
- Estimated duration per Task.
- Estimated token cost per Task.
- Resource requirements per Task.

The Scheduler is free to ignore hints (under resource pressure), but it must preserve dependency edges. Dependency edges are constraints; hints are preferences.

### RFC-0010: Memory System

The Planner is a significant consumer of the Memory System. It uses three memory tiers:

1. **Semantic Memory:** Retrieved before decomposition to surface relevant prior knowledge (e.g., known constraints, known domain facts) that can inform Method selection.

2. **Reflection Memory:** Retrieved before and during estimation to source historical performance data (e.g., "This skill type has historically taken 3× its estimated duration for goals in this domain").

3. **Working Memory:** Written during planning to store intermediate decomposition state. If the planning process is interrupted, it can resume from Working Memory rather than starting over.

4. **Project Memory:** Read to understand project-level constraints, prior decisions, and accumulated context that must be respected by the new plan.

**Interaction:** The Planner queries RFC-0010 with `MemoryQuery` operations using retrieval strategies appropriate to each tier. Memory retrieval is bounded by a configurable token budget to prevent planning from consuming the entire context window before execution begins.

## 5. Planning Model Selection

This section documents the evaluation of five planning models, the selection rationale, and the honest weaknesses of the chosen model.

### 5.1 Candidates Evaluated

#### 5.1.1 Hierarchical Task Networks (HTN)

HTN planning decomposes abstract tasks into progressively more concrete subtasks using a library of Methods. A Method specifies: the abstract task it applies to, the preconditions that must hold for the method to be applicable, and the ordered or partially-ordered set of subtasks it decomposes the abstract task into. Planning terminates when all tasks are primitive (directly executable). HTN is sound: if a plan is produced, it is guaranteed to conform to the decomposition hierarchy. It is complete relative to the Method library: if no plan exists given available methods, it reports failure rather than producing an invalid plan.

**Strengths:**
- Naturally hierarchical: matches the layered abstraction of AGY skills.
- Produces a decomposition tree that is inherently auditable.
- Plan failure is explicit and attributable to missing or blocked Methods.
- Well-studied, deterministic, and predictable.
- Efficient for structured domains where the task hierarchy is known.

**Weaknesses:**
- The Method library must be manually defined; HTN cannot discover new decomposition strategies.
- Sensitive to Method ordering (the first applicable Method is tried; backtracking is required if it fails).
- Does not natively optimize across alternative decompositions; requires explicit cost comparison.
- Poorly suited for open-world domains where the set of applicable actions is not fully enumerable.

#### 5.1.2 Goal-Oriented Action Planning (GOAP)

GOAP operates by defining the current world state and the desired goal state, then searching for a sequence of actions that transforms the current state into the goal state. Actions have preconditions (state conditions that must be true before the action can execute) and effects (state mutations the action produces). Planning is a forward or backward search through the state space.

**Strengths:**
- Flexible: new actions can be added without modifying a decomposition hierarchy.
- Naturally produces optimal (lowest-cost) plans relative to a cost function.
- Well-suited for domains where the goal state is clearly defined in terms of measurable world state changes.

**Weaknesses:**
- Requires a well-defined, enumerable world state. In AGY, the "world state" includes AI model outputs, user intent, and external system states — none of which are reliably enumerable at planning time.
- Search is exponential in the worst case. Heuristics are required but are domain-specific and hard to generalize.
- Plan quality is sensitive to state representation completeness; incomplete state models produce incorrect plans without explicit failure signals.
- Not naturally hierarchical; producing human-readable hierarchical plans requires additional post-processing.
- The state-space explosion problem is severe at the scale of thousands of skills and complex goals.

**Decision: Rejected.** GOAP's requirement for enumerable world state is incompatible with AGY's open-world, AI-driven execution model. The search complexity at scale is unacceptable.

#### 5.1.3 Task Graph / Workflow DAG

A Task Graph approach defines a plan as a static DAG of tasks with explicit dependency edges. Planning is graph construction: the planner interprets the goal and constructs a DAG where nodes are tasks and edges are dependencies. There is no hierarchical decomposition; the planner operates at a single level of abstraction.

**Strengths:**
- Simple. DAGs are well-understood, easy to implement, and easy to audit.
- Efficient: no search required, no backtracking.
- Directly compatible with modern workflow engines (Airflow, Argo, Temporal).
- Parallelism is explicit in the graph structure.

**Weaknesses:**
- Requires the goal to be expressible as a task graph at input time, or requires a separate decomposition layer before graph construction. This pushes complexity upstream.
- Cannot handle abstract goals without a prior decomposition phase. Effectively, if you add a decomposition phase to Task Graph planning, you have built a limited HTN without the formalism.
- No natural handling of alternative methods; if a task cannot be executed by any available skill, there is no fallback mechanism.
- Brittle: the plan is a static structure; replanning requires rebuilding the graph from scratch.

**Decision: Rejected as a standalone model.** Task Graph / Workflow DAG is adopted as the **output representation** of the Planner (the Execution Graph is a DAG), but not as the planning model. The planning model must handle abstract goals and hierarchical decomposition before emitting the DAG.

#### 5.1.4 Tree Search (e.g., MCTS, A\*, Beam Search)

Tree search approaches explore a search tree of possible plans, evaluating nodes by a heuristic or learned value function, and selecting the best-scoring complete plan. Monte Carlo Tree Search (MCTS) explores stochastically; A\* explores using a deterministic heuristic; Beam Search explores the top-k branches at each level.

**Strengths:**
- Can discover non-obvious plans that a human-authored Method library would not include.
- Naturally produces cost-optimal plans when search is complete.
- Flexible: any action space can be searched given a value function.

**Weaknesses:**
- Requires a reliable value function or heuristic. In AGY, the value function would need to estimate plan quality for AI skill executions — a highly uncertain and potentially circular problem (using AI to evaluate plans for AI).
- Non-deterministic in practice: stochastic search (MCTS) produces different plans on different runs for the same goal. This violates AGY's determinism requirement.
- Computationally expensive. At planning time, latency is a first-class concern. Tree search latency is unbounded without arbitrary depth/breadth limits.
- Explainability: a plan produced by tree search over thousands of nodes is not self-explanatory. Audit requires tracing the search path, which is complex and verbose.

**Decision: Rejected as primary model.** Non-determinism and latency are disqualifying. Elements of tree search (specifically, limited lookahead for method selection) are incorporated as an optional extension in the HTN implementation.

#### 5.1.5 Hierarchical Task Networks (Selected)

**Decision: Selected.**

HTN is selected as the planning model for the following reasons, stated precisely:

1. **Determinism.** Given the same Goal, the same Method library version, and the same world state, HTN produces the same plan. This is a hard requirement for AGY's audit and reproducibility model.

2. **Hierarchical auditability.** The decomposition tree is a first-class product of HTN planning. Every planning decision is traceable to a specific Method application. Operators can read the plan as a hierarchy and understand why each step is present.

3. **Natural alignment with AGY's skill abstraction.** AGY skills are already hierarchical: some skills are abstract coordinators, others are concrete executors. HTN's abstract task / primitive task distinction maps directly onto this architecture.

4. **Explicit failure attribution.** When HTN planning fails, it fails because no applicable Method exists for a specific abstract task under the current constraints. The failure is attributable and actionable: add a Method, add a skill, relax a constraint.

5. **Controlled extensibility.** New capabilities are added by adding new Methods to the Skill Registry. The Planner itself does not change. This is the correct extensibility model for a kernel subsystem.

6. **Tractable at scale.** HTN planning is polynomial in the size of the Method library for non-recursive task hierarchies, which is the common case in AGY. Exponential cases (deep recursion, large Method libraries with many alternatives) are bounded by configurable depth limits and Method selection caching.

**HTN weaknesses acknowledged and mitigated:**

- **Method library completeness:** The Planner can only produce plans that the Method library supports. Mitigation: the Method library is extensible through RFC-0002; the Planner provides explicit failure signals when no Method is found, enabling operators to identify gaps.
- **Backtracking cost:** Failed Method applications require backtracking. Mitigation: Methods are ordered by a priority score in the Registry; the highest-priority applicable Method is tried first, reducing average backtrack depth. A configurable backtrack limit prevents pathological cases.
- **No global optimization:** HTN produces the first valid plan, not the optimal plan. Mitigation: cost estimation is applied after decomposition to evaluate and compare alternative complete plans when multiple decompositions are possible. The Planner can be configured to enumerate up to N alternative plans and select the lowest-cost one.

### 6.2 World State Model

HTN requires a world state: a representation of what is currently true in the environment. In AGY, the world state is not a complete enumeration of all facts (that would be GOAP). Instead, it is a **scoped, partial world state** composed of:

1. **Declared facts:** Key-value assertions provided with the Goal or loaded from Semantic and Project Memory (RFC-0010).
2. **Resource availability:** Which resources, models, and skill types are currently available (from Runtime State RFC-0005 and Scheduler RFC-0007).
3. **Artifact availability:** Which Artifacts exist and are accessible to the requesting identity.
4. **Active constraints:** Policy-derived constraints (RFC-0003) that limit which Methods are applicable.

The world state is **open**: facts not present in the world state are treated as unknown, not false. Precondition evaluation treats unknown facts as conditionally satisfiable (the precondition may be satisfiable at runtime even if it cannot be verified at plan time). This is the **open-world assumption** and is a deliberate departure from classical HTN, which typically operates under the closed-world assumption.

**Why open-world?** AGY operates in environments where the full state of the world cannot be enumerated at planning time. A skill may produce an output whose exact value cannot be predicted before execution. Treating unknown facts as false (closed-world) would cause the Planner to reject valid plans because it cannot prove every precondition at plan time. The open-world assumption allows planning to proceed with runtime validation as the safety net.

**Risk:** The open-world assumption means the Planner may produce plans that fail at runtime because an assumed-satisfiable precondition turns out to be false. This is handled by the Replanning mechanism and is reflected in the plan's confidence score (preconditions that cannot be verified at plan time reduce the Task's confidence score).

### 6.3 Decomposition Tree vs. Execution Graph

These are two distinct data structures produced by the Planner:

**Decomposition Tree:** A tree (not a DAG) where each node is a Task (abstract or primitive), each edge is a Method application, and each leaf is a primitive Task. The tree records the hierarchical reasoning behind the plan. It is the audit record.

**Execution Graph:** A DAG where nodes are primitive Tasks and edges are dependencies. The Execution Graph is derived from the Decomposition Tree's leaves plus the Dependency Detector's analysis. The Execution Graph is the operational record — what the Scheduler executes.

The Decomposition Tree is never discarded. Both structures are materialized in the Plan Artifact.

## 7. Internal Components

### 7.1 Goal Normalizer

The Goal Normalizer transforms the input Goal into a canonical `NormalizedGoal` structure. It:

- Validates that required fields are present.
- Resolves references (e.g., Artifact IDs referenced by the Goal are validated as existing and accessible).
- Extracts structured intent parameters from semi-structured Goal descriptions.
- Assigns a canonical `goal_type` by matching the Goal against a type registry (stored in Semantic Memory or Skill Registry).
- Detects immediately unsatisfiable Goals (e.g., Goal requires a skill type that does not exist in the Registry).

The Goal Normalizer does **not** perform natural language understanding. If the Goal was expressed as natural language, it must have been parsed by a Goal Parsing skill before reaching the Planner.

### 7.2 Policy Gate

The Policy Gate is a thin wrapper around RFC-0003 calls. It is stateful within a planning session: it maintains the policy decision cache for the session and manages cache invalidation. It provides two operations to the Decomposition Engine:

- `evaluate_method(identity, task_type, method_id) → PERMIT | DENY | CONDITIONAL`
- `evaluate_task(identity, task_type) → PERMIT | DENY | CONDITIONAL`

`CONDITIONAL` decisions are permitted at plan time: a Task may be included in the plan with a runtime policy check annotation, meaning the Scheduler must re-evaluate policy before executing the Task. This handles cases where plan-time policy is permissive but runtime context may change the decision.

### 7.3 Memory Context Loader

Before decomposition begins, the Memory Context Loader queries RFC-0010 to retrieve relevant context:

1. **Semantic Memory query:** Retrieve facts relevant to the Goal's domain tags. Used to populate the World State Model with declared facts.
2. **Reflection Memory query:** Retrieve historical performance observations for skill types likely to appear in the plan. Used to prime the Cost and Confidence Estimator.
3. **Project Memory query:** Retrieve project constraints and prior decisions relevant to this Goal.

Retrieval is bounded by a configurable `planning_memory_budget` (token count). If the budget is insufficient to load all relevant memory, the Loader prioritizes by: Project Memory first (hardest constraints), Reflection Memory second (most directly affects estimation quality), Semantic Memory third (background knowledge).

### 7.4 HTN Decomposition Engine

This is the core planning component. It implements the HTN planning algorithm as follows:

**Inputs:**
- `NormalizedGoal` containing the root abstract Task.
- World State Model.
- Method Library (retrieved from RFC-0002 Skill Registry, pinned to current version).

**Outputs:**
- Decomposition Tree.
- Ordered list of primitive Tasks (the leaves of the Decomposition Tree).

**Algorithm:** See Section 11.1.

**Internal sub-components:**

**Task Stack:** A stack of tasks yet to be decomposed. Initialized with the root abstract task from the Goal. As methods are applied, abstract tasks are replaced by their subtasks. Planning completes when the stack is empty (all tasks are primitive) or fails when an abstract task has no applicable method.

**Method Selector:** Given an abstract task, retrieves all applicable Methods from the Method Library (those whose task type matches and whose preconditions are satisfiable in the current World State), orders them by priority score, and returns them as a candidate list. The Decomposition Engine tries Methods in priority order, backtracking on failure.

**Precondition Evaluator:** Evaluates a Method's preconditions against the World State Model. Returns: SATISFIED (fact is true in world state), UNSATISFIED (fact is false in world state), or UNKNOWN (fact is not in world state — open-world; proceed with runtime check annotation).

**Backtrack Manager:** Maintains a backtrack stack. When a Method application fails (no further decomposition is possible downstream), the Backtrack Manager restores the world state to the pre-application snapshot and tries the next candidate Method. Backtracking is depth-limited by `max_backtrack_depth` (configurable, default: 20).

### 7.5 Dependency Detector

The Dependency Detector analyzes the ordered list of primitive Tasks produced by the Decomposition Engine and identifies dependency relationships.

**Dependency types:**

1. **Data dependency:** Task B declares an input of type T. Task A declares an output of type T. If they share a compatible schema and Task A appears before Task B in execution order, a data dependency edge is added: A → B.

2. **Resource dependency:** Task A and Task B both require exclusive access to the same named resource (model endpoint, external API, database). A resource dependency edge serializes them: A → B (first in decomposition order goes first).

3. **Ordering constraint:** A Method explicitly declares that its subtasks must execute in a specific order. These become mandatory ordering edges.

4. **Implicit world-state dependency:** Task B has a precondition that is UNKNOWN in the current world state but is an effect of Task A. An ordering edge is added: A → B.

**Independent Tasks:** Tasks with no dependency relationship (direct or transitive) are marked as `parallel_eligible`.

### 7.6 Parallelism Analyzer

The Parallelism Analyzer processes the dependency graph produced by the Dependency Detector and computes:

- **Parallelism degree at each level:** How many tasks can execute concurrently at each "wave" of the DAG (tasks with no unresolved dependencies).
- **Estimated maximum concurrency:** The maximum number of tasks that could execute simultaneously across the entire plan.
- **Resource-constrained parallelism:** Actual achievable concurrency given resource limits declared in the World State.

The Parallelism Analyzer annotates each Task node with a `parallel_group_id` — tasks that can execute concurrently share a parallel group ID. The Scheduler uses this to drive concurrent dispatch.

### 7.7 Critical Path Finder

The Critical Path Finder applies the standard Critical Path Method (CPM) algorithm to the Execution Graph, using estimated Task durations (from the Cost and Confidence Estimator) as edge weights. It produces:

- The **critical path**: the sequence of Tasks whose total estimated duration determines the minimum possible plan completion time.
- A **critical path flag** on each Task node: true if the Task is on the critical path.
- The **estimated minimum plan duration**: the sum of estimated durations along the critical path.

The Scheduler uses critical path flags to prioritize dispatching: critical path Tasks are dispatched before non-critical Tasks at each scheduling cycle.

### 7.8 Cost and Confidence Estimator

This component assigns quantitative estimates to each Task and to the plan as a whole.

**Per-Task estimates:**

- `estimated_token_cost`: Sourced from skill manifest (declared token budget) adjusted by Reflection Memory (actual historical token usage for this skill type in similar contexts).
- `estimated_latency_ms`: Sourced from skill manifest (declared execution time estimate) adjusted by Reflection Memory.
- `estimated_compute_cost`: Sourced from skill manifest (resource tier) plus Reflection Memory adjustments.
- `confidence`: Composite score (see Section 11.3).

**Plan-level estimates:**

- `total_estimated_token_cost`: Sum of all Task token cost estimates.
- `estimated_wall_clock_duration`: CPM critical path duration (with parallelism accounted for).
- `plan_confidence`: Minimum Task confidence along the critical path (chain confidence model).
- `plan_risk_score`: Derived from the distribution of confidence scores (high variance → high risk).

**Estimation data sources (in priority order):**
1. Reflection Memory: actual historical performance for this skill type and Goal domain.
2. Skill manifest declared estimates: developer-provided baseline.
3. Tier-based defaults: coarse defaults by skill type category if no specific data is available.

### 7.9 Execution Graph Builder

The Execution Graph Builder assembles the final Execution Graph from the outputs of all preceding components:

- Nodes: primitive Tasks with full metadata (skill_type, estimated costs, confidence, critical path flag, parallel group, policy annotations).
- Edges: dependency edges (typed: DATA | RESOURCE | ORDERING | WORLD_STATE).
- Graph metadata: plan ID, plan version, goal reference, plan Artifact reference, aggregate estimates.

It validates the graph before emission:
- No cycles (DAG validation).
- All dependency edge source and target nodes exist.
- All skill types referenced in Task nodes are registered in RFC-0002.
- Aggregate confidence is above the configurable minimum plan confidence threshold.

If aggregate confidence is below threshold, the Planner may: (a) emit the plan with a `LOW_CONFIDENCE` warning, (b) reject the plan and return a `PLANNING_FAILED` result, or (c) attempt an alternative decomposition. Behavior is configurable per policy.

### 7.10 Plan Artifact Materializer

At plan completion, the Plan Artifact Materializer writes the complete planning record to RFC-0004:

**Plan Artifact contents:**
- `NormalizedGoal`
- `DecompositionTree`
- `ExecutionGraph`
- `WorldStateSnapshot` (the World State Model at planning time)
- `MethodApplicationLog` (ordered list of Methods applied during decomposition)
- `PolicyDecisionLog` (all Policy Gate decisions made during planning)
- `EstimationReport` (all per-Task estimates with sourcing annotations)
- `PlanningMetadata` (planner version, Method library version, duration, backtrack count)

The Plan Artifact is immutable once written. It is the complete, reproducible record of how the plan was constructed. Future replanning operations reference the original Plan Artifact as their provenance parent.

## 10. Runtime Lifecycle

### 10.1 Planning Session Lifecycle

```
1. Plan() received.
2. Goal Normalizer validates and normalizes the Goal.
3. Policy Gate evaluates top-level Goal permissibility.
4. Memory Context Loader retrieves planning context from RFC-0010.
5. World State Model initialized from: Runtime State + Memory Context + Goal constraints.
6. Method Library pinned (current version snapshot from RFC-0002).
7. HTN Decomposition Engine begins planning.
   7a. For each abstract task: Method Selector finds candidates.
   7b. Policy Gate evaluates each candidate method.
   7c. Precondition Evaluator assesses each precondition.
   7d. Method applied; world state updated with effects.
   7e. Subtasks pushed to Task Stack.
   7f. Repeat until Task Stack empty or failure.
8. Decomposition Tree finalized.
9. Dependency Detector analyzes primitive task list.
10. Parallelism Analyzer computes parallel groups.
11. Critical Path Finder computes critical path.
12. Cost and Confidence Estimator assigns estimates.
13. Execution Graph Builder assembles and validates the graph.
14. Plan Artifact Materializer writes Plan Artifact to RFC-0004.
15. planner.plan.completed event published to RFC-0006.
16. ExecutionGraph returned to caller.
17. Caller (typically the kernel's execution orchestrator) submits
    ExecutionGraph to RFC-0007 Scheduler.
```

### 10.2 Replanning Lifecycle

```
1. Replan() received (triggered by RFC-0006 scheduler failure event or explicit call).
2. Original Plan Artifact loaded from RFC-0004.
3. Completed tasks and produced Artifacts noted.
4. Replan strategy selected: PATCH or FULL_REPLAN.
   PATCH: only re-decompose the failed subgraph; retain completed tasks.
   FULL_REPLAN: re-plan from scratch with updated Goal and World State.
5. Updated World State constructed from:
   - Original World State snapshot (from Plan Artifact).
   - Effects of completed tasks.
   - Produced Artifacts.
   - Failure context from replan_trigger.
6. HTN Decomposition Engine runs on remaining tasks (PATCH) or
   full Goal (FULL_REPLAN).
7. New Execution Graph constructed.
8. New Plan Artifact written with parent_plan_id = original_plan_id.
9. planner.replanning.completed event published.
10. New ExecutionGraph returned.
```

### 10.3 Estimation Lifecycle (EstimatePlan)

EstimatePlan runs a partial planning session: it decomposes one or two levels of the hierarchy (not to full primitive depth), applies cost class estimates from Methods, and returns a range estimate. It does not produce an Execution Graph or Plan Artifact. It is fast (target: < 200ms for most Goals).

## 11. Algorithms

### 11.1 HTN Decomposition Algorithm

```
PROCEDURE decompose(goal: NormalizedGoal, world_state: WorldState,
                    method_library: MethodLibrary) → DecompositionTree | FAILURE:

  tree = DecompositionTree(root = Task(goal.root_task_type))
  task_stack = Stack([tree.root])
  backtrack_stack = Stack([])
  backtrack_count = 0

  WHILE task_stack is not empty:

    current_task = task_stack.pop()

    IF current_task.is_primitive:
      CONTINUE  // leaf node; no further decomposition needed

    candidates = method_library.get_applicable_methods(
      task_type = current_task.task_type,
      world_state = world_state
    )
    candidates = policy_gate.filter_permitted(candidates, requester_identity)
    candidates = sort_by_priority_descending(candidates)

    method_applied = false

    FOR EACH method IN candidates:
      precondition_result = evaluate_preconditions(method.preconditions, world_state)

      IF precondition_result == UNSATISFIED:
        log(method, FAILED_BACKTRACKED, "precondition unsatisfied")
        CONTINUE

      // Save backtrack point
      backtrack_point = BacktrackPoint(
        task_stack_state = task_stack.snapshot(),
        world_state_snapshot = world_state.snapshot(),
        tree_snapshot = tree.snapshot()
      )
      backtrack_stack.push(backtrack_point)

      // Apply method: generate subtasks
      subtasks = instantiate_subtasks(method, current_task.parameters, world_state)
      apply_effects_to_world_state(method.effects, world_state)

      // Add subtasks to tree and stack
      FOR EACH subtask IN reverse_order(subtasks):  // reverse for correct stack order
        tree.add_child(parent=current_task, child=subtask, method=method)
        task_stack.push(subtask)

      log(method, SUCCEEDED)
      method_applied = true
      BREAK

    IF NOT method_applied:
      // No applicable method: backtrack
      IF backtrack_stack is empty OR backtrack_count >= max_backtrack_depth:
        RETURN FAILURE(
          reason = NO_METHOD_FOUND,
          task_type = current_task.task_type,
          decomposition_path = tree.path_to(current_task)
        )
      backtrack_point = backtrack_stack.pop()
      task_stack.restore(backtrack_point.task_stack_state)
      world_state.restore(backtrack_point.world_state_snapshot)
      tree.restore(backtrack_point.tree_snapshot)
      backtrack_count++

  RETURN tree
```

### 11.2 Dependency Detection Algorithm

```
PROCEDURE detect_dependencies(primitive_tasks: [Task]) → [DependencyEdge]:

  edges = []
  produced_artifacts = {}  // map: artifact_type → task_id

  FOR EACH task IN primitive_tasks (in decomposition order):
    // Data dependencies
    FOR EACH input_type IN task.declared_inputs:
      IF input_type IN produced_artifacts:
        producer_task_id = produced_artifacts[input_type]
        edges.append(DataEdge(source=producer_task_id, target=task.id,
                              data_type=input_type))

    // Record outputs
    FOR EACH output_type IN task.declared_outputs:
      IF output_type IN produced_artifacts:
        // Conflict: two tasks produce same type
        // Resolved by: last writer (decomposition order)
        // Risk: may produce incorrect plans; see Compatibility Notes
      produced_artifacts[output_type] = task.id

    // Resource dependencies
    FOR EACH resource IN task.declared_exclusive_resources:
      last_user = find_last_task_using_resource(resource, preceding_tasks)
      IF last_user is not null:
        edges.append(ResourceEdge(source=last_user, target=task.id,
                                  resource_id=resource))

    // World-state dependencies
    FOR EACH precondition IN task.preconditions WHERE runtime_check_required:
      effect_producer = find_task_producing_effect(precondition.fact_key,
                                                   preceding_tasks)
      IF effect_producer is not null:
        edges.append(WorldStateEdge(source=effect_producer, target=task.id))

  RETURN deduplicate(edges)
```

### 11.3 Confidence Estimation Algorithm

```
PROCEDURE estimate_confidence(task: Task, world_state: WorldState,
                              reflection_memory: ReflectionData) → float, [ConfidenceFactor]:

  base_confidence = 1.0
  factors = []

  // Factor 1: Unknown preconditions
  unknown_count = count(task.preconditions WHERE evaluation_result == UNKNOWN)
  IF unknown_count > 0:
    reduction = 0.1 × unknown_count  // 10% per unknown precondition
    base_confidence -= min(reduction, 0.3)  // cap at 30% reduction
    factors.append(ConfidenceFactor(PRECONDITION_UNKNOWN, -reduction))

  // Factor 2: Historical failure rate from Reflection Memory
  historical = reflection_memory.get_skill_reliability(task.skill_type,
                                                        world_state.domain_tags)
  IF historical is not null:
    reliability = historical.success_count / historical.total_count
    reduction = (1.0 - reliability) × 0.5  // historical failure weighted at 50%
    base_confidence -= reduction
    factors.append(ConfidenceFactor(HISTORICAL_FAILURE_RATE, -reduction))
  ELSE:
    // Sparse data penalty
    base_confidence -= 0.05
    factors.append(ConfidenceFactor(ESTIMATION_DATA_SPARSE, -0.05))

  // Factor 3: Conditional policy annotations
  conditional_count = count(task.policy_annotations WHERE decision == CONDITIONAL)
  IF conditional_count > 0:
    reduction = 0.05 × conditional_count
    base_confidence -= reduction
    factors.append(ConfidenceFactor(POLICY_CONDITIONAL, -reduction))

  // Factor 4: Resource availability
  FOR EACH resource IN task.declared_resources:
    availability = world_state.get_resource_availability(resource)
    IF availability < 1.0:
      reduction = (1.0 - availability) × 0.2
      base_confidence -= reduction
      factors.append(ConfidenceFactor(RESOURCE_AVAILABILITY, -reduction))

  RETURN max(base_confidence, 0.0), factors

PROCEDURE estimate_plan_confidence(execution_graph: ExecutionGraph) → float:
  // Chain model: plan confidence = product of critical path task confidences
  critical_path_tasks = execution_graph.get_critical_path_tasks()
  plan_confidence = product(task.confidence FOR task IN critical_path_tasks)
  RETURN plan_confidence
```

### 11.4 Alternative Plan Selection Algorithm

When `max_alternative_plans > 1` is configured:

```
PROCEDURE select_best_plan(alternative_plans: [ExecutionGraph],
                           selection_weights: SelectionWeights) → ExecutionGraph:

  FOR EACH plan IN alternative_plans:
    plan.selection_score =
      (selection_weights.confidence × plan.aggregate_confidence) +
      (selection_weights.cost      × (1.0 / normalized_token_cost(plan))) +
      (selection_weights.speed     × (1.0 / normalized_duration(plan))) +
      (selection_weights.simplicity × (1.0 / normalized_node_count(plan)))

  RETURN max_by(alternative_plans, key=selection_score)
```

Default weights: confidence=0.4, cost=0.3, speed=0.2, simplicity=0.1.

## 12. Failure Recovery

### 12.1 Planning Failure Types and Responses

| Failure | Response |
|---|---|
| Goal normalization failure | Return GOAL_INVALID immediately; no planning attempt. |
| No method found for abstract task | Backtrack; try next method; if backtrack limit reached, return NO_METHOD_FOUND with decomposition path. |
| All methods for a task are policy-denied | Return POLICY_BLOCKED_DECOMPOSITION with task type and policy trace. |
| Depth limit exceeded | Return DEPTH_LIMIT_EXCEEDED; caller may retry with increased limit or simplified goal. |
| Confidence below threshold | Return LOW_CONFIDENCE plan (caller chooses to proceed or abort). |
| Memory context load failure | Continue planning without memory context; annotate plan with MEMORY_CONTEXT_UNAVAILABLE warning. |
| Plan Artifact write failure (RFC-0004) | Return plan to caller with ARTIFACT_WRITE_FAILED warning; plan is valid but not persisted. Caller may retry artifact write separately. |
| Policy Engine unavailable | Fail-closed: return POLICY_ENGINE_UNAVAILABLE; no plan produced. |

### 12.2 Replan Strategy Selection

```
IF trigger.type == TASK_FAILED:
  IF failed_task.is_on_critical_path:
    strategy = FULL_REPLAN  // Critical path failure; plan structure invalid
  ELSE:
    strategy = PATCH  // Non-critical task; re-plan only the failed subgraph

IF trigger.type == RESOURCE_UNAVAILABLE:
  strategy = PATCH  // Remove resource-dependent tasks; find alternatives

IF trigger.type == GOAL_CHANGED:
  strategy = FULL_REPLAN  // Goal change requires full re-decomposition

IF trigger.type == POLICY_CHANGED:
  strategy = PATCH IF affected_tasks are non-critical ELSE FULL_REPLAN
```

### 12.3 Planning Session Interruption Recovery

The Decomposition Engine writes its intermediate state (Task Stack, World State, partial Decomposition Tree) to Working Memory (RFC-0010) at configurable checkpoints (default: every 5 Method applications). If the planning session is interrupted, the next planning attempt for the same Goal ID may resume from the checkpoint rather than starting over.

Checkpoint recovery is attempted only if:
- The same Goal ID is presented.
- The Method Library version matches the checkpoint's pinned version.
- The checkpoint is younger than a configurable staleness threshold (default: 5 minutes).

## 13. Security Considerations

### 13.1 Threat Model

**Threats specific to the Planner:**

1. **Method injection:** A malicious or compromised skill registers a Method that decomposes a benign abstract task into a harmful sequence of primitive tasks.
2. **Goal crafting attacks:** A caller crafts a Goal that, through normal HTN decomposition, causes the Planner to produce a plan that accesses unauthorized resources.
3. **Backtracking exhaustion:** A caller submits a Goal designed to maximize backtracking, consuming planning resources without producing a plan.
4. **Confidence manipulation:** Reflection Memory entries are poisoned to inflate or deflate confidence estimates, causing the Planner to accept bad plans or reject good ones.
5. **Plan replay attack:** A caller submits an old, valid Plan Artifact to the Scheduler for re-execution in a new context where it would not have been permitted.

### 13.2 Defense Mechanisms

**Method injection:** Methods are registered in RFC-0002 Skill Registry, which is itself policy-governed. Only authorized identities can register Methods. The Policy Gate evaluates each Method application against the requesting identity — a Method registered by a malicious skill cannot be applied to decompose a task if the requesting identity is not permitted to use the resulting task types.

**Goal crafting:** The Policy Gate evaluates task permissibility at every decomposition step, not only at the top level. A Goal that leads to a prohibited task type through multiple levels of decomposition will be caught at the level where the prohibited task type appears. The plan fails; the prohibited task is not included.

**Backtracking exhaustion:** The Planner enforces a strict `max_backtrack_depth` limit. Additionally, planning sessions are time-bounded (configurable `planning_timeout`, default: 30 seconds). Exceeded limits result in immediate planning failure, not indefinite computation.

**Confidence manipulation:** Reflection Memory entries used for estimation are tagged with their source skill identity and subject to the same sensitivity class and access policy as any memory entry. Plans produced with Reflection Memory that has low data quality receive an `ESTIMATION_DATA_SPARSE` confidence penalty rather than blindly trusting the data.

**Plan replay attacks:** Execution Graphs carry the `requester_identity` and `created_at` timestamp of the planning session. The Scheduler must re-evaluate policy at dispatch time (RFC-0003 runtime context). A plan produced for identity A cannot be dispatched by identity B; a plan produced yesterday may be re-evaluated against current policy.

### 13.3 Decomposition Depth Limits

Unbounded decomposition depth enables stack exhaustion and denial-of-service through recursive Method definitions. The Planner enforces `max_depth` strictly. Recursive Methods (where Method M for task type T includes a subtask of type T) are flagged at Method registration time in RFC-0002 and are only permitted if they carry an explicit termination condition that is verified by the Precondition Evaluator.

```
Critical Path Finder:        < 3ms
Cost & Confidence:           < 20ms (with Reflection Memory lookup)
Graph Builder + Validation:  < 5ms
Plan Artifact Write:         < 30ms (RFC-0004)
──────────────────────────────────────────
Total P50 estimate:          ≈ 226ms
```

### 14.3 Method Library Cache

The Method Library is queried heavily during decomposition. Without caching, RFC-0002 calls would dominate planning latency. The Planner maintains a session-scoped Method Library cache pinned at a specific version. This cache is populated lazily (on first access per task type) and survives for the planning session duration only. Cross-session caching is not performed because Method versions may change between sessions.

### 14.4 Backtracking Cost

In the worst case, backtracking degrades the HTN algorithm from linear to exponential in the Method library size. The `max_backtrack_depth` limit is the primary protection. Additionally, the Method Selector's priority ordering means high-quality Methods are tried first, reducing average backtrack depth in practice. Monitoring should track backtrack counts per planning session; persistent high backtrack counts indicate Method library quality problems.

## 15. Scalability Analysis

### 15.1 Scale Targets

- 1,000 concurrent planning sessions.
- 10,000 registered Methods across 1,000 skill types.
- 50 primitive tasks per plan (common case).
- 500 primitive tasks per plan (maximum supported).
- Planning sessions are stateless across nodes; horizontal scaling is straightforward.

### 15.2 Method Library Scale

With 10,000 Methods, the Method Selector must efficiently retrieve applicable Methods for a given task type. A naive linear scan is O(10,000) per task. The Method Library index (keyed by `applies_to_task_type`) reduces this to O(k) where k is the number of Methods for a specific task type (typically < 10).

### 15.3 Parallel Planning

The Planner is stateless between sessions. Multiple planning sessions can execute concurrently on independent nodes. Session state (Task Stack, World State) is confined to the planning session's memory; there are no shared mutable structures between concurrent sessions.

### 15.4 Scalability Risks

**Risk 1: Method Library growth over time.** As the system matures, the number of registered Methods may grow to tens of thousands. Method Selector efficiency depends on a well-indexed Method Library in RFC-0002. If RFC-0002 does not index Methods by task type, Method selection degrades linearly.

**Risk 2: Deep goal hierarchies.** Goals with deep hierarchies (many levels of abstraction) produce large Decomposition Trees. At 500 primitive tasks, the Plan Artifact may be several megabytes. RFC-0004 must handle large Artifacts efficiently.

**Risk 3: Reflection Memory retrieval at scale.** At thousands of executions per day, Reflection Memory accumulates rapidly. Cost and Confidence Estimator queries must be bounded in scope (by skill type and domain tags) to avoid full-tier scans.

## 16. Concurrency Model

### 16.1 Session Isolation

Each planning session is fully isolated. Sessions share no mutable state. The Method Library cache is session-scoped. The policy decision cache is session-scoped. The World State Model is session-scoped.

### 16.2 Concurrent Read Access to Shared Registries

The Planner reads from RFC-0002 (Skill Registry) and RFC-0003 (Policy Engine) concurrently with other subsystems. Both are read-heavy. The Planner pins the Method Library version at session start; subsequent updates to the Registry during the session are not visible to the running session, avoiding mid-session consistency issues.

### 16.3 Artifact Writes at Session End

Plan Artifact writes to RFC-0004 are the only external write operations in the planning lifecycle. They occur once per session at completion. At 1,000 concurrent planning sessions completing at similar times (e.g., at the start of a burst workload), this produces a burst of 1,000 concurrent Artifact writes. RFC-0004 must be dimensioned to handle this.

### 16.4 Replanning Concurrency

It is possible for a replanning request to arrive while the original planning session's Execution Graph is partially executing. The Replan operation must acquire a logical lock on the `plan_id` to prevent the Scheduler from dispatching additional tasks from the original graph while replanning is in progress. This lock is released when the new Execution Graph is emitted. Lock acquisition and release are coordinated through RFC-0006 events.

## 17. Testing Strategy

### 17.1 Unit Tests

- **Goal Normalizer:** Invalid goals, missing fields, ambiguous goal types, unresolvable Artifact references.
- **Method Selector:** Task type matching, precondition evaluation (SATISFIED/UNSATISFIED/UNKNOWN), priority ordering, policy filtering.
- **HTN Decomposition Algorithm:** Simple linear decomposition, branching decomposition, backtracking, depth limit enforcement, recursive method detection.
- **Dependency Detector:** Data dependency detection, resource conflict detection, world-state dependency detection, no-dependency (parallel) detection.
- **Critical Path Finder:** Linear chain (critical path = entire chain), diamond (critical path = one branch), wide parallel (critical path = any one task).
- **Confidence Estimator:** Each confidence factor independently, composite score, plan-level chain confidence.

### 17.2 Integration Tests

- **Policy integration:** Plan with all-PERMIT policy. Plan with mixed PERMIT/DENY policy (denied task forces backtracking). Plan with CONDITIONAL task annotation.
- **Memory integration:** Plan with Reflection Memory data (estimates use historical data). Plan with empty Reflection Memory (sparse data penalty applied). Plan with Project Memory constraints.
- **Artifact integration:** Plan Artifact written correctly. Plan Artifact loaded correctly by GetPlan. Replan references parent plan Artifact.
- **Scheduler integration:** Execution Graph consumed by Scheduler. Scheduling hints (critical path, priority, parallel groups) correctly parsed.

### 17.3 Scenario Tests

- **Simple sequential plan:** Goal decomposes into 3 sequential primitive tasks. Verify Execution Graph has correct ordering edges.
- **Parallel plan:** Goal decomposes into 5 tasks where 3 can execute concurrently. Verify parallel group IDs assigned. Verify critical path identified correctly.
- **Backtracking plan:** First applicable Method for a task is policy-denied. Second Method is permitted. Verify backtracking occurs and plan completes successfully.
- **Failed plan:** Goal requires a task type not in the Skill Registry. Verify NO_METHOD_FOUND error with correct decomposition path.
- **Replanning:** Execute half a plan. Simulate task failure. Trigger replan. Verify PATCH strategy preserves completed tasks. Verify new Execution Graph references original plan.
- **Low-confidence plan:** Goal involves skill types with high historical failure rates. Verify plan confidence is low and LOW_CONFIDENCE warning is included.

### 17.4 Performance Tests

- Measure planning latency for goals of complexity 5, 20, 50, 200 tasks.
- Measure planning throughput (plans/second) at 100, 500, 1000 concurrent sessions.
- Measure backtracking impact: plans with 0, 5, 20 backtracks, verify latency scaling.
- Measure Method Library cache hit rate in steady state.

### 17.5 Adversarial Tests

- Submit a recursively-defined Method that would cause infinite decomposition. Verify depth limit prevents infinite loop.
- Submit a Goal designed to maximize backtracking. Verify backtrack limit and timeout prevent resource exhaustion.
- Submit a Goal as identity A that leads to task types only permitted for identity B. Verify planning fails with POLICY_BLOCKED_DECOMPOSITION.

## 18. Tradeoff Analysis

### 18.1 HTN Open-World vs. Closed-World Assumption

**Decision:** Open-world assumption for unknown preconditions.

**Rejected alternative:** Closed-world assumption (unknown = false).

**Rationale:** In AGY, the world state cannot be fully enumerated at planning time. AI skill outputs are not predictable before execution. Treating unknown facts as false would cause the Planner to reject valid plans.

**Weakness:** Plans may fail at runtime because assumed-satisfiable preconditions turn out false. Mitigation: these cases are reflected in the Task's confidence score and the plan is annotated with `runtime_check_required`, so the Scheduler knows to re-evaluate at dispatch time.

### 18.2 Chain Confidence vs. Product Confidence vs. Minimum Confidence

**Decision:** Chain confidence model: plan confidence = product of critical path task confidences.

**Rejected alternatives:**
- Average confidence: hides the compounding effect of multiple uncertain tasks. A plan with 10 tasks each at 0.9 confidence has an average confidence of 0.9, but a chain confidence of 0.35. The average is dangerously misleading.
- Minimum confidence: too conservative. A plan with 9 tasks at 0.99 confidence and one task at 0.8 confidence would have a minimum confidence of 0.8, not reflecting the strong reliability of the other tasks.

**Weakness:** Product confidence is very sensitive to chain length. A plan with 20 tasks each at 0.95 confidence has a chain confidence of 0.36 — possibly below the rejection threshold even though each individual task is quite reliable. The minimum confidence threshold should be calibrated to plan length, not applied uniformly. This RFC does not implement length-adjusted thresholds; it is a known weakness.

### 18.3 Synchronous Artifact Write vs. Asynchronous

**Decision:** Synchronous Plan Artifact write at planning completion. The caller receives the plan only after the Artifact is written.

**Rejected alternative:** Asynchronous write (return plan immediately; write Artifact in background).

**Rationale:** The Plan Artifact is the canonical record of the plan. If it is not written before the plan is dispatched to the Scheduler, and the Artifact write subsequently fails, there is no audit record of the plan that was actually executed. This is an unacceptable audit gap. Synchronous write adds latency (< 30ms target) but ensures auditability.

**Weakness:** A slow RFC-0004 write path will directly increase planning latency. This is an operational coupling that must be monitored.

### 18.4 Per-Session Method Library Pin vs. Live Method Library

**Decision:** Method Library is pinned (version-locked) at session start.

**Rejected alternative:** Live Method Library (always use current versions).

**Rationale:** Mid-session Method updates could cause the second half of a plan to be decomposed using a different Method version than the first half, producing an internally inconsistent plan with unpredictable behavior.

**Weakness:** If a critical bug fix is deployed to a Method while a planning session is in progress, the session will complete with the buggy Method version. This is acceptable because: (a) planning sessions are short (seconds to tens of seconds), (b) the bugfix will be used for all subsequent sessions, (c) the Plan Artifact records the pinned version, enabling post-hoc identification of affected plans.

### 18.5 PATCH Replan vs. FULL_REPLAN as Default

**Decision:** PATCH replan for non-critical-path failures; FULL_REPLAN for critical path failures.

**Rejected alternative:** Always FULL_REPLAN.

**Rationale:** FULL_REPLAN discards all partial results and recomputes from scratch. For large plans where significant work has been completed, this is wasteful and introduces additional latency before execution resumes. PATCH preserves completed work.

**Weakness:** PATCH replanning can accumulate technical debt. Each PATCH modifies the plan structure while retaining artifacts and world-state mutations from completed tasks. After multiple PATCH operations, the plan structure may be significantly different from any plan that would have been produced from scratch, potentially with suboptimal structure. Production deployments should consider logging the number of PATCH operations per plan and triggering a FULL_REPLAN after a threshold is exceeded.

## 19. Compatibility Notes

### 19.1 RFC-0007 (Scheduler): Execution Graph Schema Is a Joint Contract

The Execution Graph schema defined in this RFC is the primary input contract for RFC-0007. Any change to the Execution Graph schema must be coordinated between RFC-0011 (Planner) and RFC-0007 (Scheduler). Neither RFC may change this schema unilaterally.

**Observation:** RFC-0007 was finalized before RFC-0011. It is possible that RFC-0007 assumes an Execution Graph structure different from what RFC-0011 defines. This must be verified. If a discrepancy exists, RFC-0007 must be amended with a compatibility note, not silently overridden.

**Required action:** The Execution Graph schema defined in Section 9.4 of this RFC must be reviewed against RFC-0007's expected input format. Discrepancies must be resolved by amendment before either RFC moves from Proposed to Accepted status.

### 19.2 RFC-0002 (Skill Registry): Method Storage Is a New Requirement

This RFC assumes that Methods are stored in RFC-0002's Skill Registry as part of skill manifests. RFC-0002 may not have been designed with Method storage in mind — it may only support skill capability declarations without decomposition logic.

**If RFC-0002 does not support Method storage:** An RFC-0002 amendment is required to add a `methods` section to skill manifests and a Method-indexed query interface to the Registry. This RFC does not modify RFC-0002 directly.

**Risk:** If Methods are stored outside RFC-0002 (e.g., in a separate Method store), the architectural coherence of the Planner is weakened — there are now two registries (skills and methods) that must be kept consistent.

### 19.3 RFC-0003 (Policy Engine): PLAN_TIME Evaluation Context

This RFC requires RFC-0003 to support a `PLAN_TIME` evaluation context (as opposed to `RUNTIME`). If RFC-0003 does not currently distinguish between these contexts, all plan-time policy checks will be evaluated as runtime checks, which may be more restrictive than necessary and may cause valid plans to be rejected.

**Required action:** RFC-0003 should be amended to support the `PLAN_TIME` context attribute. Until this is done, the Planner must treat all PERMIT decisions as CONDITIONAL, which inflates the proportion of runtime-check-annotated Tasks and reduces plan confidence scores unnecessarily.

### 19.4 RFC-0010 (Memory System): Reflection Memory Schema Dependency

The Cost and Confidence Estimator relies on a specific structure of Reflection Memory entries (specifically: `skill_type`, `domain_tags`, `success_count`, `total_count`, `historical_duration_ms`). RFC-0010 defines Reflection Memory structurally but does not mandate a specific entry schema.

**Required action:** The Reflection Memory entry schema used by the Planner must be formalized. Either RFC-0010 should define a standard schema for skill reliability observations, or this RFC must publish a schema that Reflection skills (a future RFC concern) are expected to conform to. Until this is formalized, the Estimator will degrade gracefully (ESTIMATION_DATA_SPARSE penalty) when no conformant data is found.

### 19.5 RFC-0004 (Artifact System): Plan Artifact Size

Plan Artifacts for complex plans may be several megabytes. If RFC-0004 has implicit or explicit size limits on Artifact content, large Plan Artifacts may fail to write. RFC-0004 should be reviewed for size limits, and if limits exist, they should be documented so that the Plan Artifact Materializer can apply appropriate chunking or compression.

## 20. Critical Self-Review

### 20.1 HTN Is Fundamentally Limited by Method Library Quality

The Planner can only produce plans that the Method library supports. If a Goal requires a novel decomposition strategy not represented by any registered Method, the Planner fails with NO_METHOD_FOUND. There is no fallback that produces a valid plan from first principles.

**Honest assessment:** This is the correct behavior for a deterministic, auditable kernel subsystem — failing explicitly is better than producing an unverifiable plan. However, it means the operational quality of the Planner is entirely determined by the quality of the Method library, which is a human-authored artifact. Method library maintenance is a non-trivial operational burden that this RFC does not address. A future RFC addressing Method authoring, testing, and quality governance is essential for long-term system viability.

### 20.2 The World State Model Is Necessarily Incomplete

The open-world assumption is correct for AGY's operational environment, but it means the Planner is planning against an incomplete picture of the world. Plans will be produced and executed that fail at runtime due to world state conditions the Planner did not know about. The confidence estimation mechanism partially mitigates this, but it does not eliminate it.

**Honest assessment:** This is an inherent limitation of planning under uncertainty, not a flaw in this design. Any planning system operating in an open world faces this problem. The design's response — expose confidence scores, annotate unknown preconditions, and support replanning — is correct. What is missing is a feedback loop that updates the World State Model during execution and feeds observations back to Semantic Memory. This requires integration with a future RFC (likely an Execution Monitor) and is not addressable within the Planner's scope.

### 20.3 Confidence Estimation Is Weakly Grounded

The confidence estimation algorithm uses linear penalty factors with hard-coded coefficients (10% per unknown precondition, 50% weight for historical failure rate). These coefficients are arbitrary. They were chosen to produce intuitively reasonable results, not derived from empirical data.

**Honest assessment:** In a production system, the accuracy of confidence estimates will be the primary determinant of whether the confidence threshold mechanism is useful or noise. Arbitrary coefficients produce arbitrary estimates. Over time, a calibration mechanism that compares predicted confidence against actual execution outcomes (via Reflection Memory) and adjusts coefficients accordingly is essential. This RFC does not include this mechanism. It should be in a future RFC.

### 20.4 Replanning Is Underdetermined at the Boundaries

The PATCH replanning strategy retains completed tasks and re-plans failed subgraphs. The boundary between "completed" and "failed" is clear in the simple case. In practice, a failed Task may have produced partial Artifacts. A parallel Task that was awaiting an Artifact from the failed Task may have already started. The boundary conditions for PATCH replanning in the presence of concurrent execution and partial Artifact production are not fully specified in this RFC.

**Honest assessment:** This is a genuine gap. The interaction between parallel execution (Scheduler RFC-0007), partial Artifact production (RFC-0004), and PATCH replanning (this RFC) requires more detailed specification. The current design defers this to the Scheduler's handling of partial Execution Graph states, but if the Scheduler was not designed with mid-graph replanning in mind, there may be a structural mismatch. This should be addressed jointly with RFC-0007 in a compatibility amendment.

### 20.5 The Plan Artifact Is Both Audit Record and Operational Input

The Plan Artifact serves as the complete audit record of the planning process and as the reference for replanning. This dual purpose creates tension: audit records should be immutable and comprehensive; operational inputs should be compact and fast to load. For complex plans, loading the full Plan Artifact at replan time (which includes the full Decomposition Tree, all method application logs, all policy decisions) may be slow.

**Honest assessment:** The Plan Artifact should potentially be split into two structures: a compact Execution Graph record (for operational use) and a full planning record (for audit). The current design conflates them. This is a maintainability concern that will become more visible at scale.

### 20.6 No Mechanism for Human Plan Approval

The Planner produces an Execution Graph and the Scheduler executes it. There is no mechanism in this RFC for a human (or a policy) to review a plan and approve it before execution. For high-stakes or high-cost plans, the absence of a mandatory approval step is a governance gap.

**Honest assessment:** Plan approval is a valid and important feature, but it is properly implemented as a policy mechanism (RFC-0003 could define a `REQUIRES_APPROVAL` policy decision for plan-time evaluation) or as a workflow step in the Scheduler. Adding it to the Planner would violate the separation of concerns. This is documented here so that future RFC authors are aware of the gap.

## 22. Future RFC Dependencies

### RFC-0012 (Required): Execution Monitor

The Planner produces plans; the Scheduler executes them. What is missing is a subsystem that monitors execution in progress, detects when actual execution diverges from planned execution, and triggers replanning when necessary. RFC-0011's replanning capability is passive (it responds to requests); an active Execution Monitor is needed to detect when replanning should be triggered without waiting for the Scheduler to detect and report a failure.

### RFC-0013 (Suggested): Method Governance and Quality

This RFC exposes a critical dependency on Method library quality. RFC-0013 should define: how Methods are authored, tested (unit-testable decomposition paths), validated (against policy and Skill Registry), and versioned. It should also define Method deprecation, conflict detection (two Methods for the same task type with conflicting preconditions), and quality metrics.

### RFC-0014 (Suggested): Plan Approval and Governance

As noted in the Critical Self-Review, high-stakes plans may require human or automated approval before execution. RFC-0014 should define the plan approval workflow, integrating with RFC-0003 (policy-driven approval requirements) and RFC-0007 (execution gated on approval status).

### RFC-0015 (Suggested): Confidence Calibration

The confidence estimation system requires empirical calibration to be reliable. RFC-0015 should define the feedback loop: how actual execution outcomes are compared against plan-time confidence predictions, how calibration adjustments are computed and applied, and how the calibrated coefficients are stored and versioned.

### RFC-0016 (Suggested): Multi-Goal Planning and Plan Merging

This RFC designs single-goal planning. In practice, AGY may need to plan for multiple concurrent Goals that share resources and depend on each other's outputs. Multi-goal planning — merging multiple independent Execution Graphs into a coordinated global plan — is a significant architectural extension that should be addressed in its own RFC.

### Dependency on RFC-0007 Joint Amendment

As noted in Compatibility Notes 19.1, the Execution Graph schema defined by this RFC must be verified and reconciled against RFC-0007's expected input. This reconciliation should produce a joint RFC-0007/RFC-0011 amendment that formally specifies the Execution Graph as a shared interface contract between the Planner and the Scheduler.
