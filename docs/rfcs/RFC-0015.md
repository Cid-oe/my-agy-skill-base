## 1. Executive Overview

This RFC defines **RFC-0015 Observability**, the subsystem that provides production-grade debugging and operational insight for AGY. Observability is not logging-only and not metrics-only. It is a coordinated, policy-governed system that correlates:

- **Distributed tracing** (causal path of work across skills, tools, memory, scheduler, and policy decisions)
- **Timeline views** (what happened when, across the execution lifecycle)
- **Execution graph visualization** (planned DAG vs actual DAG, critical path, concurrency waves)
- **Performance metrics** (latency, throughput, resource usage, error rates)
- **Logs** (human-readable context for failures and anomalies)
- **Events** (RFC-0006 as canonical operational event stream)
- **Artifact lineage viewer** (RFC-0004 provenance graph and “why does this exist?”)
- **Scheduler visualization** (queue, dispatch, retries, cancellations, leases)
- **Resource dashboard** (token budgets, compute tiers, tool quotas, concurrency saturation)
- **Reflection dashboard** (RFC-0013 outputs, quality scores, failure patterns)
- **Decision journal explorer** (planner/tool routing/skill selection decisions and alternatives)

AGY is deterministic and artifact-based. Observability must be equally deterministic: the same execution and the same recorded data must yield the same derived views (timeline, graph overlays, critical path). Observability must also be **fail-safe**: it must never break or slow the primary execution path; it must degrade by dropping or sampling data and by delaying derivations rather than blocking runtime.

Observability, as specified here, is an **abstraction**: it defines canonical data models, ingestion paths, correlation rules, and query/view interfaces. It does **not** mandate any vendor (no assumption of Prometheus, Jaeger, ELK, OpenTelemetry collectors, etc.), but it intentionally aligns with widely-known concepts (trace IDs/spans, metric points, log entries) for implementability.

## 2. Responsibilities

### 2.1 Signal collection (ingestion)
- Ingest and persist **events** from RFC-0006 Event Bus as the canonical event stream.
- Ingest **trace spans** from participating subsystems (Planner, Scheduler, Tool Runtime, Memory, Policy Gate).
- Ingest **logs** emitted by kernel components and optionally by skills (skills are plugins; logs are policy-gated).
- Ingest **metrics** (counters, gauges, histograms) from all subsystems.

### 2.2 Correlation
- Correlate signals by stable IDs:
  - `execution_id` (RFC-0005/RFC-0007)
  - `plan_id`, `graph_id`, `task_id` (RFC-0011/RFC-0007)
  - `invocation_id` (RFC-0012)
  - `artifact_id` (RFC-0004)
  - `memory_entry_id` (RFC-0010)
  - `policy_decision_id` (RFC-0003, if available)
- Support multi-dimensional correlation: timeline views, trace-to-event joins, artifact lineage to execution.

### 2.3 Derived views and visualizations (data products)
- Build and serve:
  - **Execution Timeline** (ordered, causally grouped)
  - **Execution Graph View** (planned DAG + runtime overlays)
  - **Scheduler View** (queues, dispatches, retries, concurrency waves, critical path)
  - **Artifact Lineage Graph View** (provenance traversal, derived-from edges)
  - **Resource Dashboard** (tokens, tool quotas, latency budgets, compute tiers)
  - **Reflection Dashboard** (quality score trends, failure cascades, recommendations)
  - **Decision Journal Explorer** (decision points, alternatives, counterfactual summaries)

### 2.4 Production debugging tooling support
- Provide query interfaces for:
  - “Why did execution X fail?”
  - “Which tool invocation caused the cascade?”
  - “Which tasks were on the critical path and why did they stall?”
  - “What artifacts were produced and which were consumed?”
  - “Which policy denials contributed to retries or replan?”
  - “Which version of methods/skills/tools/models were used?”
- Support “debug bundles”: immutable, exportable artifact packages containing all correlated signals for an incident.

### 2.5 Governance, retention, and policy
- Enforce **access control** (RFC-0003) for all observability data.
- Support retention policies per signal type and sensitivity.
- Provide redaction and minimization hooks for logs and traces.

### 2.6 Non-invasive operation
- Never block execution when observability backends are degraded.
- Provide sampling strategies and buffer limits.
- Provide deterministic sampling rules.

## 3. Non-goals

- Defining a user interface framework. This RFC defines **view models** and query responses that any UI can render.
- Guaranteeing lossless capture of all signals. High-volume production requires sampling and dropping under pressure.
- Performing automated incident remediation. Observability explains; remediation belongs elsewhere.
- Replacing RFC-0006 event bus semantics. Observability consumes RFC-0006; it does not redefine it.
- Mandating a single “one true” store for all signals. This RFC defines store adapters.

## 4. Relationship to Previous RFCs

### RFC-0006 Event Bus (primary ingestion)
- Observability subscribes to `*` or to configured namespaces (e.g., `planner.*`, `scheduler.*`, `tool.*`, `memory.*`, `reflection.*`, `learning.*`).
- Events remain the canonical cross-subsystem signal for lifecycle and state transitions.
- Observability does not modify event schemas; it consumes envelopes and payloads.

### RFC-0004 Artifact System (lineage + debug bundles)
- Observability reads artifact metadata to build lineage graphs.
- Observability writes:
  - **Observability Snapshot Artifacts** (derived views, e.g., execution timeline snapshots)
  - **Debug Bundle Artifacts** (export packages, immutable)
- Lineage viewer depends on RFC-0004 lineage correctness and on lifecycle events for broken references.

### RFC-0005 Runtime State (correlation keys)
- Observability does not read live runtime state for debugging (avoid coupling); it uses finalized execution records and event streams that include runtime IDs.

### RFC-0007 Scheduler
- Scheduler visualization requires scheduler events/records: dispatch, completion, failure, retries, cancellation, resource leasing.
- Observability correlates scheduler activity with plan graph nodes from RFC-0011 and with tool invocations from RFC-0012.

### RFC-0011 Planner
- Execution graph visualization uses the plan artifact (decomposition tree + execution DAG) and overlays actual timing and outcomes.

### RFC-0012 Tool Runtime
- Distributed tracing spans include tool invocation spans; observability correlates them with InvocationRecord artifacts.

### RFC-0010 Memory System
- Observability monitors memory operations (reads/writes/consolidation/forgetting) as contributors to performance and correctness issues.
- Cache improvement dashboards require memory metrics and query latency.

### RFC-0013 Reflection Engine / RFC-0014 Learning Engine
- Reflection dashboard consumes reflection artifacts, quality scorecards, and recommendations.
- Learning dashboard elements (optional) show overlay applications, rollbacks, and evidence.

### RFC-0003 Policy Engine
- Observability must be policy gated, and may incorporate policy outcome metrics and denials into timelines and decision explorer.

## 5. Architecture

### 5.1 Overview

Observability is a pipeline with three layers:

1. **Signal ingestion & normalization**
2. **Correlation & storage**
3. **Derived view builders & query APIs**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Public Observability API                           │
│ QueryTraces │ QueryTimeline │ QueryGraph │ QueryMetrics │ QueryLogs   │
│ LineageView │ SchedulerView │ ResourceDash │ ReflectionDash │ Bundle   │
├─────────────────────────────────────────────────────────────────────┤
│                    Observability Kernel Core                          │
│ Policy Gate │ Correlation Engine │ Redaction │ Sampling │ Export      │
├─────────────────────────────────────────────────────────────────────┤
│          Ingestion Layer (adapters)                                   │
│ Event Bus Adapter │ Trace Adapter │ Metrics Adapter │ Logs Adapter    │
│ Artifact Metadata Adapter │ Scheduler Record Adapter                 │
├─────────────────────────────────────────────────────────────────────┤
│          Storage Abstraction Layer                                    │
│ Event Store │ Trace Store │ Metrics Store │ Logs Store │ View Store   │
├─────────────────────────────────────────────────────────────────────┤
│          Derived View Builders (batch + on-demand)                    │
│ Timeline Builder │ Graph Overlay Builder │ Lineage Builder            │
│ Scheduler View Builder │ Resource Aggregator │ Reflection Aggregator  │
│ Decision Journal Indexer │ Debug Bundle Builder                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 Determinism and sampling

Observability introduces sampling, which can undermine determinism. This RFC requires **deterministic sampling**:

- Sampling decisions are derived from stable IDs (`trace_id`, `execution_id`) via a hash function.
- For the same execution/trace ID, sampling decision is stable across runs.

This enables reproducible debugging: if an execution is flagged as “debug,” the system can deterministically capture all its signals.

### 5.3 Canonical correlation keys

Every signal (event, span, log, metric point) should include as many of the following keys as possible:

- `tenant_id`
- `execution_id`
- `plan_id`, `graph_id`
- `task_id`
- `skill_id`, `skill_version`
- `tool_id`, `capability_name`, `invocation_id`
- `artifact_id`
- `memory_entry_id`
- `policy_decision_id`
- `trace_id`, `span_id`, `parent_span_id`

This RFC defines how to build timelines and views even when some keys are missing (graceful degradation).

## 6. Internal Components

### 6.1 Policy Gate
All queries and exports are policy evaluated via RFC-0003. Sensitive observability data includes:
- tool inputs/outputs (often PII or secrets)
- policy denial reasons
- user memory access
- raw logs with content
- traces that include request payloads

The Policy Gate enforces:
- read permissions per tenant/project/user scope
- redaction requirements per sensitivity class
- export permissions for debug bundles

### 6.2 Sampling Manager
Provides:
- head-based deterministic sampling (on ingestion)
- tail-based sampling triggers (on failure signals) implemented as **best-effort**, because tail sampling requires buffering.

Sampling strategies:
- **Always sample** for `execution.priority=CRITICAL` or `policy.requires_audit=true`.
- **Hash sample** for baseline traffic.
- **Escalation sampling**: when `scheduler.task.failed` occurs, mark the execution for elevated sampling for subsequent signals (cannot recover already dropped signals).

### 6.3 Normalizers
- **Event Normalizer:** canonicalize RFC-0006 events to `ObsEventRecord`.
- **Trace Normalizer:** canonicalize span structures to `TraceSpanRecord`.
- **Log Normalizer:** canonicalize logs to `LogRecord` and apply redaction hooks.
- **Metrics Normalizer:** canonicalize metric points/histograms.

### 6.4 Correlation Engine
Builds:
- execution-centric indexes: `(execution_id → event_ids, span_ids, log_ids, metric_series_ids)`
- task-centric indexes: `(task_id → related records)`
- artifact-centric indexes: `(artifact_id → producing execution/task + consumers)`
- tool invocation correlation: `(invocation_id → span + event + invocation artifact)`

### 6.5 View Builders
- **Timeline Builder:** merges events/spans/logs into a unified timeline (Section 11.1).
- **Execution Graph Overlay Builder:** overlays runtime durations, retries, failures onto planned DAG.
- **Artifact Lineage Builder:** queries RFC-0004 lineage and builds lineage graphs.
- **Scheduler View Builder:** constructs queue/dispatch timelines, per-worker concurrency, and critical path.
- **Resource Aggregator:** aggregates token costs, tool quota usage, concurrency, and storage.
- **Reflection Aggregator:** aggregates quality scores, failure patterns, recommendations across time.
- **Decision Journal Indexer:** indexes decision journals for exploration and cross-linking.

### 6.6 Debug Bundle Builder
Creates a single exportable artifact containing:
- plan artifact
- execution graph overlay
- scheduler record
- correlated traces, logs (redacted), key metrics
- lineage subgraph of related artifacts
- reflection artifact (if exists)
- learning overlay versions active during execution (if exists)

Bundles are immutable RFC-0004 artifacts.

## 7. Public Interfaces

All interfaces are read-only except export/bundle generation and optional ingestion endpoints (for external collectors). Public interfaces are policy-gated.

### 7.1 QueryExecutionTimeline
**Input:** `execution_id`, time range, include flags (events/traces/logs/metrics), verbosity  
**Output:** `ExecutionTimelineView`

### 7.2 QueryDistributedTrace
**Input:** `trace_id` or `execution_id`, span filters, include attributes  
**Output:** `TraceView` (tree + critical spans)

### 7.3 QueryExecutionGraphView
**Input:** `plan_id` or `execution_id`  
**Output:** planned graph + overlays: actual duration, status, retries, blocking edges

### 7.4 QuerySchedulerView
**Input:** time range, queue filters, worker filters, execution_id optional  
**Output:** scheduler state snapshots + gantt-like dispatch timeline model

### 7.5 QueryArtifactLineageView
**Input:** `artifact_id`, direction (upstream/downstream), depth limit  
**Output:** `LineageGraphView`

### 7.6 QueryMetrics
**Input:** metric selector, dimensions (tenant/execution/task/tool), aggregation (p50/p95)  
**Output:** time series or histogram view models

### 7.7 QueryLogs
**Input:** filters by execution/task/span, severity, substring (optional), redaction mode  
**Output:** `LogView`

### 7.8 QueryReflectionDashboard
**Input:** tenant scope, time range, goal type filters  
**Output:** quality score trends, top failures, top recommendations, confidence calibration health

### 7.9 QueryDecisionJournalExplorer
**Input:** execution_id or plan_id, decision type filters  
**Output:** decision points, chosen options, alternatives, outcomes, links to evidence

### 7.10 BuildDebugBundle
**Input:** execution_id, bundle profile (minimal/standard/full), retention TTL  
**Output:** artifact_ref to debug bundle + manifest

### 7.11 (Optional) IngestExternalSignals
For deployments where traces/metrics/logs come from external collectors, an ingestion interface may exist:
- `IngestSpans`, `IngestMetricPoints`, `IngestLogs`
This is optional and must not be required for core AGY operation.

## 8. Data Structures

### 8.1 TraceSpanRecord
```
TraceSpanRecord {
  trace_id: bytes(16)
  span_id: bytes(8)
  parent_span_id: bytes(8) | null

  name: string
  kind: INTERNAL | SERVER | CLIENT
  start_time: Timestamp
  end_time: Timestamp

  attributes: map<string, TypedValue>
  status: OK | ERROR | UNSET
  events: [SpanEvent { time, name, attributes }]

  correlation: {
    tenant_id: TenantID
    execution_id?: UUID
    plan_id?: UUID
    task_id?: UUID
    skill_id?: string
    tool_id?: UUID
    invocation_id?: UUID
    artifact_ids?: [UUID]
  }

  sampling: { sampled: boolean, reason: string }
}
```

### 8.2 ObsEventRecord (from RFC-0006)
```
ObsEventRecord {
  event_id: UUID
  topic: string
  time: Timestamp
  payload: map<string, TypedValue>
  correlation: { tenant_id, execution_id?, plan_id?, task_id?, trace_id?, span_id? }
}
```

### 8.3 LogRecord
```
LogRecord {
  log_id: UUID
  time: Timestamp
  severity: DEBUG|INFO|WARN|ERROR
  message: string
  structured: map<string, TypedValue>

  correlation: { tenant_id, execution_id?, task_id?, trace_id?, span_id? }
  redaction: { applied: boolean, fields_redacted: [string] }
}
```

### 8.4 MetricPoint / MetricSeries
```
MetricPoint {
  metric_name: string
  time: Timestamp
  value: float | int | histogram
  dimensions: map<string, string>  // tenant_id, tool_id, skill_type, task_id, etc.
}
```

### 8.5 ExecutionTimelineView (render model)
```
ExecutionTimelineView {
  execution_id: UUID
  start_time: Timestamp
  end_time: Timestamp
  segments: [TimelineSegment {
    segment_id: UUID
    type: TASK | TOOL_INVOCATION | POLICY_CHECK | MEMORY_OP | SCHEDULER_WAIT
    subject_id: string
    start_time: Timestamp
    end_time: Timestamp
    status: SUCCESS|FAILURE|RETRY|CANCELLED|TIMEOUT
    links: { task_id?, invocation_id?, span_id?, artifact_ids? }
    annotations: map<string, TypedValue>
  }]
  incidents: [IncidentMarker { time, severity, summary, linked_records }]
  completeness: float
}
```

### 8.6 ExecutionGraphView (planned + overlays)
```
ExecutionGraphView {
  plan_id: UUID
  graph_id: UUID
  nodes: [GraphNodeView {
    task_id: UUID
    skill_type: string
    planned: { est_duration_ms, est_token_cost, priority, parallel_group }
    actual: { start_time?, end_time?, duration_ms?, status, retry_count }
    critical_path: boolean
    blockers: [UUID]  // task_ids blocking this node
    links: { trace_span_ids, logs, artifacts }
  }]
  edges: [GraphEdgeView { source_task_id, target_task_id, type }]
  derived: { critical_path_duration_ms, max_parallel_degree, underutilization_notes }
}
```

### 8.7 LineageGraphView
```
LineageGraphView {
  root_artifact_id: UUID
  nodes: [ArtifactNode {
    artifact_id: UUID
    artifact_type: string
    created_at: Timestamp
    produced_by: { execution_id?, task_id?, tool_id? }
    sensitivity: string
  }]
  edges: [LineageEdge { from_artifact_id, to_artifact_id, relation: DERIVED_FROM|CONSUMED_BY }]
  depth: int
  truncated: boolean
}
```

### 8.8 SchedulerView
Includes queue depth, worker utilization, dispatch history, retry storms, lease conflicts, and per-execution scheduling delays.

### 8.9 ReflectionDashboardView
Summaries of quality scores, failure classes, cascade patterns, recommendation backlog, calibration error trends.

### 8.10 DecisionJournalView
Decision points with alternatives and outcomes linked to trace segments and failures.

## 9. Runtime Lifecycle

### 9.1 Startup
- Load configuration (sampling rules, retention rules, redaction policy).
- Initialize store adapters (event/trace/log/metric/view stores).
- Subscribe to RFC-0006 topics.
- Register background jobs with RFC-0007:
  - view materialization (timeline/graph overlays)
  - lineage index refresh
  - retention/compaction
  - debug bundle cleanup

### 9.2 Ingestion
- Events: near-real-time ingestion from Event Bus.
- Traces: span ingestion from internal emitters or external collectors.
- Logs: streaming ingestion with backpressure.
- Metrics: periodic scrape/push ingestion.

### 9.3 Derivation
- On execution completion, build:
  - timeline view snapshot
  - execution graph overlay snapshot
  - scheduler overlay snapshot
  - incident markers (failures, timeouts, policy denials)

### 9.4 Query
- On-demand queries join raw signals with derived views.
- Derived views cached in View Store with TTL.

### 9.5 Export
- Debug bundle created on request; stored as artifact; subject to retention policy and redaction.

## 10. State Machines

### 10.1 Execution Observability State
```
EXECUTION_ACTIVE
  ├─(signals ingested)→ PARTIAL_VIEW_AVAILABLE
  └─(execution completed)→ FINALIZING_VIEWS → FINAL_VIEW_AVAILABLE
  └─(missing records)→ FINAL_VIEW_DEGRADED
```

### 10.2 Debug Bundle State
```
REQUESTED → COLLECTING → REDACTING → WRITING_ARTIFACT → AVAILABLE
                 └→ FAILED (with partial manifest)
```

### 10.3 Trace Assembly State
```
SPAN_INGESTED → PARENT_LINKED → TRACE_COMPLETE (heuristic) → TRACE_ARCHIVED
```
“TRACE_COMPLETE” is heuristic because spans can arrive late.

## 11. Algorithms

### 11.1 Timeline construction
**Goal:** merge heterogeneous records into a coherent timeline.

1. Collect all events/spans/logs linked to `execution_id`.
2. Create segments:
   - Task segments from scheduler task start/end events
   - Tool invocation segments from tool invocation started/completed
   - Policy check segments from policy decision events or spans
   - Scheduler wait segments from queueing delay (dispatch time - ready time)
3. Attach correlated spans/logs to segments by:
   - matching `task_id` / `invocation_id` / `(trace_id, span_id)`
4. Detect incident markers:
   - any FAILURE/TIMEOUT event
   - retry storms (attempts > threshold)
   - long tail latency (segment duration > p99 baseline)
5. Produce deterministic ordering:
   - primary sort by `start_time`
   - tie-break by `segment_type` priority
   - tie-break by stable ID

### 11.2 Critical path overlay (planned DAG + actual durations)
Given execution graph and actual node durations:
- compute longest path weight = duration_ms across DAG
- mark nodes/edges on longest path as critical
- annotate blocking edges causing stalls (node waiting due to predecessor not finished)

### 11.3 Artifact lineage traversal
- BFS/DFS over RFC-0004 lineage edges, depth-bounded
- stop conditions:
  - depth reached
  - max nodes reached (prevent explosion)
- deterministic traversal order:
  - sort outgoing edges by artifact_id

### 11.4 Scheduler visualization aggregation
- compute per-worker utilization time series
- compute queue depth time series
- compute per-execution scheduling delay:
  - `dispatch_time - ready_time`
- detect contention patterns:
  - repeated “resource unavailable” events
  - high cancellation rates
  - lease conflicts

### 11.5 Redaction
Redaction is policy-driven:
- identify sensitive fields by schema tags or policy classification
- replace content with placeholders while preserving structure
- keep cryptographic hashes of redacted content for correlation without exposure

## 12. Failure Recovery

Observability must fail safe.

### 12.1 Ingestion overload
- Apply backpressure and bounded queues.
- Drop lowest-priority signals first (DEBUG logs, low-value spans) while keeping:
  - lifecycle events
  - ERROR logs
  - execution completion summaries
- Emit internal `observability.dropped_signals` metrics.

### 12.2 Store unavailability
- If View Store down: serve raw queries; derived views unavailable.
- If Trace Store down: timeline still built from events; trace views degraded.
- If Event Store down: derived views incomplete; rely on artifacts for post-mortem.
- No runtime blocking; ingestion buffers with max size then drops.

### 12.3 Late-arriving data
- Update derived views opportunistically within a “late arrival window” (e.g., 10 minutes after execution end).
- After window, derived views are immutable snapshots unless explicit rebuild requested.

### 12.4 Debug bundle failures
- If any component missing, bundle includes a manifest of missing parts and a partial bundle.
- Never block; return `BUNDLE_PARTIAL` with reasons.

## 13. Security Considerations

### 13.1 Data sensitivity
Observability data often contains:
- PII (user inputs, tool outputs)
- credentials (should be excluded but can leak via logs)
- policy rationale (sensitive)
- system topology details (attack surface)

### 13.2 Policy enforcement
- All queries and exports policy-gated via RFC-0003.
- Cross-tenant isolation mandatory.
- Redaction enforced before returning results, not as a UI feature.

### 13.3 Least privilege for debug bundles
- Bundle creation requires explicit permission.
- Bundles inherit the highest sensitivity of included records/artifacts.

### 13.4 Integrity
- Derived views include hash references to source records.
- Debug bundles include hashes for included components.

## 14. Performance Analysis

- Ingestion overhead must be minimal:
  - events: already produced; adapter overhead small
  - spans/logs: must not add significant latency; ideally asynchronous
- Derived view build targets:
  - per-execution final view build: < 1s typical, < 10s worst-case
- Query targets:
  - execution timeline query p99 < 2s for typical executions
  - lineage query bounded by depth/max nodes

---

## 15. Scalability Analysis

Target scale:
- 100+ concurrent executions
- thousands of tasks per minute
- tens of thousands of tool invocations per minute
- millions of spans/day
- billions of log lines/day (requires sampling and retention controls)

Scalability mechanisms:
- deterministic sampling
- per-tenant partitioning
- bounded view materialization
- lineage traversal limits
- retention + compaction to artifacts for cold storage

---

## 16. Concurrency Model

- Ingestion pipelines are concurrent and partitioned by tenant.
- Derived view builds can run concurrently per execution_id.
- Store writes are append-only (events/logs/spans) with indexed reads.
- View rebuild uses optimistic concurrency:
  - view version increments, last-write-wins within late window.

- deterministic sampling correctness
- timeline builder ordering and tie-breaking
- critical path computation

### 17.2 Integration tests

- ingestion under burst conditions

- policy denies query; ensure no partial leakage
- redaction rules applied

## 18. Tradeoff Analysis

### 18.1 Unified store vs specialized stores
- **Chosen:** storage abstraction with specialized stores (event/trace/log/metric/view).
- **Rejected:** single monolithic store; rejected due to differing access patterns and retention.

Weakness: operational complexity; mitigated by strict adapter interfaces.

### 18.2 Snapshot views vs fully live views
- **Chosen:** derived snapshot views per execution (final view), plus bounded late update window.
- **Rejected:** fully live constantly-updating views; too expensive at scale and hard to reason about.

Weakness: late data might not appear; mitigated by explicit rebuild operation.

### 18.3 Deterministic sampling vs tail-based sampling
- **Chosen:** deterministic sampling by hash; tail-based is best-effort.
- **Rejected:** pure tail sampling; requires buffering everything, which is unrealistic at scale.

Weakness: some failures might be undersampled; mitigated by escalation sampling on failure signals.

### 18.4 Redaction at source vs redaction at query
- **Chosen:** redaction at query/export boundary (policy-driven), with optional source redaction hooks.
- **Rejected:** mandatory redaction at source; loses forensic fidelity.

Weakness: raw storage must be well-protected; requires strong access control and encryption.

## 19. Compatibility Notes

This RFC relies on correlation keys being present. Some prior RFCs may not explicitly mandate trace IDs or correlation IDs in all emitted events.

- **RFC-0006:** If event envelopes do not include optional `trace_id/span_id` fields, trace-to-event correlation is weaker; timeline still works from execution/task IDs.
- **RFC-0012:** Tool Runtime already defines `TraceContext` in `NormalizedRequest` (RFC-0012 §8.4). If not implemented, distributed tracing across tools becomes fragmented.
- **RFC-0011/RFC-0007:** If scheduler records do not emit stable task IDs consistently across retries, overlay accuracy degrades.

No contracts are changed; these are quality-of-observability dependencies, not correctness dependencies.

## 20. Critical Self Review

1. **Correlating across subsystems is only as good as the IDs.** If producers omit keys, views degrade. This RFC cannot force key inclusion without amending contracts.  
2. **Redaction is hard to get right.** Field-level sensitivity tagging is imperfect; secrets may still leak via logs. Defense requires both producer hygiene and query-time redaction.  
3. **Derived views can become expensive at scale.** Timeline and graph overlays for very large DAGs can be heavy; bounding and caching are necessary but introduce truncation.  
4. **Tail sampling remains limited.** Without buffering, you can’t retroactively capture missing pre-failure spans.  
5. **Artifact lineage graphs can explode.** Depth and node limits are essential but can hide relevant edges; the UI must show truncation clearly.  
6. **Observability itself can become a data exfiltration channel.** Strong policy gating and audit logs for observability queries are mandatory.

  Standardize secret detection and structured redaction tags at the producer side.
- **RFC-0017: Incident Management Integration**  
  Map observability incidents to tickets/alerts without coupling to a vendor.
- **RFC-0018: Observability Federation / Cross-Region Aggregation**  
  Multi-region trace/log correlation and consistent query semantics across shards.
- **RFC-0019: Formal Decision Journal Schema**  
  If decision journals remain optional, standardization would improve explorer fidelity.
- **RFC-0020: Observability Cost Controls**  
  Explicit budgets for log volume, span volume, and query costs per tenant.
