## 1. Executive Overview

### 1.1 Purpose

Given a resolved `ExecutionPlan` (RFC-0001) whose nodes have each been
governed by the Policy Engine (RFC-0003, producing `ALLOW`/`DENY`/
`MODIFIED`/`ESCALATE`/`DEFER` per node), the Scheduler decides the
concrete mechanics of running that plan: what executes now, what waits,
what runs concurrently, what is blocked, what gets retried, and what is
cancelled — and it does so **reproducibly**: identical `RuntimeState`,
`ExecutionGraph`, policy decisions, and resource availability must always
produce the same execution order.

### 1.2 Responsibilities

Dependency scheduling; the ready/waiting/blocked/retry/timeout queues;
execution ordering; concurrency limits; worker assignment; priority
scheduling; fairness and starvation prevention; cancellation propagation;
execution graph traversal.

### 1.3 Non-goals

The Scheduler does not execute anything, evaluate policy, own artifacts,
own `RuntimeState`, own the Registry, route models, grant permissions, or
own telemetry. Every one of these exclusions is a boundary this RFC
enforces structurally, not just states as intent — see §9, §10, §11 for
where each boundary is drawn in the actual contracts.

The clearest way to state the Scheduler's non-goal set: **it answers
"when and where," never "what" or "whether."** "What" was already decided
by the Resolver (RFC-0001). "Whether" was already decided by the Policy
Engine (RFC-0003). The Scheduler's only remaining degree of freedom is
timing and placement.

### 1.4 Relationship to Previous RFCs

The Scheduler reads `ExecutionPlan` structure (nodes, edges) from
RFC-0001, reads `PolicyDecision`s from RFC-0003 per §9, and — notably —
does **not** read RFC-0002's Registry directly. Loading a skill
(RFC-0002 §5) is triggered by whatever executes the node, not by the
Scheduler; the Scheduler only needs to know a node's `estimatedCost`/
`estimatedLatency`/`estimatedContext` (already present on `PlanNode` per
RFC-0001 §3) to make placement decisions, not the skill's actual code or
permissions. This is a deliberate narrowing of the Scheduler's read
surface: it needs just enough manifest-derived data to schedule, and no
more, consistent with §1.3's "what/whether are already decided" framing.

## 2. Scheduling Model

| Concept | Definition |
|---|---|
| **Task** | The Scheduler's unit of work: one `PlanNode` (RFC-0001) that has cleared policy evaluation (RFC-0003) and is a candidate for execution. A Task is *not* a `PlanNode` itself — it is a `PlanNode` wrapped with scheduling-specific state (queue membership, attempt count, lease, timing). |
| **Node** | Reused from RFC-0001 (`PlanNode`) — read-only from the Scheduler's perspective. The Scheduler never mutates a `PlanNode`; it mutates the `Task` wrapper around it. |
| **Worker** | An abstract execution slot capable of running exactly one Task at a time. A Worker is not assumed to be a thread, process, or remote machine — it is whatever the (not-yet-designed) Execution Runtime exposes as a unit of executing capacity, contracted via §11. |
| **Queue** | One of six named queues (§6) a Task occupies at any point in time; a Task is a member of exactly one queue at once. |
| **Execution Slot** | A concrete, currently-available unit of Worker capacity the Scheduler can assign a Task to — the thing capacity-limited by concurrency controls (§7). |
| **Reservation** | A time-bounded claim on resources (§8) — token budget, cost budget, a specific Worker — made *before* dispatch, so two Tasks cannot be simultaneously assigned overlapping resources the Resource Coordinator (§3) has already promised elsewhere. |
| **Lease** | A time-bounded claim a Worker holds *during* execution of a specific Task, renewed by heartbeat (§11.5) and revocable on timeout (§13.2) — leases are how the Scheduler detects a Worker that has silently died versus one that is legitimately still working. |
| **Scheduling Cycle** | One pass of the Scheduler Loop (§3.9): drain completion signals, re-evaluate the dependency graph, populate the Ready Queue, dispatch what capacity allows. Cycles are the unit of reproducibility (§5.6) — a cycle's output is a pure function of its inputs. |
| **Dispatch** | The act of moving a Task from an Execution Slot reservation into an actual `dispatch()` call against the Execution Runtime contract (§11.1). |
| **Completion** | The terminal signal — success, failure, or cancellation — a Task receives back from the Execution Runtime (§11.2, §11.3), consumed by the next Scheduling Cycle. |

### 3.2 Framework

The "framework" here is the Scheduler Loop plus the six manager
components below it — collectively the only code path permitted to
transition a Task between queues (§6.5's invariant). Every manager is
narrow and single-purpose, mirroring the Policy Engine's
framework-vs-policy split (RFC-0003 §2.1): the Scheduler Loop knows how
to *sequence* manager calls; it does not itself contain scheduling
policy logic (fairness weights, retry backoff curves) — those live inside
the respective managers, replaceable independently, for the same reason
RFC-0003's built-in policies are replaceable independently of the
Policy Engine framework.

### 3.3 Queues

Covered fully in §6. Referenced here only to place them in the component
diagram: queues are passive data structures: they hold Tasks, they do not
themselves decide anything. All decision logic lives in the managers that
read and write them.

### 3.4 Dependency Manager

Tracks, for every Task, which upstream `PlanEdge`s (RFC-0001 §3,
`kind: "data" | "ordering"`) remain unsatisfied. A Task becomes eligible
to leave the Waiting Queue only when the Dependency Manager reports zero
unsatisfied edges — see §5.1 for the exact algorithm. The Dependency
Manager owns no queue itself; it answers a query
(`isReady(task) -> bool`) the Scheduler Loop calls per cycle.

### 3.5 Priority Manager

Combines a Task's static `priority` (from RFC-0001's `PlanNode`,
ultimately from RFC-0002's manifest `priority` field) with a **fairness
adjustment** (§5.3) to produce a per-cycle ordering over the Ready Queue.
This is the only component permitted to reorder the Ready Queue; the
Dependency Manager decides *membership*, the Priority Manager decides
*order*, and this separation is deliberate — conflating "is this task
allowed to run" with "in what order should allowed tasks run" was a
structural mistake this design specifically avoids repeating from RFC-0001
§8.2's Ranker/Constraint-Solver split, which the Scheduler mirrors on
purpose.

### 3.6 Concurrency Controller

Enforces the maximum-parallelism ceiling (global and per resource
dimension, §7.1) by answering `hasCapacity() -> bool` and
`reserve(task) -> Reservation | null` before the Dispatcher is permitted
to call `dispatch()`. It is the single point of truth for "how many
Tasks are currently in flight," which is what makes concurrency limits
enforceable without race conditions despite the Scheduler Loop being able
to process multiple Ready-Queue Tasks in one cycle (§3.9).

### 3.7 Dispatcher

The only component that calls into the Execution Runtime contract (§11).
It receives a Task plus a `Reservation` from the Concurrency Controller
and a `Lease` grant, and issues `dispatch()`. It has no decision-making
role of its own — every decision (is this Task ready, is it its turn, is
there capacity) has already been made upstream by the time the Dispatcher
is invoked. This is intentional: isolating the one component that talks
to an external system keeps that boundary thin and easy to test in
isolation (§16.1) and easy to swap for a different Execution Runtime
implementation later without touching scheduling logic.

### 3.8 Resource Coordinator

Tracks token budget, cost budget, memory, model availability, and rate
limits (§8) as a set of typed, reservable pools. `Reservation`s (§2) are
issued and released here — this component is the Scheduler-side
counterpart to the Policy Engine's `CostPolicy`/`ContextPolicy` (RFC-0003
§7.3/7.4): those policies decide whether a Task is *permitted* to consume
a given amount of budget; the Resource Coordinator decides whether that
budget is *currently available* to reserve. A Task can be policy-allowed
and still wait in the Blocked Queue (§6.3) because the Resource
Coordinator has no capacity right now — these are different questions
answered by different subsystems, on purpose.

### 3.9 Scheduler Loop

```
function schedulerLoop():
    while not shutdownRequested:
        drainCompletionSignals()          # §11.2/11.3, populate Retry/Completed/Blocked
        drainHeartbeats()                 # §11.5, renew or expire leases
        reEvaluateDependencies()          # §3.4, Waiting -> Ready transitions
        expireTimeouts()                  # §6, Timeout Queue -> Retry or Failed
        candidates = readyQueue.snapshot()
        ordered = priorityManager.order(candidates)     # §3.5
        for task in ordered:
            if not concurrencyController.hasCapacity(task): continue
            reservation = resourceCoordinator.reserve(task)
            if reservation is null: 
                moveToBlocked(task, reason="resource_unavailable")
                continue
            lease = leaseManager.grant(task, reservation)
            dispatcher.dispatch(task, lease)             # §3.7, §11.1
        sleepUntilNextSignal()            # event-driven wake, not busy-poll, §15.1
```

Each iteration of this loop is one Scheduling Cycle (§2). The loop itself
holds no scheduling policy — every decision is delegated to a named
manager — which is what makes the loop's own logic trivially testable in
isolation from any specific fairness or retry policy (§16.1).

### 3.10 Retry Manager

Consumes failure completions (§11.3) and a Task's attempt history,
producing either a re-enqueue into the Retry Queue with a computed
backoff delay, or a terminal `FAILED` determination. Explicitly does
**not** duplicate RFC-0003's `RetryPolicy` (which governs *whether*
retrying is permitted at all, and how many attempts) — the Retry Manager
only implements the *mechanics* of requeueing once `RetryPolicy` has
already said yes. This is the same "policy decides, mechanism executes"
split applied one level down.

### 3.11 Cancellation Manager

Propagates a cancellation signal (triggered by policy `DENY` post-dispatch
via continuous evaluation, RFC-0003 §6.4; by an operator; or by a
downstream Task's own irrecoverable failure making an upstream Task's
result moot) through the dependency graph — see §13.4 for the full
propagation algorithm. Owns no queue; it is the only component permitted
to move a Task directly to `CANCELLED` from any non-terminal state.

## 4. Scheduler State Machine

### 4.1 Task Lifecycle (Primary State Machine)

```
                schedule()
   IDLE -----------------------> PLANNING
                                     |
                          dependency check (§3.4)
                          +----------+----------+
                          |                     |
                    unmet deps            all deps met
                          v                     v
                      WAITING               READY
                          |                     |
                  deps become met        capacity + reservation
                          |               obtained (§3.6, §3.8)
                          +---------------------+
                                                 v
                                             RUNNING
                                                 |
                +--------------------------------+----------------------------+
                |                                |                            |
          success signal                  failure signal                cancellation
          (§11.2)                          (§11.3)                       signal (§13.4)
                v                                v                            v
           COMPLETED                    RetryPolicy check (RFC-0003 §7.8)   CANCELLED
                                          +----------+----------+
                                     retry permitted      retries exhausted
                                          v                        v
                                     RETRYING                    FAILED
                                          |
                                backoff elapses (§3.10)
                                          v
                                       READY (re-enters, attempt count += 1)

   Any of {WAITING, READY, RUNNING, RETRYING} --operator/policy pause--> PAUSED
   PAUSED --resume--> (returns to the state it was paused from)
   READY --resource unavailable (§3.8)--> BLOCKED
   BLOCKED --resource becomes available--> READY
```

### 4.2 Illegal Transitions

| Attempted transition | Why illegal |
|---|---|
| `COMPLETED -> anything` | Terminal — RFC-0001's determinism guarantee (§3, "same inputs, same plan") extends to "a completed Task's result is immutable"; re-running it would silently violate any downstream Task that already consumed its `produces` artifact |
| `FAILED -> RUNNING` directly | Must pass through `RETRYING` (or a fresh `schedule()` call constructing a new Task via RFC-0001's `reresolve()`, which is a *different* Task, not a resurrection of this one) — skipping `RETRYING` would bypass `RetryPolicy`'s attempt-count and backoff enforcement (RFC-0003 §7.8) |
| `CANCELLED -> anything` | Terminal by design — a cancelled Task's Worker-side effects (if any partial work occurred) are not assumed safely resumable; RFC-0004 (Execution Runtime, not yet designed, §0) will need to define whether cancellation is cooperative-with-partial-commit or hard-abort, but from the Scheduler's side `CANCELLED` is always terminal regardless of which |
| `IDLE -> RUNNING` (skipping `PLANNING`/`READY`) | Would bypass dependency checking entirely — the one invariant this RFC treats as non-negotiable (§5.1) |
| `WAITING -> RUNNING` (skipping `READY`) | Would bypass capacity/reservation checks (§3.6, §3.8) — a Task must always pass through a state where the Concurrency Controller and Resource Coordinator had the chance to say no |

### 4.3 Recovery Transitions

| From | Trigger | To |
|---|---|---|
| `BLOCKED` | Resource Coordinator reports newly available capacity (checked every cycle, §3.9) | `READY` |
| `RUNNING` (lease expired, no heartbeat, §11.5) | Lease timeout | `RETRYING` (treated identically to a failure signal — a silent Worker is indistinguishable from a failed one from the Scheduler's point of view, and must be, since distinguishing them would require trusting a signal that, by definition, didn't arrive) |
| `PAUSED` | Resume signal | Whichever state it was paused from (state is preserved, not reset, across a pause) |
| `RETRYING` | Backoff timer elapses | `READY` |
| `WAITING` | A `PlanEdge` dependency's producing Task completes | Re-evaluated by Dependency Manager (§3.4); moves to `READY` only if *all* dependencies, not just this one, are now satisfied |

## 5. Scheduling Algorithm

### 5.1 Dependency Resolution

The Scheduler consumes the `ExecutionPlan`'s edges (RFC-0001 §3, both
`kind: "ordering"` and `kind: "data"`) as a DAG and never re-derives
dependency structure itself — that structure was already correctly built
by RFC-0001's Plan Builder (RFC-0001 §8.4), including its cycle check. The
Scheduler's Dependency Manager only tracks *satisfaction state* over an
already-known-acyclic graph:

```
function isReady(task) -> bool:
    for edge in plan.edges where edge.to == task.node:
        producerTask = taskFor(edge.from)
        if producerTask.state != COMPLETED:
            return false
    return true
```

### 5.2 Topological Ordering

Populating the Ready Queue is, at its core, Kahn's algorithm applied
incrementally rather than as a single upfront pass — chosen over a single
static topological sort computed once at plan-acceptance time because the
graph's *satisfaction* state changes continuously as Tasks complete, and
an incremental in-degree-tracking approach (decrement a Task's unsatisfied
in-degree count as each dependency completes, enqueue at zero) is O(1)
amortized per completion event rather than O(V + E) recomputed per cycle:

```
function onTaskCompleted(task):
    for edge in plan.edges where edge.from == task.node:
        dependent = taskFor(edge.to)
        dependent.unsatisfiedDeps -= 1
        if dependent.unsatisfiedDeps == 0 and dependent.state == WAITING:
            moveToReady(dependent)
```

### 5.3 Priority Scheduling

Within the Ready Queue, ordering is `priority` (RFC-0001/0002's four-tier
enum) first, then a fairness adjustment (§5.4), then insertion order as a
final deterministic tie-break — never wall-clock arrival time alone, which
would make ordering depend on incidental timing rather than declared
priority, breaking the reproducibility requirement (§5.6).

### 5.4 Fair Scheduling / Starvation Prevention

A pure strict-priority scheduler risks starving `low`/`medium` priority
Tasks indefinitely under sustained `critical`/`high` load. The fairness
adjustment applies a **weighted aging factor**: a Task's effective
priority for ordering purposes increases the longer it has waited in the
Ready Queue, using a bounded, deterministic function of wait time — not a
random or load-dependent one, again for reproducibility:

```
function effectivePriority(task, currentCycle):
    base = priorityWeight[task.priority]        # critical=1000, high=100, medium=10, low=1
    agingBonus = min(base - 1, floor((currentCycle - task.readyCycle) / agingInterval))
    return base + agingBonus
```

The `min(base - 1, ...)` cap guarantees aging can never let a `low`
Task's effective priority reach or exceed a `critical` Task's *base*
weight — starvation prevention is bounded, it does not invert the
priority ordering the source spec establishes as authoritative
(RFC-0003 §8.2's "safety is not democratically overridable" reasoning
applies here too: fairness must never let accumulated wait time override
a genuinely higher-priority Task).

### 5.5 Work Stealing

Within a single Worker pool of homogeneous capacity, work stealing is
unnecessary — the Dispatcher already assigns from a single ordered Ready
Queue to any available Execution Slot, which is optimal by construction
for a shared queue. Work stealing becomes relevant only across
*heterogeneous* pools (§7.5, e.g. a pool sized for `estimatedLatency: fast`
Tasks separate from one sized for `slow` Tasks) — an idle fast-pool Worker
may steal a Ready Task queued for the slow pool if no slow-pool Worker is
available and the fast-pool Worker's own queue is empty, using a
randomized-victim work-stealing deque (the standard choice for stealing
under contention) **only within a single Scheduling Cycle's already-
computed Ready ordering** — stealing never reorders priority, it only
reassigns *which* idle slot picks up the next-highest-priority ready Task
when the "natural" pool for that Task has no capacity.

### 5.6 Critical Path Optimization

Among Ready Tasks of equal effective priority (§5.4), the Priority
Manager breaks the tie by preferring the Task with the **longer remaining
downstream critical path** — the longest chain of dependent Tasks still
unexecuted, computed once when the plan is accepted (a static property of
the DAG, not something that changes per cycle, so this is cheap: computed
once via a single reverse-topological pass at plan-acceptance time, not
recomputed per cycle):

```
function criticalPathLength(node, plan):
    dependents = [e.to for e in plan.edges if e.from == node]
    if dependents.isEmpty(): return 1
    return 1 + max(criticalPathLength(d, plan) for d in dependents)
```

Preferring longer-critical-path Tasks when priority ties minimizes
expected plan makespan — a Task that blocks a long downstream chain
should not sit idle behind a Task of equal priority that blocks nothing,
since delaying the former delays everything after it while delaying the
latter delays nothing.

### 5.7 Backpressure

When the Ready Queue's size exceeds a configured high-water mark (a
symptom of the Concurrency Controller or Resource Coordinator being a
persistent bottleneck relative to plan fan-out, §7.3), the Scheduler
applies backpressure **upstream**, toward RFC-0001's Resolver, by
declining to accept newly-resolved plan nodes into `PLANNING` until the
Ready Queue drains below a low-water mark — implemented as
`schedule()` (§4.1) blocking or returning a `BACKPRESSURE` signal rather
than silently queueing unboundedly. This bounds Scheduler memory (§15.2)
and gives the Resolver an explicit signal it can use to throttle further
resolution rather than resolving work the Scheduler has no near-term
capacity to run.

### 5.8 Why This Algorithm, Not Something Simpler

Kahn's-algorithm-based incremental readiness plus weighted-priority-with-
bounded-aging plus critical-path tie-breaking is more machinery than a
plain FIFO or a plain priority queue. It is justified by the combination
of three requirements the source spec states as hard: dependency-aware
(rules out plain FIFO/priority-queue-without-DAG-awareness), fairness/
starvation-prevention (rules out plain strict-priority), and reproducible
determinism (rules out anything involving real-time arrival order or
randomized tie-breaking). §17 compares each rejected simpler alternative
explicitly against these three requirements.

## 6. Queue Design

### 6.1 The Six Queues

| Queue | Membership condition | Populated by | Drained by |
|---|---|---|---|
| **Ready** | Dependencies satisfied, policy-cleared, not yet capacity-checked this cycle | Dependency Manager (§3.4) | Dispatcher, via Concurrency Controller + Resource Coordinator (§3.9) |
| **Waiting** | Dependencies not yet satisfied | Initial `schedule()` call, or a Task returning from `RETRYING` whose upstream dependency was itself retried | Dependency Manager, on upstream completion (§5.2) |
| **Blocked** | Dependencies satisfied but resource/capacity unavailable | Concurrency Controller / Resource Coordinator, when `reserve()` fails (§3.9) | Resource Coordinator, when capacity frees (§4.3) |
| **Retry** | Failed, `RetryPolicy`-permitted, awaiting backoff | Retry Manager (§3.10) | Retry Manager, when backoff elapses |
| **Timeout** | Dispatched, lease outstanding, awaiting completion or lease expiry | Dispatcher, at dispatch time | Scheduler Loop, on completion signal or lease expiry (§3.9, §13.2) |
| **Completed** | Terminal — `COMPLETED`, `FAILED`, or `CANCELLED` | Any terminal transition (§4.1) | Never drained during the plan's lifetime — retained for audit/checkpoint (§12) until plan-level cleanup |

### 6.2 Why Six, Not Fewer

`Blocked` and `Waiting` are kept distinct despite both being "not
currently runnable," because they have different *recovery triggers*
(dependency completion vs. resource availability) and conflating them
would force the Scheduler Loop to re-check both conditions for every
non-ready Task every cycle, instead of only checking the specific
condition relevant to why that Task isn't ready — this is a direct
performance consequence (§15.4), not merely a taxonomic preference.
`Timeout` is kept distinct from `Retry` because a Task in `Timeout` might
still complete successfully (the completion signal simply hasn't arrived
yet) — moving it straight to `Retry` before the lease actually expires
would be premature.

### 6.3 Queue Invariants

- A Task is a member of **exactly one** queue at any instant — enforced by
  the framework (§3.2) being the sole mutator of queue membership; no
  manager ever adds a Task to a queue without first confirming (and, in
  the same atomic operation, executing) its removal from whichever queue
  it currently occupies.
- The **Ready Queue is always priority-ordered** as of the start of each
  Scheduling Cycle (§3.9) — order is recomputed at the start of dispatch
  within a cycle, not maintained incrementally as a always-sorted
  structure, because recomputation over a bounded Ready Queue size (kept
  bounded by backpressure, §5.7) is cheaper and simpler than maintaining
  sort invariants under concurrent insertion.
- **No queue transition skips validation** implied by §4's state machine —
  every queue-membership change is a Task state transition, and every
  Task state transition is checked against §4.1/§4.2's legal-transition
  table before it is applied, at the framework level, not trusted to each
  manager individually to get right.

## 7. Parallel Execution

### 7.1 Maximum Concurrency

Two independent ceilings, both enforced by the Concurrency Controller
(§3.6): a **global** max-in-flight count (bounding total Worker usage
across the whole plan) and a **per-priority-tier** max (preventing a burst
of `low`-priority Ready Tasks from consuming all global capacity and
starving a `critical` Task that becomes ready mid-burst — this is a second,
independent starvation-prevention mechanism alongside §5.4's aging,
operating on concurrency rather than ordering).

### 7.2 Dependency Barriers

A `PlanEdge` with `kind: "ordering"` (RFC-0001 §3) acts as a hard barrier:
the dependent Task cannot even enter `READY` (§4.1, §5.1) until every
ordering-predecessor is `COMPLETED`. `kind: "data"` edges are barriers in
the identical mechanical sense but additionally imply artifact
availability (the dependent needs the actual produced artifact value, not
just a completion signal) — from the Scheduler's perspective these are
handled identically (§5.1's `isReady` does not distinguish edge kind for
readiness purposes); the *data* itself flows through the Artifact
Registry (a Kernel component referenced in `AGY_HANDOFF.md`'s Current
Open Questions, not yet designed, §0), not through the Scheduler, which
only ever tracks completion state, never artifact payloads.

### 7.3 Fan-Out

A Task with multiple downstream dependents (multiple `PlanEdge`s with the
same `from`) simply results in multiple Tasks having their `unsatisfiedDeps`
decremented on that Task's completion (§5.2) — fan-out requires no special
handling beyond what the incremental readiness algorithm already does.
The scheduling-relevant consequence is a potential burst of Tasks entering
`READY` simultaneously, which is exactly what §5.7's backpressure and
§7.1's concurrency ceilings exist to absorb without unbounded queue growth
or unbounded concurrent dispatch.

### 7.4 Fan-In

A Task with multiple upstream dependencies (multiple `PlanEdge`s with the
same `to`) only becomes `READY` when *all* of them complete (§5.1's `for`
loop over all matching edges) — fan-in is a natural consequence of the
same mechanism, not a separate code path. The one Scheduler-relevant
nuance: if any one of the fan-in predecessors terminates in `FAILED` or
`CANCELLED` rather than `COMPLETED`, the fan-in Task can never become
ready by the letter of §5.1's algorithm (it explicitly checks for
`COMPLETED`, not "terminal") — this is deliberate, and its handling is
specified in §13.3 (Dependency Failure) rather than silently left to
`isReady()`'s literal behavior, since a fan-in Task waiting forever on a
predecessor that will never complete is a real failure mode requiring
explicit propagation, not an accident of the readiness check.

### 7.5 Worker Pools

The Scheduler is agnostic to *how many* Worker pools exist or what
distinguishes them (§2's Worker definition is deliberately abstract) —
pool partitioning (e.g. by `estimatedLatency` class, by model
availability, by geographic/cloud placement in a distributed deployment,
§14) is a Concurrency Controller configuration concern, not a scheduling-
algorithm concern. The algorithm in §5 operates identically regardless of
pool count; only §5.5's work-stealing behavior is pool-count-aware.

### 7.6 Dynamic Scaling

Worker pool capacity is not assumed fixed. The Concurrency Controller
exposes `reportCapacityChange(pool, delta)`, called by whatever manages
actual Worker provisioning (out of this RFC's scope — a Resource Manager
concern per `AGY_HANDOFF.md`'s architecture list) — the Scheduler reacts
to capacity changes (more Blocked-Queue Tasks becoming dispatchable) but
does not itself decide to scale Worker pools up or down. This mirrors
RFC-0003's boundary discipline exactly: the Scheduler evaluates neither
resource policy nor resource provisioning, only resource *availability as
reported to it*.

### 7.7 Synchronization

No two Scheduler components share mutable state without going through the
framework's single write path (§3.2, mirroring RFC-0002 §4.5's
coarse-grained-lock reasoning) — the same tradeoff, for the same reason:
Scheduling Cycles are not a sufficiently high-frequency, high-contention
operation (bounded by cycle rate, §15.1) to justify fine-grained locking
complexity at this design's current scale target. This is flagged in
§18.2 as a scalability limit worth revisiting, not asserted as
permanently sufficient.

## 8. Resource Scheduling

### 8.1 Resource Dimensions

| Dimension | Source of truth for limit | Source of truth for current usage |
|---|---|---|
| Token budget | RFC-0003's `ContextPolicy` (ceiling), `RuntimeState.conversationTokens` for current level | Execution Runtime completion signals report actual token consumption per Task (§11.2) |
| Cost/monetary budget | RFC-0003's `CostPolicy` | Execution Ledger (Kernel component, referenced but not designed) via `PolicyContext.ledger` (RFC-0003 §9.2) — Scheduler reads a Resource Coordinator-cached view, not the ledger directly |
| Memory | Resource Manager (Kernel component, not designed) | Worker-reported at heartbeat (§11.5) |
| Model availability | Model Router (RFC-0001 skill, `gemini-skill`-style delegation) selects a model; Scheduler only needs to know *if* the selected model's capacity pool has room, not which model was selected | Rate-limit/availability signal reported by the Execution Runtime per pool |
| Rate limits | External API/provider-imposed, tracked per pool | Sliding-window counter maintained by the Resource Coordinator |
| Worker capacity | §7.6 dynamic scaling reports | Concurrency Controller's live in-flight count |

### 8.2 Reservation Strategy

**Optimistic reservation with a short hold window**, not pessimistic
locking: the Resource Coordinator grants a `Reservation` the instant
before dispatch (§3.9's loop), valid only until the Dispatcher actually
calls `dispatch()` within the same cycle — if dispatch doesn't happen
within that window (e.g. the Dispatcher itself is momentarily saturated),
the reservation expires and must be re-requested next cycle. This
avoids holding resource claims across cycle boundaries for Tasks that
haven't actually started, which would otherwise let a burst of
reservations from one cycle starve resource availability for Tasks in a
later cycle that are equally or more deserving under §5.3/§5.4's ordering.

A reservation held *during* execution (post-dispatch) is the Lease (§2),
a distinct and longer-lived claim, released only on completion, failure,
or lease expiry (§4.3) — the Reservation/Lease split exists because
pre-dispatch resource availability and in-flight resource consumption are
different questions with different lifetimes, and conflating them would
make it impossible to distinguish "waiting for a slot" from "currently
consuming a slot" when reasoning about resource pressure (§13.7's retry
storm handling depends on this distinction).

## 9. Policy Integration

### 9.1 Contract

The Scheduler receives exactly one `PolicyDecision` per Task before it is
first permitted to leave `PLANNING` for `WAITING`/`READY`, and,
separately, may receive further `PolicyDecision`s during `RUNNING` via
RFC-0003 §6.4's continuous evaluation. **The Scheduler never calls
`IPolicyEngine.evaluateNode`/`evaluatePlan` itself and never inspects a
`PolicyContext`** — RFC-0003 §14's `IPolicyEngine` interface is called by
whatever hands the Scheduler a plan (a Kernel orchestration layer above
both, out of this RFC's scope, or the Resolver/Policy Engine pairing
directly), and the Scheduler is handed the *result* only. This is the
literal enforcement of the design constraint "Policy Engine must never
schedule" from the opposite direction: the Scheduler must never evaluate
policy either — the boundary is symmetric and both halves are enforced
here.

### 9.2 Handling Each Outcome

| Outcome | Scheduler behavior |
|---|---|
| `ALLOW` | Task proceeds through `PLANNING -> WAITING/READY` unchanged |
| `MODIFIED` | Task proceeds, but the Scheduler applies `PlanNodeModification`'s `budgetCeiling` fields directly into the Resource Coordinator's per-Task reservation limits (§8.2) — this is the one place `MODIFIED` has scheduling-visible effect; `permissionSubset` and `forcedEscalateTo` (RFC-0003 §5.2) are not scheduling concerns and are passed through untouched to whatever reads them downstream (Execution Runtime for permissions; back to the Resolver for `forcedEscalateTo`, which is a re-resolution trigger, not something the Scheduler acts on directly) |
| `DENY` | Task never enters `WAITING`/`READY` — moved directly from `PLANNING` to `FAILED` with reason `PolicyDenied`, which (per RFC-0003 §8.4) is handed back to the Resolver's `reresolve()` exactly as an execution failure would be; the Scheduler's role ends at surfacing this, it does not itself attempt fallback |
| `ESCALATE` | Task moves to `PAUSED` (§4.1, §4.3) with a scheduling-visible reason distinct from an operator- or policy-triggered pause — the Scheduler does not resolve the escalation (RFC-0003 §5.3's `EscalationTarget` is not a Scheduler concept); it only holds the Task paused until an external resume signal arrives, identical mechanically to any other `PAUSED` recovery transition (§4.3) |
| `DEFER` | Not a state the Scheduler ever observes directly — per RFC-0003 §8.1, an all-`DEFER` applicable set resolves to `ALLOW` before the Scheduler ever sees a decision; `DEFER` is purely internal to Policy Engine aggregation |

### 9.3 Continuous Evaluation Mid-Execution

A `DENY` arriving via RFC-0003 §6.4 while a Task is `RUNNING` is handled
by the Cancellation Manager (§3.11), not treated as a `PLANNING`-stage
denial — the Task is already dispatched, so this is a cancellation
request against the Execution Runtime contract (§11.4), not a queue
transition that was never allowed to happen.

## 10. Runtime Integration

### 10.1 Reads

The Scheduler reads `RuntimeState` (RFC-0001 §3's type) fields relevant
to scheduling decisions — `conversationTokens` (for §8.1's token
dimension), `priorFailures` (informs §3.10's Retry Manager attempt-count
context) — as a point-in-time snapshot per cycle, the same read-only
discipline RFC-0001's own Resolver applies to its `RuntimeState` input
(RFC-0001 §4: "the resolver never mutates state; it only reads it").

### 10.2 Allowed Mutations

**None, directly.** The Scheduler does not write to `RuntimeState`. Every
observable effect of scheduling activity on `RuntimeState` (token
consumption, cost accrual) happens because the Execution Runtime reports
it back through the completion contract (§11.2), and whatever owns
`RuntimeState` (a Kernel state-management concern outside this RFC's
scope — plausibly Checkpoint Manager or a dedicated state-owning
component not yet named in `AGY_HANDOFF.md`) applies that update. This
mirrors RFC-0001 §4's stated design exactly and is a direct instance of
the working design constraint "RuntimeState must never schedule" applied
in its complementary form: the Scheduler must never *own* RuntimeState
mutation either.

### 10.3 Forbidden Mutations

The Scheduler never writes `RuntimeState.availableArtifacts` — even
though artifact availability is exactly the kind of signal that looks
like it belongs to scheduling (it gates `kind: "data"` edges, §7.2), the
actual artifact value and the bookkeeping of "which artifacts now exist"
belongs to the not-yet-designed Artifact Registry, referenced in
`AGY_HANDOFF.md`. The Scheduler tracks only *completion*, a boolean-ish
signal (§5.1); it deliberately does not become a second source of truth
for artifact existence, which would create exactly the kind of dual-
ownership inconsistency risk RFC-0002 §4.5 warned against for its own
index consistency.

## 11. Execution Runtime Integration

**This entire section is a contract specification this RFC requires,
not a description of an accepted, existing interface** — see §0. Anything
here should be read as "whatever RFC-0004 designs must satisfy this,"
not "RFC-0004 already satisfies this."

### 11.1 Dispatch Contract

```typescript
interface IExecutionRuntime {
  dispatch(task: Task, lease: Lease): Promise<DispatchAck>;
  cancel(taskId: string, lease: Lease): Promise<CancelAck>;
  heartbeat(taskId: string): Promise<HeartbeatAck>;
}

interface DispatchAck {
  taskId: string;
  workerId: string;
  acceptedAt: Timestamp;
}
```

`dispatch()` must return a `DispatchAck` synchronously-enough to be
awaited within a single Scheduling Cycle (§3.9) — actual Task execution
is asynchronous and reported later via the completion contract (§11.2);
`dispatch()` itself only confirms the Execution Runtime has accepted
responsibility for the Task and assigned it a `workerId`. A Task whose
`dispatch()` call fails outright (Execution Runtime unreachable, rejected)
is treated as an immediate failure signal (§11.3), entering the Retry
Manager exactly as a post-execution failure would.

### 11.2 Completion Contract

```typescript
interface CompletionSignal {
  taskId: string;
  status: "success";
  producedArtifacts: ArtifactRef[];
  resourceUsage: { tokens: number; cost: number; durationMs: number };
  observedConfidence: number | null;   // feeds RFC-0003's ConfidencePolicy continuous evaluation
}
```

The Scheduler requires this signal to be **idempotent-safe to receive
more than once** for the same `taskId` (at-least-once delivery, matching
the delivery semantics already established for RFC-0002 §13.2 and
RFC-0003 §10's event buses, applied here to the Scheduler-Execution
Runtime boundary for consistency across every asynchronous boundary in
AGY) — a duplicate completion signal for an already-`COMPLETED` Task is a
no-op, not an error, and specifically not a `COMPLETED -> anything`
transition attempt that would trip §4.2's illegal-transition table.

### 11.3 Failure Contract

```typescript
interface FailureSignal {
  taskId: string;
  status: "failure";
  reason: string;
  partialResourceUsage: { tokens: number; cost: number; durationMs: number };
  retryable: boolean;   // Execution Runtime's own opinion; Scheduler still consults
                          // RetryPolicy (RFC-0003 §7.8) independently, this field is
                          // advisory input, not a binding decision (mirrors RFC-0002
                          // §5.7's "Loader exposes state, caller decides whether to retry")
}
```

### 11.4 Cancellation Contract

`cancel()` (§11.1) is fire-and-forget from the Scheduler's perspective in
the sense that the Scheduler does not block waiting for cancellation to
take effect — it immediately transitions the Task to `CANCELLED` (§4.1)
on *issuing* the cancel request, trusting the Execution Runtime to
actually stop work asynchronously. This is a deliberate choice: making
`CANCELLED` conditional on the Execution Runtime confirming would leave
the Task in an ambiguous, non-terminal state for however long that
confirmation takes, during which the Cancellation Manager's downstream
propagation (§13.4) would be blocked on a signal that is, by definition,
not scheduling-relevant once the intent to cancel has been recorded.

### 11.5 Heartbeat Contract

`heartbeat()` is polled by the Scheduler Loop (§3.9's `drainHeartbeats`)
at a configurable interval per in-flight Lease; failure to receive a
heartbeat within `leaseTimeout` (default: 3x the heartbeat interval, to
tolerate transient delay without false-positive timeout) triggers §4.3's
lease-expiry recovery transition, treating the Task as failed without
waiting for an explicit failure signal that, given the Worker is
unresponsive, will likely never arrive.

## 12. Checkpoint Integration

### 12.1 What the Scheduler Checkpoints

Following RFC-0001 §4's "resolver is stateless, checkpointing is the
caller's concern" precedent, extended here since the Scheduler is *not*
stateless (it holds live queue membership and in-flight leases) —
checkpointing is genuinely load-bearing for the Scheduler, not merely an
optimization the way it was for the Resolver:

```typescript
interface SchedulerCheckpoint {
  planId: string;
  taskStates: Map<string, TaskState>;      // full state machine position per Task
  queueSnapshots: { ready, waiting, blocked, retry, timeout, completed };
  attemptCounts: Map<string, number>;
  reservations: Reservation[];              // in-flight only, not historical
  checkpointedAtCycle: number;
}
```

### 12.2 When

A checkpoint is taken at the **end of every Scheduling Cycle** whose
Ready Queue processing resulted in at least one state transition — not
every cycle unconditionally (a cycle that only drained heartbeats with no
state change produces an identical checkpoint, wasteful to persist,
mirroring RFC-0001 §4's "checkpoint after verified subtask" principle:
checkpoint at meaningful state boundaries, not on a fixed timer
divorced from actual progress).

### 12.3 Recovery

On restart, the Scheduler reconstructs queue membership entirely from the
last `SchedulerCheckpoint` rather than re-deriving it from the
`ExecutionPlan` and `RuntimeState` from scratch — unlike RFC-0001's
Resolver (which is cheap enough to fully recompute), the Scheduler's
in-flight `Lease`/`Reservation` state is not reconstructible from the
plan alone (a Lease represents a live claim against an external Execution
Runtime that the plan itself has no record of), so the checkpoint here is
a correctness requirement, not merely a performance optimization.

### 12.4 Resume

Any Task recorded as `RUNNING` in the restored checkpoint is *not*
assumed still actually running — its Lease is immediately treated as
expired (§4.3's lease-expiry recovery transition fires unconditionally
for every `RUNNING` Task on resume), moving it to `RETRYING` pending
`RetryPolicy` evaluation. This is the safe default: assuming a Task
survived an unclean Scheduler restart would require the Execution Runtime
to independently confirm it, which the dispatch contract (§11) does not
promise across a Scheduler restart boundary — better to retry idempotent
work than to silently lose track of non-idempotent work believed
complete when it was not.

### 12.5 Partial Replay

A checkpoint restored mid-plan does not replay the *entire* plan from
`PLANNING` — only Tasks in non-terminal states at checkpoint time are
reconstructed into their recorded queue; `Completed`-Queue Tasks are
restored as-is with no re-execution, preserving their produced artifacts
(read from the Artifact Registry, not the Scheduler's own checkpoint,
per §10.3's ownership boundary) as valid inputs for any Task that
depends on them.

## 13. Failure Handling

| Failure | Detection | Recovery |
|---|---|---|
| **Worker crash** | Lease timeout (§4.3, §11.5) — no heartbeat within `leaseTimeout` | Task -> `RETRYING`, `RetryPolicy`-gated (§3.10); if the same Worker (by `workerId`) accumulates repeated crash-pattern timeouts, the Concurrency Controller marks that Worker's slot unavailable pending external health-check, out of this RFC's scope |
| **Timeout** (Worker alive, heartbeating, but Task itself exceeds a configured max-duration) | Distinct from lease timeout: a separate, longer, Task-specific duration limit checked against `dispatchedAt` | Cancellation issued (§11.4) then treated as a failure signal, `RetryPolicy`-gated identically to any other failure |
| **Dependency failure** (§7.4's fan-in gap) | A fan-in Task's upstream predecessor terminates `FAILED`/`CANCELLED` rather than `COMPLETED` | The fan-in Task is transitioned directly to `FAILED` with reason `UpstreamDependencyFailed` — it never silently waits forever; this is the explicit handling §7.4 flagged as required rather than left to `isReady()`'s literal behavior |
| **Deadlock** (a genuine cycle would deadlock the DAG traversal, but RFC-0001 §8.4 already guarantees acyclicity — so this reduces to detecting a *resource*-level deadlock: two Tasks each holding a Reservation the other needs) | Resource Coordinator tracks reservation-wait chains; a wait-for cycle among Reservations (not Tasks — the DAG itself cannot cycle) is detected via periodic cycle-check over the wait-for graph | Break the cycle deterministically: the lowest-priority Reservation-holder in the cycle is preempted (its Reservation released, Task returned to `BLOCKED`) — deterministic tie-break identical in spirit to §5.4's aging cap, so preemption choice is itself reproducible |
| **Livelock** (Tasks repeatedly entering/leaving `BLOCKED` without net progress, e.g. two resource-hungry Tasks perpetually pre-empting each other under §13's deadlock-breaking rule) | A Task whose `BLOCKED <-> READY` transition count exceeds a threshold within a bounded cycle window | Escalated to a policy-analog decision: the Task is forcibly held `BLOCKED` for a minimum cooldown period (breaking the oscillation) rather than immediately re-contending — a scheduling-level circuit breaker |
| **Queue corruption** (a Task found in queue membership inconsistent with its recorded state — a framework bug, not an external input problem) | Consistency assertions at the framework's single write path (§3.2, §6.3), mirroring RFC-0002 §16's treatment of registry corruption exactly | Not repaired in place, by the same reasoning RFC-0002 §16 gives for its own analogous case: restore from the last `SchedulerCheckpoint` (§12.3) rather than attempt runtime self-repair of a data structure whose own consistency guarantee has already been shown to be violated |
| **Lost heartbeat** | Covered under Worker crash above — this is the detection mechanism, not a distinct failure class |
| **Retry storms** (many Tasks failing and retrying simultaneously, e.g. a shared downstream dependency — a model provider, a rate-limited API — degrading and causing a burst of correlated failures) | Retry Manager tracks failure *rate*, not just per-Task attempt count — a spike in failures across unrelated Tasks within a short window is a distinct signal from an individual Task's own retry history | Applies a global backoff multiplier across all Retry-Queue Tasks sharing a detected correlated-failure signature (e.g. same `reason` string, same target pool) rather than retrying each independently at its own schedule — this is the Scheduler-level analog of a circuit breaker, preventing a struggling downstream dependency from being hammered by dozens of Tasks retrying on independent, uncoordinated timers |

## 14. Distributed Scheduling

### 14.1 Scope of This Section

Per the design constraints ("support local, distributed, cloud,
multi-model, multi-agent execution without redesign" while "avoid
speculative abstraction — every abstraction must justify its existence"),
this section designs the **extension points** a distributed deployment
would need, without designing a full distributed consensus system now,
for which there is no current concrete requirement (matching RFC-0001
§15's and RFC-0002 §20's identical "no evidence yet" deferral reasoning).

### 14.2 Multiple Schedulers

The architecture in §3 is written entirely against abstract `Queue`,
`Worker`, and `Reservation` concepts with no assumption of single-process
memory — this is the specific abstraction that "justifies its existence"
under the design constraint: a distributed deployment runs multiple
Scheduler Loop instances (§3.9), each owning a **partition** of the
overall Ready Queue (partitioned by plan, by resource pool, or by
priority tier — a deployment-time choice, not fixed by this RFC), rather
than one Scheduler instance trying to serialize all scheduling decisions
globally.

### 14.3 Leader Election Assumptions

Cross-instance coordination — specifically, assigning which Scheduler
instance owns which partition, and reassigning on instance failure —
is **assumed to be provided by an external coordination primitive** (a
leader-election/consensus system such as etcd/Raft or an equivalent), not
designed within this RFC. This RFC's contract with that external system
is narrow: a Scheduler instance must be able to determine "am I currently
the owner of partition P," and must correctly relinquish/re-acquire
ownership on that signal changing — the Scheduler Loop (§3.9) simply does
not run for a partition it does not currently own.

### 14.4 Worker Registration

Workers (§2) register with the Resource Coordinator (§3.8) via a
`registerWorker(workerId, pool, capacity)` call — analogous in spirit to
RFC-0002 §6's Discovery, but for execution capacity rather than skill
packages: a Worker's presence is discovered/declared, not assumed static,
which is what makes §7.6's dynamic scaling and §14.2's multi-instance
partitioning both work against the same underlying registration
mechanism rather than two separate ones.

### 14.5 Leases and Heartbeat at Distributed Scale

§11.5's heartbeat contract is unchanged in a distributed deployment — a
Lease is always owned by exactly one Scheduler-instance/Worker pair, and
lease timeout detection (§4.3) works identically whether the Worker is
local or remote, since the contract was already defined in terms of a
signal arriving or not, never in terms of shared memory.

### 14.6 Load Balancing

Cross-partition load balancing (one Scheduler instance's partition
consistently more loaded than another's) is explicitly **not** solved by
work-stealing (§5.5, which is scoped to within a single instance's pool
set) — it is a partition-rebalancing decision made by the external
coordination layer (§14.3), informed by each instance reporting its own
Ready Queue depth and utilization as a metric, not by instances directly
negotiating work transfer with each other (which would reintroduce
cross-instance shared mutable state, the exact thing §7.7's
single-instance locking discipline was chosen to avoid, now at a harder,
network-partition-prone scale).

### 14.7 Future Distributed Roadmap

Full multi-instance partition rebalancing, cross-partition critical-path
optimization (§5.6 currently only reasons within one instance's visible
DAG subgraph), and genuinely distributed deadlock detection (§13's
resource wait-for-graph cycle check assumes a single, consistent view of
reservations, which a partitioned deployment would need to make
eventually-consistent or centralize) are named here as concrete,
identified future work rather than designed — flagged the same way
RFC-0002 §20 and RFC-0003 §19 flag genuinely deferred capability, not
glossed over as if solved by §14.2–14.6's extension points alone.

## 15. Performance

### 15.1 Scheduling Latency

The Scheduler Loop (§3.9) is event-driven (`sleepUntilNextSignal`), not a
fixed-interval poll — woken by completion signals, heartbeats, timers
(backoff expiry, lease timeout), and new-plan acceptance. Target:
end-to-end latency from "a Task's last dependency completes" to
"that Task is dispatched" under available capacity: **< 10ms**, dominated
by one Scheduling Cycle's fixed-cost stages (§15.4), not by any polling
interval.

### 15.2 Memory

Bounded primarily by the Ready Queue high-water mark (§5.7's
backpressure) and total plan size (Waiting/Blocked/Retry/Timeout queues
are all bounded by total Task count, itself bounded by RFC-0001's
resolved plan size, typically single-to-low-double digits per RFC-0001
§12's stated typical plan size). The Completed Queue (§6.1) is the one
queue that grows unboundedly over a long-running plan's lifetime — its
retention policy (how long completed Task records are kept before
archival) is a configuration concern outside this RFC's default scope,
flagged in §18.2.

### 15.3 Queue Complexity

| Operation | Complexity |
|---|---|
| `isReady()` check (§5.1) | O(in-degree of the Task), amortized O(1) via §5.2's incremental in-degree tracking rather than a full edge scan per check |
| Ready Queue priority ordering (§5.3–5.6) | O(n log n), n = Ready Queue size, recomputed per cycle (§6.3) — bounded by backpressure (§5.7) so n stays small in practice |
| Dispatch loop (§3.9's `for task in ordered`) | O(n) per cycle, n = Ready Queue size after ordering |
| Dependency-satisfaction propagation on completion (§5.2) | O(out-degree of the completed Task) |
| Deadlock cycle check (§13) | O(V + E) over the *reservation* wait-for graph (not the plan DAG), run periodically, not every cycle — bounded by in-flight Reservation count, typically much smaller than total plan size |

### 15.4 Contention

The framework's single write path (§3.2, §7.7) is the one deliberate
contention point in this design, justified in §7.7 and revisited
critically in §18.2 — expected acceptable at current scale (bounded plan
sizes, bounded Ready Queue via backpressure) but explicitly named as the
first place to look if real-world contention measurements contradict that
expectation.

### 15.5 Scaling

Vertical (larger single-instance capacity via more Worker pools, §7.5) is
supported without any architectural change. Horizontal (multiple
Scheduler instances, §14) is supported via the partitioning extension
points named in §14, but genuinely distributed rebalancing/deadlock
detection remains future work (§14.7) — scaling beyond a single
instance's partition today means running more partitions, each still
independently bounded by this section's single-instance characteristics.

### 15.6 Optimization Opportunities

Not designed now (would be premature optimization ahead of real
measurement, consistent with Design Principle #3 applied throughout the
prior RFCs): incremental (rather than full-recompute) Ready Queue
ordering if `n` in §15.3 grows large enough for O(n log n) per cycle to
matter in practice; a persistent priority-queue data structure with
O(log n) insert/extract-min instead of full resort, if profiling shows
the current approach as a bottleneck.

## 16. Testing Strategy

### 16.1 Unit Tests

Every manager (§3.4–3.11) tested in isolation against synthetic Task
sets and mocked upstream/downstream contracts (mocked `IPolicyEngine`
decisions, mocked `IExecutionRuntime` responses) — mirroring RFC-0002
§17.1/RFC-0003 §15.1's fixture-based unit testing discipline, applied to
each Scheduler manager independently, exactly because §3.7's Dispatcher
isolation and §3.2's framework/manager separation were explicitly
designed to make this possible.

### 16.2 Stress Tests

Large synthetic `ExecutionPlan`s (wide fan-out/fan-in, deep dependency
chains, mixed priority distributions) run against the full Scheduler Loop
under the §15 performance targets, verifying latency and memory
characteristics hold at scale, not just correctness.

### 16.3 Concurrency Tests

Targeted at §7.7/§15.4's single deliberate contention point: many
simultaneous completion signals, heartbeats, and new-plan acceptances
dispatched concurrently against a live Scheduler instance, asserting the
framework's single-write-path invariant (§6.3: exactly-one-queue
membership) is never violated under load.

### 16.4 Chaos Testing

Randomized injection of: dropped/delayed heartbeats, out-of-order
completion signals, duplicate completion signals (§11.2's required
idempotency, directly tested), simulated Worker crashes mid-lease, and
simulated Scheduler-instance restart mid-cycle (§12.3–12.5's recovery
path exercised under realistic, not just clean, failure timing).

### 16.5 Determinism Testing

Direct analog to RFC-0001 §11's golden plans and RFC-0003 §15.5's
decision determinism tests, applied to scheduling order: identical
`(ExecutionPlan, PolicyDecision set, RuntimeState snapshot, resource
availability sequence)` inputs, run multiple times (including with
artificially randomized internal event-arrival ordering within a cycle),
must produce byte-identical dispatch ordering — this is the single most
important test category given §5's stated reproducibility requirement,
and is treated with the same weight RFC-0003 §15.6 gave its own
highest-value test suite.

### 16.6 Deadlock Testing

Constructed fixture scenarios specifically designed to trigger §13's
resource-level wait-for cycle (not DAG cycles, which RFC-0001 already
prevents structurally) — asserting both that the cycle is detected within
a bounded number of cycles and that the deterministic preemption choice
(§13's "lowest-priority Reservation-holder") is itself reproducible
across repeated runs of the identical scenario.

### 16.7 Property Testing

Invariant-based, not example-based, covering: "a Task is never a member
of more than one queue" (§6.3), "dispatch never exceeds concurrency
ceilings" (§7.1), "priority ordering is never inverted by aging beyond
§5.4's bound," and "every terminal-state Task's transition history is a
valid path through §4.1's state machine" — generated randomized Task/
event sequences checked against these invariants directly, the Scheduler
analog of RFC-0002 §17.4's "silent acceptance of malformed input is the
real target" fuzzing philosophy, applied here as "silent violation of a
scheduling invariant is the real target."

## 17. Alternatives Considered

| Alternative | Why not chosen |
|---|---|
| **Plain FIFO** | No dependency-awareness at all — would dispatch Tasks whose dependencies aren't satisfied, violating the single hardest requirement (§5.1) this design treats as non-negotiable. Rejected outright, not a close call. |
| **Round Robin** | Ignores both priority and dependency structure; would need to be layered under a dependency-awareness mechanism regardless, at which point it's not meaningfully simpler than what's chosen — and provides no path to critical-path optimization (§5.6), which matters for makespan on a DAG-shaped workload specifically (round robin is designed for workloads without inter-task dependencies, the opposite of this Scheduler's actual input shape). |
| **Plain priority queue (no dependency layer)** | Same core gap as FIFO — priority without dependency-awareness would dispatch a `critical` Task whose dependencies aren't met ahead of a `low` Task that's actually ready, which is not just suboptimal but incorrect (RFC-0001's DAG structure exists specifically to prevent out-of-order execution; a scheduler that ignores it defeats that purpose). |
| **Actor-model scheduling** (each Task an independent actor, self-scheduling via message passing, no central Scheduler Loop) | Attractive for the "parallel-first" requirement, but directly conflicts with the reproducibility requirement (§5.6/§16.5): actor-model scheduling's execution order is inherently a function of message-delivery timing, which is exactly the non-determinism this design is required to eliminate. A centralized-decision, distributed-execution hybrid (which is what §3's architecture actually is — one decision-making Loop, arbitrarily many Workers) achieves the parallelism goal without inheriting message-timing-dependent ordering. |
| **Fully centralized scheduler (single global instance, no partitioning)** | Simplest to reason about and reproducible by construction — genuinely the right choice at current scale (§14.1's "no concrete requirement yet" framing) — but named separately from the chosen design because the chosen design *is* this alternative with §14's extension points added, not a different architecture; listed here to make explicit that centralization is the *default*, and distribution is opt-in via those extension points, not the other way around. |
| **Fully distributed scheduler (no single decision authority, consensus-based dispatch)** | Rejected as the *default* for the same premature-complexity reasoning applied throughout every RFC in this series (Design Principle #2) — no current AGY deployment target requires it, and it would trade away easy reproducibility testing (§16.5) for a scaling property not yet needed. The extension points in §14 exist so this remains reachable later without redesign, per the explicit design constraint, without building it now. |
| **Purely event-driven scheduler (no discrete Scheduling Cycles, react-to-every-event immediately)** | Considered for its lower theoretical latency floor versus §3.9's cycle-batched loop — rejected because discrete cycles are what make §16.5's determinism testing tractable: a cycle is a clean unit of "given this exact input set, produce this exact output," whereas a purely reactive design's output would depend on the precise interleaving of arbitrarily-timed events, reintroducing the same non-determinism actor-model scheduling was rejected for. The chosen design keeps the *external* interface event-driven (§15.1's wake-on-signal, not fixed-interval polling — avoiding pure polling's latency/wastefulness) while keeping the *internal* decision-making cycle-batched and deterministic — capturing the latency benefit of event-driven wakeup without the determinism cost of fully event-driven decision-making. |
| **Hybrid scheduler (chosen design)** | Dependency-DAG-aware (via Kahn's-algorithm-style incremental readiness, §5.1–5.2) + priority-ordered with bounded fairness (§5.3–5.4) + critical-path-aware tie-breaking (§5.6) + cycle-batched-but-event-woken execution model (§3.9, §15.1) + centralized-by-default with named distributed extension points (§14). Each piece was added because a simpler alternative failed a specific stated hard requirement (dependency-awareness, fairness, reproducibility, parallelism, or the explicit distributed-without-redesign constraint) — not combined speculatively. |

## 18. Critical Review

### 18.1 Weaknesses in This Design

1. **The Reservation/Lease optimistic-hold-window mechanism (§8.2) has no
   specified behavior for what happens to Tasks that repeatedly lose the
   race for a reservation within their hold window under sustained
   contention** — in principle, a Task could be granted a Reservation,
   fail to be dispatched before it expires, and re-enter the Ready Queue
   only to lose the race again indefinitely if higher-priority Tasks
   continuously consume the Dispatcher's attention first. §5.4's aging
   mechanism mitigates this for *priority-based* starvation but was not
   explicitly designed against this specific *reservation-expiry* pattern
   — flagged as a real gap, not resolved here, because closing it properly
   likely requires either extending the hold window (with its own
   tradeoffs against §8.2's stated reasoning) or a dedicated reservation-
   starvation counter analogous to §5.4's — deferred pending evidence this
   actually occurs in practice rather than designed speculatively now.

2. **§7.7's coarse-grained single-write-path locking**, justified as
   sufficient at current scale, is the same category of tradeoff RFC-0002
   §4.5 made and RFC-0002 §21.1 flagged as revisitable — named here again
   because the Scheduler's write frequency (every Scheduling Cycle, every
   completion signal) is plausibly higher-frequency than the Registry's
   (boot-time and hot-reload only), making this a *more* likely bottleneck
   here than in RFC-0002, not less. This should be an early target for
   real-world contention measurement, not a "revisit eventually" item.

3. **The distributed extension points in §14 are, by their own framing
   (§14.1), extension points and not a validated design** — nothing in
   this RFC has been tested against an actual multi-instance deployment.
   The claim "supports distributed execution without redesign" is
   currently a design *intent* backed by the abstraction choices in §3
   (no assumed single-process memory), not a demonstrated property.

### 18.2 Scalability Limits

The single-write-path contention point (§7.7, §15.4, §18.1 item 2) is the
most concrete, near-term scalability limit — everything else in this
design (queue sizes bounded by backpressure, plan sizes bounded by
RFC-0001's typical output, deadlock checks bounded by in-flight
reservation count) scales with *plan* size, which RFC-0001 §12 already
characterizes as typically small. The write-path bottleneck scales with
*event rate* (completions, heartbeats, dispatches per second), which is a
genuinely different scaling axis this RFC has not load-tested.

### 18.3 Future Improvements

Reservation-starvation counter (§18.1 item 1); fine-grained or lock-free
write path if contention measurement justifies it (§18.1 item 2); a real
multi-instance validation of §14's extension points before any production
distributed deployment relies on them (§18.1 item 3).

### 18.4 Potential Simplifications

§5.5's work-stealing mechanism is the one piece of this design that adds
real implementation complexity for a benefit (better utilization across
heterogeneous pools under uneven load) that has not been shown necessary
at current scale — a candidate for deferral to future work if initial
implementation prioritizes simplicity, with §7.5's pool abstraction alone
(without stealing) as a simpler interim: idle Workers in a pool with no
Ready work for their pool simply stay idle, accepting some utilization
loss in exchange for materially less mechanism, revisited if that loss
proves significant in practice.

### 18.5 Open Questions

- Should `MODIFIED`'s `budgetCeiling` (§9.2) be re-checked by the
  Resource Coordinator on every heartbeat during `RUNNING`, or only at
  reservation time? This RFC currently specifies only reservation-time
  application — mid-execution ceiling enforcement would require the
  Execution Runtime's completion/heartbeat contract (§11) to report
  running-total usage, which §11.5's heartbeat contract does not
  currently include as a field. Left open pending RFC-0004.
- What is the correct default for Completed Queue retention (§15.2)
  before archival, and does that belong in this RFC's configuration
  surface or a separate Observation Engine concern (named in
  `AGY_HANDOFF.md`'s architecture list, not yet designed)? Left open.

## 19. Dependency Analysis: What Blocks the Architecture Most

The instruction for this section is to identify the next subsystem by
dependency analysis, not implementation convenience — so the method
matters as much as the conclusion.

### 19.1 Method

For each remaining undesigned Kernel component named in
`AGY_HANDOFF.md`'s architecture list (Runtime/Executor, Artifact
Registry, Observation Engine, Resource Manager, Learning Engine, Plugin
System) and this RFC's own open items, the question asked is: **which
of this RFC's own sections are currently written as a required contract
against something that does not yet exist, versus which are merely
naming a future nice-to-have?** A section written as "this RFC requires
X" is a hard block; a section written as "future work would benefit from
Y" is not.

### 19.2 Findings

| Section | What it requires | Currently exists? |
|---|---|---|
| §11 (entire section) | A dispatch/completion/failure/cancellation/heartbeat contract from an Execution Runtime | **No** — explicitly flagged in §0 and restated at the top of §11 |
| §10.2 | Something that owns `RuntimeState` mutation on the Scheduler's behalf | Partially named (`AGY_HANDOFF.md` implies Kernel-level state ownership) but not designed as its own subsystem |
| §7.2, §10.3 | An Artifact Registry to own artifact payloads and existence bookkeeping | **No** — named in `AGY_HANDOFF.md`'s open questions, not designed |
| §7.6, §14.4 | A Resource Manager to own Worker provisioning/scaling decisions | **No** — named, not designed |
| §12 | A Checkpoint Manager (referenced in the original AGY vision's Kernel component list) to own checkpoint persistence beyond what this RFC specifies as the Scheduler's own responsibility | Partially self-contained (§12 designs the Scheduler's own checkpoint contract directly, following RFC-0001 §4's precedent of not over-depending on this) |

Every one of these gaps traces back to the same root: **this RFC cannot
be implemented as written without something on the other side of §11's
contract.** The Artifact Registry gap (§7.2/§10.3) and Resource Manager
gap (§7.6/§14.4) are real, but this RFC explicitly designed around them —
narrowing its own read/write surface specifically so it does not need
those subsystems to exist yet (§10.3's artifact-ownership boundary,
§7.6's "Scheduler reacts to capacity changes, does not decide them," are
both instances of deliberately not blocking on those gaps). §11 has no
equivalent workaround: a Scheduler that decides "what executes, when, and
where" is not implementable if nothing on the other end of that decision
can actually execute anything.

### 19.3 Conclusion

**Execution Runtime is the subsystem whose absence blocks the
architecture most**, by direct dependency count (§11's entire contract
surface) and by the structural argument in §19.2 (every other named gap
was designed around; this one was not, and could not be, without the
Scheduler ceasing to have a purpose). This is not a novel conclusion —
it is what `AGY_HANDOFF.md` already stated as the next RFC before this
assignment's numbering (RFC-0007) implied otherwise (§0). The dependency
analysis performed here independently confirms the handoff document's
original sequencing rather than overriding it.

**Recommendation**: the next RFC should be Execution Runtime (whatever
its correct number turns out to be once the RFC-0004–0006 discrepancy
noted in §0 is resolved by whoever maintains the canonical sequence),
scoped specifically to satisfy §11's contract as its primary deliverable,
with node lifecycle, retries, checkpoints, cancellation, streaming,
concurrency, artifact passing, and rollback — `AGY_HANDOFF.md`'s own
originally-stated goals for it — evaluated against whether they satisfy
§11's dispatch/completion/failure/cancellation/heartbeat contract
specifically, not designed independently of it.
