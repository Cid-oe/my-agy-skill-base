# Amendment RFC-0014-A1 — Learning Engine: model-routing correction & renumbering

**Target:** RFC-0014 (Learning Engine) · **Status:** Proposed · **Severity:** Minor

## Problem

1. §6.3.6 states model-routing weights are "consumed by RFC-0008 and/or
   RFC-0009 (the model routing subsystems, whose specific architecture is
   treated as accepted and immutable)" — both assumptions are false
   (RFC-0008 is the Executor; RFC-0009 is retired).
2. §19's amendment demands on RFC-0001/0002/0003/0011/0012 needed a single
   acknowledgment point.
3. §21 suggestions collide with the reserved block (RFC-0016–0019).

## Reason

Same blind-generation substrate guess as RFC-0010's; the Learning Engine's
*domain* is unaffected — only the consumer of one parameter domain changes.

## Impact

One parameter-domain consumer re-pointed; dependency acknowledgments;
renumbering.

## Resolution

**R1 — Model routing weights.** The Model Routing Weight domain's consumer
is the **`model-router` skill** (interim: weights applied via the Parameter
Store read at routing time) and, once chartered, **RFC-0018 (Model Registry
& Router)**. The zero-floor rule (§6.3.6: never weight-rank the only
available model to 0) carries over verbatim to whichever consumer reads the
weights. RFC-0008/0009 references are void.

**R2 — Dependencies acknowledged.** RFC-0001 skill-ranking read path,
RFC-0011 parameter reload, RFC-0012 routing-weight scoring, RFC-0003
`learning.*` attributes — all granted by RFC-0001-A1 (compat), RFC-0011-A1
R5, RFC-0012-A1 R2, and RFC-0003-A1 R1 respectively. The Parameter Store
(RFC-0014 §6.5) is confirmed as the single owner of learned-parameter
state.

**R3 — Renumbering.** Cross-Tenant Learning Federation, Learning Governance
Audit Interface, Parameter Interaction Modeling, Synthetic Workloads,
Explainability → unassigned pool (RFC-0000 §8).

## Compatibility / Migration

None beyond reference updates.
