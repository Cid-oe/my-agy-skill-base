# Amendment RFC-0004-A1 — Artifact System: namespaces, event payloads, traversal bounds

**Target:** RFC-0004 (Artifact System) · **Status:** Proposed · **Severity:** Major

## Problem

1. RFC-0008 §11.2 allocates one namespace per Execution and asks whether the
   Store can tolerate that cardinality (its §19.2); RFC-0004 has no namespace
   concept.
2. RFC-0006 §14.1 asks RFC-0004 to adopt formal event payload schemas; event
   names used by later RFCs (`artifact.deleted`) differ from RFC-0004 §10's
   vocabulary (`ArtifactDeleted`).
3. RFC-0004 §17.7 self-identifies `maxDepth` being optional on
   `ancestorsOf`/`descendantsOf` as a fail-closed-posture violation.
4. RFC-0010 §11.5 / RFC-0012 §11 ask for an access-control hook; RFC-0004
   §11.5 flags that no `callerContext` exists on `get()`.

## Reason

All four are acknowledged gaps in RFC-0004's own text or explicit requests
from consumers. Each has a minimal additive resolution.

## Impact

Envelope gains one optional field; query API gains a mandatory parameter
(breaking only against a never-implemented signature — acceptable pre-
implementation); event vocabulary is normalized via alias table, not renamed.

## Resolution

**R1 — Envelope namespace.** `Artifact` gains
`namespace: string | null` (default null). Namespaces are opaque,
hierarchical strings (`exec/{executionId}` recommended for per-execution
scopes). To bound cardinality, implementations MAY bucket:
`namespace = "exec/" + (H(executionId) % B)` — isolation strength is
preserved for collision-free hashing with B ≥ 1024; this answers RFC-0008
§19.2 with "bucketed namespaces are conformant."

**R2 — Event payload schemas & naming.** Canonical event names follow
RFC-0006-A1's grammar (`<domain>.<object>.<verb>`): RFC-0004 §10's table
maps as `ArtifactCreated → artifact.artifact.created`,
`ArtifactDeleted → artifact.artifact.deleted`,
`ArtifactArchived → artifact.artifact.archived`,
`ArtifactSuperseded → artifact.artifact.superseded`,
`ArtifactReferenced → artifact.artifact.referenced`,
`ArtifactRejected → artifact.artifact.rejected`. Payload field shapes are as
in §10 (formal JSON Schemas to live in `schemas/events/artifact/`); payload
ownership: **the subsystem that owns the fact owns the payload schema**
(RFC-0004 for artifact events), registered per RFC-0006-A1. Downstream
references to `artifact.deleted`/`artifact.expired` resolve to the deleted/
archived+retention-expiry events respectively (RFC-0010 §19.1 and RFC-0012
§19.3 are satisfied by the deleted event; retention-expiry reuses the
deleted path with a reason field).

**R3 — Mandatory `maxDepth`.** `ancestorsOf`/`descendantsOf` require
`maxDepth` (integer ≥ 1). No unbounded default. Applies RFC-0004 §17.7.

**R4 — Read-time access-control hook.** `get`/`getStreaming`/`query` accept
optional `caller: CallerContext | null`. When present, the Store consults
the Policy Engine (RFC-0003-A1 R4 `DecisionRequest`, action
`artifact.read`) before returning; when absent, behavior is unchanged
(trusted in-process callers). This lands the hook RFC-0004 §11.5 said was
missing; enforcement semantics remain RFC-0003's.

## Compatibility

R1–R2 additive. R3 is a signature change to an unimplemented interface —
recorded as such, no migration needed pre-implementation. R4 optional
parameter.

## Migration

None for stored artifacts (namespace defaults null). Event consumers built
against §10's CamelCase names keep working via the alias table until schemas
land, at which point `schemas/events/` is authoritative.
