# Amendment RFC-0003-A1 — Policy Engine: attributes, contexts, obligations, snapshots

**Target:** RFC-0003 (Policy Engine) · **Status:** Proposed · **Severity:** Major

## Problem

Five downstream RFCs call the Policy Engine through interfaces it does not
define, each acknowledged by them as a required amendment that was never
written:

1. Attribute namespaces — `memory.*` (RFC-0010 §19.5), `tool.*` (RFC-0012
   §19.2), `reflection.*` (RFC-0013 §19.6), `learning.*` (RFC-0014 §19.5).
2. Evaluation contexts — `PLAN_TIME` (RFC-0011 §19.3), `TOOL_INVOCATION`
   (RFC-0012 §19.2).
3. Obligations and a principal-scoped request shape — RFC-0008 §4.3 assumes
   `permit/deny/obligate` with `obligations[]`.
4. Policy snapshot/version identifiers pinnable per execution — RFC-0008
   §19.1 ("without it, determinism across policy changes is unattainable").
5. Prefix matching for hierarchical names — RFC-0012 §20.4.

## Reason

RFC-0003's five-outcome model and closed `IPolicyContext` are sound and are
the canonical decision vocabulary; the forks are additive omissions, not
conflicts. This amendment is the single place they get one consistent answer.

## Impact

`PolicyDecision` gains an optional field; `IPolicyContext` gains optional
attributes and a context tag; the registry gains a snapshot identifier. No
outcome enum changes; no existing policy invalid.

## Resolution

**R1 — Extensible attribute namespace.** `IPolicyContext` gains
`attributes: Map<string, JSONValue>` (default empty). Subsystem-owned
namespaces (`memory.*`, `tool.*`, `reflection.*`, `learning.*`,
`sandbox.*`) are registered with the Policy framework at subsystem boot and
validated as *known-tag warnings* on unknown keys — mirroring RFC-0002's
soft-known-set philosophy. Built-in policies read attributes through the
same declared-field mechanism as §9.4.

**R2 — Evaluation context.** `IPolicyContext` gains
`evaluationContext: RUNTIME | PLAN_TIME | TOOL_INVOCATION | MEMORY_OP |
REFLECTION_OP | LEARNING_OP` (default `RUNTIME`). Policies declare which
contexts they apply to (coarse filter alongside `appliesToKinds`). Per
RFC-0011 §19.3: a `PLAN_TIME` PERMIT MAY be recorded as CONDITIONAL by the
caller and re-checked at dispatch; the Policy Engine itself never conflates
contexts.

**R3 — Obligations.** `PolicyDecision` gains
`obligations: Obligation[]` (default `[]`), where `Obligation = { kind:
string (namespace-registered), params: JSONValue }`. Mapping for RFC-0008's
dialect: `permit` → `ALLOW` (+ obligations if present); `deny` → `DENY`;
`obligate` → `MODIFIED` when the obligation constrains the node (budget,
redaction-as-modification) else `ALLOW` + obligations. The five-outcome enum
is unchanged and remains canonical.

**R4 — Principal-scoped requests & snapshot pinning.** Add overload
`evaluate(request: DecisionRequest): Promise<PolicyDecision>` where
`DecisionRequest = { targetKind, node|plan, principal: PrincipalRef (opaque
until RFC-0017), policyVersion?: PolicySetVersionId }`. A
`PolicySetVersionId` identifies an immutable snapshot of the registered
policy set; `evaluateNode/evaluatePlan/evaluateContinuous` accept an optional
`policyVersion` and default to latest. Snapshots satisfy RFC-0008 §4.3 rule 1
(pin at admission) without altering evaluation semantics.

**R5 — Prefix matching.** For any attribute whose value is a hierarchical
dot-name (e.g. `tool.capability_name`), policy rules MAY be written with a
prefix wildcard (`code.execute.*`). Matching is longest-prefix; a bare name
never matches a more specific actual value unless a `.*` rule covers it.
Default remains exact-match (fail-closed) — prefix matching is opt-in per
rule, closing RFC-0012 §20.4 without silently broadening any existing grant.

## Compatibility

All additions optional with defaults; existing decisions byte-identical.
RFC-0008's PEP cache key `(policyVersion, decisionKey)` is directly
expressible (R4).

## Migration

Subsystems that hand-built request shapes (RFC-0008 Appendix A, RFC-0010
`MemoryPolicyRequest`, RFC-0011 Policy Gate, RFC-0012 Policy Gate) migrate to
`DecisionRequest` at implementation time; no RFC body changes required in
those documents beyond their own amendments' cross-reference updates.
