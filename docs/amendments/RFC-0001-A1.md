# Amendment RFC-0001-A1 — Skill Resolver: Planner layering & escalation semantics

**Target:** RFC-0001 (Skill Resolver) · **Status:** Proposed · **Severity:** Major

## Problem

1. RFC-0001 and RFC-0011 (Planner) both produce the DAG the Scheduler runs,
   with different schemas (`ExecutionPlan`/`PlanNode` vs
   `ExecutionGraph`/`ExecutionNode`) and different selection models. RFC-0011
   §4.1 says "RFC-0001 is invoked by the Scheduler"; RFC-0007 §1.4 says the
   Scheduler consumes RFC-0001's plan directly. Planning authority is forked.
2. Two skills (`caveman → ponytail`, `caveman-review → ponytail-review`)
   declare an `escalateTo` target that is an `exclusiveWith` partner.
   RFC-0001 §8.3 (`satisfiesExclusion` checks every committed skill) makes
   the precomputed `fallbackChain` behavior on this pattern undefined.

## Reason

RFC-0011 postdates RFC-0001 and was written against a different assumed
corpus. Both subsystems are sound; only their seam is undefined. The
escalation gap is a missing rule, not a design error — escalation means
*replacement*, which exclusivity must not block.

## Impact

Resolver's contract gains one input kind; no algorithm change. Planner's
output gains a defined consumer. All existing `escalateTo`/`exclusiveWith`
declarations in the skill pack become valid without edits.

## Resolution

**R1 — Layering.** Canonical pipeline: **Planner (RFC-0011) → Resolver
(RFC-0001) → Policy (RFC-0003) → Scheduler (RFC-0007)**. The Planner owns
*task decomposition* (Goal → `ExecutionGraph`, a task-level DAG with
`skill_type` annotations). The Resolver owns *skill selection*: it accepts
`ExecutionGraph` nodes (or raw requests) as `Goal` inputs (`kind:
"raw_request" | "task"`) and produces the `ExecutionPlan` of concrete skill
invocations. The Scheduler's input remains, exclusively, the RFC-0001
`ExecutionPlan`. (Restated from the Planner side in RFC-0011-A1.)

**R2 — Dependency correction.** RFC-0001's declared dependency on "Repository
Map, Context Manager" is reduced to what it always was in substance: those
are **skills** (data sources via RuntimeState), not subsystems. Declared
upstream dependencies become: RFC-0002 (runtime), RFC-0005 (type reference:
`RuntimeState`), RFC-0004 (type reference: `ArtifactType`/`ArtifactRef`).

**R3 — Escalation supersedes exclusivity.** Add to §10 (Recovery): when a
node fails or falls below `confidenceThreshold` and `reresolve()` walks the
`fallbackChain`, the failed node's assignment is vacated **before** the
fallback candidate is constraint-checked; therefore a candidate that is
`exclusiveWith` the *failed* skill is eligible to replace it. Exclusions
still bind against all *other* concurrently assigned skills. Consequently an
`escalateTo` target MAY be an `exclusiveWith` partner; the manifest validator
shall not reject this combination (adjusts RFC-0002 §3.2 validation note).

**R4 — Duplicate producers.** When multiple skills produce the same
`ArtifactType`, candidate selection is governed solely by RFC-0001's
slot/exclusivity model. The "last writer wins" rule of RFC-0011 §11.2 applies
only to *task-level* outputs within the Planner's own decomposition, never to
skill assignment (see RFC-0011-A1 R3).

## Compatibility

Fully backward-compatible: `resolve()` signature unchanged; `Goal.kind`
gains one enum value; `ExecutionPlan` schema unchanged.

## Migration

Implementers targeting RFC-0001 alone need no change. Kernel orchestration
(RFC-0007-A1 R4) wires Planner output into Resolver input; until RFC-0011 is
implemented, `kind: "raw_request"` remains the only exercised path.
