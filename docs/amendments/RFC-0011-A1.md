# Amendment RFC-0011-A1 — Planner: task-level graph, one plan contract

**Target:** RFC-0011 (Planner) · **Status:** Proposed · **Severity:** Major

## Problem

1. RFC-0011's `ExecutionGraph` competes with RFC-0001's `ExecutionPlan` as
   the Scheduler's input. §4.1 says "the Scheduler dispatches a Task, it
   invokes RFC-0001"; the published RFC-0007 §1.4 consumes RFC-0001's plan
   directly and never mentions the Planner. §19.1 itself requires the two
   schemas be reconciled before either is Accepted.
2. §11.2 resolves two tasks producing the same artifact type by "last
   writer (decomposition order)" — contradicting RFC-0001's exclusivity/
   slot model for the same situation.
3. §4/RFC-0002 interplay: Methods live in the Skill Registry, which has no
   `methods` field (granted by RFC-0002-A1 R1).

## Reason

The Planner's HTN decomposition is sound and fills a real gap (abstract-goal
decomposition) RFC-0001 deliberately left to "task-decomposer"-style skills.
The fork is a layering ambiguity, resolvable without touching either
algorithm: Planner = *what work*, Resolver = *which skills*, Scheduler =
*when/where*. (Jointly with RFC-0001-A1 R1.)

## Impact

`ExecutionGraph` is re-scoped as the Planner-owned task-level DAG consumed
by the Resolver — not by the Scheduler. One conflict rule changes. Methods
storage is cross-referenced.

## Resolution

**R1 — Layering & naming.** Canonical chain: Planner produces the
**`ExecutionGraph`** (task-level DAG: `skill_type` annotations, scheduling
hints, decomposition tree, plan artifact). The **Resolver (RFC-0001)
consumes ExecutionGraph nodes as Goals** and produces the
**`ExecutionPlan`** (skill-level DAG: concrete skills, fallback chains) —
this, and only this, is the Scheduler's input. "ExecutionGraph" and
"ExecutionPlan" are distinct, individually-owned contracts (see Ownership
Matrix); the Scheduler-facing joint contract demanded by §19.1 is thereby
closed: RFC-0001's `ExecutionPlan`, unchanged.

**R2 — §4.1 correction.** "The Scheduler invokes RFC-0001" is corrected to:
the kernel orchestration invokes the Resolver on the ExecutionGraph before
scheduling (per RFC-0001-A1 R1). The Planner itself never invokes the
Resolver, and the Scheduler never does.

**R3 — Duplicate producers.** Delete the last-writer rule: when the
Dependency Detector finds two primitive tasks producing the same artifact
type, it emits a **producer-group annotation** on the graph; the Resolver's
slot/exclusivity constraint solving (RFC-0001 §5, §8.3) decides actual
assignment. The Planner never resolves producer conflicts.

**R4 — Methods storage.** Methods are stored/validated/indexed per
RFC-0002-A1 R1; RFC-0011 §9.5's `Method` shape is the schema of record.
Recursive-method registration checks (§13.3) execute in the Registry at
registration time.

**R5 — Future-RFC renumbering.** §21 suggestions map into the RFC-0000
registry: Execution Monitor → unassigned pool; Method Governance →
unassigned pool; Plan Approval → folds under RFC-0021 (Escalation & HITL);
Confidence Calibration consumption is already in-RFC via RFC-0014 (its
§19.2 dependency is satisfied by RFC-0014 as published + RFC-0014-A1).

## Compatibility

`ExecutionGraph` schema unchanged; only its consumer changes. Plan Artifact
contents unchanged.

## Migration

Until the Planner is implemented, the Resolver's `kind: "raw_request"` path
(plus task-decomposer-style skills) serves alone, exactly as RFC-0001
always specified.
